### Issue M1-44: [project-store] listeAusgaben implementieren

## Ziel (in einem Satz)
Der `project-store` liefert den **Ist-Bestand** des Ausgabeordners eines Projekts – Dateiname, Größe
und Änderungszeitpunkt jeder fertigen MP4 –, damit die Oberfläche die Ausgabe-Liste (FA-22) zeigen
und der Export daraus eine Datei auswählen kann.

## Modul & Datei
- Modul: `project-store` [D1] (Main)
- Datei: `src/main/project-store/ausgaben.ts`
- Vertrag: Technisches Konzept **9.5.2** (Abschnitt „Ausgabedateien (FA-22)", neu in TK v2.4),
  **9.5.7** (Pfad-Autorität) – Quelle der Wahrheit
- Prozess/Speicher: liest **ausschließlich** den Ausgabeordner `projects/<id>/output/`.
  **Kein** Zugriff auf `project.json` (D1), **kein** Zugriff auf Q3 (`protokoll.json`), **kein**
  D1-Schreib-Lock.

## Warum das im Gesamtsystem wichtig ist
Zwei Funktionen des Systems haben ohne diese Operation **überhaupt keine Datenquelle**: die
Ausgabe-Liste der Oberfläche (FA-22 – dort stehen Datum und Uhrzeit eines Renders, nicht im
Dateinamen) und die Dateiauswahl beim Export (`ExportRequest.dateiname`, TK 9.6.1). Genau deshalb
wurde sie in TK v2.4 nachgetragen.

Drei lokale Entscheidungen sind hier teuer. **Erstens die Quelle:** Wer die Liste aus dem Protokoll
Q3 baut statt aus dem Ordner, zeigt Dateien an, die längst gelöscht wurden, und verschweigt
Dateien, die jemand von Hand hineinkopiert hat – der Export scheiterte dann an einer Datei, die die
Oberfläche eben noch angeboten hat. **Zweitens die Filterung:** Rutscht eine Arbeitsdatei
(`.part`, Temporäres) in die Liste, bietet die Oberfläche eine **halb geschriebene** Datei zum
Export auf den USB-Stick an – auf dem Fernseher wäre das ein Video, das mitten im Abspielen
abbricht. **Drittens die Pfad-Autorität:** Wer den Ordnerpfad selbst zusammensetzt, statt ihn über
#49 aufzulösen, ist die zweite Stelle im System, die das Ordner-Layout kennt – und bei der nächsten
Layout-Änderung läuft eine davon leer.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/project-store/ausgaben.ts
export interface AusgabeDatei {
  dateiname: string       // MIT Endung, z. B. "sommeraktion.mp4"
  dateigroesse: number    // Bytes
  geaendertAm: string     // ISO-8601 UTC – zugleich der Renderzeitpunkt
}

export async function listeAusgaben(
  projektId: string,
): Promise<Ergebnis<AusgabeDatei[], ProjectStoreFehlercode>>
// - liest NUR den Ordner ausgabeOrdner(projektId) (#49); kein project.json, kein Q3
// - KEIN mitD1Lock: diese Operation fasst project.json nicht an (TK 9.5.2)
// - Sortierung: absteigend nach geaendertAm (neueste zuerst)
// - fehlender Ordner => leere Liste, KEIN Fehler
```

`ProjectStoreFehlercode` ist die Fehlercode-Union des Moduls `project-store`. Sie wird **nicht** hier
angelegt, sondern von **M1-41** in `src/main/project-store/assets.ts` deklariert und von dort
importiert:

```ts
// import { ProjectStoreFehlercode } from './assets'   (deklariert in M1-41, NICHT hier)
export type ProjectStoreFehlercode = 'speicher_fehler'
```

Begründung: `ergebnis.ts` (#12/#22) liefert ausschließlich die generischen Codes, und #22 legt fest,
dass **jedes Modul seine eigene Fehlercode-Union in seiner eigenen Datei** deklariert – für den
`project-store` ist das `assets.ts`. Dass TK 9.5.2 die Operation als `Ergebnis<AusgabeDatei[]>`
notiert, ist kein Widerspruch: Die TK-Schreibweise nennt die **Nutzlast**; der zweite Typparameter
ist die Fehlercode-Seite derselben Hülle.

**Fremde Funktionen, die du aufrufst** (der umsetzende Agent sieht die anderen Issues nicht – hier
stehen sie vollständig):

```ts
// #49 – src/main/project-store/pfade.ts (Pfad-Autorität; reine String-Operationen, kein fs)
export function ausgabeOrdner(projektId: string): string

// (aus derselben Datei, hier NICHT benötigt, nur zur Abgrenzung:)

// #12/#22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
// `daten` ist optional und je Fehlercode typisiert (TK 9.1.1, „Strukturierte Fehlerdaten"). Das TK
// nennt den Platzhalter `Fehlerdaten`; in `ergebnis.ts` steht `unknown` (#12) – die Form wird dort
// zugesichert, wo der Code vergeben wird. Diese Funktion vergibt KEINEN Code mit Zusatzdaten – das

```

**Wer ruft dich auf:** die Oberfläche über den IPC-Kanal `project:listeAusgaben` (wird in M1-45
verdrahtet) und main-intern der `export-service` (M6) für die Dateiauswahl.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projektId` | Projekt, dessen Ausgabeordner gelesen wird | nicht leerer String; wird **unverändert** an `ausgabeOrdner` (#49) gegeben – **keine** eigene Pfadbildung. **Wichtig, damit du dich nicht auf eine Prüfung verlässt, die es nicht gibt:** `ausgabeOrdner` ist laut #49 eine „reine String-Operation, kein Dateisystemzugriff" und prüft die `projektId` **nicht** – sie wird dort nur als Pfadsegment eingesetzt (anders als bei `loeseAssetPfad`/`loeseAusgabePfad`, die ihr zweites Argument sehr wohl prüfen). Die Form- und Traversal-Prüfung der `projektId` findet deshalb **am IPC-Kanal** `project:listeAusgaben` statt (M1-45: nicht leer, UUID-Form, keine Pfadtrenner, kein `..`); main-interne Aufrufer (der `export-service`) übergeben ohnehin die ID des geladenen Projekts. Hier bleibt es bei der Formprüfung „nicht leerer String" |

Ausgang bei Erfolg: `Ergebnis<AusgabeDatei[]>` – ein Array, absteigend nach `geaendertAm` sortiert.
Existiert der Ordner nicht, ist das Array **leer** und `ok: true`.
Ausgang bei Fehler: Codes `ungueltige_eingabe` (leere/ungültige `projektId`) und `speicher_fehler`
(Ordner vorhanden, aber nicht lesbar – s. Fehlerpfade). Geschlossener Satz.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operation und ihr Datensatz, wörtlich (TK 9.5.2):
  ```
  | `listeAusgaben` | `projektId` → `Ergebnis<AusgabeDatei[]>` – Inhalt von `projects/<id>/output/`, absteigend nach `geaendertAm` |

  AusgabeDatei {
    dateiname:    string   // MIT Endung, z. B. "sommeraktion.mp4"
    dateigroesse: number   // Bytes
    geaendertAm:  string   // ISO-8601 UTC – zugleich der Renderzeitpunkt (die Datei entsteht atomar, 9.2.6)
  }
  ```
- „**`geaendertAm` ist der Renderzeitpunkt, nicht das Protokoll.** Weil die fertige Datei in
  **einem** Schritt in den Ausgabeordner gebracht wird (Rename-mit-Ersetzen, 9.2.6), ist ihr
  Änderungsdatum genau der Zeitpunkt des erfolgreichen Renders. **Q3 ist NICHT die Quelle dieser
  Liste** – Q3 ist Historie und Nachweis (auch der Fehlschläge), die Ausgabe-Liste zeigt den
  **Ist-Bestand** des Ordners." (TK 9.5.2)
- „**Abweichung von der Abschnittsüberschrift:** Diese Operation liest **nur** den Ausgabeordner;
  sie fasst `project.json` nicht an und läuft deshalb **ohne** das D1-Schreib-Lock." (TK 9.5.2)
- „Gelistet werden **ausschließlich fertige `.mp4`-Dateien**; Arbeitsdateien (`.part`, Temporäres)
  bleiben unsichtbar. Fehlt der Ordner (noch nie gerendert), ist das Ergebnis eine **leere Liste**,
  **kein** Fehler." (TK 9.5.2)
- „**Warum beim `project-store`:** Er ist die **Pfad-Autorität** (9.5.7) und löst
  `(projektId, ausgabeName)` ohnehin auf. Ein zweiter Ort, der das Ordner-Layout kennt, ist damit
  ausgeschlossen. Der Renderer bekommt **Dateinamen, nie absolute Pfade**." (TK 9.5.2) – deshalb
  enthält `AusgabeDatei` **keinen** Pfad, und der Ordnerpfad kommt ausschließlich aus
  `ausgabeOrdner` (#49).
- „**Wozu:** Sie speist die **Ausgabe-Liste** der Oberfläche (FA-22: „Datum und Uhrzeit stehen in
  der Ausgabe-Liste der Anwendung, **nicht** im Dateinamen") und die **Auswahl im Export**
  (`ExportRequest.dateiname`, 9.6.1). Ohne diese Operation gäbe es keine Quelle für beides."
  (TK 9.5.2)
- „Er löst ebenso `(projektId, ausgabeName) → projects/<id>/output/<name>.mp4` auf und **listet
  diesen Ordner** (`listeAusgaben`, 9.5.2)." (TK 9.5.7)

**ENTSCHIEDEN – die Auslegung der vier Detailfragen (lokale Entscheidungen, mit Begründung):**
1. **Was als „fertige `.mp4`" gilt:** genau die Einträge, die (a) reguläre **Dateien** sind
   (Unterordner und Symlinks werden übersprungen) und (b) deren Name auf `.mp4` endet, verglichen
   **ohne** Rücksicht auf Groß-/Kleinschreibung (`.MP4` zählt mit). Alles andere – `.part`, `.tmp`,
   `.mp4.part`, versteckte Dateien – wird ausgelassen. Begründung: Der Render legt die Datei atomar
   per Rename an; existiert der Name mit Endung `.mp4`, ist die Datei vollständig. Ein
   Größen-Mindestwert oder ein Blick in den Dateikopf wäre eine zweite, unzuverlässige Prüfung
   derselben Aussage.
2. **Zeitquelle:** die Änderungszeit des Dateisystems (`stat.mtime`), formatiert als ISO-8601 in
   **UTC** (`new Date(stat.mtimeMs).toISOString()`). **Nicht** `birthtime`/`ctime` – die sind
   plattformabhängig und werden vom Rename-mit-Ersetzen nicht verlässlich gesetzt; genau dieser
   Rename ist laut TK 9.5.2 der Renderzeitpunkt.
3. **Gleichstand beim Sortieren:** Haben zwei Dateien dieselbe `geaendertAm`, entscheidet der
   `dateiname` **aufsteigend**. Begründung: Ohne festen zweiten Schlüssel wäre die Reihenfolge
   plattform- und laufabhängig; die Liste springt dann bei jedem Aufruf, und Tests wären nicht
   reproduzierbar.
4. **Eine Datei, die zwischen `readdir` und `stat` verschwindet** (der Nutzer löscht sie im
   Explorer, während die Liste gebaut wird), wird **still ausgelassen** – kein Fehler für die ganze
   Liste. Begründung: Der Ordner ist kein exklusiv gehaltener Bereich; eine einzelne verschwundene
   Datei ist genau das, was die Liste danach zeigen soll (sie ist ja weg). Eine Fehlermeldung würde
   die Ausgabe-Liste komplett leer lassen, obwohl zehn andere Dateien vorhanden sind.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `projektId` leer oder kein String | `ungueltige_eingabe` | keine Liste, kein Dateizugriff |
| Ausgabeordner existiert nicht (`ENOENT`) | – (**kein** Fehler) | `ok: true` mit **leerer** Liste (TK 9.5.2) |
| Ordner existiert, ist aber nicht lesbar (`EACCES`/`EPERM`) oder das Lesen scheitert anderweitig | `speicher_fehler` | keine Liste; die Meldung nennt den **Ordner** (nicht den Stacktrace). Das ist der Code der Modul-Union `ProjectStoreFehlercode` (s. Signatur) – **nicht** `unbekannter_fehler`: Ein Zugriffsfehler auf den Datenbestand ist ein bekannter, benennbarer Fall, und `unbekannter_fehler` ist laut TK 9.1.1 Punkt 8 für **unerwartete Ausnahmen** reserviert, die das Gateway fängt |
| einzelne Datei zwischen `readdir` und `stat` verschwunden | – (**kein** Fehler) | dieser eine Eintrag entfällt, die übrigen werden geliefert |

Fehlercodes werden **nicht erfunden**: „Fehlercodes sind ein geschlossener, typisierter Satz: die
fachlichen je Operation (9.4.9, 9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`,
`nicht_gefunden`, `unbekannter_fehler`. Eine rohe Exception-Meldung wird nie zum Code."
(TK 9.1.1, Punkt 3)

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – Q3 ist nicht die Quelle.** Diese Funktion öffnet `protokoll.json` **nicht**, importiert
  nichts aus dem `auftrags-manager` und liest keine Render-Historie. TK 9.5.2 sagt dazu ausdrücklich
  „**Q3 ist NICHT die Quelle dieser Liste**". Wer es doch tut, zeigt gelöschte Dateien an und
  verschweigt vorhandene. (Q3 ist in v1 ohnehin **nur schreibend** vorgesehen.)
- **Verbot – kein D1-Zugriff, kein Lock.** Kein `project.json` lesen, kein `mitD1Lock`, kein
  `planeAutoSpeicherung`. Diese Operation ändert **nichts**. Ein Lock hier würde die Liste hinter
  laufenden Schreibvorgängen einreihen und die Oberfläche ohne Grund blockieren.
- **Verbot – keine eigene Pfadbildung.** Kein `path.join(datenOrt, 'projects', projektId,
  'output')` von Hand, kein Nachbauen des Layouts, kein Zusammensetzen absoluter Pfade für die
  Rückgabe. Der Ordner kommt aus `ausgabeOrdner(projektId)` (#49); `AusgabeDatei` enthält **nur**
  den Dateinamen, weil „Der Renderer bekommt **Dateinamen, nie absolute Pfade**" (TK 9.5.2).
- **Verbot – nicht aufräumen.** Diese Funktion löscht nichts, benennt nichts um und legt den Ordner
  **nicht** an, wenn er fehlt. Ein fehlender Ordner ist der Normalzustand eines Projekts, das noch
  nie gerendert wurde.
- **Verbot – keine Sortierumkehr, keine Begrenzung.** Keine Obergrenze für die Anzahl, kein
  Paging, kein Ausblenden „alter" Dateien. Die Liste zeigt den vollständigen Ist-Bestand; das
  Aufräumen ist Sache des Nutzers.
- **Verbot – `ProjectStoreFehlercode` nicht ein zweites Mal deklarieren.** Der Typ steht in
  `src/main/project-store/assets.ts` (M1-41) und wird von dort **importiert**. Lege keine eigene
  Union in `ausgaben.ts` an, kopiere die Zeile nicht, und erweitere die Union nicht um weitere
  Codes: Zwei Deklarationen desselben Namens laufen bei der nächsten Änderung auseinander, und
  `speicher_fehler` bedeutet dann in zwei Dateien Verschiedenes.

## Definition of Done
- [ ] Ein Ordner mit drei `.mp4`-Dateien liefert drei Einträge mit korrektem `dateiname` (mit
      Endung), `dateigroesse` in Bytes und `geaendertAm` als ISO-8601-UTC-String
- [ ] Die Reihenfolge ist absteigend nach `geaendertAm`; bei gleichem Zeitstempel entscheidet der
      `dateiname` aufsteigend (Test mit gesetzten Zeitstempeln)
- [ ] `.part`-, `.tmp`- und endungslose Dateien sowie Unterordner erscheinen **nicht** in der Liste
      (Test mit gemischtem Ordnerinhalt)
- [ ] `datei.MP4` (Großschreibung) erscheint in der Liste
- [ ] Ein nicht existierender Ausgabeordner liefert `{ ok: true, wert: [] }` – **kein** Fehler und
      **kein** neu angelegter Ordner (Test prüft auch, dass der Ordner danach nicht existiert)
- [ ] Ein leerer, aber vorhandener Ordner liefert ebenfalls eine leere Liste
- [ ] Die Datei ruft `mitD1Lock` nachweislich **nicht** auf und liest `project.json` nicht
      (Grep-Probe auf `mitD1Lock`, `project.json`, `protokoll`)
- [ ] Ein vorhandener, aber nicht lesbarer Ausgabeordner liefert `speicher_fehler` (nicht
      `unbekannter_fehler`); `ProjectStoreFehlercode` wird aus
      `src/main/project-store/assets.ts` **importiert** und in `ausgaben.ts` nicht neu deklariert
      (Grep-Probe auf `type ProjectStoreFehlercode`)
- [ ] Der Ordnerpfad stammt aus `ausgabeOrdner(projektId)` (Test mit Spy: genau ein Aufruf, kein
      selbst gebauter Pfad); kein `AusgabeDatei`-Feld enthält einen absoluten Pfad
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze)
- [ ] Keine Datei außerhalb von `src/main/project-store/ausgaben.ts` (+ zugehörige Testdatei) geändert
