### Issue M8-13: [marken-store] löscheMarke – blockierend löschen, eingebaute Marke unlöschbar

## Ziel (in einem Satz)
Eine Marke wird aus `marken.json` entfernt – aber **nur**, wenn sie **keine** Aktion und **keine**
abgeleitete Marke mehr trägt und **nicht** die eingebaute Fitnessworld24-Marke ist; andernfalls
scheitert das Löschen mit einem eigenen Code und, bei Referenz, mit **beiden** Trefferlisten.

## Modul & Datei
- Modul: `marken-store` [V2] (Main)
- Datei: `src/main/marken-store/loesche-marke.ts`
- Vertrag: Technisches Konzept **9.15.1** (Operationstabelle + Lösch-Invarianten – Quelle der
  Wahrheit), **9.1.1** (Ergebnis-Hülle, strukturierte Fehlerdaten)
- Prozess/Speicher: V2 (`marken.json`, app-weit). **Kein** direkter Dateizugriff – gelesen und
  geschrieben wird über M8-03, Projekte liest M8-12. **Kein** D1-Schreibzugriff, **kein** D1-Lock.

## Warum das im Gesamtsystem wichtig ist
Löschen ist die einzige Operation dieses Moduls, die Daten **unwiederbringlich** entfernt, und eine
Marke ist – anders als eine Vorlage – **doppelt** geteilt: Sie kann in beliebig vielen Projekten
Aktionen färben **und** die Grundlage beliebig vieler Saison-Looks sein. „**Löschen blockiert bei
Referenz**, es kaskadiert **nicht** – wie bei den Vorlagen (9.12.1). Eine Marke steckt in Aktionen
**und** möglicherweise in abgeleiteten Looks; eine Kaskade änderte das Aussehen vieler Aktionen auf
einen Schlag." (TK 9.15.1) Eine Kaskade, die beim Löschen einer Partner-Marke gleich alle Aktionen
löscht, die sie tragen, würde in fremden, gerade laufenden Projekten Werbung entfernen, ohne dass
der Nutzer das je angefragt hat.

Zweitens ist die eingebaute Marke **anders geschützt als bei den Vorlagen**: „**Die eingebaute Marke
ist nie löschbar** (`eingebaut: true`): Sie ist der Projekt-Standard und die Basis der abgeleiteten
Looks. **Bearbeitbar ist sie aber** – anders als die eingebauten Vorlagen, die eingefroren sind."
(TK 9.15.1) Diese Sperre trägt einen **eigenen** Fehlercode (`marke_eingebaut`), nicht den
wiederverwendeten `ungueltige_eingabe` des `vorlagen-store` – TK 9.15.5 führt ihn als **eigenen
Eintrag** im geschlossenen Fehlercode-Satz.

```ts
export interface MarkenReferenz { projektId: string; projektName: string; aktionId: string }
export interface AbgeleiteteMarkenReferenz { markeId: string; markeName: string }
export interface Markennutzung {
  aktionen:          MarkenReferenz[]
  abgeleiteteMarken: AbgeleiteteMarkenReferenz[]
}

// M8-03 – src/main/marken-store/schreibe-marken.ts (der EINZIGE Dateizugriff des Moduls auf V2)
export interface MarkenEintrag { id: string; name: string; parent: string | null
                                  eingebaut: boolean; /* farben/schriften/logo/… ohne Belang hier */ }
export async function ladeBestand(): Promise<Ergebnis<MarkenEintrag[], MarkenFehlercode>>
export async function aendereBestand<T>(
  aenderung: (bestand: MarkenEintrag[]) => Ergebnis<{ bestand: MarkenEintrag[]; wert: T }, MarkenFehlercode>,
  schreibart: 'sofort' | 'entprellt',
): Promise<Ergebnis<T, MarkenFehlercode>>

// M8-12 – src/main/marken-store/referenzpruefung.ts (Sperrprüfung über alle Projekte + Bestand)
export async function pruefeMarkenReferenzen(
  markeId: string,
): Promise<Ergebnis<Markennutzung, MarkenFehlercode>>
// beide Listen leer = in keinem gemeldeten Projekt und von keiner Marke im Bestand benutzt;
// ok: false bedeutet „Prüfung NICHT abgeschlossen", NIE „keine Treffer"

// M8-02 – src/main/marken-store/fehlercodes.ts
export type MarkenFehlercode =
  | 'marke_referenziert' | 'marke_eingebaut' | 'marke_nicht_gefunden'
  | 'marken_datei_fehlt' | 'speicher_fehler'

// #12/#22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
// Für DIESE Funktion ist genau eine Form von `daten` festgelegt:
//   code 'marke_referenziert' -> daten: Markennutzung
// Alle übrigen Codes dieser Funktion lassen `daten` weg.
```

**Ablauf (verbindlich) – fünf Schritte, in genau dieser Reihenfolge.**
1. `markeId` formal prüfen – sonst `ungueltige_eingabe`, **ohne** irgendetwas zu lesen.
2. **Vorprüfung auf dem gelesenen Bestand:** `ladeBestand()` (M8-03); Fehler unverändert
   zurückgeben. Eintrag mit `markeId` suchen. Fehlt er → `nicht_gefunden`. Ist er `eingebaut: true`
   → `marke_eingebaut`. Hier wird **nichts** verändert.
3. **Referenzprüfung:** `await pruefeMarkenReferenzen(markeId)` (M8-12).
   - `ok: false` → **Abbruch**, Code unverändert durchreichen. **Nicht** löschen.
   - `ok: true` und mindestens eine der beiden Listen nicht leer → `marke_referenziert` mit `daten`
     = dem **vollständigen** Prüfergebnis (beide Listen, auch die leere). **Nicht** löschen.
4. **Schreiben:** `aendereBestand(aenderung, 'sofort')`. Die Änderungsfunktion ist **synchron** und:
   a) Eintrag mit `markeId` **erneut** suchen. Ist er inzwischen weg → `nicht_gefunden`. Trägt er
      inzwischen `eingebaut: true` → `marke_eingebaut`. Diese Wiederholung ist nötig, weil zwischen
      Schritt 2 und Schritt 4 das `await` auf die Referenzprüfung liegt.
   b) Eintrag mit `markeId` aus dem Bestand entfernen (Filter) und
      `{ ok: true, wert: { bestand: <Ergebnis>, wert: undefined } }` liefern.
5. Das Ergebnis von `aendereBestand` ist der Rückgabewert dieser Funktion.

**Warum die Referenzprüfung NICHT in der Änderungsfunktion steht:** Sie ist `async` (liest alle
`project.json` **und** den Marken-Bestand ein zweites Mal über M8-12). Die Änderungsfunktion von
`aendereBestand` muss **synchron** sein (M8-03); ein `await` darin hebt die Zusage auf, dass Lesen,
Ändern und Schreiben eine ununterbrechbare Einheit sind.

**ENTSCHIEDEN – `'sofort'`, nicht `'entprellt'`.** Wie bei `löscheVorlage` (M4-13): Das Löschen ist
unumkehrbar und strukturell; eine nur im Speicher übernommene Löschung käme nach einem Absturz
zurück, während der Nutzer die Marke längst für verschwunden hält.

**ENTSCHIEDEN – Prüfreihenfolge: erst `eingebaut`, dann die Referenzprüfung.** Ist die Marke
eingebaut, ist das Ergebnis unabhängig davon, ob sie referenziert ist – „nie löschbar" gilt absolut
(TK 9.15.1). Die (teure, über alle Projekte laufende) Referenzprüfung entfällt in diesem Fall
vollständig, analog zu M4-13s Behandlung von `eingebaut: true` bei Vorlagen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `markeId` | ID der zu löschenden Marke | nicht leerer String; **kein** UUID-Zwang; muss im Bestand stehen und darf **nicht** `eingebaut` sein |

Ausgang bei Erfolg: `Ergebnis<void>` – die Marke ist aus `marken.json` verschwunden. **Kein** Projekt
wurde verändert, **keine** abgeleitete Marke wurde angefasst (sie hätte die Löschung ohnehin
blockiert, s. u.).
Ausgang bei Fehler: `marke_referenziert` (mit `daten: Markennutzung`), `marke_eingebaut`,
`nicht_gefunden`, `ungueltige_eingabe`, `speicher_fehler`.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operations-Zeile, wörtlich (TK 9.15.1): „`löscheMarke` | `markeId` → `Ergebnis<void>`; im
  Fehlerfall Code `marke_referenziert` mit **beiden** Trefferlisten: betroffene **Aktionen** (je mit
  Projekt) und betroffene **abgeleitete Marken**"
- „**Löschen blockiert bei Referenz**, es kaskadiert **nicht** – wie bei den Vorlagen (9.12.1). …
  Geprüft wird über **alle** Projekte, nicht nur das geladene." (TK 9.15.1)
- „**Die eingebaute Marke ist nie löschbar** (`eingebaut: true`): Sie ist der Projekt-Standard und
  die Basis der abgeleiteten Looks." (TK 9.15.1)
- „**Eingebaute Marke unlöschbar, aber bearbeitbar** – anders als die eingebauten Vorlagen."
  (Entscheidung 7 des Auftraggebers, BRIEFING Abschnitt 3)
- Der Fehlercode-Satz, wörtlich (TK 9.15.5): „`marke_referenziert` | Löschen abgelehnt – Aktionen
  und/oder abgeleitete Marken nutzen sie noch (mit beiden Trefferlisten)" / „`marke_eingebaut` |
  Löschen der eingebauten Marke versucht"
- **Strukturierte Fehlerdaten, wörtlich (TK 9.1.1):** „**Strukturierte Fehlerdaten (`daten`,
  optional).** Manche Fehler sind erst mit ihren Nutzdaten bedienbar: … `vorlage_referenziert` beide
  Trefferlisten (9.12.1). … Regeln: Das Feld ist **optional** … seine Form ist **je Fehlercode
  festgelegt und typisiert** … es ist **kein Freitext-Anhang** und **kein Ersatz für `meldung`**."
  – dieselbe Regel gilt für `marke_referenziert` mit `Markennutzung`.
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2). „Wo eine Operation **nichts** zu melden hat, lautet die
  Nutzlast `void`: **`Ergebnis<void>`** … **Verboten** sind Ersatzformen wie `Ergebnis<boolean>`,
  `Ergebnis<null>` oder ein blankes `true`." (TK 9.1.1, Punkt 2)
- „**Fehlercodes sind ein geschlossener, typisierter Satz** … Eine rohe Exception-Meldung wird nie
  zum Code." (TK 9.1.1, Punkt 3)
- „**Der Main validiert jede eingehende Nutzlast** – er vertraut dem Renderer **nicht**." (TK 9.1.1,
  Punkt 6)

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `markeId` ist kein String oder leer | `ungueltige_eingabe` | keine Wirkung; es wird nichts gelesen |
| `ladeBestand` liefert `ok: false` | genau dieser Code (i. d. R. `speicher_fehler`) | unverändert durchreichen; die Referenzprüfung läuft gar nicht erst |
| keine Marke mit dieser `markeId` | `nicht_gefunden` | keine Wirkung; **kein** stiller Erfolg |
| Eintrag ist `eingebaut: true` | `marke_eingebaut` | keine Wirkung; **keine** Referenzprüfung mehr nötig (Spy: `pruefeMarkenReferenzen` wird nicht aufgerufen) |
| `pruefeMarkenReferenzen` liefert `ok: false` | genau dieser Code (i. d. R. `speicher_fehler`) | **Abbruch, es wird NICHT gelöscht** |
| mindestens ein Treffer in `aktionen` **oder** `abgeleiteteMarken` | `marke_referenziert` | keine Wirkung; `daten` trägt **beide** Listen vollständig; **kein** Kaskadieren |
| Eintrag ist zwischen Vorprüfung und Schreiben verschwunden oder eingebaut geworden | derselbe Code wie in der Vorprüfung | Abbruch aus der Änderungsfunktion heraus; nichts geschrieben |
| das Schreiben in `aendereBestand` schlägt fehl | `speicher_fehler` | unverändert durchgereicht |

## Nicht selbst entscheiden – STOPP und fragen
- **BEOBACHTETE DISKREPANZ, hier NICHT behoben (Regel C – keine Erweiterung der von M8-01
  vorgegebenen `Markennutzung`-Form):** Wie in M8-12 vermerkt, prüft der Vertrag **nicht**, ob die zu
  löschende Marke gerade `Project.standardMarkeId` eines Projekts ist. Diese Funktion löscht in
  diesem Fall, solange keine Aktion und keine abgeleitete Marke dagegenspricht – ein danach
  gerenderter Band-Hintergrund bzw. eine Split-Restfläche dieses Projekts würde beim nächsten Render
  auf `leseMarke(standardMarkeId)` mit `marke_nicht_gefunden` scheitern. **Nicht selbst durch eine
  dritte, hier erfundene Prüfung schließen** – das ist eine Lücke im Vertrag, keine
  Implementierungsdetail-Frage dieses Issues.
- **ECHTE OFFENE FRAGE, dieselbe wie in M8-12: noch nicht gespeicherte Änderungen des aktiven
  Projekts.** Wird eine Marke Sekunden nach ihrer ersten Verwendung gelöscht, kann die dateibasierte
  Referenzprüfung die frische Referenz noch nicht sehen. Ob ein Sofort-Flush davor nötig ist, ist
  **nicht** entschieden. **Verbindlich bis zur Klärung:** kein Flush, kein Zugriff auf den
  Speicherstand des `project-store`.
- **Verbot – keine Kaskade, kein Anfassen von Projekten oder anderen Marken.** Keine Aktion wird
  umgebogen, keine abgeleitete Marke gelöst oder gelöscht, kein `project.json` geschrieben.
- **Verbot – keine eigene Referenzprüfung.** Ausschließlich M8-12.
- **Verbot – bei einem Prüffehler niemals löschen.**
- **Verbot – kein zweiter Schreibpfad.** Ausschließlich `ladeBestand`/`aendereBestand` (M8-03). Kein
  `mitD1Lock`, kein eigenes Lock, kein `flushBestand()` (gehört dem Beenden der App).
- **Verbot – kein `await` innerhalb der Änderungsfunktion.**
- **Verbot – keine Ersatzform für `void`.**
- **Verbot – kein IPC, kein Ereignis.** Der Kanal `marken:löscheMarke` gehört M8-31.

      `{ ok: true, wert: undefined }`
- [ ] `aendereBestand` wird **genau einmal** aufgerufen, mit `schreibart === 'sofort'` (Spy)
- [ ] Ein Treffer **nur** über `abgeleiteteMarken` blockiert das Löschen genauso wie einer über
      `aktionen`: Ergebnis `marke_referenziert`, `aendereBestand` nachweislich **nicht** aufgerufen
- [ ] Der Fehler `marke_referenziert` trägt `daten` mit **beiden** Schlüsseln `aktionen` und

      `pruefeMarkenReferenzen` geliefert hat
- [ ] Liefert `pruefeMarkenReferenzen` `{ ok: false, fehler: { code: 'speicher_fehler', … } }`,

- [ ] Eine `eingebaut: true`-Marke liefert `marke_eingebaut`; `pruefeMarkenReferenzen` und

- [ ] Ist der Eintrag in dem Bestand, den die Änderungsfunktion bekommt, **nicht mehr** vorhanden

      `nicht_gefunden` und es wird nichts geschrieben – Nachweis, dass Schritt 4a wirklich erneut
