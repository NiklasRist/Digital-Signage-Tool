### Issue M8-03: [marken-store] marken.json atomar und serialisiert lesen und schreiben

## Ziel (in einem Satz)
Der app-weite Marken-Bestand wird über **eine** gemeinsame Stelle geladen und geschrieben –
absturzsicher (Backup + Temp + Rename), streng nacheinander und mit einer eigenen Serialisierung –,
sodass zwei gleichzeitige Änderungen (z. B. eine entprellte Bearbeitung und eine gleichzeitige
Löschung) sich niemals verschränken.

## Modul & Datei
- Modul: `marken-store` [V2] (Main)
- Datei: `src/main/marken-store/schreibe-marken.ts`
- Vertrag: Technisches Konzept **9.15.1** (eigene Schreib-Serialisierung), **9.5.4** (die
  Schreib-Invarianten, auf die 9.15.1 verweist), **9.5.5** (`schemaVersion`), **9.12.1**
  (`vorlagen-store` – das Muster, dem dieser Store folgt, da beide ohne D1-Lock auskommen müssen)
  – Quelle der Wahrheit
- Prozess/Speicher: V2 (`<Datenort>/marken.json`, `<Datenort>/marken.json.bak`)

## Warum das im Gesamtsystem wichtig ist
Dies ist die **einzige** Stelle im ganzen Modul, die `fs` anfasst – Gegenstück zu `schreibeProjekt`
(#46) für `project.json`, aber mit einem entscheidenden Unterschied: „Es gibt **nur ein**
D1-Schreib-Lock, und das gehört dem `project-store` und schützt **nur** `project.json`. Der
`marken-store` hat seine **eigene** [Serialisierung] – wie der `vorlagen-store` (TK 9.12.1)" (BRIEFING
Abschnitt 6). Ohne eine eigene Serialisierung sind alle Operationen des Moduls
Lesen-Ändern-Schreiben-Zyklen auf **derselben** Datei: Legt der `marken-editor` gerade eine neue
abgeleitete Marke an, während `bearbeiteMarke` (M8-11) entprellt eine andere Marke sichert, überschreibt
der zweite Schreibvorgang den ersten (Lost Update), wenn beide unabhängig lesen und zurückschreiben.

Zwei weitere Fehlerklassen entstehen, wenn diese Datei nachlässig gebaut wird, und beide sind stiller
Verlust: **Erstens der stille Fallback** – ein defektes `marken.json` mit
`try { … } catch { return [eingebauteMarke()] }` würde jede vom Nutzer angelegte abgeleitete oder
eigenständige Marke vernichten. **Zweitens das Überschreiben beim Start** – schreibt diese Datei beim
Fehlen der Datei mehr als die eine fehlende eingebaute Marke, verwechselt sie „Bestand fehlt" mit
„Bestand ist unvollständig", was hier (anders als beim `vorlagen-store` mit drei eingebauten
Vorlagen) ohnehin nicht vorkommen kann, aber als Fehlklasse dieselbe Wachsamkeit verlangt.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/marken-store/schreibe-marken.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { FarbRolle, SchriftRolle, Schrift, Herkunft } from '../../shared/contracts/marke'
import type { MarkenFehlercode } from './fehlercodes'
import { eingebauteMarke } from './anfangsbestand'
import { ermittleDatenOrt } from '../datenort'

// Fremde Aufrufe – vollstaendige Signaturen, damit hier nichts geraten wird:
//   #5:    ermittleDatenOrt(): string
//   M8-02: type MarkenFehlercode =
//            'marke_referenziert' | 'marke_eingebaut' | 'marke_nicht_gefunden'
//            | 'marken_datei_fehlt' | 'speicher_fehler'
//   M8-06: eingebauteMarke(): MarkenEintrag
//          // frische TIEFE Kopie der VOLLSTAENDIG befuellten Fitnessworld24-Marke (eingebaut: true,
//          // parent: null, alle Rollen/Logo/Sicherheit/Radien/Schatten/Slogan gesetzt) – wird NUR
//          // aufgerufen, wenn marken.json noch nicht existiert (Schritt 2 unten)
//   #12/#22: type Ergebnis<T, F extends string = GenerischerFehlercode> =
//              | { ok: true; wert: T }
//              | { ok: false; fehler: { code: F | GenerischerFehlercode
//                                       meldung: string; daten?: unknown } }

/**
 * ROHE, gespeicherte Form einer Marke in marken.json, BEVOR die Vererbung aufgeloest ist (M8-05).
 * Bei einer eigenstaendigen Marke (parent === null) sind farben/schriften VOLLSTAENDIG befuellt und
 * alle uebrigen Feld ER GESETZT (Invariante, durchgesetzt von M8-06 und M8-10). Bei einer
 * ABGELEITETEN Marke (parent !== null) darf JEDES Feld ausser id/name/parent/eingebaut fehlen bzw.
 * nur teilweise gesetzt sein: farben/schriften sind PARTIELLE Records (fehlende ROLLE = geerbt),
 * logo/sicherheit/radien/schatten/slogan sind je als GANZES Feld optional (undefined = geerbt).
 */
export interface MarkenEintrag {
  id: string
  name: string
  parent: string | null
  eingebaut: boolean
  farben: Partial<Record<FarbRolle, string>>
  schriften: Partial<Record<SchriftRolle, Schrift>>
  logo?: { datei: string; herkunft: Herkunft; seitenverhaeltnis: number } | null
  sicherheit?: { horizontal: number; vertikal: number }
  radien?: { pille: number; karte: number; klein: number }
  schatten?: { versatzY: number; weichzeichnen: number; farbe: string }
  slogan?: { text: string; aktiv: boolean }
}

/**
 * Schema-Version von marken.json. Modul-lokal und hier deklariert. NICHT die
 * AKTUELLE_SCHEMA_VERSION aus #21 verwenden – die gehoert zu project.json/config.json; eine Kopplung
 * an D1-Migrationen ist unerwuenscht. Auch NICHT VORLAGEN_SCHEMA_VERSION (M4-04) oder
 * QUEUE_SCHEMA_VERSION (#69) verwenden.
 */
export const MARKEN_SCHEMA_VERSION = 1

/** Dateiform von marken.json. */
export interface MarkenDatei {
  schemaVersion: number
  marken: MarkenEintrag[]
}

/**
 * Liefert den vollstaendigen Bestand als TIEFE Kopie. Beim ersten Aufruf wird die Datei geladen bzw.
 * (falls sie fehlt) mit GENAU der einen eingebauten Marke angelegt; danach kommt der Bestand aus dem
 * Speicher. Laeuft auf DERSELBEN Serialisierungskette wie `aendereBestand` und niemals daran vorbei;
 * der Erstladevorgang findet HOECHSTENS EINMAL statt (geteiltes in-flight-Promise).
 */
export async function ladeBestand(): Promise<Ergebnis<MarkenEintrag[], MarkenFehlercode>>

/**
 * Die EINZIGE Art, den Bestand zu aendern. Laedt (falls noetig), ruft `aenderung` mit einer tiefen
 * Kopie des Bestands auf, uebernimmt das Ergebnis in den Speicher und schreibt.
 *
 * `aenderung` ist SYNCHRON – sie darf nicht `await`en. Genau das macht Lesen-Aendern-Schreiben zu
 * einer ununterbrechbaren Einheit: Ohne `await` kann zwischen Lesen und Schreiben kein zweiter Aufruf
 * dazwischenkommen. Liefert `aenderung` ein `ok: false`, wird NICHTS geschrieben und der Fehler
 * unveraendert durchgereicht. Aufrufe laufen streng nacheinander (verkettete Promise), auch die aus
 * verschiedenen Operationen und verschiedenen Dateien des Moduls.
 */
export async function aendereBestand<T>(
  aenderung: (bestand: MarkenEintrag[]) =>
    Ergebnis<{ bestand: MarkenEintrag[]; wert: T }, MarkenFehlercode>,
  schreibart: 'sofort' | 'entprellt',
): Promise<Ergebnis<T, MarkenFehlercode>>
// 'sofort'    -> die Datei ist geschrieben, BEVOR das Promise erfuellt wird
// 'entprellt' -> der Bestand ist im Speicher uebernommen und das Promise wird erfuellt; die Datei
//                wird 4000 ms nach der LETZTEN entprellten Aenderung geschrieben

/**
 * Schreibt einen noch ausstehenden entprellten Stand sofort und bricht den Timer ab. Steht nichts
 * aus, ist das ein erfolgreicher Leerlauf ({ ok: true }), kein Fehler. Aufrufer: Main-Bootstrap (#3)
 * beim Beenden der App.
 */
export async function flushBestand(): Promise<Ergebnis<void, MarkenFehlercode>>

/**
 * Registriert einen HAUPT-INTERNEN Hoerer, der nach JEDEM abgeschlossenen Schreibversuch (gleich ob
 * 'sofort', 'entprellt' oder ueber flushBestand) genau einmal aufgerufen wird. Kein Ereignis im Sinne
 * von TK 9.1.1 (kein IPC, kein Kanalname) – reine main-interne Kopplung fuer M8-04, das daraus den
 * oeffentlichen Kanal `marken:autoSpeichernStatus` baut. Rueckgabewert ist die Abmelde-Funktion.
 */
export function aufSchreibversuch(
  hoerer: (ergebnis: { erfolgreich: true } | { erfolgreich: false; code: MarkenFehlercode }) => void,
): () => void
```

**Die oben ausgeschriebenen fremden Signaturen (#5, M8-02, M8-06, #12/#22) sind fremder Vertrag.**
Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein **Vertragsfehler**:
**melden und NICHT eigenmächtig anpassen.**

**Ablauf von `ladeBestand`, wenn der Bestand noch nicht im Speicher ist (verbindlich):**
1. `<Datenort>/marken.json` lesen. Der Datenort kommt aus `ermittleDatenOrt()` (#5); der Dateiname
   `marken.json` steht in TK Abschnitt 6.
2. **Datei fehlt** → Anfangsbestand `[eingebauteMarke()]` (genau **ein** Element, M8-06), Datei
   anlegen (Schritt-Schema wie beim Schreiben unten), fertig.
3. **Datei nicht parsebar** → `<Datenort>/marken.json.bak` versuchen. Ist die parsebar, wird deren
   Inhalt verwendet; die defekte `marken.json` bleibt dabei **unverändert liegen**. Der nächste
   Schreibvorgang überspringt deshalb einmalig das Kopieren nach `.bak`.
4. **Beide nicht parsebar oder nicht lesbar** → `speicher_fehler`. **Kein** Rückfall auf `[eingebauteMarke()]`.
5. **`schemaVersion` ungleich `MARKEN_SCHEMA_VERSION`** → `speicher_fehler`. Es gibt aktuell nur die
   Version 1 und deshalb **keine** Migration; eine unbekannte Version wird **nicht** geraten.
6. **`marken` fehlt, ist kein Array oder ist leer** → wie „nicht parsebar" behandelt (erst `.bak`, dann
   Fehler) – ein Bestand ohne **jede** Marke ist ein Datenfehler, kein gültiger Zustand: Die
   eingebaute Marke ist laut TK 9.15.1 „immer vorhanden".
7. Der Bestand wird im Speicher gehalten.

**Ablauf jedes Schreibvorgangs (verbindlich):**
1. Bestehende `marken.json` (falls vorhanden) nach `marken.json.bak` kopieren (`fs.copyFile`, **kein**
   Verschieben). **Ausnahme:** Wurde der Bestand zuvor aus dem `.bak` wiederherstellt, wird dieser
   Kopierschritt **beim ersten Schreibvorgang danach übersprungen** (sonst überschriebe er das letzte
   heile Backup mit dem Schrott, bevor die neue Fassung überhaupt geschrieben ist).
2. `{ schemaVersion: MARKEN_SCHEMA_VERSION, marken: <Bestand> }` als JSON nach `marken.json.tmp`
   schreiben.
3. `marken.json.tmp` durch Rename-mit-Ersetzen auf `marken.json` bringen (gleiche Partition). Danach
   gilt die Datei wieder als heil; die `.bak`-Ausnahme aus Schritt 1 entfällt für künftige Schreib-
   vorgänge.
4. Nach Abschluss (Erfolg **oder** Fehler): `aufSchreibversuch`-Hörer benachrichtigen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `aenderung` (`aendereBestand`) | synchrone Funktion, die aus dem alten Bestand den neuen und den Rückgabewert `T` bildet | muss synchron sein (kein `Promise`); wirft sie doch, wird sie gefangen und als `unbekannter_fehler` gemeldet, **ohne** zu schreiben |
| `schreibart` (`aendereBestand`) | `'sofort'` für strukturelle Änderungen (anlegen, ableiten, löschen), `'entprellt'` nur für das Auto-Speichern von `bearbeiteMarke` (M8-11) | genau diese zwei Werte |

Ausgang bei Erfolg: `Ergebnis<MarkenEintrag[], MarkenFehlercode>` mit einer tiefen Kopie des Bestands
(`ladeBestand`); `Ergebnis<T, MarkenFehlercode>` mit dem von `aenderung` gelieferten Wert
(`aendereBestand`); `Ergebnis<void, MarkenFehlercode>` (`flushBestand`).
Ausgang bei Fehler: `speicher_fehler`, oder einer der generischen Codes aus #12/#22 – bzw. der Code,
den `aenderung` selbst geliefert hat und der hier unverändert durchgereicht wird.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Besitzt** `marken.json` (app-weiter Bestand, Abschnitt 6) samt **eigener**
  Schreib-Serialisierung. Die Schreib-Invarianten sind **dieselben** wie in 9.5.4: **atomar** (Temp +
  Rename), **`marken.json.bak`** als letzte heile Version, **`schemaVersion`**, und Speicherfehler
  werden **sichtbar** gemacht statt still verschluckt." (TK 9.15.1) – **diese** Datei *ist* die eigene
  Schreib-Serialisierung.
- „**Lock-Grenze:** Das D1-Lock schützt **nur** `project.json`. Die Auftragsverwaltungs-Speicher Q2/Q3
  … haben ihre **eigene** Serialisierung – der `auftrags-manager` hängt **nicht** am
  `project-store`-Lock." (TK 9.5.4) – dasselbe gilt hier: Diese Datei ruft **kein** `mitD1Lock` (#32)
  auf und führt **kein** zweites, systemweites Lock ein. Die Verkettung hier ist eine
  Reihenfolge-Garantie **innerhalb dieser Datei**, kein Mutex-Objekt für andere Module.
- „**Atomar:** Schreiben nach Temp-Datei + Rename (gleiche Partition). `project.json` ist **nie**
  halb geschrieben." (TK 9.5.4) – wörtlich über `project.json` gesagt; TK 9.15.1 erklärt genau diese
  Invarianten für `marken.json` ausdrücklich für gültig.
- „**Ein Backup:** `project.json.bak` = letzte heile Version. Ist `project.json` beim Laden defekt →
  aus `.bak` wiederherstellen; ist auch das defekt → **Fehler melden**, **nicht**
  leer/verlustbehaftet weiterstarten." (TK 9.5.4) – analog entsteht genau **eine** Datei
  `marken.json.bak`, aus der auch **gelesen** wird.
- „Jede `project.json` und `config.json` trägt eine `schemaVersion`." (TK 9.5.5) – für `marken.json`
  gilt dieselbe Regel (TK 9.15.1: „`schemaVersion` und Migration wie 9.5.5").
- „**Speicherfehler sind sichtbar (NFA-02):** … die Änderungen **bleiben im Speicher** (kein Rollback,
  kein Arbeitsverlust)." (TK 9.5.4) – ein gescheiterter entprellter Schreibvorgang lässt den Bestand im
  Speicher gültig; es gibt **kein** Rollback auf den Dateistand.
- „**Instant-Op vs. Speichern getrennt:** Eine Instant-Operation … validiert und wendet **im
  Speicher** an, *bevor* sie „ok" meldet – ihr Erfolg bedeutet „gültig übernommen", **nicht** „schon
  auf Platte"." (TK 9.5.4) – das ist genau die Bedeutung von `schreibart: 'entprellt'`.
- **Die eingebaute Marke ist immer vorhanden** (TK 9.15.1: „Die Fitnessworld24-Marke ist immer
  vorhanden und **nicht löschbar**", AD FA-23) – deshalb ist ein Bestand mit **null** Einträgen ein
  Fehler, nicht die Erstbenutzung; die Erstbenutzung erzeugt genau **ein** Element.
- **Der Bestand verlässt diese Datei nur als tiefe Kopie**, und `aenderung` bekommt ebenfalls eine
  tiefe Kopie. Andernfalls könnte ein Aufrufer den zwischengespeicherten Bestand hinter dem Rücken
  dieser Datei verändern.
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2). Diese Funktionen werfen **nie**; jeder Ausgang ist eine
  Hülle.
- **Keine Kenntnis über den fachlichen Inhalt aufbauen.** Diese Datei prüft **nicht**, ob eine
  `MarkenEintrag`-Kette höchstens eine Stufe tief ist, ob eine Farb-Rolle bekannt ist oder ob
  `eingebaut` korrekt gesetzt wurde. Alle fachlichen Regeln gehören den Operationen (M8-09 bis M8-15).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `ladeBestand`: `marken.json` fehlt | – | **kein Fehler**: Anfangsbestand `[eingebauteMarke()]`, Datei wird angelegt |
| `ladeBestand`: Inhalt kein gültiges JSON, `.bak` ist gültiges JSON | – | **kein Fehler**: Inhalt des `.bak` wird Bestand; die defekte Datei bleibt unverändert liegen |
| `ladeBestand`: Inhalt kein gültiges JSON, `.bak` fehlt oder ist ebenfalls defekt | `speicher_fehler` | kein Rückfall auf den Anfangsbestand |
| `ladeBestand`: `schemaVersion` ungleich `MARKEN_SCHEMA_VERSION` | `speicher_fehler` | kein Laden, kein Raten, keine Migration |
| `ladeBestand`: `marken` fehlt, kein Array oder leer | `speicher_fehler` | wie „nicht parsebar" behandelt (erst `.bak`, dann Fehler) |
| `ladeBestand`: I/O-Fehler (Rechte, `EBUSY`, defektes Medium) | `speicher_fehler` | keine Wirkung, kein Rückfall |
| `aendereBestand`: `aenderung` liefert `ok: false` | der Code aus `aenderung` | nichts wird geschrieben, der Bestand im Speicher bleibt unverändert |
| `aendereBestand`: `aenderung` wirft eine Ausnahme | `unbekannter_fehler` | wie oben: nichts geschrieben, Bestand unverändert; kein Stacktrace nach außen |
| `aendereBestand`/`flushBestand`: I/O-Fehler beim Kopieren nach `.bak` | `speicher_fehler` | Abbruch vs. trotzdem schreiben ist offen, s. „Nicht selbst entscheiden" |
| `aendereBestand`/`flushBestand`: I/O-Fehler beim Schreiben von `.tmp` (Platte voll, Rechte) | `speicher_fehler` | Zieldatei bleibt unverändert; Bestand **bleibt im Speicher** (kein Rollback) |
| `aendereBestand`/`flushBestand`: Rename schlägt fehl (`EBUSY`/`EPERM` unter Windows) | `speicher_fehler` | Zieldatei bleibt unverändert; Retry+Backoff offen, s. „Nicht selbst entscheiden" |
| `flushBestand`: es steht nichts aus | – | **kein Fehler**: `{ ok: true, wert: undefined }`, keine Datei wird angefasst |
| unerwartete Ausnahme irgendwo im Ablauf | `unbekannter_fehler` | gefangen und als Hülle gemeldet, kein `throw` |

## Nicht selbst entscheiden – STOPP und fragen
- **Rename-mit-Ersetzen ist plattformabhängig.** Dieselbe offene Frage wie bei #31
  (`config.json`), #46 (`project.json`), #69 (Queue-Dateien) und der `vorlagen-store`-Entsprechung
  (M4-04): Ob unter Windows bei `EBUSY`/`EPERM` ein Retry+Backoff nötig ist (wie beim Export, TK
  9.6.2 entschieden), ist hier **nicht** festgelegt. **Falls dort bereits eine Lösung feststeht: exakt
  dieselbe verwenden.** Sonst gemeinsam klären – nicht selbst erfinden.
- **`fsync` vor der Erfolgsmeldung.** TK 9.15.1 nennt es für `marken.json` nicht ausdrücklich, ebenso
  wenig TK 9.5.4 für `project.json`. **Gleiche Antwort wie #31, #46, #69, M4-04 verwenden.**
- **Verhalten bei einem Fehlschlag des `.bak`-Kopierens.** Bricht der ganze Schreibvorgang ab oder
  wird trotzdem geschrieben? Dieselbe ungeklärte Frage wie bei #46 und M4-04 – **dieselbe Antwort**
  verwenden, sobald geklärt.
- **ECHTE OFFENE FRAGE, betrifft ALLE Operationen des Moduls (M8-08 bis M8-15 – sie sind
  inzwischen ALLE geschrieben): `aendereBestand` löst KEIN Lesen-Ändern-Schreiben über mehrere
  Aufrufe hinweg atomar.** Jeder
  Aufruf von `aendereBestand` ist für sich verkettet und damit unterbrechungsfrei – **aber** eine
  Operation, die zuerst über einen **eigenen** `await` (z. B. eine Existenzprüfung, ein Datei-Import)
  etwas außerhalb der `aenderung`-Funktion liest und danach `aendereBestand` mit dem Ergebnis dieser
  Lesung aufruft, hat zwischen Lesen und Schreiben eine Lücke, in die ein anderer `aendereBestand`-
  Aufruf hineinlaufen kann (M8-10 dokumentiert das für den Parent-Existenz-Check bereits als eigene
  offene Frage). **Diese Datei löst das nicht** – sie serialisiert nur **innerhalb** eines einzelnen
  `aendereBestand`-Aufrufs. Ob eine Operation ihre Vorbedingungen **innerhalb** der synchronen
  `aenderung`-Funktion erneut prüfen muss (wie in M8-13 für `löscheMarke` bereits vorgemacht), ist
  keine Frage dieser Datei, sondern jeder einzelnen Operation – **hier nur vermerkt, damit es nicht
  als „durch M8-03 bereits gelöst" missverstanden wird.** *(Der frühere Hinweis, M8-14 und M8-15
  seien „hier noch nicht geschrieben", ist überholt: **beide sind geschrieben.** Es ist also nichts
  mehr zu melden und auf nichts zu warten – die Frage bleibt trotzdem offen, weil sie in jeder
  einzelnen Operation zu beantworten ist.)*
- **VERMERK FÜR DEN AUFTRAGGEBER (kein Arbeitsauftrag an den umsetzenden Agenten):** Der ursprüngliche
  Zuschnitt trennt „Atomares Schreiben" (M8-03) von „Auto-Speichern beim Bearbeiten + Ereignis" (M8-04)
  in zwei Issues. Die bereits geschriebenen Nachbarn M8-09/M8-10/M8-11 setzen jedoch voraus, dass der
  **Entprellungs-Mechanismus selbst** (`schreibart: 'entprellt'`) Teil von `aendereBestand` – also Teil
  **dieser** Datei – ist, weil `bearbeiteMarke` (M8-11) diese Funktion direkt mit `'entprellt'` aufruft.
  Dieses Issue trägt deshalb den Timer; M8-04 baut **nur** die öffentliche Ereignis-Schicht
  (`marken:autoSpeichernStatus`) auf dem hier neu eingeführten, main-internen Hörer `aufSchreibversuch`
  auf. Diese Aufteilung ist die einzige, die mit den bereits verfassten Nachbar-Dateien konsistent ist
  – der Zuschnitt-Text selbst benennt diese Grenze nicht so fein.

## Definition of Done
- [ ] `ladeBestand` legt bei fehlender `marken.json` eine Datei mit genau **einem** Element an
      (`eingebauteMarke()`, vollständig befüllt) und liefert sie zurück
- [ ] `ladeBestand` liefert bei ungültigem JSON **ohne** brauchbares `.bak` `speicher_fehler` – und
      **nicht** `[eingebauteMarke()]` als Ersatz
- [ ] `ladeBestand` liefert bei ungültigem JSON **mit** gültigem `.bak` dessen Inhalt; die defekte
      `marken.json` ist danach byte-identisch zu vorher
- [ ] `ladeBestand` liefert bei `schemaVersion: 2` `speicher_fehler` und lädt nichts
- [ ] `ladeBestand` liefert bei `marken: []` (leeres Array in einer sonst validen Datei)
      `speicher_fehler` – **kein** gültiger Zustand ohne die eingebaute Marke
- [ ] `MARKEN_SCHEMA_VERSION` ist als `1` exportiert; die Datei importiert weder
      `AKTUELLE_SCHEMA_VERSION` (#21) noch `VORLAGEN_SCHEMA_VERSION` (M4-04) noch
      `QUEUE_SCHEMA_VERSION` (#69) – Grep-Probe
- [ ] Nach einem erfolgreichen Schreibvorgang enthält `marken.json.bak` genau den vorherigen
      Dateiinhalt und `marken.json` den neuen
- [ ] Nach einer `.bak`-Wiederherstellung ist das `.bak` beim nächsten Schreibvorgang **unverändert**
      – erst der übernächste Schreibvorgang legt wieder ein frisches `.bak` an
- [ ] Zwei gleichzeitig gestartete `ladeBestand`-Aufrufe auf einem leeren Datenort legen die Datei
