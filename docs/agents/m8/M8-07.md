### Issue M8-07: [marken-store] Migration – bestehende Projekte auf die eingebaute Marke ausrichten

## Ziel (in einem Satz)
Ein bereits bestehendes Projekt, dessen `Aktion`en und `standardMarkeId` aus der Zeit vor dem
Marken-Bestand (v3.3) stammen, wird auf die neue eingebaute Fitnessworld24-Marke ausgerichtet, sodass
kein Update ein Projekt mit einer ins Leere zeigenden oder fehlenden Marken-Referenz zurücklässt.

## Modul & Datei
- Modul: `marken-store` [V2] (Main)
- Datei: `src/main/marken-store/migration.ts`
- Vertrag: Technisches Konzept **9.15.1** (Migrations-Absatz, wörtlich – Quelle der Wahrheit),
  **9.5.5** (`schemaVersion` & Migration, allgemeine Regel), **9.5.6** (config-store, Anmerkung zum
  entfallenen Feld)
- Prozess/Speicher: liest/verändert **D1** (`Project.standardMarkeId`, `Aktion.markeId` **aller**
  Projekte), liest V2 (die eingebaute Marke muss bereits existieren, s. Abhängigkeiten)

## Warum das im Gesamtsystem wichtig ist
„**`schemaVersion` und Migration** wie 9.5.5. **Für den Übergang von v3.3 wichtig:** Die bisher in
`config.json` geführte Marke war ein **namenloses Wertobjekt**. Die Migration legt daraus die
eingebaute Marke in `marken.json` an …, setzt `Project.standardMarkeId` und `Aktion.markeId` aller
Projekte darauf und entfernt das Feld aus `config.json`." (TK 9.15.1) Vor v3.4 kannten weder `Project`
noch `Aktion` eine Marken-Referenz – es gab nur **eine** Marke, unsichtbar und implizit. Mit `markeId`
als **neuem Pflichtfeld** an `Aktion` (Zuschnitt M8, Edit an #14/M1-02) hätte jedes bestehende Projekt
nach dem Update Aktionen **ohne** dieses Feld: Jeder Aufrufer, der `aktion.markeId` erwartet (19 Stellen
laut TK 9.15.4, plus M8-12s Referenzprüfung, die **alle** Projekte nach `aktion.markeId` durchsucht),
träfe auf `undefined` statt auf eine gültige ID. Ohne diese Migration verlieren bestehende Projekte
beim ersten Start nach dem Update ihre Marke – nicht als Absturz, sondern als **stiller
Zeichenfehler**: `leseMarke(undefined)` liefert `marke_nicht_gefunden`, und jedes Segment dieser
Aktion würde ohne Marke gezeichnet (Farben, Schriften, Logo fehlen).

**Abgrenzung zu M8-06 (wichtig, um Doppelarbeit zu vermeiden).** M8-06 sorgt dafür, dass **die
Marke selbst** existiert (`marken.json` bekommt die eingebaute Fitnessworld24-Marke, mit festen,
TK-vorgegebenen Werten) – unabhängig davon, ob dieses Projektverzeichnis neu oder alt ist. **Dieses**
Issue setzt dagegen die **Referenzen in den Projekten** auf die durch M8-06 bereitgestellte Marke:
`Project.standardMarkeId` und jedes `Aktion.markeId`. Beide Migrationen laufen **nacheinander** (erst
M8-06: Marke existiert; dann M8-07: Referenzen zeigen darauf) und **unabhängig davon**, ob im alten
`config.json` überhaupt je eine Marke geführt wurde – der Fall „Marke existiert, aber Projekte
verweisen noch nicht darauf" tritt bei **jedem** bestehenden Projekt auf, ganz gleich, was vorher in
`config.json` stand.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/marken-store/migration.ts
import type { Project } from '../../shared/contracts/project'

/**
 * REINE Funktion (kein I/O): Prueft ein bereits geladenes Project darauf, ob standardMarkeId bzw.
 * eine oder mehrere Aktion.markeId fehlen, und ergaenzt sie um eingebauteMarkeId. Aendert NICHTS an
 * Feldern, die bereits gesetzt sind (auch nicht, wenn sie auf eine andere, gueltige Marke zeigen –
 * ein Projekt, das bereits eine Marke gewaehlt hat, wird NICHT ueberschrieben).
 *
 * Gibt IMMER eine neue, unveraenderte oder ergaenzte Kopie zurueck; `geaendert` sagt dem Aufrufer,
 * ob ueberhaupt etwas zu schreiben ist (vermeidet unnoetige Schreibvorgaenge fuer bereits
 * migrierte Projekte).
 */
export function migriereProjektAufMarke(
  project: Project,
  eingebauteMarkeId: string,
): { project: Project; geaendert: boolean }
```

**Ablauf (verbindlich):**
1. `standardMarkeId` fehlt, ist leer oder kein String → auf `eingebauteMarkeId` setzen, `geaendert =
   true`. Ist bereits ein nicht-leerer String gesetzt (gleich welcher Wert) → **unverändert lassen**.
2. Für **jede** `Aktion` in `project.aktionen`: `markeId` fehlt, ist leer oder kein String →
   auf `eingebauteMarkeId` setzen, `geaendert = true`. Ist bereits gesetzt → **unverändert lassen**.
3. `{ project: <ggf. ergänzte Kopie>, geaendert }` zurückgeben. `project` selbst bleibt unverändert
   (keine Mutation des Arguments).

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `project` | ein bereits geparstes, geladenes `Project` | wird **nicht** verändert (reine Funktion) |
| `eingebauteMarkeId` | die `id` der eingebauten Fitnessworld24-Marke, wie sie in `marken.json` steht | nicht leerer String; **diese Funktion prüft nicht**, ob die ID tatsächlich zu einer Marke im Bestand gehört – das ist Sache des Aufrufers |

Ausgang: `{ project, geaendert }` – kein `Ergebnis<T>` und kein Fehlerfall, da die Funktion rein ist
und keine Nutzlast von außen validiert (sie verarbeitet bereits geladene, interne Daten).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „Die Migration legt daraus die eingebaute Marke in `marken.json` an (`eingebaut: true`, `parent:
  null`, neue `id`), setzt `Project.standardMarkeId` und `Aktion.markeId` aller Projekte darauf und
  entfernt das Feld aus `config.json`." (TK 9.15.1) – die beiden Zuweisungen (`standardMarkeId`,
  `markeId`) sind damit wörtlich vorgegeben.
- „Jede `project.json` und `config.json` trägt eine `schemaVersion`. Beim Laden: **höhere**
  (unbekannte) Version → Fehler (nicht raten); **ältere** Version → definierte Migration auf die
  aktuelle. So bleiben ältere Projekte nach App-Updates lesbar." (TK 9.5.5) – diese Migration ist
  genau eine solche „definierte Migration"; sie darf **kein** Feld stillschweigend verwerfen (nur
  `standardMarkeId` und `Aktion.markeId` werden ergänzt, sonst bleibt `project` unverändert).
- **Bereits gesetzte Referenzen werden nicht überschrieben.** Ein Projekt, in dem eine Aktion bereits
  eine `markeId` trägt (z. B. weil es nach v3.4 neu angelegt wurde, oder weil die Migration bereits
  einmal lief), bleibt **unangetastet** – diese Funktion ist damit idempotent: ein zweiter Lauf
  ändert nichts mehr.
- „**Der Main validiert jede eingehende Nutzlast**" (TK 9.1.1, Punkt 6) gilt hier sinngemäß nicht für
  externe IPC-Nutzlast (diese Funktion hat keine), sondern in seinem Geist: **kein** Feld wird ohne
  klaren, oben beschriebenen Grund verändert.

## Nicht selbst entscheiden – STOPP und fragen
- **ECHTE OFFENE FRAGE, die zentrale dieses Issues: Wie und wann läuft diese Migration über ALLE
  Projekte – und wer schreibt das Ergebnis zurück?** Zwei grundverschiedene, beide plausible
  Herangehensweisen stehen offen, und TK 9.15.1/9.5.5 entscheiden nicht zwischen ihnen:
  1. **Bulk-Migration beim App-Start**, analog zur Referenzprüfung `pruefeMarkenReferenzen` (M8-12,
     die bereits „über **alle** von `listeProjekte` gemeldeten Projekte" liest): Der Main iteriert
     beim Hochfahren über jedes gemeldete Projekt, liest dessen `project.json` **direkt** (nicht über
     den normalen „ein Projekt ist aktiv"-Weg, TK 9.5.1), wendet `migriereProjektAufMarke` an und
     schreibt bei `geaendert: true` zurück. **Vorteil:** Jedes Projekt ist sofort konsistent, auch
     eines, das nie wieder geöffnet wird – genau das braucht `pruefeMarkenReferenzen` (M8-12), das
     `aktion.markeId` über **alle** Projekte liest, **auch die nie geöffneten**. **Nachteil:** Es gibt
     **keinen vorgesehenen Schreibweg** für ein `project.json`, das nicht das eine im Speicher
     gehaltene, aktive Projekt ist (TK 9.5.1: „nur das aktive liegt im Speicher"; das D1-Lock, #32,
     schützt ausdrücklich nur dieses eine). Ein Direktzugriff auf `projects/<id>/project.json` für
     **andere** Projekte hat noch **keinen** etablierten, sicheren Schreibmechanismus – ein zweiter,
     unabhängiger Schreibpfad neben `schreibeProjekt` (#46) wäre ein neues Risiko (kein Backup, kein
     Lock, keine Garantie gegen einen gleichzeitig laufenden zweiten Zugriff auf **dasselbe**
     Projekt).
  2. **Lazy Migration** im bereits bestehenden Pfad für `project.json`-Schemamigrationen (#48,
     `öffneProjekt` erkennt die `schemaVersion`, TK 9.5.5): Wird ein Projekt geöffnet, prüft #48 seine
     `schemaVersion` und wendet u. a. diese Funktion an, **bevor** das Projekt aktiv wird – derselbe
     Schreibpfad wie jede andere Instant-Änderung. **Vorteil:** Nutzt die bereits vorhandene,
     abgesicherte Infrastruktur (Lock, Backup, Auto-Speichern) vollständig mit. **Nachteil:** Ein
     Projekt, das nach dem Update **nicht** erneut geöffnet wird, bleibt auf unbestimmte Zeit
     unmigriert – `pruefeMarkenReferenzen` (M8-12) liest dessen `Aktion.markeId` dann als fehlend, was
     **fälschlich** wie „referenziert die gesuchte Marke nicht" aussieht und im schlimmsten Fall eine
     tatsächlich noch benutzte Marke zum Löschen freigäbe (die Prüfung „unterzählt" statt zu
     überzählen).
  **Nicht selbst entscheiden** – die Wahl bestimmt, ob ein neues, ungesichertes Schreib-Verfahren nötig
  wird (Variante 1) oder ob die Referenzprüfung (M8-12) mit einer bekannten Unschärfe bei nie erneut
  geöffneten Alt-Projekten leben muss (Variante 2). **Abgrenzung, damit hier nichts doppelt entschieden
  wird:** Sollte Variante 2 gewählt werden, gehört die eigentliche Verdrahtung in #48 (`öffneProjekt`
  erkennt die `schemaVersion`) – dieses Issue liefert dafür bereits die reine Transformationsfunktion
  und muss dann **nicht** erneut geändert werden. Sollte Variante 1 gewählt werden, braucht es ein
  **eigenes**, hier noch nicht spezifiziertes Folge-Issue für den Bulk-Schreibmechanismus.
- **ECHTE OFFENE FRAGE: Was passiert, wenn ein einzelnes Projekt sich nicht öffnen bzw. nicht lesen
  lässt (defekte `project.json`, auch nach `.bak`-Fallback)?** Wird die Migration für die **übrigen**,
  lesbaren Projekte trotzdem angewendet (Teil-Erfolg), oder bricht der gesamte Migrationslauf ab, bis
  das defekte Projekt behoben ist? TK 9.5.5 und TK 9.15.1 schweigen dazu; `listeProjekte` (#35) meldet
  ein defektes Projekt bereits als `beschaedigt: true`, statt es auszulassen – ein Hinweis, dass die
  Liste **vollständig** bleiben soll, aber keine Aussage darüber, ob die **Migration** ein solches
  Projekt überspringt oder daran scheitert. **Nicht selbst festlegen** – ein Abbruch des gesamten
  Laufs wegen eines einzigen, ohnehin schon als beschädigt gemeldeten Projekts wäre unverhältnismäßig;
  ein stilles Überspringen ohne Protokoll ließe dasselbe Projekt für immer unmigriert.
- **ECHTE OFFENE FRAGE: Ist „das Feld aus config.json entfernen" (TK 9.15.1) ein tatsächlich
  persistiertes JSON-Feld oder der Rückbau von `config-store.leseMarke` (M1-17)?** `leseMarke` (M1-17)
  liest laut seiner eigenen Beschreibung „die gebündelte Markenkonfiguration" – eine gebündelte
  Konstante bzw. Datei, **nicht** nachweislich ein Feld, das jemals in `config.json` selbst
  geschrieben wurde (die Operationstabelle von `config-store`, TK 9.5.6, führt `leseKonfig`,
  `setzeAktivesProjekt`, `setzeExportZiel`, `setzeUIVoreinstellung` – kein `marke`-Feld). TK 9.15.1
  spricht dennoch wörtlich vom „Feld aus `config.json`". Ob das ein reales JSON-Feld ist, das diese
  Migration aus einer bestehenden Datei löschen muss, oder ob damit nur gemeint ist, dass
  `config-store.leseMarke` (M1-17) als Operation entfällt, ist **nicht zweifelsfrei zu klären**, ohne
  #17/#29 (config-store) erneut anzufassen. **Nicht selbst festlegen und nicht in dieser Datei
  „vorsorglich" ein Feld aus `config.json` löschen, dessen Existenz nicht gesichert ist** – das gehört,
  sobald geklärt, in ein Issue, das `config-store` selbst ändert (**nicht** in dieses, das nur
  `Project` liest/schreibt).
- **Verbot – kein Zugriff auf `marken.json` in dieser Datei.** Die `eingebauteMarkeId` wird als
  Parameter übergeben; diese Funktion ruft **weder** `ladeBestand` (M8-03) **noch** `eingebauteMarke`
  (M8-06) selbst auf – wer die ID ermittelt und übergibt, ist Teil der noch offenen Orchestrierung
  (s. o.).

## Definition of Done
- [ ] Ein `Project` ohne `standardMarkeId` (leer/undefiniert) und mit zwei Aktionen ohne `markeId`
      liefert nach `migriereProjektAufMarke` ein `Project`, bei dem **alle drei** Stellen die
      übergebene `eingebauteMarkeId` tragen, und `geaendert: true`
- [ ] Ein `Project`, dessen `standardMarkeId` bereits gesetzt ist (auf eine **andere**, beliebige ID),
      bleibt dort **unverändert** – auch wenn diese ID nicht zur eingebauten Marke gehört
- [ ] Ein `Project`, in dem **eine** von drei Aktionen bereits eine `markeId` trägt, bekommt **nur**
      die beiden fehlenden ergänzt; die bereits gesetzte bleibt unverändert
- [ ] Ein bereits vollständig migriertes `Project` (alle Referenzen gesetzt) liefert `geaendert: false`
      und ein `project`, das **deep-gleich** dem Original ist
- [ ] Das übergebene `project`-Argument ist nach dem Aufruf **unverändert** (keine Mutation – Test
      vergleicht Referenz und Inhalt vor/nach dem Aufruf)
- [ ] Ein zweifacher Aufruf mit demselben Ergebnis des ersten Aufrufs ändert nichts mehr
      (Idempotenz-Test)
- [ ] Die Datei enthält keinen `fs`-Import, kein `async`, keinen Zugriff auf `marken.json` oder
      `config.json` – Grep-Probe
- [ ] Keine Datei außerhalb von `src/main/marken-store/migration.ts` (+ zugehörige Testdatei) geändert
