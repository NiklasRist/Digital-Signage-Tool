### Issue M8-08: [marken-store] listeMarken – der vollständige, aufgelöste Marken-Bestand

## Ziel (in einem Satz)
Die Oberfläche bekommt mit einem Aufruf **alle** Marken des app-weiten Bestands – eigenständige
**und** abgeleitete –, jede davon bereits **vollständig aufgelöst** (Vererbung angewandt), sodass
kein Aufrufer je eine Teilmenge oder einen unaufgelösten Datensatz zu sehen bekommt.

## Modul & Datei
- Modul: `marken-store` [V2] (Main)
- Datei: `src/main/marken-store/liste.ts`
- Vertrag: Technisches Konzept **9.15.1** (Operationstabelle und Invarianten – Quelle der Wahrheit),
  **9.11.2** (Ableitung/Auflösung)
- Prozess/Speicher: V2 (`marken.json`), nur lesend

## Warum das im Gesamtsystem wichtig ist
Diese Funktion füllt die Marken-Liste im `marken-editor` (M8-22) und jede Auswahl, aus der eine
Aktion ihre `markeId` oder ein Projekt seine `standardMarkeId` bekommt. Zwei Fehler wären hier teuer:

**Erstens eine unaufgelöste Marke.** Lieferte diese Funktion den rohen Speicher-Eintrag einer
abgeleiteten Marke (nur die von ihr **gesetzten** Felder), müsste **jeder** Aufrufer selbst wissen,
dass fehlende Felder vom Parent kommen – genau die Vererbungslogik, die TK 9.11.2 an **einer**
Stelle bündelt: „**Die Auflösung geschieht an genau EINER Stelle:** im `marken-store`.
`leseMarke(markeId)` liefert die **fertig aufgelöste** Marke; kein Aufrufer sieht je eine Teilmenge,
keiner implementiert Vererbung selbst." Für `listeMarken` gilt dieselbe Zusage für **jeden** Eintrag
der Liste.

**Zweitens eine gefilterte Liste.** Anders als beim `vorlagen-store`, dessen `listeVorlagen` **nur**
Vorlagen mit `parent = null` liefert und Arbeitskopien ausdrücklich ausblendet (TK 9.12.1), gibt es
im `marken-store` **keine** Arbeitskopie-Halbfertigkeit, die verborgen werden müsste (s. Invarianten
unten für die Begründung). Ein Filter „nur eigenständige Marken" wäre hier ein erfundenes Konzept
ohne Grundlage im Vertrag und würde jede Saison-/Kampagnen-Marke aus der Auswahl nehmen, obwohl sie
laut FA-23 eine vollwertige, sofort nutzbare Marke ist.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/marken-store/liste.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { Marke } from '../../shared/contracts/marke'
import type { MarkenFehlercode } from './fehlercodes'
import { ladeBestand } from './schreibe-marken'
import { loeseMarkeAuf } from './vererbung'

// Fremde Aufrufe – vollstaendige Signaturen, damit hier nichts geraten wird:
//   M8-03: interface MarkenEintrag {
//            id: string; name: string; parent: string | null; eingebaut: boolean
//            farben: Partial<Record<FarbRolle, string>>
//            schriften: Partial<Record<SchriftRolle, Schrift>>
//            logo?: { datei: string; herkunft: Herkunft; seitenverhaeltnis: number } | null
//            sicherheit?: { horizontal: number; vertikal: number }
//            radien?: { pille: number; karte: number; klein: number }
//            schatten?: { versatzY: number; weichzeichnen: number; farbe: string }
//            slogan?: { text: string; aktiv: boolean }
//          }
//          // RAW Speicherform in marken.json – NICHT der geteilte Typ `Marke`. Bei einer
//          // abgeleiteten Marke (parent !== null) fehlen absichtlich Felder (TK 9.11.2, Teilmenge).
//          ladeBestand(): Promise<Ergebnis<MarkenEintrag[], MarkenFehlercode>>
//          // vollstaendiger, ROHER Bestand als TIEFE Kopie, IN Bestandsreihenfolge
//   M8-05: loeseMarkeAuf(eintrag: MarkenEintrag, bestand: MarkenEintrag[]): Ergebnis<Marke, MarkenFehlercode>
//          // wendet die feldweise Vererbung an (eine Stufe, TK 9.11.2); sucht den Parent im
//          // uebergebenen bestand; fehlt der referenzierte Parent -> marke_nicht_gefunden
//   M8-02: type MarkenFehlercode =
//            'marke_referenziert' | 'marke_eingebaut' | 'marke_nicht_gefunden'
//            | 'marken_datei_fehlt' | 'speicher_fehler'

/** Alle Marken des Bestands, jede AUFGELÖST. Keine Filterung, keine Sortierung. */
export async function listeMarken(): Promise<Ergebnis<Marke[], MarkenFehlercode>>
```

**Ablauf (verbindlich):**
1. `ladeBestand()` (M8-03) aufrufen. Fehler → unverändert zurückgeben, **nichts** auflösen.
2. Für **jeden** Eintrag, in Bestandsreihenfolge: `loeseMarkeAuf(eintrag, bestand)` (M8-05) aufrufen.
3. Liefert **irgendein** Aufruf `ok: false`, bricht die gesamte Funktion mit genau diesem Code ab
   (s. „Nicht selbst entscheiden" für die Begründung) – **keine** Teilliste, kein Auslassen des
   betroffenen Eintrags.
4. Sonst: `{ ok: true, wert: <alle aufgelösten Marken, in Bestandsreihenfolge> }`.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – | kein Parameter | – |

Ausgang bei Erfolg: `Ergebnis<Marke[]>` – **alle** Einträge des Bestands, jeder vollständig aufgelöst
(mindestens die eingebaute Fitnessworld24-Marke, s. M8-06). Reihenfolge = Bestandsreihenfolge.
Ausgang bei Fehler: `speicher_fehler` (durchgereicht von `ladeBestand`), `marke_nicht_gefunden`
(verwaiste Ableitung, durchgereicht von `loeseMarkeAuf`), sowie `unbekannter_fehler` aus dem
generischen Satz (#12/#22).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operations-Zeile, wörtlich (TK 9.15.1): „`listeMarken` | – → `Ergebnis<Marke[]>` –
  **aufgelöst**, einschließlich abgeleiteter"
- „**Die Vererbung wird an genau EINER Stelle aufgelöst** – hier. `leseMarke` und `listeMarken`
  liefern **fertige** Marken; kein Aufrufer sieht je eine Teilmenge." (TK 9.15.1)
- „**Marken sind ableitbar (`parent`), und die Vererbung wird an genau EINER Stelle aufgelöst**
  (9.11.2, 9.15.1)." (TK, Nachtrag v3.4 Punkt 2)
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Kein `throw`. „**Ausschreiben statt andeuten.** In **allen** Operations-Signaturen von Abschnitt 9
  steht die Hülle **explizit**" (TK 9.1.1) – deshalb `Promise<Ergebnis<Marke[], MarkenFehlercode>>`
  und nicht `Promise<Marke[]>`.
- „**Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code." (TK 9.1.1, Punkt 7) – ein
  Fehler aus `ladeBestand` oder `loeseMarkeAuf` wird **durchgereicht**, nicht in eine leere oder
  verkürzte Liste verwandelt.
- **Kein Zugriff auf `fs`.** Der Dateizugriff läuft ausschließlich über `ladeBestand` (M8-03).
- **Keine Zwischenspeicherung in dieser Datei.** Der Bestand wird bereits in M8-03 im Speicher
  gehalten; ein zweiter Zwischenspeicher hier liefert nach einer Änderung veraltete Marken.

**ENTSCHIEDEN – warum diese Funktion NICHT filtert (lokale Entscheidung, mit Begründung).** Beim
`vorlagen-store` verschwinden Arbeitskopien aus `listeVorlagen`, weil sie ein **bewusst halbfertiger**
Zwischenstand sind: „Arbeitskopien (`parent ≠ null`) sind nicht auswählbar. `composer` und
`action-editor` bekommen sie nicht angeboten – halbfertige Vorlagen können nicht in einen Render
geraten." (TK 9.12.1) Eine abgeleitete **Marke** ist dagegen kein Zwischenstand: Sie entsteht fertig
über `erstelleMarke(name, parentId)` (M8-10) und ist ab dem ersten Aufruf sofort nutzbar – FA-23
nennt sie ausdrücklich „einen Saison- oder Kampagnen-Look", keinen Entwurf. Es gibt im `marken-store`
kein zweites Feld, das „im Bearbeiten" von „fertig" unterscheidet (`bearbeiteMarke`, M8-11, ändert
die Marke selbst, es entsteht **keine** Kopie). Ein Filter auf `parent === null` hätte deshalb keine
Entsprechung im Datenmodell und würde **jede** Saison-Marke aus jeder Auswahl nehmen.

**ENTSCHIEDEN – Abbruch statt Auslassen bei einer nicht auflösbaren Marke.** Kann ein Eintrag nicht
aufgelöst werden (seine `parent`-Referenz zeigt ins Leere – strukturell nur durch Datei-Korruption
möglich, da `löscheMarke`, M8-13, genau das verhindert), liefert die gesamte Funktion
`marke_nicht_gefunden` statt den betroffenen Eintrag stillschweigend wegzulassen. Begründung wie bei
der Referenzprüfung des `vorlagen-store` (TK 9.12.1, M4-12): Eine verkürzte Liste sähe für den
Nutzer wie eine vollständige aus, und eine fehlende Marke in einer Auswahl ist nicht von „gibt es
nicht" zu unterscheiden.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `ladeBestand` meldet `speicher_fehler` | `speicher_fehler` | unverändert durchgereicht; **keine** leere Liste als Ersatz |
| ein Eintrag hat `parent !== null`, aber die Parent-`id` steht nicht im Bestand | `marke_nicht_gefunden` | Abbruch der gesamten Funktion, **keine** Teilliste |
| Bestand enthält genau einen Eintrag (nur die eingebaute Marke) | – | **kein Fehler**: `{ ok: true, wert: [<eingebaute Marke>] }` |
| unerwartete Ausnahme | `unbekannter_fehler` | gefangen und als Hülle gemeldet, kein `throw` |

## Nicht selbst entscheiden – STOPP und fragen
- **ERLEDIGT – nicht mehr melden.** Die gemeldete Lücke war echt und ist mit **TK v3.5**
  geschlossen: Die aufgelöste `Marke` trägt den Herkunfts-Stempel **`herkunftJeFeld`** als
  eigenes Feld (TK 9.11.2), gesetzt an der einen Auflösungsstelle (M8-05). **Diese Signatur
  bleibt dadurch unverändert** – der Stempel steckt im **Typ `Marke`**, nicht in einer
  zusätzlichen Rückgabeform; es gibt weiterhin **keine** zweite, unaufgelöste Leseoperation.
  Der Editor (M8-26) bekommt die Information damit an der Marke mit.
- **Reihenfolge bei mehrfacher, aber je einzeln gültiger Auflösung:** Wird `loeseMarkeAuf` pro
  Eintrag unabhängig aufgerufen (wie oben beschrieben) oder sollte der Bestand für Performance einmal
  vorindiziert werden (z. B. eine `Map<id, MarkenEintrag>`)? Beides ist fachlich gleichwertig; falls
  M8-05 eine bestimmte Aufrufform erwartet (z. B. nur ein `bestand`-Array, kein Index), gilt die dort
  ausgeschriebene Signatur unverändert – **kein** eigener Index-Aufbau, der von M8-05 unbemerkt bliebe.

## Definition of Done
- [ ] Bei frisch angelegter `marken.json` (nur die eingebaute Marke, M8-06) liefert `listeMarken`
      genau ein Element
- [ ] Ein Bestand mit einer eigenständigen und zwei abgeleiteten Marken liefert alle drei, in
      Bestandsreihenfolge, jede mit `loeseMarkeAuf` aufgelöst (Spy: genau ein Aufruf je Eintrag)
- [ ] Für eine abgeleitete Marke, deren `farben.akzent` gesetzt ist und deren übrige `FarbRolle`n
      fehlen, enthält das Ergebnis-Element **alle** `FarbRolle`n (die fehlenden aus dem Parent) –
      Nachweis, dass `loeseMarkeAuf` tatsächlich verwendet und sein Ergebnis nicht verworfen wird
- [ ] Meldet `ladeBestand` `speicher_fehler`, liefert `listeMarken` genau diesen Code und
      `loeseMarkeAuf` wird nachweislich **nicht** aufgerufen (Spy: null Aufrufe)
- [ ] Liefert `loeseMarkeAuf` für **einen** Eintrag `marke_nicht_gefunden`, ist das Gesamtergebnis
      dieser Code – **kein** Ergebnis mit den übrigen, erfolgreich aufgelösten Marken
- [ ] Die Datei enthält keinen `fs`-Import und keinen eigenen Zwischenspeicher – Grep-Probe
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze)
- [ ] Keine Datei außerhalb von `src/main/marken-store/liste.ts` (+ zugehörige Testdatei) geändert
