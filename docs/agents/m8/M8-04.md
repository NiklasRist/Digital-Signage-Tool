### Issue M8-04: [marken-store] Ereignis marken:autoSpeichernStatus – Speicherfehler sichtbar machen

## Ziel (in einem Satz)
Ein gescheiterter Schreibvorgang des Marken-Bestands – insbesondere ein entprellter, den niemand
gerade erwartet – wird über einen **eigenen** Ereignis-Kanal an die Oberfläche gemeldet, sodass
„deine Marke ist nicht gesichert" nie mit „dein Projekt ist nicht gesichert" verwechselt wird.

## Modul & Datei
- Modul: `marken-store` [V2] (Main)
- Datei: `src/main/marken-store/speicher-status.ts`
- Vertrag: Technisches Konzept **9.15.1** (eigener Kanal, Begründung), **9.5.4**
  (`project:autoSpeichernStatus` – das Verhalten, dem dieser Kanal gleichartig folgt), **9.12.1**
  (`vorlagen:autoSpeichernStatus` – dieselbe Bauweise beim `vorlagen-store`), **9.1.1** (Ereignis-
  Konvention) – Quelle der Wahrheit
- Prozess/Speicher: V2; kein eigener Dateizugriff – beobachtet nur M8-03

## Warum das im Gesamtsystem wichtig ist
`bearbeiteMarke` (M8-11) sichert **entprellt**: Der Aufrufer bekommt sein `ok: true` (Änderung „gültig
übernommen im Speicher", TK 9.5.4), lange bevor der eigentliche Schreibvorgang – 4 Sekunden später,
im Hintergrund – überhaupt läuft. Scheitert **der**, gibt es **keine Antwort**, an die sich ein
Fehler hängen könnte; ohne diese Datei ist ein Fehlschlag **vollständig unsichtbar**, und eine im
`marken-editor` über Minuten bearbeitete Marke steht beim nächsten Start wieder auf dem alten Stand –
ohne dass der Nutzer je erfahren hätte, dass etwas fehlte.

**Warum ein eigener Kanal statt einer Mitbenutzung von `project:autoSpeichernStatus`:** „Ein
**eigener** Kanal … ist nötig, weil die Oberfläche „deine Marke ist nicht gesichert" von „dein Projekt
ist nicht gesichert" unterscheiden muss – der Bestand ist app-weit und hängt nicht am geladenen
Projekt." (TK 9.15.1) Eine Marke ohne offenes Projekt zu bearbeiten (z. B. eine Partner-Marke direkt
nach dem App-Start) ist ein regulärer Ablauf; ein gemeinsamer Kanal würde dem Nutzer entweder einen
Projekt-Hinweis zeigen, obwohl gar kein Projekt offen ist, oder den Marken-Fehler unter dem
Projekt-Hinweis verstecken.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/marken-store/speicher-status.ts
import type { MarkenFehlercode } from './fehlercodes'
import type { GenerischerFehlercode } from '../../shared/contracts/ergebnis'
import { aufSchreibversuch } from './schreibe-marken'

// Fremde Aufrufe – vollstaendige Signaturen, damit hier nichts geraten wird:
//   M8-03: aufSchreibversuch(
//            hoerer: (ergebnis: { erfolgreich: true }
//                             | { erfolgreich: false; code: MarkenFehlercode }) => void,
//          ): () => void
//          // main-interner Hoerer, fuer JEDEN abgeschlossenen Schreibversuch (sofort/entprellt/Flush)

/**
 * Ereignisform des Speicherstatus dieses Stores. Gleichartig zu `AutoSpeichernEreignis` des
 * project-store (#47) und `VorlagenSpeichernEreignis` (M4-04) – TK 9.15.1: "gleichartig zu
 * `vorlagen:autoSpeichernStatus` (9.12.1)". KEINE Ergebnis-Huelle: Ereignisse tragen keine
 * (TK 9.1.1 Punkte 2 und 5).
 */
export type MarkenSpeichernEreignis =
  | { typ: 'gespeichert' }
  | { typ: 'fehler'; code: MarkenFehlercode | GenerischerFehlercode }
// Kanalname (an ipc-gateway zu uebergeben, M8-31): "marken:autoSpeichernStatus"
// ("<modul>:<ereignis>", TK 9.1.1 Punkt 4)

/**
 * Registriert einen Hoerer fuer Statuswechsel des Marken-Speichers; Rueckgabewert ist die
 * ABMELDE-Funktion. Diese Datei kennt WEDER den Kanalnamen NOCH ein `BrowserWindow`: Sie meldet
 * main-intern. Den Weg auf den IPC-Kanal baut die Verdrahtung im `ipc-gateway` (M8-31).
 */
export function aufMarkenSpeichernEreignis(
  hoerer: (ereignis: MarkenSpeichernEreignis) => void,
): () => void
```

**Interne Übersetzung (verbindlich, Muster aus #47/M4-04):** Diese Datei abonniert bei ihrer
Initialisierung **einmal** `aufSchreibversuch` (M8-03) und hält dabei einen einzigen internen
Zustand `istInFehlerzustand: boolean` (Start: `false`):

1. Meldet `aufSchreibversuch` `{ erfolgreich: false, code }`: **immer** `{ typ: 'fehler', code }` an
   alle über `aufMarkenSpeichernEreignis` angemeldeten Hörer weiterreichen; `istInFehlerzustand = true`.
2. Meldet `aufSchreibversuch` `{ erfolgreich: true }` **und** `istInFehlerzustand` ist `true`:
   `{ typ: 'gespeichert' }` weiterreichen; `istInFehlerzustand = false`.
3. Meldet `aufSchreibversuch` `{ erfolgreich: true }` **und** `istInFehlerzustand` ist bereits `false`:
   **nichts** weiterreichen (kein Dauerfeuer aus „gespeichert" bei jedem Tastendruck – der Hinweis
   soll verschwinden, nicht blinken).
4. Ein werfender Hörer bringt weder die Übersetzung noch die übrigen Hörer zu Fall; der Wurf verlässt
   diese Datei nicht.
5. Ein zweimal angemeldeter Hörer wird zweimal gerufen – **keine** Entdopplung. Die Abmelde-Funktion
   entfernt genau eine Anmeldung.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `hoerer` | Callback für Statuswechsel | keine fachliche Validierung, reine Registrierung |

Ausgang: kein `Ergebnis<T>` – diese Funktion **ist** die Ereignis-Registrierung, kein Aufruf mit
Antwort (TK 9.1.1: „Ereignisse … tragen ebenfalls keine Hülle").

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „Die Schreib-Invarianten sind **dieselben** wie in 9.5.4 … und Speicherfehler werden **sichtbar**
  gemacht statt still verschluckt – über einen **eigenen** Kanal `marken:autoSpeichernStatus`,
  gleichartig zu `vorlagen:autoSpeichernStatus` (9.12.1). Ein eigener Kanal ist nötig, weil die
  Oberfläche „deine Marke ist nicht gesichert" von „dein Projekt ist nicht gesichert" unterscheiden
  muss – der Bestand ist app-weit und hängt nicht am geladenen Projekt." (TK 9.15.1)
- „**Speicherfehler sind sichtbar (NFA-02):** Scheitert eine Auto-Speicherung (Platte voll, Rechte),
  wird das **nicht still verschluckt** – die UI zeigt dauerhaft „nicht gespeichert" + automatischer
  Wiederholversuch; die Änderungen **bleiben im Speicher** (kein Rollback, kein Arbeitsverlust). Erst
  nach erfolgreichem Schreiben verschwindet der Hinweis." (TK 9.5.4) – **Folge hier:** Diese Datei
  entscheidet **nur**, ob und wann sie meldet; den Wiederholversuch selbst führt `M8-03`s
  Entprellungs-/Schreibmechanismus, **nicht** diese Datei.
- „**Kanalbenennung** … Ereignisse (Main → Renderer) heißen `<modul>:<ereignis>`, z. B.
  `queue:geaendert`, `render:fortschritt`." (TK 9.1.1, Punkt 4) – hier `marken:autoSpeichernStatus`.
- „Ereignisse (Main → Renderer) tragen ebenfalls keine Hülle" und „Ereignisse sind Einbahnstraßen und
  tragen keinen Endzustand." (TK 9.1.1, Punkte 2 und 5) – `MarkenSpeichernEreignis` ist deshalb
  **kein** `Ergebnis<T>` und **kein** Ersatz für den Rückgabewert der eigentlichen Schreiboperation.
- „**Die App hat GENAU EIN Fenster** – und jedes Ereignis geht an dieses eine Fenster." (TK 9.1.1,
  Punkt 10) – diese Datei kennt **kein** `BrowserWindow` und trifft **keine** Empfänger-Entscheidung;
  das Adressieren des einen Fensters liegt in der Verdrahtung (M8-31).
- „**Ereignisse vor dem Aufbau des Fensters verfallen still – es wird NICHT gepuffert (bindend).**"
  (TK 9.1.1) – diese Datei merkt sich **keine** verpasste Meldung für einen späteren Abonnenten; sie
  reicht nur an aktuell angemeldete Hörer weiter.

## Fehlerpfade (vollständig)
Entfällt im engeren Sinn – diese Datei liefert kein `Ergebnis<T>` und keinen eigenen Fehlercode. Ihr
einziger „Fehlerfall" ist ein werfender Hörer (s. Ablauf, Punkt 4): Der Wurf wird gefangen und
verlässt die Datei nicht; es entsteht **kein** `unbekannter_fehler` und **kein** Abbruch der
Übersetzung.

## Nicht selbst entscheiden – STOPP und fragen
- **ECHTE OFFENE FRAGE: Braucht der Marken-Bestand dieselben vier Sofort-Flush-Auslöser wie
  `project.json` (TK 9.5.4: Auftragsstart, Projektwechsel, Beenden, Ende eines D1-verändernden
  Auftrags)?** TK 9.15.1 verlangt nur „gleichartig" für das **Ereignis**, nicht für die
  **Flush-Auslöser** – TK 9.5.4s Vier-Fälle-Liste ist ausdrücklich für `project.json` formuliert und
  wird für `marken.json` nirgends wiederholt. Klar ist nur „**beim Beenden**" (dieselbe Grundlogik wie
  bei jedem anderen Auto-Speicher-Mechanismus: kein Schließen mit ausstehendem Schreiben) – dafür ruft
  der Main-Bootstrap (#3) `flushBestand()` (M8-03) auf, analog zu `project-store`/`vorlagen-store`.
  **Nicht entschieden** ist, ob zusätzlich (a) ein Wechsel des Marken-Reiters im `marken-editor`, (b)
  der Start eines Render-Auftrags (falls die gerade bearbeitete Marke referenziert wird) oder (c)
  überhaupt keiner der übrigen drei Fälle einen Flush auslösen soll. **Ein unabhängig schreibender
  Nachbar-Agent hat dieselbe Lücke bereits gefunden** (`docs/agents/m8/M8-22.md`, STOPP-Block:
  „Muss beim Schließen des Reiters „Marken" ein Sofort-Flush angestoßen werden? … legt TK 9.15.1
  **nicht** fest … melden und diesen Punkt offen lassen."). **Nicht raten, keinen Kanal erfinden.**
  Bis zur Klärung löst diese Datei **selbst keinen** Flush aus – sie meldet nur, was M8-03 ihr über
  `aufSchreibversuch` mitteilt.
- **Wiederholstrategie nach einem Fehlschlag.** TK 9.5.4 verlangt „automatischer Wiederholversuch",
  ohne Intervall oder Obergrenze zu nennen – dieselbe offene Frage wie bei `project-store` (#47) und
  `vorlagen-store` (M4-04). Der Wiederholversuch selbst gehört **nicht** in diese Datei (sie
  beobachtet nur), aber die Antwort muss mit `project-store`/`vorlagen-store` konsistent sein, sobald
  sie feststeht.
- **Verbot – keine eigene Fehler-Wiederholung.** Diese Datei plant **keinen** Timer, ruft **kein**
  `aendereBestand` (M8-03) erneut auf und enthält **keine** Backoff-Logik. Ein Wiederholversuch ist
  Sache des Schreibmechanismus (M8-03), nicht der Melde-Schicht.
- **Verbot – kein `webContents.send`, kein `ipcMain`, kein String `'marken:'` in dieser Datei.** Der
  Kanalname entsteht in der Verdrahtung des `ipc-gateway` (M8-31), die sich über
  `aufMarkenSpeichernEreignis` anmeldet.
