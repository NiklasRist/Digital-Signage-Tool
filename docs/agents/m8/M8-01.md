### Issue M8-01: [contracts] Typ Markennutzung definieren – die drei Trefferlisten der Referenzprüfung

## Ziel (in einem Satz)
Ein geteilter Typ trägt das vollständige Ergebnis der Marken-Referenzprüfung – betroffene Aktionen
(je mit Projekt-Bezug), betroffene abgeleitete Marken und die Projekte, die die Marke als
**Standardmarke** führen –, sodass die Lösch-Sperre und die Editor-Warnung dieselbe, einmal
definierte Form benutzen statt sie zu erraten.

## Modul & Datei
- Modul: `contracts/types` (geteilt)
- Datei: `src/shared/contracts/marke.ts` (Ergänzung des bestehenden Typs `Marke`, #52/M1-40)
- Vertrag: Technisches Konzept **9.15.1** (Operationstabelle: `löscheMarke`, `pruefeMarkenReferenzen`
  – Quelle der Wahrheit), **9.12.1** (`Vorlagennutzung`/`VorlagenReferenz` – das Muster, dem dieser
  Typ folgt), **9.1.1** (`fehler.daten` – Quelle für strukturierte Fehlerdaten)
- Prozess/Speicher: geteilt zwischen Main und Renderer; kein eigener Speicher – reist als Rückgabewert
  von `pruefeMarkenReferenzen` und als `fehler.daten` einer abgelehnten Löschung

## Warum das im Gesamtsystem wichtig ist
Ohne diesen Typ hat die Referenzprüfung des `marken-store` (M8-12, M8-13) keine Rückgabeform: TK
9.15.1 verlangt wörtlich, dass `löscheMarke` im Fehlerfall „Code `marke_referenziert` mit **allen
drei** Trefferlisten: betroffene **Aktionen** (je mit Projekt), betroffene **abgeleitete Marken** und
die **Projekte**, die die Marke als **Standardmarke** führen" liefert und dass
`pruefeMarkenReferenzen` „**Ergebnis<Markennutzung>**" zurückgibt – beide Operationen brauchen exakt
dieselbe Form, sonst zeigt die Warnung vor dem Löschen (TK 9.15.2, „Löschen fragt vorher") etwas
anderes als die tatsächliche Sperre.

Eine Marke hat, anders als eine Vorlage, **drei grundverschiedene** Referenzquellen: Aktionen in
Projekten (`aktion.markeId`, verteilt über D1, ein Fundort **pro Projekt**), abgeleitete Marken im
eigenen, app-weiten Bestand (`marke.parent`, V2, **kein** Projekt-Bezug) und Projekte, die die Marke
als **Standardmarke** führen (`Project.standardMarkeId`, D1, ein Fundort **je Projekt**, aber **ohne**
Aktions-Bezug – hier färbt die Marke den **Rahmen**, nicht ein einzelnes Segment). Ein einziger,
gemeinsamer „Fundort"-Typ für alle drei (wie `VorlagenReferenz`, das sowohl Aktionen als auch
Listenelemente über `{ projektId, projektName, id }` abbildet) würde jeweils ein Feld erzwingen, das
für die anderen Arten keinen Sinn hat: Eine abgeleitete Marke gehört **keinem** Projekt, und ein
Projekt, das die Marke als Standardmarke führt, hat **keine** Aktions-ID. Dieser Typ trägt deshalb
**drei** eigene Fundort-Formen statt einer wiederverwendeten.

**Warum die dritte Liste überhaupt existiert – wörtlich (TK 9.15.1):** „**Die dritte Liste ist der
Grund, warum diese Fassung entstand (v3.11).** Bis v3.10 kannte die Prüfung nur Aktionen und
abgeleitete Marken. Eine Marke, die ein Projekt als **Standardmarke** führt
(`Project.standardMarkeId`, 9.11.3), galt damit als **frei** und war löschbar – der nächste Render
dieses Projekts liefe in `marke_nicht_gefunden`, und zwar an der Stelle, an der die Marke den
**Rahmen** färbt (Band-Hintergrund und Split-Restflächen, 9.15.4): mitten in der Hauptbetriebsart.
FA-23 nennt seit Anforderungsdokument v1.4 deshalb **drei** Bedingungen." Wer die dritte Liste
wegließe, ließe die Sperre aus FA-23 **nirgends** greifen: Sie ist der einzige Ort, an dem der Treffer
`Project.standardMarkeId` überhaupt transportiert werden kann.

**Warum das ein eigenes, neues Issue ist und keine Erweiterung eines bestehenden:** `Marke` (#52) wird
bereits an anderer Stelle um `id`, `name`, `parent`, `eingebaut`, `logo | null` und `Herkunft`
erweitert (Zitat-Abgleich nach dem Anlegen von M8, s. `docs/agents/m8-zuschnitt.md`). Für
`Markennutzung` gibt es dagegen **keine** bestehende Datei, die man erweitern könnte – deshalb ein
neues Issue, das dieselbe Datei (`marke.ts`) **zusätzlich** anfasst. Das ist bewusst dieselbe Struktur
wie bei `Vorlagennutzung`/`VorlagenReferenz` (M4-01): Beide Nutzungs-Typen liegen **in derselben
Datei** wie das Fachobjekt, auf das sie sich beziehen (`vorlage.ts` bzw. `marke.ts`), nicht in einer
dritten Datei – der Renderer bekommt sie über **denselben** Import wie den Typ `Marke` selbst.

## Signatur (verbindlich – NICHT ändern)
```ts
// Ergänzung in src/shared/contracts/marke.ts – NICHT die bereits bestehenden Felder von Marke
// anfassen (id, name, parent, eingebaut, farben, schriften, logo, sicherheit, radien, schatten,
// slogan sind Gegenstand des separaten Zitat-Abgleichs zu #52, nicht dieses Issues).

/** Ein Fundort in einem Projekt (Referenzart 1: Aktionen tragen die Marke). */
export interface MarkenReferenz {
  projektId: string    // Project.id
  projektName: string  // Project.name – für die Meldung "in 2 Projekten"
  aktionId: string      // Aktions-ID des Treffers (Aktion.id, #14)
}

/** Ein Fundort im Marken-Bestand selbst (Referenzart 2: eine abgeleitete Marke). KEIN Projekt-Bezug –
 *  Marken sind app-weit; eine abgeleitete Marke gehört keinem Projekt. */
export interface AbgeleiteteMarkenReferenz {
  markeId: string    // id der abgeleiteten Marke
  markeName: string  // name der abgeleiteten Marke – für die Meldung
}

/** Ein Fundort im Projekt-Kopf (Referenzart 3: das Projekt führt die Marke als STANDARDMARKE).
 *  KEIN Aktions-Bezug – hier färbt die Marke den Rahmen (Band-Hintergrund, Split-Restflächen,
 *  TK 9.15.4), nicht ein einzelnes Segment. */
export interface StandardmarkenReferenz {
  projektId: string    // Project.id
  projektName: string  // Project.name – die Sperre nennt den NAMEN, nie nur eine Anzahl
}

/** Das vollständige Prüfergebnis: alle drei Trefferlisten, getrennt nach Referenzart. */
export interface Markennutzung {
  aktionen: MarkenReferenz[]                      // Treffer über aktion.markeId
  abgeleiteteMarken: AbgeleiteteMarkenReferenz[]  // Treffer über marke.parent === markeId
  standardInProjekten: StandardmarkenReferenz[]   // Treffer über Project.standardMarkeId
}
```

**ENTSCHIEDEN – die dritte Liste bekommt einen eigenen benannten Typ: keine Inline-Form, und nicht
`MarkenReferenz` wiederverwendet.** Der Vertrag schreibt sie inline aus
(`standardInProjekten: { projektId: string, projektName: string }[]`, TK 9.15.1, s. Invarianten); die
**Form ist damit vorgegeben**, der **Name** nicht. `StandardmarkenReferenz` trägt genau diese beiden
Felder unter genau diesen Namen – es ist dieselbe Form, nur benannt. Drei Gründe für den Namen:
(1) Diese Datei benennt die beiden anderen Fundort-Formen bereits (`MarkenReferenz`,
`AbgeleiteteMarkenReferenz`) – eine anonyme dritte daneben wäre die einzige Ausnahme und läse sich wie
ein Versehen. (2) Die Anzeige der Sperre (M8-29) und die Fehlerdaten-Auswertung brauchen einen Namen
für ihre Hilfsfunktionen; ohne ihn schreibt **jeder** Aufrufer die anonyme Form ein zweites Mal ab –
und genau dagegen existiert dieser Typ. (3) **`MarkenReferenz` darf hier nicht wiederverwendet
werden:** Sie trägt `aktionId`, und ein Projekt, das die Marke als Standardmarke führt, hat **keine**
Aktions-ID – das Feld müsste erfunden oder leer gelassen werden, und ein leeres Pflichtfeld ist genau
die Art Kompromiss, an der später jemand hängen bleibt.

**Diese Datei enthält ausschließlich Typen** – keine Laufzeit-Werte, keine Konstanten, keine
Vergleichs- oder Sortierlogik. Das Ermitteln der Treffer ist Sache von `pruefeMarkenReferenzen`
(M8-12) und `löscheMarke` (M8-13); dieser Typ liefert nur die Form, in der beide reden.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – | reine Typdefinition, kein Laufzeit-Eingang | – |

Ausgang bei Erfolg: `MarkenReferenz`, `AbgeleiteteMarkenReferenz`, `StandardmarkenReferenz` und
`Markennutzung` sind aus `src/shared/contracts/marke.ts` importierbar – vom Main **und** vom
Renderer, da der Typ als `fehler.daten` über die IPC-Grenze reist (TK 9.1.1).
Ausgang bei Fehler: entfällt (Typdefinition, keine Laufzeit-Fehlerpfade).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Der Vertrag schreibt die Form aus, wörtlich (TK 9.15.1, Codeblock):
  ```
  MarkenReferenz {             // ein Fundort in einem Projekt
    projektId:   string
    projektName: string        // für die Meldung „… in 2 Projekten"
    aktionId:    string        // Aktions-ID des Treffers (v3.12: hiess vorher id)
  }

  Markennutzung {
    aktionen:            MarkenReferenz[]                  // Treffer über aktion.markeId
    abgeleiteteMarken:   { id: string, name: string }[]     // Marken mit parent = dieser markeId
    standardInProjekten: { projektId: string, projektName: string }[]
                                                            // Treffer über Project.standardMarkeId
  }
  ```
  **Die drei Feldnamen `aktionen`/`abgeleiteteMarken`/`standardInProjekten` und ihre getrennte
  Führung sind damit wörtlich vorgegeben** – ebenso `aktionId` (**nicht** `id`; die Umbenennung ist
  TK v3.12) und die beiden Feldnamen `projektId`/`projektName` der dritten Liste.
  **Zwei Abweichungen dieser Datei vom Codeblock – beide entschieden, beide nur Benennung:**
  (a) Die zweite Liste heißt hier `AbgeleiteteMarkenReferenz` mit den Feldern `markeId`/`markeName`
  statt anonym mit `id`/`name`. Grund ist derselbe, mit dem der Vertrag in v3.12 `id` zu `aktionId`
  gemacht hat: „Der Vertrag folgt hier der genaueren Fassung." (TK, Nachtrag v3.12, Punkt 2) In einem
  Objekt, das **neben** `MarkenReferenz.projektId` steht, ist ein blankes `id` nicht allgemein,
  sondern nur ungenau. (b) Die dritte Liste bekommt den Namen `StandardmarkenReferenz` – **Felder und
  Typen identisch** zum Codeblock. **Verbindlich für die Umsetzung ist der Signaturblock oben**, nicht
  dieser Codeblock; er steht hier vollständig, damit die beiden Abweichungen sichtbar sind statt
  unbemerkt.
- „`löscheMarke` | `markeId` → `Ergebnis<void>`; im Fehlerfall Code `marke_referenziert` mit **allen
  drei** Trefferlisten: betroffene **Aktionen** (je mit Projekt), betroffene **abgeleitete Marken**
  und die **Projekte**, die die Marke als **Standardmarke** führen." (TK 9.15.1)
- „`pruefeMarkenReferenzen` | `markeId` → `Ergebnis<Markennutzung>` – **rein lesend**: ermittelt über
  **alle** Projekte, wer die Marke nutzt; speist die Warnung **vor** dem Löschen." (TK 9.15.1)
- „**Löschen blockiert bei Referenz**, es kaskadiert **nicht** – wie bei den Vorlagen (9.12.1). Eine
  Marke steckt in Aktionen, **möglicherweise in abgeleiteten Looks** und **möglicherweise als
  Standardmarke eines Projekts**; eine Kaskade änderte das Aussehen vieler Aktionen auf einen Schlag.
  Geprüft wird über **alle** Projekte, nicht nur das geladene, und über **alle drei** Referenzarten
  (s. `Markennutzung` oben): `aktion.markeId`, `Marke.parent` und `Project.standardMarkeId`. **Wer die
  dritte vergisst, hält eine benutzte Marke fälschlich für frei** – der Fehler zeigt sich erst beim
  nächsten Render des betroffenen Projekts, nicht beim Löschen." (TK 9.15.1) – deshalb tragen
  `MarkenReferenz` **und** `StandardmarkenReferenz` `projektId`/`projektName`: Der Nutzer muss
  erfahren, **in welchem** Projekt der Treffer liegt, nicht nur, dass es einen gibt.
- „**Namentlich, nicht als Zahl.** Alle drei Listen tragen Namen, nicht nur Anzahlen – bei
  `standardInProjekten` den **Projektnamen**. Ohne ihn stünde der Nutzer vor „geht nicht, 2 Projekte"
  und wüsste nicht, **welche**; die Sperre wäre eine Sackgasse. Den Ausweg baut `setzeStandardMarke`
  (9.5.2): Der Editor kann von hier aus in die `projekt-verwaltung` verweisen, wo sich die
  Standardmarke wechseln lässt." (TK 9.15.1) – das ist der Grund, warum `StandardmarkenReferenz`
  `projektName` **führen muss** und eine blanke `projektId[]` nicht genügt.
- Anforderungsdokument v1.4, FA-23, wörtlich: „Eine Marke lässt sich nur löschen, wenn **keine
  Aktion**, **keine abgeleitete Marke** und **kein Projekt als Standardmarke** sie mehr nutzt." – drei
  Bedingungen, drei Listen.
- **Strukturierte Fehlerdaten** (TK 9.1.1): „Manche Fehler sind erst mit ihren Nutzdaten bedienbar:
  `asset_referenziert` muss die **betroffenen Listenelemente** nennen (`{ referenzenIds: string[] }`,
  9.4.9), `vorlage_referenziert` beide Trefferlisten (9.12.1), `marke_referenziert` alle drei –
  einschließlich der **Projekte**, die die Marke als Standardmarke führen (`Markennutzung`, 9.15.1)."
  – für `marke_referenziert` ist `Markennutzung` genau diese Nutzlast; sie ist **typisiert und
  dokumentiert dort, wo der Code vergeben wird** (M8-13), aber die **Form** steht hier, an der Quelle,
  damit sie nicht zweimal erfunden wird.
- Vorbild `Vorlagennutzung`/`VorlagenReferenz` (TK 9.12.1, wörtlich):
  ```
  VorlagenReferenz {           // ein Fundort
    projektId:   string
    projektName: string        // für die Meldung „… in 2 Projekten"
    id:          string        // Aktions-ID bzw. Listenelement-ID des Treffers
  }
  Vorlagennutzung {
    aktionen:       VorlagenReferenz[]   // Treffer über aktion.vorlagenId
    listenelemente: VorlagenReferenz[]   // Treffer über listenelement.einblendung.bandVorlageId
  }
  ```
  **Dieses Zitat bleibt unverändert: `VorlagenReferenz.id` heißt weiterhin `id`** – zu Recht, weil
  eine Vorlage auch von **Listenelementen** benutzt wird und der Fundort dort beides sein kann. Die
  Umbenennung zu `aktionId` betrifft **nur** `MarkenReferenz` (TK v3.12).
  `MarkenReferenz`/`Markennutzung` übernehmen dieselbe Bauweise (ein Fundort-Typ pro Referenzart, ein
  Sammel-Typ mit einer Liste je Art) – **abweichend nur dort, wo die Referenzart selbst abweicht**:
  Referenzart 2 hat keinen Projekt-Bezug, also bekommt sie einen **eigenen** Fundort-Typ
  (`AbgeleiteteMarkenReferenz`) statt denselben `MarkenReferenz` mit einem sinnlosen Projekt-Feld;
  Referenzart 3 hat zwar einen Projekt-Bezug, aber **keine Aktion**, und bekommt deshalb ebenfalls
  einen eigenen (`StandardmarkenReferenz`) statt `MarkenReferenz` mit einer leeren `aktionId`.

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – keine dritte Datei.** `MarkenReferenz`, `AbgeleiteteMarkenReferenz`,
  `StandardmarkenReferenz` und `Markennutzung` gehören in `src/shared/contracts/marke.ts` –
  **nicht** in eine neue `markennutzung.ts`. Begründung:
  Sie sind Nutzungs-Metadaten **von** `Marke` (dieselbe Bauweise wie `Vorlagennutzung` in
  `vorlage.ts`), und ein zweiter Import-Pfad für eng zusammengehörende Typen ist ein unnötiger zweiter
  Ort, an dem sie auseinanderlaufen können.
- **Verbot – `id`/`name`/`parent`/`eingebaut`/`logo`/`Herkunft` an `Marke` selbst NICHT anfassen.**
  Diese Felder sind Gegenstand des separaten Zitat-Abgleichs zu #52 (s. `m8-zuschnitt.md`). Wer sie
  hier „nebenbei mitzieht", weil ohnehin dieselbe Datei geöffnet ist, erzeugt genau die
  Datei-Kollision zwischen zwei Issues, die dieses Projekt wiederholt gefunden hat.
- **Verbot – kein `aktionTitel` oder ähnliches Zusatzfeld an `MarkenReferenz`.** Das Vorbild
  `VorlagenReferenz` trägt nur die ID des Fundorts, keinen Anzeigenamen der Aktion; dieser Typ bleibt
  strukturell gleich. Ob die Oberfläche zusätzlich einen Aktions-Titel anzeigen will, ist eine Frage
  der aufrufenden Stelle (sie kann `aktionId` gegen die ohnehin geladenen Projektdaten auflösen), nicht
  dieses geteilten Typs.
- **ERLEDIGT – nicht mehr melden.** Die gemeldete Abweichung war echt und ist **behoben**: Der
  Entwurf `docs/agents/m8/M8-29.md` ging zeitweise von einer eigenen Datei
  `src/shared/contracts/markennutzung.ts` und einem Zusatzfeld `aktionTitel` an `MarkenReferenz` aus.
  M8-29 ist inzwischen nachgezogen – es importiert `Markennutzung` aus
  `src/shared/contracts/marke.ts`, führt `MarkenReferenz`/`AbgeleiteteMarkenReferenz`/`Markennutzung`
  genau in der hier festgelegten Form und hält das fehlende `aktionTitel`-Feld ausdrücklich fest.
  Die Signatur oben ist damit die einzige im Umlauf; hier ist nichts mehr zu klären.
