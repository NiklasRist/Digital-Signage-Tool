### Issue M8-05: [marken-store] Vererbung auflösen – die eine Stelle

## Ziel (in einem Satz)
Ein roher `MarkenEintrag` wird zusammen mit dem Bestand, in dem er liegt, in eine vollständig
aufgelöste `Marke` verwandelt – feldweise, eine Vererbungsstufe tief –, sodass diese eine Funktion
die einzige Stelle im ganzen System ist, die je Werte aus einer Parent-Marke übernimmt.

## Modul & Datei
- Modul: `marken-store` [V2] (Main)
- Datei: `src/main/marken-store/vererbung.ts`
- Vertrag: Technisches Konzept **9.11.2** (Ableitungsregel, wörtlich zu übernehmen – Quelle der
  Wahrheit), **9.15.1** (warum die Auflösung an genau einer Stelle geschieht), **9.10.9**
  (dieselbe Begründung bei den Farb-Rollen), **9.15.4** (die 19 Aufrufer, die sich auf diese
  Funktion verlassen)
- Prozess/Speicher: V2; **reine Funktion, kein I/O** – sie liest weder Datei noch Bestand selbst,
  sondern bekommt beides als Argument (s. Begründung unten)

## Warum das im Gesamtsystem wichtig ist
Das ist das Herzstück des Meilensteins, gemessen an der Zahl der Abhängigen: „**Die Auflösung
geschieht an genau EINER Stelle:** im `marken-store`. `leseMarke(markeId)` liefert die **fertig
aufgelöste** Marke; kein Aufrufer sieht je eine Teilmenge, keiner implementiert Vererbung selbst. Das
ist dieselbe Begründung wie bei den Farb-Rollen (9.10.9): **neunzehn** Aufrufer holen die Marke
(9.15.1) – neunzehn eigene Vererbungslogiken liefen unweigerlich auseinander." (TK 9.11.2) Wäre diese
Funktion falsch oder gäbe es sie nicht, hätte **jeder** der neunzehn Aufrufer (M8-09 zitiert die
vollständige Liste: `#77`, `#112`, `#119`, `#134` … `#262`) seine eigene Vererbung gebaut – ein Fehler
in einer einzigen dieser neunzehn Kopien wäre unsichtbar, bis genau der betroffene Zeichenpfad einmal
mit einer abgeleiteten Marke läuft.

**Warum eine reine Funktion und kein eigener Lesezugriff.** Diese Funktion liest **nicht** selbst
`marken.json` – sie bekommt den bereits geladenen Bestand als Argument (`bestand`, von `M8-03`s
`ladeBestand()`). Begründung: (a) Testbarkeit ohne Dateisystem – die Vererbungsregel ist reine
Berechnung, jeder Testfall braucht nur zwei Objekte, keine temporäre Datei; (b) die Aufrufer
`leseMarke` (M8-09) und `listeMarken` (M8-08) laden den Bestand ohnehin **einmal** und rufen diese
Funktion **mehrfach** auf demselben Bestand auf – ein eigener Lesezugriff hier würde den Bestand
mehrfach laden oder eine zweite Zwischenspeicherung nötig machen, die mit der aus M8-03 auseinander-
laufen könnte.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/marken-store/vererbung.ts
import type { Marke, FarbRolle, SchriftRolle } from '../../shared/contracts/marke'
import type { MarkenEintrag } from './schreibe-marken'
import type { MarkenFehlercode } from './fehlercodes'
import type { Ergebnis } from '../../shared/contracts/ergebnis'

// Fremde Aufrufe – vollstaendige Signaturen, damit hier nichts geraten wird:
//   M8-03: interface MarkenEintrag {
//            id: string; name: string; parent: string | null; eingebaut: boolean
//            farben: Partial<Record<FarbRolle, string>>
//            schriften: Partial<Record<SchriftRolle, Schrift>>
//            logo?: { datei: string; herkunft: Herkunft; seitenverhaeltnis: number } | null
//            sicherheit?: { horizontal: number; vertikal: number }
//            radien?: { pille: number; karte: number; klein: number }
//            schatten?: { versatzY: number; weichzeichnen: number; farbe: string }
//            slogan?: { text: string; aktiv: boolean }
//          }
//   M8-02: type MarkenFehlercode =
//            'marke_referenziert' | 'marke_eingebaut' | 'marke_nicht_gefunden'
//            | 'marken_datei_fehlt' | 'speicher_fehler'

/**
 * Loest die Vererbung eines EINZELNEN Eintrags auf. `bestand` ist der VOLLSTAENDIGE, bereits
 * geladene Bestand (aus dem der Parent bei Bedarf gesucht wird) – NICHT nur der bereits gefundene
 * Parent, damit der Aufrufer keinen zweiten Suchschritt braucht und diese Funktion die einzige
 * Stelle bleibt, die je einen Parent nachschlaegt.
 *
 * Ist `eintrag.parent === null`, wird `eintrag` unveraendert (reshaped) als `Marke` zurueckgegeben –
 * die Systeminvariante, dass eine NICHT abgeleitete Marke IMMER vollstaendig befuellt ist, wird HIER
 * nicht erneut geprueft (sie ist durch M8-06/M8-10 strukturell erzwungen).
 *
 * SETZT AUSSERDEM `Marke.herkunftJeFeld` (TK 9.11.2, seit v3.5): je Feld "eigen" oder "geerbt",
 * beim `logo` zusaetzlich "keins" (wenn die aufgeloeste `logo` null ist). Die Angabe entsteht IM
 * SELBEN SCHRITT wie die Wertwahl - nicht durch einen nachtraeglichen Vergleich mit dem Parent,
 * der waere falsch (ein bewusst gleich gesetzter Wert gilt als "eigen") und ist verboten.
 * Bei `parent === null` ist der Stempel durchgehend "eigen", nie leer.
 *
 * Ist `eintrag.parent !== null`, wird der Parent in `bestand` gesucht:
 *   - fehlt er (verwaiste Ableitung) -> { ok: false, fehler: { code: 'marke_nicht_gefunden', ... } }
 *   - sonst: feldweise Vererbung, s. Ablauf unten. Es wird davon ausgegangen, dass der Parent selbst
 *     `parent === null` hat (Kettensperre, durchgesetzt von M8-10) – diese Funktion prueft die
 *     Kettentiefe NICHT erneut (s. "Nicht selbst entscheiden").
 */
export function loeseMarkeAuf(
  eintrag: MarkenEintrag,
  bestand: MarkenEintrag[],
): Ergebnis<Marke, MarkenFehlercode>
```

**Ablauf (verbindlich):**
1. `eintrag.parent === null` → Ergebnis ist `eintrag`, unverändert in die Form `Marke` gebracht
   (`farben`/`schriften` werden von `Partial<Record<…>>` nach `Record<…>` durchgereicht, ohne Werte zu
   ändern oder zu ergänzen – die Vollständigkeit ist eine fremde Invariante, s. o.). `{ ok: true,
   wert: <Marke> }`.
2. `eintrag.parent !== null`: In `bestand` den Eintrag mit `id === eintrag.parent` suchen.
   - Nicht gefunden → `{ ok: false, fehler: { code: 'marke_nicht_gefunden', meldung: '…' } }`. **Kein**
     Rückfall auf den unaufgelösten `eintrag`.
   - Gefunden (`parentEintrag`): Für jede der zwölf `FarbRolle`n und vier `SchriftRolle`n gilt
     `ergebnis.farben[rolle] = eintrag.farben[rolle] !== undefined ? eintrag.farben[rolle] :
     parentEintrag.farben[rolle]` (analog für `schriften`). Für `logo`, `sicherheit`, `radien`,
     `schatten`, `slogan` gilt jeweils als **ganzes Feld**: `ergebnis.X = eintrag.X !== undefined ?
     eintrag.X : parentEintrag.X`. `id`, `name`, `parent`, `eingebaut` kommen **ausschließlich** von
     `eintrag` selbst – niemals vom Parent.
   - `{ ok: true, wert: <zusammengesetzte Marke> }`.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `eintrag` | der aufzulösende, rohe Bestandseintrag | muss ein Element von `bestand` sein (nicht erzwungen, aber vorausgesetzt) |
| `bestand` | der vollständige, geladene Bestand | wird **nicht** verändert (reine Funktion); `eintrag.parent`, falls gesetzt, wird darin gesucht |

Ausgang bei Erfolg: `Ergebnis<Marke>` – jedes Feld gefüllt (bei `parent === null`: die eigenen Werte;
bei `parent !== null`: eine Mischung aus eigenen und geerbten Werten, feldweise).
Ausgang bei Fehler: `marke_nicht_gefunden` (verwaiste Ableitung – der referenzierte Parent steht nicht
in `bestand`). **Kein** anderer Code: Diese Funktion validiert keine Nutzlast von außen, sie
verarbeitet bereits gespeicherte Daten.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „Bei `parent ≠ null` sind `farben` und `schriften` **Teilmengen**: Für jede Rolle, die die
  abgeleitete Marke **nicht** setzt, gilt der Wert des Parents – **feldweise, nicht objektweise**. Ein
  Saison-Look, der nur `farben.akzent` setzt, erbt damit alle übrigen Farben, alle Schriften, Logo,
  Abstände, Radien, Schatten und Slogan. Setzt er ein Feld, gilt seins. Das gilt für **jedes** Feld
  außer `id`, `name`, `parent` und `eingebaut`." (TK 9.11.2)
- „**Ketten sind auf EINE Stufe begrenzt:** Ein Parent darf selbst keinen Parent haben. Sonst müsste
  die Auflösung beliebig tief laufen und die Referenzprüfung beim Löschen (9.15.1) rekursiv über einen
  Baum statt über eine Liste – beides ohne fachlichen Gewinn, denn zwei Stufen decken „Marke + Look"
  ab." (TK 9.11.2) – diese Funktion löst deshalb **maximal eine** Stufe auf: Sie ruft sich **nicht**
  rekursiv auf den Parent des Parents auf.
- „**Die Auflösung geschieht an genau EINER Stelle:** im `marken-store`. `leseMarke(markeId)` liefert
  die **fertig aufgelöste** Marke; kein Aufrufer sieht je eine Teilmenge, keiner implementiert
  Vererbung selbst." (TK 9.11.2) – **diese** Datei ist diese eine Stelle. Weder `leseMarke` (M8-09)
  noch `listeMarken` (M8-08) noch irgendeine andere Datei des Moduls darf `eintrag.farben[rolle]` und
  `parentEintrag.farben[rolle]` selbst vergleichen.
- „Es gibt genau eine Auflösungsstelle." (TK 9.10.9, für die Farb-Rollen; dieselbe Begründung gilt
  hier für die gesamte Marke.)
- **NEU mit TK v3.5 – diese Funktion SETZT den Herkunfts-Stempel:** „**Der Stempel `herkunftJeFeld` –
  Metadatum, nie Wertquelle (bindend).** Beim Auflösen hält der `marken-store` fest, welchen Zweig er
  **je Feld** genommen hat. Der Stempel trägt **keine Werte**, sondern ausschließlich die Angabe
  `"eigen"` oder `"geerbt"`" (TK 9.11.2). Er entsteht **genau hier** und nirgends sonst – wer den Wert
  eines Feldes aus dem Parent nimmt, schreibt `"geerbt"`, wer den eigenen nimmt, `"eigen"`. Die
  Entscheidung fällt **im selben Schritt** wie die Wertwahl; ein nachträglicher Vergleich der
  fertigen Marke mit dem Parent wäre **falsch** (ein bewusst gleich gesetzter Wert gälte sonst als
  geerbt, obwohl er künftigen Parent-Änderungen **nicht** folgt) und ist ausdrücklich **verboten**
  (TK 9.15.2).
- **Bei `parent === null` ist der Stempel durchgehend `"eigen"`** – **nie** leer, **nie** undefiniert,
  damit kein Aufrufer einen Sonderfall behandeln muss (TK 9.11.2). **`logo` trägt zusätzlich
  `"keins"`**, und zwar genau dann, wenn die aufgelöste `logo` `null` ist (weder eigen noch geerbt
  gesetzt) – dann greift das Ersatz-Logo (TK 9.10.10).
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2). Diese Funktion wirft **nie** – auch bei einer strukturell
  unerwarteten Eingabe (z. B. `eintrag` nicht Teil von `bestand`) liefert sie eine Hülle, keinen
  Absturz.

**ENTSCHIEDEN – Granularität außerhalb von `farben`/`schriften` ist FELD-, nicht UNTERFELD-genau
(lokale Festlegung, durch einen bereits verfassten Nachbarn bestätigt).** TK 9.11.2 spricht von
„feldweise, nicht objektweise" im Zusammenhang mit `farben`/`schriften` – beides sind `Record`-Typen,
bei denen „Feld" sinnvoll eine einzelne Rolle bezeichnet. Für `logo`, `sicherheit`, `radien`,
`schatten`, `slogan` (keine `Record`-Typen, sondern feste Objektformen) gibt es **keine** vergleichbare
Unterteilung in der TK-Formulierung. Die bereits geschriebene Nachbar-Datei `bearbeite-marke.ts`
(M8-11) legt diese Granularität bereits strukturell fest: Ihr `MarkenTeilwerte`-Typ modelliert
`sicherheit?: MarkenFeld<{ horizontal: number; vertikal: number }>` **als Ganzes**, nicht
`sicherheit?: { horizontal？: MarkenFeld<number>; vertikal?: MarkenFeld<number> }` – wer `sicherheit`
eigen setzt, setzt **beide** Werte gemeinsam; wer es an den Parent zurückgibt, gibt **beide** zurück.
Diese Funktion übernimmt dieselbe Granularität: **ein** Vergleich pro Top-Level-Feld, **kein**
Hinabsteigen in `sicherheit.horizontal` einzeln. Wäre das falsch, widerspräche `loeseMarkeAuf` der
Datenform, die `bearbeiteMarke` bereits erzeugt, und die beiden Dateien liefen auseinander.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `eintrag.parent !== null`, Parent-`id` nicht in `bestand` | `marke_nicht_gefunden` | kein Ergebnis; **kein** Rückfall auf den unaufgelösten `eintrag` |
| `eintrag.parent === null` | – (kein Fehler) | `eintrag` wird 1:1 als `Marke` zurückgegeben |
| gefundener Parent hat selbst `parent !== null` (verletzte Kettensperre) | – | s. „Nicht selbst entscheiden" – **kein** definierter Fehlercode hierfür, da die Kette laut TK 9.11.2 strukturell nie entstehen darf |

## Nicht selbst entscheiden – STOPP und fragen
- **ECHTE OFFENE FRAGE: Was passiert, wenn der gefundene Parent selbst `parent !== null` hat?** TK
  9.11.2 sagt, das darf strukturell nie vorkommen – die Kettensperre sitzt in `erstelleMarke` (M8-10).
  Tritt es dennoch auf (Dateikorruption, ein Fehler in M8-10, ein manuell bearbeitetes `marken.json`),
  ist unklar, ob diese Funktion (a) den Parent so behandelt, als wäre **sein** `parent`-Feld `null`
  (stillschweigend nur eine Stufe auflösen und den Rest ignorieren), (b) einen eigenen, hier noch
  nicht existierenden Fehlercode liefert, oder (c) `ungueltige_eingabe`/`unbekannter_fehler` als
  Notlösung verwendet. **Nicht selbst festlegen** – jede Variante hat eine echte Konsequenz für die
  Fehlerbehandlung der Aufrufer (M8-08, M8-09).
- **ECHTE OFFENE FRAGE: Was passiert, wenn selbst der Parent für eine Rolle/ein Feld keinen Wert
  trägt?** Die Systeminvariante „eine nicht abgeleitete Marke ist immer vollständig befüllt" wird von
  M8-06 (Seeding) und M8-10 (`erstelleMarke`) durchgesetzt, aber **nicht** von dieser Datei selbst
  geprüft (s. Signatur-Kommentar). Liegt dennoch eine Lücke vor (z. B. nach einer fehlerhaften
  Migration, M8-07), wäre das Ergebnis eine `Marke` mit einem `undefined`-Feld, obwohl der Typ
  `Record<FarbRolle, string>` das nicht zulässt. **Nicht selbst entscheiden**, ob das ein
  `unbekannter_fehler` werden soll oder ob die Lücke stillschweigend bestehen bleibt (Letzteres wäre
  ein Vertragsbruch gegenüber dem `Marke`-Typ).
- **Verbot – keine Rekursion über mehr als eine Stufe.** Auch wenn `bestand` es technisch erlaubt,
  ruft diese Funktion sich **nicht** selbst auf den Parent des Parents auf. Eine „vorsorgliche"
  Mehrstufen-Auflösung würde die Kettensperre aus M8-10 unterlaufen, ohne dass das an dieser Stelle
  sichtbar wäre.
- **Verbot – kein Zugriff auf `fs`, kein Aufruf von `ladeBestand` (M8-03).** Diese Funktion bekommt
  `bestand` ausschließlich als Argument.

## Definition of Done
- [ ] `loeseMarkeAuf(<eigenständiger, vollständiger Eintrag>, [<dieser Eintrag>])` liefert diesen
      Eintrag unverändert als `Marke` zurück
- [ ] Für eine abgeleitete Marke, die nur `farben.akzent` setzt, liefert `loeseMarkeAuf` eine `Marke`,
      bei der **alle** übrigen Farben, alle Schriften, `logo`, `sicherheit`, `radien`, `schatten` und
      `slogan` die Werte des Parents tragen, und `farben.akzent` den eigenen Wert (deckungsgleicher
      Test zu TK 9.11.2, Beispiel „Saison-Look setzt nur Farben")
- [ ] Eine abgeleitete Marke, die `sicherheit` **eigen** setzt, liefert dieses `sicherheit` **als
      Ganzes** – auch wenn der Parent andere Werte hätte; ein Test mit `sicherheit: { horizontal: 50,
      vertikal: 50 }` beim Kind zeigt, dass **keins** der beiden Felder vom Parent durchsickert
- [ ] Eine abgeleitete Marke ohne jedes eigene Feld (nur `id`, `name`, `parent`, `eingebaut`) liefert
      eine `Marke`, die in **jedem** übrigen Feld exakt dem Parent entspricht
- [ ] Eine abgeleitete Marke, deren `parent`-`id` nicht in `bestand` steht, liefert
      `marke_nicht_gefunden`
- [ ] **`herkunftJeFeld` ist im Ergebnis IMMER vollständig gefüllt** – für jede Farb-Rolle, jede
      Schrift-Rolle und jedes der Felder `logo`, `sicherheit`, `radien`, `schatten`, `slogan`; kein
      Schlüssel fehlt, keiner ist `undefined` (Test über die vollständigen Rollen-Listen)
- [ ] Bei einem **eigenständigen** Eintrag (`parent === null`) ist **jeder** Wert in
      `herkunftJeFeld` `"eigen"` – Ausnahme `logo`, das `"keins"` trägt, wenn die aufgelöste `logo`
      `null` ist
- [ ] Bei der abgeleiteten Marke, die **nur** `farben.akzent` setzt, ist
      `herkunftJeFeld.farben.akzent === 'eigen'` und **jeder** andere Eintrag `'geerbt'`
- [ ] **Setzt das Kind einen Wert, der mit dem des Parents ÜBEREINSTIMMT, steht dort `'eigen'`** –
      nicht `'geerbt'`. Das ist der Test, der den verbotenen Wert-Vergleich ausschließt: Er schlägt
      fehl, sobald jemand die Herkunft nachträglich aus einem Vergleich ableitet statt sie beim
      Auflösen mitzuschreiben
- [ ] `id`, `name`, `parent`, `eingebaut` im Ergebnis stammen **immer** von `eintrag`, nie vom Parent
      (Test mit unterschiedlichen Namen bei Kind und Parent)
- [ ] Die Funktion ist **rein**: Zwei Aufrufe mit identischen Eingaben liefern deep-gleiche Ergebnisse;
      `bestand` und `eintrag` sind nach dem Aufruf unverändert (Referenzvergleich/Deep-Freeze im Test)
- [ ] Die Datei enthält keinen `fs`-Import, keinen `async`, keinen Aufruf von `ladeBestand` – Grep-Probe
