### Issue M8-16: [marken-store] Lese-Protokoll `marken://` für den Ordner `marken-assets/`

## Ziel (in einem Satz)
Der Renderer bekommt importierte Marken-Dateien (Logos, Schriften) ausschließlich über ein eigenes,
schreibgeschütztes Protokoll `marken://<markeId>/<dateiname>` – analog zu `media://` –, ohne
jemals einen absoluten Pfad zu sehen, und ohne dass dafür eine zweite Pfad-Autorität entsteht.

## Modul & Datei
- Modul: `marken-store` [V2] (Main)
- Datei: `src/main/marken-store/marken-protokoll.ts`
- Vertrag: Technisches Konzept **9.15.3** (Bündelungs-Riegel – Quelle der Wahrheit für dieses Issue),
  **9.5.7** (`media://` als Vorbild), **9.1.1** (Abgrenzung IPC-Grenze vs. Protokoll-Handler)
- Prozess/Speicher: V2 (marken-assets/, nur lesend)

## Warum das im Gesamtsystem wichtig ist
Seit v3.4 kann jede Marke eigene Schrift- und Logo-Dateien mitbringen (`herkunft: "importiert"`,
9.15.3). Diese Dateien liegen im Datenort unter `marken-assets/<markeId>/`, **nicht** im
Programmordner – der Renderer darf das Dateisystem aber grundsätzlich nicht berühren (TK 9.1,
Variante A). Ohne dieses Protokoll hätte der Renderer **keinen** Weg, ein importiertes Logo
anzuzeigen oder eine importierte Schrift zu laden – `template-canvas` (M8-17, M8-20) und der
`marken-editor` (M8-24, M8-25) hängen beide direkt an dieser Datei.

Zwei lokale Fehlentscheidungen wären hier besonders teuer, weil sie lautlos bleiben, bis jemand einen
Marken-Editor öffnet oder eine importierte Marke rendert:

**Erstens eine zweite Pfad-Autorität.** Baut dieser Handler selbst `path.join('marken-assets',
markeId, dateiname)` zusammen, entsteht exakt die Doppelung, die TK 9.5.7 für `media://` ausschließt
– jede spätere Verschärfung der Traversal-Prüfung in M8-14 (`loeseMarkenDateiPfad`) würde diesen
Handler dann nicht mehr erreichen.

**Zweitens eine vermischte Fehlerbehandlung.** Ein Protokoll-Handler ist **kein** IPC-Kanal; er
beantwortet eine Fetch-artige `Request` mit einer `Response`. Wer hier `Ergebnis<T>` einbaut, baut
etwas, das der Renderer als `<link rel="preload">`/`FontFace`/`<img src="marken://…">` gar
nicht auswerten kann – der Browser erwartet einen HTTP-artigen Status, keine JSON-Hülle.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/marken-store/marken-protokoll.ts

/**
 * Die Schema-Beschreibung als DATEN, nicht als Aufruf. Der Bootstrap (M8-36) sammelt sie zusammen
 * mit MEDIA_SCHEMA (#9) und ruft protocol.registerSchemesAsPrivileged GENAU EINMAL auf.
 *
 * WARUM KEINE registriere...()-FUNKTION: registerSchemesAsPrivileged nimmt ein Array und darf laut
 * electron.d.ts "can be called only once" nur EINMAL gerufen werden. Zwei Registrierer - einer fuer
 * 'media', einer fuer 'marken' - haetten still entweder 'marken' unprivilegiert gelassen ODER
 * 'media' ausser Kraft gesetzt; dann fehlten in der Vorschau alle Projektmedien, ohne dass etwas
 * auf die Marken zeigt. Diese Datei ruft die Electron-API deshalb NICHT selbst auf.
 */
export const MARKEN_SCHEMA: CustomScheme
// scheme: 'marken'
// privileges: { standard: true, secure: true, supportFetchAPI: true, stream: true }
//   - dieselben VIER wie beim gebauten 'media'-Schema (#9, src/main/media-protokoll.ts).
//     TK 9.15.3: "Gleiche Bauart und gleiche Schutzregeln wie `media://` (9.5.7)".
//   - `standard`  : laesst marken://<markeId>/<dateiname> nach den ueblichen URL-Regeln in Host
//                   und Pfad zerlegen - sonst gibt es kein verlaessliches Trennen von markeId
//                   und Dateiname, und genau die beiden braucht loeseMarkenDateiPfad (M8-14).
//   - `secure`    : das Schema gilt als sicherer Kontext; ohne das behandelt Chromium die Inhalte
//                   wie unsicheres Fremdmaterial und blockiert sie in der geladenen Seite.
//   - `supportFetchAPI`: der Renderer laedt Logo-Bytes und Schriften VOR dem Zeichnen (TK 9.10.3).
//   - `stream`    : fuer Logos und Schriften ohne praktische Wirkung (Teilbereichs-Anfragen
//                   braucht nur <video>); MITGEFUEHRT, damit beide Schemata zeichengleich
//                   beschrieben sind und niemand je Schema neu abwaegen muss.
// UEBER EINE MOEGLICHE FUENFTE EIGENSCHAFT s. STOPP - dort und NUR dort.

/**
 * Registriert den eigentlichen Anfrage-Handler. Wird NACH app.whenReady(), vor dem Laden des
 * Hauptfensters aufgerufen – dieselbe Reihenfolge wie beim bestehenden 'media'-Handler.
 */
export function registriereMarkenProtokollHandler(): void

/**
 * Electron protocol.handle-Signatur (Fetch-API-Typen). Löst NIE selbst Pfade auf – jede Auflösung
 * läuft über loeseMarkenDateiPfad() aus M8-14 (src/main/marken-store/pfade.ts). Liest NUR die Datei;
 * schreibt, löscht oder verändert nichts.
 */
export async function behandleMarkenAssetAnfrage(request: Request): Promise<Response>
```

```ts
export function loeseMarkenDateiPfad(
  markeId: string,
  dateiname: string,
): Ergebnis<string, MarkenFehlercode>
// absoluter Pfad zur Datei; liefert NUR einen Pfad, wenn dieser nach Normalisierung nachweislich
```

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.**

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `request.url` | Anfrage-URL im Schema `marken://<markeId>/<dateiname>` | muss exakt diesem Schema entsprechen (Host = `markeId`, Pfad = `dateiname`); alles andere ist eine ungültige Anfrage |
| `request.method` | HTTP-artige Methode der Fetch-API | **nur `GET`** – jede andere Methode wird abgelehnt, ohne die Auflösung zu versuchen |

Ausgang bei Erfolg: eine `Response` mit dem Dateiinhalt und passendem `Content-Type` (Status 200).
Ausgang bei Fehler: eine `Response` mit Fehlerstatus – **keine** `Ergebnis<T>`-Hülle, kein geworfener
Fehler, der den Main-Prozess destabilisieren könnte.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Zwei Herkünfte, eine Auflösung.** `gebuendelt` löst auf den Bundle-Pfad auf (die vier
  OFL-Schriften, das Fitnessworld24-Logo), `importiert` auf `marken-assets/<markeId>/`. Der Renderer
  bekommt importierte Dateien über ein **Lese-Protokoll** wie die Projektmedien (`media://`, 9.5.7)
  und **nie** über absolute Pfade. **Genau eine** Stelle löst auf – nicht jede Zonen-Sorte einzeln."
  (TK 9.15.3)
- „**Ablage neben den Daten, nicht im Programmordner.** `marken-assets/` liegt im Datenort
  (Abschnitt 6). So wandern importierte Schriften mit den Daten – bei portabler Auslieferung genau
  richtig." (TK 9.15.3)
- „Für die Vorschau (P5) und Thumbnails (`composer`, `action-editor`) muss der **Renderer** Medien
  anzeigen. Dafür registriert der Main ein eigenes Protokoll `media://<projektId>/<dateiname>`,
  dessen Handler die Auflösung des `project-store` nutzt und die Datei **nur lesend** ausliefert."
  (TK 9.5.7) – dieses Issue überträgt dasselbe Muster eins zu eins auf `marken-assets`.
- „Der Renderer sieht **nur relative** Referenzen (`dateiname`), **nie** absolute Pfade. Der Resolver
  stellt sicher, dass das Ziel **innerhalb** des […] Ordners […] bleibt (kein `..`-Ausbruch, keine
  Symlink-Flucht); Zugriff strikt **read-only**." (TK 9.5.7)
- „Diese Konventionen gelten für **jede** Operation über die Renderer↔Main-Grenze." (TK 9.1.1) –
  **Klarstellung, keine TK-Invariante:** Ein Custom-Protocol-Handler ist **kein** IPC-Kanal, sondern
  ein Ressourcen-Loader (Fetch-API `Request`/`Response`). `behandleMarkenAssetAnfrage` gibt deshalb
  **niemals** `Ergebnis<T>` zurück; Fehler werden über den Response-Status ausgedrückt.

## Fehlerpfade (vollständig)
| Situation | Antwort | Verhalten |
|---|---|---|
| `request.method !== 'GET'` | Fehlerstatus | keine Dateisystemoperation |
| `request.url` entspricht nicht `marken://<markeId>/<dateiname>` | Fehlerstatus | keine Dateisystemoperation |
| `loeseMarkenDateiPfad(markeId, dateiname)` liefert `ok: false` | Fehlerstatus | keine Dateisystemoperation; die `meldung` wird **nicht** in die Response übernommen (keine Pfad-Details leaken) |
| Aufgelöster Pfad existiert nicht (Datei entfernt, `entferneMarkenDatei` lief zwischenzeitlich) | Fehlerstatus | keine Dateisystemoperation über den Lesevorgang hinaus |
| Datei existiert, Lesen schlägt fehl (Windows `EBUSY`/`EPERM`) | Fehlerstatus | Handler wirft **nicht**, Main-Prozess bleibt stabil |

## Nicht selbst entscheiden – STOPP und fragen
- **ERLEDIGT – nicht mehr melden:** Wie und wo `MARKEN_SCHEMA` und
  `registriereMarkenProtokollHandler()` in den Main-Bootstrap gelangen, klärt **M8-36**:
  `MARKEN_SCHEMA` reist neben `MEDIA_SCHEMA` (#9) in **einem einzigen**
  `protocol.registerSchemesAsPrivileged([…])`-Aufruf **vor** `app.whenReady()`; die Handler-Anmeldung
  steht **nach** `app.whenReady()` und **vor** dem Fensterladen – dieselben zwei Stellen wie für
  `media`. **Diese Datei ruft die Electron-API nicht selbst auf, ruft sich nicht selbst aus dem
  Bootstrap und trägt sich nicht in eine fremde Bootstrap-Datei ein**; sie stellt nur die
  Schema-Beschreibung und die beiden Funktionen bereit.
- **Verbot – kein eigenes `protocol.registerSchemesAsPrivileged` in dieser Datei**, auch nicht „nur
  zum Ausprobieren" und auch nicht in einer Testdatei, die die echte Electron-API träfe. Der Grund
  steht wörtlich in der Typdeklaration von Electron (Fassung 43.2.0,
  `node_modules/electron/electron.d.ts`): „This method can only be used before the `ready` event of
  the `app` module gets emitted and can be called only once." Ein zweiter Registrierer neben dem des
  Bootstraps hätte **beide** Ausgänge still gemacht – entweder wäre `marken://` nicht privilegiert,
  oder **`media://` hätte aufgehört zu funktionieren**, und dann fehlten in der Vorschau sämtliche
  Projektmedien, ohne dass irgendetwas auf die Marken zeigt.
- **EXPERIMENT, keine Entscheidung – braucht `marken` als FÜNFTE Eigenschaft `corsEnabled: true`,
  damit `FontFace` eine importierte Schrift überhaupt lädt?** Das ist **auszuprobieren**, nicht zu
  beschließen: Die Frage ist empirisch, und niemand kann sie am Schreibtisch beantworten.

  **Was gemessen ist.** Beim Bauen von **#9** wurde für `media://` Folgendes festgestellt und im
  Quelltext (`src/main/index.ts`) festgehalten – wörtlich:

  > „Gemessen beim Bauen von #9: `fetch('media://...')` scheitert auch dann, wenn connect-src es
  > erlaubt - und der Protokoll-Handler wird dabei NICHT EINMAL ERREICHT (nachgewiesen mit einer
  > Protokollzeile im Handler selbst). Die Ursache liegt also nicht in der CSP, sondern davor:
  > `media://` ist gegenueber der Seite ein fremder Ursprung, und Electron kennt dafuer ein eigenes
  > Schema-Privileg (`corsEnabled`), das in der verbindlichen Signatur von #9 nicht steht."

  **Was daraus NUR VERMUTET ist.** M8-17 lädt importierte Schriften über
  `new FontFace(familie, 'url(marken://…)')`. `FontFace` ist wie `fetch` ein Cross-Origin-Ladeweg
  und unterliegt CORS – **derselben** Ursache, an der der gemessene `fetch`-Fall gescheitert ist.
  Daraus folgt der **Verdacht**, dass ohne `corsEnabled: true` **keine** importierte Schrift lädt,
  und zwar **unabhängig** davon, was in `font-src` steht. **Gemessen wurde `fetch`, nicht
  `FontFace`** – der Schluss ist eine Ableitung, kein Messwert, und `<img src="marken://…">`
  funktioniert nachweislich **ohne** das Privileg (für `media://` „in beiden Modi geprueft").

  **Die Probe, benannt und wiederholbar:** Eine echte `.woff2`-Datei in `marken-assets/<markeId>/`
  ablegen, im Renderer `await new FontFace('Probe', 'url(marken://<markeId>/<datei>.woff2)').load()`
  ausführen und `document.fonts.check('16px Probe')` auswerten – **einmal mit** `corsEnabled: true`
  in `MARKEN_SCHEMA`, **einmal ohne**, sonst identisch. Zusätzlich im Handler eine Protokollzeile
  setzen, um wie bei #9 zu unterscheiden, ob er **erreicht** wird oder der Ladeversuch schon davor
  abbricht. Gegenprobe im selben Lauf: `<img src="marken://…">` muss in **beiden** Fassungen laden.

  **Warum du das nicht selbst entscheiden darfst, obwohl es nur ein Wort ist:** Fällt es falsch aus,
  ist der Schaden **still**. Der Canvas nimmt bei nicht geladener Schrift klanglos eine
  Ersatzschrift (TK 9.10.4) – Vorschau und Endvideo sehen „richtig" aus, der Markenbruch fällt erst
  am 85-Zoll-Fernseher auf, und dann zeigt nichts mehr auf ein fehlendes Schema-Privileg. Umgekehrt
  ist `corsEnabled` eine echte Lockerung und wird nicht „vorsichtshalber" gesetzt. **Erst messen,
  dann eintragen** – und fällt die Probe positiv aus, gehört im selben Zug der zugehörige
  CSP-Eintrag geprüft (Edit-Ziel an **#3**, geführt in M8-36).
- **Gilt die Anfrage für jede `markeId`, oder nur für Marken, die tatsächlich existieren?** Analog zur
  offenen Frage bei `media://` (gilt es nur fürs aktive Projekt oder jede `projektId`): Der
  `marken-store` führt den **gesamten** Bestand im Speicher (anders als `project-store`, der nur ein
  Projekt aktiv hält) – ob das etwas an der Antwort ändert, ist nicht spezifiziert.
- **Exakte HTTP-artige Statuscodes** je Fehlerfall (400/403/404/500) sind im TK nicht festgelegt –
  wie bei `media://` (M1-38) nicht selbst festlegen, wenn die UI sie ohnehin nicht differenziert.
- **Content-Type-Bestimmung** für `.woff2` und die Bild-Whitelist: allein aus der Dateiendung geraten
  oder zusätzlicher Kontext nötig? Nicht entschieden.

- [ ] `behandleMarkenAssetAnfrage` löst eine gültige Anfrage ausschließlich über einen Aufruf von
      `loeseMarkenDateiPfad` auf – **kein** eigenes `path.join`/`path.resolve` gegen einen selbst
      zusammengesetzten `marken-assets`-Pfad in dieser Datei
- [ ] Eine Anfrage, für die `loeseMarkenDateiPfad` `ok: false` liefert, führt nachweislich zu
      **keinem** Dateisystemzugriff (Test mit Spy auf `fs`)
- [ ] Eine Anfrage mit `request.method !== 'GET'` wird abgelehnt, ohne dass `loeseMarkenDateiPfad`
      überhaupt aufgerufen wird
- [ ] Kein Test- oder Produktionscode dieser Datei erzeugt oder verwendet ein `Ergebnis<T>` als
      Rückgabewert von `behandleMarkenAssetAnfrage`
- [ ] Ein simulierter Lesefehler (`EBUSY`) führt zu einer Fehler-`Response`, nicht zu einer
      unbehandelten Exception im Main-Prozess
- [ ] `MARKEN_SCHEMA` ist eine exportierte Konstante mit `scheme: 'marken'` und **genau** den vier
      Privilegien `standard`, `secure`, `supportFetchAPI`, `stream` (Test liest die Konstante
      direkt); **wann** sie registriert wird, testet diese Datei **nicht** – das entscheidet der
      Aufrufer (M8-36, s. STOPP)
- [ ] `corsEnabled` ist **nicht** gesetzt, solange die im STOPP-Block benannte Probe nicht gelaufen
      und ihr Ergebnis nicht abgenommen ist (Test prüft die Abwesenheit der Eigenschaft) – kein
      „vorsichtshalber" gesetztes fünftes Privileg
- [ ] Ein Grep über Quell- **und** Testdatei findet **kein**
      `protocol.registerSchemesAsPrivileged` – diese Datei ruft die API nicht auf (s. STOPP)
- [ ] `registriereMarkenProtokollHandler()` ruft `protocol.handle('marken',
      behandleMarkenAssetAnfrage)` mit **genau** diesem Schema-Namen auf
- [ ] Keine Datei außerhalb von `src/main/marken-store/marken-protokoll.ts` (+ zugehörige Testdatei)
      geändert
