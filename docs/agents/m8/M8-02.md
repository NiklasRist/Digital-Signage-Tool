### Issue M8-02: [marken-store] Fehlercode-Union des Moduls definieren

## Ziel (in einem Satz)
Der `marken-store` besitzt eine eigene, geschlossene Fehlercode-Union, sodass jede seiner Operationen
einen typisierten Code liefert statt einer Textmeldung – und die Oberfläche eine blockierte Löschung
von einer defekten Datei unterscheiden kann.

## Modul & Datei
- Modul: `marken-store` [V2] (Main)
- Datei: `src/main/marken-store/fehlercodes.ts`
- Vertrag: Technisches Konzept **9.15.5** (der geschlossene Satz – Quelle der Wahrheit), **9.1.1**
  Punkt 3 (geschlossener Satz, generisch + fachlich)
- Prozess/Speicher: V2; kein Speicherzugriff (reine Typdatei)

## Warum das im Gesamtsystem wichtig ist
An diesen Codes hängt **echtes Verhalten**, nicht nur eine Meldung. `marke_referenziert` führt in der
Oberfläche zur Anzeige beider Trefferlisten aus `Markennutzung` (M8-01) – der Nutzer sieht, **was** er
zuerst aufräumen muss. `marke_eingebaut` führt zu der Erklärung, dass die Fitnessworld24-Marke nie
löschbar ist, aber bearbeitbar bleibt (TK 9.15.1) – eine andere Handlungsempfehlung als
`marke_referenziert`. `marken_datei_fehlt` wird **im RENDERER festgestellt, beim Vorbereiten der
Marke vor dem Zeichnen** (TK 9.15.5/9.15.3, seit v3.7) – **nicht** im `render-service`; dann entsteht
kein Segment-PNG, der `composer` führt in denselben geführten Reparatur-Modus wie bei einem
fehlenden Medium (FA-19), und der Auftrag wird gar nicht erst eingereiht. Degradieren diese zu einem
gemeinsamen „irgendwas ist schiefgelaufen", stehen Reparatur-Modus und Löschsperre ohne Grundlage.

Zweitens ist diese Datei der Ort, der verhindert, dass jedes weitere `marken-store`-Issue seine eigenen
Codes erfindet. Dreizehn Operationen des Moduls (M8-08 bis M8-15 sowie deren Aufrufer) liefern Fehler;
schreibt jede ihre Codes als eigenes String-Literal hin, weicht früher oder später eine Schreibweise ab
(`markeReferenziert` in camelCase, `marke_referenziert_von_aktion` als Erweiterung), und ein Aufrufer,
der auf den Code prüft, trifft ihn nicht mehr.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/marken-store/fehlercodes.ts

/**
 * Fachliche Fehlercodes des marken-store (TK 9.15.5).
 *
 * `ungueltige_eingabe` steht hier BEWUSST NICHT: Sie kommt über den zweiten Typparameter von
 * Ergebnis (#12/#22) automatisch dazu, ebenso `nicht_gefunden` und `unbekannter_fehler`. TK 9.15.5
 * fuehrt sie in der GLEICHEN Tabelle wie die vier folgenden Codes auf, aber das Modul definiert
 * ausdruecklich eine EIGENE, fachlich schaerfere Variante von "nicht gefunden"
 * (marke_nicht_gefunden statt des generischen nicht_gefunden) - beide existieren nebeneinander,
 * s. Invarianten. Eine Wiederholung der drei generischen Codes hier erzeugte zwei Quellen fuer
 * denselben Wert.
 */
export type MarkenFehlercode =
  | 'marke_referenziert'
  | 'marke_eingebaut'
  | 'marke_nicht_gefunden'
  | 'marken_datei_fehlt'
  | 'speicher_fehler'
```

Genau diese fünf Werte. **Keine** zweite Union, **kein** Alias, **kein** `const`-Array „zum Prüfen".

**Fremde Typen, die du benutzt** (der umsetzende Agent sieht die anderen Issues nicht):

```ts
// #12 + #22 – src/shared/contracts/ergebnis.ts, bereits angelegt:
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'

export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }

// Der zweite Typparameter ist der Einhaengepunkt fuer DIESE Datei. Eine Operation schreibt danach
// z. B.:  Promise<Ergebnis<Marke, MarkenFehlercode>>
// Die drei generischen Codes sind darin automatisch enthalten und werden hier NICHT wiederholt.
// `daten` ist das optionale Feld fuer strukturierte Fehlerdaten (TK 9.1.1); seine Form ist JE
// FEHLERCODE festgelegt und wird NICHT hier deklariert - fuer marke_referenziert ist das
// Markennutzung (M8-01), zugeteilt dort, wo der Code vergeben wird (M8-13).
```

**Wo jeder Code vergeben wird und was er bedeutet** (gehört als Kommentar bzw. Doku in die Datei):

| Code | Vergeben von | Ursache |
|---|---|---|
| `marke_referenziert` | `löscheMarke` (M8-13) | Mindestens eine Aktion (`aktion.markeId`) in irgendeinem Projekt **oder** mindestens eine abgeleitete Marke (`marke.parent`) zeigt noch auf diese Marke. Trägt **beide** Trefferlisten (`Markennutzung`, M8-01) in `daten`. Blockierend, **nicht** kaskadierend. |
| `marke_eingebaut` | `löscheMarke` (M8-13) | Löschen der Fitnessworld24-Marke (`eingebaut: true`) versucht. Sie ist nie löschbar, aber – anders als eingebaute Vorlagen – bearbeitbar (TK 9.15.1). |
| `marke_nicht_gefunden` | `leseMarke`, `bearbeiteMarke`, `löscheMarke`, `pruefeMarkenReferenzen`, `importiereMarkenDatei`/`entferneMarkenDatei` u. a. (M8-09, M8-11, M8-13, M8-12, M8-15) | Eine übergebene `markeId` steht nicht im Bestand – **oder** die `parent`-Referenz einer abgeleiteten Marke zeigt ins Leere (verwaiste Ableitung, M8-05). |
| `marken_datei_fehlt` | `template-canvas`, Vorbereiten der Marke vor dem Zeichnen (M8-17) | Ein importiertes Logo oder eine importierte Schrift liegt nicht (mehr) in `marken-assets/<markeId>/`. **Festgestellt im RENDERER, nicht im `render-service`** – der sieht bei Variante A nie eine Marken-Datei (TK 9.2.3/9.15.3, v3.7). Dann entsteht kein Segment-PNG, und der Auftrag wird gar nicht erst eingereiht. |
| `speicher_fehler` | jede schreibende Operation, über M8-03 | `marken.json` ließ sich nicht lesen oder nicht schreiben (Platte voll, Rechte, defekte Datei ohne brauchbares `.bak`). |

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – | reine Typdefinition, kein Laufzeit-Eingang | – |

Ausgang bei Erfolg: Jede Operation des `marken-store` kann `Ergebnis<T, MarkenFehlercode>` schreiben
und bekommt beim Typecheck exakt die Vereinigung aus den fünf fachlichen Codes und den drei
generischen – nicht mehr, nicht weniger.
Ausgang bei Fehler: entfällt (Typdefinition, keine Laufzeit-Fehlerpfade).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Fehlercode-Tabelle, wörtlich (TK 9.15.5):
  | Fehlercode | Ursache |
  |---|---|
  | `marke_referenziert` | Löschen abgelehnt – Aktionen und/oder abgeleitete Marken nutzen sie noch (mit beiden Trefferlisten) |
  | `marke_eingebaut` | Löschen der eingebauten Marke versucht |
  | `marke_nicht_gefunden` | unbekannte `markeId` |
  | `ungueltige_eingabe` | unbekannte Rolle, Ableitungskette länger als eine Stufe, Datei nicht in der Whitelist |
  | `marken_datei_fehlt` | Eine importierte Datei der Marke liegt nicht (mehr) in `marken-assets/<markeId>/`. **Festgestellt wird das im RENDERER, beim Vorbereiten der Marke vor dem Zeichnen** (9.15.3, 9.10.4) – **nicht** im `render-service`, der nie eine Marken-Datei sieht (9.2.3). Das betroffene Segment wird nicht gezeichnet, der `composer` führt in den Reparatur-Modus (9.7.5), der Auftrag wird **gar nicht erst eingereiht** |
  | `speicher_fehler` | `marken.json` nicht schreibbar (Platte voll, Rechte) |
- „**Fehlercodes sind ein geschlossener, typisierter Satz:** die fachlichen je Operation (9.4.9, 9.6.4,
  9.12.1) plus die generischen `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`. **Eine
  rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1, Punkt 3)
- **`marke_nicht_gefunden` ist ein FACHLICHER Code und ersetzt hier den generischen
  `nicht_gefunden`.** Anders als beim `vorlagen-store` (der für eine unbekannte `id` schlicht den
  generischen `nicht_gefunden` liefert) führt TK 9.15.5 für den `marken-store` ausdrücklich einen
  eigenen, benannten Code für „unbekannte `markeId`". Beide Codes existieren nebeneinander (der
  generische bleibt über `Ergebnis` verfügbar), aber die Operationen dieses Moduls verwenden für eine
  unbekannte `markeId` **immer** `marke_nicht_gefunden`, **nie** den generischen `nicht_gefunden` –
  sonst gäbe es zwei verschiedene Codes für denselben Sachverhalt, je nachdem, wer ihn zufällig wählt.
- **`ungueltige_eingabe` wird hier NICHT wiederholt.** Sie ist der generische Code aus #12/#22 und
  deckt laut TK 9.15.5 „unbekannte Rolle, Ableitungskette länger als eine Stufe, Datei nicht in der
  Whitelist" ab – alles Fälle einer **formal** falschen Nutzlast, keine fachliche Besonderheit dieses
  Moduls.
- **Muster aus #22 (verbindlich):** „Fachliche Module deklarieren ihre eigene Union in ihrer eigenen
  Datei" und „re-exportieren sie hier NICHT automatisch – der Aufrufer einer bestimmten Operation
  importiert die konkrete Fehlercode-Union der jeweiligen Operation direkt".
- **Die generischen Codes werden hier NICHT wiederholt.** Weder `ungueltige_eingabe` noch
  `nicht_gefunden` noch `unbekannter_fehler` taucht in der Union auf – sie kommen über den `Ergebnis`-
  Typ automatisch dazu.
- **Die Codes erreichen den Renderer, ohne durch `Fehlercode` (#12) zu müssen.** `HandlerErgebnis` ist
  seit #60 über seinen Fehlercode generisch; ein Marken-Handler gibt seinen fachlichen Code also
  **unverengt** heraus. **Kein** `as Fehlercode`-Cast, **keine** Erweiterung von `ergebnis.ts`, **kein**
  Abbilden auf `unbekannter_fehler`.
- Diese Datei enthält **ausschließlich Typen** – keine Laufzeit-Werte, keine Meldungstexte, keine
  Übersetzungstabelle Code → Klartext.

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – `src/shared/contracts/ergebnis.ts` wird nicht angefasst**, auch nicht „nur um den
  Re-Export zu ergänzen".
- **Verbot – kein sechster Wert.** Insbesondere **kein** `parent_eingebaut` (die Kettensperre bei
  `erstelleMarke` ist laut TK 9.15.1 `ungueltige_eingabe`, kein eigener Code – anders als beim
  `vorlagen-store`, wo `parent_eingebaut` **wegen** einer eingefrorenen eingebauten Vorlage nötig
  ist; die eingebaute Marke ist dagegen bearbeitbar, s. TK 9.15.1, und braucht diese Sperre nicht),
  **kein** `datei_nicht_in_whitelist` (das ist `ungueltige_eingabe`, TK 9.15.5).
- **Verbot – keine Sammel-Union über Module hinweg** und kein Alias wie `StoreFehlercode`.
- **Verbot – keine Datenform-Typen.** Die Gestalt von `daten` bei `marke_referenziert`
  (`Markennutzung`, M8-01) wird dort festgelegt, wo der Code vergeben wird (M8-13), nicht hier.
- **ERLEDIGT – nicht mehr melden.** Die gemeldete Abweichung vom ursprünglichen Zuschnitt (dieses
  Issue als `[contracts]` mit einer Datei unter `src/shared/contracts/`) ist **aufgelöst**:
  `docs/agents/m8-zuschnitt.md` führt M8-02 inzwischen als `[marken-store]` und hält ausdrücklich
  fest, dass fachliche Fehlercode-Unionen in `src/main/**` liegen (Präzedenz: `VorlagenFehlercode`
  in M4-03; TK-Begründung E3 aus dem M5-Nachtrag: „Fachliche Fehlercode-Unionen liegen in
  `src/main/**` und dürfen vom Renderer nicht importiert werden; die Enge sitzt dort, wo der Code
  entsteht"). Auch die zuvor gegenläufige Datei `docs/agents/m8/M8-29.md` ist nachgezogen und
  importiert `MarkenFehlercode` aus `src/main/marken-store/fehlercodes.ts`. **Alle** Nachbar-Issues
  (M8-08, M8-09, M8-10, M8-11, M8-12, M8-13, M8-22, M8-23, M8-29) benutzen damit denselben,
  main-lokalen Pfad. Für den umsetzenden Agenten gilt schlicht die Datei aus dem Abschnitt
  „Modul & Datei" – hier ist nichts mehr zu klären.
