### Issue M2-01: [contracts] Typen ProtokollEintrag und JournalEintrag definieren

## Ziel (in einem Satz)
Die beiden Datensätze der Auftragsverwaltung, die den Neustart überleben – der Protokolleintrag je
beendetem Versuch (Q3) und die Journalzeile je Warteschlangen-Bewegung (Q4) – existieren als
geteilte, verbindliche Typen, auf die sich alle schreibenden Stellen des `auftrags-manager` stützen.

## Modul & Datei
- Modul: `contracts/types` (geteilt)
- Datei: `src/shared/contracts/protokoll.ts`
- Vertrag: Technisches Konzept **9.3** (Abschnitt „Datensätze von Q3 und Q4", Quelle der Wahrheit),
  TK **9.1.1** Punkt 3 (Fehlercode-Satz), TK **9.2.3** (Herkunft der `ausgabe`-Nutzdaten)
- Prozess/Speicher: P6, Q3 (`protokoll.json`, app-weit), Q4 (`warteschlangen-journal.json`, app-weit)

## Warum das im Gesamtsystem wichtig ist
Q3 ist der **einzige** dauerhafte Nachweis darüber, was die Anwendung jemals produziert hat – jeder
Render, jeder Export, jeder Fehlschlag, unbegrenzt aufbewahrt. Diese Datei wird über Jahre
fortgeschrieben; ihr Format ist damit faktisch nicht mehr änderbar, ohne alte Einträge zu entwerten.
Fehlt hier ein Feld (etwa `versuch`), lässt sich später nicht mehr rekonstruieren, ob ein Export im
zweiten oder im fünften Anlauf gelang; ist ein Feld zu weich typisiert (`fehler: any`, `art: string`),
schreibt irgendeine Stelle eine rohe Exception-Meldung statt eines Fehlercodes hinein, und die
Auswertung „warum scheitert der Export immer" wird unmöglich. Die Typen werden von M2-04 (Q3
schreiben), M2-05 (Q4 schreiben) und M2-18 (terminaler Übergang, erzeugt den Eintrag) benutzt –
wenn jedes dieser Issues seinen eigenen lokalen Typ definierte, driften Schreiber und Format
auseinander, ohne dass der Compiler es meldet.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/shared/contracts/protokoll.ts
import type { AuftragArt } from './auftrag'      // aus #16 – NICHT hier neu definieren
import type { Fehlercode } from './ergebnis'     // aus #12 – NICHT hier neu definieren
                                                 // (#22 fuegt Ergebnis nur den Typparameter F hinzu)

export type Bewegung = 'eingereiht' | 'gestartet' | 'entfernt' | 'erneut_eingereiht'

export type ProtokollErgebnis = 'erfolg' | 'fehlgeschlagen' | 'abgebrochen'

export interface ProtokollEintrag {
  id: string                    // UUID, erzeugt über den geteilten Generator (#20)
  auftragId: string             // derselbe Auftrag kann mehrere Einträge haben (Wiederholungen)
  art: AuftragArt
  projektId: string             // Herkunft: auftrag.payload.projektId – alle vier Nutzlasten
                                // tragen sie (ImportRequest/LoeschRequest TK 9.4.3,
                                // RenderRequest TK 9.2.1, ExportRequest TK 9.6.1).
                                // Der auftrags-manager fuehrt KEIN eigenes "aktives Projekt".
  versuch: number               // 1, 2, 3 … – steigt bei jeder Wiederholung
                                // NICHT verwechseln mit Auftrag.versuche (#16) – dort die
                                // laufende Zaehlung, hier der Stand DIESES Versuchs
  begonnenAm: string            // ISO-8601 UTC
  beendetAm: string             // ISO-8601 UTC
  ergebnis: ProtokollErgebnis
  fehler: { code: Fehlercode; meldung: string } | null
  ausgabe: { pfad: string; dateigroesse: number; gesamtdauer: number | null } | null
  // gesamtdauer ist bei art: export IMMER null – der export-service liefert laut TK 9.6.2
  // nur { zielPfad, dateigroesse }; eine Dauer kennt er nicht. Bei art: render ist sie gesetzt.
}

export interface JournalEintrag {
  zeit: string                  // ISO-8601 UTC
  auftragId: string
  bewegung: Bewegung
  position: number | null       // Platz in der Schlange, wo sinnvoll
}
```

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – | reine Typdefinition, keine Laufzeit-Logik | – |

Ausgang bei Erfolg: `ProtokollEintrag`, `JournalEintrag`, `Bewegung` und `ProtokollErgebnis` sind
projektweit importierbar; M2-04 schreibt ausschließlich `ProtokollEintrag`, M2-05 ausschließlich
`JournalEintrag`, M2-18 erzeugt den `ProtokollEintrag` beim terminalen Übergang.
Ausgang bei Fehler: entfällt (Typdefinition).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Datensätze stehen wörtlich so im Vertrag (TK 9.3):

  ```
  ProtokollEintrag {              // Q3 – ein Eintrag je BEENDETEM Versuch
    id:         string            // UUID
    auftragId:  string            // derselbe Auftrag kann mehrere Einträge haben (Wiederholungen)
    art:        "import" | "loeschen" | "render" | "export"
    projektId:  string
    versuch:    number            // 1, 2, 3 … – steigt bei jeder Wiederholung
    begonnenAm: string            // ISO-8601 UTC
    beendetAm:  string            // ISO-8601 UTC  → die Dauer ergibt sich daraus
    ergebnis:   "erfolg" | "fehlgeschlagen" | "abgebrochen"
    fehler:     { code, meldung } | null
    ausgabe:    { pfad, dateigroesse, gesamtdauer } | null   // nur bei erfolgreichem render/export
  }

  JournalEintrag {               // Q4 – eine Zeile je Bewegung
    zeit:      string             // ISO-8601 UTC
    auftragId: string
    bewegung:  "eingereiht" | "gestartet" | "entfernt" | "erneut_eingereiht"
    position:  number | null      // Platz in der Schlange, wo sinnvoll
  }
  ```
- „**Q3 protokolliert nur, was tatsächlich gelaufen ist.** Ein Auftrag, der die Schlange nie
  verlassen hat, erzeugt **keinen** Protokolleintrag – es gibt nichts zu berichten. Seine Bewegungen
  stehen in Q4." (TK 9.3) – deshalb hat `ProtokollEintrag` **kein** Feld `anstehend` und **keinen**
  Zwischenzustand: er entsteht ausschließlich beim Übergang nach `erfolg`, `fehlgeschlagen` oder
  `abgebrochen`.
- „**Fehlschläge bleiben sichtbar:** Eine Wiederholung erzeugt einen **neuen** Q3-Eintrag mit
  höherem `versuch`. Ein Export, der zweimal an einem vollen Stick scheitert und beim dritten Mal
  klappt, hinterlässt **drei** Einträge – die Fehlerhistorie geht nicht verloren, auch wenn der
  Q2-Eintrag nach dem Erfolg verschwindet." (TK 9.3) – daraus folgt: `auftragId` ist **nicht**
  eindeutig über die Einträge; die Eindeutigkeit trägt allein `id`. Ein Modellieren als
  `Record<auftragId, Eintrag>` ist damit ausgeschlossen.
- „**Die Trennung Q3/Q4 ist Absicht:** Q3 beantwortet „**was wurde produziert**" (nutzerlesbare
  Historie), Q4 „**was passierte in der Schlange**" (Diagnose). Beides in einem Speicher würde die
  Historie im Bewegungsrauschen untergehen lassen – deshalb ist Q3 unbegrenzt und Q4 rotierend."
  (TK 9.3) – die beiden Typen werden deshalb **nicht** zu einem gemeinsamen „Ereignis"-Typ
  verschmolzen, auch wenn sie sich ähneln.
- „**Fehlercodes sind ein geschlossener, typisierter Satz:** die fachlichen je Operation (9.4.9,
  9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`.
  **Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1 Punkt 3) – `fehler.code` ist deshalb
  `Fehlercode` aus #12 und **nie** `string`.
- Die Nutzdaten in `ausgabe` stammen aus dem Render-Ergebnis: „`historieEintrag` | ID, Datum, Pfad,
  Dauer, Größe → von der Auftragsverwaltung ins Protokoll Q3 geschrieben (9.3)" (TK 9.2.3). Die
  Auftragsverwaltung **erzeugt** diese Werte nicht selbst, sie übernimmt sie.
- **`ausgabe.gesamtdauer` ist bei `art: export` immer `null`.** Der `export-service` meldet laut
  TK 9.6.2 Schritt 6 nur `{ zielPfad, dateigroesse }` – eine Dauer kennt er nicht, und sie darf
  weder aus einem vorangegangenen Render übernommen noch als `0` erfunden werden (`0` wäre von
  einer echten Dauer nicht unterscheidbar). Bei `art: render` ist das Feld gesetzt. Deshalb
  `gesamtdauer: number | null` **innerhalb** des `ausgabe`-Objekts – nicht optional (`?`) und nicht
  als eigenes, zweites `ausgabe`-Format je Auftragsart.
- **`projektId` kommt aus `auftrag.payload.projektId`.** Alle vier Nutzlasten tragen dieses Feld –
  `ImportRequest` und `LöschRequest` (TK 9.4.3), `RenderRequest` (TK 9.2.1), `ExportRequest`
  (TK 9.6.1). Die Auftragsverwaltung führt **kein** eigenes „aktives Projekt", aus dem der Wert
  stattdessen stammen könnte; M2-18 liest ihn beim Erzeugen des Eintrags aus der Nutzlast.
- Alle Zeitangaben sind Zeichenketten im Format **ISO-8601 UTC**, nie `Date`-Objekte und nie
  Millisekunden-Zahlen: die Einträge werden als JSON in eine dauerhafte Datei geschrieben, und ein
  `Date` überlebt `JSON.parse` nicht als `Date`.

## Fehlerpfade (vollständig)
Entfällt (reine Typdefinition, keine Laufzeit-Logik und damit keine Fehlerpfade). Die Fehlerpfade
der schreibenden Seite liegen bei M2-04 (Q3), M2-05 (Q4) und M2-17 (Datei-Zugriff).

## Nicht selbst entscheiden – STOPP und fragen
- **Ist `ausgabe.pfad` ein absoluter oder ein projektrelativer Pfad?** `RenderResult.ausgabePfad` ist
  laut TK 9.2.3 „absoluter Pfad der erzeugten `projects/<id>/output/<name>.mp4`" – und genau dieser
  Wert liegt beim Schreiben des Eintrags vor. Q3 ist aber **dauerhaft und unbegrenzt**, und die
  Anwendung ist **portabel**: Ein absoluter Pfad, der heute auf `E:\signage\projects\…` zeigt, ist
  falsch, sobald derselbe App-Ordner an einem anderen Laufwerksbuchstaben, auf einem anderen Rechner
  oder unter macOS eingehängt wird. Ein projektrelativer Wert (`projektId` steht ohnehin daneben,
  der Rest wäre der Dateiname) bliebe gültig, verlöre aber die wörtliche Übereinstimmung mit dem
  Render-Ergebnis. **Nicht selbst wählen** – die Entscheidung ist nach dem ersten geschriebenen
  Protokoll praktisch nicht mehr revidierbar. **Und für `art: export` steckt dieselbe Frage doppelt
  drin:** Dort gibt es zwei Pfade – die **Quelle** im Projekt (`projects/<id>/output/<name>.mp4`)
  und das **Ziel** auf dem USB-Stick (`<Laufwerk>:\<dateiname>`). Welcher von beiden protokolliert
  wird, ist **nicht** entschieden; der Stick-Pfad ist der, der den Nutzer interessiert („ist die
  Datei angekommen?"), und zugleich der, der morgen an einem anderen Laufwerksbuchstaben hängt.
- **Keine Domänentypen erfinden.** `AuftragArt` gehört #16 (`src/shared/contracts/auftrag.ts`),
  `Fehlercode` gehört #12 (`src/shared/contracts/ergebnis.ts`). Beide werden **importiert**, nicht
  hier nachgebaut – auch nicht „nur als String-Union, damit es kompiliert". Fehlt etwas in diesen
  Dateien, wird das **erfragt**; sie zu ändern ist außerhalb dieses Issues (Regel E).
- **Der Typ `Auftrag` (#16) wird nicht erweitert.** `begonnenAm` fehlt dort bewusst; die
  Auftragsverwaltung hält es in ihrem internen Q1-Datensatz (M2-02). Wer hier ein Feld in `Auftrag`
  ergänzen will, greift in eine fremde Datei ein.
- **Keine Ergebnis-Hülle und keine Funktionen in dieser Datei.** Sie enthält ausschließlich Typen;
  `Ergebnis<T>` gehört an die Operationen, nicht an die Datensätze.

## Definition of Done
- [ ] `Bewegung`, `ProtokollErgebnis`, `ProtokollEintrag` und `JournalEintrag` sind exakt wie in der
      Signatur exportiert – keine zusätzlichen, keine fehlenden Felder
- [ ] `art` verwendet den importierten `AuftragArt` aus `./auftrag`, `fehler.code` den importierten
      `Fehlercode` aus `./ergebnis`; in dieser Datei wird keiner der beiden Typen neu deklariert
- [ ] `Bewegung` und `ProtokollErgebnis` sind geschlossene String-Unionen (kein `string`)
- [ ] `fehler` und `ausgabe` sind `| null`, nicht optional (`?`) – ein beendeter Versuch trägt das
      Feld immer, mit oder ohne Inhalt
- [ ] Die Datei enthält keine Funktion, keine Konstante und keinen Laufzeit-Code (Typen und
      `import type` genügen)
- [ ] Diese Datei typecheckt fehlerfrei gegen die Importe aus #16 und #12
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze) – hier
      gegenstandslos, da die Datei keinen Laufzeit-Code enthält; nachgewiesen durch das Kriterium darüber
- [ ] Keine Datei außerhalb von `src/shared/contracts/protokoll.ts` (+ zugehörige Testdatei) geändert
