### Issue M2-19: [auftrags-manager] Die vier Queue-Kanäle und das Ereignis verdrahten

## Ziel (in einem Satz)
Die vier Warteschlangen-Operationen und der Zustands-Push werden beim `ipc-gateway` angemeldet,
sodass die Oberfläche `reiheEin`, `entferne`, `wiederhole` und `holeStand` überhaupt aufrufen kann
und den Stand nach jeder Änderung als Ereignis `queue:geaendert` zugeschickt bekommt.

## Modul & Datei
- Modul: `auftrags-manager` (Main)
- Datei: `src/main/auftrags-manager/ipc-verdrahtung.ts`
- Zusätzlich erlaubte Datei: `src/shared/contracts/kanaele.ts` – für die Einträge unter `queue`
  (die Registry wird laut #25 „von M2–M7 **iterativ ergänzt**"; dieses Issue ist der erste Ergänzer).
  **Dies ist die einzige Datei in ganz M2, die `kanaele.ts` ändert** – M2-09 bis M2-13 haben die
  Registry ausdrücklich **nicht** in ihrem Dateibereich.
- Vertrag: Technisches Konzept **9.1.1** (IPC-Konventionen), **9.3.4** (IPC-Oberfläche der
  Auftragsverwaltung) – Quelle der Wahrheit
- Prozess/Speicher: P6; **kein** eigener Speicher. Diese Datei liest und schreibt weder Q1, Q2, Q3
  noch Q4 – sie reicht nur durch.
- IPC-Kanäle: `queue:reiheEin`, `queue:entferne`, `queue:wiederhole`, `queue:holeStand`;
  Ereignis: `queue:geaendert`

## Warum das im Gesamtsystem wichtig ist
Ohne dieses Issue endet der ganze Meilenstein M2 mit vier Main-Funktionen, **die niemand aufrufen
kann**: Der Wrapper aus #23 (`registriereHandler(kanal, validiere, ausfuehren)`) ist generisch und
registriert von sich aus **nichts**; M2-09 bis M2-12 sind gewöhnliche Funktionen ohne Kanalbezug;
M2-13 meldet nur main-intern an Hörer und kennt kein Fenster. Erst hier entsteht die Verbindung zur
Oberfläche – und damit sind FA-16 („erkennbar ist jederzeit, welcher Auftrag läuft"), FA-17
(Wiederholen) und FA-18 (Entfernen/Abbrechen) überhaupt bedienbar.

Zwei lokale Entscheidungen sind hier teuer. Erstens die **Validierung**: Diese Datei ist die Stelle,
an der Renderer-Daten zum ersten Mal in den Main gelangen. Wird sie schlampig gebaut (etwa
`validiere` als „gibt immer ok zurück"), reicht ein Bug in der Oberfläche, um einen Auftrag mit
kaputter Nutzlast in die Warteschlange zu bekommen – der scheitert dann irgendwo tief im
`media-service` oder `render-service`, mit einem Fehlerbild, das niemand mehr auf seine Ursache
zurückführen kann. Zweitens die **Fensterreferenz**: Weil nur diese Datei ein Fenster kennen darf,
entstehen zwei Ereigniswege, sobald jemand anderswo „auch schnell" `webContents.send` aufruft – der
Renderer bekäme denselben Stand doppelt und würde bei ungleicher Reihenfolge einen veralteten
anzeigen.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/auftrags-manager/ipc-verdrahtung.ts

export function verdrahteQueueIPC(): void
// 1. registriert die vier Kanäle über den Wrapper aus #23 (je mit eigener Validierungsfunktion)
// 2. meldet sich über aufQueueGeaendert (M2-13) als Hörer an und gibt jede Meldung auf dem
//    Ereigniskanal queue:geaendert an den Renderer weiter – OHNE Hülle, OHNE Endzustand
```

Ergänzung in der Kanal-Registry (#25) – **hier** entstehen die Namen, nirgends sonst:

```ts
// src/shared/contracts/kanaele.ts (Ergänzung)
export const KANAELE = {
  queue: {
    reiheEin:   'queue:reiheEin',
    entferne:   'queue:entferne',
    wiederhole: 'queue:wiederhole',
    holeStand:  'queue:holeStand',
    geaendert:  'queue:geaendert',   // Ereignis Main → Renderer
  },
} as const
```

**Der veraltete Beispiel-Kommentar in `kanaele.ts` wird dabei mit korrigiert.** Dort steht als
Platzhalter noch `// auftrag: { reiheEin: 'auftrag:reiheEin', geaendert: 'auftrag:geaendert' },`
mit dem Präfix `auftrag:`. Verbindlich ist `queue:`, weil TK 9.1.1 Punkt 4 `queue:geaendert`
**wörtlich** als Beispiel führt. Ein stehengebliebener Kommentar mit dem falschen Präfix ist die
wahrscheinlichste Quelle dafür, dass ein späteres Modul (M3–M7) den falschen Namensraum abschreibt.

Die fremden Funktionen, die diese Datei benutzt, mit vollständiger Signatur (der umsetzende Agent
sieht die anderen Issues nicht):

```ts
// #23 – ipc-gateway, generischer Wrapper (registriert nichts von selbst)
registriereHandler<T, F extends string>(
  kanal: string,
  validiere: (nutzlast: unknown) => Ergebnis<unknown, 'ungueltige_eingabe'> | { ok: true; wert: unknown },
  ausfuehren: (validierteNutzlast: unknown) => Promise<Ergebnis<T, F>>,
): void

// M2-09
reiheEin<A extends AuftragArt>(art: A, payload: NutzlastVon<A>): Promise<Ergebnis<{ auftragId: string }>>
// M2-10
entferne(auftragId: string): Promise<Ergebnis<void>>
// M2-11
wiederhole(auftragId: string): Promise<Ergebnis<void>>
// M2-12
holeStand(): Promise<Ergebnis<Auftrag[]>>
// M2-13 – main-interne Hörer-Registrierung; Rückgabewert ist die Abmelde-Funktion
aufQueueGeaendert(hoerer: (auftraege: Auftrag[]) => void): () => void
```

**Nutzlast-Form je Kanal (verbindlich).** Der Wrapper aus #23 übergibt **eine** Nutzlast; die
Operationen haben aber teils zwei bzw. gar kein Argument. Deshalb trägt jeder Kanal ein **Objekt**,
und das Auspacken passiert hier:

| Kanal | Nutzlast | Aufruf |
|---|---|---|
| `queue:reiheEin` | `{ art, payload }` | `reiheEin(nutzlast.art, nutzlast.payload)` |
| `queue:entferne` | `{ auftragId }` | `entferne(nutzlast.auftragId)` |
| `queue:wiederhole` | `{ auftragId }` | `wiederhole(nutzlast.auftragId)` |
| `queue:holeStand` | keine (`undefined`) | `holeStand()` |

Begründung: `reiheEin` **braucht** ohnehin ein Objekt (zwei Argumente, eine Nutzlast), und die
Signaturen aus TK 9.3.4 sind unveränderlich. Ein einheitliches Objekt für alle Kanäle hält die
Renderer-Seite (#24) gleichförmig und lässt sich später um ein Feld erweitern, ohne dass sich der
Aufruftyp ändert; ein nackter String bei zwei von vier Kanälen wäre eine Sonderform, die jeder
Aufrufer einzeln nachschlagen müsste.

**Was die Validierungsfunktionen prüfen (verbindlich):**

| Kanal | Prüfung |
|---|---|
| `queue:reiheEin` | Nutzlast ist ein Objekt; `art` ist einer der vier Werte `import`, `loeschen`, `render`, `export`; `payload` ist ein Objekt. **Nicht** tiefer – die fachliche Prüfung der Nutzlast macht `reiheEin` (M2-09) bzw. der Fachdienst. |
| `queue:entferne` | Nutzlast ist ein Objekt; `auftragId` ist ein nicht leerer String. |
| `queue:wiederhole` | Nutzlast ist ein Objekt; `auftragId` ist ein nicht leerer String. |
| `queue:holeStand` | keine Nutzlast erwartet; eine trotzdem übergebene wird ignoriert, **nicht** als Fehler gemeldet. |

Scheitert eine Prüfung, antwortet der Wrapper mit `ungueltige_eingabe` und ruft die Operation
**gar nicht erst** auf – es entsteht **keine** Wirkung auf Q1/Q2/Q4 und kein Ereignis.

**Das Ereignis (verbindlich):**

1. `verdrahteQueueIPC` meldet sich **genau einmal** über `aufQueueGeaendert(hoerer)` an.
2. Der Hörer bekommt `Auftrag[]` und schickt **genau dieses Array** auf dem Kanal `queue:geaendert`
   an den Renderer – **ohne** Ergebnis-Hülle, **ohne** Endzustand, **ohne** Umsortieren, Filtern
   oder Zusatzfelder.
3. Der Versand darf **nie** werfen: Ein fehlender oder zerstörter Empfänger beendet weder den Hörer
   noch den Main. Der Hörer-Aufruf ist Teil von `sendeQueueGeaendert` (M2-13), das seinerseits von
   `reiheEin`/`entferne`/`wiederhole`/`beendeAuftrag` **abgewartet** wird – eine Ausnahme hier
   brächte den Auftragsfluss zum Stehen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – (`verdrahteQueueIPC` hat kein Argument) | einmalige Verdrahtung beim Programmstart | mehrfacher Aufruf würde vier Kanäle doppelt registrieren und den Hörer doppelt anmelden – s. STOPP |
| Nutzlast auf `queue:reiheEin` | `{ art, payload }` vom Renderer | `art` ∈ vier Werte, `payload` ist ein Objekt; sonst `ungueltige_eingabe` |
| Nutzlast auf `queue:entferne` / `queue:wiederhole` | `{ auftragId }` vom Renderer | nicht leerer String; sonst `ungueltige_eingabe` |
| Nutzlast auf `queue:holeStand` | keine | eine übergebene Nutzlast wird ignoriert |

Ausgang bei Erfolg: `verdrahteQueueIPC` selbst liefert nichts (`void`); Wirkung sind vier
registrierte Kanäle und ein angemeldeter Hörer. Die **Kanäle** liefern jeweils das unveränderte
Ergebnis ihrer Operation: `Ergebnis<{ auftragId: string }>` (`reiheEin`), `Ergebnis<void>`
(`entferne`, `wiederhole`), `Ergebnis<Auftrag[]>` (`holeStand`).
Ausgang bei Fehler: `ungueltige_eingabe` (Validierung schlägt fehl, Operation läuft nicht an),
`nicht_gefunden` (von `entferne`/`wiederhole` durchgereicht), `unbekannter_fehler` (unerwartete
Ausnahme, vom Wrapper aus #23 übersetzt). Diese Datei erzeugt **keine** eigenen Codes.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string } }
  ```
  Sie wird hier **unverändert durchgereicht** – nicht ausgepackt, nicht vereinfacht, nicht in eine
  Exception verwandelt. Begründung aus demselben Abschnitt: Renderer und Main sind „**getrennte
  Prozesse**"; ein `throw` über die Grenze verliert Fehlerklasse und Code – „**Fehlerklasse und
  eigene Felder wie `code` sind verloren** – übrig ist Text."
- „**Der Main validiert jede eingehende Nutzlast** – er vertraut dem Renderer **nicht**. Ungültige
  Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten. Ein Fehler im Renderer darf
  D1 niemals beschädigen." (TK 9.1.1, Punkt 6)
- „**Kanalbenennung `<modul>:<operation>`** – z. B. `media:importMedium`, `project:setzeTrim`,
  `vorlagen:löscheVorlage`. Ereignisse (Main → Renderer) heißen `<modul>:<ereignis>`, z. B.
  `queue:geaendert`, `render:fortschritt`. Damit erfindet niemand eigene Kanalnamen." (TK 9.1.1,
  Punkt 4) – daraus folgt das Präfix `queue:` für dieses Modul; `queue:geaendert` steht dort
  wörtlich.
- „**Ereignisse sind Einbahnstraßen und tragen keinen Endzustand** (für `RenderProgress` bereits
  festgelegt, 9.2.7). Terminale Zustände kommen ausschließlich über Aufruf-Ergebnis bzw.
  Auftrags-Zustand." (TK 9.1.1, Punkt 5)
- „**Ereignisse** (Main → Renderer) tragen ebenfalls keine Hülle (Punkt 5)." (TK 9.1.1, Punkt 2)
- „`QueueGeändert(Auftrag[])   // Main → Renderer: Push bei jeder Zustandsänderung → speist das
  queue-panel" und „// Ereignis: OHNE Hülle und ohne Endzustand (9.1.1 Punkte 5 und 2)" (TK 9.3.4)
- Die vier Operationen, wörtlich (TK 9.3.4) – die Signaturen sind unveränderlich, diese Datei passt
  sich ihnen an, nicht umgekehrt:
  ```
  reiheEin(art, payload) → Ergebnis<{ auftragId }>   // kehrt SOFORT zurück; sagt nichts über den Ausgang
  entferne(auftragId)    → Ergebnis<void>            // anstehend: aus Schlange nehmen; laeuft+render: Abbruch (→ cancelRender)
  wiederhole(auftragId)  → Ergebnis<void>            // fehlgeschlagen → anstehend, ans Ende, versuche +1
  holeStand()            → Ergebnis<Auftrag[]>       // Snapshot für die UI (z. B. beim Öffnen des Panels)
  ```
- „Alle vier Aufrufe sind **Instant** und tragen die Ergebnis-Hülle (9.1.1): `Ergebnis<void>` heißt
  „eingereiht/entfernt/wiederholt", **nicht** „fertig". Ein `entferne` auf einen bereits beendeten
  Auftrag ist kein Erfolg, sondern `nicht_gefunden`." (TK 9.3.4)
- „**Zwei Ebenen nicht verwechseln.** … **Aufruf-Ergebnis:** Hat der *Aufruf* funktioniert …
  **Auftrags-Ergebnis:** Wie ging der *Vorgang* aus (`RenderResult`, Export-Ergebnis …)? Das reist
  **nicht** als Aufruf-Antwort, sondern über den **Auftrags-Zustand** (9.3)." (TK 9.1.1, Punkt 1) –
  deshalb gibt es hier **keinen** Kanal `queue:warteAufErgebnis` und keinen Rückkanal für den
  Ausgang eines Auftrags.
- „`import`, `loeschen`, `render` und `export` werden damit **nicht** als direkte Request/Response-
  Operationen aufgerufen, sondern über `reiheEin` eingereiht; ihr Fach-Ergebnis (`erfolg`/
  `fehlgeschlagen` samt Fachfehlercode) kommt über den Auftrags-Zustand." (TK 9.3.4) – es entstehen
  hier also **keine** Kanäle `media:importMedium`-artiger Bauart für die vier Auftragsarten.
- „**Fehlercodes sind ein geschlossener, typisierter Satz** … **Eine rohe Exception-Meldung wird nie
  zum Code.**" (TK 9.1.1, Punkt 3)
- „**Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code. Es gibt keine Operation,
  die „einfach nichts" zurückgibt und auf Gelingen hofft." (TK 9.1.1, Punkt 7)
- „**Unerwartete Ausnahmen fängt das Gateway** und übersetzt sie in `unbekannter_fehler` (intern
  protokolliert). Die App stürzt nicht ab, und **kein Stacktrace** gelangt in die Oberfläche."
  (TK 9.1.1, Punkt 8) – das erledigt der Wrapper aus #23; diese Datei baut **kein** eigenes
  `try/catch` um `ausfuehren` daneben.
- **ENTSCHIEDEN – dies ist die einzige Datei in M2 mit einer Fensterreferenz.** Kein anderes
  M2-Issue darf `BrowserWindow`, `webContents` oder `ipcMain` anfassen; M2-13 meldet ausdrücklich
  nur main-intern. Zwei Ereigniswege bedeuten zwei Meldungen desselben Stands beim Renderer.
- **ENTSCHIEDEN – hier steckt keine Fachlogik.** Diese Datei baut keinen `Auftrag`, ändert keinen
  Status, schreibt kein Journal, kein Protokoll und stößt den Torwächter nicht an. Sie packt
  Nutzlasten aus, prüft ihre Form und ruft die vier Operationen auf.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| Nutzlast auf `queue:reiheEin` ist kein Objekt, `art` unbekannt oder `payload` kein Objekt | `ungueltige_eingabe` | `reiheEin` wird **nicht** aufgerufen; keine Wirkung auf Q1/Q4, kein Ereignis |
| Nutzlast auf `queue:entferne`/`queue:wiederhole` ohne gültige `auftragId` | `ungueltige_eingabe` | Operation wird **nicht** aufgerufen; keine Wirkung |
| eine Operation liefert regulär `ok: false` (z. B. `nicht_gefunden` aus `entferne`) | der Code der Operation | unverändert durchreichen – **kein** Umschreiben, **kein** Vereinheitlichen |
| eine Operation wirft unerwartet | `unbekannter_fehler` | vom Wrapper (#23) gefangen und übersetzt; kein Stacktrace in die Oberfläche |
| kein Empfänger für `queue:geaendert` (Fenster noch nicht geladen oder bereits zerstört) | – | der Versand verfällt **still**; er wirft nicht und bricht `sendeQueueGeaendert` (M2-13) nicht ab (Verhalten bei **mehreren** Fenstern: s. STOPP) |

Fehlercodes werden **nicht erfunden**: Der Satz ist geschlossen – die fachlichen je Operation plus
`ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler` (TK 9.1.1 Punkt 3).

## Nicht selbst entscheiden – STOPP und fragen
- **Wann wird `verdrahteQueueIPC` beim Programmstart gerufen, und wer ruft es?** M0 hat dafür
  **keine** Stelle vorgesehen: #3 (Main-Bootstrap) kennt nur App-Lifecycle und `BrowserWindow`, und
  kein M0/M1-Issue führt eine zentrale „Verdrahtungs"-Funktion, in die sich Module eintragen. Die
  Antwort hat Folgen: Vor `app.whenReady()` registriert, aber nach dem Fensterladen aufgerufen –
  dann verpasst das Panel den ersten Stand; zu früh angemeldet – dann läuft der Ereignisversand ins
  Leere, weil noch kein Fenster existiert. Und es ist zugleich die Frage, ob ein **zweiter** Aufruf
  von `verdrahteQueueIPC` abgewiesen, ignoriert oder als Programmierfehler gemeldet wird (eine
  doppelte `ipcMain.handle`-Registrierung desselben Kanals ist in Electron ein Fehler). **Nicht
  selbst festlegen** – und den Aufruf **nicht** eigenmächtig in eine fremde Datei (`main.ts`,
  Bootstrap) einbauen; das wäre außerdem eine Änderung außerhalb des erlaubten Dateibereichs
  (Regel E).
- **Wie sieht der Ereignis-Versand aus, wenn mehrere Fenster existieren oder noch keines geladen
  ist?** Geht `queue:geaendert` an **alle** `BrowserWindow`-Instanzen, an ein bestimmtes
  „Hauptfenster", oder an das zuletzt fokussierte? Und was passiert mit Meldungen, die anfallen,
  **bevor** ein Fenster geladen ist – verfallen sie, oder muss der letzte Stand nachgeliefert
  werden, sobald das Fenster da ist (sonst zeigt das Panel bis zur nächsten Zustandsänderung eine
  leere Warteschlange, obwohl Aufträge laufen)? Die Planung sieht in v1 **ein** Fenster vor, aber
  das ist nirgends als Invariante festgeschrieben. **Fragen, nicht annehmen** – eine falsche Wahl
  fällt erst auf, wenn ein zweites Fenster existiert oder der Start langsam ist.
- **Verbot – kein zweiter Ereignisweg.** Der Versand von `queue:geaendert` passiert ausschließlich
  hier, ausgelöst über den Hörer aus M2-13. Kein direkter `webContents.send` in einer anderen
  M2-Datei, kein zusätzlicher Kanal für Teilmengen („nur der laufende Auftrag", „nur der
  Fortschritt").
- **Verbot – die Hülle nicht anfassen.** Der Rückgabewert jeder Operation wird **unverändert**
  weitergereicht: kein Auspacken von `wert`, kein `throw` im Fehlerfall, kein Umschreiben von
  Codes, keine zusätzlichen Felder. Wer hier „vereinfacht", vernichtet den `Fehlercode` und macht
  aus Reparatur-Modus, Wiederholen und dem FAT32-Hinweis ein „irgendwas ist schiefgelaufen".
- **Verbot – keine eigenen Kanalnamen.** Alle fünf Namen stehen in `src/shared/contracts/kanaele.ts`
  und werden von dort importiert; kein String-Literal `'queue:…'` im Code dieser Datei. Und
  **keine** Kanäle über die vier plus das Ereignis hinaus – insbesondere kein Lesezugang zu Q3
  (`protokoll.json`), der in v1 ausdrücklich nicht vorgesehen ist, und keine Kanäle für
  `pendingDeletions` (die sind main-intern, TK 9.4.7).
- **Verbot – keine Fachlogik und keine Nutzlast-Reparatur.** Eine ungültige Nutzlast wird
  abgelehnt, **nicht** zurechtgebogen (keine Vorbelegung fehlender Felder, kein Trimmen von
  Strings, kein Umwandeln von Zahlen). Ein Renderer-Fehler soll sichtbar werden, nicht
  stillschweigend geheilt.
- **Verbot – die vier Operationen nicht umbenennen oder zusammenfassen.** Kein Sammelkanal
  `queue:befehl` mit einem `typ`-Feld; die vier Kanäle stehen so im Vertrag.
