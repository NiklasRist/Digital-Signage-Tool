### Issue M2-17: [auftrags-manager] Queue-Dateien atomar und serialisiert lesen und schreiben

## Ziel (in einem Satz)
Jede Datei der Auftragsverwaltung (Q2, Q3, Q4) wird über **eine** gemeinsame Stelle gelesen und
geschrieben – absturzsicher (Backup + Temp + Rename) und pro Pfad serialisiert –, sodass zwei
gleichzeitige Schreibvorgänge auf dieselbe Datei sich niemals verschränken können.

## Modul & Datei
- Modul: `auftrags-manager` [P6] (Main)
- Datei: `src/main/auftrags-manager/schreibe-queue-json.ts`
- Vertrag: Technisches Konzept **9.3** (die vier Speicher), **9.5.4** (Lock-Grenze, atomares
  Schreiben, Sichtbarkeit von Speicherfehlern) – Quelle der Wahrheit
- Prozess/Speicher: P6, Q2 (`projects/<id>/queue-retry.json`), Q3 (`protokoll.json`),
  Q4 (`warteschlangen-journal.json`)

## Warum das im Gesamtsystem wichtig ist
Dies ist die **einzige** Stelle im ganzen Modul, die `fs` anfasst. M2-03 (Q2), M2-04 (Q3), M2-05
(Q4) und M2-14 (`pendingDeletions`) rufen ausschließlich hier auf. Zwei Fehlerklassen entstehen,
wenn diese Funktion nachlässig gebaut wird, und beide sind stiller Datenverlust:
**Erstens die Verschränkung.** Q2 wird im Betrieb aus mehreren Richtungen fortgeschrieben – ein
Auftrag scheitert (`merkeFehlschlag`), gleichzeitig meldet der `media-service` eine offene Löschung
(`merkePendingDeletion`). Beide lesen die Datei, ändern ihren Teil und schreiben zurück. Ohne
Serialisierung pro Pfad überschreibt der zweite Schreibvorgang die Änderung des ersten (Lost Update)
– und anders als bei `project.json` gibt es hier **kein** Lock, das das verhindern könnte: das D1-Lock
schützt ausdrücklich nur `project.json`.
**Zweitens der stille Fallback.** Wer eine defekte JSON-Datei mit `try { … } catch { return fallback }`
behandelt, verwandelt eine kaputte Q2-Datei in eine leere – alle vorgemerkten Fehlschläge und alle
offenen Löschungen sind damit weg, ohne dass irgendjemand es merkt. Genau deshalb muss diese
Funktion zwischen „Datei existiert noch nicht" (normal, Erstbenutzung) und „Datei ist unlesbar"
(Fehler, meldepflichtig) hart unterscheiden.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/auftrags-manager/schreibe-queue-json.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'

// Die modul-eigene Fehlercode-Union der Auftragsverwaltungs-Speicher. #12 liefert NUR die drei
// generischen Codes (ungueltige_eingabe, nicht_gefunden, unbekannter_fehler); #22 fuegt Ergebnis
// den zweiten Typparameter F hinzu, ueber den jedes Modul seine EIGENE Union in seiner EIGENEN
// Datei einhaengt. speicher_fehler steht deshalb HIER und nicht in einem geteilten Typ;
// src/shared/contracts/ergebnis.ts wird dafuer NICHT angefasst (fremde Datei, Regel E).
export type QueueFehlercode = 'speicher_fehler'

// Schema-Version ALLER Queue-Dateien (Q2, Q3, Q4). Modul-lokal und hier deklariert, damit die
// drei Speicher nicht je eine eigene Zahl erfinden. NICHT die AKTUELLE_SCHEMA_VERSION aus #21
// verwenden – die gehoert zu project.json/config.json, eine Kopplung an D1-Migrationen ist
// unerwuenscht.
export const QUEUE_SCHEMA_VERSION = 1

export async function leseQueueDatei<T>(pfad: string, fallback: T): Promise<Ergebnis<T, QueueFehlercode>>
// pfad existiert nicht        -> { ok: true, wert: fallback }
// pfad existiert und ist gueltiges JSON -> { ok: true, wert: <geparster Inhalt> }
// pfad existiert, ist NICHT parsebar, <pfad>.bak ist parsebar
//                             -> { ok: true, wert: <geparster Inhalt von <pfad>.bak> }
// pfad NICHT parsebar UND <pfad>.bak fehlt oder ist ebenfalls NICHT parsebar
//                             -> { ok: false, fehler: { code: 'speicher_fehler', … } }

export async function schreibeQueueDatei(pfad: string, inhalt: unknown): Promise<Ergebnis<void, QueueFehlercode>>
// 1. bestehende Datei (falls vorhanden) nach <pfad>.bak kopieren (fs.copyFile, kein Verschieben)
// 2. inhalt als JSON nach <pfad>.tmp schreiben
// 3. <pfad>.tmp durch Rename-mit-Ersetzen auf <pfad> bringen (gleiche Partition)
// Schreibvorgaenge auf DENSELBEN pfad laufen streng nacheinander (verkettete Promise je Pfad);
// Schreibvorgaenge auf VERSCHIEDENE Pfade laufen unabhaengig und blockieren einander nicht.
```

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `pfad` (beide Funktionen) | absoluter Pfad einer Queue-Datei, vom Aufrufer über die Pfad-Autorität (`projektOrdner(projektId): string`, #49) bzw. `ermittleDatenOrt(): string` (#5) ermittelt | nicht leer; wird als Schlüssel der Serialisierungs-Kette verwendet – derselbe logische Pfad muss denselben Schlüssel ergeben (Normalisierung, s. STOPP) |
| `fallback` (`leseQueueDatei`) | Wert, der bei **fehlender** Datei zurückgegeben wird | wird unverändert durchgereicht; er wird **nicht** geschrieben und **nicht** bei einer defekten Datei verwendet |
| `inhalt` (`schreibeQueueDatei`) | vollständiger neuer Dateiinhalt | muss serialisierbar sein (kein Zyklus, kein `BigInt`, keine Funktion); es wird **immer** die ganze Datei geschrieben, nie ein Teil angehängt |

Ausgang bei Erfolg: `Ergebnis<T, QueueFehlercode>` mit dem geparsten Inhalt bzw. dem `fallback`
(Lesen); `Ergebnis<void, QueueFehlercode>` und eine Datei, die entweder vollständig alt oder
vollständig neu ist, plus ein `<pfad>.bak` mit der zuvor gültigen Fassung (Schreiben).
Ausgang bei Fehler: `fehler.code` ist `speicher_fehler` (die modul-eigene Union `QueueFehlercode`,
in dieser Datei deklariert) oder einer der generischen Codes `ungueltige_eingabe`,
`nicht_gefunden`, `unbekannter_fehler` aus #12, die `Ergebnis` immer zulässt.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Lock-Grenze:** Das D1-Lock schützt **nur** `project.json`. Die Auftragsverwaltungs-Speicher
  Q2/Q3 (eigene Dateien, 9.3) haben ihre **eigene** Serialisierung – der `auftrags-manager` hängt
  **nicht** am `project-store`-Lock." (TK 9.5.4) – **diese** Funktion *ist* die eigene
  Serialisierung. Sie ruft **kein** `mitD1Lock` auf und führt **kein** zweites Lock ein.
- „**Seriell:** höchstens **ein** Auftrag in `laeuft`. Das ist der einzige Sperr-Mechanismus des
  Systems; ein zweites Lock ist nicht nötig und darf nicht eingeführt werden." (TK 9.3.5) – die
  Verkettung pro Pfad ist eine **Reihenfolge-Garantie innerhalb dieser Datei**, keine
  systemweite Sperre und kein Ersatz für die serielle Auftragsordnung. Es entsteht daraus insbesondere
  **keine** OS-Dateisperre und kein Mutex-Objekt, das andere Module benutzen könnten.
- „**Atomar:** Schreiben nach Temp-Datei + Rename (gleiche Partition). `project.json` ist **nie**
  halb geschrieben." (TK 9.5.4) – wörtlich über `project.json` gesagt; hier gilt dasselbe Verfahren
  für die Queue-Dateien, weil sie derselben Absturzgefahr unterliegen.
- „**Ein Backup:** `project.json.bak` = letzte heile Version. Ist `project.json` beim Laden defekt
  → aus `.bak` wiederherstellen; ist auch das defekt → **Fehler melden**, **nicht**
  leer/verlustbehaftet weiterstarten." (TK 9.5.4) – analog entsteht je Queue-Datei genau **eine**
  `.bak`-Fassung. Keine Generationen, keine Zeitstempel im Backup-Namen. Und analog wird aus dieser
  `.bak` auch **gelesen**: Ein Backup, aus dem nie wiederhergestellt wird, wäre reine Schreiblast.
- „**Speicherfehler sind sichtbar (NFA-02):** Scheitert eine Auto-Speicherung (Platte voll, Rechte),
  wird das **nicht still verschluckt** – die UI zeigt dauerhaft „nicht gespeichert" + automatischer
  Wiederholversuch; die Änderungen **bleiben im Speicher** (kein Rollback, kein Arbeitsverlust).
  Erst nach erfolgreichem Schreiben verschwindet der Hinweis." (TK 9.5.4) – diese Funktion
  **meldet** den Fehler mit Code nach oben; die Sichtbarmachung selbst ist Sache der Aufrufer.
  Ein verschluckter Fehler (leeres `catch`, Rückgabe von `ok: true` trotz Fehlschlag) ist hier der
  schwerste denkbare Verstoß.
- „**Fehlercodes sind ein geschlossener, typisierter Satz:** die fachlichen je Operation (9.4.9,
  9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`.
  **Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1 Punkt 3)
- Die Ergebnis-Hülle lautet wörtlich (TK 9.1.1):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Diese Funktion wirft **nie**; jeder Ausgang ist eine Hülle. Der Grund steht im Vertrag: Renderer
  und Main sind getrennte Prozesse, ein `throw` verliert Fehlerklasse und `code`, übrig bleibt Text.
- **Fehlende Datei ist kein Fehler.** Beim allerersten Start existiert keine der drei Dateien; die
  Erstbenutzung darf nicht als Defekt erscheinen. Deshalb: fehlende Datei → `ok: true` mit
  `fallback`, ohne die Datei anzulegen.
- **Defekte Datei: erst `.bak`, dann Fehler – nie der `fallback`.** Ein `JSON.parse`-Fehler, ein
  abgeschnittener Inhalt oder eine Datei, die sich nicht lesen lässt, führt zuerst zu einem
  Leseversuch auf `<pfad>.bak`; ist der erfolgreich, wird dessen Inhalt zurückgegeben (`ok: true`).
  Fehlt `<pfad>.bak` oder ist es ebenfalls defekt, ergibt das `speicher_fehler`. Ein stiller
  Rückfall auf den `fallback` würde eine beschädigte Q2-Datei in eine leere verwandeln und alle
  vorgemerkten Fehlschläge und offenen Löschungen unbemerkt vernichten – der `fallback` gilt
  **ausschließlich** für die fehlende Datei.
- **Die Wiederherstellung aus `.bak` repariert nichts von selbst.** Der Inhalt wird gelesen und
  zurückgegeben; die defekte `<pfad>` wird dabei **nicht** überschrieben, nicht gelöscht und nicht
  durch das Backup ersetzt. Das Zurückschreiben geschieht erst beim nächsten regulären
  `schreibeQueueDatei` des Aufrufers.
- **`QUEUE_SCHEMA_VERSION` wird hier deklariert, aber nicht ausgewertet.** Die Konstante gehört in
  diese Datei, damit Q2 (M2-03/M2-14), Q3 (M2-04) und Q4 (M2-05) dieselbe Zahl verwenden statt je
  eine eigene zu erfinden. Das Prüfen der `schemaVersion` einer gelesenen Datei ist Sache der
  Aufrufer – `leseQueueDatei` und `schreibeQueueDatei` sehen den Inhalt als `unknown` bzw. `T`.
- **Immer die ganze Datei.** Es wird nie zeilenweise angehängt und nie in eine bestehende Datei
  hineingeschrieben; `inhalt` ersetzt den kompletten Dateiinhalt.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `leseQueueDatei`: Datei existiert nicht (`ENOENT`) | – | **kein Fehler**: `{ ok: true, wert: fallback }`; es wird nichts angelegt |
| `leseQueueDatei`: Inhalt ist kein gültiges JSON, `<pfad>.bak` ist gültiges JSON | – | **kein Fehler**: `{ ok: true, wert: <Inhalt von .bak> }`; die defekte `<pfad>` bleibt unverändert liegen |
| `leseQueueDatei`: Inhalt ist kein gültiges JSON, `<pfad>.bak` fehlt oder ist ebenfalls defekt | `speicher_fehler` | kein Rückfall auf `fallback`; Meldung nennt den Pfad, keine Exception-Rohmeldung als Code |
| `leseQueueDatei`: I/O-Fehler (Rechte, `EBUSY`, defektes Medium) | `speicher_fehler` | keine Wirkung, kein Rückfall auf `fallback`; ein I/O-Fehler auch beim `.bak`-Versuch ändert daran nichts |
| `pfad` ist leer oder kein String | `ungueltige_eingabe` | keine Datei wird angefasst |
| `schreibeQueueDatei`: `inhalt` nicht serialisierbar (Zyklus, `BigInt`, Funktion) | `ungueltige_eingabe` | Prüfung **vor** jedem Dateizugriff; weder `.bak` noch `.tmp` noch Zieldatei werden berührt |
| `schreibeQueueDatei`: I/O-Fehler beim Kopieren nach `.bak` | `speicher_fehler` | ob der Vorgang abbricht oder trotzdem geschrieben wird, ist offen – s. „Nicht selbst entscheiden" |
| `schreibeQueueDatei`: I/O-Fehler beim Schreiben von `.tmp` (Platte voll, Rechte) | `speicher_fehler` | Zieldatei bleibt unverändert (das Rename fand nie statt); `.tmp`-Rest wird aufgeräumt |
| `schreibeQueueDatei`: Rename schlägt fehl (`EBUSY`/`EPERM` unter Windows) | `speicher_fehler` | Zieldatei bleibt unverändert; ob vorher ein Retry+Backoff läuft, s. „Nicht selbst entscheiden" |
| unerwartete Ausnahme irgendwo im Ablauf | `unbekannter_fehler` | wird gefangen und als Hülle gemeldet, **kein** Stacktrace nach außen, kein `throw` |

## Nicht selbst entscheiden – STOPP und fragen
- **Rename-mit-Ersetzen ist plattformabhängig.** Der Vertrag stellt das ausdrücklich fest:
  „**Rename-mit-Ersetzen plattformsicher:** Das atomare Ersetzen verhält sich auf Windows anders als
  auf POSIX; die Umsetzung muss ein **Ersetzen** garantieren, ohne die alte Datei vor Fertigstellung
  der neuen zu entfernen." (TK 9.6.3) Für den USB-Export ist die Antwort vorgezeichnet – „**Atomar
  ersetzen:** `.part` → `<dateiname>` per Rename-mit-Ersetzen. Auf Windows bei `EBUSY`/`EPERM`
  **Retry+Backoff**." (TK 9.6.2) –, für die Queue-Dateien nicht. **Dies ist dieselbe offene Frage
  wie bei #31 (`config.json` atomar schreiben), #46 (`project.json` atomar schreiben) und beim
  `export-service` in M6.** Falls dort bereits eine Lösung feststeht: **exakt dieselbe verwenden.**
  Sonst gemeinsam klären – vier unterschiedliche Workarounds für dasselbe Problem sind das schlechteste
  aller Ergebnisse. **Nicht selbst erfinden.**
- **Ist ein `fsync` vor der Erfolgsmeldung nötig?** Für den Export ist es entschieden: „**`fsync` vor
  Erfolg:** Erst wenn die Bytes physisch auf dem Stick sind, gilt der Export als fertig – ein sofort
  abgezogener Stick verliert so keine gepufferten Daten." (TK 9.6.3) Für `project.json` (TK 9.5.4)
  und für die Queue-Dateien nennt der Vertrag es **nicht**. Zu klären ist, ob die `.tmp`-Datei vor
  dem Rename ge-`fsync`t wird und ob zusätzlich der Verzeichnis-Eintrag ge-`fsync`t werden muss,
  damit das Rename selbst einen Stromausfall übersteht. **Nicht stillschweigend weglassen** – Q2
  liegt möglicherweise auf einem USB-Stick, und dort ist genau dieser Fall real.
- **Verhalten, wenn das `.bak`-Kopieren fehlschlägt.** Bricht der ganze Schreibvorgang ab (keine
  neue Fassung ohne frisches Backup) oder wird trotzdem geschrieben (die neuen Daten haben Vorrang,
  `.bak` bleibt veraltet)? Der Vertrag entscheidet das weder in TK 9.5.4 noch anderswo, und beide
  Varianten haben eine echte Konsequenz. **Dieselbe Frage stellt sich in #31 und #46** – dieselbe
  Antwort verwenden.
- **Läuft `leseQueueDatei` ebenfalls über die Verkettung oder nur `schreibeQueueDatei`?** Die
  Aufrufer arbeiten in Lesen-Ändern-Schreiben-Zyklen (M2-03 `merkeFehlschlag`, M2-14
  `merkePendingDeletion`). Bleibt das Lesen außerhalb der Kette, kann ein Zyklus einen Stand lesen,
  der noch nicht geschrieben ist, und die fremde Änderung anschließend überschreiben – die
  Serialisierung des Schreibens allein verhindert das **nicht**. Für Q2 ist die Aufrufer-Seite
  inzwischen entschieden – M2-03 hält den geladenen Stand im Speicher und ist der **einzige**
  Schreiber der Q2-Datei (M2-14 geht über M2-03) –; ob zusätzlich das **Lesen** in dieser Datei in
  die Kette gehört, ist damit **nicht** beantwortet und gilt genauso für Q3 und Q4.
- **Wie wird der Schlüssel der Serialisierungs-Kette gebildet?** Zwei Schreibvorgänge auf
  physisch dieselbe Datei, deren `pfad`-Zeichenketten sich in Groß-/Kleinschreibung, Trennzeichen
  oder `.`-Segmenten unterscheiden, würden in **zwei** Ketten landen und sich wieder verschränken.
  Ob und wie normalisiert wird (`path.resolve`, Kleinschreibung nur unter Windows, `fs.realpath`),
  ist offen – und die Entscheidung entwertet bei falscher Wahl die gesamte Serialisierung.
- **Keine Kenntnis über den Inhalt aufbauen.** Diese Funktion ist generisch (`<T>`, `unknown`); sie
  **prüft** die `schemaVersion` nicht (sie exportiert nur die Konstante `QUEUE_SCHEMA_VERSION` für
  die Aufrufer), migriert **nicht**, kennt **keine** Q2-/Q3-/Q4-Struktur und schreibt eine defekte
  Datei **nicht** aus dem `.bak` zurück. Alles davon gehört den Aufrufern (M2-03/M2-04/M2-05).
  Auch nicht „nur schnell die schemaVersion mitschreiben".
- **Keine Aufräumlogik erfinden.** Kein Löschen alter `.bak`-Dateien, kein periodisches Kürzen,
  keine Rotation – die Rotation von Q4 gehört ausschließlich M2-05.
