### Issue M2-04: [auftrags-manager] Q3-Ausführungsprotokoll anhängen

## Ziel (in einem Satz)
Jeder beendete Auftragsversuch – erfolgreich, fehlgeschlagen oder abgebrochen – hinterlässt einen
dauerhaften Eintrag in `protokoll.json`, sodass später nachvollziehbar bleibt, was die Anwendung
wann produziert hat und woran etwas gescheitert ist.

## Modul & Datei
- Modul: `auftrags-manager` [P6] (Main)
- Datei: `src/main/auftrags-manager/q3-protokoll.ts`
- Vertrag: Technisches Konzept **9.3** (die vier Speicher, Q3 und die Tabelle „Wann geschrieben
  wird") – Quelle der Wahrheit; TK **9.5.2** (Abgrenzung zur Ausgabe-Liste)
- Prozess/Speicher: P6, Q3 (`<Datenort>/protokoll.json`, **app-weit**)

## Warum das im Gesamtsystem wichtig ist
Q3 ist der einzige dauerhafte Nachweis des Systems. Er beantwortet die Fragen, die im Studio
tatsächlich gestellt werden: Wann wurde die aktuelle Schleife erzeugt? Warum ist der Export
gestern nicht auf dem Stick gelandet? Hat der Import der beschädigten Datei jemals funktioniert?
Weil die Datei **unbegrenzt** wächst und nie automatisch gelöscht wird, ist jede lokale Entscheidung
hier praktisch endgültig. Drei Fehlgriffe sind besonders teuer: Wer bei einer defekten
`protokoll.json` „einfach neu anfängt", löscht die gesamte Historie mit einem Schreibvorgang. Wer
zeilenweise anhängt statt die Datei atomar neu zu schreiben, hinterlässt bei einem Absturz mitten im
Schreiben eine halbe Zeile – und damit eine Datei, die beim nächsten Start unlesbar ist. Und wer
„zur Bequemlichkeit" eine Leseoperation samt IPC-Kanal ergänzt, baut eine **zweite** Quelle für die
Ausgabe-Liste der Oberfläche auf; die Liste zeigt dann Dateien an, die es auf der Platte gar nicht
mehr gibt, weil Q3 Historie ist und nicht Ist-Bestand.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/auftrags-manager/q3-protokoll.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { ProtokollEintrag } from '../../shared/contracts/protokoll'
import type { QueueFehlercode } from './schreibe-queue-json'   // = 'speicher_fehler' (M2-17)

// Fremde Aufrufe – vollstaendige Signaturen, damit hier nichts geraten wird:
//   M2-17: leseQueueDatei<T>(pfad: string, fallback: T): Promise<Ergebnis<T, QueueFehlercode>>
//   M2-17: schreibeQueueDatei(pfad: string, inhalt: unknown): Promise<Ergebnis<void, QueueFehlercode>>
//   M2-17: const QUEUE_SCHEMA_VERSION = 1   // gilt fuer Q2, Q3 und Q4 – KEINE eigene Zahl erfinden
//   #5:    ermittleDatenOrt(): string       // app-weiter Datenort der portablen App

export async function haengeProtokollEintragAn(eintrag: ProtokollEintrag): Promise<Ergebnis<void, QueueFehlercode>>
// Dateiform: { schemaVersion: number; eintraege: ProtokollEintrag[] }
//            schemaVersion beim Schreiben IMMER QUEUE_SCHEMA_VERSION aus M2-17
// Ablauf: Datei lesen -> eintrag ans Ende von eintraege haengen -> Datei KOMPLETT neu schreiben,
//         atomar ueber schreibeQueueDatei (M2-17). Kein zeilenweises Anhaengen.
// Ort: <Datenort>/protokoll.json, Datenort ueber ermittleDatenOrt() (#5).
```

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `eintrag` | vollständiger `ProtokollEintrag` (M2-01) eines **beendeten** Versuchs | `id`, `auftragId`, `art`, `projektId`, `versuch`, `begonnenAm`, `beendetAm` und `ergebnis` müssen gesetzt sein; `fehler` und `ausgabe` müssen **vorhanden** sein, ihr Wert darf `null` sein (M2-01 typisiert beide als `| null`, nicht als optional – ein fehlendes Feld ist etwas anderes als ein leeres); `ergebnis` ist einer von `erfolg`/`fehlgeschlagen`/`abgebrochen` – ein Eintrag über einen noch laufenden Auftrag ist ein Programmfehler und wird abgewiesen |

Ausgang bei Erfolg: `Ergebnis<void, QueueFehlercode>`; `protokoll.json` enthält danach alle
bisherigen Einträge plus den neuen, in dieser Reihenfolge.
Ausgang bei Fehler: `fehler.code` ist `speicher_fehler` (die modul-eigene Union `QueueFehlercode`
aus M2-17) oder einer der generischen Codes `ungueltige_eingabe`, `nicht_gefunden`,
`unbekannter_fehler` aus #12, die `Ergebnis` immer zulässt.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Q3 laut Speicher-Tabelle (TK 9.3): Inhalt „**ein Eintrag je beendetem Versuch** (append-only)",
  Persistenz „**dauerhaft, unbegrenzt** — nie automatisch gelöscht", Ort „`protokoll.json`
  (app-weit)", Begründung „Nachvollziehbarkeit/Audit; enthält die Ausgabe-Historie (erfolgreiche
  Renders) als Teilmenge".
- „**Q3 protokolliert nur, was tatsächlich gelaufen ist.** Ein Auftrag, der die Schlange nie
  verlassen hat, erzeugt **keinen** Protokolleintrag – es gibt nichts zu berichten. Seine Bewegungen
  stehen in Q4." (TK 9.3)
- „**Fehlschläge bleiben sichtbar:** Eine Wiederholung erzeugt einen **neuen** Q3-Eintrag mit
  höherem `versuch`. Ein Export, der zweimal an einem vollen Stick scheitert und beim dritten Mal
  klappt, hinterlässt **drei** Einträge – die Fehlerhistorie geht nicht verloren, auch wenn der
  Q2-Eintrag nach dem Erfolg verschwindet." (TK 9.3) – daraus folgt: **niemals** einen bestehenden
  Eintrag mit gleicher `auftragId` überschreiben oder ersetzen. Angehängt wird immer.
- Geschrieben wird ausschließlich bei den terminalen Übergängen. Wörtlich aus der Tabelle „Wann
  geschrieben wird" (TK 9.3): `laeuft` → `erfolg` = **Eintrag**, `laeuft` → `fehlgeschlagen` =
  **Eintrag**, `laeuft` → `abgebrochen` = **Eintrag**; bei „– → `anstehend` (eingereiht)",
  „`anstehend` → `laeuft`", „`anstehend` → entfernt" und „`fehlgeschlagen` → `anstehend`
  (`wiederhole`)" steht in der Q3-Spalte jeweils „–".
- „**Q3 ist NICHT die Quelle dieser Liste** – Q3 ist Historie und Nachweis (auch der Fehlschläge),
  die Ausgabe-Liste zeigt den **Ist-Bestand** des Ordners." (TK 9.5.2, zur Operation
  `listeAusgaben`) – die Oberfläche bezieht ihre Ausgabedateien aus `listeAusgaben` des
  `project-store`, **nicht** aus Q3.
- Die Datei wird **komplett und atomar neu geschrieben**, nie zeilenweise angehängt. Begründung: Ein
  Anhängen ohne Temp+Rename übersteht keinen Absturz mitten im Schreiben, und das Volumen ist
  harmlos – wenige Dutzend Aufträge pro Woche zu je etwa 200 Bytes ergeben nach Jahren einige
  hundert Kilobyte. Der Schreibvorgang läuft ausschließlich über `schreibeQueueDatei` aus M2-17;
  ein direktes `fs.appendFile` oder `fs.writeFile` in dieser Datei ist verboten.
- „**Lock-Grenze:** Das D1-Lock schützt **nur** `project.json`. Die Auftragsverwaltungs-Speicher
  Q2/Q3 (eigene Dateien, 9.3) haben ihre **eigene** Serialisierung – der `auftrags-manager` hängt
  **nicht** am `project-store`-Lock." (TK 9.5.4)
- **Eine defekte `protokoll.json` wird nie überschrieben.** Lässt sich die Datei nicht lesen oder
  parsen, meldet diese Funktion `speicher_fehler` und schreibt **nicht**. Ein Neuanfang mit einer
  leeren Liste würde die gesamte, unwiederbringliche Historie löschen – genau das, wogegen die
  Persistenzstufe „dauerhaft, unbegrenzt" gedacht ist. **Für Q4 gilt bewusst das Gegenteil:** Dort
  (M2-05) darf eine defekte Journal-Datei durch eine neue, leere ersetzt werden, weil Q4 laut
  Speicher-Tabelle (TK 9.3) „rein **diagnostisch**" ist und keine Nutzdaten enthält. Q3 enthält
  Nutzdaten – hier ist der Neuanfang ausgeschlossen. Wer die Q4-Regel auf Q3 überträgt, weil beide
  „nur Protokolle" sind, löscht die Historie.
- **Die Reaktion auf einen Schreibfehler liegt beim Aufrufer.** Diese Funktion meldet den Fehler
  über die Ergebnis-Hülle, mehr nicht: Sie ändert keinen Auftragszustand, sendet kein Ereignis und
  zeigt nichts in der Oberfläche an. Die Reaktion auf einen Schreibfehler liegt beim Aufrufer; für
  den Abschluss eines Auftrags ist das in M2-18 geregelt, für das Journal gilt die Regel aus M2-05,
  dass der Auftragsfluss nie anhält.
- **Fehlende Datei ist kein Fehler.** Beim ersten beendeten Auftrag existiert `protokoll.json` noch
  nicht; dann wird mit einer leeren Eintragsliste begonnen und die Datei angelegt.
- **Die `schemaVersion` ist `QUEUE_SCHEMA_VERSION` aus M2-17 (Wert `1`).** Beim Schreiben wird sie
  immer aus dieser Konstante gesetzt, beim Laden gegen sie geprüft – **keine** eigene Zahl in dieser
  Datei und **nicht** die `AKTUELLE_SCHEMA_VERSION` aus #21 (die gehört zu
  `project.json`/`config.json`). Gleiche Version → laden; **höhere** (unbekannte) Version →
  `speicher_fehler`, nicht raten; eine **niedrigere** Version existiert noch nicht (es gibt nur
  Version 1) und ergibt ebenfalls `speicher_fehler` mit dem Hinweis, dass eine Migration noch nicht
  vorgesehen ist. Geschrieben wird in keinem dieser Fälle.
- **`fehler` und `ausgabe` sind Pflichtfelder mit erlaubtem Wert `null`.** M2-01 typisiert beide als
  `| null` und ausdrücklich **nicht** als optional. Diese Funktion prüft deshalb ihr **Vorhandensein**
  mit, nicht ihren Inhalt: Ein Eintrag ohne die Schlüssel ist ein Programmfehler des Aufrufers
  (M2-18) und wird abgewiesen, ein Eintrag mit `null` ist der Normalfall (jeder Erfolg ohne Ausgabe,
  jeder Nicht-Fehlschlag).
- Die Ergebnis-Hülle lautet wörtlich (TK 9.1.1):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string } }
  ```
  Kein `throw`.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `eintrag` fehlt ein Pflichtfeld (`id`, `auftragId`, `art`, `projektId`, `versuch`, `begonnenAm`, `beendetAm`, `ergebnis`) | `ungueltige_eingabe` | Datei wird nicht angefasst |
| `eintrag` fehlt `fehler` oder `ausgabe` als Feld (`null` ist erlaubt, `undefined`/fehlend nicht) | `ungueltige_eingabe` | Datei wird nicht angefasst – sonst entstünde ein Eintrag, dem beim späteren Auswerten nicht anzusehen ist, ob es keine Ausgabe gab oder ob der Schreiber sie vergessen hat |
| `eintrag.ergebnis` ist kein terminaler Wert (`erfolg`/`fehlgeschlagen`/`abgebrochen`) | `ungueltige_eingabe` | Datei wird nicht angefasst – Q3 protokolliert nur Beendetes |
| `protokoll.json` existiert nicht | – | **kein Fehler**: mit leerer Eintragsliste beginnen, Datei anlegen |
| `protokoll.json` ist nicht parsebar (von M2-17 gemeldet, d. h. auch `.bak` half nicht) | `speicher_fehler` | **nicht** überschreiben, **nicht** neu beginnen – die Historie bleibt unangetastet |
| `schemaVersion` ungleich `QUEUE_SCHEMA_VERSION` (M2-17) | `speicher_fehler` | nicht raten, nicht schreiben; bei einer niedrigeren Version nennt die Meldung, dass eine Migration nicht vorgesehen ist |
| Schreibfehler (Platte voll, Rechte, Rename) – von M2-17 gemeldet | `speicher_fehler` | durchreichen, nicht verschlucken (NFA-02); was daraus folgt, entscheidet der Aufrufer (M2-18), nicht diese Funktion |
| Datenort nicht ermittelbar (#5) | `speicher_fehler` | Code und Meldung durchreichen, keinen eigenen Pfad erraten |
| unerwartete Ausnahme | `unbekannter_fehler` | gefangen und als Hülle gemeldet, kein `throw`, kein Stacktrace nach außen |

## Nicht selbst entscheiden – STOPP und fragen
- **Keine Reaktion auf den eigenen Fehler.** Diese Funktion meldet einen Schreibfehler über die
  Ergebnis-Hülle und hört dort auf: kein Verändern eines Auftragszustands, kein Ereignis, keine
  Anzeige in der Warteschlangen-Leiste, kein eigener Wiederholversuch. Was daraus folgt, gehört dem
  Aufrufer (M2-18).
- **Keine Leseoperation nach außen und kein IPC-Kanal für Q3 in Version 1.** Diese Datei exportiert
  ausschließlich `haengeProtokollEintragAn` – kein `leseProtokoll`, kein `holeHistorie`, kein
  `queue:protokoll`-Kanal, auch nicht „nur intern für Tests" in der Produktivdatei. Die
  Ausgabe-Liste der Oberfläche speist sich aus `listeAusgaben` (TK 9.5.2, `project-store`), nicht
  aus dem Protokoll. Wer hier eine Leseoperation ergänzt, schafft eine zweite Quelle für dieselbe
  Anzeige, und beide driften auseinander, sobald eine Ausgabedatei gelöscht oder ersetzt wird.
- **Kein automatisches Kürzen, kein Rotieren, kein Löschen.** Q3 ist „**dauerhaft, unbegrenzt** —
  nie automatisch gelöscht" (TK 9.3). Keine Obergrenze, kein Höchstalter, kein „ab 10 000 Einträgen
  die ältesten weg", kein Auslagern in Jahresdateien. Die Rotation gehört ausschließlich Q4 (M2-05)
  und ist dort mit Absicht anders geregelt: „**Die Trennung Q3/Q4 ist Absicht:** Q3 beantwortet
  „**was wurde produziert**" (nutzerlesbare Historie), Q4 „**was passierte in der Schlange**"
  (Diagnose). … deshalb ist Q3 unbegrenzt und Q4 rotierend." (TK 9.3)
- **Keine Fachlogik und keine Interpretation.** Diese Funktion bewertet nicht, ob ein Render „gut"
  war, berechnet keine Dauer neu, prüft keine Ausgabedatei auf Existenz und ergänzt keine Felder.
  Sie schreibt genau den übergebenen Eintrag. Zum Modul gilt: „Sie **plant, ordnet und
  protokolliert** nur — sie ersetzt keine Fachlogik." (TK 9.3)
- **Kein direkter Dateizugriff und kein zweites Lock.** Jeder Zugriff läuft über M2-17; kein
  `fs.appendFile`, kein eigener Schreib-Mutex, keine OS-Dateisperre.

## Definition of Done
- [ ] Ein Aufruf mit gültigem Eintrag hängt genau **ein** Element an `eintraege` an; alle zuvor
      vorhandenen Einträge stehen unverändert und in gleicher Reihenfolge davor
- [ ] Zwei Aufrufe mit derselben `auftragId`, aber unterschiedlichem `versuch`, ergeben **zwei**
      Einträge (kein Überschreiben)
- [ ] Bei fehlender `protokoll.json` entsteht eine Datei mit `schemaVersion: QUEUE_SCHEMA_VERSION`
      und genau einem Eintrag
- [ ] Ein Eintrag ohne den Schlüssel `fehler` oder ohne den Schlüssel `ausgabe` liefert
      `ungueltige_eingabe`; ein Eintrag mit `fehler: null` und `ausgabe: null` wird angenommen
- [ ] Bei nicht parsebarer `protokoll.json` liefert die Funktion `speicher_fehler` und die Datei ist
      danach **byte-identisch** zu vorher (Test vergleicht den Inhalt)
- [ ] Ein Eintrag mit `ergebnis` außerhalb von `erfolg`/`fehlgeschlagen`/`abgebrochen` liefert
      `ungueltige_eingabe` und lässt die Datei unverändert
- [ ] Die Datei exportiert ausschließlich `haengeProtokollEintragAn` – keine Lese-, Lösch- oder
      Kürzungsfunktion, kein IPC-Kanal
- [ ] Kein direkter `fs`-Aufruf in dieser Datei; jeder Zugriff läuft über M2-17
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze)
- [ ] Keine Datei außerhalb von `src/main/auftrags-manager/q3-protokoll.ts`
      (+ zugehörige Testdatei) geändert
