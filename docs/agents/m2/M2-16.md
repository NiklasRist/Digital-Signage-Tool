### Issue M2-16: [auftrags-manager] Render-Handler verzahnen

## Ziel (in einem Satz)
Der `render`-Auftrag bekommt seinen ausführenden Dienst: `renderReel` und `cancelRender` werden von
außen hineingereicht und in der Handler-Registry so verdrahtet, dass Fortschritt am Auftrag sichtbar
wird, das `RenderResult` zum terminalen Auftragszustand führt und ein Abbruch die richtige
`renderId` trifft.

## Modul & Datei
- Modul: `auftrags-manager` (Main)
- Datei: `src/main/auftrags-manager/render-verzahnung.ts`
- Vertrag: Technisches Konzept **9.3.6** (Verzahnung mit `render-service`), **9.2.3**
  (`RenderResult`), **9.2.7** (Fortschritt/Abbruch), **9.3.1** (`Auftrag`) – Quelle der Wahrheit
- Prozess/Speicher: P6 ↔ P4; verändert den laufenden Auftrag in **Q1**. Kein neuer IPC-Kanal (diese
  Datei registriert nur main-intern; `kanaele.ts` wird hier **nicht** angefasst).

## Warum das im Gesamtsystem wichtig ist
Der Render ist der einzige Auftrag, der Minuten dauert, Fortschritt meldet und abgebrochen werden
kann. Diese Datei ist die Naht zwischen der Steuerungsschicht (P6) und dem Fachdienst (P4) – und
Nähte sind die Stellen, an denen Zustände doppelt oder gar nicht gepflegt werden.

Drei konkrete Folgen falscher lokaler Entscheidungen: (1) Wird das `RenderResult` nicht in einen
terminalen Handler-Ausgang übersetzt – etwa weil eine Ausnahme aus `renderReel` unbehandelt bleibt –,
bleibt der Auftrag für immer auf `laeuft`. Da die serielle Ordnung der **einzige** Sperr-Mechanismus
des Systems ist, steht danach die **gesamte** Warteschlange still, und der Nutzer kann nichts mehr
importieren, löschen oder exportieren. (2) Wird `RenderResult.status: 'fehler'` unbesehen als
Auftragsstatus übernommen, entsteht ein Status, den die Zustandsmaschine nicht kennt – der Auftrag
heißt `fehlgeschlagen`, das Ergebnis heißt `fehler`. (3) Werden die Nutzdaten (Pfad, Ausgabename,
Größe, Dauer) nicht weitergereicht, fehlt dem Q3-Protokolleintrag genau der Teil, der die
Ausgabe-Historie ausmacht – und der Oberfläche fehlt der **Ausgabename**, mit dem sie ihre
Vorbelegung für den nächsten Render (FA-22) auf dem Stand von D1 hält.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/auftrags-manager/render-verzahnung.ts
import type { RenderRequest } from '../../shared/contracts/render-request'
import type { RenderResult, RenderProgress } from '../../shared/contracts/render-result'

export function registriereRenderHandler(
  renderReel: (
    request: RenderRequest,
    aufFortschritt: (fortschritt: RenderProgress) => void,
  ) => Promise<RenderResult>,
  cancelRender: (renderId: string) => void,
): void
```

Die beiden Funktionen werden **hineingereicht, nicht importiert**: Der `render-service` entsteht erst
in M6, und M2 darf nicht auf ihn warten. Mit Test-Handlern ist diese Verzahnung vollständig
prüfbar – das ist der Zweck der Umkehr.

Die fremden Funktionen, die diese Datei aufruft, mit vollständiger Signatur (der umsetzende Agent
sieht die anderen Issues nicht):

```ts
// M2-08 (Handler-Registry) – heißt registriereAuftragsHandler, NICHT registriereHandler
// (registriereHandler ist bereits vom ipc-gateway belegt, #23)
registriereAuftragsHandler<A extends AuftragArt>(
  art: A,
  handler: HandlerFuer<A>,
  brichAb?: (auftrag: Auftrag) => void,
): void

// Der Ausgang, den der Handler liefern muss (M2-08) – über seinen Fehlercode generisch:
export type HandlerErgebnis<F extends string = string> =
  | { status: 'erfolg'; ergebnis: unknown | null }
  | { status: 'fehlgeschlagen';
      fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
  | { status: 'abgebrochen' }

// Der Handler-Typ, den registriereAuftragsHandler verlangt (M2-08):
type HandlerFuer<A extends AuftragArt> = (
  auftrag: Extract<Auftrag, { art: A }>,
  kontext: AusfuehrungsKontext,
) => Promise<HandlerErgebnis<string>>

export interface AusfuehrungsKontext {
  auftragId: string
  meldeFortschritt: (prozent: number | null) => void
}
```

**Der Typparameter nimmt dir die Wertprüfung NICHT ab.** `HandlerFuer` verlangt
`HandlerErgebnis<string>` – typmäßig ginge dort jede Zeichenkette durch. Genau deshalb prüft diese
Datei den aus dem `RenderResult` kommenden `fehlercode` **zur Laufzeit** gegen die unten
ausgeschriebene Wertliste (Punkt 3). Die Enge sitzt hier, weil hier der `string` zum Auftrags-Code
**wird**: Ab M2-18 gilt „der fachliche Code wird unverändert übernommen, nie abgebildet" – was diese
Datei durchlässt, steht danach unkorrigiert in Q3, und **Q3 ist dauerhaft**.

`ergebnis` ist das **gemeinsame** Nutzdaten-Feld aller vier Auftragsarten (TK 9.3.1): Bei `import`
steht dort der fertige `Asset`, bei `loeschen` `{ assetId }`, bei `export`
`{ zielPfad, dateigroesse }`. **Diese Datei füllt ausschließlich den Render-Fall** – sie kennt die
anderen Formen nicht und erzeugt sie nicht. Deshalb steht im Typ `unknown` und nicht die
Render-Form; wer sie hier auf `{ pfad, dateigroesse, gesamtdauer }` verengt, greift in eine fremde
Datei (`dispatcher.ts`, M2-08) ein und nähme dem Import sein Ergebnis.

Aufgabe der Registrierung (verbindlich):

1. **Handler für `art: 'render'`** über `registriereAuftragsHandler('render', handler, brichAb)` in
   der Handler-Registry (M2-08) eintragen. Beim Start eines `render`-Auftrags ruft er
   `renderReel(auftrag.payload, aufFortschritt)` auf – **ausschließlich** mit `auftrag.payload`, nie
   mit frisch aus dem Projekt geholten Daten (Snapshot, TK 9.3.5).
2. **Fortschritt abbilden:** `RenderProgress.prozent` → `Auftrag.fortschritt` des laufenden Auftrags
   (0–100). Werte **außerhalb** dieses Bereichs werden **auf ihn begrenzt** – kleiner 0 wird 0,
   größer 100 wird 100 –, nicht ungeprüft durchgereicht und **niemals** zum Anlass genommen, den
   laufenden Auftrag scheitern zu lassen. Andere Felder von `RenderProgress` (`phase`,
   `elementIndex`, `elementAnzahl`, `elementId`) wandern **nicht** in den `Auftrag` – der Typ hat dafür kein Feld (#16), und der Typ
   wird nicht geändert.
3. **Ergebnis übersetzen:** das terminale `RenderResult` in das `HandlerErgebnis` der Registry
   (M2-08) überführen. **Das `HandlerErgebnis` ist der Trichter – mehr als seine Felder kann diese
   Datei nicht weiterreichen:**
   - `status: 'erfolg'` → `{ status: 'erfolg', ergebnis: { pfad: <RenderResult.ausgabePfad>,
     ausgabeName: <RenderResult.ausgabeName>, dateigroesse: <RenderResult.dateigroesse>,
     gesamtdauer: <RenderResult.gesamtdauer> } }`.
     Inhaltlich unverändert – nur das Feld heißt `ergebnis` statt `ausgabe`, weil es bei den
     anderen Auftragsarten andere Nutzdaten trägt (s. o.); diese Datei füllt allein den
     Render-Fall. **Das sind alle vier Nutzdaten, die es gibt:** Seit TK v2.8 hat das
     `RenderResult` **kein** Feld `historieEintrag` mehr (TK 9.2.3) – es gibt also nichts
     Zusätzliches weiterzureichen und nichts, wofür ein weiteres Feld zu erfinden wäre.
     **`ausgabeName` ist seit TK v3.2 die vierte Nutzdate und wird hier zeichengleich
     übernommen** (Name **ohne** Endung, TK 9.2.3). Er heißt im `ergebnis` genauso wie im
     `RenderResult` – **nicht** `name`, **nicht** `dateiname` – und wird **nicht** aus `pfad`
     abgeleitet. Er reist **nur** hierher: „Der **Ausgabename** reist dabei **nur** in
     `Auftrag.ergebnis` […] In `ProtokollEintrag.ausgabe` steht er **nicht** – er ist dort
     bereits Teil des Pfades." (TK 9.3.6) Das Weglassen im Protokoll ist Sache von M2-18; diese
     Datei liefert den Wert vollständig ab.
   - `status: 'fehler'` → `{ status: 'fehlgeschlagen', fehler: { code, meldung, daten } }` (der
     Status heißt `fehlgeschlagen`, nicht „fehler" – so steht er in TK 9.3.1).
     **`fehlerhaftesElementId` WIRD weitergereicht, und zwar in `daten`:** Ist der Wert nicht
     `null`, wird `daten = { elementId: <RenderResult.fehlerhaftesElementId> }` gesetzt; ist er
     `null`, bleibt `daten` **weg** (das Feld ist optional). TK 9.2.3 schreibt diesen Weg wörtlich
     vor (s. Invarianten): Ohne ihn erreichte die ID **nie** den Nutzer, obwohl TK 9.2.1 die
     `RenderItem.id` genau damit begründet und der geführte Reparatur-Modus (FA-19) die Stelle
     benennen muss, zu der er führt.
   - `status: 'abgebrochen'` → `{ status: 'abgebrochen' }`. `abgebrochenBei` wird nicht
     weitergereicht (das `HandlerErgebnis` hat dafür kein Feld, und ein Abbruch trägt keine
     Nutzdaten).
   - **`RenderResult.fehlercode` ist laut #19 ein `string`; `HandlerErgebnis<F>.fehler.code` ist
     `F | GenerischerFehlercode` (M2-08/#22).** Der Wert wird deshalb **gegen die unten
     ausgeschriebene Wertliste geprüft und abgebildet**, nicht ungeprüft durchgereicht: Steht er in
     der Liste, wird er **zeichengleich** übernommen; steht er **nicht** darin, wird
     `unbekannter_fehler` gesetzt und der ursprüngliche Wert in die `meldung` aufgenommen. Ein
     `as`-Cast ist verboten – er brächte einen Wert in den Auftrag, den `queue-panel` und Q3 nicht
     kennen, und „Fehlercodes sind ein geschlossener, typisierter Satz" (TK 9.1.1) wäre nur noch auf
     dem Papier wahr.

     **Die Prüfliste – wörtlich der geschlossene Satz aus TK 9.2.3, hier ausgeschrieben, weil diese
     Datei nichts aus dem `render-service` importieren darf (M6 existiert noch nicht):**

     ```ts
     // Genau diese sieben Werte – keiner mehr, keiner weniger. Quelle: TK 9.2.3.
     const RENDER_FEHLERCODES = [
       'medium_fehlt',        // referenziertes Medium fehlt in media/ oder ist zustand: "fehlt"
       'ungueltiges_element', // einzelnes RenderItem in sich unstimmig (Trim, Dauer, PNG, Band)
       'ungueltige_eingabe',  // die ANFRAGE verletzt den Vertrag (generisch, TK 9.1.1 Punkt 3)
       'ffmpeg_fehler',       // ffmpeg/ffprobe scheitert – einschliesslich fehlgeschlagener Verifikation
       'kein_platz',          // zu wenig freier Speicher (T1 ODER Ausgabeordner)
       'speicher_fehler',     // Schreib-/Rename-Fehler am Ziel jenseits von Platzmangel
       'unbekannter_fehler',  // nicht zuordenbare Ausnahme (generisch, TK 9.1.1 Punkt 3)
     ] as const
     ```

     **`abgebrochen` steht bewusst NICHT in dieser Liste.** TK 9.2.3: „**`abgebrochen` ist *kein*
     Fehlercode.**" Ein abgebrochener Lauf kommt über `status: 'abgebrochen'` und trägt **kein**
     `fehler`-Objekt. Träfe diese Datei ihn trotzdem als Fehlercode an, zeigte die Oberfläche einen
     vom Nutzer selbst ausgelösten Abbruch als Fehler an.

     **Die Liste wird nicht ergänzt und nicht gekürzt.** Sie ist keine Sammelstelle für Codes, die
     einem beim Bauen einfallen; sie ist die Abschrift einer geschlossenen Vertragstabelle. Steht in
     M6 später ein Code darin, der hier fehlt, ist das ein **Vertragsfehler** – melden, nicht
     eigenmächtig nachtragen.
4. **Abbrecher registrieren:** als dritter Parameter von `registriereAuftragsHandler` eine Funktion
   `brichAb(auftrag: Auftrag): void`, die die `renderId` aus `auftrag.payload` (dem `RenderRequest`)
   zieht und damit `cancelRender(renderId)` aufruft. Der Abbrecher bekommt den **ganzen `Auftrag`**,
   nicht nur eine ID – nur so kommt er an die `renderId`. `entferne` (M2-10) erreicht ihn
   ausschließlich über `brich(auftrag)` aus M2-08 und importiert `cancelRender` **nicht** selbst.
5. **Kein terminaler Zustand aus dem Fortschrittskanal.** Fortschritt setzt niemals `status`,
   `fehler` oder einen Q3-Eintrag. Verspätete `RenderProgress`-Ereignisse, die nach dem terminalen
   `RenderResult` desselben Laufs eintreffen, werden **verworfen** – nicht angewendet.
6. **Eine gescheiterte Zusage ist ein Fehlschlag, kein Stillstand:** Lehnt das von `renderReel`
   zurückgegebene Promise ab (Ausnahme statt `RenderResult`), wird der Auftrag als
   **fehlgeschlagen** mit `unbekannter_fehler` abgeschlossen. Ein Auftrag darf unter keinen
   Umständen dauerhaft auf `laeuft` stehen bleiben – das blockiert den einzigen Sperr-Mechanismus
   des Systems auf unbestimmte Zeit.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `renderReel` | die Ausführung eines Render-Laufs; bekommt den `RenderRequest` und einen Fortschritts-Rückruf | wird beim Start eines `render`-Auftrags genau **einmal** aufgerufen; darf nicht parallel für zwei Aufträge laufen (serielle Invariante) |
| `cancelRender` | Abbruch-Signal an den laufenden Lauf | wird ausschließlich mit der `renderId` des **laufenden** Auftrags aufgerufen |
| `aufFortschritt` (an `renderReel` übergeben) | Rückruf des Dienstes für `RenderProgress` | nur `prozent` wird übernommen; Werte außerhalb 0–100 werden auf den Bereich begrenzt (<0 → 0, >100 → 100) |

Ausgang: kein Rückgabewert (`void`). Wirkung ist der eingetragene Handler samt Abbrecher in der
Registry (M2-08).
Ausgang bei Fehler: Diese Funktion ist keine IPC-Operation und trägt **keine** Ergebnis-Hülle. Fehler
des Laufs reisen über den Auftrags-Zustand: „**Auftrags-Ergebnis:** Wie ging der *Vorgang* aus
(`RenderResult`, Export-Ergebnis …)? Das reist **nicht** als Aufruf-Antwort, sondern über den
**Auftrags-Zustand** (9.3)." (TK 9.1.1, Punkt 1)

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „Ein `render`-Auftrag führt beim Start intern `renderReel(payload)` aus – **nach** dem Sofort-Flush
  von D1 (9.5.4). `RenderProgress.prozent` (Kanal `render:fortschritt`, 9.2.7) speist
  `Auftrag.fortschritt`; `RenderResult` bestimmt den terminalen Auftrags-`status`
  (erfolg/fehlgeschlagen/abgebrochen) und liefert bei Erfolg die Nutzdaten **Pfad, Ausgabename,
  Größe und Gesamtdauer** (9.2.3) – daraus baut die Auftragsverwaltung `Auftrag.ergebnis` **und**
  den Q3-Protokolleintrag. Der **Ausgabename** reist dabei **nur** in `Auftrag.ergebnis`: Über ihn
  erfährt die Oberfläche, welcher Name tatsächlich verwendet wurde, und hält ihre Vorbelegung mit
  `Project.letzterAusgabeName` (FA-22) im Gleichklang. In `ProtokollEintrag.ausgabe` steht er
  **nicht** – er ist dort bereits Teil des Pfades. Einen fertig vorbereiteten Historie-Eintrag
  liefert der `render-service` **nicht**; das wäre eine zweite Quelle für dieselbe Information."
  (TK 9.3.6)
  **Zum Sofort-Flush (seit TK v2.8 hier verortet):** Er ist der **erste Schritt dieses Handlers**,
  vor dem Aufruf von `renderReel`. TK 9.3.3 wörtlich: „Bei `render` und `export` erzwingt der Main
  den **Sofort-Flush** von D1 (9.5.4) – nicht beim Einreihen. **Er läuft als erster Schritt IM
  HANDLER**, also nach dem Statuswechsel und bevor der Handler die eigentliche Arbeit aufnimmt."
  Der Torwächter (#59) darf ihn **nicht** auslösen: Sein Auswahl- und Statuswechsel-Abschnitt ist
  bewusst synchron und enthält kein `await`; ein Flush ist asynchron und öffnete dort genau das
  Fenster, in dem ein zweiter Auftrag starten könnte – die serielle Invariante bräche lautlos.
  Nach dem Statuswechsel ist der Platz belegt, ein `await` also gefahrlos. Es bleibt bei **einer**
  Flush-Stelle je Auftragsart; der `export`-Handler macht es genauso.
- „`entferne` auf einen laufenden `render` delegiert an `cancelRender(renderId)`; die `renderId`
  liegt im `RenderRequest` des Auftrags — `auftragId` und `renderId` bleiben fest verknüpft."
  (TK 9.3.6)
- „Der frühere Fehlercode `render_aktiv` **entfällt** — durch die serielle Ordnung kann die
  Kollision, die er gemeldet hätte, gar nicht mehr auftreten." (TK 9.3.6) – dieser Code darf
  nirgends wieder auftauchen, auch nicht als Zwischenwert.
- „Der Fortschrittskanal trägt **keinen** Endzustand. Erfolg, Fehler und Abbruch kommen
  **ausschließlich** über das `RenderResult` (9.2.3)." (TK 9.2.7)
- „Nach dem terminalen `RenderResult` dürfen **keine** weiteren `RenderProgress`-Ereignisse dieser
  `renderId` mehr folgen. Verspätete Ereignisse eines bereits beendeten Laufs erkennt der Renderer an
  der nicht mehr aktuellen `renderId` und verwirft sie." (TK 9.2.7)
- „Genau **ein** terminaler Ausgang je Lauf, diskriminiert über `status` ∈ { `erfolg`, `fehler`,
  `abgebrochen` }. Alle drei tragen die `renderId`." (TK 9.2.3)
- „Bei `fehler` und `abgebrochen` entsteht **keine** neue Ausgabedatei; eine **bereits vorhandene
  Datei gleichen Namens bleibt unversehrt** (9.2.6). Aufgeräumt sind in beiden Fällen **der
  Arbeitsbereich T1 *und* die angefangene `<name>.mp4.part` im Ausgabeordner** – sonst bliebe im
  Ausgabeordner eine wachsende Leiche liegen. **Der Q3-Protokolleintrag entsteht trotzdem:** Q3 hält
  *einen Eintrag je beendetem Versuch*, also auch für Fehlschlag und Abbruch (9.3); nur das Feld
  `ausgabe` bleibt dort `null`." (TK 9.2.3) – bei `fehler`/`abgebrochen` gibt es folglich **keine**
  Nutzdaten weiterzureichen; das Aufräumen selbst gehört dem `render-service`, nicht dieser Datei.
- **ENTSCHIEDEN (TK v2.8) – es gibt KEINEN `historieEintrag` mehr.** „**Es gibt bewusst *kein* Feld
  `historieEintrag`.** Der Q3-Protokolleintrag wird **allein von der Auftragsverwaltung** gebaut
  (9.3) – sie besitzt ohnehin `auftragId`, `art`, `projektId`, `versuch`, `begonnenAm` und
  `beendetAm`. Der `render-service` liefert nur, was **nur er** weiß: Pfad, Größe, Gesamtdauer und den
  verwendeten Ausgabenamen; aus den ersten dreien wird `ProtokollEintrag.ausgabe`." (TK 9.2.3) Der frühere Platzhalter `HistorieEintrag` ist
  aus #19 entfernt. Diese Datei sucht ihn also **nicht**, reicht ihn **nicht** weiter und legt
  **kein** Feld dafür an – weder im `HandlerErgebnis` (fremde Datei, M2-08) noch daneben.
- **ENTSCHIEDEN – der Render-Fall füllt `ergebnis` mit genau drei Werten:** bei `art: 'render'`
  stehen in `HandlerErgebnis.ergebnis` (M2-08) `pfad`, `dateigroesse` und `gesamtdauer` – sonst
  nichts. Dass das Feld im Typ `unknown` heißt, ist **keine** Einladung, weitere Werte
  hineinzulegen. Wer dort ein Zusatzfeld erfindet, legt die Q3-Form fest, die M2-01/M2-18 bereits
  festgelegt haben, und das Protokoll ist **dauerhaft und unbegrenzt** – ein falsches Feld darin
  bleibt für immer.
- **ENTSCHIEDEN (TK v2.8) – `fehlerhaftesElementId` reist als `fehler.daten = { elementId }`
  weiter.** Wörtlich: „**Die betroffene Element-ID erreicht die Oberfläche über die strukturierten
  Fehlerdaten.** `RenderResult.fehlerhaftesElementId` ist Modul-intern; beim Abschluss des Auftrags
  übernimmt die Auftragsverwaltung `fehlercode` → `Auftrag.fehler.code`, `meldung` →
  `Auftrag.fehler.meldung` und `fehlerhaftesElementId` → **`Auftrag.fehler.daten = { elementId }`**
  (9.1.1, 9.3.1). Ohne diesen Weg käme die ID **nie** beim Nutzer an […] Die Form von `daten` ist
  damit **je Fehlercode festgelegt**: `{ elementId: string }` bei `medium_fehlt` und
  `ungueltiges_element`, sonst nicht gesetzt." (TK 9.2.3) Der Schlüssel heißt **`elementId`**, nicht
  `fehlerhaftesElementId` und nicht `id` – M2-18 reicht `daten` unverändert an `Auftrag.fehler` weiter,
  und der Reparatur-Modus (FA-19, #132/#133) liest genau diesen Schlüssel.
- **`RenderResult.fehlercode` ist ein `string` (#19); `HandlerErgebnis<F>.fehler.code` ist
  `F | GenerischerFehlercode` (M2-08/#22).** Der Wert wird gegen die oben ausgeschriebene Wertliste
  aus TK 9.2.3 geprüft und abgebildet; ein Wert außerhalb der Liste wird zu `unbekannter_fehler`,
  der Originalwert wandert in die `meldung`. „**Fehlercodes sind ein geschlossener, typisierter
  Satz** … **Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1)
- **Diese Abbildung widerspricht M2-18 nicht – die beiden Stellen tun Verschiedenes.** M2-18 („der
  fachliche Fehlercode wird **unverändert** übernommen, nie abgebildet, nie auf
  `unbekannter_fehler` gesetzt") gilt für Codes, die als **typisierter** Code im `HandlerErgebnis`
  ankommen. Diese Datei sitzt eine Stufe davor: Sie bekommt einen **untypisierten `string`** aus dem
  `RenderResult` und ist die Stelle, an der er zum Code **wird**. Genau deshalb prüft **sie** – und
  genau deshalb prüft **M2-18 nicht mehr**. Zwei Prüfungen wären zwei Wahrheiten, keine Prüfung wäre
  ein offener Satz.
- „**`abgebrochen` ist *kein* Fehlercode.** Ein vom Nutzer abgebrochener Lauf endet über
  `status: "abgebrochen"` (9.2.7) und trägt **kein** `fehler`-Objekt – sonst gäbe es zwei Wege,
  denselben Ausgang zu melden, und die Oberfläche zeigte einen Abbruch als Fehler an." (TK 9.2.3)
- Namensunterschied, der **nicht** eingeebnet werden darf: `RenderResult.status` kennt `erfolg` |
  `fehler` | `abgebrochen` (TK 9.2.3); `Auftrag.status` kennt `anstehend` | `laeuft` | `erfolg` |
  `fehlgeschlagen` | `abgebrochen` (TK 9.3.1). `fehler` → `fehlgeschlagen` ist eine bewusste
  Übersetzung, keine Umbenennung, die man sich sparen kann.
- „`fortschritt` | 0–100 oder `null` | grober Fortschritt (bei `render` aus `RenderProgress`,
  9.2.7); `null` wo unbestimmt" (TK 9.3.1)
- **ENTSCHIEDEN – Prozentwerte außerhalb von 0–100 werden auf den Bereich begrenzt.** Kleiner 0
  wird 0, größer 100 wird 100; der Wert wird weder ungeprüft durchgereicht noch führt er dazu, dass
  der Auftrag scheitert. Begründung: `Auftrag.fortschritt` ist laut TK 9.3.1 „0–100 oder `null`" –
  ein Wert außerhalb wäre ein **Vertragsbruch nach außen** (`queue-panel` und Q3 bekämen etwas, das
  der Typ nicht zulässt). Und ein Fortschrittswert ist nie ein Grund, einen laufenden Render
  abzubrechen: Der Fortschrittskanal trägt keinen Endzustand (TK 9.2.7), ein verrutschter Prozentwert
  darf also keine Minuten Renderarbeit vernichten.
- „**Seriell:** höchstens **ein** Auftrag in `laeuft`. Das ist der einzige Sperr-Mechanismus des
  Systems; ein zweites Lock ist nicht nötig und darf nicht eingeführt werden." (TK 9.3.5)
- „**Render friert seinen Eingang beim Einreihen ein:** die geordnete Liste + Profil des
  `RenderRequest` werden **zum Einreih-Zeitpunkt** als Snapshot genommen. Spätere Listenänderungen
  betreffen einen bereits eingereihten Render **nicht** (verhindert „gedrückt, dann getweakt,
  anderes Video")." (TK 9.3.5) – der Handler übergibt deshalb `auftrag.payload` an `renderReel` und
  beschafft sich nichts nach.
- „**Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code. Es gibt keine Operation,
  die „einfach nichts" zurückgibt und auf Gelingen hofft." (TK 9.1.1, Punkt 7) – Grundlage für
  Punkt 6 des Ablaufs (abgelehnte Zusage → `fehlgeschlagen`, nicht Stillstand).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `RenderResult { status: 'fehler' }`, `fehlercode` steht in `RENDER_FEHLERCODES` (z. B. `medium_fehlt`, `ffmpeg_fehler`, `ungueltiges_element`, `kein_platz`, `speicher_fehler`) | genau dieser Code, zeichengleich | Handler-Ausgang **fehlgeschlagen**; `meldung` wird mitgeführt; keine Nutzdaten in `ergebnis` |
| dazu: `fehlerhaftesElementId` ist gesetzt (kommt bei `medium_fehlt` und `ungueltiges_element` vor) | – | `fehler.daten = { elementId: <der Wert> }`; ohne das findet der Reparatur-Modus (FA-19) die Stelle nicht |
| dazu: `fehlerhaftesElementId` ist `null` | – | `daten` bleibt **weg** (Feld nicht setzen); **kein** `{ elementId: null }`, denn TK 9.2.3 legt die Form je Fehlercode fest und ein leerer Beutel wäre eine dritte Bedeutung |
| `RenderResult { status: 'fehler' }`, `fehlercode` steht **nicht** in `RENDER_FEHLERCODES` | `unbekannter_fehler` | Handler-Ausgang **fehlgeschlagen**; der gelieferte Rohwert wird in die `meldung` aufgenommen, damit er diagnostisch nicht verloren geht |
| `RenderResult { status: 'fehler' }`, `fehlercode` ist `'abgebrochen'` | `unbekannter_fehler` | `abgebrochen` ist laut TK 9.2.3 **kein** Fehlercode und steht deshalb nicht in der Liste; der Fall ist ein Vertragsbruch des `render-service` und wird als solcher gemeldet, **nicht** in `status: 'abgebrochen'` umgedeutet |
| `RenderResult { status: 'abgebrochen' }` | – | Handler-Ausgang **abgebrochen**; keine Nutzdaten |
| `renderReel`-Zusage wird abgelehnt (Ausnahme statt Ergebnis) | `unbekannter_fehler` | Handler-Ausgang **fehlgeschlagen**; der Auftrag verlässt `laeuft` in jedem Fall, damit die Schlange weiterläuft |
| Fortschritts-Rückruf nach dem terminalen Ergebnis | – | wird verworfen; `Auftrag.fortschritt` bleibt unangetastet |
| `RenderProgress.prozent` außerhalb 0–100 (z. B. `-5` oder `130`) | – | wird auf 0 bzw. 100 begrenzt; kein Statuswechsel, kein Abbruch, kein Fehler |

Fehlercodes werden **nicht erfunden**: Der Satz ist geschlossen – die sieben Render-Codes aus
TK 9.2.3, oben als `RENDER_FEHLERCODES` ausgeschrieben (die generischen `ungueltige_eingabe` und
`unbekannter_fehler` sind darin schon enthalten, TK 9.1.1 Punkt 3). Ein gelisteter Render-Code wird
**unverändert** übernommen, nie umgeschrieben und nie aus einer Meldung abgeleitet; ein nicht
gelisteter wird auf `unbekannter_fehler` abgebildet, **nicht** durchgereicht und **nicht** gecastet.

## Nicht selbst entscheiden – STOPP und fragen
- **Nicht monoton steigende Prozentwerte** (der Dienst meldet 50, danach 30): Sollen sie übernommen
  werden – die Anzeige springt dann zurück –, oder soll der bisherige Höchstwert stehen bleiben? Für
  Werte **außerhalb** 0–100 ist die Frage entschieden (Begrenzung, s. Invarianten); für den Rücklauf
  **innerhalb** des Bereichs ist sie es nicht, und ein hier eingebautes „nur aufwärts" würde einen
  echten Fehler im Fortschrittskanal des `render-service` unsichtbar machen. **Fragen** – bis dahin
  den gemeldeten Wert unverändert (nur begrenzt) übernehmen.
- **Ob jede Fortschrittsänderung ein `queue:geaendert` auslöst**, ist offen und gehört zu M2-13 –
  dort steht die Frage nach der Drosselung. Diese Datei entscheidet sie **nicht** eigenständig und
  baut insbesondere keine eigene Drossel-Logik daneben.
- **Verbot – nicht importieren, was hineingereicht wird.** Kein `import` aus dem `render-service`,
  kein `ffmpeg`, kein direkter Prozesszugriff. Sonst hängt M2 an M6 und ist nicht isoliert testbar.
- **Verbot – keine Fachlogik.** Diese Datei normalisiert nichts, prüft keine Medien, validiert keinen
  `ausgabeName` und räumt kein T1 auf; das gehört dem `render-service`.
- **Verbot – keinen zweiten Abbruchweg.** Der Abbruch läuft ausschließlich über den hier
  registrierten Abbrecher. Kein Prozess-Kill, kein zweites Abbruch-Flag.
- **Verbot – den `Auftrag`-Typ nicht erweitern.** Kein zusätzliches Feld für `phase`,
  `elementIndex` oder `renderId` am Auftrag. Was in `contracts` fehlt, wird **erfragt**, nicht lokal
  definiert (#16 ist fertig und wird nicht geändert).
- **Verbot – das `HandlerErgebnis` nicht erweitern.** Kein neues Feld, kein zweiter
  „Zusatzdaten"-Beutel neben `fehler.daten`. Der Typ liegt in `dispatcher.ts` (M2-08) und ist aus
  diesem Issue heraus eine **fremde Datei** (Regel E). Die betroffene Element-ID braucht auch kein
  neues Feld – sie reist im **vorhandenen** `fehler.daten` als `{ elementId }` (s. Invarianten).
- **Sofort-Flush: genau einmal, als erster Schritt.** `sofortFlush` (#47) wird **hier** gerufen,
  bevor `renderReel` startet – und **nur** hier (TK 9.3.3/9.5.4, seit v2.8). *Verbot:* keinen
  zweiten Flush an anderer Stelle dieser Datei, keinen im Torwächter (#59), und keine eigene
  Entprellung nachbauen. Scheitert der Flush, startet der Render **nicht** – der Auftrag
  scheitert mit `speicher_fehler`; einen Render auf einen Stand zu fahren, der nicht auf der
  Platte steht, wäre genau der Datenverlust, den der Flush verhindern soll.
- **Verbot – `RenderResult.fehlercode` nicht casten.** Kein `as Fehlercode`, kein
  `@ts-expect-error`. Unbekannt heißt `unbekannter_fehler`.
- **Verbot – kein `render_aktiv`** (TK 9.3.6), auch nicht als interner Zwischenwert.
- **Verbot – kein zweites Lock** (TK 9.3.5): kein eigenes „Render läuft"-Flag neben dem
  Auftragsstatus.
