### Issue M2-06: [auftrags-manager] Zustandsübergänge der Aufträge prüfen

## Ziel (in einem Satz)
Eine reine Prüfstelle beantwortet für jedes Paar (alter Status, neuer Status), ob dieser Übergang laut
Zustandsmaschine der Auftragsverwaltung erlaubt ist – damit kein anderer Teil des Systems einen Auftrag
in einen Zustand versetzt, den es fachlich nicht geben darf.

## Modul & Datei
- Modul: `auftrags-manager` (Main)
- Datei: `src/main/auftrags-manager/zustandsuebergang.ts`
- Vertrag: Technisches Konzept **9.3.3** (Quelle der Wahrheit), ergänzend 9.3.5
- Prozess/Speicher: P6 (kein Speicherzugriff – reine Funktionen)

## Warum das im Gesamtsystem wichtig ist
Der Auftrags-Status ist die einzige Stelle, an der das Fach-Ergebnis eines Imports, einer Löschung, eines
Renders oder eines Exports beim Nutzer ankommt: Das Aufruf-Ergebnis sagt nur „eingereiht", der Ausgang
reist über den Auftrags-Zustand (TK 9.1.1). Vier Stellen schreiben an diesem Status – Einreihen (M2-09),
Torwächter (M2-07), Abschluss (M2-18) und Wiederholen (M2-11). Ohne eine gemeinsame Prüfstelle
implementiert jede ihre eigene Vorstellung davon, was erlaubt ist. Die teuren Fehler dabei sind: ein
`erfolg` wird nachträglich auf `fehlgeschlagen` gesetzt (ein verspätetes Ereignis kippt ein bereits
protokolliertes Ergebnis), ein `abgebrochen` wird über `wiederhole` reaktiviert (obwohl der Nutzer den
Vorgang bewusst beendet hat), oder ein `anstehend` springt direkt auf `erfolg` (dann fehlt der
Q3-Eintrag, denn der entsteht nur beim Übergang aus `laeuft`). Diese Datei ist die einzige Wahrheit
darüber, welche Übergänge existieren.

## Signatur (verbindlich – NICHT ändern)
```ts
import type { AuftragStatus } from '../../shared/contracts/auftrag';
import type { Ergebnis } from '../../shared/contracts/ergebnis';

export function istUebergangErlaubt(von: AuftragStatus, nach: AuftragStatus): boolean;

export function pruefeUebergang(von: AuftragStatus, nach: AuftragStatus): Ergebnis<void>;
```

Beide Funktionen sind **rein**: keine Ein-/Ausgabe, kein Modulzustand, keine Zeit, kein Zufall, kein
Logging, kein Zugriff auf Q1–Q4. Gleiche Eingabe → immer gleiche Ausgabe.

Das Paar ist Absicht und **kein** Verstoß gegen das Verbot von `Ergebnis<boolean>`:
`istUebergangErlaubt` ist ein **Prädikat** für Verzweigungen im Main (nackter `boolean`, keine Hülle);
`pruefeUebergang` ist die **Wächter-Form**, deren Ergebnis ein Aufrufer unverändert an die IPC-Grenze
durchreichen kann. Verboten bleibt, was TK 9.1.1 verbietet: eine Hülle mit Nutzlast `boolean` oder
`null`.

## Eingang → Ausgang

| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `von` | aktueller Status des Auftrags | einer aus `anstehend` \| `laeuft` \| `erfolg` \| `fehlgeschlagen` \| `abgebrochen` (#16) |
| `nach` | gewünschter Zielstatus | derselbe geschlossene Satz |

**Erlaubt sind GENAU diese fünf Übergänge – alle anderen sind verboten:**

| von | nach | Auslöser |
|---|---|---|
| `anstehend` | `laeuft` | Torwächter gibt frei (M2-07) |
| `laeuft` | `erfolg` | Fachdienst meldet Erfolg (M2-18) |
| `laeuft` | `fehlgeschlagen` | Fachdienst meldet Fehler (M2-18) |
| `laeuft` | `abgebrochen` | Abbruch eines laufenden Renders (M2-10 → M2-18) |
| `fehlgeschlagen` | `anstehend` | `wiederhole` (M2-11) |

Die Zustandsmaschine aus TK 9.3.3, aus der diese Tabelle stammt:

```
        reiheEin                start (frei)              Erfolg
  (–) ─────────────▶ anstehend ───────────▶ laeuft ───────────────▶ erfolg
                        │                     │
              entferne  │                     │ Fehler
                        ▼                     ▼
                    (entfernt)          fehlgeschlagen ──wiederhole──▶ anstehend (ans Ende)
                                              │
                          entferne/cancel     ▼
                    laeuft ───────────────▶ abgebrochen
```

**„entfernt" ist KEIN Status.** In der Zeichnung steht `(entfernt)` in Klammern, weil ein entfernter
Auftrag aus Q1 **verschwindet**, ohne einen Statuswechsel zu durchlaufen. Es gibt deshalb keinen
Übergang `anstehend → entfernt`, den diese Funktion prüfen könnte, und `AuftragStatus` bekommt
**keinen** zusätzlichen Wert. Wer `entfernt` hier ergänzt, ändert den Typ aus #16 – verboten.

Ausgang bei Erfolg: `istUebergangErlaubt` → `true`; `pruefeUebergang` → `{ ok: true, wert: undefined }`.
Ausgang bei Fehler: `istUebergangErlaubt` → `false`; `pruefeUebergang` → `{ ok: false, fehler: { code:
'ungueltige_eingabe', meldung } }`. Die `meldung` nennt beide Status im Klartext (z. B. „Übergang von
erfolg nach anstehend ist nicht vorgesehen") und ist **reiner Anzeigetext** – niemand vergleicht sie.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**`fehlgeschlagen`/`abgebrochen`/`erfolg`** sind terminal. `fehlgeschlagen` ist über `wiederhole`
  reaktivierbar; der **selbe** Eintrag wird wieder `anstehend` und **ans Ende** gestellt
  (kein neuer Eintrag)." (TK 9.3.3)
- „**`anstehend` → `laeuft`:** nur wenn **kein** anderer Auftrag `laeuft` (serielle Invariante). Auswahl
  in FIFO-Reihenfolge." (TK 9.3.3) — Diese Zusatzbedingung prüft der **Torwächter** (M2-07) über Q1;
  diese Datei kennt Q1 nicht und prüft **nur** die Zulässigkeit des Paares.
- Daraus folgt, was hier verbindlich gilt: `erfolg` und `abgebrochen` sind **endgültig** und haben
  **keinen** ausgehenden Übergang. Nur `fehlgeschlagen` ist reaktivierbar, und zwar **ausschließlich**
  nach `anstehend`.
- Die Ergebnis-Hülle laut TK 9.1.1, die `pruefeUebergang` bedient:
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  „Wo eine Operation **nichts** zu melden hat, lautet die Nutzlast `void`: **`Ergebnis<void>`** – das
  gelungene `ok` **ist** die Information. **Verboten** sind Ersatzformen wie `Ergebnis<boolean>`,
  `Ergebnis<null>` oder ein blankes `true`." (TK 9.1.1)
- „**Fehlercodes sind ein geschlossener, typisierter Satz:** die fachlichen je Operation (9.4.9, 9.6.4,
  9.12.1) plus die generischen `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`. **Eine rohe
  Exception-Meldung wird nie zum Code.**" (TK 9.1.1) — Diese Funktion verwendet **nur**
  `ungueltige_eingabe` und erfindet keinen eigenen Code.
- Niemals `throw`, auch nicht bei einem Wert außerhalb des Typs (siehe Fehlerpfade). Ein `throw` würde
  am Gateway zu `unbekannter_fehler` degradieren und den Grund vernichten (TK 9.1.1).

## Fehlerpfade (vollständig)

| Situation | Code | Verhalten |
|---|---|---|
| Übergang nicht in der Fünfer-Tabelle (z. B. `erfolg → anstehend`, `abgebrochen → anstehend`, `anstehend → erfolg`) | `ungueltige_eingabe` | `pruefeUebergang` liefert `ok: false`, `istUebergangErlaubt` liefert `false`; **keine** Wirkung, es gibt nichts zu verändern |
| `von === nach` (z. B. `laeuft → laeuft`) | `ungueltige_eingabe` | ebenso abgelehnt – ein Übergang auf sich selbst steht nicht in der Tabelle |
| `von` oder `nach` ist zur Laufzeit kein gültiger `AuftragStatus` (nur möglich, wenn ein Aufrufer den Typ umgeht) | `ungueltige_eingabe` | abgelehnt statt geworfen; die Funktion behandelt unbekannte Werte wie einen nicht eingetragenen Übergang |

## Nicht selbst entscheiden – STOPP und fragen
- **Einen abgelehnten Übergang NICHT vermerken – auch nicht im Journal Q4.** Diese Funktion ist **rein**
  und schreibt in **keinem** Fall irgendwohin: kein Q4-Eintrag, kein Logger, kein Zähler, keine
  „Diagnose-Hilfe". Q4 kennt ohnehin nur die vier Bewegungen `eingereiht`, `gestartet`, `entfernt`,
  `erneut_eingereiht`; eine fünfte wird hier weder gebraucht noch erfunden. Ein abgelehnter Übergang ist
  ein **Programmierfehler** im Main, den der **Aufrufer** behandelt – diese Datei meldet ihn ausschließlich
  über ihren Rückgabewert.
- **Keine weiteren Übergänge ergänzen**, auch nicht „offensichtlich harmlose". Insbesondere nicht
  `abgebrochen → anstehend` („der Nutzer will es doch noch"), nicht `anstehend → abgebrochen`
  („Entfernen ist doch ein Abbruch") und nicht `laeuft → anstehend` („zurückstellen"). Jeder zusätzliche
  Übergang verändert, welche Q3- und Q4-Einträge entstehen (TK 9.3, Tabelle „Wann geschrieben wird").
- **`AuftragStatus` nicht erweitern** – der Typ gehört #16 und ist fertig. Kein `entfernt`, kein
  `wartet`, kein `abbrechend`.
- **Keine Zusatzbedingungen einbauen**, die Zustand brauchen (z. B. „läuft schon einer?" oder „ist der
  Auftrag noch in Q1?"). Diese Funktion sieht zwei Status und sonst nichts; die serielle Bedingung sitzt
  im Torwächter (M2-07).

## Definition of Done
- [ ] `istUebergangErlaubt` liefert für **genau** die fünf Paare `anstehend→laeuft`, `laeuft→erfolg`,
      `laeuft→fehlgeschlagen`, `laeuft→abgebrochen`, `fehlgeschlagen→anstehend` den Wert `true`.
- [ ] Ein Test durchläuft **alle** 25 Kombinationen der fünf Status und weist nach, dass genau 5 `true`
      und 20 `false` ergeben – inklusive der fünf Selbstübergänge.
- [ ] `pruefeUebergang` liefert bei erlaubtem Übergang `{ ok: true, wert: undefined }` und bei jedem anderen
      `{ ok: false, fehler: { code: 'ungueltige_eingabe', meldung } }` mit einer Meldung, die beide
      Status benennt.
- [ ] Kein Aufruf wirft – auch nicht bei einem über `as unknown as AuftragStatus` eingeschleusten
      Fremdwert.
- [ ] Die Datei importiert nur Typen (`AuftragStatus`, `Ergebnis`) und **kein** Laufzeitmodul: kein `fs`,
      kein Q1–Q4-Modul, kein Journal, kein Logger.
- [ ] Beide Funktionen sind frei von Nebenwirkungen: ein Test ruft sie 100-mal in wechselnder Reihenfolge
      und erhält stets identische Ergebnisse.
- [ ] Keine Datei außerhalb von `src/main/auftrags-manager/zustandsuebergang.ts` **(+ zugehörige
      Testdatei)** geändert.
