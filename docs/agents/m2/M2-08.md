### Issue M2-08: [auftrags-manager] Fachdienst-Handler registrieren und ausführen

## Ziel (in einem Satz)
Die Auftragsverwaltung bekommt eine Registry, in der sich je Auftragsart genau ein Fachdienst als
Handler einträgt, und eine Ausführungsstelle, die einen Auftrag an seinen Handler übergibt und dessen
Ausgang **immer** als geordnetes Ergebnis zurückliefert – nie als Ausnahme.

## Modul & Datei
- Modul: `auftrags-manager` (Main)
- Datei: `src/main/auftrags-manager/dispatcher.ts`
- Vertrag: Technisches Konzept **9.3.2** (Auftragsarten und ausführende Dienste), ergänzend 9.3.6, 9.2.7
  (Quelle der Wahrheit)
- Prozess/Speicher: P6 (kein eigener Speicher; die Registry lebt im RAM des Main-Prozesses)

## Warum das im Gesamtsystem wichtig ist
Diese Datei ist die Naht zwischen Steuerung und Fachlichkeit. Der `auftrags-manager` darf nach Planung
selbst **nichts** tun: kein Kopieren, kein Löschen, kein `ffmpeg`. TK 9.3 sagt über ihn: „Sie **plant,
ordnet und protokolliert** nur — sie ersetzt keine Fachlogik." Die Registry ist der Mechanismus, der
das durchsetzt: `media-service`, `render-service` und `export-service` tragen sich ein, der Torwächter
ruft blind über `art` auf. Zwei konkrete Folgen, wenn das hier falsch gebaut wird. Erstens: Wirft ein
Handler nach außen, verlässt die Ausnahme den Ablauf des Torwächters – der Auftrag bliebe auf `laeuft`
stehen, `beendeAuftrag` (M2-18) liefe nie, es gäbe keinen Q3-Eintrag, und weil kein weiterer Auftrag
starten darf, solange einer läuft, **steht die Warteschlange für den Rest der Sitzung still**. Zweitens:
Diese Registry ist der Grund, warum M2 überhaupt gebaut und getestet werden kann, obwohl `media-service`
(M3) und `render-service`/`export-service` (M6) noch gar nicht existieren – die Tests registrieren
eigene Handler und prüfen den kompletten Warteschlangen-Ablauf ohne eine einzige echte Datei.

## Signatur (verbindlich – NICHT ändern)
```ts
import type { Auftrag, AuftragArt } from '../../shared/contracts/auftrag';
import type { Fehlercode } from '../../shared/contracts/ergebnis';

export interface AusfuehrungsKontext {
  auftragId: string;
  meldeFortschritt: (prozent: number | null) => void;
}

export type HandlerErgebnis =
  | {
      status: 'erfolg';
      // gesamtdauer ist bei art: export IMMER null – der export-service liefert
      // laut TK 9.6.2 nur { zielPfad, dateigroesse }.
      ausgabe: { pfad: string; dateigroesse: number; gesamtdauer: number | null } | null;
    }
  | { status: 'fehlgeschlagen'; fehler: { code: Fehlercode; meldung: string } }
  | { status: 'abgebrochen' };

export type HandlerFuer<A extends AuftragArt> = (
  auftrag: Extract<Auftrag, { art: A }>,
  kontext: AusfuehrungsKontext,
) => Promise<HandlerErgebnis>;

export function registriereAuftragsHandler<A extends AuftragArt>(
  art: A,
  handler: HandlerFuer<A>,
  brichAb?: (auftrag: Auftrag) => void,
): void;

export function fuehreAus(auftrag: Auftrag, kontext: AusfuehrungsKontext): Promise<HandlerErgebnis>;

export function kannAbbrechen(art: AuftragArt): boolean;

/** true, wenn ein Abbrecher registriert war und gerufen wurde. */
export function brich(auftrag: Auftrag): boolean;
```

**Der Name lautet `registriereAuftragsHandler`, nicht `registriereHandler`.** Issue **#23** exportiert
bereits ein `registriereHandler` (der Kanal-Wrapper des `ipc-gateway`). Zwei gleichnamige Exporte im
Main-Baum sind eine Einladung zum falschen Import; der längere Name macht am Aufrufort sichtbar, dass
hier ein **Auftrags**-Handler eingetragen wird und kein IPC-Kanal.

**Der Handler bekommt den GANZEN `Auftrag`, nicht nur die Nutzlast.** Zwei Gründe: Er braucht die
`auftragId` (für Korrelation und Diagnose) und die `payload` gemeinsam, und `Auftrag` ist in #16 eine
über `art` **diskriminierte Union** – `Extract<Auftrag, { art: A }>` typisiert damit die `payload`
automatisch richtig (ein `render`-Handler sieht `RenderRequest`, ein `import`-Handler `ImportRequest`).
Würde nur die Nutzlast übergeben, ginge diese Typisierung verloren und jeder Handler müsste raten oder
casten.

**Auch der Abbrecher bekommt den GANZEN `Auftrag`, nicht nur eine ID.** Nur so kommt der Abbrecher des
Render-Handlers (M2-16) an die `renderId` aus `auftrag.payload` – sie ist der Schlüssel, mit dem der
`render-service` seinen Lauf identifiziert, und der `auftrags-manager` kennt sie nicht.

`HandlerErgebnis` ist **nicht** die Ergebnis-Hülle und darf nicht mit ihr verwechselt werden: Es ist das
**Auftrags-Ergebnis** („wie ging der Vorgang aus"), nicht das **Aufruf-Ergebnis** („hat der Aufruf
geklappt"). TK 9.1.1 trennt beides ausdrücklich; das Auftrags-Ergebnis reist über den Auftrags-Zustand,
nicht als `Ergebnis<T>`.

## Eingang → Ausgang

| Funktion | Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|---|
| `registriereAuftragsHandler` | `art` | `import` \| `loeschen` \| `render` \| `export` (#16) | genau **ein** Handler je Art; eine erneute Registrierung derselben Art **ersetzt** die vorherige vollständig (s. Invarianten) |
| | `handler` | die Ausführung des Fachdienstes | liefert immer ein `HandlerErgebnis`, wirft nie |
| | `brichAb` | optionaler Abbruch-Rückruf für diese Art, er bekommt den **ganzen** `Auftrag` | fehlt er, ist die Art **nicht** abbrechbar |
| `fuehreAus` | `auftrag` | der auszuführende Auftrag | Auswahl des Handlers **allein** über `auftrag.art` |
| | `kontext` | `auftragId` + `meldeFortschritt` | vom Torwächter (M2-07) gebaut |
| `kannAbbrechen` | `art` | Auftragsart | `true` genau dann, wenn für diese Art ein `brichAb` registriert wurde |
| `brich` | `auftrag` | der abzubrechende, **laufende** Auftrag | ruft den für `auftrag.art` registrierten `brichAb` mit dem ganzen `auftrag` auf; `true` = es gab einen Abbrecher und er wurde gerufen, `false` = für diese Art ist keiner registriert (dann geschieht **nichts**) |

Ausgang bei Erfolg: `fuehreAus` liefert das `HandlerErgebnis` des Fachdienstes unverändert weiter.
Bei `status: 'erfolg'` trägt `ausgabe` die Nutzdaten für den Q3-Protokolleintrag (`pfad`,
`dateigroesse`, `gesamtdauer`) oder `null`, wenn die Art nichts produziert (Import, Löschen).
`gesamtdauer` ist bei `art: export` **immer `null`** – der `export-service` liefert laut TK 9.6.2 nur
`{ zielPfad, dateigroesse }`. Deshalb ist das Feld `number | null` und nicht `number`.
`brich` liefert `true`/`false` und **kein** `HandlerErgebnis`.
Ausgang bei Fehler: **immer** `{ status: 'fehlgeschlagen', fehler: { code, meldung } }` – nie eine
geworfene Ausnahme. Verwendete Codes: der vom Fachdienst gelieferte Code aus dem geschlossenen Satz
(#22) bzw. `unbekannter_fehler` in den beiden Fällen der Fehlerpfad-Tabelle.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Zuordnung Art → Dienst laut TK 9.3.2: `import` → `media-service` (`ImportRequest`), `loeschen` →
  `media-service` (`LöschRequest`), `render` → `render-service` (`RenderRequest`), `export` →
  `export-service` (`ExportRequest`). Diese Datei kennt **keinen** dieser Dienste beim Namen – sie kennt
  nur die vier Arten und die eingetragenen Rückrufe.
- „**Zwei Ebenen nicht verwechseln.** … **Aufruf-Ergebnis:** Hat der *Aufruf* funktioniert …
  **Auftrags-Ergebnis:** Wie ging der *Vorgang* aus (`RenderResult`, Export-Ergebnis …)? Das reist
  **nicht** als Aufruf-Antwort, sondern über den **Auftrags-Zustand** (9.3)." (TK 9.1.1)
- „**Fehlercodes sind ein geschlossener, typisierter Satz** … **Eine rohe Exception-Meldung wird nie zum
  Code.**" (TK 9.1.1) — Eine gefangene Ausnahme darf ihren Text in die `meldung` schreiben, **nie** in
  den `code`.
- „Ein `render`-Auftrag führt beim Start intern `renderReel(payload)` aus. `RenderProgress.prozent`
  speist `Auftrag.fortschritt`" (TK 9.3.6) — deshalb reicht `meldeFortschritt` genau eine Zahl 0–100
  oder `null` durch, passend zum Feld `fortschritt` aus #16.
- „**Keine** Restzeit-Schätzung" und die Drosselungs-Regel „Ereignisse an den Element-Grenzen
  (Beginn/Ende je `seg_*.mp4`) plus grobe Zwischen-Ticks; **kein** Pro-Frame-Feuerwerk über IPC
  (Obergrenze wenige Ereignisse/Sekunde)." (TK 9.2.7) — Die Drosselung ist Sache des meldenden
  Fachdienstes; `meldeFortschritt` ist nur die Durchreiche. **Hier wird nichts gepuffert und nichts
  zusammengefasst.**
- „Der Fortschrittskanal trägt **keinen** Endzustand." (TK 9.2.7) — `meldeFortschritt` transportiert
  deshalb **nie** ein Ergebnis, keinen Status und keinen Fehler. Der Ausgang kommt ausschließlich über
  den aufgelösten `Promise<HandlerErgebnis>`.
- **Keine Fachlogik in dieser Datei.** Kein `ffmpeg`, kein Kopieren, kein Löschen, kein Dateisystem-
  Zugriff. TK 9.3: „Sie **plant, ordnet und protokolliert** nur — sie ersetzt keine Fachlogik."
- **Der Handler bekommt `auftrag.payload` und beschafft sich seinen Eingang NIE neu.** TK 9.3.5:
  „**Render friert seinen Eingang beim Einreihen ein:** die geordnete Liste + Profil des `RenderRequest`
  werden **zum Einreih-Zeitpunkt** als Snapshot genommen. Spätere Listenänderungen betreffen einen
  bereits eingereihten Render **nicht**." Diese Datei darf deshalb die Nutzlast weder ergänzen noch aus
  dem Projekt nachladen – sie reicht den Auftrag **unverändert** durch.
- **Genau ein Handler je Art.** Keine Ketten, keine Middleware, keine Mehrfachregistrierung mit
  Reihenfolge.
- **Eine erneute Registrierung derselben Art ERSETZT die vorherige.** Der Eintrag wird dabei als Ganzes
  ausgetauscht – Handler **und** `brichAb`; wird beim zweiten Aufruf kein `brichAb` übergeben, ist die
  Art danach **nicht** abbrechbar (`kannAbbrechen` liefert `false`). Kein `throw`, keine Ablehnung, keine
  Warnung als Rückgabewert. Begründung: Genau das brauchen die Tests, die eigene Handler registrieren,
  und es ist die einzige Variante **ohne verstecktes Verhalten** – ein stilles Ignorieren würde dazu
  führen, dass ein Test scheinbar den echten Dienst prüft, obwohl er seinen eigenen registriert hat.
- **Es gibt KEINE zeitliche Obergrenze je Auftrag.** Kein Timeout, kein Wächter-Timer, kein
  automatisches Beenden eines langlaufenden Handlers. Begründung: Ein Render kann berechtigt zwanzig
  Minuten dauern; eine Zeitgrenze würde **gültige Arbeit abbrechen und die Ausgabedatei zerstören**. Wer
  einen laufenden Render beenden will, benutzt den Abbruch (FA-18) – über `entferne` (M2-10) und `brich`.
- **`brich` beendet den Auftrag NICHT.** Es ruft nur den registrierten Abbrecher. Der Abschluss kommt
  regulär über das `HandlerErgebnis { status: 'abgebrochen' }`, das der Handler daraufhin liefert, und
  über `beendeAuftrag` (M2-18). Wer hier zusätzlich den Status setzt, den Auftrag aus Q1 nimmt oder einen
  Q3-Eintrag schreibt, erzeugt einen **zweiten** Abschlussweg – und damit doppelte Protokolleinträge.
  Ausnahmen des Abbrechers werden genauso abgefangen wie die des Handlers (siehe Fehlerpfade).
- **Abbrechen gibt es nur für `render` – das ist entschieden, keine offene Frage.** Die Oberfläche bietet
  `Abbrechen` ausschließlich bei einem laufenden `render` an (FA-18: „Ein noch nicht gestarteter Auftrag
  kann aus der Warteschlange entfernt, ein laufender Render abgebrochen werden."). Erreicht ein
  Abbruch-Wunsch für einen laufenden `import`, `loeschen` oder `export` dennoch den Main, ist das ein
  **Programmierfehler in der Oberfläche**; die Antwort lautet dann `ungueltige_eingabe` mit einer Meldung,
  die sagt, dass sich diese Auftragsart nicht abbrechen lässt. Diese Antwort erzeugt `entferne` (M2-10),
  **nicht** diese Datei – hier liefert `kannAbbrechen` schlicht `false` und `brich` täte nichts. Es wird
  dafür **kein** neuer Fehlercode eingeführt.

## Fehlerpfade (vollständig)

| Situation | Code | Verhalten |
|---|---|---|
| Handler lehnt fachlich ab (liefert `status: 'fehlgeschlagen'`) | der Code des Fachdienstes (z. B. `datei_nicht_gefunden`, `format_nicht_unterstuetzt`, `kopier_fehler`, `asset_referenziert`, `medium_fehlt`, `ffmpeg_fehler`, `kein_platz`, `datei_zu_gross_fat32`) | unverändert durchreichen – **kein** Umschreiben, **kein** Vereinheitlichen |
| Handler wirft eine Ausnahme oder sein Promise wird abgelehnt | `unbekannter_fehler` | fangen und in `{ status: 'fehlgeschlagen', fehler: { code: 'unbekannter_fehler', meldung } }` wandeln; die `meldung` ist für den Nutzer aufbereiteter Klartext, **kein** Stacktrace |
| Für `auftrag.art` ist **kein** Handler registriert | `unbekannter_fehler` | ebenfalls `fehlgeschlagen` mit klarer Meldung („Für die Auftragsart `<art>` ist kein Dienst registriert"). Das ist ein **Programmierfehler im Main**, kein Nutzerfehler – es gibt trotzdem keinen `throw`, sonst bliebe die Warteschlange stehen |
| `meldeFortschritt` wirft (fehlerhafter Aufrufer) | – | darf die Ausführung **nicht** beenden; der Aufruf wird abgesichert, der Auftrag läuft weiter |
| `brich` auf eine Art **ohne** registrierten `brichAb` | – | `false`, **keine** Wirkung, **kein** `throw`; den Fehlercode `ungueltige_eingabe` erzeugt der Aufrufer `entferne` (M2-10) |
| Der registrierte `brichAb` wirft | – | wie beim Handler abfangen; `brich` liefert trotzdem `true` (der Abbrecher **war** registriert und **wurde** gerufen) und wirft nicht. Der Auftrag läuft weiter, bis sein Handler ein `HandlerErgebnis` liefert |

Es wird **kein** neuer Fehlercode eingeführt. Der Satz ist geschlossen (#22).

## Nicht selbst entscheiden – STOPP und fragen
- **Keine Zeitgrenze je Auftrag einbauen** – kein Timeout, kein Wächter-Timer, kein `setTimeout` um den
  Handler herum, auch nicht „großzügig bemessen". Die Festlegung steht in den Invarianten.
- **Eine erneute Registrierung nicht ablehnen und nicht still ignorieren** – sie ersetzt den vorherigen
  Eintrag. Siehe Invarianten.
- **Keine Wiederholung hier einbauen.** Ein fehlgeschlagener Auftrag wird **nicht** automatisch erneut
  ausgeführt. Wiederholen ist eine ausdrückliche Nutzeraktion (FA-17, `wiederhole`, M2-11); ein
  automatischer Retry im Dispatcher würde `versuche` verfälschen und ohne Zutun des Nutzers Dateien
  anfassen.
- **Kein zweites Lock.** Diese Datei führt weder ein „gerade läuft ein Handler"-Flag noch ein Mutex.
  Die serielle Ordnung des Torwächters (M2-07) **ist** der Sperr-Mechanismus des Systems.
- **Keine Domänentypen erfinden.** Was in `contracts` fehlt (z. B. eine Nutzlast-Struktur), wird
  erfragt, nicht lokal definiert.

## Definition of Done
- [ ] `registriereAuftragsHandler` trägt einen Handler unter seiner Art ein; `fuehreAus` wählt ihn
      **allein** über `auftrag.art` aus und übergibt den vollständigen Auftrag samt Kontext.
- [ ] Ein Test registriert für alle vier Arten je einen eigenen Test-Handler und weist nach, dass
      `fuehreAus` jeweils den richtigen aufruft (kein echter Fachdienst beteiligt).
- [ ] Ein Test-Handler, der `throw` ausführt, führt zu `{ status: 'fehlgeschlagen', fehler: { code:
      'unbekannter_fehler' } }`; `fuehreAus` lehnt sein Promise **nie** ab. Gleiches gilt für einen
      Handler, der ein abgelehntes Promise zurückgibt.
- [ ] `fuehreAus` auf eine Art **ohne** registrierten Handler liefert ebenfalls `fehlgeschlagen` mit
      `unbekannter_fehler` und einer Meldung, die die Art nennt – und wirft nicht.
- [ ] Ein Test-Handler, der `kontext.meldeFortschritt(0)`, `(50)`, `(null)` und `(100)` aufruft, wird
      unverändert durchgereicht: der Test zählt die Aufrufe und prüft die Werte. Ein `meldeFortschritt`,
      das wirft, beendet die Ausführung nicht.
- [ ] `kannAbbrechen` liefert `true` nur für Arten, die mit einem `brichAb` registriert wurden, sonst
      `false` – ein Test deckt beide Fälle ab.
- [ ] `brich(auftrag)` ruft den registrierten `brichAb` **mit dem ganzen `auftrag`** auf (der Test prüft
      das übergebene Objekt, nicht nur die Anzahl der Aufrufe) und liefert `true`; für eine Art ohne
      `brichAb` liefert es `false`, ohne etwas zu rufen.
- [ ] Ein `brichAb`, der `throw` ausführt, lässt `brich` **nicht** werfen; `brich` liefert weiterhin
      `true`.
- [ ] `brich` verändert weder Status noch Q1 noch Q3 – der Test weist nach, dass es ausschließlich den
      Abbrecher ruft.
- [ ] Die Datei importiert **kein** `fs`, `child_process`, `electron` und keinen Fachdienst; sie enthält
      keinen `ffmpeg`-Bezug.
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze).
- [ ] Keine Datei außerhalb von `src/main/auftrags-manager/dispatcher.ts` **(+ zugehörige Testdatei)**
      geändert.
