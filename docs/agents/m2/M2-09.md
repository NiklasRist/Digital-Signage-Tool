### Issue M2-09: [auftrags-manager] reiheEin implementieren

## Ziel (in einem Satz)
Ein Renderer-Aufruf kann einen Auftrag (`import`, `loeschen`, `render`, `export`) in die Warteschlange
stellen: Die Nutzlast wird geprüft, ein `Auftrag` gebaut, ans Ende von Q1 gehängt, die Bewegung in Q4
protokolliert, die Oberfläche benachrichtigt und der Torwächter angestoßen – der Aufruf antwortet
**sofort** mit der `auftragId` und sagt **nichts** darüber, wie der Vorgang ausgeht.

## Modul & Datei
- Modul: `auftrags-manager` (Main)
- Datei: `src/main/auftrags-manager/reihe-ein.ts` – **die einzige** Datei dieses Issues
- **Nicht** erlaubt: `src/shared/contracts/kanaele.ts`. Diese Datei registriert **keinen** IPC-Kanal
  und trägt **nichts** in die Kanal-Registry ein; die Verdrahtung (Registrierung über den Wrapper
  aus #23, Eintrag in die Registry aus #25) übernimmt **M2-19**
  (`src/main/auftrags-manager/ipc-verdrahtung.ts`).
- Vertrag: Technisches Konzept **9.3.4** (IPC-Oberfläche), **9.3.5** (Invarianten), **9.1.1**
  (IPC-Konventionen) – Quelle der Wahrheit
- Prozess/Speicher: P6; schreibt **Q1** (aktive Warteschlange, flüchtig/RAM) und **Q4**
  (Warteschlangen-Journal, `warteschlangen-journal.json`)
- IPC-Kanal: `queue:reiheEin` (Muster `<modul>:<operation>`, TK 9.1.1 Punkt 4) – **registriert wird
  er in M2-19**, nicht hier

## Warum das im Gesamtsystem wichtig ist
`reiheEin` ist die **einzige** Tür, durch die dateiverändernde Arbeit ins System kommt: Import,
Löschen, Render und Export werden nie direkt aufgerufen, sondern hier eingereiht (TK 9.3.4). Damit
hängt an dieser Funktion die wichtigste Zusicherung des ganzen Systems – dass **höchstens ein**
Auftrag gleichzeitig läuft (NFA-09). Wer hier den Auftrag am Torwächter vorbei „schon mal startet",
hebelt den einzigen Sperr-Mechanismus aus, und ein `loeschen` kann mitten in einen laufenden Render
fahren (auf Windows: `EBUSY` auf einer offenen Mediendatei, im schlimmeren Fall eine halbe
Ausgabedatei).

Zweitens entsteht hier der **Snapshot** des Render-Eingangs. Nimmt der Handler beim Start die Liste
frisch aus dem Projekt statt aus `auftrag.payload`, bekommt der Nutzer ein **anderes** Video als das,
das er abgeschickt hat – der Fehler ist im Betrieb praktisch nicht zu erkennen, weil beides
„funktioniert".

Drittens ist dies die Stelle, an der die zwei Ebenen des IPC-Vertrags auseinandergehalten werden
müssen. Wer hier auf das Ende des Auftrags wartet, bevor er antwortet, blockiert die Oberfläche für
die gesamte Renderdauer (Minuten) und macht die ganze Warteschlange sinnlos.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/auftrags-manager/reihe-ein.ts
import type { Auftrag, AuftragArt } from '../../shared/contracts/auftrag'
import type { Ergebnis } from '../../shared/contracts/ergebnis'

// Bindet die Nutzlast typsicher an die Auftragsart (Auftrag ist eine diskriminierte Union über
// `art`, #16): NutzlastVon<'render'> ist RenderRequest, NutzlastVon<'import'> ist ImportRequest usw.
export type NutzlastVon<A extends AuftragArt> = Extract<Auftrag, { art: A }>['payload']

export async function reiheEin<A extends AuftragArt>(
  art: A,
  payload: NutzlastVon<A>,
): Promise<Ergebnis<{ auftragId: string }>>
```

Der Kanalname `queue:reiheEin` kommt in dieser Datei **nicht** vor – weder als String-Literal noch
als Import aus der Registry. `reiheEin` ist hier eine gewöhnliche Main-Funktion; sie an den Kanal zu
hängen ist Aufgabe von **M2-19** (`verdrahteQueueIPC(): void` in
`src/main/auftrags-manager/ipc-verdrahtung.ts`).

Die fremden Funktionen, die dieser Ablauf aufruft, mit vollständiger Signatur (der umsetzende Agent
sieht die anderen Issues nicht):

```ts
// #20
erzeugeId(): string
// M2-02 (Q1) – liefert die Position in der Schlange
fuegeAnsEndeAn(auftrag: Auftrag): number
// M2-05 (Q4-Journal)
haengeJournalEintragAn(eintrag: JournalEintrag): Promise<Ergebnis<void, QueueFehlercode>>
// M2-13 (Ereignis)
sendeQueueGeaendert(): Promise<void>
// M2-07 (Torwächter)
starteNaechsten(): void
```

Verbindlicher Ablauf (Reihenfolge ist Teil der Vorgabe):

1. **Nutzlast validieren.** Ungültig → `ungueltige_eingabe`, **ohne jede Wirkung**: kein Eintrag in
   Q1, keine Journalbewegung, kein Ereignis, kein Anstoß des Torwächters.
2. **Auftrag bauen:** `auftragId` = neue UUID über `erzeugeId(): string` (#20); `art` und `payload`
   wie übergeben; `status: 'anstehend'`; `versuche: 0`; `fortschritt: null`; `fehler: null`;
   `ergebnis: null`; `erstelltAm` = aktueller Zeitpunkt als ISO-8601 UTC; `label` nach den vier
   Regeln unten. `ergebnis` wird hier aus demselben Grund auf `null` gesetzt wie `fehler`: Ein eben
   eingereihter Auftrag hat noch nichts hervorgebracht; die fachlichen Nutzdaten trägt erst der
   Abschluss ein (M2-18), und zwar nur bei `erfolg` (TK 9.3.1).
3. **Ans Ende von Q1 anhängen** über `fuegeAnsEndeAn(auftrag): number` (FIFO, M2-02); der
   Rückgabewert ist die Position, die Schritt 4 braucht. Das Anhängen geschieht **synchron**,
   unmittelbar nach dem Bauen des Auftrags – zwischen Bauen und Anhängen darf **nichts** abgewartet
   werden, sonst kann die tatsächliche Reihenfolge in Q1 von der Aufrufreihenfolge abweichen, und
   der Nutzer sieht im Panel eine andere Reihenfolge, als tatsächlich ausgeführt wird.
4. **Q4-Journalbewegung `eingereiht`** über
   `haengeJournalEintragAn(eintrag): Promise<Ergebnis<void, QueueFehlercode>>` schreiben (M2-05),
   mit `position` = dem Rückgabewert aus Schritt 3. **Der Journal-Aufruf wird nicht awaited; sein
   Promise bekommt ein `.catch`, das den Fehler nur vermerkt – ein floating Promise ohne `catch` ist
   verboten.** Scheitert das Schreiben, bleibt der Auftrag eingereiht und der Ablauf läuft weiter.
5. **Ereignis `queue:geaendert`** über `await sendeQueueGeaendert(): Promise<void>` auslösen
   (M2-13). Die Funktion ist **asynchron** und wird **abgewartet**, bevor Schritt 7 antwortet.
6. **Torwächter anstoßen** über `starteNaechsten(): void` (M2-07). Ob tatsächlich etwas startet,
   entscheidet allein der Torwächter – läuft bereits ein Auftrag, passiert nichts.
7. **Sofort mit `{ ok: true, wert: { auftragId } }` antworten.** Auf den Ausgang des Auftrags wird
   **nicht** gewartet.

**Der `label`-Klartext wird hier gebaut – verbindliche Regeln (entschieden, Auftraggeber 03.08.2026).**
Die Signatur `reiheEin(art, payload)` aus TK 9.3.4 bleibt **unverändert**; das Label kommt **nicht**
vom Renderer, sondern entsteht in dieser Funktion aus `art` und `payload`:

| `art` | `label` |
|---|---|
| `import` | `Import: ` + Dateiname aus `payload.quellPfad`, **ohne** Verzeichnisanteil |
| `render` | `Render: ` + `payload.ausgabeName` + `.mp4` |
| `export` | `Export: ` + `payload.dateiname` |
| `loeschen` | `Löschen: ` + `originalname` des Assets zu `payload.assetId` |

Beispiel für `import` bei `quellPfad = C:\Videos\sommer-aktion.mp4`: `Import: sommer-aktion.mp4` –
genau die Form, die TK 9.3.1 als Muster nennt. Nur der Fall `loeschen` braucht einen Nachschlag im
geladenen Projekt (`Asset.originalname`, TK 9.4.4), weil der `LöschRequest` nur `projektId` und
`assetId` trägt (TK 9.4.3) – **über welche Funktion** dieser Nachschlag läuft, ist der einzige noch
offene Punkt zum Label (s. STOPP).

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `art` | Auftragsart | genau einer der vier Werte `import`, `loeschen`, `render`, `export`; alles andere → `ungueltige_eingabe` |
| `payload` | Nutzlast der Art (`ImportRequest`, `LöschRequest`, `RenderRequest`, `ExportRequest`) | muss ein Objekt sein und zur `art` passen; eine `render`-Nutzlast unter `art: 'import'` ist ungültig (Tiefe der Prüfung: s. STOPP) |

Ausgang bei Erfolg: `Ergebnis<{ auftragId: string }>` mit `ok: true` – die `auftragId` ist ab sofort
die Referenz für `entferne`, `wiederhole` und den Zustands-Push.
Ausgang bei Fehler: `ungueltige_eingabe` (Nutzlast ungültig) oder `unbekannter_fehler`
(unerwartete Ausnahme, vom `ipc-gateway` übersetzt). Weitere Codes gibt es hier nicht.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Begründung aus demselben Abschnitt: Renderer und Main sind „**getrennte Prozesse**"; ein `throw`
  über die Grenze verliert Fehlerklasse und Code – „**Fehlerklasse und eigene Felder wie `code` sind
  verloren** – übrig ist Text." (TK 9.1.1). Also **niemals** eine Exception über die Grenze werfen und
  **nie** Meldungstexte vergleichen.
- „`reiheEin(art, payload) → Ergebnis<{ auftragId }>   // kehrt SOFORT zurück; sagt nichts über den
  Ausgang" (TK 9.3.4)
- „Alle vier Aufrufe sind **Instant** und tragen die Ergebnis-Hülle (9.1.1): `Ergebnis<void>` heißt
  „eingereiht/entfernt/wiederholt", **nicht** „fertig"." (TK 9.3.4)
- „**Zwei Ebenen nicht verwechseln.** … **Aufruf-Ergebnis:** Hat der *Aufruf* funktioniert …
  **Auftrags-Ergebnis:** Wie ging der *Vorgang* aus (`RenderResult`, Export-Ergebnis …)? Das reist
  **nicht** als Aufruf-Antwort, sondern über den **Auftrags-Zustand** (9.3)." (TK 9.1.1, Punkt 1)
- „**Der Main validiert jede eingehende Nutzlast** – er vertraut dem Renderer **nicht**. Ungültige
  Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten. Ein Fehler im Renderer darf D1
  niemals beschädigen." (TK 9.1.1, Punkt 6)
- „**Seriell:** höchstens **ein** Auftrag in `laeuft`. Das ist der einzige Sperr-Mechanismus des
  Systems; ein zweites Lock ist nicht nötig und darf nicht eingeführt werden." (TK 9.3.5)
- „**FIFO** unter `anstehend`; `wiederhole` hängt hinten an." (TK 9.3.5)
- „**Render friert seinen Eingang beim Einreihen ein:** die geordnete Liste + Profil des
  `RenderRequest` werden **zum Einreih-Zeitpunkt** als Snapshot genommen. Spätere Listenänderungen
  betreffen einen bereits eingereihten Render **nicht** (verhindert „gedrückt, dann getweakt,
  anderes Video")." (TK 9.3.5)
- **ENTSCHIEDEN – der eingereihte `payload` IST der Snapshot.** Es wird **keine** zweite Kopie, kein
  separater Snapshot-Speicher und keine Snapshot-Datei angelegt: Der `Auftrag` bewahrt seine
  `payload` vollständig auf (TK 9.3.1: „vollständig aufbewahrt → Wiederholung ohne Neu-Eingabe
  möglich"). Daraus folgt bindend für den Start (M2-07/M2-08): Der Handler darf **ausschließlich**
  `auftrag.payload` benutzen und sich die Liste **nicht** frisch aus dem Projekt holen – sonst ist
  das Einfrieren wertlos und der Nutzer bekommt ein anderes Video als das, das er abgeschickt hat.
- „`import`, `loeschen`, `render` und `export` werden damit **nicht** als direkte Request/Response-
  Operationen aufgerufen, sondern über `reiheEin` eingereiht; ihr Fach-Ergebnis (`erfolg`/
  `fehlgeschlagen` samt Fachfehlercode) kommt über den Auftrags-Zustand." (TK 9.3.4)
- Q4-Bewegung beim Einreihen (TK 9.3, Tabelle „Wann geschrieben wird"): Übergang „– → `anstehend`
  (eingereiht)" schreibt **keinen** Q3-Eintrag und **eine** Q4-Bewegung `eingereiht`. Passend dazu:
  „**Q3 protokolliert nur, was tatsächlich gelaufen ist.** Ein Auftrag, der die Schlange nie
  verlassen hat, erzeugt **keinen** Protokolleintrag – es gibt nichts zu berichten." (TK 9.3)
- „**Alle IDs sind UUIDs** – `Project`, `Asset`, `Aktion`, `Listenelement`, `Vorlage`, `Auftrag`.
  **Keine** fortlaufenden Zähler … **Keine** aus Namen abgeleiteten IDs" (TK 9.11.4). Die `auftragId`
  kommt daher aus `erzeugeId()` (#20), nicht aus einem lokalen Zähler und nicht aus einem Zeitstempel.
- **ENTSCHIEDEN – das Q4-Journal wird nicht abgewartet und hält den Auftragsfluss nie an.** `reiheEin`
  **awaitet** `haengeJournalEintragAn` **nicht**; das zurückgegebene Promise bekommt ein `.catch`,
  das den Fehler nur vermerkt (ein floating Promise **ohne** `catch` ist verboten). Scheitert das
  Schreiben (Platte voll, Datei gesperrt), wird der Auftrag **trotzdem** eingereiht und der Aufruf
  antwortet mit `ok: true` – es gibt dafür keinen Fehlercode. Dieselbe Regel gilt bereits in M2-07
  (Start) und ist in M2-05 festgehalten: ein Journal-Fehler hält den Auftragsfluss nie an.
  Begründung: Q4 ist laut TK 9.3 rein **diagnostisch**; es gibt keinen Betriebszustand, der von ihm
  abhängt. Ein gesperrtes oder volles Journal darf weder die Antwortzeit von `reiheEin` bestimmen
  noch das Einreihen verhindern.
- `versuche` startet bei **0**. Hochgezählt wird genau einmal beim tatsächlichen Start des Auftrags
  (M2-07) – nicht hier und nicht in `wiederhole` (M2-11). Diese Festlegung ist projektweit einheitlich,
  damit ein Auftrag nicht doppelt gezählt wird.
- **ENTSCHIEDEN – das `label` baut der Main, nicht der Renderer.** TK 9.3.1 verlangt für
  `Auftrag.label` einen „UI-Klartext, z. B. „Import: sommer-aktion.mp4"", die Signatur aus TK 9.3.4
  (`reiheEin(art, payload)`) hat aber keinen `label`-Parameter. Der Auftraggeber hat am 03.08.2026
  entschieden: Die **Signatur bleibt unverändert**, das Label entsteht **hier** nach den vier Regeln
  in der Tabelle oben (`Import: <Dateiname>`, `Render: <ausgabeName>.mp4`, `Export: <dateiname>`,
  `Löschen: <originalname>`). Begründung: Ein vom Renderer geliefertes Label hätte den Vertrag aus
  9.3.4 gebrochen; ein aus `art` und IDs zusammengesetztes Label („loeschen: 9f3c…-a1") wäre im
  `queue-panel` für den Nutzer wertlos. Das Label ist **reine Anzeige** – es wird nie zur Steuerung,
  nie für einen Vergleich und nie als Dateiname benutzt.
- Beim `import` wird der Dateiname aus `quellPfad` **ohne Verzeichnisanteil** genommen; der
  `quellPfad` ist laut TK 9.4.3 der „absoluter Pfad der Quelldatei (aus `öffneMedienDialog`)" und
  gehört nicht ins Panel. Beim `render` steht `.mp4` fest, weil `ausgabeName` laut TK 9.2.1 der
  „Dateiname **ohne** Endung" ist und die Zieldatei `projects/<id>/output/<ausgabeName>.mp4` heißt
  (FA-22).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `art` ist keiner der vier gültigen Werte | `ungueltige_eingabe` | keine Wirkung: kein Q1-Eintrag, keine Q4-Bewegung, kein Ereignis, kein `starteNaechsten` |
| `payload` fehlt, ist kein Objekt oder passt nicht zur `art` | `ungueltige_eingabe` | wie oben, keine Wirkung |
| `payload` verletzt eine Pflichtangabe der Art (Tiefe s. STOPP) | `ungueltige_eingabe` | wie oben, keine Wirkung |
| unerwartete Ausnahme irgendwo im Ablauf | `unbekannter_fehler` | vom `ipc-gateway` (#23) gefangen und übersetzt; kein Stacktrace in die Oberfläche |

Es gibt hier **kein** `nicht_gefunden` und keinen fachlichen Fehlercode: Ob das Medium existiert, ob
der Stick voll ist oder ob ffmpeg scheitert, entscheidet sich erst beim Ausführen und reist über den
Auftrags-Zustand. Fehlercodes werden **nicht erfunden** – der Satz ist geschlossen (fachliche je
Operation plus `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`, TK 9.1.1 Punkt 3).

## Nicht selbst entscheiden – STOPP und fragen
- **Über welche Funktion des `project-store` liest der Main den `originalname` zu einer `assetId`?**
  Die vier Label-Regeln stehen fest (s. Signatur-Block); offen ist **allein** der Nachschlag im
  Fall `loeschen`. M1 definiert **keinen** Zugriff auf das geladene Projekt – die Pfad-Autorität
  (#49) löst nur Pfade auf, und `Asset.originalname` (TK 9.4.4) liegt im Projekt, nicht im
  `LöschRequest`. **Derselbe offene Punkt steht bereits in #50** und muss einheitlich beantwortet
  werden; ein Alleingang hier erzeugt einen zweiten Weg an das geladene Projekt. **Nicht selbst
  wählen** – und bis zur Klärung `label` bei `loeschen` **nicht** stillschweigend mit der `assetId`
  befüllen; ein Panel mit „Löschen: 9f3c…-a1" wäre für den Nutzer wertlos.
- **Wie tief geht die Nutzlast-Validierung hier?** TK 9.1.1 Punkt 6 verlangt, dass der Main jede
  eingehende Nutzlast validiert; die Fachdienste (M3 `media-service`, M6 `render-service`/
  `export-service`) validieren beim Ausführen **erneut**. Prüft `reiheEin` nur die Struktur
  (Art bekannt, Nutzlast ist ein Objekt, Pflichtfelder vorhanden und vom richtigen Typ), oder auch
  fachliche Bedingungen (existiert die Datei? ist `ausgabeName` zulässig?)? Beides hat Nachteile:
  eine flache Prüfung reiht Aufträge ein, die deterministisch scheitern werden; eine tiefe Prüfung
  bringt Fachwissen und Dateisystemzugriffe in den `auftrags-manager`, der laut TK 9.3 nur „plant,
  ordnet und protokolliert". **Nicht raten** – die Antwort bestimmt, was ein Nutzer als Fehler
  sofort sieht und was erst als fehlgeschlagener Auftrag erscheint.
- **Verbot – nicht selbst starten.** Diese Funktion ruft **niemals** direkt einen Fachdienst oder
  einen Handler auf, auch nicht „wenn die Schlange gerade leer ist". Der Start läuft ausschließlich
  über den Torwächter (M2-07). Wer hier abkürzt, bricht die serielle Invariante.
- **Verbot – kein zweites Lock.** Kein Mutex, keine Dateisperre, kein zusätzliches „gerade
  beschäftigt"-Flag. Die serielle Ordnung **ist** der Sperr-Mechanismus (TK 9.3.5).
- **Verbot – keine Fachlogik.** Hier wird nichts importiert, gelöscht, gerendert oder exportiert und
  kein `ffmpeg` angefasst.
- **Verbot – keine Domänentypen erfinden.** Fehlt etwas in `contracts` (z. B. eine genaue Form von
  `ImportRequest`), wird das **erfragt**, nicht lokal definiert.
- **Verbot – hier wird kein IPC-Kanal registriert.** Weder `ipcMain.handle`, noch der Wrapper aus
  #23, noch ein Eintrag in `src/shared/contracts/kanaele.ts`, noch der String `'queue:reiheEin'`
  irgendwo in dieser Datei. Die Verdrahtung ist **M2-19**; wer sie hier nachbaut, registriert den
  Kanal doppelt.
