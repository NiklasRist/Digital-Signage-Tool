### Issue M3-12: [media-service] Aufräumen: fehlende Dateien als `fehlt` markieren

## Ziel (in einem Satz)
Beim Öffnen eines Projekts bekommt jeder Medien-Datensatz, dessen Datei nicht mehr auf der Platte
liegt, den Zustand `fehlt` – und jeder, dessen Datei wieder da ist, den Zustand `ok` –, sodass die
Oberfläche den Schaden **vor** dem Rendern zeigt statt mitten im Lauf.

## Modul & Datei
- Modul: `media-service` [P1] (Main)
- Datei: `src/main/media-service/reconcile-fehlt.ts`
- Vertrag: Technisches Konzept **9.4.7** (Quelle der Wahrheit), **9.4.4** (Feld `zustand`),
  ergänzend **9.4.1** (Delegation aller D1-Schreibvorgänge), **9.4.8** Punkt 1 und 9
- Prozess/Speicher: P1; liest **D2** (`projects/<id>/media/`), schreibt **D1** ausschließlich
  **delegiert** über den `project-store`.

## Warum das im Gesamtsystem wichtig ist
Ein Nutzer kann Mediendateien jederzeit außerhalb der Anwendung löschen, verschieben oder auf einem
Netzlaufwerk unerreichbar machen; ebenso hinterlässt jede misslungene Löschung (TK 9.4.6) und jeder
abgestürzte Import einen Datensatz ohne Datei. Diese Funktion ist die einzige Stelle, an der die
Anwendung so etwas **bemerkt**. Der Vertrag beschreibt beide Folgen ausdrücklich: „**D1-Eintrag ohne
Datei** → `Asset.zustand = "fehlt"`. Die UI zeigt ihn rot; der `render-service` bricht **früh** mit
`medium_fehlt` ab statt mitten im Lauf." (TK 9.4.7).

Beides hängt an genau diesem Feld. Wird es nicht gesetzt, sieht der Nutzer eine unauffällige Liste,
startet einen Render, wartet Minuten – und bekommt einen Abbruch irgendwo in der Mitte; die geführte
Reparatur (FA-19), die kaputte Elemente **vor** dem Rendern nacheinander abarbeitet, hat dann nichts,
woran sie erkennen könnte, welche Elemente betroffen sind. Wird es umgekehrt zu großzügig gesetzt –
etwa weil ein Lesefehler wie „Verzeichnis kurz nicht erreichbar" als „Datei fehlt" gewertet wird –,
färbt sich die halbe Bibliothek rot und die Reparatur verlangt vom Nutzer, Dateien neu zu verknüpfen,
die es längst gibt.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/media-service/reconcile-fehlt.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { Asset } from '../../shared/contracts/asset'
import type { ReconcileFehlercode } from './fehlercodes'

export async function markiereFehlende(
  projektId: string,
  assets: Asset[],
): Promise<Ergebnis<{ markiert: number }, ReconcileFehlercode>>
```

`ReconcileFehlercode = 'speicher_fehler' | 'datei_fehler'` (M3-02); die drei generischen Codes
kommen über den `Ergebnis`-Typ automatisch dazu. Diese Union ist der Grund, warum ein
`speicher_fehler` aus dem `project-store` hier **unverändert** weitergereicht werden kann, statt auf
`unbekannter_fehler` abgebildet zu werden. TK 9.1.1 warnt genau davor: „Geht der Code verloren,
degradieren Reparatur-Modus, Wiederholen und der FAT32-Hinweis alle zu „irgendwas ist
schiefgelaufen"."

Die Asset-Liste wird **hineingereicht**, nicht hier beschafft: „**`media-service` besitzt NICHT:**
das Lesen der Asset-Liste (das macht `project-store`)" (TK 9.4.1). Der Aufrufer (M3-14) hat sie
ohnehin.

`markiert` zählt **ausschließlich** die Datensätze, die in diesem Lauf **neu** auf `fehlt` gesetzt
wurden – nicht die, die schon `fehlt` waren, und nicht die Rückkehrer, die auf `ok` zurückgesetzt
wurden. Grund: Der Zähler wandert in das Ergebnis des Aufräum-Ablaufs (M3-14) und beantwortet dort
die Frage „**ist seit dem letzten Mal etwas kaputtgegangen?**". Ein Zähler, der Rückkehrer
mitzählte, könnte diese Frage nicht mehr beantworten.

### Fremde Funktionen, die du aufrufst
Der umsetzende Agent sieht die anderen Issues **nicht**; deshalb hier die vollständigen Signaturen:

```ts
// #49 – project-store, Pfad-Autorität (src/main/project-store/pfade.ts)
export function loeseAssetPfad(projektId: string, dateiname: string): Ergebnis<string>
// absoluter Pfad zur Asset-Datei; liefert NUR einen Pfad, wenn dieser nach Normalisierung
// nachweislich innerhalb von medienOrdner(projektId) liegt, sonst `ungueltige_eingabe`;
// reine String-/Pfad-Operation (kein `fs.*`-Aufruf, KEINE Existenzprüfung)

// M1-43 – project-store, Asset-Zustand setzen (src/main/project-store/assets.ts)
export async function setzeAssetZustand(
  projektId: string,
  assetId: string,
  zustand: 'ok' | 'fehlt',
): Promise<Ergebnis<void, ProjectStoreFehlercode>>
// ProjectStoreFehlercode = 'speicher_fehler' (M1-41, src/main/project-store/assets.ts)
// setzt Asset.zustand im geladenen Projekt und läuft über das EINE D1-Schreib-Lock (#32);
// die Platten-Schreibung übernimmt das entprellte Auto-Speichern (TK 9.5.4)
```

**`loeseAssetPfad` prüft nicht, ob die Datei existiert** – das ist ausdrücklich Teil seines
Vertrags. Die Existenzprüfung findet hier statt, und sie ist der einzige Dateisystemzugriff dieser
Datei.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projektId` | Projekt, dessen Medien geprüft werden | nicht leer, kein Pfadtrenner, kein `..`; wird unverändert an `loeseAssetPfad` und `setzeAssetZustand` weitergereicht |
| `assets` | alle `Asset`-Einträge des Projekts (Schnappschuss aus dem geladenen Projekt) | leeres Array ist zulässig → `{ markiert: 0 }`, kein Fehler; jeder Eintrag wird **genau einmal** besucht |

Ausgang bei Erfolg: `{ markiert: <Anzahl der in diesem Lauf neu auf `fehlt` gesetzten Assets> }`.
Ausgang bei Fehler: `ungueltige_eingabe` (unbrauchbare `projektId`), `speicher_fehler`
(fehlgeschlagener D1-Schreibvorgang – der Code von `setzeAssetZustand`, unverändert),
`unbekannter_fehler` (unerwartete Ausnahme – s. Fehlerpfade).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**D1-Eintrag ohne Datei** → `Asset.zustand = "fehlt"`. Die UI zeigt ihn rot; der `render-service`
  bricht **früh** mit `medium_fehlt` ab statt mitten im Lauf." (TK 9.4.7) – das ist der Auftrag
  dieser Datei, wörtlich, samt Begründung.
- Der Wertebereich des Feldes, wörtlich aus dem Datenmodell (TK 9.4.4):
  ```
  zustand:      "ok" | "fehlt"      // "fehlt" gesetzt vom Reconcile, wenn die Datei fehlt (9.4.7)
  ```
  Es gibt **keinen** dritten Wert. Kein `unbekannt`, kein `pruefung_laeuft`, kein `null`.
- „Alle D1-Schreibvorgänge delegiert er an den `project-store` (dessen einziges Schreib-Lock,
  9.3.5)." (TK 9.4.1) – diese Datei schreibt **nie** selbst in `project.json`, verändert **nie** das
  übergebene `Asset`-Objekt und fordert **kein** Lock an. Sie ruft `setzeAssetZustand`.
- „Auch die **Pfadauflösung** (welcher absolute Pfad zu `projektId`+`dateiname` gehört) kommt vom
  `project-store` (Pfad-Autorität, 9.5.7) – `media-service` liest/schreibt die Bytes, kennt das
  Ordner-Layout aber nicht selbst." (TK 9.4.1)
- „**`dateiname` = `<uuid>.<ext_kleingeschrieben>`, ohne Verzeichnisanteil.** Auflösung immer per
  `path.join(projektMediaDir, dateiname)`. Nie der Originalname, nie ein gespeicherter OS-Pfad mit
  `\`/`/` — sonst ist das Projekt nicht zwischen Windows und macOS portabel." (TK 9.4.8, Punkt 1) –
  geprüft wird `Asset.dateiname`, nie `Asset.originalname`.
- „**Kein zweites Lock.** … `media-service` führt **kein** eigenes Lock und **keine**
  OS-Dateisperren ein (Over-Engineering-Falle)." (TK 9.4.8, Punkt 9)
- „**Instant-Op vs. Speichern getrennt:** Eine Instant-Operation (9.5.2) validiert und wendet **im
  Speicher** an, *bevor* sie „ok" meldet – ihr Erfolg bedeutet „gültig übernommen", **nicht** „schon
  auf Platte". Die Platten-Schreibung ist die entprellte Auto-Speicherung." (TK 9.5.4) – ein
  erfolgreiches `setzeAssetZustand` heißt also **nicht**, dass `project.json` schon geschrieben ist.
  Diese Datei wartet darauf **nicht** und stößt **keine** Speicherung an.
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Kein `throw` nach außen. Das Feld `daten` bleibt hier leer: „Das Feld ist **optional** – Codes ohne
  Zusatzdaten lassen es weg" (TK 9.1.1). Kein Code dieser Datei trägt Zusatzdaten.
- **ENTSCHIEDEN – ein Asset, dessen Datei wieder da ist, wird auf `ok` zurückgesetzt.** Ist
  `zustand === 'fehlt'` und die Datei existiert, ruft diese Funktion `setzeAssetZustand(projektId,
  asset.id, 'ok')`. Begründung: Ohne diesen Rückweg bliebe ein einmal als fehlend markiertes Medium
  **für immer rot**, auch nachdem der Nutzer die Datei zurückgelegt hat – und der Reparatur-Modus
  (FA-19) würde vor jedem Render eine Reparatur verlangen, die längst erfolgt ist. Der Zustand ist
  eine **Feststellung über die Platte**, kein dauerhaftes Kennzeichen des Datensatzes; er muss
  deshalb in beide Richtungen dem entsprechen, was gerade da ist.
- **ENTSCHIEDEN – geschrieben wird nur, wenn sich der Zustand tatsächlich ändert.** Stimmt der
  gespeicherte `zustand` bereits mit dem Befund überein, unterbleibt der Aufruf von
  `setzeAssetZustand`. Begründung: Jeder Aufruf nimmt das D1-Schreib-Lock und stößt die entprellte
  Auto-Speicherung an (TK 9.5.4). Bei einem Projekt mit hundert intakten Medien wären das hundert
  Lock-Zyklen und ein Plattenschreibvorgang bei **jedem** Projektöffnen, ohne dass sich ein Byte
  ändert. Der Aufräumlauf soll nichts anfassen, was in Ordnung ist.
- **ENTSCHIEDEN – „vorhanden" heißt: es gibt dort eine reguläre Datei.** Ein Verzeichnis, ein
  Gerätename oder ein ins Leere zeigender Symlink an derselben Stelle gilt als **fehlend**.
  Begründung: Der `render-service` und der `preview-player` brauchen Bytes; ein Verzeichnis mit dem
  Namen eines Videos ist für sie genauso unbrauchbar wie gar nichts, und ein früher Abbruch mit
  `medium_fehlt` ist die ehrlichere Antwort als ein Lesefehler tief im ffmpeg-Aufruf.
- **ENTSCHIEDEN – liefert `loeseAssetPfad` `ok: false`, gilt das Asset als fehlend.** Das passiert
  nur bei einem `dateiname`, der die Form aus TK 9.4.8 Punkt 1 verletzt (Pfadtrenner, `..`,
  absoluter Pfad) – also bei einem beschädigten oder von außen manipulierten `project.json`. Ein
  solcher Eintrag kann **nie** gelesen werden; ihn auf `fehlt` zu setzen ist genau richtig und führt
  den Nutzer über die geführte Reparatur (FA-19) zu dem Element hin. Der Lauf bricht deswegen
  **nicht** ab.
- **ENTSCHIEDEN – ein Lesefehler des Dateisystems, der nicht „nicht vorhanden" bedeutet, gilt NICHT
  als fehlend.** Meldet die Existenzprüfung `ENOENT` (bzw. das plattformgleiche „gibt es nicht"),
  ist die Datei weg. Meldet sie etwas anderes (z. B. `EACCES`, `EPERM`, `EIO`, ein nicht
  verbundenes Netzlaufwerk), bleibt der bisherige `zustand` **unverändert** und der Eintrag wird
  weder gezählt noch geschrieben. Begründung: „Ich darf nicht hinsehen" ist nicht dasselbe wie „ist
  nicht da". Ein temporär gesperrter Ordner würde sonst die gesamte Bibliothek rot färben, und weil
  der Zustand persistiert wird, bliebe der Schaden auch dann bestehen, wenn der Ordner Sekunden
  später wieder verfügbar ist.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `projektId` leer, kein String, enthält `/`, `\` oder `..` | `ungueltige_eingabe` | **keine** Prüfung, **kein** Schreibvorgang |
| `assets` ist leer | – (kein Fehler) | `{ ok: true, wert: { markiert: 0 } }` |
| Datei existiert nicht (`ENOENT`) | – | `setzeAssetZustand(..., 'fehlt')`, falls der Zustand nicht schon `fehlt` ist; `markiert` +1 |
| Datei existiert, Asset stand auf `fehlt` | – | `setzeAssetZustand(..., 'ok')`; `markiert` bleibt unverändert |
| Datei existiert, Asset stand auf `ok` | – | **kein** Aufruf, **kein** Zähler |
| An der Stelle liegt ein Verzeichnis oder ein toter Symlink | – | behandelt wie „existiert nicht" (s. Invarianten) |
| `loeseAssetPfad` liefert `ok: false` | – | behandelt wie „existiert nicht"; der Lauf geht weiter |
| Existenzprüfung meldet einen anderen Fehler als `ENOENT` (z. B. `EACCES`, `EIO`) | – | Eintrag **überspringen**: kein Schreibvorgang, kein Zähler, Lauf geht weiter |
| `setzeAssetZustand` liefert `ok: false` | der Code von `setzeAssetZustand`, **unverändert** (z. B. `speicher_fehler`) | **Lauf abbrechen** und melden; die bereits gesetzten Zustände bleiben (kein Rollback, s. u.). Der Code wird **nicht** umgeschrieben und **nicht** in die `meldung` verschoben – `ReconcileFehlercode` führt ihn |
| unerwartete Ausnahme | `unbekannter_fehler` | gefangen und als Hülle gemeldet, kein `throw`, kein Stacktrace nach außen |

**Warum diese Datei bei einem D1-Schreibfehler abbricht, M3-11 bei einem Löschfehler dagegen nicht:**
Dort ging es um Speicherplatz, hier geht es um **Konsistenz**. Läuft das Markieren nach einem
Schreibfehler einfach weiter, entsteht ein Datenbestand, in dem ein Teil der Medien korrekt rot ist
und ein anderer Teil unauffällig aussieht, obwohl er fehlt – und genau das Versprechen „der
`render-service` bricht **früh** ab statt mitten im Lauf" (TK 9.4.7) ist gebrochen, ohne dass es
jemand sieht. Ein sichtbarer Fehler ist besser als eine halbe Wahrheit.

**Kein Rollback der bereits gesetzten Zustände.** Sie sind für sich genommen richtig – die Dateien
fehlen tatsächlich. TK 9.5.4 gibt für Speicherfehler dieselbe Richtung vor: „die Änderungen
**bleiben im Speicher** (kein Rollback, kein Arbeitsverlust)".

Fehlercodes werden **nicht erfunden:** „**Fehlercodes sind ein geschlossener, typisierter Satz** …
**Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1, Punkt 3).

## Nicht selbst entscheiden – STOPP und fragen
- **Keine eigene Fehlercode-Union in dieser Datei.** Der Rückgabetyp ist
  `Ergebnis<{ markiert: number }, ReconcileFehlercode>`, und `ReconcileFehlercode` steht in
  `fehlercodes.ts` (M3-02) – dort und nur dort. Kein zusätzlicher Code, kein `as`-Cast, kein
  `@ts-expect-error`, keine Erweiterung der fremden Datei (Regel E). Fehlt dort ein Code, den diese
  Datei bräuchte, ist das eine Frage an M3-02: **STOPP und fragen**.
- **Hier wird keine Datei gelöscht und keine wiederbeschafft.** Kein `unlink`, kein Kopieren, kein
  Suchen der Datei an anderer Stelle, kein „vielleicht liegt sie ja im Downloads-Ordner". Das
  Wiederverknüpfen ist Sache der geführten Reparatur (FA-19, TK 9.7.5) und geschieht mit dem Nutzer,
  nicht hinter seinem Rücken.
- **Das übergebene `Asset`-Objekt wird nicht verändert.** Kein `asset.zustand = 'fehlt'` im Array.
  Der Schnappschuss stammt aus dem geladenen Projekt; ihn direkt zu beschreiben, hieße, am D1-Lock
  vorbei zu schreiben – genau der zweite Schreibweg, den TK 9.4.1 ausschließt.
- **Keine eigene Pfad-Autorität.** Kein `path.join(medienOrdner, dateiname)` von Hand, kein
  `ermittleDatenOrt()`. Der Pfad kommt aus `loeseAssetPfad` (#49).
- **Keine Schleife und kein Beobachter.** Kein `fs.watch`, kein Intervall, kein erneutes Prüfen nach
  n Sekunden: „**kein** periodisches Aufräumen im laufenden Betrieb." (TK 9.4.8, Punkt 8)
- **Kein zweites Lock** (TK 9.4.8, Punkt 9): kein eigenes „Reconcile läuft"-Flag, keine
  OS-Dateisperre, keine Serialisierung neben dem D1-Lock.
