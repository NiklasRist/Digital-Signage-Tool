### Issue M3-11: [media-service] Aufräumen: verwaiste Dateien und `.part`-Leichen entfernen

## Ziel (in einem Satz)
Beim Öffnen eines Projekts verschwinden alle Dateien aus dem Medienordner, zu denen es keinen
Datensatz mehr gibt – einschließlich der `.part`-Leichen im Staging-Ordner –, sodass abgestürzte
Importe und misslungene Löschungen keinen Speicher dauerhaft belegen.

## Modul & Datei
- Modul: `media-service` [P1] (Main)
- Datei: `src/main/media-service/reconcile-waisen.ts`
- Vertrag: Technisches Konzept **9.4.7** (Quelle der Wahrheit), ergänzend **9.4.5** (woher Waisen
  kommen), **9.4.8** Punkt 8 und Punkt 9
- Prozess/Speicher: P1, **D2** (`projects/<id>/media/`). Diese Datei liest und schreibt **D1 nicht**
  und fordert **kein** D1-Lock an.

## Warum das im Gesamtsystem wichtig ist
Der Import ist bewusst in vier Schritte zerlegt, und zwei Absturzstellen dazwischen sind
unvermeidlich: „Crash vor 3 → nur eine `.part`-Leiche; Crash nach 3 vor 4 → eine fertige Waise ohne
D1-Eintrag. Beides räumt der Reconcile (9.4.7) auf." (TK 9.4.5). Dazu kommen die Dateien, deren
`unlink` beim Löschen fehlgeschlagen ist (TK 9.4.6). Diese Datei ist die **einzige** Stelle im ganzen
System, die solche Reste wieder loswird – es gibt ausdrücklich **kein** periodisches Aufräumen. Läuft
sie nicht oder zu vorsichtig, wächst der Projektordner mit jeder abgestürzten Sitzung um die Größe
eines ganzen Videos, und nichts in der Oberfläche weist darauf hin, weil zu diesen Dateien kein
Eintrag existiert.

Die gefährliche Richtung ist die andere: Diese Funktion **löscht Dateien**, die der Nutzer nicht
zurückholen kann. Eine falsche lokale Entscheidung – ein zu großzügiger Vergleich der Dateinamen, ein
rekursives Löschen von Unterordnern, ein Vergleich unter Missachtung der Groß-/Kleinschreibung auf
einem Windows-Dateisystem – vernichtet echte Medien, auf die Listenelemente zeigen. Das Projekt hat
dann keine kaputten Verweise (die repariert FA-19), sondern **fehlende Quelldateien**, und die
Wiederbeschaffung ist Sache des Nutzers.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/media-service/reconcile-waisen.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { ReconcileFehlercode } from './fehlercodes'
import { STAGING_ORDNER, PART_ENDUNG } from './import-datei'
// importiere, was der Ablauf braucht – mindestens STAGING_ORDNER. Wird PART_ENDUNG nicht
// gebraucht, bleibt es weg (ein ungenutzter Import bricht den Typecheck); abgeschrieben wird
// aber KEINER der beiden Werte.

export async function entferneWaisen(
  projektId: string,
  bekannteDateinamen: Set<string>,
): Promise<Ergebnis<{ entfernt: number }, ReconcileFehlercode>>
```

`ReconcileFehlercode = 'speicher_fehler' | 'datei_fehler'` (M3-02). Die drei generischen Codes
(`ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`) sind über den `Ergebnis`-Typ
automatisch enthalten. Die eigene Union ist nötig, damit ein echter Dateisystem-Fehler als
`datei_fehler` **erhalten bleibt**, statt auf `unbekannter_fehler` abgebildet zu werden. TK 9.1.1
warnt ausdrücklich davor: „Geht der Code verloren, degradieren Reparatur-Modus, Wiederholen und der
FAT32-Hinweis alle zu „irgendwas ist schiefgelaufen"." Der Aufräum-Ablauf (M3-14) reicht den Code
unverändert weiter, und das geht nur, wenn beide dieselbe Union führen.

`bekannteDateinamen` enthält die `dateiname`-Werte **aller** `Asset`-Einträge des Projekts (Form
`<uuid>.<ext_kleingeschrieben>`, ohne Verzeichnisanteil). Die Menge wird **hineingereicht**, nicht
hier beschafft: Das Lesen der Asset-Liste gehört dem `project-store` – „**`media-service` besitzt
NICHT:** das Lesen der Asset-Liste (das macht `project-store`)" (TK 9.4.1) –, und der Aufrufer
(M3-14) hat sie ohnehin schon. Zwei Leser derselben Liste wären zwei Wahrheiten.

### Fremde Funktionen, die du aufrufst
Der umsetzende Agent sieht die anderen Issues **nicht**; deshalb hier die vollständigen Signaturen:

```ts
// #49 – project-store, Pfad-Autorität (src/main/project-store/pfade.ts)
export function medienOrdner(projektId: string): string
// absoluter Pfad `<Datenort>/projects/<projektId>/media`;
// reine String-Operation, KEIN Dateisystemzugriff, KEINE Existenzprüfung, kann nicht fehlschlagen

// M3-07 – media-service, Kopie ins Staging (src/main/media-service/import-datei.ts)
export const STAGING_ORDNER = '.staging'   // Ordnername INNERHALB des Medienordners
export const PART_ENDUNG = '.part'         // Endung der noch unfertigen Arbeitsdatei
// Beides wird IMPORTIERT, nicht abgeschrieben (s. Invarianten). Ein Import ändert die fremde
// Datei nicht und verletzt Regel E daher nicht.
```

Mehr fremde Funktionen braucht diese Datei nicht. Insbesondere wird `loeseAssetPfad` **nicht**
benutzt: Es prüft einen `dateiname` gegen die Regeln des Datenmodells und würde für genau die
Namen, um die es hier geht (`<uuid>.<ext>.part`, Reste beliebiger Herkunft), teils `ok: false`
liefern. Der Pfad einer zu löschenden Datei entsteht hier aus `medienOrdner(projektId)` plus dem
Namen, den das Betriebssystem beim Auflisten des Ordners geliefert hat – ein Name, der aus dem
Verzeichnis selbst stammt, kann per Konstruktion nicht aus ihm ausbrechen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projektId` | Projekt, dessen Medienordner aufgeräumt wird | nicht leer, kein Pfadtrenner, kein `..`; der Pfad wird ausschließlich über `medienOrdner` gebildet |
| `bekannteDateinamen` | alle `Asset.dateiname` des Projekts | leere Menge ist zulässig und bedeutet: **jede** Datei im Ordner ist eine Waise |

Ausgang bei Erfolg: `{ entfernt: <Anzahl tatsächlich gelöschter Dateien> }`. Gezählt wird **nur**,
was wirklich verschwunden ist – nicht, was versucht wurde.
Ausgang bei Fehler: `ungueltige_eingabe` (unbrauchbare `projektId`), `datei_fehler` (der
Medienordner selbst ließ sich nicht auflisten), `unbekannter_fehler` (unerwartete Ausnahme). Ein
Fehler beim Löschen **einer einzelnen** Datei ist **kein** Fehler dieser Operation (s. Invarianten).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Datei in `media/` ohne D1-Eintrag** (Crash-/`unlink`-Waise, `.part`-Leiche) → löschen, Speicher
  zurück." (TK 9.4.7) – das ist der ganze Auftrag dieser Datei, wörtlich.
- „Crash vor 3 → nur eine `.part`-Leiche; Crash nach 3 vor 4 → eine fertige Waise ohne D1-Eintrag.
  Beides räumt der Reconcile (9.4.7) auf." (TK 9.4.5) – daher gehört der Staging-Ordner mit
  aufgeräumt.
- Der Staging-Ordner liegt **innerhalb** des Medienordners: „Quelle → `media/.staging/<uuid>.<ext>.part`
  kopieren *(langsam, **außerhalb** des D1-Locks)*." (TK 9.4.5, Schritt 1) und „`fs.rename` `.part` →
  `media/<uuid>.<ext>` — **atomar**, weil gleiche Partition (Staging liegt in `media/`;
  cross-volume-rename wäre copy+delete und **nicht** atomar)." (TK 9.4.5, Schritt 3)
- „**`media/` enthält im Normalbetrieb nur Dateien mit D1-Eintrag.** Abweichungen (nur durch
  Crash/`unlink`-Fehler möglich) bereinigt ausschließlich der Reconcile beim Start; **kein**
  periodisches Aufräumen im laufenden Betrieb." (TK 9.4.8, Punkt 8) – diese Funktion wird also
  **einmal je Projektöffnen** gerufen, nicht in einer Schleife, nicht auf einem Timer.
- „**Kein zweites Lock.** Serialisierung von Operationen liefert die Queue (9.3), Serialisierung von
  D1-Schreibvorgängen das eine `project-store`-Lock. `media-service` führt **kein** eigenes Lock und
  **keine** OS-Dateisperren ein (Over-Engineering-Falle)." (TK 9.4.8, Punkt 9)
- „Auch die **Pfadauflösung** (welcher absolute Pfad zu `projektId`+`dateiname` gehört) kommt vom
  `project-store` (Pfad-Autorität, 9.5.7) – `media-service` liest/schreibt die Bytes, kennt das
  Ordner-Layout aber nicht selbst." (TK 9.4.1) – der Medienordner kommt deshalb ausschließlich aus
  `medienOrdner(projektId)`; kein selbst zusammengesetztes `<Datenort>/projects/<id>/media`.
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Kein `throw` nach außen. Das Feld `daten` ist **optional** und wird hier **nicht** gefüllt: „Das
  Feld ist **optional** – Codes ohne Zusatzdaten lassen es weg" (TK 9.1.1). Keiner der Codes dieser
  Datei trägt Zusatzdaten.
- **ENTSCHIEDEN – `.staging` und `.part` werden IMPORTIERT, nicht abgeschrieben.** Die Werte kommen
  als `STAGING_ORDNER` und `PART_ENDUNG` aus `import-datei.ts` (M3-07). In dieser Datei steht
  **kein** Zeichenketten-Literal `'.staging'` und **kein** `'.part'`. Begründung: Der Import legt
  die `.part`-Datei mit genau diesen Werten an; zwei getrennte Literale in zwei Dateien laufen
  irgendwann auseinander, und dann findet der Aufräumlauf die Importreste **nie** – lautlos, weil er
  in einem Ordner sucht, den es nicht gibt, und dabei brav `{ entfernt: 0 }` meldet.
- **ENTSCHIEDEN – ein Fehler beim Löschen einer einzelnen Waise bricht den Lauf NICHT ab.** Die
  Datei wird übersprungen, der Zähler nicht erhöht, der Lauf geht weiter, und das Gesamtergebnis
  bleibt `ok: true`. Begründung: Hier geht es um **Speicherplatz, nicht um Konsistenz**. Der
  Datenbestand D1 ist bereits stimmig – eine liegengebliebene Waise hat definitionsgemäß keinen
  Eintrag und kann deshalb weder in der Liste erscheinen noch einen Render kaputt machen. Würde eine
  einzelne gesperrte Datei (unter Windows der Regelfall, wenn ein Virenscanner oder ein
  Explorer-Fenster sie gerade anfasst) den Lauf abbrechen, blieben die **nachfolgenden** Waisen für
  immer liegen, und – schwerer – der Aufräum-Ablauf (M3-14) meldete einen Fehler, obwohl das Projekt
  vollkommen in Ordnung ist. Genau das würde nach M3-17 verhindern, dass das Projekt normal geöffnet
  wird.
- **ENTSCHIEDEN – der Staging-Ordner wird geleert, aber NICHT gelöscht.** Jede Datei in
  `media/.staging/` ist per Konstruktion eine Waise: Ein `Asset.dateiname` trägt „**ohne**
  Verzeichnisanteil" (TK 9.4.8, Punkt 1) und kann deshalb niemals auf eine Datei im Staging zeigen;
  eine fertige Datei wird durch `fs.rename` aus dem Staging **heraus** bewegt (TK 9.4.5, Schritt 3).
  Was dort liegt, ist also immer Rest eines abgebrochenen Imports. Der **Ordner selbst** bleibt
  stehen: Er ist Teil des Ordner-Layouts, das der `project-store` verantwortet (TK 9.5.7); ihn hier
  zu entfernen hieße, dass der nächste Import ihn wieder anlegen muss – eine stillschweigende
  Kopplung zwischen Aufräumen und Import, die keiner der beiden Verträge vorsieht.
- **ENTSCHIEDEN – Unterordner werden weder betreten noch gelöscht, mit der einen Ausnahme
  `.staging`.** Der Vertrag spricht von einer *Datei* in `media/`. Ein rekursives Löschen unbekannter
  Verzeichnisse ist die gefährlichste denkbare Auslegung dieses Satzes und ausgeschlossen. Gefunden
  wird ein unbekannter Unterordner: **stehen lassen**, nicht betreten, nicht zählen.
- **ENTSCHIEDEN – der Namensvergleich ist unabhängig von Groß-/Kleinschreibung.** Ein Dateiname aus
  dem Verzeichnis gilt als **bekannt**, wenn er einem Eintrag aus `bekannteDateinamen` bei
  Kleinschreibung beider Seiten entspricht. Begründung: Die App läuft auf Windows und macOS, deren
  Dateisysteme im Regelfall **case-insensitive** sind. Bei einem exakten Vergleich würde eine Datei,
  die sich von ihrem D1-Eintrag nur in der Schreibweise unterscheidet, als Waise eingestuft und
  gelöscht – und damit genau die Datei vernichtet, auf die der Eintrag zeigt. Der umgekehrte Fehler
  (eine echte Waise bleibt liegen, weil sie einem Eintrag case-insensitiv gleicht) kostet nur
  Speicherplatz. Die Asymmetrie der Folgen entscheidet.
- **ENTSCHIEDEN – hier wird nichts an D1 geschrieben und nichts an Q2 gemeldet.** Diese Funktion
  markiert keinen Zustand (das ist M3-12), streicht keine offene Löschung (das ist M3-13) und legt
  keinen Eintrag an. Sie löscht Dateien und zählt.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `projektId` leer, kein String, enthält `/`, `\` oder `..` | `ungueltige_eingabe` | **keine** Datei wird angefasst; kein Ordner gelesen |
| Medienordner existiert nicht (Projekt hat nie importiert) | – (kein Fehler) | `{ ok: true, wert: { entfernt: 0 } }`; der Ordner wird **nicht** angelegt |
| `.staging` existiert nicht | – (kein Fehler) | übersprungen; der Ordner wird **nicht** angelegt |
| Medienordner ist nicht lesbar (Rechte, E/A-Fehler) | `datei_fehler` | Meldung nennt den Grund und den Betriebssystem-Code; nichts wurde gelöscht. **Nicht** `unbekannter_fehler`: Der Code ist der einzige Hinweis darauf, dass hier das Dateisystem und nicht die Programmlogik das Problem ist |
| Löschen **einer** Waise scheitert (`EBUSY`, `EPERM`, `EACCES`, beliebig) | – (kein Fehler) | Datei überspringen, intern protokollieren, weitermachen; `entfernt` zählt sie **nicht**; Gesamtergebnis bleibt `ok: true` |
| Eintrag im Verzeichnis ist ein Unterordner (außer `.staging`) | – | stehen lassen, nicht betreten |
| unerwartete Ausnahme außerhalb der Einzeldatei-Schleife | `unbekannter_fehler` | gefangen und als Hülle gemeldet, kein `throw`, kein Stacktrace nach außen |

Fehlercodes werden **nicht erfunden:** „**Fehlercodes sind ein geschlossener, typisierter Satz** …
**Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1, Punkt 3). Diese Datei benutzt
ausschließlich die generischen Codes und `ReconcileFehlercode` (M3-02); die Codes von Import und
Löschen (`ImportFehlercode`, `LoeschFehlercode`, ebenfalls M3-02) gehören zu jenen Operationen und
haben hier nichts zu suchen. `speicher_fehler` aus `ReconcileFehlercode` entsteht in dieser Datei
nicht – sie schreibt nichts; der Wert gehört zur gemeinsamen Union des Aufräumlaufs.

## Nicht selbst entscheiden – STOPP und fragen
- **Kein zweites Lock, keine eigene Sperre gegen gleichzeitige Importe.** Es ist verlockend, den
  Ordner während des Aufräumens zu sperren oder ein „Reconcile läuft"-Flag zu setzen, damit kein
  Import dazwischenfunkt. Verboten: „`media-service` führt **kein** eigenes Lock und **keine**
  OS-Dateisperren ein (Over-Engineering-Falle)." (TK 9.4.8, Punkt 9). Die zeitliche Ordnung stellt
  der Ablauf beim Projektöffnen her (M3-17): Der Aufräumlauf läuft, **bevor** die Oberfläche Medien
  zeigt, und damit bevor der Nutzer einen Import auslösen kann.
- **Keine Schleife, kein Timer, kein „regelmäßiges" Nachfassen.** TK 9.4.8 Punkt 8 schließt
  periodisches Aufräumen ausdrücklich aus. Wer hier ein Intervall einbaut, löscht irgendwann eine
  `.part`-Datei, die ein **laufender** Import gerade schreibt.
- **Keine eigene Pfad-Autorität.** Kein selbst zusammengesetztes `<Datenort>/projects/<id>/media`,
  kein `ermittleDatenOrt()`-Aufruf, keine zweite Auflösungsfunktion – der Ordner kommt aus
  `medienOrdner(projektId)` (#49). Fehlt dort etwas, ist das eine Frage an #49, kein Freibrief.
- **Den Namen des Staging-Ordners nicht neu erfinden und nicht abschreiben.** Er kommt als
  `STAGING_ORDNER` aus `import-datei.ts` (M3-07), die Endung der unfertigen Datei als
  `PART_ENDUNG` aus derselben Datei. Kein eigenes Literal, keine Konstante mit demselben Wert in
  dieser Datei, keine Ableitung aus einem Pfad. Weicht der dort exportierte Wert von `.staging` bzw.
  `.part` ab, ist das ein Widerspruch zwischen zwei Issues: **STOPP und fragen**, nicht
  stillschweigend anpassen – zwei verschiedene Staging-Namen bedeuten, dass Importreste nie gefunden
  werden.
- **Nichts löschen, was nicht aus dem Verzeichnislisting stammt.** Keine Namen aus
  `bekannteDateinamen` ableiten, keine Muster raten („alles was auf `.tmp` endet"), keine
  Heuristik über das Alter einer Datei. Gelöscht wird ausschließlich, was der Ordner selbst geliefert
  hat und was nicht in `bekannteDateinamen` steht.
- **Keine Ausgabedateien anfassen.** `projects/<id>/output/` gehört nicht zu D2 und wird von dieser
  Funktion **nie** gelesen und **nie** aufgeräumt. Dort liegen die gerenderten MP4s (FA-22), die der
  Nutzer noch exportieren will; sie haben grundsätzlich keinen D1-Eintrag und würden von einer
  „Waisen"-Logik alle vernichtet.

## Definition of Done
- [ ] Eine Datei im Medienordner, deren Name **nicht** in `bekannteDateinamen` steht, ist nach dem
      Aufruf verschwunden und in `entfernt` gezählt (Test mit echtem Temp-Ordner; `medienOrdner` als
      Attrappe, die auf diesen Ordner zeigt)
- [ ] Eine Datei, deren Name in `bekannteDateinamen` steht, existiert danach unverändert
- [ ] Eine Datei, die sich von einem Eintrag aus `bekannteDateinamen` **nur in der
      Groß-/Kleinschreibung** unterscheidet, wird **nicht** gelöscht
- [ ] Jede Datei in `<medienOrdner>/.staging` ist danach gelöscht, der Ordner `.staging` existiert
      aber weiterhin (Test prüft beides)
- [ ] Ein Unterordner im Medienordner (Name ungleich `.staging`) existiert danach unverändert und
      wurde nicht betreten
- [ ] Fehlender Medienordner: `{ ok: true, wert: { entfernt: 0 } }`, und es wurde **kein** Ordner
      angelegt
- [ ] Scheitert das Löschen genau einer von drei Waisen (Attrappe des Löschaufrufs wirft für eine
      Datei), sind die anderen beiden gelöscht, `entfernt` ist **2**, und das Ergebnis ist
      `ok: true`
- [ ] Leere `bekannteDateinamen`-Menge: alle Dateien im Medienordner werden gelöscht, Unterordner
      nicht
- [ ] `ungueltige_eingabe` bei `projektId` `''`, `'../x'`, `'a/b'` – und in allen drei Fällen wurde
      nachweislich **keine** Datei gelöscht (Spion auf den Löschaufruf: null Aufrufe)
- [ ] Ein nicht lesbarer Medienordner liefert `datei_fehler` (nicht `unbekannter_fehler`), und der
      Betriebssystem-Code steht ausschließlich in der `meldung`
- [ ] Die Datei enthält keinen Zugriff auf `project.json`, keinen D1-Lock-Aufruf, keinen Timer,
      keinen `rm -r`/rekursiven Verzeichnislöschaufruf und keinen selbst zusammengesetzten Datenort
      (Grep-Probe)
- [ ] Die Datei enthält **kein** Literal `'.staging'` und **kein** Literal `'.part'`; der
      Staging-Ordnername kommt nachweislich als Import aus `import-datei.ts` (Grep-Probe)
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze)
- [ ] Keine Datei außerhalb von `src/main/media-service/reconcile-waisen.ts` **(+ zugehörige
      Testdatei)** geändert
