### Issue M3-14: [media-service] Aufräum-Ablauf zusammensetzen

## Ziel (in einem Satz)
Die drei Aufräum-Schritte laufen beim Öffnen eines Projekts in einer festen, begründeten Reihenfolge
genau einmal durch, sodass danach der Medienordner und der Datenbestand D1 wieder dasselbe erzählen.

## Modul & Datei
- Modul: `media-service` [P1] (Main)
- Datei: `src/main/media-service/reconcile.ts`
- Vertrag: Technisches Konzept **9.4.7** (Quelle der Wahrheit), **9.4.8** Punkt 8 und Punkt 9
- Prozess/Speicher: P1; berührt über die drei Schritte **D2**, **D1** (delegiert) und **Q2** (über
  die Auftragsverwaltung). **Kein** eigener Dateizugriff, **kein** Lock.

## Warum das im Gesamtsystem wichtig ist
Diese Datei enthält kaum Logik und trotzdem die wichtigste Entscheidung des ganzen Aufräumens: die
**Reihenfolge**. Die drei Schritte sehen unabhängig aus, sind es aber nicht – jeder verändert die
Grundlage, auf der der nächste urteilt. In der falschen Reihenfolge produzieren dieselben drei
korrekten Funktionen ein falsches Ergebnis, und zwar ohne Fehlermeldung.

Zwei konkrete Beispiele. Erstens: Würden die Waisen **vor** den offenen Löschungen entfernt, wäre die
Datei einer offenen Löschung längst weg, wenn `entferneDatei` sie anfassen will – der Vermerk in Q2
bliebe (im günstigen Fall) nur einen Lauf länger stehen, und die Zahlen im Ergebnis behaupteten, es
sei eine Waise beseitigt worden, wo in Wirklichkeit eine vorgemerkte Löschung nachgeholt wurde.
Zweitens, und das ist der teure Fall: Würde **zuerst** markiert und **danach** aufgeräumt, entstünde
die Aussage „`zustand: fehlt`" aus einem Ordnerzustand, der Sekunden später ein anderer ist – der
Nutzer sähe rote Einträge für Medien, die vorhanden sind, und die geführte Reparatur (FA-19) würde
ihn zwingen, intakte Elemente neu zu verknüpfen.

Der zweite Wert dieser Datei ist eine Verneinung: Sie ist **kein** Dienst, der im Hintergrund läuft.
Wer hier einen Timer oder eine Schleife einbaut, löscht irgendwann die `.part`-Datei eines gerade
laufenden Imports.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/media-service/reconcile.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { Asset } from '../../shared/contracts/asset'
import type { ReconcileFehlercode } from './fehlercodes'

export async function reconcile(
  projektId: string,
  assets: Asset[],
): Promise<Ergebnis<{ entfernt: number; markiert: number; erledigt: number }, ReconcileFehlercode>>
```

`ReconcileFehlercode = 'speicher_fehler' | 'datei_fehler'` (M3-02); die drei generischen Codes kommen
über den `Ergebnis`-Typ automatisch dazu. Alle drei Schritte führen dieselbe Union – nur deshalb kann
diese Datei ihren Fehler **unverändert** durchreichen, statt ihn auf `unbekannter_fehler`
abzubilden. TK 9.1.1 warnt genau davor: „Geht der Code verloren, degradieren Reparatur-Modus,
Wiederholen und der FAT32-Hinweis alle zu „irgendwas ist schiefgelaufen"."

### Die verbindliche Reihenfolge
1. **Offene Löschungen nachholen** – `holeLoeschungenNach(projektId)` (M3-13)
2. **Waisen entfernen** – `entferneWaisen(projektId, bekannteDateinamen)` (M3-11)
3. **Fehlende Dateien markieren** – `markiereFehlende(projektId, assets)` (M3-12)

**Begründung, die im Code als Kommentar stehen bleiben soll:** Eine gerade erfolgreich nachgeholte
Löschung darf nicht im selben Lauf als „Waise" wieder auftauchen – nach Schritt 1 ist die Datei weg
und Schritt 2 findet sie gar nicht mehr vor. Und ob ein D1-Eintrag wirklich ohne Datei dasteht, ist
erst **nach beiden** vorangehenden Schritten zuverlässig feststellbar: Schritt 1 kann eine Datei
entfernen, Schritt 2 ebenfalls; ein vorgezogenes Schritt 3 urteilte über einen Ordnerzustand, den es
selbst gleich veralten lässt. (Dass Schritt 2 nie eine Datei mit D1-Eintrag anfasst, ist dort
zugesichert – die Reihenfolge ist trotzdem bindend, weil das Ergebnis sonst von einer Zusicherung
eines Nachbar-Issues abhinge statt von der Ablauflogik hier.)

### Fremde Funktionen, die du aufrufst
Der umsetzende Agent sieht die anderen Issues **nicht**; deshalb hier die vollständigen Signaturen:

```ts
// M3-13 (src/main/media-service/reconcile-loeschungen.ts)
export async function holeLoeschungenNach(
  projektId: string,
): Promise<Ergebnis<{ erledigt: number; offen: number }, ReconcileFehlercode>>
// erledigt = Datei weg UND Vermerk gestrichen; offen = Einträge, die danach noch in Q2 stehen;
// ein einzelner gescheiterter Löschversuch ist KEIN Fehler dieser Operation

// M3-11 (src/main/media-service/reconcile-waisen.ts)
export async function entferneWaisen(
  projektId: string,
  bekannteDateinamen: Set<string>,
): Promise<Ergebnis<{ entfernt: number }, ReconcileFehlercode>>
// bekannteDateinamen = alle Asset.dateiname des Projekts; leere Menge bedeutet:
// jede Datei im Medienordner ist eine Waise

// M3-12 (src/main/media-service/reconcile-fehlt.ts)
export async function markiereFehlende(
  projektId: string,
  assets: Asset[],
): Promise<Ergebnis<{ markiert: number }, ReconcileFehlercode>>
// markiert zählt NUR die in diesem Lauf neu auf 'fehlt' gesetzten Assets

// #49 – project-store, Pfad-Autorität (src/main/project-store/pfade.ts)
export function medienOrdner(projektId: string): string
// absoluter Pfad `<Datenort>/projects/<projektId>/media`; reine String-Operation, kein fs-Zugriff
// – wird von M3-11 benutzt; diese Datei ruft ihn nur auf, wenn sie ihn selbst braucht
```

**Woher die Asset-Liste kommt – entschieden, nicht mehr offen:** Sie wird von oben
**durchgereicht**. Der Koordinations-Ablauf beim Projektöffnen (M3-17) hat das vollständige
`Project` bereits als Rückgabewert von `öffneProjekt` (#34) in der Hand und übergibt
`projekt.assets` an diese Funktion. Begründung, warum es **keine** neue Leseoperation gibt: Ein
exportierter Zugriff auf das geladene Projekt wäre eine **zweite Tür** in den `project-store` neben
seinen Operationen – ab da gäbe es zwei Wege an dieselben Daten, von denen nur einer am D1-Lock
vorbeikommt. Und dem `media-service` ist das Lesen der Asset-Liste ohnehin verboten:
„**`media-service` besitzt NICHT:** das Lesen der Asset-Liste (das macht `project-store`)"
(TK 9.4.1). Die Daten kommen deshalb von oben, nicht durch eine neue Leseoperation.

`bekannteDateinamen` und `assets` stammen damit aus **derselben** Quelle: dem übergebenen Array. Die
Menge entsteht hier aus der Liste (`new Set(assets.map(a => a.dateiname))`) – sie wird **nicht**
getrennt beschafft und **nicht** als zweiter Parameter erwartet, damit beide Schritte über denselben
Bestand urteilen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projektId` | das gerade geöffnete Projekt | nicht leer, kein Pfadtrenner, kein `..`; wird unverändert an die drei Schritte weitergereicht |
| `assets` | die Asset-Liste des **bereits geladenen** Projekts, vom Koordinations-Ablauf (M3-17) durchgereicht | muss ein Array sein; ein **leeres** Array ist zulässig und bedeutet „das Projekt hat keine Medien" – dann ist jede Datei im Medienordner eine Waise. Die Liste wird **nur gelesen**, nie verändert und nie sortiert |

Ausgang bei Erfolg: `{ entfernt, markiert, erledigt }` – die drei Zahlen aus den Schritten 2, 3
und 1, jeweils unverändert übernommen.
Ausgang bei Fehler: der Fehler des **ersten** scheiternden Schritts, **unverändert** durchgereicht
(Code und Meldung). Diese Datei erfindet keinen eigenen Code.

**`offen` aus Schritt 1 wandert nicht ins Ergebnis** – das Rückgabeobjekt ist verbindlich festgelegt
und hat kein solches Feld. Der Wert wird intern protokolliert und dort nicht weiter verwendet.
Begründung: Das Ergebnis beantwortet „was hat dieser Lauf **verändert**"; die Zahl der weiterhin
offenen Löschungen ist ein Bestand, der beim nächsten Öffnen ohnehin erneut ermittelt wird. Das
Rückgabeobjekt wird **nicht** um ein Feld erweitert.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Der Zeitpunkt, wörtlich: „Beim Öffnen eines Projekts, **bevor** die UI Medien zeigt (kein
  Render/keine Vorschau hält dann Handles):" (TK 9.4.7) – daraus folgt zweierlei: Der Lauf muss
  **abgeschlossen** sein, ehe die Oberfläche Medien anzeigt (das stellt M3-17 sicher), und er darf
  sich darauf verlassen, dass in diesem Moment kein Handle auf eine Mediendatei offen ist. Deshalb
  braucht er **keine** eigene Absicherung dagegen.
- Die drei Schritte, wörtlich (TK 9.4.7):
  - „**Datei in `media/` ohne D1-Eintrag** (Crash-/`unlink`-Waise, `.part`-Leiche) → löschen,
    Speicher zurück."
  - „**D1-Eintrag ohne Datei** → `Asset.zustand = "fehlt"`. Die UI zeigt ihn rot; der
    `render-service` bricht **früh** mit `medium_fehlt` ab statt mitten im Lauf."
  - „**`pendingDeletions` aus Q2** (`projects/<id>/queue-retry.json`) → jetzt nachholen. Q2 liegt
    **pro Projekt**, weil ausstehende Löschungen zum Projekt gehören und mit ihm verschwinden (9.3)."
- Kein Dauerbetrieb, wörtlich: „**`media/` enthält im Normalbetrieb nur Dateien mit D1-Eintrag.**
  Abweichungen (nur durch Crash/`unlink`-Fehler möglich) bereinigt ausschließlich der Reconcile beim
  Start; **kein** periodisches Aufräumen im laufenden Betrieb." (TK 9.4.8, Punkt 8) – der Lauf ist
  **nicht** in einer Schleife und **nicht** periodisch; er läuft **genau einmal beim Öffnen eines
  Projekts**.
- „**Kein zweites Lock.** Serialisierung von Operationen liefert die Queue (9.3), Serialisierung von
  D1-Schreibvorgängen das eine `project-store`-Lock. `media-service` führt **kein** eigenes Lock und
  **keine** OS-Dateisperren ein (Over-Engineering-Falle)." (TK 9.4.8, Punkt 9)
- „**`media-service` besitzt NICHT:** das Lesen der Asset-Liste (das macht `project-store`)"
  (TK 9.4.1) – diese Datei liest `project.json` **nicht** selbst und öffnet das Projekt **nicht**
  (das ist bereits geschehen, s. M3-17). Genau deshalb kommt die Liste als Parameter herein.
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Kein `throw` nach außen. Trägt der Fehler eines Schritts ein `daten`-Feld, wird es mit
  durchgereicht – „Ein Aufrufer, der `daten` nicht kennt, funktioniert unverändert weiter."
  (TK 9.1.1). Diese Datei füllt das Feld **nie** selbst.
- **ENTSCHIEDEN – die Asset-Liste wird durchgereicht, es entsteht kein neuer Zugriffsweg.** `assets`
  kommt vom Koordinations-Ablauf (M3-17), der es von `öffneProjekt` (#34) hat. Diese Datei
  beschafft die Liste **nicht** selbst: kein zweiter `öffneProjekt`-Aufruf, kein Lesen von
  `project.json`, keine gemerkte Kopie im Modul – und der `project-store` bekommt dafür **keine**
  neue exportierte Leseoperation. Eine solche wäre eine **zweite Tür** in den `project-store` neben
  seinen Operationen; das Verbot aus TK 9.4.1 (oben) sagt ohnehin, dass das Lesen der Asset-Liste
  nicht dem `media-service` gehört.
- **ENTSCHIEDEN – die Reihenfolge ist sequenziell und bindend.** Die drei Schritte laufen
  **nacheinander**, jeder wird **abgewartet**. Kein `Promise.all`, keine Parallelisierung „weil es
  schneller geht": Schritt 2 und 3 urteilen beide über den Ordnerinhalt, den Schritt 1 gerade
  verändert; parallel gestartet, entscheidet der Zufall, wer welchen Zustand sieht.
- **ENTSCHIEDEN – der erste scheiternde Schritt beendet den Lauf.** Die folgenden Schritte laufen
  dann **nicht** mehr, und der Fehler wird unverändert weitergereicht. Begründung: Die drei Zahlen
  im Erfolgsfall sind eine Aussage über den Endzustand; ein Lauf, in dem ein Schritt ausgefallen ist,
  hätte diese Aussage nicht mehr gedeckt. Und die Fehlerfälle der drei Schritte sind bewusst eng
  gehalten – jeder von ihnen bedeutet, dass ein Speicher des Projekts (Q2, der Medienordner oder D1)
  nicht benutzbar ist. Das gehört gemeldet, nicht überspielt.
- **ENTSCHIEDEN – kein teilweiser Erfolg im Ergebnis.** Es gibt keine Mischform „ok mit Warnungen".
  Entweder alle drei Schritte sind gelaufen (`ok: true` mit den drei Zahlen) oder es liegt ein Fehler
  vor. Die Fälle, die man als „Warnung" empfinden könnte – eine nicht löschbare Waise, eine weiterhin
  offene Löschung –, sind in den Schritten selbst ausdrücklich **kein** Fehler und stecken in den
  Zahlen.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `projektId` leer, kein String, enthält `/`, `\` oder `..` | `ungueltige_eingabe` | **kein** Schritt wird gestartet |
| `assets` ist kein Array | `ungueltige_eingabe` | **kein** Schritt wird gestartet. Ein leeres Array ist dagegen gültig (s. Eingang) und wird **nicht** abgelehnt |
| Schritt 1 (`holeLoeschungenNach`) liefert `ok: false` | Code aus Schritt 1, unverändert | Schritte 2 und 3 laufen **nicht** |
| Schritt 2 (`entferneWaisen`) liefert `ok: false` | Code aus Schritt 2, unverändert | Schritt 3 läuft **nicht**; das Ergebnis von Schritt 1 bleibt bestehen (nichts wird zurückgenommen) |
| Schritt 3 (`markiereFehlende`) liefert `ok: false` | Code aus Schritt 3, unverändert | die Wirkungen der Schritte 1 und 2 bleiben bestehen |
| unerwartete Ausnahme | `unbekannter_fehler` | gefangen und als Hülle gemeldet, kein `throw`, kein Stacktrace nach außen |

Fehlercodes werden **nicht erfunden** und **nicht umgeschrieben:** „**Fehlercodes sind ein
geschlossener, typisierter Satz** … **Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1,
Punkt 3). Was aus einem Schritt kommt, kommt unverändert heraus.

## Nicht selbst entscheiden – STOPP und fragen
- **Die Asset-Liste nicht selbst beschaffen.** Sie kommt als Parameter herein (entschieden,
  s. Invarianten). Verboten ist deshalb:
  - `öffneProjekt(projektId)` aufrufen – das lädt neu, setzt über den `config-store` erneut das
    aktive Projekt und macht aus einem Aufräumlauf einen zweiten Ladevorgang mit eigenem
    `.bak`-Fallback;
  - `project.json` selbst lesen oder parsen (zweiter Leseweg neben dem `project-store`);
  - eine eigene Zwischenablage/„zuletzt gesehenes Projekt"-Variable im `media-service` anlegen;
  - beim `project-store` eine neue exportierte Leseoperation für das geladene Projekt anfordern
    oder anlegen (fremde Datei, Regel E – und eine zweite Tür neben seinen Operationen).
  „Das **aktive** Projekt lebt zur Laufzeit **im Speicher**" (TK 9.5.1) – wer es braucht, bekommt es
  von dem, der es geladen hat.
- **Kein Timer, keine Schleife, kein Wiederholen.** Der Lauf findet genau einmal je Projektöffnen
  statt (TK 9.4.8, Punkt 8). Kein `setInterval`, kein `fs.watch`, kein „nach dem Import nochmal
  kurz aufräumen".
- **Keine Fachlogik in dieser Datei.** Kein `fs`-Aufruf, kein `unlink`, kein Zustand-Setzen, keine
  eigene Prüfung „existiert die Datei?". Diese Datei ruft drei Funktionen in einer Reihenfolge auf,
  addiert nichts hinzu und filtert nichts weg.
- **Die Reihenfolge nicht ändern und nicht konfigurierbar machen.** Kein Parameter, kein Schalter,
  keine „schnelle Variante ohne Schritt 2". Die Begründung steht oben.
- **Kein zweites Lock** (TK 9.4.8, Punkt 9): kein Mutex, keine OS-Dateisperre, kein
  „Reconcile läuft"-Flag – auch nicht, um einen zweiten gleichzeitigen Aufruf abzufangen. Dass der
  Lauf genau einmal und zum richtigen Zeitpunkt geschieht, stellt der Ablauf beim Projektöffnen
  sicher (M3-17), nicht diese Datei.
- **Kein IPC-Kanal.** `reconcile` ist main-intern und wird ausschließlich vom Koordinations-Ablauf
  (M3-17) gerufen: kein Eintrag in `kanaele.ts` (#25), keine Registrierung im `ipc-gateway`, kein
  Auftrag über `reiheEin`.
