### Issue M3-06: [media-service] Metadaten auswerten: Maße, Rotation, Dauer

## Ziel (in einem Satz)
Aus der Rohausgabe von `ffprobe` werden die drei Werte gewonnen, die im `Asset` landen: die
**Display**-Maße (mit Rotationskorrektur), ganzzahlig, und die Dauer in Sekunden mit drei
Dezimalstellen – bei Bildern immer `null`.

## Modul & Datei
- Modul: `media-service` (Main)
- Datei: `src/main/media-service/metadaten.ts`
- Vertrag: Technisches Konzept **9.4.8** Punkte 3 und 4, ergänzend **9.4.4** (`Asset`), **9.4.9**
  (`probe_fehler`) – Quelle der Wahrheit
- Prozess/Speicher: P1; **kein** Datei- und **kein** Prozesszugriff (reine Funktion)

## Warum das im Gesamtsystem wichtig ist
Die beiden Werte, die hier entstehen, wandern in den `Asset`-Datensatz und werden **dauerhaft
gespeichert**. Sie werden danach nirgends mehr nachgerechnet, sondern überall geglaubt: Die
Oberfläche zeigt die Maße an, der `composer` begrenzt den Trim-Regler an der Dauer, der
`render-service` skaliert und schneidet auf ihrer Grundlage.

**Falsche Maße** entstehen genau dann, wenn die Rotation übersehen wird: Ein Hochkant-Video vom
Handy meldet in `stream.width`/`stream.height` die **codierten** Maße (z. B. 1920×1080) und trägt
zusätzlich einen Rotations-Tag. Ungeschützt übernommen, hält das System ein Hochformat-Video für ein
Querformat-Video – die Vorschau zeigt es anders als das Endvideo, und der Nutzer setzt seine
Trim-Punkte auf einer falschen Darstellung.

Eine **auf Integer gerundete Dauer** ist noch heimtückischer: Sie sieht richtig aus. Aus 12,033 s
werden 12 s, und der frame-genaue Schnitt (30 fps, TK 9.2.6) verschiebt sich um bis zu einer Sekunde
– bei jedem Element. Über eine Schleife aus vielen Elementen summiert sich das zu einer Ausgabedatei,
deren Länge nicht mehr zur Anzeige im `composer` passt. Beides ist im Nachhinein nur durch einen
Neu-Import aller Medien zu heilen, weil die falschen Werte gespeichert sind.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/media-service/metadaten.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { ImportFehlercode } from './fehlercodes'

export function werteMetadatenAus(
  roh: unknown,
  typ: 'video' | 'bild',
): Ergebnis<{ maße: { breite: number; höhe: number }; dauer: number | null }, 'probe_fehler'>
```

Rein und synchron, ohne Datei- und ohne Prozesszugriff: Damit ist jeder Sonderfall (Rotation,
fehlende Dauer, kaputte Struktur) mit einem von Hand geschriebenen JSON-Objekt testbar – ohne
`ffprobe`, ohne Testvideo, in Millisekunden.

Der Fehlercode-Typparameter ist auf das eine Literal `'probe_fehler'` verengt: Eine unbrauchbare
Rohausgabe ist derselbe Fall wie ein fehlgeschlagener Probe-Lauf (TK 9.4.9 nennt „`ffprobe` liefert
keine Metadaten"). (`ImportFehlercode` wird trotzdem importiert – als Beleg, dass das Literal aus der
Modul-Union stammt und nicht frei erfunden ist. Löst der sonst ungenutzte Import eine Compiler- oder
Lint-Warnung aus, gehört der Beleg stattdessen in die Testdatei:
`const c: ImportFehlercode = 'probe_fehler'`.)

**Woher `roh` kommt, vollständig ausgeschrieben** (der umsetzende Agent sieht die anderen Issues
nicht):

```ts
// M3-05 – src/main/media-service/ffprobe.ts:
export async function leseRohMetadaten(
  dateiPfad: string,
): Promise<Ergebnis<unknown, 'probe_fehler'>>
// Der Erfolgswert ist das mit JSON.parse geparste Objekt (KEIN String) des Aufrufs
//   ffprobe -v error -print_format json -show_streams -show_format <dateiPfad>
// Genau dieser Wert wird als `roh` hier hereingereicht.
```

Die Struktur, mit der du rechnen musst (Ausschnitt; **alle Zahlen kommen von ffprobe als
Zeichenkette**, nicht als Zahl):

```jsonc
{
  "streams": [
    {
      "codec_type": "video",     // auch bei Bildern: png/mjpeg/webp erscheinen als Video-Stream
      "width": 1920,             // CODIERTE Breite (Zahl)
      "height": 1080,            // CODIERTE Höhe (Zahl)
      "duration": "12.033000",   // ZEICHENKETTE, kann fehlen
      "tags": { "rotate": "90" } // ZEICHENKETTE, kann fehlen
    },
    { "codec_type": "audio" }    // gibt es auch – NICHT auswerten
  ],
  "format": { "duration": "12.033000" }   // ZEICHENKETTE, kann fehlen
}
```

**Der Ablauf, verbindlich:**

1. `roh` defensiv prüfen: Objekt, `streams` ist ein Array. Sonst → `probe_fehler`.
2. Den **ersten** Eintrag mit `codec_type === 'video'` nehmen. Gibt es keinen → `probe_fehler`
   (eine reine Tondatei ist kein importierbares Medium). Audio-Streams werden nie ausgewertet.
3. `width`/`height` lesen. Beide müssen endliche Zahlen > 0 sein, sonst → `probe_fehler`. Danach
   `Math.round` anwenden (TK 9.4.8 Punkt 3 verlangt ganzzahlige Werte ausdrücklich).
4. Rotation bestimmen: `tags.rotate` lesen, sofern vorhanden. Der Wert ist eine Zeichenkette und wird
   mit `Number(...)` gelesen; ist er nicht numerisch oder fehlt er, gilt 0. Danach auf den Bereich
   0–359 normalisieren: `((n % 360) + 360) % 360`. Grund für die Normalisierung: `ffprobe` liefert je
   nach Quelle `"90"` **oder** `"-90"` für dieselbe Drehung; ohne Normalisierung würde die eine
   Schreibweise erkannt und die andere übersehen – und die Übersehene ist genau der Hochkant-Fall.
5. Ist die normalisierte Rotation **90 oder 270**, werden `breite` und `höhe` **getauscht**. Bei 0
   und 180 werden sie direkt übernommen (180 dreht das Bild, nicht die Kanten).
6. Dauer:
   - `typ === 'bild'` → **immer** `null`. Kein Blick in die Daten. (`ffprobe` meldet für Einzelbilder
     regelmäßig eine erfundene Dauer wie `"0.040000"` – die wäre schlicht falsch.)
   - `typ === 'video'` → zuerst `format.duration`, ersatzweise `duration` des gewählten Video-Streams.
     Beide sind Zeichenketten und werden mit `Number(...)` gelesen. Ergibt sich keine endliche Zahl
     > 0 → `probe_fehler`. Der Container-Wert hat Vorrang, weil er die Länge beschreibt, die ein
     Abspieler tatsächlich zeigt.
   - Auf **drei Dezimalstellen** runden: `Math.round(sekunden * 1000) / 1000`. **Nie** `Math.round`
     auf ganze Sekunden, nie `Math.floor`, nie `toFixed` als Rückgabewert (das liefert eine
     Zeichenkette, und `Asset.dauer` ist eine Zahl).
7. Ergebnis: `{ ok: true, wert: { maße: { breite, höhe }, dauer } }`.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `roh` | die geparste `ffprobe`-Ausgabe aus M3-05 | `unknown` – **jede** Struktur muss defensiv geprüft werden; fehlende oder unerwartete Felder führen zu `probe_fehler`, niemals zu einer Ausnahme |
| `typ` | `'video'` oder `'bild'`, wie ihn `pruefeFormat` (M3-03) bestimmt hat | steuert allein die Dauer: Bild → `null`, ohne die Daten anzusehen |

Ausgang bei Erfolg: `{ maße: { breite, höhe }, dauer }` – `maße` sind **Display**-Maße, ganzzahlig
und > 0; `dauer` ist bei Video eine Zahl mit höchstens drei Dezimalstellen, bei Bild `null`.
Ausgang bei Fehler: Code `probe_fehler` (einziger fachlicher Code dieser Funktion).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**`maße` = Display-Maße.** Trägt der Videostream einen Rotations-Tag `rotate ∈ {90, 270}`, werden
  `breite`/`höhe` getauscht; sonst direkt übernommen. Immer ganzzahlig (`Math.round`). Nie
  `stream.width`/`stream.height` ohne Rotationskorrektur — sonst zeigt die UI falsche Maße und der
  Nutzer setzt falsche Trim-Punkte." (TK 9.4.8, Punkt 3)
- „**`dauer` = ffprobe-Sekunden, 3 Dezimalstellen, nie auf Integer gerundet** (z. B. `12.033`). Für
  Bilder immer `null`." (TK 9.4.8, Punkt 4)
- Die Zielfelder im `Asset` (TK 9.4.4, wörtlich):

  ```
  maße: { breite: number, höhe: number }   // DISPLAY-Maße in Pixeln, ganzzahlig (9.4.8)
  dauer:        number | null       // Sekunden, 3 Nachkommastellen (Video); null (Bild)
  ```

  Die Feldnamen `maße`, `breite`, `höhe` werden **mit Umlaut** geschrieben, genau wie im
  `Asset`-Typ (#13); eine „Vereinfachung" zu `masse`/`hoehe` bräche die Zuweisung.
- „| `probe_fehler` | `ffprobe` liefert keine Metadaten (beschädigte Datei) **oder** Timeout
  (gekillt) |" (TK 9.4.9) – eine unbrauchbare oder unvollständige Rohausgabe fällt unter „liefert
  keine Metadaten" und bekommt denselben Code.
- **Niemals `throw`, auch nicht bei völlig fremdartiger Struktur.** `roh` ist `unknown` und stammt
  aus einem fremden Programm; jeder Zugriff wird geprüft. Eine Ausnahme hier ließe den Import-Auftrag
  ohne brauchbaren Code scheitern (TK 9.1.1).
- **Rein und deterministisch:** kein `fs`, kein Prozessstart, kein `await`, kein Zufall, kein Zugriff
  auf Datum oder Umgebung. Dieselbe Eingabe liefert immer dasselbe Ergebnis.
- **Keine Normalisierung auf das Ausgabeprofil.** Hier wird **nicht** auf 1920×1080 skaliert, nicht
  auf 30 fps gerechnet, nichts begrenzt. „1080p ist Render-Normalisierung, kein Import-Umschreiben."
  (TK 9.1) Die gespeicherten Importe bleiben roh; die Anpassung geschieht zur Render-Zeit (M6).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `roh` ist kein Objekt / `streams` fehlt oder ist kein Array | `probe_fehler` | keine Wirkung, keine Ausnahme |
| Kein Stream mit `codec_type === 'video'` (z. B. reine Tondatei) | `probe_fehler` | keine Wirkung |
| `width` oder `height` fehlt, ist keine Zahl, ist ≤ 0 oder nicht endlich | `probe_fehler` | keine Wirkung |
| `typ === 'video'`, aber weder `format.duration` noch `stream.duration` ergibt eine endliche Zahl > 0 | `probe_fehler` | keine Wirkung |
| `tags.rotate` fehlt oder ist nicht numerisch | – (**kein** Fehler) | Rotation gilt als 0, Maße werden direkt übernommen |
| `typ === 'bild'`, Rohausgabe enthält eine Dauer | – (**kein** Fehler) | Dauer wird **ignoriert**, Ergebnis ist `null` |

## Nicht selbst entscheiden – STOPP und fragen
- **Ob die Rotation auch aus `side_data_list` gelesen werden muss, ist offen.** TK 9.4.8 nennt
  ausschließlich den Rotations-Tag `rotate`. Neuere `ffprobe`-Fassungen legen die Drehung jedoch
  häufig **nicht** mehr unter `tags.rotate` ab, sondern als `side_data_list`-Eintrag vom Typ
  „Display Matrix" mit einem Feld `rotation`. Trifft das auf das gebündelte Binary zu, bliebe jedes
  Hochkant-Video **unerkannt** – der Fehler wäre unsichtbar, weil Maße geliefert werden, nur die
  falschen. Das ist eine **empirische** Frage (was liefert genau unser Binary bei einem
  Handy-Hochkantvideo?) und keine Geschmacksfrage: **nicht raten, sondern ausprobieren lassen und
  fragen.** Bis zur Antwort wird ausschließlich `tags.rotate` gelesen, wie im Vertrag beschrieben.
- **Ob nicht-quadratische Pixel (SAR) in die Display-Maße einfließen, ist offen.** Der Vertrag nennt
  „Display-Maße", regelt aber nur die Rotation. Trägt eine Quelle ein Seitenverhältnis ≠ 1:1
  (`sample_aspect_ratio`), weichen codierte und tatsächlich angezeigte Breite voneinander ab.
  **Nicht selbst einbauen** – eine hier erfundene Umrechnung würde bei allen normalen Dateien
  (SAR 1:1) nichts ändern und bei den seltenen anderen still von der Vorschau abweichen. Fragen.
- **Verbot – kein `ffprobe`-Aufruf, kein Dateizugriff.** Diese Funktion bekommt ihre Daten
  ausschließlich als Parameter. Sonst wäre der ganze Zweck der Trennung (Testbarkeit ohne Binary)
  dahin.
- **Verbot – keine Ersatzwerte.** Kein `breite = 1920` „als Standard", kein `dauer = 0`, kein
  `dauer = 10` aus der Standard-Segmentdauer. Ein unbekannter Wert ist ein `probe_fehler`, kein
  erratener Wert – ein gespeicherter Ersatzwert wäre später nicht mehr von einer echten Messung zu
  unterscheiden.
- **Verbot – die Dauer nicht auf ganze Sekunden runden**, auch nicht „für die Anzeige". Die Anzeige
  formatiert selbst; gespeichert wird der genaue Wert.
- **Verbot – keine Sonderbehandlung für Aktions-Bilder.** „eine Sonderbehandlung von Aktions-Bildern
  (jedes importierte Bild ist ein gleichwertiges `Asset`)" besitzt der `media-service` ausdrücklich
  **nicht** (TK 9.4.1).
