### Issue M3-07: [media-service] Quelldatei ins Staging kopieren und atomar umbenennen

## Ziel (in einem Satz)
Eine ausgewählte Quelldatei liegt danach vollständig und unter ihrem endgültigen Namen im
Medienordner des Projekts – und zwar so, dass zu **keinem** Zeitpunkt eine halb geschriebene Datei
unter dem endgültigen Namen sichtbar ist.

## Modul & Datei
- Modul: `media-service` [P1] (Main)
- Datei: `src/main/media-service/import-datei.ts`
- Vertrag: Technisches Konzept **9.4.5** Schritte 1 und 3 (Quelle der Wahrheit), ergänzend **9.4.8**
  Punkte 1, 5, 8, 9
- Prozess/Speicher: P1, **D2** (`projects/<id>/media/`) – **kein** D1-Zugriff, **kein** D1-Lock

## Warum das im Gesamtsystem wichtig ist
Diese beiden Funktionen sind die einzige Stelle im ganzen Programm, an der Bytes in den
Medienbestand eines Projekts gelangen. Alles, was danach mit einem Medium geschieht – Vorschau,
Thumbnail, Normalisieren zur Render-Zeit –, setzt voraus, dass eine Datei im Medienordner
**fertig** ist, sobald sie dort unter ihrem endgültigen Namen auftaucht. Genau das stellt die
Zweiteilung her: erst eine Arbeitsdatei mit `.part`-Endung in einem Unterordner, dann **ein**
unteilbarer Rename. Wer das zusammenzieht und direkt auf den Zielnamen kopiert, erzeugt ein
Zeitfenster von Sekunden bis Minuten, in dem eine 2-GB-Videodatei unter ihrem gültigen Namen
halbfertig im Ordner liegt: Ein Absturz, ein Stromausfall oder ein abgezogener USB-Stick hinterlässt
dann eine Datei, die für den Reconcile (M3-11) „in Ordnung" aussieht (der Name passt zu einem
D1-Eintrag), aber beim Render mitten im Lauf zu einem `ffmpeg`-Fehler führt – also genau die
Fehlerklasse, die die gesamte Planung vermeiden will.

**⚠ Warum ein Fehler hier teuer ist (`risiko:datenverlust`):** Kopieren ist der langsamste Vorgang
des Programms und läuft auf Nutzerdaten, die es sonst nirgends gibt. Ein falsch gewählter
Staging-Ort (z. B. `os.tmpdir()`) verwandelt den vermeintlich atomaren Rename lautlos in
Kopieren-und-Löschen – auf derselben Maschine, mit denselben Tests, ohne Fehlermeldung. Der Schaden
zeigt sich erst beim Absturz eines echten Nutzers: eine halbe Datei mit gültigem Namen.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/media-service/import-datei.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis';

/** Ordnername des Staging-Ordners INNERHALB des Medienordners. */
export const STAGING_ORDNER = '.staging';

/** Endung der Arbeitsdatei, solange sie noch nicht fertig ist. */
export const PART_ENDUNG = '.part';

export async function kopiereInsStaging(
  quellPfad: string,
  zielOrdner: string,
  dateiname: string,
): Promise<Ergebnis<{ partPfad: string }, 'datei_nicht_gefunden' | 'kopier_fehler'>>;

export async function macheEndgueltig(
  partPfad: string,
  endPfad: string,
): Promise<Ergebnis<void, 'kopier_fehler'>>;
```

`STAGING_ORDNER` und `PART_ENDUNG` werden **aus dieser Datei exportiert**, weil der Ordnername
auch anderswo gebraucht wird: Der Reconcile (M3-11) importiert `STAGING_ORDNER`, damit er den Ordner
`.staging` nicht für eine verwaiste Mediendatei hält. `PART_ENDUNG` bleibt hier, weil der Reconcile
den gesamten Staging-Ordner leert und die Endung dafür nicht prüfen muss. Zwei getrennte Literale in zwei Dateien wären genau
die Doppelung, an der so etwas später auseinanderläuft.

## Fremde Funktionen, die du aufrufst
Diese Datei ruft **keine** projektfremde Funktion auf – sie arbeitet ausschließlich mit
`node:fs/promises` und `node:path` auf den drei übergebenen Zeichenketten. Der Vollständigkeit
halber, damit du sie **nicht** selbst nachbaust: Die Pfade, die du bekommst, stammen von der
Pfad-Autorität des `project-store` (Issue **#49**, `src/main/project-store/pfade.ts`) und werden
dir vom Aufrufer (M3-08) übergeben:

```ts
// #49 — src/main/project-store/pfade.ts (NICHT von dieser Datei aufgerufen, nur zur Einordnung)
export function medienOrdner(projektId: string): string
// absoluter Pfad `<Datenort>/projects/<projektId>/media` – reine String-Operation

export function loeseAssetPfad(projektId: string, dateiname: string): Ergebnis<string>
// absoluter Pfad der Asset-Datei, nur wenn er nachweislich innerhalb von medienOrdner liegt
```

## Eingang → Ausgang

| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `quellPfad` | absoluter Pfad der Quelldatei, wie ihn der Datei-Dialog geliefert hat | nicht leer; Existenz wird geprüft (s. Fehlerpfade); **wird nie verändert, verschoben oder gelöscht** |
| `zielOrdner` | absoluter Pfad des Medienordners des Projekts, geliefert von `medienOrdner(projektId)` (#49) | nicht leer; wird **unverändert** benutzt – diese Datei baut **keinen** Pfad aus `projektId` selbst zusammen |
| `dateiname` | endgültiger Dateiname **ohne** Verzeichnisanteil, Form `<uuid>.<ext_kleingeschrieben>` | darf keinen Pfadtrenner (`/`, `\`) und kein `..` enthalten → sonst `ungueltige_eingabe` |
| `partPfad` | Rückgabe von `kopiereInsStaging` | wird unverändert durchgereicht |
| `endPfad` | endgültiger Zielpfad, geliefert von `loeseAssetPfad(projektId, dateiname)` (#49) | wird **unverändert** benutzt |

Ausgang bei Erfolg (`kopiereInsStaging`): `{ partPfad }` mit
`partPfad = <zielOrdner>/.staging/<dateiname>.part`. Die Datei existiert dort **vollständig**.
Ausgang bei Erfolg (`macheEndgueltig`): `Ergebnis<void>` – die Datei liegt unter `endPfad`, der
`.part`-Pfad existiert nicht mehr.
Ausgang bei Fehler: Codes `datei_nicht_gefunden` und `kopier_fehler` (geschlossener Satz, s. u.)
sowie – für einen formal falschen `dateiname` – der generische Code `ungueltige_eingabe`, der über
`Ergebnis<T, F>` (`F | GenerischerFehlercode`) ohnehin zulässig ist und deshalb **nicht** in den
Typparameter geschrieben wird; `macheEndgueltig` kennt **nur** `kopier_fehler`.

**Der Ablauf, in den du eingebettet bist (TK 9.4.5) – du lieferst Schritt 1 und Schritt 3:**

| Schritt | Wer | Was |
|---|---|---|
| 1 | **du** (`kopiereInsStaging`) | Quelle → `media/.staging/<uuid>.<ext>.part` kopieren |
| 2 | M3-05/M3-06 | `ffprobe` **auf die `.part`-Datei**, mit Timeout |
| 3 | **du** (`macheEndgueltig`) | `fs.rename` `.part` → `media/<uuid>.<ext>` |
| 4 | M1-41 über den `project-store` | **[D1-Lock]** Asset anhängen und schreiben |

Dass `ffprobe` **zwischen** deinen beiden Funktionen läuft, ist der Grund für die Zweiteilung: Eine
Datei, die die Prüfung nicht besteht, darf den endgültigen Namen nie bekommen.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „Quelle → `media/.staging/<uuid>.<ext>.part` kopieren *(langsam, **außerhalb** des D1-Locks)*."
  (TK 9.4.5, Schritt 1) — Diese Datei fordert **kein** Lock an, hält keins und weiß von keinem.
- „`fs.rename` `.part` → `media/<uuid>.<ext>` — **atomar**, weil gleiche Partition (Staging liegt in
  `media/`; cross-volume-rename wäre copy+delete und **nicht** atomar)." (TK 9.4.5, Schritt 3)
  — **Der Staging-Ordner liegt deshalb INNERHALB von `media/`.** Ein Temp-Ordner des Betriebssystems
  (`os.tmpdir()`, `app.getPath('temp')`) liegt regelmäßig auf einer **anderen** Partition; `fs.rename`
  fällt dort auf `EXDEV` zurück bzw. wird von Hilfsbibliotheken still durch Kopieren-und-Löschen
  ersetzt – und ist dann **nicht mehr unteilbar**. Auf dem Entwicklungsrechner fällt das nicht auf,
  weil dort oft alles auf einem Laufwerk liegt.
- „Crash vor 3 → nur eine `.part`-Leiche; Crash nach 3 vor 4 → eine fertige Waise ohne D1-Eintrag.
  Beides räumt der Reconcile (9.4.7) auf." (TK 9.4.5) — **Beide Zustände sind eingeplant und
  erlaubt.** Diese Datei versucht **nicht**, sie zu verhindern oder nachträglich zu bereinigen.
- „**`media/` enthält im Normalbetrieb nur Dateien mit D1-Eintrag.** Abweichungen (nur durch
  Crash/`unlink`-Fehler möglich) bereinigt ausschließlich der Reconcile beim Start; **kein**
  periodisches Aufräumen im laufenden Betrieb." (TK 9.4.8, Punkt 8) — Du suchst also **nie** nach
  fremden `.part`-Dateien, löschst keine alten Staging-Reste und legst keinen Timer an.
- „**`dateiname` = `<uuid>.<ext_kleingeschrieben>`, ohne Verzeichnisanteil.** Auflösung immer per
  `path.join(projektMediaDir, dateiname)`. Nie der Originalname, nie ein gespeicherter OS-Pfad mit
  `\`/`/` — sonst ist das Projekt nicht zwischen Windows und macOS portabel." (TK 9.4.8, Punkt 1)
- „**Atomizität Import:** Kopie scheitert → kein D1-Eintrag. D1-Schreibfehler nach Rename → kein
  Halbzustand mit Referenz. (Reconcile bereinigt Waisen.)" (TK 9.4.8, Punkt 5)
- „**Kein zweites Lock.** Serialisierung von Operationen liefert die Queue (9.3), Serialisierung von
  D1-Schreibvorgängen das eine `project-store`-Lock. `media-service` führt **kein** eigenes Lock und
  **keine** OS-Dateisperren ein (Over-Engineering-Falle)." (TK 9.4.8, Punkt 9)
- „jede Normalisierung/Konvertierung der Quelldatei (die bleibt **roh**; das Normalisieren auf das
  Profil geschieht erst zur Render-Zeit, 9.2.4/9.2.6)" gehört **nicht** zum `media-service`
  (TK 9.4.1) — du kopierst **Bytes**, unverändert. Kein Umkodieren, kein Herunterskalieren, kein
  Entfernen von Metadaten, keine Kompression.
- Niemals `throw` – diese Datei läuft innerhalb eines Auftrags-Handlers, dessen Ergebnis über die
  IPC-Grenze reist (TK 9.1.1).

## Festlegungen, die du NICHT neu treffen musst (lokale Entscheidungen, hier bereits getroffen)
1. **Der Staging-Ordner wird bei Bedarf angelegt** (`fs.mkdir(..., { recursive: true })`), und zwar
   in `kopiereInsStaging` unmittelbar vor dem Kopieren. Grund: Ein frisch erstelltes Projekt hat
   noch keinen `.staging`-Ordner; ein separates Einrichtungs-Issue dafür wäre eine zusätzliche
   Reihenfolge-Abhängigkeit ohne Nutzen. `recursive: true` macht den Aufruf idempotent – ein
   bereits vorhandener Ordner ist **kein** Fehler.
2. **Kopiert wird mit `fs.promises.copyFile`**, nicht mit einem selbstgebauten Stream-Paar. Grund:
   `copyFile` nutzt auf beiden Zielplattformen die schnellsten Systemaufrufe (u. a.
   Copy-on-Write auf APFS) und hat keinen Fehlerpfad, in dem ein halb geschriebener Stream
   unbemerkt „fertig" meldet.
3. **Kein `COPYFILE_EXCL`, keine Vorab-Existenzprüfung des Ziels.** Der Zielname enthält eine frisch
   erzeugte UUID; eine Kollision im `.staging`-Ordner ist praktisch ausgeschlossen, und eine
   Existenzprüfung wäre eine klassische TOCTOU-Attrappe.
4. **Vor dem Rename wird die `.part`-Datei per `fsync` auf die Platte gezwungen** (Datei öffnen,
   `filehandle.sync()`, schließen – in `macheEndgueltig`, direkt vor `fs.rename`). Grund: Ohne
   `fsync` kann ein Absturz kurz nach dem Rename eine Datei hinterlassen, die **existiert** und einen
   **D1-Eintrag** hat, deren Inhalt aber unvollständig ist. Diesen Zustand erkennt der Reconcile
   **nicht** – Name und Eintrag passen ja zusammen. Er ist damit der einzige stille Schaden dieses
   Ablaufs, und `fsync` ist der einzige Weg, ihn auszuschließen.
5. **Das Verzeichnis wird NICHT zusätzlich per `fsync` synchronisiert.** Grund: Geht bei einem
   Absturz der Verzeichniseintrag des Renames verloren, liegt entweder noch die `.part`-Datei da
   (Leiche) oder die Datei fehlt, während der D1-Eintrag existiert – **beide** Zustände sind vom
   Reconcile abgedeckt (`.part` löschen bzw. `zustand = "fehlt"`). Es gibt hier also nichts zu
   schützen, was nicht ohnehin repariert wird.
6. **Kein Retry um `fs.rename`.** Grund: Ein gescheiterter Rename ist folgenlos – es entsteht kein
   D1-Eintrag, die zurückgebliebene `.part`-Datei räumt der Aufrufer (M3-08) weg, und der Nutzer kann
   den Import einfach wiederholen. Wiederholversuche gehören dorthin, wo ein Fehlschlag
   **dauerhaften** Schaden hinterlässt: ins Löschen (M3-09), wo eine nicht gelöschte Datei sonst für
   immer Platz belegt.
7. **Die Quelldatei wird nur gelesen.** Kein Verschieben, kein Löschen, kein Setzen von Zeitstempeln
   oder Rechten auf der Quelle – der Nutzer hat sein Original nach dem Import unverändert an
   seinem Platz: „**Medien werden in das Projekt kopiert** (nicht referenziert) – robust gegen
   verschobene/gelöschte Originale." (TK Abschnitt 5, Punkt 1)

## Fehlerpfade (vollständig)

| Situation | Code | Verhalten |
|---|---|---|
| `quellPfad` existiert nicht (Vorab-Prüfung per `fs.stat`) | `datei_nicht_gefunden` | nichts kopiert, kein Ordner angelegt; Meldung nennt den Quellnamen, **nicht** den ganzen Pfad |
| `quellPfad` verschwindet zwischen Prüfung und `copyFile` (`ENOENT`) | `datei_nicht_gefunden` | derselbe Code – die Vorab-Prüfung ersetzt das Abfangen **nicht**, sie ergänzt es (TOCTOU) |
| `quellPfad` zeigt auf ein Verzeichnis (`EISDIR`) | `kopier_fehler` | Meldung sagt ausdrücklich, dass ein Ordner keine Mediendatei ist |
| `dateiname` enthält `/`, `\` oder `..` | `ungueltige_eingabe` | **vor** jedem Dateisystemzugriff abbrechen; nichts angelegt. **Kein** `kopier_fehler`: Das ist ein Formfehler des Aufrufers, kein Dateisystemproblem – TK 9.4.9 führt `kopier_fehler` als „Disk-Fehler, Platzmangel" |
| `.staging` lässt sich nicht anlegen (`EACCES`, `EROFS`, `EPERM`) | `kopier_fehler` | nichts kopiert |
| Platte voll während der Kopie (`ENOSPC`) | `kopier_fehler` | die unvollständige `.part`-Datei bleibt liegen – **du räumst sie NICHT weg** (das tut der Reconcile, M3-11: der Aufrufer bekommt bei gescheiterter Kopie **keinen** `partPfad` und kann sie deshalb gar nicht entfernen); Meldung nennt Platzmangel als Ursache |
| Lese-/Schreibfehler während der Kopie (`EIO`, `EACCES`, `EPERM`) | `kopier_fehler` | wie oben |
| Quelle ist größer als der freie Platz, ohne dass `ENOSPC` kommt (z. B. Quota) | `kopier_fehler` | keine Sonderbehandlung, keine Vorab-Platzberechnung |
| `fsync` schlägt fehl (`macheEndgueltig`) | `kopier_fehler` | **kein** Rename ausführen – lieber eine `.part`-Datei zurücklassen als eine unvollständige Datei unter gültigem Namen. Du **löschst sie nicht**; der Aufrufer (M3-08) räumt sie weg, er kennt den `partPfad` |
| `fs.rename` schlägt fehl (`EXDEV`, `EPERM`, `EBUSY`, `EACCES`) | `kopier_fehler` | Ziel unverändert; die `.part`-Datei bleibt liegen und wird vom Aufrufer (M3-08) entfernt – **nicht** von dir. Bei `EXDEV` nennt die Meldung ausdrücklich, dass Staging und Ziel auf verschiedenen Partitionen liegen – das ist ein **Konstruktionsfehler**, kein Nutzerfehler |
| `partPfad` existiert nicht mehr (`ENOENT` beim Rename) | `kopier_fehler` | Ziel unverändert |

Es wird **kein** neuer Fehlercode eingeführt: `datei_nicht_gefunden` und `kopier_fehler` stammen aus
der Import-Liste TK 9.4.9 und sind in M3-02 (`ImportFehlercode`) deklariert, `ungueltige_eingabe` ist
einer der drei generischen Codes aus `ergebnis.ts` (#12).

## Nicht selbst entscheiden – STOPP und fragen
- **Den Staging-Ort nicht verlegen.** Nicht `os.tmpdir()`, nicht `app.getPath('temp')`, nicht der
  Projektordner-Wurzel, nicht T1 (der Render-Arbeitsbereich). Das Staging gehört **in** `media/` –
  begründet in den Invarianten. Wer es „sauberer" nach Temp legt, macht den Rename unbemerkt
  nicht-atomar.
- **Keine Aufräumarbeiten.** Weder eigene noch fremde `.part`-Dateien löschen, keinen Timer, keinen
  „Beim-Start-einmal-durchsehen"-Code. Aufräumen ist nicht deine Aufgabe: Sobald der Aufrufer einen
  `partPfad` in der Hand hat, räumt **er** (M3-08) die Datei weg – bis einschließlich eines
  gescheiterten Renames. Alles, was ein Absturz hinterlässt, räumt der Reconcile (M3-11) beim
  Projektstart.
- **Kein Lock, keine OS-Dateisperre, kein Mutex** – siehe Invariante TK 9.4.8 Punkt 9.
- **Keine Pfade selbst zusammenbauen.** `zielOrdner` und `endPfad` kommen fertig herein; du hängst an
  `zielOrdner` ausschließlich `STAGING_ORDNER` und `<dateiname><PART_ENDUNG>` an. Kein
  `ermittleDatenOrt()`, kein `projects/`-Literal, keine `projektId` in dieser Datei.
- **Kein D1-Zugriff.** Diese Datei kennt weder `Project` noch `Asset` noch `project.json`.
- **ECHTE OFFENE FRAGE – Fortschrittsmeldung beim Kopieren:** Das Kopieren einer 2-GB-Datei dauert
  spürbar lange und ist der einzige Teil des Imports, bei dem ein Fortschrittsbalken überhaupt Sinn
  ergäbe. `AusfuehrungsKontext.meldeFortschritt(prozent)` steht aber nur dem Auftrags-Handler
  (M3-08) zur Verfügung, nicht dieser Funktion, und `fs.copyFile` meldet **keinen** Zwischenstand –
  Fortschritt gäbe es nur über eine Stream-Kopie mit Zähler, also über eine **andere Signatur** (ein
  zusätzlicher Rückruf-Parameter) und einen anderen Kopiermechanismus. Das ist eine
  Schnittstellenentscheidung: **nicht** eigenmächtig einen Parameter ergänzen, **nicht** eigenmächtig
  auf Streams umbauen – **fragen**.

## Definition of Done
- [ ] `kopiereInsStaging` legt `<zielOrdner>/.staging/` bei Bedarf an und kopiert die Quelldatei
      **byte-identisch** nach `<zielOrdner>/.staging/<dateiname>.part`; ein Test vergleicht Größe und
      Inhalt von Quelle und `.part`-Datei.
- [ ] Der zurückgegebene `partPfad` ist genau
      `path.join(zielOrdner, STAGING_ORDNER, dateiname + PART_ENDUNG)` – ein Test prüft die
      Zeichenkette, nicht nur die Existenz.
- [ ] Die Quelldatei existiert nach dem Aufruf unverändert (Größe, Inhalt und Änderungsdatum
      gleich) – ein Test weist das ausdrücklich nach.
- [ ] Ein zweiter Aufruf von `kopiereInsStaging` mit bereits vorhandenem `.staging`-Ordner gelingt
      (Ordner-Anlage ist idempotent).
- [ ] `macheEndgueltig` bewegt die Datei nach `endPfad`; danach existiert `partPfad` **nicht** mehr
      und `endPfad` hat exakt die Größe der Quelldatei.
- [ ] Nach `macheEndgueltig` enthält der `.staging`-Ordner keine Datei mit diesem Namen mehr; der
      Ordner selbst bleibt bestehen (er wird **nicht** gelöscht).
- [ ] `quellPfad` auf eine nicht existierende Datei liefert `datei_nicht_gefunden` und legt **nichts**
      an (Test prüft, dass `.staging` in diesem Fall nicht entstanden ist, wenn es vorher fehlte).
- [ ] `dateiname` mit `/`, `\` oder `..` liefert `ungueltige_eingabe`, **ohne** einen
      Dateisystemzugriff auszulösen (Spion auf `fs.mkdir`/`fs.copyFile`).
- [ ] Ein simulierter `ENOSPC` beim Kopieren (Attrappe auf `node:fs/promises`) liefert
      `kopier_fehler`; die Funktion **löscht** die entstandene `.part`-Datei **nicht**.
- [ ] Ein simulierter Fehler bei `fsync` verhindert den Rename: `endPfad` existiert danach **nicht**,
      `partPfad` existiert noch, Rückgabe `kopier_fehler`.
- [ ] Ein simulierter `EXDEV` beim Rename liefert `kopier_fehler` mit einer Meldung, die die
      Partitionsgrenze benennt.
- [ ] Beide Funktionen werfen in **keinem** Fehlerfall (Test: jeder Fehlerpfad wird als aufgelöstes
      Promise mit `ok: false` geprüft, nicht als `rejects`).
- [ ] Die Datei importiert **kein** `electron`, **kein** `child_process`, **kein**
      `project-store`-Modul und **kein** `ffmpeg`; sie liest keine Konfiguration.
- [ ] Die Tests laufen ausschließlich auf einem echten Temp-Verzeichnis der Testumgebung bzw. mit
      Attrappen auf `node:fs/promises` – **kein** echter `project-store`, **kein** echtes Projekt,
      **kein** `ffprobe`.
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze).
- [ ] Keine Datei außerhalb von `src/main/media-service/import-datei.ts` **(+ zugehörige Testdatei)**
      geändert.
