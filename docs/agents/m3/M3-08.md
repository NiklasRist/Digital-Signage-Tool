### Issue M3-08: [media-service] importMedium zusammensetzen

## Ziel (in einem Satz)
Ein `import`-Auftrag führt die vorhandenen Bausteine in der festgelegten Reihenfolge aus, sodass am
Ende entweder eine vollständige Mediendatei **und** ihr Datensatz im Projekt stehen – oder keins von
beidem.

## Modul & Datei
- Modul: `media-service` [P1] (Main)
- Datei: `src/main/media-service/import-medium.ts`
- Vertrag: Technisches Konzept **9.4.3** (Operation `importMedium`), **9.4.5** (Import-Ablauf,
  Quelle der Wahrheit), ergänzend **9.4.4**, **9.4.8**, **9.4.9**
- Prozess/Speicher: P1, **D2** (Mediendatei), **D1** (Asset-Eintrag – ausschließlich über den
  `project-store`), Auftragsart `import` (Q1/Q2/Q3 führt der `auftrags-manager`)

## Warum das im Gesamtsystem wichtig ist
Dies ist der Ablauf, in dem die Reihenfolge über Datenverlust entscheidet. Jeder einzelne Baustein
ist harmlos; ihre **Anordnung** ist es, die garantiert, dass niemals ein Asset-Eintrag auf eine
unvollständige oder gar nicht existierende Datei zeigt. Wer hier die Schritte umstellt – etwa den
D1-Eintrag vor dem Rename schreibt, weil man „die ID ja schon hat", oder `ffprobe` erst nach dem
Rename laufen lässt, weil der endgültige Pfad hübscher aussieht –, erzeugt genau die Zustände, die
der Rest der Planung mit großem Aufwand ausschließt: ein Listenelement, das auf ein kaputtes Medium
zeigt, und ein Renderlauf, der nach zwölf Minuten mitten im Durchlauf abbricht. Der Fehler wäre auf
dem Entwicklungsrechner nicht zu sehen – er zeigt sich erst bei einem Absturz oder einer defekten
Quelldatei beim Kunden.

**⚠ Warum ein Fehler hier teuer ist (`risiko:datenverlust`):** Diese Funktion ist die einzige
Stelle, an der Bytes **und** Datensatz gemeinsam entstehen. Alle nachgelagerten Reparaturmechanismen
(Reconcile M3-11/M3-12, geführte Reparatur FA-19) können nur das aufräumen, was der hier
festgelegte Ablauf als Schadensbild **zulässt**. Erzeugt der Ablauf ein Schadensbild, das dort nicht
vorgesehen ist – etwa einen D1-Eintrag auf eine halb kopierte Datei –, findet es niemand mehr.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/media-service/import-medium.ts
import type { Auftrag } from '../../shared/contracts/auftrag';
import type { AusfuehrungsKontext, HandlerErgebnis } from '../auftrags-manager/dispatcher';
import type { ImportFehlercode } from './fehlercodes';

export async function importMedium(
  auftrag: Extract<Auftrag, { art: 'import' }>,
  kontext: AusfuehrungsKontext,
): Promise<HandlerErgebnis<ImportFehlercode>>;
```

**Der Typparameter ist `ImportFehlercode` (M3-02) – nicht weggelassen und nicht `string`.**
`HandlerErgebnis` ist über seinen Fehlercode generisch (#60, Muster von `Ergebnis<T, F>` aus #22);
`HandlerErgebnis<ImportFehlercode>` erlaubt im Fehlerfall genau die fünf fachlichen Codes aus
TK 9.4.9 **plus** die drei generischen (`ungueltige_eingabe`, `nicht_gefunden`,
`unbekannter_fehler`) – die kommen über `F | GenerischerFehlercode` automatisch dazu und werden in
`ImportFehlercode` nicht wiederholt. Der Compiler fängt damit hier ab, was TK 9.1.1 verhindern will:
„Geht der Code verloren, degradieren Reparatur-Modus, Wiederholen und der FAT32-Hinweis alle zu
„irgendwas ist schiefgelaufen"." Diese Funktion ist die **einzige** Stelle, an der der fachliche
Import-Code entsteht; der Dispatcher nimmt ihn als `HandlerErgebnis<string>` entgegen und reicht ihn
unverändert weiter, ohne ihn zu deuten.

**Keine `Ergebnis<T>`-Hülle.** Das ist kein Versehen: `import` ist ein **Auftrag**, keine
Instant-Operation. TK 9.1.1 trennt beide Ebenen ausdrücklich – „**Aufruf-Ergebnis:** Hat der *Aufruf*
funktioniert … **Auftrags-Ergebnis:** Wie ging der *Vorgang* aus (`RenderResult`, Export-Ergebnis …)?
Das reist **nicht** als Aufruf-Antwort, sondern über den **Auftrags-Zustand** (9.3)." Der Aufruf, den
die Oberfläche macht, ist `reiheEin('import', …)`; wie der Import ausging, transportiert das
`HandlerErgebnis` an den `auftrags-manager` und von dort in den Auftrags-Zustand.

**Ein `import` ist NIE `abgebrochen`.** Abbrechen gibt es laut FA-18 nur für einen laufenden
`render`. Diese Funktion liefert deshalb ausschließlich `erfolg` oder `fehlgeschlagen` – und wertet
kein Abbruch-Signal aus.

export type ImportFehlercode =

  | 'kopier_fehler' | 'speicher_fehler'
// Die drei generischen Codes stehen hier NICHT drin - sie kommen ueber F | GenerischerFehlercode.

// #60 — src/main/auftrags-manager/dispatcher.ts   (nur Typen, kein Aufruf)
export interface AusfuehrungsKontext {
  auftragId: string;
  meldeFortschritt: (prozent: number | null) => void;
}

export type HandlerErgebnis<F extends string = string> =
  | { status: 'erfolg'; ergebnis: unknown | null }
  | {
      status: 'fehlgeschlagen';
      fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown };

  | { status: 'abgebrochen' }

// unverändert nach `Auftrag.ergebnis` (TK 9.3.1) und deutet sie nicht.
// Der auftrags-manager nimmt das Ergebnis als HandlerErgebnis<string> entgegen und reicht Code,
// Meldung und `daten` unveraendert weiter - er verengt den Code NIE.

**Hinweis zu den Fehlercode-Typen:** `pruefeFormat`, `leseRohMetadaten` und `werteMetadatenAus`
verengen ihren Fehlercode-Typparameter jeweils auf **ein** Literal (`'format_nicht_unterstuetzt'`
bzw. `'probe_fehler'`), weil sie gar keinen anderen fachlichen Fehler erzeugen können. Die
vollständige Union `ImportFehlercode` (M3-02) entsteht erst **hier**, wo alle Zweige
zusammenlaufen. Erweitere die Signaturen der Bausteine deshalb **nicht** – fange ihre Codes ab und
gib sie unverändert weiter.

## Eingang → Ausgang

| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `auftrag.payload.projektId` | Ziel-Projekt; bestimmt den `media/`-Ordner (TK 9.4.3) | nicht leer; wird **nur** an `medienOrdner`/`loeseAssetPfad`/`fuegeAssetHinzu` weitergereicht |
| `auftrag.payload.quellPfad` | absoluter Pfad der Quelldatei, aus `öffneMedienDialog` (TK 9.4.3) | nicht leer; Existenz prüft `kopiereInsStaging` |
| `auftrag.auftragId` | Korrelation für Diagnose | wird nicht ausgewertet |
| `kontext.meldeFortschritt` | Fortschritts-Durchreiche | siehe STOPP – der Import meldet in v1 **keinen** Zwischenstand |

Ausgang bei Erfolg: `{ status: 'erfolg', ergebnis: <der fertige Asset aus Schritt 8> }` – **genau das
Objekt**, das an `fuegeAssetHinzu` übergeben wurde, unverändert und vollständig. Wörtlich aus
TK 9.4.3: „**Auftrags**-Ergebnis bei Erfolg: der fertige `Asset` (9.4.4) – er steht in
**`Auftrag.ergebnis`** (9.3.1) und erreicht die Oberfläche über den Auftrags-Zustand
(`queue:geaendert`/`holeStand`), **nicht** als `Ergebnis<T>` einer Aufrufantwort (9.1.1); der Aufruf
selbst ist `reiheEin('import', …)` → `Ergebnis<{ auftragId }>`." Der `auftrags-manager` legt den Wert
unverändert nach `Auftrag.ergebnis` – TK 9.3.1 zum Feld `ergebnis`: „fachliche Nutzdaten des Dienstes
oder `null`", „gesetzt bei `erfolg`: `import` → der fertige `Asset` (9.4.4)". **Kein** `null`, **kein**
Teilobjekt, **keine** Ersatzform wie `{ assetId }` – der Import ist die einzige Stelle, an der dieser
Datensatz entsteht, und ohne ihn „erführe die Oberfläche nie, was ein Auftrag hervorgebracht hat"
(TK 9.3.1).
Ausgang bei Fehler: `{ status: 'fehlgeschlagen', fehler: { code, meldung } }` mit einem Code aus dem
geschlossenen Satz TK 9.4.9: `datei_nicht_gefunden`, `format_nicht_unterstuetzt`, `probe_fehler`,
`kopier_fehler`, `speicher_fehler` – dazu die generischen `ungueltige_eingabe` (unbrauchbare Nutzlast,
unbrauchbarer Zielpfad, Formfehler aus `fuegeAssetHinzu`) und `nicht_gefunden` (`fuegeAssetHinzu`
findet das Projekt nicht mehr).

## Der Ablauf – verbindlich, in dieser Reihenfolge

| # | Schritt | Aufruf | Warum genau hier |
|---|---|---|---|
| 0 | Nutzlast prüfen | – | `projektId` und `quellPfad` nicht leer, beides Zeichenketten. „Der Main validiert jede eingehende Nutzlast – er vertraut dem Renderer **nicht**." (TK 9.1.1, Punkt 6). Fehlschlag → `ungueltige_eingabe`, **ohne jede Wirkung** |
| 1 | Format prüfen | `pruefeFormat(auftrag.payload.quellPfad)` (M3-03) | **Vor** dem Kopieren, weil sonst eine 2-GB-Datei kopiert wird, nur um danach abgewiesen zu werden. Liefert `typ` und die kleingeschriebene `endung` |
| 2 | Asset-Id erzeugen | `erzeugeId()` (#20) | Die UUID wird **jetzt** gebraucht, weil sie **im Dateinamen steckt**. Genau **ein** Aufruf – dieselbe ID landet im Dateinamen und in `Asset.id` |
| 3 | Pfade auflösen | `medienOrdner(projektId)` und `loeseAssetPfad(projektId, dateiname)` (#49) | Vor dem Kopieren, damit ein unbrauchbarer Pfad **vor** jedem Dateisystemzugriff auffällt. `dateiname = <assetId>.<endung>` |
| 4 | Kopieren | `kopiereInsStaging(quellPfad, medienOrdner, dateiname)` (M3-07) | Der langsame Teil, **außerhalb** jedes Locks. Ergebnis: `partPfad` |
| 5 | `ffprobe` | `leseRohMetadaten(partPfad)` (M3-05) | **Auf der `.part`-Datei**, nicht auf der Quelle: geprüft wird die Datei, die tatsächlich im Projekt landet. Eine Kopie kann beschädigt sein, die Quelle nicht mehr erreichbar |
| 6 | Auswerten | `werteMetadatenAus(roh, typ)` (M3-06) | Rotationskorrektur und Dauer; noch **vor** dem Rename, damit eine Datei, deren Metadaten unbrauchbar sind, den endgültigen Namen nie bekommt |
| 7 | Endgültig umbenennen | `macheEndgueltig(partPfad, endPfad)` (M3-07) | Der eine unteilbare Schritt. **Ab hier** ist die Datei für alle sichtbar |
| 8 | `Asset` bauen | – | Reines Zusammensetzen, kein IO (Felder s. u.) |
| 9 | In D1 anhängen | `fuegeAssetHinzu(projektId, asset)` (M1-41) | **Zuletzt**, unter dem einen D1-Schreib-Lock (Millisekunden), mit **Sofort-Flush** – erst wenn der Eintrag auf der Platte steht, meldet dieser Auftrag Erfolg. Das erledigt M1-41 selbst; du stößt **keinen** Flush an. Erst jetzt existiert das Medium für die Oberfläche |

**Der `Asset` aus Schritt 8 – Feld für Feld (TK 9.4.4):**

| Feld | Wert |
|---|---|
| `id` | die UUID aus Schritt 2 – **dieselbe**, die im Dateinamen steht |
| `typ` | `typ` aus Schritt 1 |
| `dateiname` | `<assetId>.<endung>`, Endung **kleingeschrieben**, **ohne** Verzeichnisanteil |
| `originalname` | `path.basename(auftrag.payload.quellPfad)` **mit** Endung – „ursprünglicher Dateiname, nur für die UI-Anzeige" (TK 9.4.4) |
| `maße` | aus Schritt 6 |
| `dauer` | aus Schritt 6 (Video: Sekunden mit 3 Dezimalstellen; Bild: `null`) |
| `importdatum` | `new Date().toISOString()` – **eine** Zeitabfrage, in Schritt 8 |
| `zustand` | `'ok'` – „fehlt" setzt ausschließlich der Reconcile (TK 9.4.4/9.4.7) |

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Der Ablauf laut TK 9.4.5, vollständig:
  1. „Quelle → `media/.staging/<uuid>.<ext>.part` kopieren *(langsam, **außerhalb** des D1-Locks)*."
  2. „`ffprobe` auf die `.part`-Datei, **mit Timeout** *(außerhalb des Locks)*."
  3. „`fs.rename` `.part` → `media/<uuid>.<ext>` — **atomar**, weil gleiche Partition (Staging liegt
     in `media/`; cross-volume-rename wäre copy+delete und **nicht** atomar)."
  4. „**[D1-Lock]** Asset in D1 anhängen, danach **Sofort-Flush** (9.5.4) – der Auftrag meldet
     Erfolg erst, wenn der Eintrag auf der Platte steht *(Millisekunden)*. Scheitert der Flush →
     `speicher_fehler` (9.4.9)."
- „**`dateiname` = `<uuid>.<ext_kleingeschrieben>`, ohne Verzeichnisanteil.** Auflösung immer per
  `path.join(projektMediaDir, dateiname)`. Nie der Originalname, nie ein gespeicherter OS-Pfad mit
  `\`/`/` — sonst ist das Projekt nicht zwischen Windows und macOS portabel." (TK 9.4.8, Punkt 1)
  — **Die `uuid` im Dateinamen IST die `Asset.id`.** Es gibt keine zweite ID und keinen zweiten
  Namensbestandteil; der Reconcile schließt aus dem Dateinamen auf den Eintrag.
- „Crash vor 3 → nur eine `.part`-Leiche; Crash nach 3 vor 4 → eine fertige Waise ohne D1-Eintrag.
  Beides räumt der Reconcile (9.4.7) auf." (TK 9.4.5)
- „**Atomizität Import:** Kopie scheitert → kein D1-Eintrag. D1-Schreibfehler nach Rename → kein
  Halbzustand mit Referenz. (Reconcile bereinigt Waisen.)" (TK 9.4.8, Punkt 5)
- Der `media-service` besitzt **nicht**: „eine Sonderbehandlung von Aktions-Bildern (jedes importierte
  Bild ist ein gleichwertiges `Asset`); jede Normalisierung/Konvertierung der Quelldatei (die bleibt
  **roh**; das Normalisieren auf das Profil geschieht erst zur Render-Zeit, 9.2.4/9.2.6)."
  (TK 9.4.1)
- „Alle D1-Schreibvorgänge delegiert er an den `project-store` (dessen einziges Schreib-Lock, 9.3.5).
  Auch die **Pfadauflösung** (welcher absolute Pfad zu `projektId`+`dateiname` gehört) kommt vom
  `project-store` (Pfad-Autorität, 9.5.7) – `media-service` liest/schreibt die Bytes, kennt das
  Ordner-Layout aber nicht selbst." (TK 9.4.1)
- „**Kein zweites Lock.** Serialisierung von Operationen liefert die Queue (9.3), Serialisierung von
  D1-Schreibvorgängen das eine `project-store`-Lock. `media-service` führt **kein** eigenes Lock und
  **keine** OS-Dateisperren ein (Over-Engineering-Falle)." (TK 9.4.8, Punkt 9)
- „**`media/` enthält im Normalbetrieb nur Dateien mit D1-Eintrag.** Abweichungen (nur durch
  Crash/`unlink`-Fehler möglich) bereinigt ausschließlich der Reconcile beim Start; **kein**
  periodisches Aufräumen im laufenden Betrieb." (TK 9.4.8, Punkt 8)
- „**Fehlercodes sind ein geschlossener, typisierter Satz** … **Eine rohe Exception-Meldung wird nie
  zum Code.**" (TK 9.1.1, Punkt 3) — Ein gefangener Ausnahmetext darf in die `meldung`, **nie** in
  den `code`.
- „Der Main validiert jede eingehende Nutzlast – er vertraut dem Renderer **nicht**. Ungültige
  Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten." (TK 9.1.1, Punkt 6)
- Niemals `throw` – diese Funktion ist der Handler eines Auftrags; eine Ausnahme würde die
  Warteschlange stehen lassen (#60 fängt sie zwar ab, aber der Code ginge verloren und würde zu
  `unbekannter_fehler`).

## Fehlerpfade (vollständig) – mit Aufräumen

| Situation | Code | Aufräumen | Verhalten |
|---|---|---|---|
| `projektId` oder `quellPfad` fehlt/leer/kein String | `ungueltige_eingabe` | – | Abbruch vor jedem IO |
| Schritt 1: Endung nicht in `FORMAT_WHITELIST` | `format_nicht_unterstuetzt` | – | nichts wurde angelegt; Meldung nennt die erlaubten Formate |
| Schritt 3: `loeseAssetPfad` liefert `ok: false` | `ungueltige_eingabe` | – | nichts wurde angelegt (kann nur bei beschädigten Daten passieren) |
| Schritt 4: Quelldatei weg | `datei_nicht_gefunden` | – | keine `.part` entstanden |
| Schritt 4: Platte voll / IO-Fehler | `kopier_fehler` | – (der Reconcile räumt, M3-11) | kein D1-Eintrag. Du kannst hier gar nicht aufräumen: `kopiereInsStaging` liefert den `partPfad` **nur im Erfolgsfall**, und ihn selbst zusammenzubauen wäre eine zweite Pfadwahrheit (verboten, s. STOPP) |
| Schritt 5: `ffprobe` liefert nichts oder läuft in den Timeout | `probe_fehler` | **`.part` entfernen** | kein D1-Eintrag, kein Rename |
| Schritt 6: Metadaten unbrauchbar (keine Maße) | `probe_fehler` | **`.part` entfernen** | kein D1-Eintrag, kein Rename |

| Schritt 9: `fuegeAssetHinzu` meldet `speicher_fehler` (Sofort-Flush **nach** dem Rename gescheitert) | `speicher_fehler` | **NICHTS** – die fertige Datei bleibt als **Waise** liegen | ausdrücklich so gewollt: „Crash nach 3 vor 4 → eine fertige Waise ohne D1-Eintrag. Beides räumt der Reconcile (9.4.7) auf." (TK 9.4.5). Die Waise **hier** zu löschen wäre falsch: der D1-Schreibfehler kann ein voller Datenträger sein, und dann hätte der Nutzer eine erfolgreich kopierte Datei verloren, die beim nächsten Versuch nur noch einmal kopiert werden müsste |
| Schritt 9: `fuegeAssetHinzu` meldet `nicht_gefunden` (kein aktives Projekt geladen, oder `projektId` ist nicht dessen id – der Nutzer hat während des Imports das Projekt gewechselt) | `nicht_gefunden` | **NICHTS** – Waise wie oben | Code **unverändert** durchreichen, **nicht** auf `speicher_fehler` oder `unbekannter_fehler` umdeuten |
| Schritt 9: `fuegeAssetHinzu` meldet `ungueltige_eingabe` (doppelte `id`, `dateiname` mit Verzeichnisanteil) | `ungueltige_eingabe` | **NICHTS** – Waise wie oben | Das ist ein **Programmierfehler in dieser Funktion** (die `id` kommt aus einem einzigen `erzeugeId()`, der `dateiname` wird hier gebaut) – die Meldung nennt ihn als solchen, statt ihn dem Nutzer als Dateiproblem zu erklären |
| Unerwartete Ausnahme in einem beliebigen Schritt | `unbekannter_fehler` | **`.part` entfernen**, falls Schritt 4 bereits erfolgreich war | fangen, Text in die `meldung`, **kein** `throw` |

**Regel zum Aufräumen der eigenen `.part`-Datei:** Ab dem Moment, in dem `kopiereInsStaging` einen
`partPfad` geliefert hat, bis **einschließlich** eines gescheiterten Renames (Schritt 7) gehört die
`.part`-Datei dir: Scheitert einer dieser Schritte, wird sie über `entferneDatei(partPfad)` (M3-09)
entfernt. **Vorher** (gescheiterte Kopie) gibt es keinen `partPfad` – dort räumt der Reconcile
(M3-11). **Nachher** (Schritt 9) gibt es keine `.part`-Datei mehr, sondern eine fertige Waise, und
die bleibt ausdrücklich liegen. M3-07 räumt in **keinem** Fall selbst auf; es gibt also genau eine
Stelle, die es tut.
Begründung für M3-09 statt eines direkten `fs.unlink`: Unter Windows hängt der Handle des
gerade beendeten `ffprobe` gelegentlich Millisekunden nach (`EBUSY`/`EPERM`) – exakt die Falle, für
die M3-09 den Retry mitbringt. Eine zweite Löschroutine im selben Modul wäre die Doppelung, die
M3-09 verhindern soll.

**Das Aufräumen darf den gemeldeten Fehler NICHT verändern.** Gelingt es nicht, bleibt eine
`.part`-Leiche liegen (Reconcile), und gemeldet wird trotzdem der **ursprüngliche** Fehlercode –
niemals `datei_fehler`. Der Nutzer soll erfahren, warum sein Import scheiterte, nicht warum eine
Zwischendatei nicht wegging.

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – für den fertigen `Asset` keinen zweiten Transportweg bauen.** Er reist im Feld
  `ergebnis` des `HandlerErgebnis` (s. „Eingang → Ausgang") und von dort über den Auftrags-Zustand.
  Also: **kein** eigener IPC-Kanal, **kein** eigenes Ereignis `media:assetHinzugefuegt`, **kein**
  direkter Push an den Renderer, **kein zusätzliches Feld** in `HandlerErgebnis` (fremde Datei,
  Regel E). Den **Typparameter** `HandlerErgebnis<ImportFehlercode>` zu setzen ist damit **nicht**
  gemeint – das ist die vorgesehene Verwendung des Typs (#60), keine Erweiterung.
- **Verbot – kein Sammelmodus.** Wer eine Mehrfachauswahl in N Aufträge zerlegt, ist **entschieden**:
  die Oberfläche reiht für jeden gewählten Pfad einen eigenen Auftrag ein (`reiheEin('import', …)`
  je Pfad); das zugehörige Issue liegt im Oberflächen-Meilenstein. Grund: Die Warteschlange arbeitet
  die Dateien dann einzeln und sichtbar ab, und jeder Fehlschlag ist einzeln wiederholbar (FA-17) –
  ein Sammel-Auftrag wäre unteilbar. **Diese Funktion verarbeitet genau eine Datei**, akzeptiert
  **kein** Array und baut **keine** Schleife über mehrere Quellpfade.
- **ECHTE OFFENE FRAGE – Fortschritt.** `kontext.meldeFortschritt` steht bereit, aber der einzige
  lange Schritt (die Kopie) meldet keinen Zwischenstand (M3-07, offener Punkt dort). Ob der Import
  in v1 gar keinen Fortschritt meldet (`fortschritt` bleibt `null`) oder grobe Marken zwischen den
  Schritten setzt, ist Verhalten der Oberfläche – **nicht raten**. Ohne Antwort: **kein** Aufruf von
  `meldeFortschritt`.
- **Die Reihenfolge der neun Schritte nicht „optimieren".** Insbesondere: `ffprobe` läuft auf der
  `.part`-Datei **vor** dem Rename, und `fuegeAssetHinzu` läuft **nach** dem Rename. Beides ist
  keine Geschmacksfrage – begründet in den Invarianten.
- **Die Quelldatei bleibt roh.** Keine Konvertierung, keine Normalisierung, kein Herunterskalieren,
  kein Neukodieren, kein Strippen von Metadaten, keine Thumbnail-Erzeugung, keine Kompression. Das
  Normalisieren geschieht erst zur Render-Zeit (TK 9.4.1). Wer hier „schon mal auf 1920×1080
  bringt", zerstört das Original unwiederbringlich und nimmt dem Render-Profil seine einzige
  Quelle.
- **Keine Sonderbehandlung von Aktions-Bildern.** Ein Bild, das später eine Aktion bebildert, ist
  ein ganz gewöhnlicher `Asset` (TK 9.4.1). Kein zweiter Ordner, kein Flag, keine abweichende
  Prüfung.
- **Kein direkter Schreibzugriff auf `project.json`**, kein `fs`-Zugriff auf D1, kein Anfordern des
  D1-Locks. Der einzige Weg in D1 ist `fuegeAssetHinzu` (M1-41).
- **Kein eigenes Ordner-Layout.** Kein `path.join(datenOrt, 'projects', …)`, kein `'media'`-Literal.
  Pfade kommen ausschließlich von #49.
- **Waisen nicht reparieren.** Schlägt Schritt 9 fehl, bleibt die Datei liegen. Kein
  Wiederholversuch für den D1-Schreibvorgang, kein Zurückrollen des Renames, kein Löschen der
  fertigen Datei.
- **Kein automatischer erneuter Versuch des ganzen Imports.** Wiederholen ist eine ausdrückliche
  Nutzeraktion (FA-17), gesteuert vom `auftrags-manager`.
- **Keine Existenzprüfung des Ziels vor dem Rename**, kein „Datei schon vorhanden?"-Zweig: Der
  Zielname enthält eine frisch erzeugte UUID.
