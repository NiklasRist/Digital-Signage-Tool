### Issue M3-16: [media-service] Dialog-Kanal verdrahten

## Ziel (in einem Satz)
Der native Datei-Dialog des `media-service` wird als IPC-Kanal beim `ipc-gateway` angemeldet, sodass
die Oberfläche ihn überhaupt öffnen kann – und zwar als einziger Kanal dieses Moduls.

## Modul & Datei
- Modul: `media-service` [P1] (Main)
- Datei: `src/main/media-service/ipc-verdrahtung.ts`
- Zusätzlich erlaubte Datei: `src/shared/contracts/kanaele.ts` – **nur** für den Eintrag unter
  `media`. Die Registry (#25) wird „von M2–M7 **iterativ ergänzt**"; dieses Issue ist der Ergänzer
  für den `media-service`. **Kein anderes M3-Issue fasst `kanaele.ts` an.**
- Vertrag: Technisches Konzept **9.1.1** (IPC-Konventionen – Quelle der Wahrheit), **9.4.3**
  (Operation `öffneMedienDialog`), ergänzend **9.3.2** und **9.3.4** (Abgrenzung Auftrag ↔ Instant)
- Prozess/Speicher: P1; **kein** eigener Speicher, **kein** Dateizugriff, **kein** D1-Zugriff –
  diese Datei reicht nur durch.
- IPC-Kanal: `media:öffneMedienDialog` (Instant, mit Ergebnis-Hülle). **Kein** Ereignis.

## Warum das im Gesamtsystem wichtig ist
Der Wrapper aus #23 registriert von sich aus **nichts**, und `öffneMedienDialog` (M3-04) ist eine
gewöhnliche Main-Funktion ohne Kanalbezug. Ohne dieses Issue gibt es also keinen Weg, aus der
Oberfläche einen Datei-Dialog zu öffnen – und damit keinen Weg, überhaupt ein Medium zu importieren
(FA-01). Genau dieses Muster – fertige Funktionen ohne Anbindung – war im M2-Prüflauf der häufigste
kritische Befund.

Zwei lokale Entscheidungen sind hier teuer. Erstens die **Validierung**: Diese Datei ist eine der
Stellen, an denen Renderer-Daten in den Main gelangen; auch bei einer Operation ohne Nutzlast muss
die Prüffunktion existieren und sich richtig verhalten, sonst wird der Kanal entweder unbenutzbar
(weil eine mitgeschickte `undefined`-Nutzlast als ungültig gilt) oder die Prüfstelle wird im ganzen
System zur reinen Formalie, die niemand mehr ernst nimmt. Zweitens die **Abgrenzung**: Import und
Löschen dürfen hier **keinen** Kanal bekommen. Wer sie „der Symmetrie halber" mitregistriert, schafft
einen zweiten Weg an der Warteschlange vorbei – und damit an der seriellen Ordnung, die der einzige
Sperr-Mechanismus des Systems ist. Ein Import, der direkt läuft, kann parallel zu einem Render eine
Datei anfassen; genau diese Kollision schließt die Queue aus.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/media-service/ipc-verdrahtung.ts

export function verdrahteMedienIPC(): void
// registriert GENAU EINEN Kanal – media:öffneMedienDialog – über den Wrapper aus #23,
// mit einer eigenen Validierungsfunktion. Kein Ereignis, kein zweiter Kanal.
```

Ergänzung in der Kanal-Registry (#25) – **hier** entsteht der Name, nirgends sonst:

```ts
// src/shared/contracts/kanaele.ts (Ergänzung, bestehende Einträge bleiben unverändert)
export const KANAELE = {
  // … bestehende Einträge (z. B. queue: { … }) unverändert lassen …
  media: {
    oeffneMedienDialog: 'media:öffneMedienDialog',
  },
} as const
```

**Der Kanal-String trägt den Umlaut, der Objektschlüssel nicht.** Der String folgt der
Kanalbenennung `<modul>:<operation>` mit der Operation, wie sie im Vertrag heißt (TK 9.4.3:
`öffneMedienDialog`) – der Vertrag führt selbst umlauthaltige Kanäle als Beispiel
(`vorlagen:löscheVorlage`, TK 9.1.1 Punkt 4). Der **Schlüssel** bleibt ASCII, weil er im Quelltext
beider Prozesse getippt und importiert wird und ein Umlaut dort nur Kodierungsfallen einlädt. Beide
Schreibweisen stehen genau einmal, an dieser Stelle.

### Fremde Funktionen, die du benutzt
Der umsetzende Agent sieht die anderen Issues **nicht**; deshalb hier alles ausgeschrieben:

```ts
// #23 – ipc-gateway, generischer Wrapper (src/main/ipc-gateway/registriere-handler.ts)
//       registriert von sich aus NICHTS
export function registriereHandler<T, F extends string>(
  kanal: string,
  validiere: (nutzlast: unknown) => Ergebnis<unknown, 'ungueltige_eingabe'> | { ok: true; wert: unknown },
  ausfuehren: (validierteNutzlast: unknown) => Promise<Ergebnis<T, F>>,
): void
// 1. ruft validiere(); bei ok:false → sofort Ergebnis mit code 'ungueltige_eingabe',
//    OHNE ausfuehren() aufzurufen (keine Wirkung auf Daten)
// 2. ruft ausfuehren() in try/catch; jede unerwartete Ausnahme → 'unbekannter_fehler',
//    intern protokolliert, KEIN Stacktrace im Rückgabewert
// 3. gibt das Ergebnis von ausfuehren() unverändert zurück

// M3-04 – media-service, nativer Datei-Dialog (src/main/media-service/dialog.ts)
export async function öffneMedienDialog(): Promise<Ergebnis<{ pfade: string[] }>>
// Nutzer wählt Dateien → pfade = Array absoluter Quellpfade
// Nutzer bricht ab      → ok: true mit pfade = [] (Abbruch ist KEIN Fehler)
```

### Was die Validierungsfunktion prüft (verbindlich)
`öffneMedienDialog` hat **keine** Nutzlast. Die Prüffunktion entfällt deshalb **nicht** – der Wrapper
verlangt sie, und sie ist die Stelle, an der festgehalten wird, dass hier nichts erwartet wird. Sie
verhält sich so:

- Sie nimmt **jede** Eingabe entgegen und liefert `{ ok: true, wert: undefined }`.
- Eine trotzdem übergebene Nutzlast (etwa `undefined`, `null` oder ein versehentlich mitgeschicktes
  Objekt) wird **ignoriert**, **nicht** als Fehler gemeldet und **nicht** an `öffneMedienDialog`
  weitergegeben – die Funktion hat keinen Parameter.
- Sie ist eine echte Funktion, kein `null`, kein Cast, kein `() => nutzlast as any`.

**Begründung für „ignorieren statt ablehnen":** Genau so ist der nutzlastfreie Kanal
`queue:holeStand` festgelegt („keine Nutzlast erwartet; eine trotzdem übergebene wird ignoriert,
**nicht** als Fehler gemeldet"). Zwei verschiedene Regeln für zwei nutzlastfreie Kanäle wären eine
Falle für jeden, der den Renderer-Aufruf schreibt; außerdem schickt eine typische
`invoke(kanal)`-Aufrufform ohnehin `undefined` mit, und ein strenges Ablehnen würde den Kanal auf
manchen Aufrufwegen unbenutzbar machen, ohne dass irgendetwas dadurch sicherer wird: Es gibt keine
Nutzlast, die Schaden anrichten könnte.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – (`verdrahteMedienIPC` hat kein Argument) | einmalige Verdrahtung beim Programmstart | ein zweiter Aufruf würde denselben Kanal doppelt registrieren – s. STOPP |
| Nutzlast auf `media:öffneMedienDialog` | keine erwartet | eine übergebene wird ignoriert |

Ausgang: `verdrahteMedienIPC` liefert nichts (`void`); Wirkung ist **ein** registrierter Kanal. Der
**Kanal** liefert das unveränderte Ergebnis von `öffneMedienDialog`: `Ergebnis<{ pfade: string[] }>`.
Ausgang bei Fehler: `unbekannter_fehler` (unerwartete Ausnahme, vom Wrapper aus #23 übersetzt) sowie
jeder Code, den `öffneMedienDialog` selbst liefert. Diese Datei erzeugt **keine** eigenen Codes.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operation, wörtlich (TK 9.4.3):
  ```
  öffneMedienDialog() → Ergebnis<{ pfade: string[] }>     // Instant
  ```
  und dazu die Tabelle: „Nutzer wählt Dateien | `pfade` = Array absoluter Quellpfade" ·
  „Nutzer bricht ab | `ok: true` mit `pfade = []` – Abbruch ist **kein** Fehler". Diese Datei macht
  aus einem Abbruch also **niemals** einen Fehler und filtert ein leeres Array **nicht** weg.
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Sie wird hier **unverändert durchgereicht** – nicht ausgepackt, nicht vereinfacht, nicht in eine
  Exception verwandelt. Begründung aus demselben Abschnitt: Renderer und Main sind „**getrennte
  Prozesse**"; über die Grenze geworfen gilt: „**Fehlerklasse und eigene Felder wie `code` sind
  verloren** – übrig ist Text."
- „**Kanalbenennung `<modul>:<operation>`** – z. B. `media:importMedium`, `project:setzeTrim`,
  `vorlagen:löscheVorlage`. Ereignisse (Main → Renderer) heißen `<modul>:<ereignis>`, z. B.
  `queue:geaendert`, `render:fortschritt`. Damit erfindet niemand eigene Kanalnamen." (TK 9.1.1,
  Punkt 4) – daraus folgt das Präfix `media:` für dieses Modul.
- „**Der Main validiert jede eingehende Nutzlast** – er vertraut dem Renderer **nicht**. Ungültige
  Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten. Ein Fehler im Renderer darf D1
  niemals beschädigen." (TK 9.1.1, Punkt 6)
- „**Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code. Es gibt keine Operation,
  die „einfach nichts" zurückgibt und auf Gelingen hofft." (TK 9.1.1, Punkt 7)
- „**Unerwartete Ausnahmen fängt das Gateway** und übersetzt sie in `unbekannter_fehler` (intern
  protokolliert). Die App stürzt nicht ab, und **kein Stacktrace** gelangt in die Oberfläche."
  (TK 9.1.1, Punkt 8) – das erledigt der Wrapper aus #23; diese Datei baut **kein** eigenes
  `try/catch` daneben.
- **Die Abgrenzung, wörtlich:** „`import`, `loeschen`, `render` und `export` werden damit **nicht**
  als direkte Request/Response-Operationen aufgerufen, sondern über `reiheEin` eingereiht; ihr
  Fach-Ergebnis (`erfolg`/`fehlgeschlagen` samt Fachfehlercode) kommt über den Auftrags-Zustand."
  (TK 9.3.4) – deshalb entstehen hier **keine** Kanäle `media:importMedium` oder
  `media:löscheMedium`, obwohl TK 9.1.1 Punkt 4 `media:importMedium` als *Namens*beispiel führt. Das
  Beispiel erklärt die Benennung, nicht die Aufrufart.
- Warum ausgerechnet der Dialog ein Kanal ist, wörtlich: „**Nicht** über die Queue laufen
  **Instant-Operationen** (Millisekunden, reine D1-Schreibvorgänge): Aktion anlegen/bearbeiten, Liste
  umsortieren, Trim setzen, **Aktion** löschen, Datei-Dialog öffnen." (TK 9.3.2)
- „**Nur Instant-Aufrufe tragen die Hülle.**" (TK 9.1.1, Punkt 2) – der Dialog ist eine
  Instant-Operation und trägt sie folglich.
- **ENTSCHIEDEN – hier steckt keine Fachlogik und keine Fensterreferenz.** Diese Datei öffnet keinen
  Dialog, kennt keinen Formatfilter, liest `FORMAT_WHITELIST` nicht und fasst `BrowserWindow` nicht
  an. Sie registriert einen Kanal und ruft `öffneMedienDialog` auf. Alles Weitere gehört M3-04.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| irgendeine Nutzlast wird auf dem Kanal mitgeschickt | – (kein Fehler) | ignoriert; `öffneMedienDialog()` wird ohne Argument aufgerufen |
| `öffneMedienDialog` liefert `ok: true` mit `pfade: []` (Nutzer hat abgebrochen) | – (kein Fehler) | unverändert durchreichen; **kein** Umdeuten in `nicht_gefunden` oder `ungueltige_eingabe` |
| `öffneMedienDialog` liefert regulär `ok: false` | genau dieser Code | unverändert durchreichen – **kein** Umschreiben, **kein** Vereinheitlichen |

Fehlercodes werden **nicht erfunden**: „**Fehlercodes sind ein geschlossener, typisierter Satz** …
**Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1, Punkt 3)

## Nicht selbst entscheiden – STOPP und fragen
- **Wann wird `verdrahteMedienIPC()` beim Programmstart gerufen, und wer ruft es?** M0/M1 haben dafür
  **keine** Stelle vorgesehen: #3 (Main-Bootstrap) kennt nur App-Lifecycle und `BrowserWindow`, und
  kein Issue führt eine zentrale „Verdrahtungs"-Funktion, in die sich Module eintragen. Dieselbe
  Frage steht bereits bei der Queue-Verdrahtung (#71) offen und muss **einmal** beantwortet werden,
  nicht zweimal verschieden. Sie hat Folgen: Zu spät registriert, läuft der erste Klick auf
  „Medien hinzufügen" ins Leere; und eine doppelte Registrierung desselben Kanals ist in Electron ein
  Fehler – ob ein zweiter Aufruf abgewiesen, ignoriert oder als Programmierfehler gemeldet wird,
  gehört zur selben Antwort. **Nicht selbst festlegen** – und den Aufruf **nicht** eigenmächtig in
  eine fremde Datei (`main.ts`, Bootstrap) einbauen; das wäre zugleich eine Änderung außerhalb des
  erlaubten Dateibereichs (Regel E).
- **Verbot – keine Kanäle für Import und Löschen.** Weder `media:importMedium` noch
  `media:löscheMedium`, auch nicht „nur zum Testen". Sie laufen über `reiheEin` der
  Auftragsverwaltung (TK 9.3.4). Ein direkter Kanal wäre ein zweiter Weg an der seriellen Ordnung
  vorbei – dem einzigen Sperr-Mechanismus des Systems.
- **Verbot – keine Kanäle für den Aufräumlauf und die offenen Löschungen.** `reconcile` (M3-14) und
  die `pendingDeletions` sind main-intern (TK 9.4.7 bzw. TK 9.3: „**main-intern** (kein
  IPC-Kanal)"). Kein `media:reconcile`, kein Lesezugang zu Q2.
- **Verbot – die Hülle nicht anfassen.** Der Rückgabewert wird **unverändert** weitergereicht: kein
  Auspacken von `wert`, kein `throw` im Fehlerfall, kein Umschreiben von Codes, keine zusätzlichen
  Felder, kein Entfernen eines vorhandenen `daten`-Feldes, kein Umdeuten des Abbruchs (leeres
  `pfade`) in einen Fehler.
- **Verbot – keine eigenen Kanalnamen.** Der Name steht in `src/shared/contracts/kanaele.ts` und wird
  von dort importiert; **kein** String-Literal `'media:…'` im Code dieser Datei.
- **Verbot – bestehende Einträge in `kanaele.ts` nicht verändern.** Nur der `media`-Block kommt
  hinzu; alles andere (insbesondere `queue`) bleibt Zeichen für Zeichen, wie es ist – dort arbeiten
  andere Agents.
- **Verbot – kein Ereignis.** Der `media-service` hat in v1 keinen Push an den Renderer. Der Stand
  der Import-/Löschaufträge kommt über `queue:geaendert` aus der Auftragsverwaltung; ein zweiter
  Ereignisweg brächte denselben Stand doppelt in die Oberfläche.
