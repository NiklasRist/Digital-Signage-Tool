### Issue M3-02: [media-service] Fehlercode-Unionen des Moduls definieren

## Ziel (in einem Satz)
Der `media-service` besitzt seine eigenen, geschlossenen Fehlercode-Unionen für Import, Löschen und
den Aufräumlauf, sodass jede Operation des Moduls einen typisierten Code liefert statt einer
Textmeldung.

## Modul & Datei
- Modul: `media-service` (Main)
- Datei: `src/main/media-service/fehlercodes.ts`
- Vertrag: Technisches Konzept **9.4.9** (Fehlercodes), ergänzend **9.1.1** Punkt 3 (geschlossener
  Satz) – Quelle der Wahrheit
- Prozess/Speicher: P1; kein Speicherzugriff (reine Typdatei)

## Warum das im Gesamtsystem wichtig ist
An diesen Codes hängt **echtes Verhalten**, nicht nur eine Meldung: `asset_referenziert` führt in der
Oberfläche zur Anzeige der betroffenen Listenelemente, `format_nicht_unterstuetzt` zur Erklärung
„bitte vorher konvertieren", `datei_fehler` zur Vormerkung einer offenen Löschung, die der Reconcile
beim nächsten Start nachholt. Geht der Code verloren oder wird er als freier `string` modelliert,
degradiert jeder dieser Fälle zu „irgendwas ist schiefgelaufen", und der Nutzer bekommt keinen
Hinweis, was zu tun ist.

Zweitens ist diese Datei der Ort, der verhindert, dass jedes M3-Issue seine eigenen Codes erfindet.
Fünf spätere Issues (Format-Prüfung, ffprobe, Kopie, Import-Ablauf, Lösch-Ablauf) liefern Fehler –
schreiben sie ihre Codes je selbst als String-Literal hin, weicht früher oder später eine Schreibweise
ab (`format_nicht_unterstützt` mit Umlaut, `probeFehler` in camelCase), und der Aufrufer, der auf den
Code prüft, trifft ihn nicht mehr. Der Fehler ist dabei **nicht sichtbar**: Der Ablauf läuft, nur der
Sonderfall greift nicht mehr.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/media-service/fehlercodes.ts

/** Fachliche Fehlercodes von importMedium (TK 9.4.9). */
export type ImportFehlercode =
  | 'datei_nicht_gefunden'
  | 'format_nicht_unterstuetzt'
  | 'probe_fehler'
  | 'kopier_fehler'
  | 'speicher_fehler'

/** Fachliche Fehlercodes von löscheMedium (TK 9.4.9). */
export type LoeschFehlercode =
  | 'asset_nicht_gefunden'
  | 'asset_referenziert'
  | 'datei_fehler'
  | 'speicher_fehler'

/** Fehlercodes des Aufräumlaufs (Reconcile, TK 9.4.7) – s. Begründung unten. */
export type ReconcileFehlercode = 'speicher_fehler' | 'datei_fehler'
```

Genau diese drei Unionen. **Keine** Sammel-Union über sie hinweg (`type MediaFehlercode =
ImportFehlercode | LoeschFehlercode`): Sie würde erlauben, aus einem Import `asset_referenziert`
zurückzugeben, und genau die Trennschärfe zerstören, die TK 9.4.9 mit zwei getrennten Tabellen
herstellt.

**Warum der Aufräumlauf eine EIGENE Union bekommt** (und nicht auf `Ergebnis<T>` ohne zweiten
Typparameter zurückfällt): Der Reconcile (M3-11 bis M3-14) ruft ausschließlich fremde Bausteine auf
und bekommt deren Codes herein – `datei_fehler` vom Löschen einer verwaisten Datei, `speicher_fehler`
vom `project-store` beim Setzen des Zustands „fehlt". Ohne eigene Union müsste er sie auf
`unbekannter_fehler` abbilden, und **der Originalcode ginge verloren** – genau davor warnt TK 9.1.1:
„Geht der Code verloren, degradieren Reparatur-Modus, Wiederholen und der FAT32-Hinweis alle zu
„irgendwas ist schiefgelaufen"." Die beiden Werte sind bewusst **keine** neuen Codes, sondern
dieselben, die TK 9.4.9 bereits für Import (`speicher_fehler`) und Löschen (`datei_fehler`) führt –
der Reconcile erfindet nichts, er reicht durch.

**Die Bedeutung jedes Codes (wörtlich aus TK 9.4.9, gehört als Kommentar bzw. Doku in die Datei):**

`importMedium`:

| Fehlercode | Ursache |
|---|---|
| `datei_nicht_gefunden` | `quellPfad` existiert nicht mehr (zwischen Dialog und Import verschoben) |
| `format_nicht_unterstuetzt` | Endung/MIME nicht in der Whitelist (9.4.2) |
| `probe_fehler` | `ffprobe` liefert keine Metadaten (beschädigte Datei) **oder** Timeout (gekillt) |
| `kopier_fehler` | Disk-Fehler, Platzmangel |
| `speicher_fehler` | D1-Schreibfehler |

`löscheMedium`:

| Fehlercode | Ursache |
|---|---|
| `asset_nicht_gefunden` | `assetId` existiert nicht in D1 |
| `asset_referenziert` | ein ListItem zeigt noch darauf; trägt `daten: { referenzenIds: string[] }` (strukturierte Fehlerdaten, 9.1.1) |
| `datei_fehler` | Datei konnte nicht gelöscht werden (nach Retry) → als `pendingDeletion` vorgemerkt |
| `speicher_fehler` | D1-Schreibfehler beim Entfernen des Eintrags (Platte voll, Rechte) – die Datei bleibt unangetastet, weil Schritt 1 nie abgeschlossen wurde |

**Zur letzten Zeile:** `speicher_fehler` steht seit TK v2.5 auch in der Lösch-Tabelle. Der Fall ist
real – das Entfernen des D1-Eintrags kann an einer vollen Platte scheitern –, war in der als
vollständig geführten Tabelle aber nicht vorgesehen. `entferneAsset` (M1-42) liefert ihn; ohne diesen
Wert in `LoeschFehlercode` ließe er sich nicht unverengt durchreichen. Es ist **kein** neuer Code,
sondern derselbe, den die Import-Tabelle darüber bereits führt.

**Fremde Typen, die du benutzt** (der umsetzende Agent sieht die anderen Issues nicht):

```ts
// #12 + #22 – src/shared/contracts/ergebnis.ts, bereits angelegt:
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'

export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: Fehlerdaten } }

// Der zweite Typparameter ist der Einhängepunkt für DIESE Datei. Eine Operation schreibt danach
// z. B.:  Promise<Ergebnis<Asset, ImportFehlercode>>
// Die drei generischen Codes sind darin automatisch enthalten und werden hier NICHT wiederholt.
// `daten` ist das optionale Feld für strukturierte Fehlerdaten (TK 9.1.1); seine Form ist JE
// FEHLERCODE festgelegt und wird NICHT hier deklariert – s. Invariante zu `asset_referenziert`.
```

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – | reine Typdefinition, kein Laufzeit-Eingang | – |

Ausgang bei Erfolg: Jede Operation des `media-service` kann `Ergebnis<T, ImportFehlercode>`,
`Ergebnis<T, LoeschFehlercode>` oder `Ergebnis<T, ReconcileFehlercode>` schreiben und bekommt beim
Typecheck exakt die Vereinigung aus den
fachlichen Codes dieser Operation **und** den drei generischen – nicht mehr, nicht weniger.
Ausgang bei Fehler: entfällt (Typdefinition, keine Laufzeit-Fehlerpfade).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Fehlercodes sind ein geschlossener, typisierter Satz:** die fachlichen je Operation (9.4.9,
  9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`.
  **Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1, Punkt 3)
- „Bei uns hängt an den Codes **echtes Verhalten**: `asset_referenziert` zeigt die betroffenen
  Listenelemente" (TK 9.1.1) – deshalb ist der Code eine typisierte Konstante, nie ein freier String.
- **ENTSCHIEDEN – `asset_referenziert` transportiert seine Nutzdaten im Feld `daten` der
  Ergebnis-Hülle.** Wörtlich aus TK 9.4.9: „| `asset_referenziert` | ein ListItem zeigt noch darauf;
  trägt `daten: { referenzenIds: string[] }` (strukturierte Fehlerdaten, 9.1.1) |". Die Hülle führt
  dieses Feld inzwischen ausdrücklich: „**Strukturierte Fehlerdaten (`daten`, optional).** Manche
  Fehler sind erst mit ihren Nutzdaten bedienbar: `asset_referenziert` muss die **betroffenen
  Listenelemente** nennen (`{ referenzenIds: string[] }`, 9.4.9)" (TK 9.1.1). Damit ist die früher
  offene Frage nach dem Transportweg beantwortet – es gibt **keinen** Sondertyp und **keinen**
  Sonderkanal dafür.
  **Folge für DIESE Datei:** Sie deklariert weiterhin **nur den Code**. Die Form von `daten` ist „je
  Fehlercode festgelegt und typisiert (dokumentiert dort, wo der Code vergeben wird: 9.4.9, 9.6.4,
  9.12.1)" (TK 9.1.1) – vergeben wird `asset_referenziert` in M3-10, dort wird das Objekt gefüllt.
  Hier entsteht **kein** Typ `AssetReferenzFehler`, **kein** `Fehlerdaten`-Alias und **keine**
  Zuordnungstabelle Code → Datenform.
- **ENTSCHIEDEN – die Codes dieser Datei erreichen die Auftragsverwaltung, ohne durch `Fehlercode`
  (#12) zu müssen.** `HandlerErgebnis` ist seit #60 über seinen Fehlercode generisch: `HandlerErgebnis<F>`
  typisiert `fehler.code` als `F | GenerischerFehlercode`. Ein Medien-Handler schreibt also
  `HandlerErgebnis<ImportFehlercode>` bzw. `HandlerErgebnis<LoeschFehlercode>` und gibt seinen
  fachlichen Code **unverengt** heraus; die Auftragsverwaltung nimmt ihn als `HandlerErgebnis<string>`
  entgegen und reicht ihn unverändert weiter. Abgelegt wird er in `Auftrag.fehler.code` (#16) und
  `ProtokollEintrag.fehler.code` (#53) – dort ist der Typ bewusst `string`, weil der **geteilte**
  Vertrag die fachlichen Unionen der Main-Module nicht kennen darf (sonst müsste `contracts/` auf
  Main-Code zeigen). `Fehlercode` (#12) bleibt unverändert der Satz der drei generischen Codes.
  **Folge für DIESE Datei:** Es gibt nichts zu melden und nichts zu umgehen – kein `as Fehlercode`-Cast,
  keine Erweiterung von `ergebnis.ts`, kein Abbilden auf `unbekannter_fehler`. Der geschlossene Satz
  aus TK 9.1.1 Punkt 3 bleibt gewahrt: Er ist **je Operation** geschlossen und typisiert, nämlich
  dort, wo der Code **entsteht**; weit typisiert ist nur der Ablageort, der alle Arten gleichzeitig
  trägt.
- **Muster aus #22 (verbindlich):** Fachliche Module deklarieren ihre eigene Union in ihrer eigenen
  Datei; `src/shared/contracts/ergebnis.ts` wird dafür **nicht** angefasst. Wörtlich aus #22:
  „Fachliche Module deklarieren ihre eigene Union in ihrer eigenen Datei" und „und re-exportieren sie
  hier NICHT automatisch – der Aufrufer einer bestimmten Operation importiert die konkrete
  Fehlercode-Union der jeweiligen Operation direkt".
- **Die generischen Codes werden hier NICHT wiederholt.** Weder `ungueltige_eingabe` noch
  `nicht_gefunden` noch `unbekannter_fehler` taucht in einer der beiden Unionen auf – sie kommen über
  den `Ergebnis`-Typ automatisch dazu. Eine Wiederholung erzeugt zwei Quellen für denselben Wert.
- **Kein Code, den TK 9.4.9 nicht nennt.** Insbesondere **kein** `medium_fehlt` (das ist ein
  Render-Code, TK 9.4.7), **kein** `render_aktiv` (dieser Code ist laut TK 9.3.6 entfallen und darf
  nirgends wieder auftauchen), kein `timeout` (der Timeout **ist** `probe_fehler`, s. Tabelle oben),
  kein `abgebrochen` (Import und Löschen kennen keinen Abbruch).
- Diese Datei enthält **ausschließlich Typen** – keine Laufzeit-Werte, keine Meldungstexte, keine
  Übersetzungstabelle Code → Klartext. Der Klartext für die Oberfläche entsteht später und woanders.

- **Verbot – `src/shared/contracts/ergebnis.ts` wird nicht angefasst**, auch nicht „nur um den
  Re-Export zu ergänzen".
- **Verbot – keine Sammel-Union und kein Alias.** Weder `MediaFehlercode` noch
  `MediaServiceFehlercode` noch ein `const`-Array der Codes „zum Prüfen". Wer zur Laufzeit prüfen
  will, ob ein Wert ein gültiger Code ist, tut das dort, wo er den Wert bekommt – nicht hier.

  beiden führt, legen M3-11 bis M3-14 fest, nicht diese Datei.
