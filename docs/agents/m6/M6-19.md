### Issue M6-19: [render-service] Frame-Rundung und Gesamtdauer berechnen

## Ziel (in einem Satz)
Jede Sekundenangabe eines Render-Auftrags wird nach **einer einzigen**, überall gleichen Regel auf
das Frame-Raster des Ausgabe-Profils gerundet, und die gemeldete Gesamtdauer ist die Summe genau
dieser gerundeten Dauern.

## Modul & Datei
- Modul: `render-service` [P4] (Main)
- Datei: `src/main/render-service/frames.ts`
- Vertrag: Technisches Konzept **9.2.6** (Trim ist framegenau; `gesamtdauer` zählt gerundete
  Frame-Dauern), **9.2.4** (Bildrate 30 fps CFR), **9.2.3** (`gesamtdauer` im `RenderResult`),
  **9.2.8** (Abschnitts-Dauern unterliegen derselben Rundung) – Quelle der Wahrheit
- Prozess/Speicher: P4; **kein** Dateisystem, **kein** ffmpeg, **kein** Zustand – reine Rechnung

## Warum das im Gesamtsystem wichtig ist
Diese Datei ist die **zweite Hälfte einer Zusage**, deren erste Hälfte in einem ganz anderen Modul
liegt. Der `composer` zeigt dem Nutzer vor dem Rendern die Gesamtlänge der Wiedergabeliste an und
warnt ab dreißig Minuten (#127). Diese Datei bestimmt, wie lang die Datei **wirklich** wird. Beide
müssen dieselbe Zahl liefern – nicht „ungefähr".

Der konkrete Fehler, wenn man rohe Sekunden addiert: Jede Trim-Grenze wird auf das Frame-Raster
gerundet. Je Grenze weicht die gerundete Dauer um bis zu einen halben Frame von der rohen
Sekundendifferenz ab. Bei einem Element ist das unsichtbar; über eine Schleife mit hundert Elementen
summiert es sich auf Sekunden. Dann stimmt die angezeigte Länge nicht mehr mit der Datei überein –
und weil die fertige Datei am Ende gegen genau diese Gesamtdauer **verifiziert** wird (TK 9.2.6),
scheitert der Lauf mit `ffmpeg_fehler`, obwohl `ffmpeg` alles richtig gemacht hat. Der Nutzer
bekäme dann „Wiederholen" empfohlen für einen Fehler, der bei jeder Wiederholung erneut auftritt.

Der zweite Fehlgriff ist subtiler und rechnerisch verlockend: `round((ende − start) × fps)` statt
`round(ende × fps) − round(start × fps)`. Die beiden Ausdrücke sind **nicht** gleich. Nachrechenbares
Beispiel bei 30 fps mit `trimStart = 2.51` und `trimEnde = 10.49`:

- einzeln gerundet: `round(10.49 × 30) − round(2.51 × 30)` = `315 − 75` = **240 Frames**
- gemeinsam gerundet: `round((10.49 − 2.51) × 30)` = `round(239.4)` = **239 Frames**

Ein Frame Unterschied – und der `composer` (#127) rechnet nachweislich in der **ersten** Form. Über
eine Liste hinweg summiert sich das, und es ist genau die Drift, die dieser ganze Abschnitt des TK
verhindern soll.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/render-service/frames.ts
import type { RenderItem } from '../../shared/contracts/render-request'
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { RenderFehlercode } from './fehlercodes'

/** Frame-Grenzen eines Video-Ausschnitts. Behalten werden die Frames [startFrame, endFrame). */
export interface TrimFrames {
  startFrame: number
  endFrame: number
  frames: number        // endFrame - startFrame, immer >= 1
}

/** Sekunden auf das Frame-Raster des Ausgabe-Profils runden: round(sekunden × fps). */
export function zuFrames(sekunden: number): number

/** Frame-Anzahl zurück in Sekunden: frames / fps. */
export function zuSekunden(frames: number): number

/** Die beiden Trim-Grenzen eines Video-Elements auf dasselbe Raster runden. */
export function trimFrames(
  trimStart: number,
  trimEnde: number,
): Ergebnis<TrimFrames, RenderFehlercode>

/** Frame-Dauer genau eines Elements: bei `video` aus dem Trim, bei `bild`/`segment` aus `dauer`. */
export function frameDauer(element: RenderItem): Ergebnis<number, RenderFehlercode>

/** Summe der frame-gerundeten Elementdauern, in Frames. Leere Liste ergibt 0. */
export function gesamtFrames(elemente: readonly RenderItem[]): Ergebnis<number, RenderFehlercode>

/** Dieselbe Summe in Sekunden – der Wert, der als `RenderResult.gesamtdauer` gemeldet wird. */
export function gesamtdauer(elemente: readonly RenderItem[]): Ergebnis<number, RenderFehlercode>
```

**Die Rundung je `art` (verbindlich):**

| `art` | Frames | Quelle |
|---|---|---|
| `video` | `zuFrames(trimEnde) − zuFrames(trimStart)` | TK 9.2.6, wörtlich unten |
| `bild` | `zuFrames(dauer)` | TK 9.2.6, „Dieselbe Rundungsregel gilt ausnahmslos" |
| `segment` | `zuFrames(dauer)` | TK 9.2.6, dieselbe Stelle |

`fps` kommt **ausschließlich** aus `RENDER_PROFILE.fps` (#18). Die Zahl `30` steht **nicht** in
dieser Datei.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `sekunden` (`zuFrames`) | eine Zeitangabe in Sekunden | endlich und `≥ 0`; **`zuFrames` prüft das nicht** – sie ist eine reine Umrechnung, die Prüfung machen die Aufrufer darüber (s. ENTSCHIEDEN 4) |
| `frames` (`zuSekunden`) | eine Frame-Anzahl | ganzzahlig, `≥ 0`; ebenfalls ungeprüft |
| `trimStart` / `trimEnde` | Schnittgrenzen des Video-Elements in Sekunden (aus dem `RenderItemVideo`) | beide endlich, `trimStart ≥ 0`, `trimEnde > trimStart`, nach der Rundung mindestens **ein** Frame Abstand |
| `element` (`frameDauer`) | ein `RenderItem` des Auftrags | die Feldbelegung muss zur `art` passen; `dauer` bei `bild`/`segment` endlich und `> 0` |
| `elemente` | die geordnete Elementliste des `RenderRequest` | leeres Array erlaubt → `0` (s. ENTSCHIEDEN 5) |

Ausgang bei Erfolg: ganze Frame-Zahlen bzw. – bei `gesamtdauer` – ein exaktes Vielfaches von
`1 / RENDER_PROFILE.fps`.
Ausgang bei Fehler: `ungueltiges_element`, bei `frameDauer`/`gesamtFrames`/`gesamtdauer` **mit**
`daten = { elementId }`; bei `trimFrames` **ohne** `daten`, weil diese Funktion die Element-ID nicht
kennt (der Aufrufer ergänzt sie). **Zwei** Ausnahmen ergeben `ungueltige_eingabe` statt
`ungueltiges_element`: eine unbekannte `art` und ein `elemente`, das gar kein Array ist. Beide
Male fehlt der Elementbezug, und TK 9.2.3 ordnet einen Mangel ohne Elementbezug der **Anfrage**
zu (s. Fehlerpfade).

## ENTSCHIEDEN (lokale Festlegungen dieses Issues)

1. **Gerundet wird mit `Math.round`, ohne jedes Epsilon.** Kein `toFixed`, keine Toleranz, kein
   `Number.EPSILON`-Zuschlag, keine Vorab-Rundung der Sekunden auf drei Nachkommastellen.
   Begründung: Der `composer` (#127) rechnet mit derselben Formel auf denselben Gleitkommazahlen.
   Solange **beide** Seiten exakt `Math.round(x * fps)` schreiben, liefern sie **bitgleich**
   dasselbe Ergebnis – IEEE-754 ist deterministisch. Jede „Verbesserung" auf einer Seite (ein
   Epsilon, das den halben Frame „gerechter" verteilt) macht die beiden Seiten unterschiedlich, und
   der Unterschied fällt erst am fertigen Video auf. Genau davor warnt TK 9.2.6 mit „kein `floor`
   an einer, `round` an anderer Stelle".
2. **Die Reihenfolge der Operationen ist Teil der Regel: erst multiplizieren, dann runden, dann
   subtrahieren.** `zuFrames(trimEnde) − zuFrames(trimStart)`, **nie**
   `zuFrames(trimEnde − trimStart)`. Begründung oben unter „Warum das wichtig ist"; TK 9.2.6
   schreibt beide Grenzen einzeln aus.
3. **`zuFrames` ist die einzige Stelle im ganzen Modul, an der `fps` benutzt wird.** Alle anderen
   Funktionen dieser Datei rufen `zuFrames`/`zuSekunden` auf, statt selbst zu multiplizieren.
   Begründung: Eine zweite Multiplikation im selben Modul ist eine zweite Rundungsstelle, und genau
   die verbietet der Vertrag.
4. **`zuFrames` und `zuSekunden` validieren nicht und geben keine `Ergebnis`-Hülle zurück.** Sie
   sind reine Umrechnungen; eine Hülle um `x * 30` zu legen, zwingt jeden Aufrufer zu einer
   Fallunterscheidung, die es nicht gibt. Die Prüfung der Eingaben passiert **einmal**, in
   `trimFrames` bzw. `frameDauer`.
5. **Eine leere Elementliste ergibt `0` Frames und ist hier KEIN Fehler.** Dass ein `RenderRequest`
   mindestens ein Element enthalten muss, ist eine Regel der **Anfrage** und wird dort geprüft
   (`ungueltige_eingabe`, M6-18). Diese Datei rechnet; sie beurteilt nicht die Anfrage.
6. **`gesamtFrames` bricht beim ersten unstimmigen Element ab** und meldet dessen `elementId` –
   sie sammelt **nicht** alle Fehler ein. Begründung: Der geführte Reparatur-Modus (FA-19) führt
   den Nutzer ohnehin „eins nach dem anderen" (TK 9.7.5), und `RenderResult` hat genau **ein**
   Feld `fehlerhaftesElementId`.
7. **Ein Ergebnis von 0 Frames ist ein Fehler, kein leeres Element.** Sowohl bei `trimFrames`
   (Rundung ergibt `startFrame >= endFrame`) als auch bei `frameDauer` (eine `dauer`, die auf 0
   Frames rundet). Ein Segment ohne Frames erzeugt eine leere Eingabedatei für den concat-Schritt,
   und `-c copy` bricht daran **nicht** ab – es entsteht eine Datei mit einem Sprung darin.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Video-Trim ist framegenau (30 fps):** Bei `"video"`-Items wird der Ausschnitt
  `[trimStart, trimEnde)` **framegenau** geschnitten […] Beide Grenzen werden auf **dasselbe**
  30-fps-Raster gerundet: `startFrame = round(trimStart × 30)`, `endFrame = round(trimEnde × 30)`;
  behalten werden die Frames `[startFrame, endFrame)`. Die effektive Elementdauer ist damit
  `(endFrame − startFrame) / 30` – **nicht** die rohe Sekundendifferenz. Der Zwischenclip ist
  **CFR** (konstante Bildrate 30 fps), damit die Frame-Anzahl deterministisch bleibt. Dieselbe
  Rundungsregel gilt ausnahmslos (kein `floor` an einer, `round` an anderer Stelle) – sonst weicht
  die Dauer um einen Frame ab." (TK 9.2.6)
- „**`gesamtdauer` zählt gerundete Frame-Dauern:** Die im `RenderResult` gemeldete `gesamtdauer`
  summiert die **gerundeten** Elementdauern (Frame-Anzahl / 30), nicht die rohen Trim-Sekunden –
  sonst driften die angezeigte Gesamtlänge (5.3, 30-Minuten-Warnung) und die tatsächliche Länge der
  Ausgabedatei auseinander." (TK 9.2.6)
- „**Standbild → Clip:** `"segment"`-Items werden als Standbild über ihre `dauer`
  bei 30 fps im Profil ausgehalten; harter Schnitt an den Grenzen." (TK 9.2.6) – ihre Dauer ist die
  Elementdauer, ohne Zu- oder Abschlag für Übergänge (es gibt keine).
- „| Bildrate | **30 fps, CFR** (konstant) | Voraussetzung für die Frame-Rundung (9.2.6) |"
  (TK 9.2.4) – die Zahl kommt aus `RENDER_PROFILE.fps` (#18), **nie** als Literal in diese Datei.
- „Abschnitts-Dauern unterliegen **derselben Frame-Rundung** wie alles andere (30 fps, 9.2.6) –
  sonst driftet das Band gegen das Video." (TK 9.2.8) – deshalb ist `zuFrames` **öffentlich**: Die
  Bandspur (M6-13) rundet ihre Abschnitts-Dauern mit **dieser** Funktion, nicht mit einer eigenen.
- „Die Elementdauer bestimmt **allein das Video** (Trim). Das Band verlängert oder verkürzt sie
  **nie**." (TK 9.2.8) – `frameDauer` eines `video`-Elements liest **ausschließlich** `trimStart`
  und `trimEnde`. Die Dauern in `einblendung.abschnitte` gehen in **keine** Summe dieser Datei ein.
- „**`gesamtdauer`** | Summe der (getrimmten) Elementdauern in Sekunden – **framegerundet** gezählt
  (Frame-Anzahl / 30, s. 9.2.6)" (TK 9.2.3)
- „**„Verifiziert" ist definiert, nicht Auslegungssache:** Bevor die fertige Datei die vorherige
  Fassung ersetzt, wird sie **genau einmal** mit `ffprobe` ausgelesen und gegen das Ausgabe-Profil
  (9.2.4) geprüft: **Dauer** im erwarteten Rahmen (die framegerundete `gesamtdauer`, mit enger
  Toleranz)" (TK 9.2.6) – die Zahl, gegen die dort geprüft wird, entsteht **hier**.
- Niemals `throw` – diese Funktionen werden aus einer IPC-bedienten Operation heraus benutzt
  (TK 9.1.1).

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – die Zahl 30 steht nicht in dieser Datei.** Weder als Literal, noch als lokale
  Konstante, noch als Vorgabewert eines Parameters. `RENDER_PROFILE.fps` ist die einzige Quelle;
  eine spätere Profil-Änderung muss ein Datenwert bleiben, kein Schnittstellenbruch (TK 9.2.4).
- **Verbot – kein Epsilon, keine Toleranz, keine „gerechtere" Rundung.** Begründung: ENTSCHIEDEN 1.
  Wer hier eine numerisch elegantere Lösung sieht, hat sie im `composer` (#127) nicht – und das
  Projekt bräuchte sie an **beiden** Stellen gleichzeitig. Das ist eine Vertragsänderung, kein
  lokaler Feinschliff: **melden**.
- **Verbot – die Dauern der Band-Abschnitte werden hier nicht summiert.** Ein Band läuft
  **parallel** zum Video. Wer `einblendung.abschnitte[].dauer` in `frameDauer` oder `gesamtFrames`
  einrechnet, meldet eine Gesamtdauer, die bis zum Doppelten der echten sein kann – und die
  anschließende Verifikation der fertigen Datei (TK 9.2.6) scheitert dann bei **jedem** Lauf mit
  einem Band.
- **Verbot – keine Quelldauer-Prüfung.** Ob `trimEnde` innerhalb der tatsächlichen Länge der
  Videodatei liegt, kann diese Datei nicht wissen: Dafür müsste sie `ffprobe` aufrufen. Diese
  Prüfung gehört dorthin, wo die Quelle ohnehin gelesen wird (Normalisierung eines Elements,
  M6-22), und liefert denselben Code `ungueltiges_element`. Hier wird **kein** Parameter
  `quellDauer` ergänzt, auch kein optionaler.
- **Verbot – keine Dauer-Grenzen (10–45 s) hier.** Sie stehen in `DAUER_BEREICH` (#21) und werden
  bei der Prüfung der Anfrage angewandt (M6-18). Diese Datei rechnet nur; eine zweite Prüfung mit
  eigener Auslegung wäre eine zweite Wahrheit.
- **Verbot – kein Zustand, kein Zwischenspeicher.** Keine Memoisierung, kein Modul-Zustand. Die
  Funktionen sind rein; zweimal derselbe Eingang ergibt zweimal denselben Ausgang.
