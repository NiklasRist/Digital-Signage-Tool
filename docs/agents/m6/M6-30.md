### Issue M6-30: [export-service] Exportquelle über die Pfad-Autorität auflösen und prüfen

## Ziel (in einem Satz)
Aus `projektId` und dem gewählten Dateinamen wird der absolute Pfad der zu exportierenden
Ausgabedatei **über die Pfad-Autorität** ermittelt und ihre Größe gelesen – oder es steht fest,
dass die Datei nicht (mehr) da ist.

## Modul & Datei
- Modul: `export-service` (Main)
- Datei: `src/main/export-service/quelle.ts`
- Vertrag: Technisches Konzept **9.6.2** Schritt 1 und **9.6.1** (Quelle der Wahrheit), ergänzend
  **9.5.7** (Pfad-Autorität), **9.2.6** (Namensvalidierung), **9.6.4** (Fehlercodes)
- Prozess/Speicher: P4 (Export-Teil); liest **ausschließlich** Metadaten einer Datei in
  `projects/<id>/output/`. **Kein** D1-Zugriff (`project.json` wird nicht geöffnet), **kein** Lock,
  **kein** Schreiben.

## Warum das im Gesamtsystem wichtig ist
Diese Funktion ist die Stelle, an der ein **Nutzer-gewählter Dateiname** zum ersten Mal zu einem
**absoluten Pfad** wird – und damit die Stelle, an der ein Ausbruch aus dem Projektordner
stattfinden könnte. Der Name kommt aus `ExportRequest.dateiname`, also über die IPC-Grenze aus dem
Renderer; TK 9.1.1 sagt dazu: „**6. Der Main validiert jede eingehende Nutzlast** – er vertraut dem
Renderer **nicht**." Ein Name wie `../../config` oder `..\..\project.json` würde ohne Schranke eine
beliebige Datei des Datenorts auf einen USB-Stick kopierbar machen.

Genau diese Schranke gibt es bereits – in `loeseAusgabePfad` (#49). **Deshalb baut diese Datei
keinen eigenen Pfad.** Wer stattdessen `path.join(ausgabeOrdner(projektId), dateiname)` schreibt,
umgeht die Prüfung, die #49 gerade dafür bereitstellt, und ist zugleich die zweite Stelle im System,
die das Ordner-Layout kennt (TK 9.5.7: „So kann eine Layout-Änderung nirgends auseinanderlaufen.").

Der zweite teure Punkt ist die **Endung**. Hier stoßen zwei Verträge aneinander:
`ExportRequest.dateiname` kommt **MIT** Endung (er stammt aus `listeAusgaben`, #75:
„`dateiname: string // MIT Endung, z. B. "sommeraktion.mp4"`"), `loeseAusgabePfad` (#49) erwartet
den Namen **OHNE** Endung und hängt selbst `.mp4` an. Wer das übersieht, resolved
`sommeraktion.mp4` zu `…/output/sommeraktion.mp4.mp4` – eine Datei, die es nie gibt. Jeder Export
scheiterte dann mit `keine_ausgabe`, und zwar **immer**, bei jeder Datei, ohne dass an irgendetwas
anderem etwas falsch wäre.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/export-service/quelle.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { ExportFehlercode } from './fehlercodes'

export interface ExportQuelle {
  quellPfad: string       // absoluter Pfad der Datei in projects/<id>/output/
  dateigroesse: number    // Bytes – Grundlage für Platzprüfung (M6-29) und Verifikation (M6-31)
}

export async function loeseExportQuelle(
  projektId: string,
  dateiname: string,      // MIT Endung, wie aus listeAusgaben (#75), z. B. "sommeraktion.mp4"
): Promise<Ergebnis<ExportQuelle, ExportFehlercode>>
// - baut den Pfad AUSSCHLIESSLICH über loeseAusgabePfad (#49); KEIN eigenes path.join
// - fehlt die Datei → 'keine_ausgabe'
```

**Fremde Funktionen und Typen, die du benutzt, vollständig ausgeschrieben** (der umsetzende Agent
sieht die anderen Issues nicht):

```ts
// #49 – src/main/project-store/pfade.ts (DEFINIERENDE QUELLE, Pfad-Autorität)
export function loeseAusgabePfad(projektId: string, ausgabeName: string): Ergebnis<string>
// absoluter Pfad `ausgabeOrdner(projektId)/<ausgabeName>.mp4`; liefert NUR einen Pfad, wenn
// `ausgabeName` die Namensvalidierung aus TK 9.2.6 besteht UND das normalisierte
// Ergebnis nachweislich innerhalb von ausgabeOrdner(projektId) liegt, sonst `ungueltige_eingabe`;
// reine String-/Validierungs-Operation (kein `fs.*`-Aufruf, keine Existenzprüfung)
// ACHTUNG: `ausgabeName` ist der Dateiname OHNE Endung – die Funktion hängt `.mp4` selbst an.

// (aus derselben Datei, hier NICHT zu benutzen – nur zur Abgrenzung:)
// export function ausgabeOrdner(projektId: string): string
//   reine String-Operation ohne jede Prüfung. Wer damit selbst joint, umgeht die Schranke.

// #75 – src/main/project-store/ausgaben.ts (Quelle des Dateinamens, hier NICHT aufzurufen)
export interface AusgabeDatei {
  dateiname: string       // MIT Endung, z. B. "sommeraktion.mp4"
  dateigroesse: number    // Bytes
  geaendertAm: string     // ISO-8601 UTC
}

// M6-27 – src/main/export-service/fehlercodes.ts (DEFINIERENDE QUELLE)
export type ExportFehlercode =
  | 'keine_ausgabe' | 'ziel_nicht_verfügbar' | 'datei_zu_gross_fat32'
  | 'kein_platz' | 'ziel_gesperrt' | 'schreib_fehler' | 'speicher_fehler'
// SIEBEN Werte (`speicher_fehler` ist der Zusatz aus TK v2.9).
// Diese Datei vergibt davon GENAU EINEN: keine_ausgabe.
// `speicher_fehler` vergibt allein M6-33 – im Fehlerzweig des Sofort-Flushs, NICHT hier.

// #12 + #22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
```

Weicht eine dieser Signaturen von der tatsächlichen Fassung der definierenden Datei ab, ist das ein
**Vertragsfehler** – **melden, NICHT eigenmächtig anpassen.** Die definierende Datei gewinnt immer.
Das gilt besonders für `loeseAusgabePfad`: Nähme sie den Namen **mit** Endung entgegen, wäre der
gesamte Ablauf unten falsch, und das Abschneiden müsste entfallen.

### Der Ablauf (verbindlich – in genau dieser Reihenfolge)
1. **Formprüfung.** `projektId` und `dateiname` sind nicht leere Strings → sonst
   `ungueltige_eingabe`, **ohne** jeden Dateisystemzugriff.
2. **Endung prüfen.** `dateiname` muss auf `.mp4` enden, verglichen **ohne** Rücksicht auf
   Groß-/Kleinschreibung (`.MP4` zählt mit). Andernfalls → `ungueltige_eingabe`. Der Rest darf
   **nicht** leer sein: `".mp4"` allein ist ungültig.
3. **Endung abschneiden.** `ausgabeName` = `dateiname` **ohne** die letzten vier Zeichen. Nicht
   „alles ab dem letzten Punkt" entfernen – ein Name wie `sommer.aktion.mp4` behält so korrekt
   `sommer.aktion`.
4. **Pfad auflösen.** `loeseAusgabePfad(projektId, ausgabeName)` (#49). Liefert die Funktion
   `ok: false`, wird ihr Code (`ungueltige_eingabe`) **unverändert** durchgereicht – nicht
   umgedeutet, nicht in `keine_ausgabe` verwandelt. Ein ungültiger Name und eine fehlende Datei
   sind verschiedene Dinge und brauchen verschiedene Hinweise.
5. **Existenz und Größe lesen.** `fs.promises.stat(quellPfad)`.
   - `ENOENT` **oder** das Ziel ist kein reguläres File (Verzeichnis, Symlink auf nichts) →
     `keine_ausgabe`.
   - Anderer `fs`-Fehler (`EACCES`, `EIO`, …) → `keine_ausgabe` (s. ENTSCHIEDEN unten).
   - Erfolg → `{ ok: true, wert: { quellPfad, dateigroesse: stat.size } }`.

**ENTSCHIEDEN – die Endung wird ohne Rücksicht auf Groß-/Kleinschreibung erkannt.** `listeAusgaben`
(#75) nimmt `.MP4` ausdrücklich in die Liste auf; ein von Hand in den Ausgabeordner kopiertes
`FERIEN.MP4` erscheint also in der Oberfläche und muss exportierbar sein. **Folge, die bewusst in
Kauf genommen wird:** `loeseAusgabePfad` hängt immer `.mp4` in Kleinschreibung an. Auf den
Zielplattformen des Produkts – Windows 10/11 und macOS 13+ – sind die Standard-Dateisysteme
**nicht** zwischen Groß- und Kleinschreibung unterscheidend, `FERIEN.MP4` und `FERIEN.mp4`
bezeichnen dort dieselbe Datei. Auf einem case-sensitiven Datenträger würde die Auflösung ins Leere
gehen und mit `keine_ausgabe` enden – ein sichtbarer, benannter Fehler, kein stiller Griff auf die
falsche Datei.

**ENTSCHIEDEN – jeder Zugriffsfehler auf die Quelldatei ist `keine_ausgabe`, nicht
`schreib_fehler`.** TK 9.6.4 beschreibt `schreib_fehler` als „sonstiger I/O-Fehler beim
Kopieren"; hier wird nichts kopiert. Für den Nutzer ist die Aussage in beiden Fällen dieselbe:
„Diese Ausgabedatei steht nicht zur Verfügung – rendere sie neu oder wähle eine andere." Ein
zusätzlicher Code für „vorhanden, aber unlesbar" existiert im geschlossenen Satz von TK 9.6.4
**nicht** und wird **nicht** erfunden. Die genaue Ursache (`EACCES` o. ä.) steht in der `meldung`.

**ENTSCHIEDEN – der Zielname des Exports ist der übergebene `dateiname`, unverändert.** Diese
Funktion gibt ihn **nicht** verändert zurück und normalisiert ihn nicht (kein Kleinschreiben, kein
Umbenennen der Endung). TK 9.6.3: „**Zieldateiname = Quelldateiname.**" Aus `FERIEN.MP4` wird auf
dem Stick `FERIEN.MP4`. Den Zielpfad baut M6-33 aus `zielPfad` und dem **unveränderten**
`dateiname`.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projektId` | Projekt, dessen Ausgabeordner die Quelle enthält (`ExportRequest.projektId`) | nicht leerer String; wird **unverändert** an `loeseAusgabePfad` gegeben. **Wichtig:** `loeseAusgabePfad` prüft laut #49 seinen **zweiten** Parameter, die `projektId` aber **nicht** – sie wird dort nur als Pfadsegment eingesetzt. Die Form-/Traversal-Prüfung der `projektId` findet am IPC-Kanal statt; main-interne Aufrufer übergeben ohnehin die ID des geladenen Projekts. Hier bleibt es bei „nicht leerer String" |
| `dateiname` | **welche** Ausgabedatei kopiert wird (FA-22), **MIT** Endung, wie von `listeAusgaben` geliefert | nicht leer; muss auf `.mp4` enden (Groß-/Kleinschreibung egal); der Namensteil davor darf nicht leer sein. Pfadtrenner, `..` und unzulässige Zeichen fängt `loeseAusgabePfad` (#49) ab – **diese Datei prüft sie nicht ein zweites Mal und anders** |

Ausgang bei Erfolg: `{ quellPfad, dateigroesse }`. `quellPfad` liegt garantiert innerhalb von
`projects/<projektId>/output/` (Zusage von #49); `dateigroesse` ist die Größe in Bytes und die
Grundlage sowohl der Platzprüfung (M6-29) als auch der Größen-Verifikation nach dem Kopieren
(M6-31).
Ausgang bei Fehler: Codes `keine_ausgabe` (fachlich, TK 9.6.4) und `ungueltige_eingabe`
(generisch, durchgereicht von #49 oder aus der eigenen Formprüfung). Geschlossener Satz. Diese
Funktion vergibt **nie** `ziel_nicht_verfügbar`, `kein_platz`, `ziel_gesperrt`, `schreib_fehler`
oder `datei_zu_gross_fat32` – sie fasst das Ziel überhaupt nicht an.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Quelle prüfen:** existiert `projects/<id>/output/<dateiname>`? Sonst `keine_ausgabe` (erst
  rendern bzw. andere Datei wählen)." (TK 9.6.2, Schritt 1)
- „`dateiname` | **welche** Ausgabedatei kopiert wird (FA-22) – aufgelöst zu
  `projects/<id>/output/<dateiname>`" (TK 9.6.1)
- „**Woher `dateiname` kommt:** Die Auswahl speist sich aus `listeAusgaben` (9.5.2); der Renderer
  liest den Ausgabeordner **nie** selbst und kennt **keine** absoluten Pfade." (TK 9.6.1)
- „**`project-store` ist die eine Pfad-Autorität.** Er löst `(projektId, dateiname) → absoluter
  Pfad` auf – die **einzige** Quelle der Wahrheit für das Datei-Layout eines Projekts
  (`projects/<id>/media/<datei>`). Jeder Main-Dienst, der eine Mediendatei anfassen muss,
  **resolved den Pfad über den `project-store`**, statt das Layout selbst zu kennen: `media-service`
  (kopieren/löschen), `render-service` (lesen beim Normalisieren), `export-service` (Quelle: die
  gewählte Datei aus `projects/<id>/output/`). Er löst ebenso
  `(projektId, ausgabeName) → projects/<id>/output/<name>.mp4` auf und **listet diesen Ordner**
  (`listeAusgaben`, 9.5.2). So kann eine Layout-Änderung nirgends auseinanderlaufen." (TK 9.5.7)
- „**Der Name ist Nutzereingabe** und wird wie in 9.2.6 validiert: keine Pfadtrenner, kein `..`,
  keine für das Zieldateisystem unzulässigen Zeichen. Der Export darf **nie** außerhalb von
  `zielPfad` schreiben." (TK 9.6.3) – **die Validierung leistet `loeseAusgabePfad` (#49); diese
  Datei baut sie nicht nach.**
- „**Zieldateiname = Quelldateiname.** Der frühere Zwang auf exakt `loop.mp4` ist **entfallen**
  (FA-22)" (TK 9.6.3)
- „**6. Der Main validiert jede eingehende Nutzlast** – er vertraut dem Renderer **nicht**.
  Ungültige Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten. Ein Fehler im
  Renderer darf D1 niemals beschädigen." (TK 9.1.1)
- Der Fehlercode, wörtlich aus der geschlossenen Tabelle TK 9.6.4:

  | Fehlercode | Ursache |
  |---|---|
  | `keine_ausgabe` | die gewählte Datei fehlt in `projects/<id>/output/` – noch nicht gerendert oder gelöscht |

- Niemals `throw`: Der Aufrufer ist der Export-Handler eines Auftrags; eine Ausnahme ließe den
  Auftrag auf `laeuft` stehen und brächte die streng serielle Warteschlange für den Rest der
  Sitzung zum Stillstand (TK 9.3.5).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `projektId` oder `dateiname` leer/kein String | `ungueltige_eingabe` | **kein** Dateisystemzugriff, keine Wirkung |
| `dateiname` endet nicht auf `.mp4` (Groß-/Kleinschreibung egal) | `ungueltige_eingabe` | **kein** Dateisystemzugriff; Meldung nennt die erwartete Endung |
| `dateiname` ist genau `".mp4"` (kein Namensteil) | `ungueltige_eingabe` | **kein** Dateisystemzugriff |
| `loeseAusgabePfad` (#49) liefert `ok: false` (Pfadtrenner, `..`, unzulässige Zeichen, reservierter Windows-Name, Ausbruch aus `output/`) | `ungueltige_eingabe` (**durchgereicht**) | kein Pfad, kein Dateisystemzugriff; der Code wird **nicht** in `keine_ausgabe` umgedeutet |
| Datei existiert nicht (`ENOENT`) | `keine_ausgabe` | Meldung nennt den **Dateinamen** (nicht den absoluten Pfad) und dass er neu gerendert oder ein anderer gewählt werden muss |
| Pfad existiert, ist aber kein reguläres File (Verzeichnis o. ä.) | `keine_ausgabe` | wie oben |
| `stat` scheitert anderweitig (`EACCES`, `EIO`, …) | `keine_ausgabe` | Betriebssystem-Code steht in der `meldung`, **nie** im `code` (s. ENTSCHIEDEN) |
| unerwartete Ausnahme | `unbekannter_fehler` | fangen und in das Ergebnis wandeln; **kein** `throw`, **kein** Stacktrace in der Meldung |

Es wird **kein** Fehlercode erfunden: „**3. Fehlercodes sind ein geschlossener, typisierter Satz:**
die fachlichen je Operation (9.4.9, 9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`,
`nicht_gefunden`, `unbekannter_fehler`. **Eine rohe Exception-Meldung wird nie zum Code.**"
(TK 9.1.1)

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – kein eigenes `path.join`, kein eigenes `path.resolve`, kein eigenes Layout-Wissen.**
  Der Pfad entsteht **ausschließlich** durch `loeseAusgabePfad(projektId, ausgabeName)` (#49). Auch
  `ausgabeOrdner(projektId)` (aus derselben Datei) darf hier **nicht** benutzt werden, um selbst
  zusammenzusetzen: `ausgabeOrdner` ist laut #49 eine reine String-Operation **ohne jede Prüfung**;
  wer damit joint, umgeht genau die Traversal-Schranke, die `loeseAusgabePfad` dafür bereitstellt,
  und macht mit einem präparierten `dateiname` beliebige Dateien des Datenorts auf einen USB-Stick
  kopierbar.
- **Verbot – die Namensvalidierung aus TK 9.2.6 nicht nachbauen.** Keine eigene Prüfung auf `..`,
  Pfadtrenner, reservierte Windows-Namen oder unzulässige Zeichen. Das tut #49, und eine zweite,
  abweichende Prüfung wäre eine zweite Wahrheit: Sobald die beiden unterschiedlich streng sind,
  weiß niemand mehr, welche gilt.
- **Verbot – `listeAusgaben` (#75) wird hier NICHT aufgerufen.** Diese Funktion prüft **einen**
  bekannten Namen; sie listet den Ordner nicht, sucht nicht nach ähnlichen Namen und schlägt keine
  Alternative vor. Die Liste ist Sache der Oberfläche.
- **Verbot – kein D1-Zugriff.** `project.json` wird nicht geöffnet, kein `mitD1Lock`, kein
  `öffneProjekt`. Der Ausgabeordner ist eine Dateiablage, kein Datenbestand; TK 9.5.2 hält für
  `listeAusgaben` dasselbe fest.
- **Verbot – keine `.part`-Dateien als Quelle.** Endet der Name auf `.part`, ist er kein `.mp4`
  und wird von Schritt 2 abgewiesen. Eine halb geschriebene Datei auf den Stick zu kopieren, ergäbe
  am Fernseher ein Video, das mitten im Abspielen abbricht.
- **Verbot – keine inhaltliche Prüfung der Datei.** Kein Blick in den Dateikopf, kein `ffprobe`,
  keine Mindestgröße. Die Datei ist per Rename-mit-Ersetzen entstanden (TK 9.2.6) – existiert der
  Name, ist sie vollständig. Eine zweite, unzuverlässige Prüfung derselben Aussage bringt nur
  Fehlalarme.
- **Verbot – nichts verändern.** Diese Funktion legt nichts an, löscht nichts, benennt nichts um
  und öffnet die Datei nicht zum Schreiben. Ein offen gehaltener Handle wäre auf Windows genau die
  Ursache für `EBUSY` beim späteren Aufräumen.

## Definition of Done
- [ ] `loeseExportQuelle` liefert `ungueltige_eingabe` **ohne** jeden `fs`-Aufruf für: leere
      `projektId`, leerer `dateiname`, `dateiname` ohne `.mp4`-Endung (`"sommer"`, `"sommer.mov"`,
      `"sommer.mp4.part"`), `dateiname` genau `".mp4"` (Test mit Spy auf das `fs`-Modul)
- [ ] `sommeraktion.mp4` wird nachweislich als `loeseAusgabePfad(projektId, 'sommeraktion')`
      aufgelöst – also **ohne** Endung übergeben (Test mit Spy auf `loeseAusgabePfad`, der das
      zweite Argument prüft)
- [ ] `sommer.aktion.mp4` wird zu `loeseAusgabePfad(projektId, 'sommer.aktion')` – es wird **nur**
      die Endung abgeschnitten, nicht ab dem ersten Punkt gekürzt
- [ ] `FERIEN.MP4` wird akzeptiert und zu `loeseAusgabePfad(projektId, 'FERIEN')` aufgelöst
- [ ] Liefert `loeseAusgabePfad` `ok: false`, wird `ungueltige_eingabe` durchgereicht und **kein**
      `stat` aufgerufen (Test mit Spy)
- [ ] In dieser Datei kommt nachweislich **kein** `path.join`/`path.resolve` auf den Ausgabeordner
      vor (Prüfung durch Codeinspektion im Test oder Spy auf `ausgabeOrdner`, der nie gerufen wird)
- [ ] Eine fehlende Datei liefert `keine_ausgabe`; die `meldung` enthält den **Dateinamen** und
      **nicht** den absoluten Pfad
- [ ] Eine vorhandene Datei liefert `{ quellPfad, dateigroesse }` mit der echten Bytegröße
      (Test mit temporärer Datei bekannter Größe)
- [ ] Ein Verzeichnis unter dem aufgelösten Pfad liefert `keine_ausgabe`, kein `ok: true`
- [ ] Keine Fehlersituation führt zu einem `throw`
- [ ] Keine Datei außerhalb von `src/main/export-service/quelle.ts` (+ zugehörige Testdatei)
      geändert
