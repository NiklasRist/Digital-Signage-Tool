### Issue M6-35: [export-service] Den Export-Handler bei der Auftragsverwaltung anmelden

## Ziel (in einem Satz)
Die Auftragsverwaltung weiß, welche Funktion einen `export`-Auftrag ausführt, sodass ein
eingereihter Export tatsächlich läuft, statt beim Dispatcher ins Leere zu fallen.

## Modul & Datei
- Modul: `export-service` (Main)
- Datei: `src/main/export-service/handler-anmeldung.ts`
- Vertrag: Technisches Konzept **9.3.2** (Auftragsarten und ausführende Dienste – Quelle der
  Wahrheit), ergänzend **9.6.1** (die Operation `export`), **9.6.5** (Verzahnung mit der Queue),
  **9.3.4** (Aufruf über `reiheEin`), **9.1.1** Punkt 1 (Aufruf-Ergebnis ≠ Auftrags-Ergebnis)
- Prozess/Speicher: P4 (Export-Teil) ↔ P6. **Kein** eigener Speicher, **kein** Dateizugriff,
  **kein** IPC-Kanal (`kanaele.ts` wird hier **nicht** angefasst).

## Warum das im Gesamtsystem wichtig ist
Der Dispatcher der Auftragsverwaltung wählt den Ausführenden **allein über `auftrag.art`** und kennt
keinen Fachdienst beim Namen – genau so ist die Schichtung gedacht: „Sie **plant, ordnet und
protokolliert** nur — sie ersetzt keine Fachlogik." (TK 9.3). Die Kehrseite: Ohne diese Anmeldung
findet der Dispatcher für `export` **keinen** Handler.

**Für `export` gibt es heute gar nichts.** #92 meldet die Handler für `import` und `loeschen` an,
#68 verzahnt den `render`-Handler (angemeldet in M6-34). Die vierte Auftragsart hat bislang
**keine** Anmeldestelle. Ohne dieses Issue liefe jeder Export mit `unbekannter_fehler` ins Leere –
sichtbar als ein Auftrag, der sofort und immer fehlschlägt, ohne dass an `exportiereAusgabe`
irgendetwas falsch wäre. Das ist genau die Fehlerklasse, die in den Prüfläufen von M1, M2, M3 und
M5 wiederholt gefunden wurde: fertige Funktionen, die niemand je aufruft. Betroffen sind
**FA-09** („Eine gewählte Ausgabedatei kann in einen Zielordner bzw. direkt auf den USB-Speicher
exportiert werden – **unter ihrem eigenen Namen**. Auf dem Speicher dürfen mehrere Ausgabedateien
nebeneinander liegen.") und der zweite Teil von **Akzeptanzkriterium 2**.

Die zweite Eigenschaft dieser Datei ist, dass sie **keine zweite Leistung** hat: `exportiereAusgabe`
(M6-33) **ist** bereits ein Handler. Die Funktion trägt die Handler-Signatur
`(auftrag, kontext) => Promise<HandlerErgebnis<…>>` und liefert den Auftrags-Ausgang fertig – mit
Status, fachlichem Fehlercode und Nutzdaten. Diese Datei reicht sie deshalb **unverändert** an die
Registry weiter: keine Hülle, keine Umwandlung, kein zweites Ergebnis. Jede Zwischenschicht wäre
eine zusätzliche Stelle, an der ein Fehlercode verloren gehen kann, und TK 9.1.1 nennt die Folge:
„Geht der Code verloren, degradieren Reparatur-Modus, Wiederholen und der FAT32-Hinweis alle zu
„irgendwas ist schiefgelaufen"." Beim Export ist das besonders greifbar: `datei_zu_gross_fat32`
muss zur exFAT-Empfehlung führen, `ziel_gesperrt` zu „Programm schließen", `kein_platz` zu
„aufräumen" – drei verschiedene Handlungen aus drei verschiedenen Codes.

Wirft ein Handler statt zu antworten, bleibt der Auftrag auf `laeuft` stehen; da die serielle
Ordnung der **einzige** Sperr-Mechanismus des Systems ist, steht danach die **gesamte**
Warteschlange still – kein Import, kein Löschen, kein Render, kein Export mehr in dieser Sitzung.
Dass das nicht passiert, sichert M6-33 in seinem eigenen Vertrag zu („Sie wirft NIE"); diese Datei
baut dafür **kein** zusätzliches Sicherheitsnetz.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/export-service/handler-anmeldung.ts

export function meldeExportHandlerAn(): void
// 1. trägt für art: 'export' die Funktion exportiereAusgabe (M6-33) DIREKT als Handler ein
// 2. registriert für diese Art KEINEN Abbrecher (dritter Parameter bleibt weg)
```

**ENTSCHIEDEN – der Name lautet `meldeExportHandlerAn`.** Im Main-Baum stehen bereits
`registriereAuftragsHandler` (#60, die Registry), `registriereRenderHandler` (#68, die
Render-Verzahnung), `registriereHandler` (#23, der IPC-Kanal-Wrapper) und `registriereMedienHandler`
(#92). Ein fünfter Name im selben Wortfeld wäre eine Einladung zum falschen Import – und ein
falscher Import wäre tückisch, weil mehrere Kandidaten kompilieren. `meldeExportHandlerAn` steht
sichtbar daneben; dasselbe Muster gilt für den Render (`meldeRenderHandlerAn`, M6-34).

**ENTSCHIEDEN – kein Abbrecher.** Der dritte Parameter von `registriereAuftragsHandler` bleibt
**weg**, damit `kannAbbrechen('export')` `false` liefert. Begründung aus dem Anforderungsdokument,
FA-18, wörtlich: „Ein noch nicht gestarteter Auftrag kann aus der Warteschlange entfernt, ein
laufender Render abgebrochen werden." Abbrechbar ist also **nur** der Render; ein **anstehender**
Export lässt sich weiterhin über `entferne` aus der Schlange nehmen, das braucht keinen Abbrecher.
Technisch wäre ein Abbruch mitten im Kopieren zudem der gefährlichste Zeitpunkt: Es liegt eine
unvollständige `.part` am Ziel, und jede halbfertige Abbruch-Aufräumung könnte die vorhandene
gültige Zieldatei berühren – genau das, was TK 9.6.3 ausschließt.

### Fremde Funktionen und Typen, die du benutzt
Der umsetzende Agent sieht die anderen Issues **nicht**; deshalb hier alles ausgeschrieben:

```ts
// #60 – auftrags-manager, Handler-Registry (src/main/auftrags-manager/dispatcher.ts)
// ACHTUNG: heißt registriereAuftragsHandler, NICHT registriereHandler
// (registriereHandler ist der IPC-Kanal-Wrapper des ipc-gateway, #23)
export interface AusfuehrungsKontext {
  auftragId: string
  meldeFortschritt: (prozent: number | null) => void
}

export type HandlerErgebnis<F extends string = string> =
  | { status: 'erfolg'; ergebnis: unknown | null }
  | {
      status: 'fehlgeschlagen'
      fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown }
    }
  | { status: 'abgebrochen' }
// `ergebnis` trägt die fachlichen Nutzdaten des Dienstes und landet in `Auftrag.ergebnis`
// (TK 9.3.1); `fehler.daten` trägt die Nutzdaten des Fehlercodes (TK 9.1.1).

export type HandlerFuer<A extends AuftragArt> = (
  auftrag: Extract<Auftrag, { art: A }>,
  kontext: AusfuehrungsKontext,
) => Promise<HandlerErgebnis<string>>
// Der Dispatcher nimmt das Ergebnis als HandlerErgebnis<string> entgegen - der weiteste Typ, weil
// er die fachlichen Unionen weder kennt noch kennen darf - und reicht es unveraendert weiter.
// HandlerErgebnis<ExportFehlercode> ist darauf zuweisbar; ein Adapter ist NICHT noetig.

export function registriereAuftragsHandler<A extends AuftragArt>(
  art: A,
  handler: HandlerFuer<A>,
  brichAb?: (auftrag: Auftrag) => void,
): void
// genau EIN Handler je Art; fehlt brichAb, ist die Art NICHT abbrechbar

// #12 + #22 (src/shared/contracts/ergebnis.ts)
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'

// M6-33 (src/main/export-service/export.ts) – DEFINIERENDE QUELLE
// Diese Funktion IST bereits ein Handler - Signatur und Rueckgabetyp passen unveraendert
// auf HandlerFuer<'export'>.
export async function exportiereAusgabe(
  auftrag: Extract<Auftrag, { art: 'export' }>,
  kontext: AusfuehrungsKontext,
): Promise<HandlerErgebnis<ExportFehlercode>>
// Erfolg: { status: 'erfolg', ergebnis: { zielPfad, dateigroesse } }
//         zielPfad = VOLLSTÄNDIGER Pfad der geschriebenen Zieldatei (TK 9.6.1)
// Fehler: { status: 'fehlgeschlagen', fehler: { code, meldung } }
// Sie wirft nie und liefert nie { status: 'abgebrochen' }.

// M6-27 (src/main/export-service/fehlercodes.ts)
export type ExportFehlercode =
  | 'keine_ausgabe' | 'ziel_nicht_verfügbar' | 'datei_zu_gross_fat32'
  | 'kein_platz' | 'ziel_gesperrt' | 'schreib_fehler' | 'speicher_fehler'
// SIEBEN Werte (`speicher_fehler` ist der Zusatz aus TK v2.9; vergeben wird er in M6-33).

// M6-01 (src/shared/contracts/export-request.ts) - die Nutzlast, die in auftrag.payload liegt
export interface ExportRequest { projektId: string; dateiname: string; zielPfad: string }
```

**MELDE-KLAUSEL (bindend).** Weicht eine dieser Signaturen von der tatsächlichen Fassung des
Nachbar-Issues ab, ist das ein Widerspruch zwischen zwei Issues: **STOPP und fragen**, nicht die
fremde Datei anpassen (Regel E) und **nicht** hier einen Adapter „passend machen". Das gilt
besonders für `exportiereAusgabe` (M6-33) und `ExportRequest` (M6-01) – beide entstehen parallel zu
diesem Issue.

### Der Ablauf (verbindlich)
Der ganze Rumpf von `meldeExportHandlerAn()` besteht aus **einem** Aufruf:

```
registriereAuftragsHandler('export', exportiereAusgabe)
```

– die Funktionsreferenz aus M6-33, **ohne** dritten Parameter.

Mehr passiert hier nicht. Insbesondere gibt es **keinen** Schritt, der ein Ergebnis auswertet,
umwandelt, prüft, fängt oder neu zusammensetzt: Was `exportiereAusgabe` liefert, **ist** bereits das
`HandlerErgebnis`, das die Auftragsverwaltung erwartet – samt Status, fachlichem Fehlercode,
`meldung` und `ergebnis`. Auch `auftrag` und `kontext` werden hier weder angefasst noch
weitergegeben; der Dispatcher übergibt sie direkt an die Fachfunktion.

**„Direkt" heißt: die Funktionsreferenz selbst, nicht ein Lambda um sie herum.** Die Fachfunktion
hat bereits exakt die von der Registry verlangte Handler-Signatur (`HandlerFuer<'export'>`). Ein
`async (auftrag, kontext) => { … }` dazwischen wäre eine **Übersetzungsschicht** – und damit genau
die zweite Stelle, an der ein Fehlercode, ein `daten`-Feld oder das Auftrags-Ergebnis verloren
gehen kann. Es gibt hier keine.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – (`meldeExportHandlerAn` hat kein Argument) | einmalige Anmeldung beim Programmstart, gerufen von #3 (s. STOPP) | ein zweiter Aufruf würde die Art erneut registrieren; #3 ruft genau einmal, und diese Datei ruft sich **nicht selbst** |
| `auftrag`, `kontext` | **kein Eingang dieser Datei** | Dispatcher → Fachfunktion; diese Datei sieht die beiden Werte nie, weil sie keinen Rumpf um die Fachfunktion legt |

Ausgang: `meldeExportHandlerAn` liefert nichts (`void`); Wirkung ist **ein** eingetragener Handler
für `art: 'export'` und **kein** eingetragener Abbrecher.
Was die eingetragene Funktion zurückgibt, legt **ihr** Vertrag fest (M6-33:
`{ zielPfad, dateigroesse }` in `ergebnis`) – diese Datei bestimmt darüber nichts.
Ausgang bei Fehler: Diese Funktion ist **keine** IPC-Operation und trägt **keine** Ergebnis-Hülle.
Fehler des Vorgangs reisen über den Auftrags-Zustand: „**Auftrags-Ergebnis:** Wie ging der *Vorgang*
aus (`RenderResult`, Export-Ergebnis …)? Das reist **nicht** als Aufruf-Antwort, sondern über den
**Auftrags-Zustand** (9.3)." (TK 9.1.1, Punkt 1)

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Zuordnung laut Tabelle TK 9.3.2 (Spalten `art` / ausführender Dienst / Nutzlast), wörtlich:

  | `art` | ausführender Dienst | Nutzlast |
  |---|---|---|
  | `export` | `export-service` | `ExportRequest` |

  Diese Datei trägt genau **diese eine** Art ein – **keine** zweite, insbesondere **nicht**
  `render` (das ist M6-34) und **nicht** `import`/`loeschen` (das ist #92).
- „`import`, `loeschen`, `render` und `export` werden damit **nicht** als direkte
  Request/Response-Operationen aufgerufen, sondern über `reiheEin` eingereiht; ihr Fach-Ergebnis
  (`erfolg`/`fehlgeschlagen` samt Fachfehlercode) kommt über den Auftrags-Zustand." (TK 9.3.4) –
  deshalb wird hier **kein** IPC-Kanal angemeldet.
- „**Auftrags**-Ergebnis bei Erfolg: `{ zielPfad, dateigroesse }` – über den **Auftrags-Zustand**,
  **nicht** als Aufrufantwort (9.1.1); der Aufruf ist `reiheEin('export', …)` →
  `Ergebnis<{ auftragId }>`." (TK 9.6.1)
- „`export` ist ein Auftrag der Auftragsverwaltung (9.3): seriell **nach** dem Render; ein
  Fehlschlag (Stick voll/abgezogen) landet in **Q2** und ist per „erneut einreihen" wiederholbar,
  sobald der Nutzer das Ziel behoben hat – genau der Wiederhol-Fall aus FA-17." (TK 9.6.5) – die
  Wiederholung erledigt die Auftragsverwaltung über denselben hier eingetragenen Handler; diese
  Datei baut dafür nichts Zusätzliches.
- „Sie **plant, ordnet und protokolliert** nur — sie ersetzt keine Fachlogik." (TK 9.3)
- FA-18, wörtlich: „Ein noch nicht gestarteter Auftrag kann aus der Warteschlange entfernt, ein
  laufender Render abgebrochen werden." – **nur** der Render ist abbrechbar; deshalb **kein**
  `brichAb` für `export`.
- **Niemals `throw`.** Wirft die Anmeldung, startet die App nicht sauber. Sie hat aber auch nichts,
  was werfen könnte: Sie ruft eine Funktion mit einer Zeichenkette und einer Funktionsreferenz auf.

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – keine Übersetzungsschicht, kein Lambda.** `exportiereAusgabe` wird als
  **Funktionsreferenz** eingetragen. Kein `async (auftrag, kontext) => exportiereAusgabe(...)`,
  kein `try/catch`, kein Umformen des Ergebnisses, kein Ergänzen von Feldern. Begründung oben.
- **Verbot – kein dritter Parameter.** `brichAb` bleibt weg. Wer ihn ergänzt, macht den Export
  abbrechbar, obwohl FA-18 das nicht vorsieht – und das `queue-panel` böte dann einen Knopf an, der
  mitten in einem Kopiervorgang auf ein Wechselmedium eingreift.
- **Verbot – keine zweite Art anmelden.** Diese Datei trägt **nur** `export` ein. `import` und
  `loeschen` gehören #92, `render` gehört M6-34. Wer hier „der Vollständigkeit halber" eine zweite
  Art registriert, überschreibt eine fremde Registrierung (#60: eine erneute Registrierung ersetzt
  die vorherige vollständig) – und je nach Startreihenfolge fällt das erst zur Laufzeit auf.
- **Verbot – diese Datei ruft sich nicht selbst auf.** Kein `meldeExportHandlerAn()` am Modulende,
  kein Seiteneffekt beim Import. Die Anmeldung gehört in die **feste Startreihenfolge** des
  Bootstraps: „Warum das hier steht und nicht in den Modulen selbst: Eine Stelle, eine nachlesbare
  Reihenfolge. Eine Anmeldung „beim ersten Import des Moduls" hinge davon ab, wer wen zuerst
  importiert – eine klassische Quelle für Fehler, die nur manchmal auftreten und sich beim
  Umstellen einer einzigen `import`-Zeile anders verhalten. Und ohne feste Stelle kann ein früh
  eingereihter Auftrag ins Leere laufen, weil zu diesem Zeitpunkt noch kein Handler registriert
  ist." (#3)
- **Verbot – `src/main/index.ts` (#3) wird von diesem Issue NICHT geändert.** Dass
  `meldeExportHandlerAn()` dort in die feste Startreihenfolge aufgenommen wird, zieht der
  Auftraggeber nach; die Datei gehört einem anderen Issue (Regel E).
- **Verbot – kein IPC-Kanal.** `kanaele.ts` wird hier nicht angefasst, `registriereHandler` (#23)
  nicht aufgerufen. Ein Export wird **nie** direkt aufgerufen, sondern über `reiheEin` eingereiht
  (TK 9.3.4). Der **einzige** Export-Kanal des Systems ist `export:wähleExportZiel`, und der wird
  in M6-36 angemeldet.
- **Verbot – keine Absicherung gegen doppelte Registrierung hier.** Kein „schon angemeldet"-Flag,
  kein Idempotenz-Schutz. Was bei einer zweiten Registrierung geschieht, legt #60 fest.
