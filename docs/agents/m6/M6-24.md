### Issue M6-24: [render-service] Abbruch entgegennehmen

## Ziel (in einem Satz)
`cancelRender(renderId)` stoppt den laufenden ffmpeg-Prozess und sorgt dafür, dass der Lauf über
seinen **einen** terminalen Ausgang mit `RenderResult { status: 'abgebrochen' }` endet – ohne ein
zweites Abbruch-Flag und ohne ein zweites Lock.

## Modul & Datei
- Modul: `render-service` [P4] (Main)
- Datei: `src/main/render-service/abbruch.ts`
- Vertrag: Technisches Konzept **9.2.7** (Abbruch), **9.2.3** (`RenderResult`, Aufräumen),
  **9.3.5** (serielle Invariante, kein zweites Lock), **9.3.6** (Verzahnung) – Quelle der Wahrheit
- Prozess/Speicher: P4; hält **nur Laufzeitzustand** (die Registrierung des laufenden Laufs), keine
  Datei, keinen Speicher

## Warum das im Gesamtsystem wichtig ist
Der Render ist der einzige Vorgang im ganzen Werkzeug, der Minuten dauert. Ohne Abbruch müsste der
Nutzer einen versehentlich gestarteten 40-Minuten-Lauf aussitzen – und weil die Warteschlange
**streng seriell** ist, stünde in dieser Zeit auch jeder Import, jedes Löschen und jeder Export
still. Der Abbruch ist damit nicht Komfort, sondern der Notausgang aus der einzigen Sperre des
Systems.

Drei lokale Entscheidungen sind hier besonders teuer:

**Erstens ein zweites Lock oder ein zweites Abbruch-Flag.** Die serielle Ordnung der
Auftragsverwaltung ist der **einzige** Sperr-Mechanismus des Systems. Wer hier eine eigene
„läuft gerade“-Sperre einführt, hat zwei Wahrheiten über denselben Zustand – und die eine wird
irgendwann nicht mit aufgeräumt. Dasselbe gilt für ein zweites Abbruch-Kennzeichen neben dem hier
geführten: Wird nur eines gesetzt, läuft der Render weiter, obwohl die Oberfläche „abgebrochen“
zeigt.

**Zweitens das Löschen zur falschen Zeit.** Wer hier sofort T1 und die `.part`-Datei entfernt,
löscht Dateien, die der eben gestoppte ffmpeg-Prozess noch offen hält. Auf Windows scheitert das mit
`EBUSY`/`EPERM`; auf macOS gelingt der `unlink` still, obwohl die Datei noch geöffnet ist – der
Speicher wird also erst frei, wenn der Prozess wirklich endet, und in der Zwischenzeit schreibt er
in eine Datei, die es nicht mehr gibt. Beide Fälle sind Plattform-Fallen, die im Entwicklungsalltag
nicht auffallen.

**Drittens ein Aufruf, der hängt.** Wenn `cancelRender` auf das Prozessende wartet und der Prozess
nicht reagiert, hängt die Oberfläche an der Stelle, an der der Nutzer gerade „Abbrechen“ gedrückt
hat.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/render-service/abbruch.ts

export interface LaufRegistrierung {
  /** true, sobald cancelRender fuer GENAU DIESEN Lauf gerufen wurde. */
  istAbgebrochen(): boolean
  /**
   * DASSELBE Abbruch-Kennzeichen in der Form, die der ffmpeg-adapter versteht
   * (FfmpegLauf.abbruchSignal, M6-03). KEIN zweites Flag - eine Quelle, zwei Formen.
   */
  readonly signal: AbortSignal
  /** Am terminalen Ausgang aufzurufen; hebt die Registrierung auf. Idempotent. */
  freigeben(): void
}

/**
 * Meldet den beginnenden Lauf an. renderReel (M6-26) ruft das als ersten Schritt auf und
 * `freigeben()` in seinem finally-Zweig.
 */
export function registriereLauf(renderId: string): LaufRegistrierung

/**
 * Abbruch-Signal. Kommt aus #68 (der Abbrecher des render-Auftrags) und damit letztlich aus
 * `entferne(auftragId)` im queue-panel. Kehrt SOFORT zurueck und wartet NICHT auf das Prozessende.
 */
export function cancelRender(renderId: string): void
```

Die Signatur von `cancelRender` ist **abgeschrieben** aus #68, das diese Funktion als Parameter
entgegennimmt:

```ts
// #68 – src/main/auftrags-manager/render-verzahnung.ts
export function registriereRenderHandler(
  renderReel: (
    request: RenderRequest,
    aufFortschritt: (fortschritt: RenderProgress) => void,
  ) => Promise<RenderResult>,
  cancelRender: (renderId: string) => void,
): void
```

**Weicht die tatsächliche Signatur in #68 davon ab, ist das ein Vertragsfehler – melden, NICHT
eigenmächtig anpassen.** Insbesondere ist `cancelRender` **synchron und ohne Rückgabewert**; ein
`Promise<void>` daraus zu machen bräche den Aufrufer.

## Fremde Bausteine, die du aufrufst
```ts
// M6-04 – src/main/ffmpeg-adapter/abbruch.ts
import type { ChildProcess } from 'node:child_process'

export function merkeProzess(kindProzess: ChildProcess): void
// Merkt sich das Handle des laufenden ffmpeg-Prozesses. Es gibt genau EINEN Platz.
// DIESE Datei ruft das NICHT auf - verdrahtet wird es in renderReel (M6-26) ueber
// FfmpegLauf.aufProzessStart.

export function gibProzessFrei(kindProzess: ChildProcess): void
// Gibt den Platz wieder frei. Ebenfalls NICHT von dieser Datei gerufen.

export function beendeLaufendenProzess(): Promise<void>
// Beendet den gemerkten Prozess plattformsicher.
// Loest IMMER auf - auch wenn kein Prozess gemerkt ist, der Prozess schon tot ist
// oder das Beenden selbst fehlschlaegt. Lehnt NIE ab und wirft NIE.
// DAS ist die eine Funktion, die cancelRender aufruft.
```

**Die definierende Datei gewinnt: Weicht die tatsächliche Signatur von M6-04 ab, ist das ein
Vertragsfehler – melden, NICHT eigenmächtig anpassen und keine eigene Prozessverwaltung bauen.** Wer
hier selbst `child_process`, `process.kill` oder `taskkill` anfasst, erzeugt die zweite Stelle im
Projekt, die ffmpeg-Prozesse kennt – und die eine räumt dann auf, während die andere noch schreibt.

Und aus M6-03, warum die Registrierung ein `AbortSignal` mitliefern muss:

```ts
// M6-03 – src/main/ffmpeg-adapter/prozess.ts
export interface FfmpegLauf {
  argumente: readonly string[]
  aufAusgabeZeile?: (zeile: string) => void
  aufProzessStart?: (kindProzess: ChildProcess) => void
  abbruchSignal?: AbortSignal   // <- hier kommt LaufRegistrierung.signal an
}
export type FfmpegFehlercode = 'ffmpeg_fehler' | 'ffmpeg_abgebrochen'
```

Der Adapter **killt nicht** anhand des Signals – er **deutet** damit nur, ob ein abgebrochener Lauf
`ffmpeg_abgebrochen` statt `ffmpeg_fehler` melden soll. Getötet wird über
`beendeLaufendenProzess()`. Deshalb braucht der Abbruch **beides** aus **einer** Quelle: das Signal
für die Deutung, den Aufruf für die Wirkung.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `renderId` (`registriereLauf`) | die ID des beginnenden Laufs, aus `RenderRequest.renderId` | nicht leer; sie wird **vom Renderer vergeben** (TK 9.2.1) |
| `renderId` (`cancelRender`) | der Lauf, der gestoppt werden soll | stimmt sie nicht mit dem registrierten Lauf überein, passiert **nichts** – s. u. |

Ausgang: kein Rückgabewert. Wirkung ist (a) das gesetzte Abbruch-Kennzeichen und (b) der gestoppte
ffmpeg-Prozess.
Ausgang bei Fehler: Diese Datei ist **keine** IPC-Operation und trägt **keine** Ergebnis-Hülle. Der
Ausgang des Laufs reist über den Auftrags-Zustand: „**Auftrags-Ergebnis:** Wie ging der *Vorgang*
aus (`RenderResult`, Export-Ergebnis …)? Das reist **nicht** als Aufruf-Antwort, sondern über den
**Auftrags-Zustand** (9.3).“ (TK 9.1.1, Punkt 1)

## ENTSCHIEDEN (lokale Festlegungen dieses Issues – verbindlich, nicht erneut abwägen)

- **`cancelRender` mit einer unbekannten oder veralteten `renderId` tut GAR NICHTS** – kein Fehler,
  kein Protokolleintrag als Warnung, kein `throw`. Grund: Der Aufruf kommt aus der Oberfläche; ein
  Klick auf „Abbrechen“ kann eintreffen, nachdem der Lauf gerade von selbst fertig geworden ist.
  Ein Fehler an dieser Stelle wäre für den Nutzer unverständlich – er hat richtig gehandelt, es war
  nur zu spät. Ausserdem darf ein Abbruch **niemals** einen fremden, inzwischen gestarteten Lauf
  treffen; genau dagegen schützt der Vergleich der `renderId`.
- **`cancelRender` kehrt sofort zurück und wartet NICHT auf das Prozessende.** `beendeLaufendenProzess()`
  (M6-04) liefert ein `Promise<void>`, das **immer** auflöst und **nie** ablehnt; es wird deshalb
  bewusst **nicht** abgewartet, sondern als „starten und weitergehen“ aufgerufen (in TypeScript
  `void beendeLaufendenProzess()`), damit `cancelRender` synchron bleiben kann. Dass der Lauf danach
  wirklich endet, stellt `renderReel` fest, indem sein `await` zurückkehrt.
- **Das Abbruch-Kennzeichen existiert in ZWEI Formen aus EINER Quelle.** Intern hält die
  Registrierung einen `AbortController`; `istAbgebrochen()` liest dessen Zustand, `signal` gibt
  dessen `AbortSignal` heraus, und `cancelRender` ruft genau einmal `abort()`. Das ist **kein**
  zweites Flag: Es gibt einen Zustand, der auf zwei Arten gelesen werden kann. Der `ffmpeg-adapter`
  braucht die Signal-Form, weil `FfmpegLauf.abbruchSignal` (M6-03) darüber entscheidet, ob ein
  beendeter Lauf als `ffmpeg_abgebrochen` statt als `ffmpeg_fehler` gemeldet wird; `renderReel`
  braucht die Frage-Form, um zwischen den Schritten zu prüfen. Zwei **unabhängige** Kennzeichen wären
  der Fehler – dann meldete der Adapter „abgebrochen“, während `renderReel` noch „läuft“ denkt.
- **`registriereLauf` erzeugt für jeden Lauf einen FRISCHEN `AbortController`.** Ein
  wiederverwendeter Controller wäre nach dem ersten Abbruch dauerhaft ausgelöst und liesse jeden
  folgenden Render sofort als abgebrochen enden.
- **Diese Datei löscht KEINE Datei – weder T1 noch die `.part`.** Das Aufräumen gehört zum
  **einen** terminalen Ausgang in `render-reel.ts` (M6-26), und zwar aus einem harten Grund: Erst
  dort ist das `await` des ffmpeg-Aufrufs zurückgekehrt, also der Prozess wirklich beendet und das
  Datei-Handle freigegeben. Räumte diese Datei sofort auf, liefe sie auf Windows in `EBUSY`/`EPERM`
  und auf macOS in einen stillen `unlink` bei noch offener Datei. **Die Zusage aus TK 9.2.7 – T1
  *und* die angefangene `<name>.mp4.part` werden aufgeräumt – bleibt damit vollständig erfüllt; sie
  wird nur an der Stelle eingelöst, an der sie gefahrlos einlösbar ist.** M6-26 räumt in **jedem**
  Zweig auf, also auch im Abbruch-Zweig.
- **Es gibt genau EINE Registrierung zur Zeit.** Ein zweites `registriereLauf`, während noch eines
  aktiv ist, ersetzt es und wird intern protokolliert. Diese Datei **verhindert** den zweiten Lauf
  nicht: Die serielle Garantie ist Sache des Torwächters (#59), und ein zweiter Mechanismus hier
  wäre genau das zweite Lock, das TK 9.3.5 verbietet.
- **`freigeben()` und mehrfaches `cancelRender` sind idempotent.** Zweimal abbrechen setzt dasselbe
  Kennzeichen und stösst den Stopp erneut an – beides folgenlos. Zweimal freigeben ist wirkungslos.
- **`istAbgebrochen()` bleibt auch nach `freigeben()` bei `true`, wenn abgebrochen wurde.** Die
  Registrierung, die `renderReel` in der Hand hält, ist an **ihren** Lauf gebunden; sie darf ihre
  Antwort nicht ändern, während der terminale Ausgang sie noch einmal abfragt.
- **Kein Zeitgeber, kein „hart nachtreten“.** Wenn der Prozess nach dem Stopp nicht endet, ist das
  ein Problem des `ffmpeg-adapter` (M6-04), nicht dieser Datei. Ein hier eingebauter zweiter
  Kill-Versuch nach *n* Sekunden wäre die zweite Prozessverwaltung.

## Der Ablauf eines Abbruchs, vollständig
1. Der Nutzer drückt im `queue-panel` „Abbrechen“ → `entferne(auftragId)` (#62).
2. Der Auftrag `laeuft` und hat `art: 'render'` → die Auftragsverwaltung ruft den bei ihr
   registrierten Abbrecher, der die `renderId` aus `auftrag.payload` zieht und `cancelRender(renderId)`
   aufruft (#68, Punkt 4). „`entferne` auf einen laufenden `render` delegiert an
   `cancelRender(renderId)`; die `renderId` liegt im `RenderRequest` des Auftrags — `auftragId` und
   `renderId` bleiben fest verknüpft.“ (TK 9.3.6)
3. **Hier:** `renderId` stimmt mit dem registrierten Lauf überein → Kennzeichen setzen, Stopp an
   M6-04 geben, sofort zurückkehren.
4. Der laufende ffmpeg-Aufruf in `renderReel` kehrt zurück (mit Fehler oder abgebrochen).
5. `renderReel` fragt `istAbgebrochen()` und wählt den Ausgang `RenderResult { status:
   'abgebrochen' }` statt eines Fehlers – **ein abgebrochener Lauf ist kein Fehlschlag.**
6. `renderReel` räumt in seinem terminalen Zweig T1 **und** die `.part` auf und ruft `freigeben()`.
7. Die Auftragsverwaltung übersetzt `status: 'abgebrochen'` in den Auftrags-Zustand `abgebrochen`
   (#68, Punkt 3) – **ohne** `fehler`-Objekt.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Abbruch `cancelRender` (Renderer → Main):** Signal mit `renderId`. Der Main stoppt den laufenden
  `ffmpeg`-Prozess, räumt T1 **und die angefangene `<name>.mp4.part` im Ausgabeordner** auf und
  schließt den Lauf mit `RenderResult { status: abgebrochen }` ab (9.2.3).“ (TK 9.2.7)
- „Bei `fehler` und `abgebrochen` entsteht **keine** neue Ausgabedatei; eine **bereits vorhandene
  Datei gleichen Namens bleibt unversehrt** (9.2.6). Aufgeräumt sind in beiden Fällen **der
  Arbeitsbereich T1 *und* die angefangene `<name>.mp4.part` im Ausgabeordner** – sonst bliebe im
  Ausgabeordner eine wachsende Leiche liegen.“ (TK 9.2.3)
- „**`abgebrochen` ist *kein* Fehlercode.**“ (TK 9.2.3) – der Abbruch bekommt **kein**
  `fehler`-Objekt und **keinen** Code; sonst zeigte die Oberfläche einen vom Nutzer selbst
  ausgelösten Abbruch als Fehler an.
- „Genau **ein** terminaler Ausgang je Lauf, diskriminiert über `status` ∈ { `erfolg`, `fehler`,
  `abgebrochen` }. Alle drei tragen die `renderId`.“ (TK 9.2.3)
- „**Seriell:** höchstens **ein** Auftrag in `laeuft`. Das ist der einzige Sperr-Mechanismus des
  Systems; ein zweites Lock ist nicht nötig und darf nicht eingeführt werden.“ (TK 9.3.5)
- „`entferne` auf einen laufenden `render` delegiert an `cancelRender(renderId)`; die `renderId`
  liegt im `RenderRequest` des Auftrags — `auftragId` und `renderId` bleiben fest verknüpft.“
  (TK 9.3.6)
- „Der Fortschrittskanal trägt **keinen** Endzustand. Erfolg, Fehler und Abbruch kommen
  **ausschließlich** über das `RenderResult` (9.2.3).“ (TK 9.2.7) – ein Abbruch wird also **nicht**
  als Fortschritts-Ereignis gemeldet.
- Die `renderId` „wird **vom Renderer vergeben**, sodass er verspätete Ereignisse eines alten Laufs
  sicher erkennen kann (9.2.7).“ (TK 9.2.1) – deshalb ist der Vergleich der `renderId` verlässlich
  und nicht nur eine Vorsichtsmassnahme.

## Warnblock: warum ein Fehler hier teuer ist (`risiko:datenverlust`)
Diese Datei entscheidet mit darüber, **wann** die `.part`-Datei im Projekt-Ausgabeordner
verschwindet. Räumt sie zu früh auf, während ffmpeg die Datei noch schreibt, bleibt auf Windows eine
gesperrte Halbdatei liegen (`EBUSY`), die beim nächsten Lauf mit demselben Namen im Weg steht – und
auf macOS läuft der Prozess weiter in eine Datei, die im Verzeichnis schon nicht mehr existiert.
Beides fällt in der Entwicklung nicht auf und trifft den Nutzer als „der Render geht plötzlich nicht
mehr“.

Und der zweite, schwerere Fall: Bricht der Abbruch nicht sauber ab, sondern lässt den Lauf
weiterlaufen, während die Oberfläche ihn schon als abgebrochen führt, schreibt ein „abgebrochener“
Render am Ende doch noch seine Datei über die letzte funktionierende Ausgabe. Genau das schliesst
die Zusicherung aus, dass bei `abgebrochen` **keine** neue Ausgabedatei entsteht.

`RenderResult { status: 'abgebrochen' }` in M6-26 – und das ist ausdrücklich **kein** Fehlercode.

## Nicht selbst entscheiden – STOPP und fragen
- **Führe kein zweites Abbruch-Flag ein.** Es gibt **einen** `AbortController` je Lauf, und er lebt
  in der Registrierung dieser Datei; `istAbgebrochen()` und `signal` sind zwei Sichten auf **ihn**,
  keine zwei Zustände. Verboten ist ein zusätzliches Modul-Flag daneben, ein zweiter Controller pro
  ffmpeg-Aufruf oder ein „hat schon jemand abgebrochen“-Merker in einer anderen Datei.
- **Führe kein Lock ein**, keine „ist gerade ein Render aktiv“-Sperre, kein Mutex, keine
  Warteschlange. Der einzige Sperr-Mechanismus des Systems ist die serielle Ordnung des
  Torwächters (#59). Eine zweite Sperre hier wäre genau der Fehler, den TK 9.3.5 ausschliesst.
- **Lösche hier nichts.** Kein `fs.rm`, kein `unlink`, kein Aufräumen von T1 oder `.part` – das
  gehört in den terminalen Ausgang von M6-26. Wer es hier tut, löscht unter einem noch laufenden
  Prozess.
- **Fasse keinen Prozess direkt an.** Kein `child_process`, kein `process.kill`, kein `taskkill`,
  kein `SIGTERM`. Der Stopp läuft ausschliesslich über M6-04.
- **Mach `cancelRender` nicht asynchron.** Die Signatur ist von #68 vorgegeben; ein `Promise`
  bräche den Aufrufer und liesse die Oberfläche am Abbrechen-Knopf hängen.
- **Behandle den Abbruch nicht als Fehler.** Kein Fehlercode, kein `fehler`-Objekt, kein
  `unbekannter_fehler` – auch nicht „damit man sieht, dass etwas passiert ist“.
