### Issue M6-32: [export-service] Atomar ersetzen: Rename-mit-Ersetzen mit Retry und Backoff

## Ziel (in einem Satz)
Die fertige `.part`-Datei wird in **einem** Schritt zur Zieldatei – auch wenn dort bereits eine
gültige Datei gleichen Namens liegt –, und eine kurzzeitige Windows-Sperre auf dieser Datei führt
nicht sofort zum Fehlschlag, sondern zu einer begrenzten Wiederholung.

## Modul & Datei
- Modul: `export-service` (Main)
- Datei: `src/main/export-service/ersetzen.ts`
- Vertrag: Technisches Konzept **9.6.2** Schritt 5 und **9.6.3** (Quelle der Wahrheit), ergänzend
  **9.6.4** (Fehlercodes)
- Prozess/Speicher: P4 (Export-Teil). Berührt **ausschließlich** die beiden übergebenen Pfade am
  Ziel. **Kein** D1-Zugriff, **kein** Lock, **kein** Lesen oder Schreiben von Dateiinhalten.

## Warum das im Gesamtsystem wichtig ist
**⚠ Warum ein Fehler hier teuer ist (`risiko:datenverlust`).** Dies ist der Moment, in dem die
vorhandene, funktionierende Datei auf dem USB-Stick durch die neue ersetzt wird. **Überschreiben ist
dabei der Regelfall, nicht der Ausnahmefall:** Der vorbelegte Ausgabename ist der zuletzt verwendete
(FA-22), das Studio rendert dieselbe Schleife immer wieder unter demselben Namen, und auf dem Stick
liegt sie unter genau diesem Namen.

Der naheliegende und **falsche** Weg ist: erst die alte Datei löschen, dann die `.part` umbenennen.
Zwischen diesen beiden Schritten existiert die Datei **überhaupt nicht** – wird der Stick in diesem
Moment gezogen oder scheitert der zweite Schritt, ist die einzige lauffähige Werbeschleife des
Studios weg, und die neue ist es auch. TK 9.6.3 verbietet das ausdrücklich: „Eine Datei gleichen
Namens auf dem Ziel wird **nie** gelöscht oder überschrieben, bevor die neue **vollständig kopiert
und größen-verifiziert** ist."

Der zweite teure Punkt ist Windows: Hält ein anderer Prozess die Zieldatei geöffnet – der
Datei-Explorer für die Vorschau, ein Virenscanner, der die eben geschriebene `.part` prüft, oder ein
Mediaplayer, in dem der Nutzer die alte Fassung gerade angesehen hat –, scheitert das Umbenennen mit
`EBUSY` oder `EPERM`. Das ist ein **Zustand von Millisekunden bis wenigen Sekunden**, kein dauerhaftes
Hindernis. Wer beim ersten Versuch aufgibt, lässt einen Export scheitern, der eine Sekunde später
funktioniert hätte – nach einem 2,5-GB-Kopiervorgang, der dann komplett wiederholt werden muss.
TK 9.6.2 Schritt 5 verlangt deshalb wörtlich: „Auf Windows bei `EBUSY`/`EPERM` **Retry+Backoff**."

## Warum diese Datei ihre eigene Retry-Schleife baut (und #86 NICHT importiert)
Es gibt bereits eine Retry-Schleife im Projekt: `entferneDatei` in
`src/main/media-service/datei-entfernen.ts` (**#86**). Sie löst dasselbe Windows-Problem und ist
das **Vorbild** für die Struktur dieser Schleife. Sie wird hier trotzdem **nicht importiert**, und
das ist eine bewusste Entscheidung des Auftraggebers:

1. **#86 gehört zum `media-service`.** Ein Import aus dem `export-service` heraus wäre der **erste
   modulübergreifende Import zwischen zwei Main-Fachdiensten** im ganzen Projekt und damit ein
   Präzedenzfall, der den Modulschnitt aufweicht – ausgerechnet zwischen zwei Diensten, die fachlich
   nichts miteinander zu tun haben.
2. **Die Operationen sind verschieden.** #86 macht `unlink` (löschen), diese Datei macht `rename`
   (ersetzen). Die Fehlerbehandlung unterscheidet sich grundlegend: Für #86 ist `ENOENT` ein
   **Erfolg** (die Datei ist ja weg), hier ist ein fehlender `partPfad` ein **Fehler**. Und die
   Codes sind andere: #86 meldet `datei_fehler` (aus TK 9.4.9), hier gilt `ziel_gesperrt` bzw.
   `schreib_fehler` (aus TK 9.6.4).
3. Wer die Regel „kein modulübergreifender Import" ändern will, hebt sie an **einer** Stelle für
   alle auf – nicht nebenbei in einem Issue.

**Was aus #86 sinngemäß übernommen wird** (dort bereits entschieden, hier gilt dasselbe):
- Wiederholt wird **nur** bei `EBUSY` und `EPERM`. Jeder andere Code führt **sofort** zum
  Fehlschlag, ohne Wartezeit – eine schreibgeschützte Platte oder ein fehlendes Recht bessert sich
  durch Warten nicht, und die Warteschlange steht währenddessen still.
- Das Warten ist ein echtes `await` auf einen Timer, **keine** Beschäftigungsschleife. Eine
  `while`-Schleife, die die Zeit abfragt, blockiert den Main-Prozess und damit die gesamte
  Oberfläche.
- **Kein `chmod`, kein Entfernen von Schreibschutz-Attributen, kein `takeown`.** Wenn eine Datei aus
  Rechtegründen nicht ersetzbar ist, ist das eine Nutzer-Information, kein Hindernis, das das
  Programm eigenmächtig aus dem Weg räumt.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/export-service/ersetzen.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { ExportFehlercode } from './fehlercodes'

/** Anzahl der Umbenennungs-Versuche insgesamt (erster Versuch eingeschlossen). */
export const ERSETZEN_VERSUCHE = 5
/** Wartezeiten in Millisekunden VOR dem 2., 3., 4. und 5. Versuch. */
export const ERSETZEN_BACKOFF_MS = [100, 200, 400, 800] as const

export async function ersetzeAtomar(
  partPfad: string,   // absolut, die fertig kopierte und gesyncte Arbeitsdatei (M6-31)
  zielPfad: string,   // absolut, der endgültige Name: <zielOrdner>/<dateiname>
): Promise<Ergebnis<void, ExportFehlercode>>
// - EIN Aufruf von fs.promises.rename(partPfad, zielPfad) je Versuch – mehr nicht
// - die vorhandene Zieldatei wird NIE vorher gelöscht, geleert oder umbenannt
// - nur EBUSY/EPERM lösen eine Wiederholung aus; nach dem letzten Versuch: 'ziel_gesperrt'
```

**ENTSCHIEDEN – fünf Versuche mit 100/200/400/800 ms Wartezeit (Summe rund 1,5 s).** Begründung:
Der reale Blocker ist ein Handle, der Millisekunden bis wenige Sekunden nachhängt (Virenscanner,
Explorer-Vorschau). Anderthalb Sekunden decken das ab. Länger geht nicht, weil die Warteschlange
streng seriell ist – „Es läuft stets nur **ein** Auftrag gleichzeitig" (NFA-09): Solange gewartet
wird, steht das ganze Programm, und die Oberfläche wirkt eingefroren. Kürzer geht nicht, weil ein
einziger Fehlversuch nach einem minutenlangen Kopiervorgang bedeutet, dass der Nutzer den ganzen
Export wiederholen muss. Der wachsende Abstand (Verdopplung) trifft den kurzen Fall schnell und
verschwendet im langen Fall keine Aufrufe.
**Diese Werte sind bewusst nicht an #86 angeglichen** – dort geht es um einen nachhängenden
Vorschau-Handle auf der internen Platte, hier um ein Wechselmedium nach einem Großkopiervorgang.
Die Werte stehen als benannte Konstanten in dieser Datei und werden vom umsetzenden Agenten
**nicht** verändert.

**Fremde Typen, die du benutzt, vollständig ausgeschrieben** (der umsetzende Agent sieht die
anderen Issues nicht):

```ts
// M6-27 – src/main/export-service/fehlercodes.ts (DEFINIERENDE QUELLE)
export type ExportFehlercode =
  | 'keine_ausgabe' | 'ziel_nicht_verfügbar' | 'datei_zu_gross_fat32'
  | 'kein_platz' | 'ziel_gesperrt' | 'schreib_fehler' | 'speicher_fehler'
// SIEBEN Werte (`speicher_fehler` ist der Zusatz aus TK v2.9).
// Diese Datei vergibt davon DREI: ziel_gesperrt, ziel_nicht_verfügbar, schreib_fehler.
// `speicher_fehler` vergibt allein M6-33 – im Fehlerzweig des Sofort-Flushs, NICHT hier.

// #12 + #22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }

// #86 – src/main/media-service/datei-entfernen.ts   (NICHT importieren – nur zur Abgrenzung!)
export async function entferneDatei(pfad: string): Promise<Ergebnis<void, 'datei_fehler'>>
// Vorbild für die Struktur der Retry-Schleife, aber anderes Modul, andere Operation,
// andere Fehlercodes. Begründung der Doppelung s. o.
```

Weicht eine dieser Signaturen von der tatsächlichen Fassung der definierenden Datei ab, ist das ein
**Vertragsfehler** – **melden, NICHT eigenmächtig anpassen.** Die definierende Datei gewinnt immer.

### Der Ablauf (verbindlich)
1. **Formprüfung.** `partPfad` und `zielPfad` sind nicht leere Strings und **verschieden** → sonst
   `ungueltige_eingabe`, **ohne** jeden Dateisystemzugriff.
2. **Versuchsschleife**, höchstens `ERSETZEN_VERSUCHE` Durchläufe:
   1. `fs.promises.rename(partPfad, zielPfad)`.
   2. Erfolg → sofort `{ ok: true, wert: undefined }`, Schleife verlassen.
   3. Fehler `EBUSY` **oder** `EPERM` → ist noch ein Versuch übrig, `ERSETZEN_BACKOFF_MS[i]`
      Millisekunden **awaiten** und erneut versuchen; ist keiner mehr übrig → `ziel_gesperrt`.
   4. Fehler `ENOENT`/`ENODEV`/`ENXIO` **auf den Zielordner** (Stick gezogen) →
      **sofort** `ziel_nicht_verfügbar`, **ohne** Wartezeit.
   5. Jeder andere Fehler → **sofort** `schreib_fehler`, **ohne** Wartezeit.
3. Diese Funktion räumt **nichts** auf: Bleibt die `.part` nach einem endgültigen Fehlschlag liegen,
   ist das der von TK 9.6.3 ausdrücklich vorgesehene Ausgang („hinterlässt höchstens eine
   `.part`-Leiche"). Das Aufräumen einer liegengebliebenen `.part` nach gescheitertem Ersetzen
   erledigt der Aufrufer (M6-33).

**ENTSCHIEDEN – ein einzelner `fs.promises.rename`-Aufruf je Versuch, nichts davor und nichts
danach.** Auf POSIX ersetzt `rename` eine vorhandene Zieldatei unteilbar; auf Windows setzt Node
`MOVEFILE_REPLACE_EXISTING` und ersetzt ebenfalls. Es gibt damit **keinen** Zeitpunkt, in dem die
Zieldatei fehlt. Jede Variante mit einem vorherigen `unlink`, `copyFile`+`unlink`, `rm` oder einem
Umbenennen der alten Datei auf einen Sicherungsnamen erzeugt genau dieses Fenster und ist
**verboten** – auch als „Rückfalllösung, falls `rename` scheitert".

**ENTSCHIEDEN – `ENOENT` ist hier ein Fehler, nicht wie in #86 ein Erfolg.** Fehlt `partPfad`,
ist die Vorbedingung dieser Funktion verletzt (M6-31 hat sie gerade erst erzeugt und gesynct); ein
stiller Erfolg würde einen Export als gelungen melden, bei dem am Ziel gar nichts angekommen ist.
Fehlt dagegen der **Zielordner**, ist der Stick gezogen – das ist `ziel_nicht_verfügbar`. Da beide
Fälle denselben Code `ENOENT` liefern, wird unterschieden, ob der **Zielordner** noch erreichbar ist;
ist er es, lag es an `partPfad` → `schreib_fehler` mit einer Meldung, die das benennt.

**ENTSCHIEDEN – die Meldungen nennen Zielordner und Dateinamen im Klartext, aber nie einen
Stacktrace.** Der Zielordner ist eine Nutzereingabe außerhalb des Projektdatenbestands; der Nutzer
hat ihn selbst gewählt und muss ihn wiedererkennen. Bei `ziel_gesperrt` nennt die Meldung
ausdrücklich, dass die Zieldatei von einem anderen Programm geöffnet ist und geschlossen werden
muss – das ist die Handlungsanweisung, die den Wiederholversuch (FA-17) erfolgreich macht.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `partPfad` | absoluter Pfad der fertig kopierten, größen-verifizierten und gesyncten Arbeitsdatei (M6-31) | nicht leer; wird **unverändert** benutzt. **Keine** eigene Pfadprüfung, **keine** Normalisierung – der Pfad wurde vom Aufrufer gebildet |
| `zielPfad` | absoluter Pfad der endgültigen Zieldatei, `<zielOrdner>/<dateiname>` | nicht leer und **verschieden** von `partPfad`; wird **unverändert** benutzt |

Ausgang bei Erfolg: `Ergebnis<void>` – „unter `zielPfad` liegt jetzt die neue Datei, und zu keinem
Zeitpunkt lag dort etwas Unvollständiges". `partPfad` existiert danach nicht mehr (der Rename hat
ihn verbraucht).
Ausgang bei Fehler: Codes `ziel_gesperrt`, `ziel_nicht_verfügbar`, `schreib_fehler` (fachlich,
TK 9.6.4) sowie `ungueltige_eingabe` und `unbekannter_fehler` (generisch). Geschlossener Satz.
**In jedem Fehlerfall ist die vorhandene Zieldatei unverändert** – das ist die zentrale Zusage
dieser Funktion.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Atomar ersetzen:** `.part` → `<dateiname>` per Rename-mit-Ersetzen. Auf Windows bei
  `EBUSY`/`EPERM` **Retry+Backoff**." (TK 9.6.2, Schritt 5)
- „**Die vorhandene Zieldatei ist geschützt:** Eine Datei gleichen Namens auf dem Ziel wird **nie**
  gelöscht oder überschrieben, bevor die neue **vollständig kopiert und größen-verifiziert** ist.
  Deshalb `.part` + Rename-mit-Ersetzen zum Schluss. Ein Abbruch (Stick abgezogen, Absturz)
  hinterlässt höchstens eine `.part`-Leiche, nie eine **halbe** MP4, die der TV abspielen würde."
  (TK 9.6.3)
- „**Rename-mit-Ersetzen plattformsicher:** Das atomare Ersetzen verhält sich auf Windows anders als
  auf POSIX; die Umsetzung muss ein **Ersetzen** garantieren, ohne die alte Datei vor Fertigstellung
  der neuen zu entfernen." (TK 9.6.3)
- „**Zieldateiname = Quelldateiname.** Der frühere Zwang auf exakt `loop.mp4` ist **entfallen**
  (FA-22)" (TK 9.6.3) – der Zielname kommt fertig herein und wird hier **nicht** verändert.
- „Der Export darf **nie** außerhalb von `zielPfad` schreiben." (TK 9.6.3)
- „**Nur der Main** berührt das Dateisystem. **Kein zweites Lock** – die Serialisierung liefert die
  Queue (`export` ist ein Auftrag)." (TK 9.6.3)
- Plattform-Invariante der Planung (Übergabe-Prompt 5.7, „Plattform-Fallen"): „**Windows:**
  gesperrte Datei → `EBUSY`/`EPERM`. **macOS:** `unlink` gelingt still, obwohl noch geöffnet. Beide
  Fälle **explizit** behandeln." – Auf macOS gelingt auch das Ersetzen eines geöffneten Ziels
  still; der Retry-Pfad wird dort im Normalfall **nie** betreten. Das ist der gewünschte Zustand und
  **kein** Hinweis darauf, dass die Wiederholung überflüssig wäre.
- Die drei Fehlercodes, wörtlich aus der geschlossenen Tabelle TK 9.6.4:

  | Fehlercode | Ursache |
  |---|---|
  | `ziel_nicht_verfügbar` | Zielpfad/Laufwerk nicht erreichbar (Stick abgezogen) |
  | `ziel_gesperrt` | Zieldatei durch anderen Prozess gesperrt (nach Retry) |
  | `schreib_fehler` | sonstiger I/O-Fehler beim Kopieren |

- „Wo eine Operation **nichts** zu melden hat, lautet die Nutzlast `void`: **`Ergebnis<void>`** –
  das gelungene `ok` **ist** die Information." (TK 9.1.1)
- Niemals `throw`: Der Aufrufer ist der Export-Handler eines Auftrags; eine Ausnahme ließe den
  Auftrag auf `laeuft` stehen und brächte die streng serielle Warteschlange für den Rest der
  Sitzung zum Stillstand (TK 9.3.5).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `partPfad` oder `zielPfad` leer/kein String, oder beide identisch | `ungueltige_eingabe` | **kein** Dateisystemzugriff, keine Wirkung |
| `rename` gelingt im 1.–5. Versuch | – | **Erfolg**; keine weiteren Versuche, keine Restwartezeit |
| `EBUSY`/`EPERM`, noch Versuche übrig | – | Wartezeit gemäß `ERSETZEN_BACKOFF_MS`, dann erneut versuchen |
| `EBUSY`/`EPERM` nach dem letzten Versuch | `ziel_gesperrt` | Meldung nennt Zielordner und Dateinamen und sagt ausdrücklich, dass ein anderes Programm die Datei geöffnet hält und geschlossen werden muss. Die vorhandene Zieldatei ist **unverändert**, die `.part` liegt noch da |
| `ENOENT`/`ENODEV`/`ENXIO` und der **Zielordner** ist nicht mehr erreichbar | `ziel_nicht_verfügbar` | **sofort**, ohne Wartezeit; Meldung rät, den Speicher wieder anzuschließen |
| `ENOENT` und der Zielordner **ist** erreichbar (also fehlt `partPfad`) | `schreib_fehler` | **sofort**, ohne Wartezeit; Meldung benennt, dass die Arbeitsdatei verschwunden ist |
| `EXDEV` (`partPfad` und `zielPfad` auf verschiedenen Datenträgern) | `schreib_fehler` | **sofort**; Meldung benennt, dass Arbeitsdatei und Ziel auf demselben Datenträger liegen müssen. Dieser Fall ist ein **Programmierfehler des Aufrufers**, kein Nutzerfehler – M6-33 bildet beide Pfade aus demselben Zielordner |
| `EACCES`, `EROFS`, `EIO`, `EISDIR` oder ein unbekannter Code | `schreib_fehler` | **sofort**, ohne Wartezeit; der Code des Betriebssystems steht in der `meldung`, **nie** im `code` |
| unerwartete Ausnahme | `unbekannter_fehler` | fangen und in das Ergebnis wandeln; **kein** `throw`, **kein** Stacktrace in der Meldung |

Es wird **kein** Fehlercode erfunden: „**3. Fehlercodes sind ein geschlossener, typisierter Satz:**
die fachlichen je Operation (9.4.9, 9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`,
`nicht_gefunden`, `unbekannter_fehler`. **Eine rohe Exception-Meldung wird nie zum Code.**"
(TK 9.1.1)

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – die vorhandene Zieldatei wird NIE vorher angefasst.** Kein `unlink` auf `zielPfad`,
  kein `rm`, kein Leeren, kein Umbenennen auf `<name>.alt`, kein `truncate`, kein
  `copyFile`+`unlink`. **Auch nicht als Rückfalllösung**, wenn `rename` scheitert. Jede dieser
  Varianten erzeugt ein Zeitfenster, in dem am Ziel keine gültige Datei liegt – und genau dieses
  Fenster ist der Grund, warum es das `.part`-Verfahren überhaupt gibt.
- **Verbot – `entferneDatei` (#86) wird NICHT importiert.** Begründung im eigenen Abschnitt oben.
  Wer die Regel „kein modulübergreifender Import" ändern will, meldet das – er hebt sie nicht
  nebenbei in diesem Issue auf.
- **Verbot – keine Wiederholung bei anderen Fehlercodes als `EBUSY`/`EPERM`.** Kein Retry bei
  `EACCES`, `EROFS`, `ENOSPC`, `EIO` oder unbekannten Codes. Diese Zustände bessern sich durch
  Warten nicht; ein Retry verzögert nur die Fehlermeldung und blockiert die serielle Warteschlange.
- **Verbot – die Konstanten `ERSETZEN_VERSUCHE` und `ERSETZEN_BACKOFF_MS` werden nicht verändert,
  nicht parametrisiert und nicht aus einer Konfiguration gelesen.** Sie sind oben entschieden. Kein
  zusätzlicher Funktionsparameter, auch kein optionaler, und **keine** zweite Einstiegsfunktion mit
  anderen Werten daneben. Verlangt die Praxis später andere Zahlen, ist das eine Änderung dieses
  Vertrags und keine lokale Entscheidung.
- **Verbot – das Warten ist ein `await` auf einen Timer.** Keine Beschäftigungsschleife, kein
  synchrones Blockieren, kein `Atomics.wait`. Der Main-Prozess bedient die gesamte Oberfläche.
- **Verbot – kein `chmod`, kein Entfernen von Schreibschutz-Attributen, kein `takeown`, kein
  Beenden fremder Prozesse.** Eine gesperrte Datei ist eine Nutzer-Information (Programm
  schließen), kein Hindernis, das die App eigenmächtig aus dem Weg räumt.
- **Verbot – hier wird nichts aufgeräumt.** Kein Entfernen der `.part` nach einem Fehlschlag. Diese
  Funktion hat genau eine Aufgabe. Das Aufräumen macht M6-33, der beide Pfade gebildet hat.
- **Verbot – kein Verzeichnis-`fsync` und kein zweiter Sync.** Die Daten sind bereits gesynct
  (M6-31, TK 9.6.3). Ein zusätzlicher Sync hier wäre eine zweite Zuständigkeit für dieselbe Zusage.

## Definition of Done
- [ ] `ersetzeAtomar` liefert `ungueltige_eingabe` **ohne** jeden `fs`-Aufruf für leere Pfade und
      für `partPfad === zielPfad` (Test mit Spy auf das `fs`-Modul)
- [ ] Ein erfolgreicher Lauf über eine **bereits vorhandene** Zieldatei ersetzt deren Inhalt
      vollständig, und `partPfad` existiert danach nicht mehr (Test mit zwei temporären Dateien
      unterschiedlichen Inhalts)
- [ ] In dieser Datei wird nachweislich **kein** `unlink`, `rm` oder `truncate` aufgerufen (Test mit
      Spys, die nie aufgerufen werden)
- [ ] Ein gemocktes `rename`, das zweimal `EBUSY` wirft und beim dritten Mal gelingt, führt zu
      `ok: true` und **genau drei** `rename`-Aufrufen (Test mit künstlicher Zeitsteuerung)
- [ ] Ein gemocktes `rename`, das durchgehend `EBUSY` wirft, führt zu `ziel_gesperrt` nach genau
      `ERSETZEN_VERSUCHE` Aufrufen; die Gesamtwartezeit entspricht der Summe von
      `ERSETZEN_BACKOFF_MS`
- [ ] Ein gemocktes `rename` mit `EACCES` führt **sofort** zu `schreib_fehler` – genau **ein**
      Aufruf, **keine** Wartezeit
- [ ] `ENOENT` bei erreichbarem Zielordner ergibt `schreib_fehler`; `ENOENT` bei nicht mehr
      erreichbarem Zielordner ergibt `ziel_nicht_verfügbar` (zwei getrennte Tests)
- [ ] Nach **jedem** Fehlschlag ist eine zuvor vorhandene Zieldatei bit-identisch unverändert
      (Test vergleicht Inhalt vorher/nachher)
- [ ] Keine Fehlersituation führt zu einem `throw`
- [ ] Keine Datei außerhalb von `src/main/export-service/ersetzen.ts` (+ zugehörige Testdatei)
