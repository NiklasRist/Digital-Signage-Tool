### Issue M6-05: [ffmpeg-adapter] Fortschritt aus der ffmpeg-Ausgabe lesen und drosseln

## Ziel (in einem Satz)
Aus den `-progress`-Zeilen eines laufenden `ffmpeg`-Aufrufs entsteht ein Prozentwert von 0 bis 100 –
gedrosselt auf wenige Werte je Sekunde, damit die IPC-Grenze nicht mit einem Ereignis je Bild
geflutet wird.

## Modul & Datei
- Modul: `ffmpeg-adapter` (Main)
- Datei: `src/main/ffmpeg-adapter/fortschritt.ts`
- Vertrag: Technisches Konzept **9.2.7** (Fortschritts-Ereignisse, **Drosselung als Vertrag**),
  **9.1.1** Punkt 5 (Ereignisse tragen keinen Endzustand) – Quelle der Wahrheit
- Prozess/Speicher: P4; **reine Laufzeitdaten (Kategorie D), keine Persistenz**, keine Datei, kein IPC

## Warum das im Gesamtsystem wichtig ist
Ein Render kann Minuten dauern. Ohne Fortschritt sieht der Nutzer einen Balken, der nicht sagt, ob
überhaupt etwas passiert – TK 9.2.7 begründet den Kanal genau damit.

Die eigentliche Gefahr sitzt aber auf der anderen Seite: `ffmpeg` schreibt bei `-progress` mehrmals
**pro Sekunde** einen Block, bei manchen Einstellungen im Bildtakt. Wird daraus ungebremst je ein
IPC-Ereignis, gehen bei einer zehnminütigen Sequenz Zehntausende Nachrichten über die
Prozessgrenze; jede davon wird serialisiert und löst im Renderer eine React-Aktualisierung aus. Die
Oberfläche wird dann **während** des Renders zäh – also genau dann, wenn der Nutzer sie beobachtet.
Deshalb ist die Drosselung im Technischen Konzept ausdrücklich als **Vertrag** und nicht als
Umsetzungsdetail geführt.

Die zweite Gefahr ist die Zeiteinheit. `ffmpeg` liefert im `-progress`-Block mehrere Zeitfelder mit
verwirrend ähnlichen Namen, und **`out_time_ms` trägt trotz seines Namens keine Millisekunden**. Wer
darauf rechnet, bekommt einen Fortschritt, der um den Faktor 1000 danebenliegt – der Balken springt
sofort auf 100 % und bleibt dort, während der Render noch minutenlang läuft. Das sieht nicht nach
einem Rechenfehler aus, sondern nach einem hängenden Programm.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/ffmpeg-adapter/fortschritt.ts

export interface FortschrittsLeser {
  /**
   * Nimmt EINE Zeile der ffmpeg-Standardausgabe entgegen.
   * Liefert einen Prozentwert 0..100 (ganzzahlig), wenn jetzt ein Wert gemeldet werden soll,
   * sonst null (Zeile uninteressant ODER Drosselung greift).
   * `jetztMs` ist die Zeitquelle - sie wird HINEINGEREICHT, nicht in dieser Datei gelesen.
   */
  nimmZeile(zeile: string, jetztMs: number): number | null
}

/**
 * Erzeugt einen Leser fuer GENAU EINEN ffmpeg-Aufruf.
 * `erwarteteDauerSekunden` ist die Solldauer des Ergebnisses DIESES Aufrufs.
 * Ist sie <= 0, nicht endlich oder keine Zahl, liefert der Leser dauerhaft null -
 * er rechnet dann nicht, statt zu raten.
 */
export function erzeugeFortschrittsLeser(erwarteteDauerSekunden: number): FortschrittsLeser
```

**Warum die Zeit hereingereicht wird und nicht `Date.now()` in dieser Datei steht:** Die Drosselung
ist damit ohne Zeitmanipulation prüfbar – der Test schiebt `jetztMs` weiter, statt fünf Sekunden zu
warten oder eine Zeitfälschung einzurichten. Zugleich gibt es **keinen Zeitgeber** in dieser Datei:
kein `setInterval`, kein `setTimeout`. Ein Zeitgeber wäre eine zweite, unabhängige Quelle für die
Frage „wann wird gemeldet" und würde nach dem Prozessende weiterfeuern.

**Fremde Funktionen, die diese Datei beliefern** (der umsetzende Agent sieht die anderen Issues
nicht):

```ts
// M6-03 – src/main/ffmpeg-adapter/prozess.ts (Schwester-Datei, gleiches Modul).
// Sie ruft `aufAusgabeZeile` je VOLLSTAENDIGER stdout-Zeile. DIESE Datei importiert sie NICHT;
// verdrahtet wird beides in renderReel (M6-26).
export interface FfmpegLauf {
  argumente: readonly string[]
  aufAusgabeZeile?: (zeile: string) => void
  aufProzessStart?: (kindProzess: ChildProcess) => void
  abbruchSignal?: AbortSignal
}
```

**Melde-Klausel:** Weicht eine der hier abgeschriebenen Signaturen von der tatsächlichen ab, ist das
ein **Vertragsfehler – melden, NICHT eigenmächtig anpassen.** Die definierende Datei gewinnt immer.

**Der Ablauf, verbindlich:**

1. Eine Zeile hat die Form `schluessel=wert`. Zeilen ohne `=` werden **ignoriert** (null).
2. **Die Zeitquelle ist `out_time_us`** – Mikrosekunden seit Beginn der Ausgabe. Fehlt das Feld in
   dieser Zeile, ist ersatzweise **`out_time`** zu benutzen (Form `HH:MM:SS.uuuuuu`, in Sekunden
   umzurechnen). **`out_time_ms` wird NIE benutzt** (s. Verbote).
3. Prozent = `abgelaufeneSekunden / erwarteteDauerSekunden × 100`, auf eine **ganze Zahl** gerundet
   und auf **0..100 begrenzt** (kleiner 0 → 0, größer 100 → 100).
4. **Drosselung:** Ein Wert wird nur zurückgegeben, wenn seit dem zuletzt zurückgegebenen Wert
   mindestens `MIND_ABSTAND_MS` vergangen sind. Der **allererste** ermittelte Wert geht immer durch
   (sonst bliebe der Balken bei einem kurzen Lauf ganz leer).

   ```ts
   const MIND_ABSTAND_MS = 250   // hoechstens vier Meldungen je Sekunde
   ```

   Begründung des Werts: TK 9.2.7 gibt „Obergrenze wenige Ereignisse/Sekunde" vor. Vier je Sekunde
   sind für das Auge flüssig – schneller kann ein Mensch einen Balken ohnehin nicht lesen – und
   erzeugen bei einem zehnminütigen Render rund 2400 statt zehntausender Nachrichten.
5. **`progress=end`** kommt am Ende jedes `-progress`-Blocks-Laufs genau einmal. Diese Zeile liefert
   **100** und geht **an der Drosselung vorbei**, damit der letzte gemeldete Wert nicht bei 93 %
   stehen bleibt. Danach setzt der Leser sich **nicht** zurück – er ist für genau einen Aufruf da.
6. Ein Wert wird **nie** unterdrückt, weil er kleiner als der vorige ist. Der Fortschritt ist eine
   Schätzung und darf springen; ein erzwungen monotoner Verlauf würde eine Genauigkeit vortäuschen,
   die es nicht gibt.

**ENTSCHIEDEN – dieser Leser kennt nur SEINEN Aufruf, nicht die Sequenz.** Der zurückgegebene Wert
ist der Fortschritt **dieses einen** `ffmpeg`-Aufrufs (ein Zwischenclip, die Bandspur oder der
concat-Schritt). Ihn auf den **Gesamtfortschritt** über alle Elemente umzurechnen und daraus das
Ereignis `RenderProgress` mit `phase`, `elementIndex` und `elementAnzahl` zu bauen, ist Sache des
`render-service` (M6-23). *Begründung:* Der `ffmpeg-adapter` kennt keine Fachbegriffe – er weiß
nichts von Elementen, Listen oder Phasen und darf es nicht wissen, sonst wandert die Sequenzlogik in
zwei Module.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `erwarteteDauerSekunden` | Solldauer des Ergebnisses **dieses** Aufrufs | `> 0` und endlich; sonst liefert der Leser dauerhaft `null` – **ohne** zu werfen und **ohne** einen Ersatzwert zu erfinden |
| `zeile` | eine vollständige Zeile der Standardausgabe | beliebiger Text; alles, was nicht `schluessel=wert` ist, wird ignoriert |
| `jetztMs` | Zeitstempel in Millisekunden | monoton steigend erwartet; ein rückwärts laufender Wert darf **nicht** zu einer Ausnahme führen (dann greift die Drosselung eben nicht) |

Ausgang bei Erfolg: ganze Zahl `0..100`, oder `null`, wenn nichts zu melden ist.
Ausgang bei Fehler: **entfällt** – diese Datei liefert **keine** Fehlercodes und wirft nie. Eine
unverständliche Zeile ist kein Fehler, sondern ein `null`. Ein Fortschritt, der die Ursache eines
Fehlschlags wäre, gäbe es im ganzen Entwurf nicht.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Drosselung (Vertrag, nicht nur Umsetzung):** Ereignisse an den Element-Grenzen (Beginn/Ende je
  `seg_*.mp4`) plus grobe Zwischen-Ticks; **kein** Pro-Frame-Feuerwerk über IPC (Obergrenze wenige
  Ereignisse/Sekunde). Die genaue Rate ist Umsetzungsdetail, *dass* gedrosselt wird, ist
  verbindlich." (TK 9.2.7)
- „| `prozent` | grober Gesamtfortschritt 0–100 |" (TK 9.2.7, Tabelle `RenderProgress`)
- „**Keine** Restzeit-Schätzung – bei `ffmpeg` unzuverlässig, sie würde nur falsche Erwartungen
  erzeugen. Reine Laufzeitdaten (Kategorie D), **keine** Persistenz." (TK 9.2.7)
- „Der Fortschrittskanal trägt **keinen** Endzustand. Erfolg, Fehler und Abbruch kommen
  **ausschließlich** über das `RenderResult` (9.2.3)." (TK 9.2.7) → `progress=end` bedeutet hier
  **100 Prozent**, **nicht** „erfolgreich". Ob der Aufruf gelang, sagt allein der Exit-Code (M6-03).
- „**5. Ereignisse sind Einbahnstraßen und tragen keinen Endzustand** (für `RenderProgress` bereits
  festgelegt, 9.2.7)." (TK 9.1.1)
- **Der Wert geht nie über 100 und nie unter 0** – auch nicht kurzzeitig. `ffmpeg` meldet bei
  ungenauer Quelldauer regelmäßig eine Ausgabezeit **jenseits** der erwarteten Länge; ohne Begrenzung
  stünde im Balken „117 %".
- **Nach dem terminalen Ergebnis darf nichts mehr gemeldet werden.** Diese Datei kann das nicht
  erzwingen (sie kennt das Ergebnis nicht) – deshalb hat sie **keinen Zeitgeber** und meldet
  ausschließlich **als Antwort auf eine hereingereichte Zeile**. So endet der Fluss automatisch mit
  dem letzten Datenblock des Prozesses.
- **Der `ffmpeg-adapter` kennt keine Fachbegriffe.** Kein `renderId`, kein `elementIndex`, kein
  `phase`, kein `RenderProgress` in dieser Datei.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| Zeile ohne `=` oder mit unbekanntem Schlüssel | – | `null`, keine Wirkung |
| `out_time_us` nicht als Zahl lesbar | – | `null`; es wird **nicht** geraten und **nicht** der letzte Wert wiederholt |
| weder `out_time_us` noch `out_time` in dieser Zeile | – | `null` |
| `erwarteteDauerSekunden` ≤ 0, `NaN` oder unendlich | – | der Leser liefert **dauerhaft** `null` (keine Division, kein `Infinity`, kein `NaN` im Prozentwert) |
| berechneter Wert außerhalb 0..100 | – | wird auf 0 bzw. 100 begrenzt |
| `jetztMs` läuft rückwärts | – | kein Wurf; die Drosselung lässt den Wert dann durch |

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – `out_time_ms` NICHT benutzen.** Der Name verspricht Millisekunden, die Einheit ist es
  je nach `ffmpeg`-Fassung **nicht** (dort stehen Mikrosekunden). Ein daraus errechneter Fortschritt
  liegt um den Faktor 1000 daneben: Der Balken springt in der ersten Sekunde auf 100 % und steht
  dann minutenlang still – ein Fehler, der wie ein Absturz aussieht und in keinem Testlauf mit einem
  kurzen Beispielvideo auffällt. Benutzt wird `out_time_us`, ersatzweise `out_time`.
- **Verbot – keine Restzeit, keine Geschwindigkeit, keine Glättung.** Kein `eta`, kein
  gleitender Durchschnitt, keine Extrapolation aus `speed=`. TK 9.2.7 schließt die Restzeit
  ausdrücklich aus, und eine geglättete Kurve wäre ein zweiter, unabgestimmter Wahrheitsbegriff für
  denselben Wert.
- **Verbot – kein Zeitgeber in dieser Datei.** Kein `setInterval`, kein `setTimeout`, kein
  `Date.now()`, kein `performance.now()`. Die Zeit kommt als Parameter herein.
- **Verbot – kein IPC, kein Ereignis, kein `RenderProgress`.** Diese Datei **liefert eine Zahl
  zurück**; sie sendet nichts. Das Bauen und Senden der Ereignisse ist M6-23.
- **Verbot – keine Monotonie erzwingen.** Kein „nur melden, wenn größer als zuletzt", kein
  Merken eines Höchstwerts.
- **Verbot – die Zeilen nicht aus `stderr` lesen.** `-progress` schreibt in den Kanal, den der
  Aufrufer im Argument-Array bestimmt; diese Datei bekommt ausschließlich die Zeilen, die ihr
  hereingereicht werden, und sucht sich keine eigene Quelle.
- **Verbot – den Leser nicht wiederverwenden.** Ein Leser gehört zu **einem** `ffmpeg`-Aufruf. Kein
  `zuruecksetzen()`, kein globaler Zustand, kein Modul-Singleton.
