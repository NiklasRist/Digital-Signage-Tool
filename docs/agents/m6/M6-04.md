### Issue M6-04: [ffmpeg-adapter] Laufenden ffmpeg-Prozess plattformsicher beenden

## Ziel (in einem Satz)
Der `ffmpeg-adapter` merkt sich das Handle des laufenden `ffmpeg`-Prozesses und kann ihn auf Windows
**und** macOS zuverlässig beenden – wobei die Zusage **in jedem Fall** aufgelöst wird, auch wenn gar
kein Prozess läuft oder er längst tot ist.

## Modul & Datei
- Modul: `ffmpeg-adapter` (Main)
- Datei: `src/main/ffmpeg-adapter/abbruch.ts`
- Vertrag: Technisches Konzept **9.2.7** (Abbruch `cancelRender`), **9.2.3** (`abgebrochen` ist kein
  Fehlercode), **9.3.5** (serielle Ausführung) – Quelle der Wahrheit
- Prozess/Speicher: P4; beendet einen Kindprozess, berührt **keine** Datei und **keinen** Speicher
  (kein T1, kein `.part`, kein D1)

## Warum das im Gesamtsystem wichtig ist
Der Render ist der einzige Vorgang im Werkzeug, der Minuten dauert. Ohne einen funktionierenden
Abbruch muss der Nutzer entweder warten oder die App abschießen – und danach liegt eine halbe
`.part`-Datei herum. TK 9.2.7 sagt zu: „Der Main stoppt den laufenden `ffmpeg`-Prozess" – **diese**
Datei ist die Stelle, die das tut.

Zwei lokale Fehlentscheidungen wären hier besonders teuer:

**Erstens die Plattform.** Der naheliegende Weg `kindProzess.kill('SIGTERM')` ist auf POSIX richtig
und auf Windows eine Attrappe: **Windows kennt keine Signale.** Node bildet dort jeden Signalnamen
auf ein hartes `TerminateProcess` ab – der Prozess bekommt also nie die Gelegenheit, seine Dateien
ordentlich zu schließen –, und etwaige Kindprozesse überleben. Ein Agent, der nur `SIGTERM` schickt,
baut einen Abbruch, der im Test auf dem Mac funktioniert und beim Nutzer unter Windows entweder gar
nichts tut oder eine gesperrte Datei hinterlässt. Der zweite Teil ist der wirklich teure: Ein noch
offenes Datei-Handle erzeugt beim anschließenden Aufräumen der `.part`-Datei genau das
`EBUSY`/`EPERM`, an dem der Abbruch dann scheinbar grundlos scheitert.

**Zweitens die Antwortpflicht.** Die serielle Ausführung ist der **einzige** Sperr-Mechanismus des
Systems (TK 9.3.5). Löst diese Zusage sich nicht auf – etwa weil auf ein `exit`-Ereignis gewartet
wird, das bei einem bereits beendeten Prozess nie mehr kommt –, hängt der Aufrufer, der Auftrag
bleibt auf `laeuft`, und danach steht die **gesamte** Warteschlange für den Rest der Sitzung still.
Ein Abbruch, der die Anwendung lahmlegt, ist schlimmer als kein Abbruch.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/ffmpeg-adapter/abbruch.ts
import type { ChildProcess } from 'node:child_process'

/**
 * Merkt sich das Handle des laufenden ffmpeg-Prozesses. Es gibt genau EINEN Platz:
 * es laeuft nie mehr als ein ffmpeg gleichzeitig (serielle Ausfuehrung, TK 9.3.5).
 * Ein zweiter Aufruf, waehrend noch ein Handle liegt, ERSETZT es und meldet das intern
 * als Programmierfehler - er wirft NICHT.
 */
export function merkeProzess(kindProzess: ChildProcess): void

/**
 * Gibt den Platz wieder frei. Ist ein ANDERES als das gemerkte Handle uebergeben,
 * passiert nichts (ein spaet eintreffendes Ende eines alten Laufs darf den neuen
 * nicht abmelden).
 */
export function gibProzessFrei(kindProzess: ChildProcess): void

/**
 * Beendet den gemerkten Prozess plattformsicher.
 * Loest IMMER auf - auch wenn kein Prozess gemerkt ist, der Prozess schon tot ist
 * oder das Beenden selbst fehlschlaegt. Lehnt NIE ab und wirft NIE.
 */
export function beendeLaufendenProzess(): Promise<void>
```

**Fremde Funktionen und APIs, die du benutzt, vollständig ausgeschrieben** (der umsetzende Agent
sieht die anderen Issues nicht):

```ts

// Sie startet den Prozess und reicht das Handle heraus; DIESE Datei importiert sie NICHT.

export interface FfmpegLauf {

  abbruchSignal?: AbortSignal
}
export async function fuehreFfmpegAus(lauf: FfmpegLauf): Promise<Ergebnis<void, FfmpegFehlercode>>

// Node (externe API), die relevanten Teile:
import { spawn } from 'node:child_process'
kindProzess.pid: number | undefined        // undefined, wenn der Start fehlschlug
kindProzess.exitCode: number | null        // nicht null => Prozess ist beendet
kindProzess.signalCode: NodeJS.Signals | null
kindProzess.killed: boolean                // true, sobald ein Signal GESENDET wurde (nicht: tot)
kindProzess.kill(signal?: NodeJS.Signals): boolean
kindProzess.once('exit', (code, signal) => void)
```

**Melde-Klausel:** Weicht eine der hier abgeschriebenen Signaturen von der tatsächlichen ab, ist das
ein **Vertragsfehler – melden, NICHT eigenmächtig anpassen.** Die definierende Datei gewinnt immer.

**Der Ablauf von `beendeLaufendenProzess`, verbindlich:**

1. Ist **kein** Handle gemerkt → sofort auflösen. Kein Fehler, keine Warnung nach außen: Ein Abbruch
   ohne laufenden Prozess ist ein normaler Wettlauf (der Lauf war gerade fertig), kein Fehlerfall.
2. Ist das Handle gemerkt, aber der Prozess bereits beendet (`exitCode !== null` **oder**
   `signalCode !== null`) → Platz freigeben und sofort auflösen.
3. Sonst plattformabhängig beenden:
   - **Auf POSIX (`process.platform !== 'win32'`):** `kindProzess.kill('SIGTERM')`. `ffmpeg` beendet
     daraufhin geordnet und gibt seine Datei-Handles frei. Endet der Prozess nicht binnen
     `GNADENFRIST_MS`, folgt `kindProzess.kill('SIGKILL')`.
   - **Auf Windows:** `taskkill` mit **Argument-Array** starten:
     `spawn('taskkill', ['/pid', String(pid), '/t', '/f'], { windowsHide: true })`.
     `/t` beendet auch etwaige Kindprozesse, `/f` erzwingt das Ende. Schlägt der Start von `taskkill`
     fehl (nicht vorhanden, keine Rechte), folgt ersatzweise `kindProzess.kill()`.
4. In **beiden** Fällen auf das `exit`-Ereignis warten, aber höchstens `ABSCHLUSS_FRIST_MS`. Danach
   wird ohnehin aufgelöst – der Aufrufer darf nie hängen.
5. Am Ende **immer** den Platz freigeben, in jedem der Zweige.

**Die beiden Fristen stehen als benannte Konstanten am Dateikopf und sind entschieden:**

```ts
const GNADENFRIST_MS = 3_000     // POSIX: Zeit fuer SIGTERM, bevor SIGKILL folgt
const ABSCHLUSS_FRIST_MS = 5_000 // Obergrenze fuer das Warten auf 'exit' - danach wird aufgeloest
```

Begründung: Drei Sekunden reichen `ffmpeg` sicher, um den Encoder zu schließen und die Datei-Handles
freizugeben – genau darum geht es, denn ein noch offenes Handle erzeugt beim anschließenden Löschen
der `.part`-Datei unter Windows `EBUSY`. Länger zu warten hilft nicht, denn ein `ffmpeg`, das nach
drei Sekunden nicht reagiert, reagiert gar nicht mehr. Die zweite Frist ist die **Notbremse gegen den
Stillstand der Warteschlange**: Sie ist bewusst größer als die erste, damit der reguläre Weg
(SIGTERM → SIGKILL → `exit`) hineinpasst, und trotzdem so kurz, dass der Nutzer nach dem Klick auf
„Abbrechen" nicht rätselt, ob etwas passiert.

**ENTSCHIEDEN – hier liegt KEIN Abbruch-Flag.** Diese Datei merkt sich **nicht**, dass abgebrochen
wurde. Das eine Abbruch-Flag lebt im `render-service` (M6-24) und reist als `AbortSignal` in den
Prozessstart hinein (M6-03), der daraus `ffmpeg_abgebrochen` statt `ffmpeg_fehler` macht. Ein zweites
Flag hier wäre eine zweite Quelle für denselben Zustand – dieselbe Fehlerklasse, die im Projekt schon
das `position`-Feld und `historieEintrag` gekostet hat.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `merkeProzess(kindProzess)` | das Handle des soeben gestarteten Laufs | wird **unverändert** aufbewahrt; kein `pid`-Kopieren „für später" (eine PID kann nach dem Ende neu vergeben werden – ein späteres `taskkill` träfe dann einen **fremden** Prozess) |
| `gibProzessFrei(kindProzess)` | Abmeldung nach dem Prozessende | ein **anderes** als das gemerkte Handle wird ignoriert |
| `beendeLaufendenProzess()` | Abbruchwunsch | kein Parameter; es gibt nur einen laufenden Prozess |

Ausgang bei Erfolg: Die Zusage von `beendeLaufendenProzess` ist aufgelöst, der Platz ist frei, und –
soweit das Betriebssystem es zulässt – läuft kein `ffmpeg` mehr.
Ausgang bei Fehler: **entfällt** – diese Datei liefert **keine** Fehlercodes. Ob der Lauf als
abgebrochen oder als fehlgeschlagen gilt, entscheidet der Prozessstart (M6-03) anhand des
`AbortSignal`, nicht diese Datei. Ein misslungenes Beenden führt hier **nicht** zu einer Ablehnung,
sondern zum Auflösen nach der Frist (s. Fehlerpfade).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Abbruch `cancelRender` (Renderer → Main):** Signal mit `renderId`. Der Main stoppt den laufenden
  `ffmpeg`-Prozess, räumt T1 **und die angefangene `<name>.mp4.part` im Ausgabeordner** auf und
  schließt den Lauf mit `RenderResult { status: abgebrochen }` ab (9.2.3)." (TK 9.2.7)
  → Von diesem Satz erfüllt **diese** Datei ausschließlich den ersten Teil („stoppt den laufenden
  `ffmpeg`-Prozess"). Aufräumen und `RenderResult` sind M6-24; hier wird **keine** Datei angefasst.
- „**`abgebrochen` ist *kein* Fehlercode.**" (TK 9.2.3) → Deshalb liefert diese Datei überhaupt
  keinen Code, sondern nur `Promise<void>`.
- „**ffprobe/ffmpeg-Argumente nie per String-Konkatenation, immer als Argument-Array.**"
  (TK 9.4.8 Punkt 2) → Gilt **auch** für `taskkill`: Die PID wird als eigenes Array-Element
  übergeben, niemals in eine Kommandozeile eingesetzt. Ein `exec('taskkill /pid ' + pid …)` ist
  verboten.
- „Es läuft stets nur **ein** Auftrag gleichzeitig; die übrigen warten in Reihenfolge."
  (Anforderungsdokument NFA-09) → deshalb genau **ein** Platz für ein Handle, keine Liste, keine Map.
- **Kein zweites Lock.** Kein Mutex, keine eigene Warteschlange; die Serialisierung liefert die
  Auftragsverwaltung (TK 9.3.5).
- **Der `ffmpeg-adapter` kennt keine Fachbegriffe.** Diese Datei weiß nichts von `renderId`,
  Aufträgen, Projekten oder Ausgabedateien. Sie kennt genau ein Prozess-Handle.
- **Niemals `throw`, niemals ablehnen.** Auch nicht bei einem unmöglichen Zustand; ein unbehandelter
  Fehler an dieser Stelle nimmt dem Nutzer den Abbruch **und** die Warteschlange.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| kein Handle gemerkt | – | sofort auflösen; kein Fehler (normaler Wettlauf mit dem regulären Ende) |
| Prozess bereits beendet (`exitCode`/`signalCode` gesetzt) | – | Platz freigeben, sofort auflösen |
| `kill` wirft (Prozess in der Zwischenzeit verschwunden, `ESRCH`) | – | Fehler schlucken, Platz freigeben, auflösen |
| `taskkill` nicht startbar oder Exit-Code ≠ 0 | – | ersatzweise `kindProzess.kill()`, dann weiter nach Punkt 4 |
| `exit` bleibt aus | – | nach `ABSCHLUSS_FRIST_MS` trotzdem auflösen; der Aufrufer darf **nie** hängen |
| `merkeProzess` wird gerufen, während schon ein Handle liegt | – | das alte wird ersetzt; **kein** `throw` – aber der Umstand wird intern protokolliert, denn er verletzt die serielle Zusage und ist ein Programmierfehler |
| `gibProzessFrei` mit einem fremden Handle | – | wirkungslos |

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – auf Windows NICHT auf Signale verlassen.** Kein `kill('SIGTERM')` als alleiniger Weg,
  kein `kill('SIGINT')`, kein `process.kill(-pid)` (negative PIDs sind eine POSIX-Prozessgruppen-
  Eigenheit und existieren unter Windows nicht). Der Windows-Zweig geht über `taskkill` mit
  Argument-Array.
- **Verbot – keine PID zwischenspeichern und später wiederverwenden.** Das Betriebssystem vergibt
  PIDs nach dem Prozessende erneut; ein verspätetes `taskkill` auf eine gemerkte PID kann einen
  **fremden** Prozess des Nutzers beenden. Immer über das gemerkte Handle gehen und vorher prüfen,
  ob es noch lebt.
- **Verbot – hier wird nichts aufgeräumt.** Kein Löschen von T1, kein Entfernen der `.part`-Datei,
  kein `RenderResult`, kein Auftrags-Zustand. Das ist M6-24; diese Datei fasst **keine** Datei an.
- **Verbot – kein zweites Abbruch-Flag.** Kein `wurdeAbgebrochen`, kein Zähler, kein Ereignis nach
  außen. Der Zustand liegt im `render-service` (M6-24) und reist als `AbortSignal` (M6-03).
- **Verbot – `beendeLaufendenProzess` lehnt nie ab.** Kein `reject`, kein `throw`, kein
  „Fehler weiterreichen, der Aufrufer wird es schon fangen".
- **Verbot – keine Liste von Prozessen.** Ein Platz. Wer meint, mehrere gleichzeitig verwalten zu
  müssen, hat die serielle Zusage missverstanden: **melden**, nicht erweitern.
