### Issue M6-34: [render-service] Den Render-Handler beim Programmstart anmelden

## Ziel (in einem Satz)
Beim Programmstart erfährt die Auftragsverwaltung, welche Funktionen einen `render`-Auftrag
ausführen und abbrechen – sodass ein eingereihter Render tatsächlich läuft, statt beim Dispatcher
ins Leere zu fallen.

## Modul & Datei
- Modul: `render-service` [P4] (Main)
- Datei: `src/main/render-service/handler-anmeldung.ts`
- Vertrag: Technisches Konzept **9.3.2** (Auftragsarten und ausführende Dienste – Quelle der
  Wahrheit), ergänzend **9.3.6** (Verzahnung mit dem `render-service`), **9.2** (`renderReel`),
  **9.2.7** (Abbruch `cancelRender`), **9.1.1** Punkt 1 (Aufruf-Ergebnis ≠ Auftrags-Ergebnis)
- Prozess/Speicher: P4 ↔ P6. **Kein** eigener Speicher, **kein** Dateizugriff, **kein** ffmpeg-
  Aufruf, **kein** IPC-Kanal (`kanaele.ts` wird hier **nicht** angefasst).

## Warum das im Gesamtsystem wichtig ist
**Ohne dieses Issue hat #68 keinen Aufrufer.** #68 (`registriereRenderHandler` in
`src/main/auftrags-manager/render-verzahnung.ts`) baut die vollständige Verzahnung zwischen
Auftragsverwaltung und `render-service`: Fortschritt am Auftrag, `RenderResult` → terminaler
Auftragszustand, Abbrecher mit der richtigen `renderId`. Aber es **registriert von sich aus
nichts** – es nimmt `renderReel` und `cancelRender` als Argumente entgegen, weil der
`render-service` zum Zeitpunkt von M2 noch gar nicht existierte. Ruft niemand diese Funktion mit
den echten Implementierungen auf, bleibt sie ein ungenutzter Baustein.

Die Folge wäre still und vollständig: Der Nutzer stellt seine Werbeschleife zusammen, drückt
„Rendern", der Auftrag erscheint in der Warteschlange, wird an die Reihe genommen – und der
Dispatcher findet für `art: 'render'` **keinen** Handler. Der Auftrag scheitert sofort und immer
mit `unbekannter_fehler`, obwohl an `renderReel` nichts falsch ist. **FA-08** („Aus der
Wiedergabeliste wird **je Lauf eine einzige, durchgehende MP4-Datei** in definierter Auflösung und
Codierung erzeugt (Verkettung aller Segmente).") und
**Akzeptanzkriterium 2** („Aus der Zusammenstellung **eine durchgehende** abspielbare MP4-Datei
erzeugt und auf einen USB-Speicher exportiert wird (FA-08, FA-09).") wären unerfüllbar – das
Kernversprechen des Produkts.

**Das ist die vierte Wiederholung derselben Lückenklasse.** In M1 meldete **keine** Operation ihren
IPC-Kanal an (behoben durch die Nachzügler #76/#77), in M2 registrierte **niemand** die vier
Queue-Kanäle (behoben durch #71), in M3 fehlte die Anmeldung der Medien-Handler (behoben durch #92),
und in M5 fehlte die Verdrahtung zweier `project-store`-Kanäle (behoben durch #153). Das Muster ist
immer dasselbe: Fertige Funktionen, die niemand je aufruft. Deshalb ist das hier ein **eigenes
Issue** mit eigenem Dateibereich und nicht ein Nebensatz in M6-26.

Die zweite Eigenschaft dieser Datei ist, dass sie **keine zweite Leistung** hat. Sie übersetzt
nichts, prüft nichts, fängt nichts ab. Die gesamte Übersetzungsarbeit – `RenderProgress` →
`Auftrag.fortschritt`, `RenderResult` → `HandlerErgebnis`, Prüfung des Fehlercodes gegen den
geschlossenen Satz, Abbrecher mit der `renderId` – steckt in #68. Jede Zwischenschicht hier wäre
eine zusätzliche Stelle, an der ein Fehlercode verloren geht.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/render-service/handler-anmeldung.ts

export function meldeRenderHandlerAn(): void
// Ruft registriereRenderHandler (#68) GENAU EINMAL mit den beiden echten Funktionen des
// render-service auf:
//   1. renderReel     (M6-26, src/main/render-service/render-reel.ts)
//   2. cancelRender   (M6-24, src/main/render-service/abbruch.ts)
// Mehr passiert hier nicht: keine Übersetzung, kein try/catch, kein Zustand, kein Lambda um
// die beiden Funktionen herum.
```

**ENTSCHIEDEN – der Name lautet `meldeRenderHandlerAn`, nicht `registriereRenderHandler` und nicht
`registriereRenderServiceHandler`.** Im Main-Baum existieren bereits zwei sehr ähnliche Namen:
`registriereAuftragsHandler` (#60, die Registry des Dispatchers) und `registriereRenderHandler`
(#68, die Verzahnung im `auftrags-manager`). Ein dritter Name im selben Wortfeld ist eine Einladung
zum falschen Import – und ein falscher Import wäre hier besonders tückisch, weil beide Kandidaten
kompilieren. `meldeRenderHandlerAn` steht sichtbar daneben und macht am Aufrufort (dem Bootstrap,
#3) klar, dass hier **angemeldet** und nicht **registriert** wird. Dasselbe Muster gilt für den
Export (`meldeExportHandlerAn`, M6-35).

**Fremde Funktionen und Typen, die du benutzt, vollständig ausgeschrieben** (der umsetzende Agent
sieht die anderen Issues nicht):

```ts
// #68 – src/main/auftrags-manager/render-verzahnung.ts (DEFINIERENDE QUELLE)
import type { RenderRequest } from '../../shared/contracts/render-request'
import type { RenderResult, RenderProgress } from '../../shared/contracts/render-result'

export function registriereRenderHandler(
  renderReel: (
    request: RenderRequest,
    aufFortschritt: (fortschritt: RenderProgress) => void,
  ) => Promise<RenderResult>,
  cancelRender: (renderId: string) => void,
): void
// Diese Funktion registriert intern über registriereAuftragsHandler('render', handler, brichAb)
// (#60) und leistet die GESAMTE Übersetzung: Fortschritt -> Auftrag.fortschritt (auf 0–100
// begrenzt), RenderResult -> HandlerErgebnis, Prüfung des Fehlercodes gegen den geschlossenen
// Satz aus TK 9.2.3, Abbrecher, der die renderId aus auftrag.payload zieht.

// #19 – src/shared/contracts/render-result.ts (DEFINIERENDE QUELLE von RenderResult)
export type RenderResult =
  | { status: 'erfolg'; renderId: string; ausgabePfad: string; ausgabeName: string; gesamtdauer: number; dateigroesse: number }
  | { status: 'fehler'; renderId: string; fehlercode: string; fehlerhaftesElementId: string | null; meldung: string }
  | { status: 'abgebrochen'; renderId: string; abgebrochenBei: number | null }

// M6-02 – src/shared/contracts/render-progress.ts (DEFINIERENDE QUELLE von RenderProgress)
// M6-02 zieht den Typ aus render-result.ts heraus und lässt dort NUR eine Re-Export-Zeile stehen
// (`export type { RenderProgress } from './render-progress'`) – deshalb übersetzt die
// Import-Zeile von #68 oben unverändert weiter. Braucht DIESE Datei den Typ irgendwo selbst,
// kommt er aus `render-progress`, NICHT aus `render-result`.
export interface RenderProgress {
  renderId: string
  phase: 'normalisieren' | 'verketten'
  elementIndex: number | null
  elementAnzahl: number | null
  elementId: string | null
  prozent: number                  // 0–100
}

// M6-26 – src/main/render-service/render-reel.ts (entsteht parallel)
// MUSS exakt auf den ersten Parameter von registriereRenderHandler passen:
export async function renderReel(
  request: RenderRequest,
  aufFortschritt: (fortschritt: RenderProgress) => void,
): Promise<RenderResult>

// M6-24 – src/main/render-service/abbruch.ts (entsteht parallel)
// MUSS exakt auf den zweiten Parameter von registriereRenderHandler passen:
export function cancelRender(renderId: string): void
```

**MELDE-KLAUSEL (bindend).** `M6-24` und `M6-26` entstehen **parallel** zu diesem Issue. Weicht eine
ihrer tatsächlichen Signaturen von der oben ausgeschriebenen Form ab – anderer Name, andere
Parameterreihenfolge, `Promise<void>` statt `void` bei `cancelRender`, ein zusätzlicher
Pflichtparameter, ein anderer Rückgabetyp –, ist das ein **Vertragsfehler zwischen zwei Issues:
STOPP und melden.** **Nicht** die fremde Datei anpassen und **nicht** hier einen Adapter oder ein
umschließendes Lambda bauen, das es „passend macht".

**Zu `RenderProgress` ist nichts zu raten – der Sachstand steht fest:** #19 hatte ihn in
`src/shared/contracts/render-result.ts` mitdefiniert, **M6-02** zieht ihn nach
`src/shared/contracts/render-progress.ts` und hinterlässt in `render-result.ts` genau eine
Re-Export-Zeile. Die oben abgeschriebene Import-Zeile von #68 bleibt deshalb gültig, und diese
Datei braucht den Typ ohnehin nicht selbst zu importieren – sie legt keinen Rumpf um die
Fachfunktionen. Findest du in `render-progress.ts` andere als die sechs Felder oben: **melden**.

### Der Ablauf (verbindlich)
Der ganze Rumpf von `meldeRenderHandlerAn()` besteht aus **einem** Aufruf:

```
registriereRenderHandler(renderReel, cancelRender)
```

Mehr passiert hier nicht. Insbesondere gibt es **keinen** Schritt, der ein Ergebnis auswertet,
umwandelt, prüft, fängt oder neu zusammensetzt, und **keinen** Zustand, den diese Datei hält.

**„Direkt" heißt: die Funktionsreferenzen selbst, nicht Lambdas um sie herum.** Beide Funktionen
haben bereits exakt die von #68 verlangte Form. Ein `async (request, aufFortschritt) => { … }`
dazwischen wäre eine **Übersetzungsschicht** – und damit genau die zweite Stelle, an der ein
Fortschritts-Ereignis, ein Fehlercode oder das `RenderResult` verloren gehen kann. Es gibt hier
keine.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – (`meldeRenderHandlerAn` hat kein Argument) | einmalige Anmeldung beim Programmstart | wird **genau einmal** aus dem Main-Bootstrap (#3) gerufen; ein zweiter Aufruf würde den Handler für `art: 'render'` erneut registrieren. Diese Datei ruft sich **nicht selbst** – s. STOPP |
| `request`, `aufFortschritt`, `renderId` | **kein Eingang dieser Datei** | Dispatcher → #68 → `renderReel`/`cancelRender`; diese Datei sieht diese Werte nie, weil sie keinen Rumpf um die Fachfunktionen legt |

Ausgang: `meldeRenderHandlerAn` liefert nichts (`void`); Wirkung ist ein eingetragener Handler und
ein eingetragener Abbrecher für `art: 'render'`.
Ausgang bei Fehler: Diese Funktion ist **keine** IPC-Operation und trägt **keine** Ergebnis-Hülle.
Fehler des Vorgangs reisen über den Auftrags-Zustand: „**Auftrags-Ergebnis:** Wie ging der *Vorgang*
aus (`RenderResult`, Export-Ergebnis …)? Das reist **nicht** als Aufruf-Antwort, sondern über den
**Auftrags-Zustand** (9.3)." (TK 9.1.1, Punkt 1)

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Zuordnung laut Tabelle TK 9.3.2 (Spalten `art` / ausführender Dienst / Nutzlast), wörtlich:

  | `art` | ausführender Dienst | Nutzlast |
  |---|---|---|
  | `render` | `render-service` (9.2, `renderReel`) | `RenderRequest` |

  Diese Datei meldet genau **diese eine** Art an – **keine** zweite, insbesondere **nicht**
  `export` (das ist M6-35) und **nicht** `import`/`loeschen` (das ist #92).
- „Ein `render`-Auftrag führt beim Start intern `renderReel(payload)` aus – **nach** dem
  Sofort-Flush von D1 (9.5.4)." (TK 9.3.6) – **den Flush löst der Handler in #68 aus, nicht diese
  Datei.**
- „`entferne` auf einen laufenden `render` delegiert an `cancelRender(renderId)`; die `renderId`
  liegt im `RenderRequest` des Auftrags — `auftragId` und `renderId` bleiben fest verknüpft."
  (TK 9.3.6) – **die `renderId` zieht der Abbrecher in #68 aus dem Auftrag; diese Datei kennt sie
  nicht.**
- „**Richtung:** Renderer → Main **über die Auftrags-Queue** (`reiheEin`, `art: render`) – **kein**
  direkter Request/Response-Aufruf (9.3.4)" (TK 9.2) – deshalb gibt es für `renderReel` **keinen**
  IPC-Kanal und wird hier **keiner** angemeldet.
- „Sie **plant, ordnet und protokolliert** nur — sie ersetzt keine Fachlogik." (TK 9.3, über die
  Auftragsverwaltung) – die Registry ist der Mechanismus, der das durchsetzt; diese Datei ist die
  Stelle, an der sich der `render-service` einträgt.
- **Niemals `throw`.** Wirft die Anmeldung, startet die App nicht sauber. Sie hat aber auch nichts,
  was werfen könnte: Sie ruft eine Funktion mit zwei Referenzen auf.

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – keine Übersetzungsschicht.** Kein Lambda um `renderReel` oder `cancelRender`, kein
  `try/catch`, kein Umformen von `RenderProgress` oder `RenderResult`, keine Prüfung des
  `fehlercode`. Das alles leistet #68, und zwar an **einer** Stelle. Wer es hier zusätzlich tut,
  erzeugt eine zweite Stelle, an der ein Fehlercode abgeschnitten werden kann – „Geht der Code
  verloren, degradieren Reparatur-Modus, Wiederholen und der FAT32-Hinweis alle zu „irgendwas ist
  schiefgelaufen"." (TK 9.1.1)
- **Verbot – `registriereAuftragsHandler` (#60) wird hier NICHT direkt aufgerufen.** Der Weg für
  `render` führt über `registriereRenderHandler` (#68), weil dort die gesamte Übersetzung sitzt.
  Ein direkter Eintrag würde #68 umgehen und den Auftrag ohne Fortschritt, ohne Abbrecher und ohne
  geprüften Fehlercode laufen lassen. (Für `import`/`loeschen`/`export` ist der direkte Weg der
  richtige – dort gibt es keine Verzahnungsschicht. Diese Asymmetrie ist gewollt.)
- **Verbot – diese Datei ruft sich nicht selbst auf.** Kein `meldeRenderHandlerAn()` am Modulende,
  kein Seiteneffekt beim Import. Die Anmeldung gehört in die **feste Startreihenfolge** des
  Bootstraps: „Warum das hier steht und nicht in den Modulen selbst: Eine Stelle, eine nachlesbare
  Reihenfolge. Eine Anmeldung „beim ersten Import des Moduls" hinge davon ab, wer wen zuerst
  importiert – eine klassische Quelle für Fehler, die nur manchmal auftreten und sich beim
  Umstellen einer einzigen `import`-Zeile anders verhalten. Und ohne feste Stelle kann ein früh
  eingereihter Auftrag ins Leere laufen, weil zu diesem Zeitpunkt noch kein Handler registriert
  ist." (#3)
- **Verbot – `src/main/index.ts` (#3) wird von diesem Issue NICHT geändert.** Dass
  `meldeRenderHandlerAn()` dort in die feste Startreihenfolge aufgenommen wird, zieht der
  Auftraggeber nach; die Datei gehört einem anderen Issue (Regel E).
- **Verbot – kein zweiter Abbruchweg.** Kein Prozess-Kill, kein eigenes Abbruch-Flag, keine
  zusätzliche Abbruch-Funktion neben `cancelRender`. Der Abbruch läuft ausschließlich über den in
  #68 registrierten Abbrecher.
- **Verbot – kein IPC-Kanal.** `kanaele.ts` wird hier nicht angefasst, `registriereHandler` (#23)
  nicht aufgerufen. Ein Render wird **nie** direkt aufgerufen, sondern über `reiheEin` eingereiht
  (TK 9.2, TK 9.3.4).
- **Verbot – keine Absicherung gegen doppelte Registrierung hier.** Kein „schon angemeldet"-Flag,
  kein Idempotenz-Schutz. Was bei einer zweiten Registrierung geschieht, legt #60 fest; eine
  zusätzliche Regel hier wäre eine zweite Wahrheit über dasselbe Verhalten.
