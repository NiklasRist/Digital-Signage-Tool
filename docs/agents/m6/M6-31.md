### Issue M6-31: [export-service] Nach .part kopieren, Größe verifizieren, fsync vor der Erfolgsmeldung

## Ziel (in einem Satz)
Die Ausgabedatei liegt danach vollständig, größen-verifiziert und **physisch** (nicht nur im
Schreibpuffer) als `<ziel>.part` auf dem Zielspeicher – oder es steht fest, warum nicht, und der
angefangene Rest ist weggeräumt.

## Modul & Datei
- Modul: `export-service` (Main)
- Datei: `src/main/export-service/kopieren.ts`
- Vertrag: Technisches Konzept **9.6.2** Schritte 3 und 4 sowie **9.6.3** (Quelle der Wahrheit),
  ergänzend **9.6.4** (Fehlercodes)
- Prozess/Speicher: P4 (Export-Teil). Liest die Quelldatei aus `projects/<id>/output/`, schreibt
  **ausschließlich** die `.part`-Datei am Ziel. **Kein** D1-Zugriff, **kein** Lock, **kein**
  Anfassen der eigentlichen Zieldatei.

## Warum das im Gesamtsystem wichtig ist
**⚠ Warum ein Fehler hier teuer ist (`risiko:datenverlust`).** Diese Funktion schreibt auf ein
Wechselmedium, das der Nutzer jederzeit abziehen kann – und das er abzieht, sobald die App „fertig"
meldet. Genau hier sitzt die Falle:

**Ohne `fsync` meldet das Betriebssystem Erfolg, während die Daten noch im Schreibpuffer stehen.**
Das ist kein theoretischer Fall, sondern das normale Verhalten: Der Kernel bestätigt einen
Schreibvorgang, sobald die Bytes im Cache liegen; auf einen USB-Stick gelangen sie erst Sekunden
später oder beim Auswerfen. Zieht der Nutzer den Stick, nachdem die App „Export fertig" gezeigt
hat, liegt dort eine **halbe MP4**. Der Fernseher spielt sie an – und bricht mitten in der
Werbeschleife ab. Im Studio steht dann ein 85-Zoll-Bildschirm mit einem eingefrorenen Bild, und
niemand vor Ort kann diagnostizieren, warum. Deshalb ist TK 9.6.3 an dieser Stelle eindeutig:
„**`fsync` vor Erfolg:** Erst wenn die Bytes physisch auf dem Stick sind, gilt der Export als
fertig – ein sofort abgezogener Stick verliert so keine gepufferten Daten."

Zweitens: Es wird **nach `.part` geschrieben, nicht auf den Zielnamen**. Eine gültige Datei
gleichen Namens liegt auf dem Stick und wird gerade im Studio abgespielt oder ist die letzte
funktionierende Fassung. Würde direkt auf sie geschrieben, zerstörte ein abgebrochener Kopiervorgang
die einzige lauffähige Datei. TK 9.6.3: „Ein Abbruch (Stick abgezogen, Absturz) hinterlässt
höchstens eine `.part`-Leiche, nie eine **halbe** MP4, die der TV abspielen würde."

Drittens die **Größenverifikation**. Sie ist das einzige Mittel, einen unvollständigen Kopiervorgang
zu erkennen, der ohne Fehlermeldung endete (abgeschnittener Schreibvorgang bei vollem Medium,
wackelnder USB-Kontakt). Sie läuft **vor** dem `fsync` und damit vor jeder Erfolgsmeldung.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/export-service/kopieren.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { ExportFehlercode } from './fehlercodes'

export async function kopiereNachPart(
  quellPfad: string,      // absolut, aus loeseExportQuelle (M6-30) – bereits geprüft
  partPfad: string,       // absolut, `<zielOrdner>/<dateiname>.part` – vom Aufrufer gebildet
  quellGroesse: number,   // Bytes, aus loeseExportQuelle (M6-30) – die Sollgröße
): Promise<Ergebnis<void, ExportFehlercode>>
// Reihenfolge verbindlich: kopieren -> Größe vergleichen -> fsync -> ERST DANN Erfolg melden.
// Bei jedem Fehlschlag wird die angefangene .part-Datei best-effort entfernt (s. Ablauf).
// Diese Funktion fasst die eigentliche Zieldatei NICHT an – weder lesend noch schreibend.
```

**ENTSCHIEDEN – `Ergebnis<void>`, kein Rückgabewert mit Prüfbericht.** „Wo eine Operation **nichts**
zu melden hat, lautet die Nutzlast `void`: **`Ergebnis<void>`** – das gelungene `ok` **ist** die
Information. **Verboten** sind Ersatzformen wie `Ergebnis<boolean>`, `Ergebnis<null>` oder ein
blankes `true`." (TK 9.1.1) Die Größe kennt der Aufrufer bereits (`quellGroesse`).

**ENTSCHIEDEN – der `.part`-Pfad wird übergeben, nicht hier gebildet.** So gibt es genau **eine**
Stelle, die den Zielnamen und den `.part`-Namen bildet (M6-33), und der Aufräum-Pfad bei einem
gescheiterten Rename (M6-32) benutzt garantiert denselben String.

**Fremde Typen, die du benutzt, vollständig ausgeschrieben** (der umsetzende Agent sieht die
anderen Issues nicht):

```ts
// M6-27 – src/main/export-service/fehlercodes.ts (DEFINIERENDE QUELLE)
export type ExportFehlercode =
  | 'keine_ausgabe' | 'ziel_nicht_verfügbar' | 'datei_zu_gross_fat32'
  | 'kein_platz' | 'ziel_gesperrt' | 'schreib_fehler' | 'speicher_fehler'
// SIEBEN Werte (`speicher_fehler` ist der Zusatz aus TK v2.9).
// Diese Datei vergibt davon DREI: kein_platz, ziel_nicht_verfügbar, schreib_fehler.
// `speicher_fehler` vergibt allein M6-33 – im Fehlerzweig des Sofort-Flushs, NICHT hier.

// #12 + #22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
```

Weicht eine dieser Signaturen von der tatsächlichen Fassung der definierenden Datei ab, ist das ein
**Vertragsfehler** – **melden, NICHT eigenmächtig anpassen.** Die definierende Datei gewinnt immer.

### Der Ablauf (verbindlich – in genau dieser Reihenfolge)
1. **Formprüfung.** `quellPfad` und `partPfad` sind nicht leere Strings, `quellGroesse` ist eine
   endliche, nicht negative Zahl → sonst `ungueltige_eingabe`, **ohne** jeden Dateisystemzugriff.
2. **Alten `.part`-Rest entfernen.** Existiert `partPfad` bereits (Leiche eines früheren,
   abgebrochenen Exports), wird er **vor** dem Kopieren entfernt. `ENOENT` dabei ist **Erfolg**
   (nichts zu tun). Scheitert das Entfernen aus einem anderen Grund → `schreib_fehler`.
   Begründung: `fs.copyFile` überschreibt zwar, aber ein Rest unbekannter Größe macht jede spätere
   Aussage über „vollständig kopiert" wackelig, und auf manchen Dateisystemen bleibt bei einem
   kürzeren Schreibvorgang ein längerer Rest stehen.
3. **Kopieren.** `fs.promises.copyFile(quellPfad, partPfad)`.
4. **Verifizieren.** `fs.promises.stat(partPfad)`; `stat.size` muss **exakt gleich**
   `quellGroesse` sein. Abweichung → `schreib_fehler`, `.part` best-effort entfernen.
   **Kein** Toleranzbereich, **kein** „ungefähr", **keine** Prüfsumme (s. ENTSCHIEDEN unten).
5. **`fsync`.** `partPfad` mit `fs.promises.open(partPfad, 'r+')` öffnen, `handle.sync()` aufrufen,
   `handle.close()` **immer** ausführen (auch im Fehlerfall, `finally`). Scheitert `sync()` →
   `schreib_fehler`, `.part` best-effort entfernen. **Erst nach** erfolgreichem `sync()` und
   erfolgreichem `close()` darf Erfolg gemeldet werden.
6. **Erfolg.** `{ ok: true, wert: undefined }`.

**Aufräumen bei Fehlschlag (verbindlich).** Scheitert Schritt 3, 4 oder 5, wird die angefangene
`.part`-Datei **best-effort** entfernt: ein `unlink`-Versuch, `ENOENT` ist dabei Erfolg, **jeder**
andere Fehler wird **verschluckt** und ändert das gemeldete Ergebnis **nicht**. Begründung: Der
ursprüngliche Fehler ist die Information, die der Nutzer braucht; ihn durch einen Aufräumfehler zu
ersetzen, verdeckt die Ursache. Und eine liegengebliebene `.part` ist laut TK 9.6.3 ein
hinnehmbarer Ausgang („hinterlässt höchstens eine `.part`-Leiche"), im Gegensatz zu einer halben
MP4 unter dem Zielnamen.

**ENTSCHIEDEN – Verifikation ist ein reiner Größenvergleich, keine Prüfsumme.** TK 9.6.2 Schritt 4
schreibt wörtlich „Größe von `.part` == Quellgröße". Eine Prüfsumme über 2,5 GB würde die Datei ein
zweites Mal vollständig **vom Stick lesen** – bei USB 2.0 verdoppelt das die Exportdauer, und der
Nutzer wartet nochmal so lange. Der Nutzen wäre gering: Der realistische Fehler ist der
abgeschnittene, nicht der verfälschte Kopiervorgang.

**ENTSCHIEDEN – `fs.copyFile` statt eines eigenen Stream-Kopierens.** `copyFile` nutzt auf beiden
Zielplattformen die schnellste Systemroutine, hat weniger Fehlerquellen als eine selbstgebaute
Pipe und meldet `ENOSPC` sauber. Der Preis ist, dass es **keinen** Byte-Fortschritt liefert – das
ist bewusst in Kauf genommen (s. **Verbot im STOPP-Block**: der Export meldet in v1 keinen
Fortschritt).
**Kein** `COPYFILE_EXCL`-Flag: `partPfad` wurde in Schritt 2 gerade entfernt, und `EXCL` würde bei
einem gescheiterten Entfernen zu einer verwirrenden zweiten Fehlerursache führen.

**ENTSCHIEDEN – nur die Datei wird gesynct, nicht das Verzeichnis.** TK 9.6.3 verlangt `fsync` für
die Daten der Datei; das ist der Fall, der die halbe MP4 verhindert. Ein zusätzliches
Verzeichnis-`fsync` gehört – wenn überhaupt – zum Rename und damit in ein anderes Issue; hier wird
es **nicht** eingebaut, damit nicht zwei Dateien dieselbe Zuständigkeit beanspruchen.

**ENTSCHIEDEN – die Meldungen nennen den Zielordner und den Dateinamen im Klartext.** Der
Zielordner ist eine **Nutzereingabe außerhalb** des Projektdatenbestands (der Nutzer hat ihn selbst
im Dialog gewählt, M6-28); er muss in der Fehlermeldung wiedererkennbar sein. Der **Quellpfad**
dagegen wird **nicht** ausgeschrieben – dort gilt weiter „Der Renderer sieht **nur relative**
Referenzen (`dateiname`), **nie** absolute Pfade" (TK 9.5.7). Ein Stacktrace gehört **nie** in die
Meldung.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `quellPfad` | absoluter Pfad der Ausgabedatei in `projects/<id>/output/`, bereits von der Pfad-Autorität aufgelöst und auf Existenz geprüft (M6-30) | nicht leer; wird **unverändert** benutzt. **Keine** eigene Pfadprüfung, **kein** `..`-Test, **keine** Normalisierung – das hat #49 über M6-30 bereits getan, und eine zweite, abweichende Prüfung wäre eine zweite Wahrheit |
| `partPfad` | absoluter Pfad der Arbeitsdatei am Ziel, `<zielOrdner>/<dateiname>.part` | nicht leer; wird **unverändert** benutzt; wird vom Aufrufer (M6-33) gebildet, damit M6-32 denselben String bekommt |
| `quellGroesse` | Sollgröße in Bytes (aus M6-30) | endlich, `>= 0`; der Vergleich ist **exakt** |

Ausgang bei Erfolg: `Ergebnis<void>` – „die vollständige Datei liegt physisch als `.part` am Ziel".
Die eigentliche Zieldatei ist zu diesem Zeitpunkt **unverändert** und weiterhin gültig.
Ausgang bei Fehler: Codes `kein_platz`, `ziel_nicht_verfügbar`, `schreib_fehler` (fachlich,
TK 9.6.4) sowie `ungueltige_eingabe` und `unbekannter_fehler` (generisch). Geschlossener Satz.
Diese Funktion vergibt **nie** `keine_ausgabe`, `datei_zu_gross_fat32` oder `ziel_gesperrt`.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Kopieren** nach `zielPfad/<dateiname>.part` *(langsam)*." (TK 9.6.2, Schritt 3)
- „**Verifizieren:** Größe von `.part` == Quellgröße; danach **`fsync`** (Schreibpuffer physisch auf
  den Stick zwingen)." (TK 9.6.2, Schritt 4)
- „**`fsync` vor Erfolg:** Erst wenn die Bytes physisch auf dem Stick sind, gilt der Export als
  fertig – ein sofort abgezogener Stick verliert so keine gepufferten Daten." (TK 9.6.3)
- „**Die vorhandene Zieldatei ist geschützt:** Eine Datei gleichen Namens auf dem Ziel wird **nie**
  gelöscht oder überschrieben, bevor die neue **vollständig kopiert und größen-verifiziert** ist.
  Deshalb `.part` + Rename-mit-Ersetzen zum Schluss. Ein Abbruch (Stick abgezogen, Absturz)
  hinterlässt höchstens eine `.part`-Leiche, nie eine **halbe** MP4, die der TV abspielen würde."
  (TK 9.6.3)
- „**Nur der Main** berührt das Dateisystem. **Kein zweites Lock** – die Serialisierung liefert die
  Queue (`export` ist ein Auftrag)." (TK 9.6.3)
- „Der Export darf **nie** außerhalb von `zielPfad` schreiben." (TK 9.6.3)
- Die drei Fehlercodes, wörtlich aus der geschlossenen Tabelle TK 9.6.4:

  | Fehlercode | Ursache |
  |---|---|
  | `ziel_nicht_verfügbar` | Zielpfad/Laufwerk nicht erreichbar (Stick abgezogen) |
  | `kein_platz` | zu wenig freier Speicher am Ziel |
  | `schreib_fehler` | sonstiger I/O-Fehler beim Kopieren |

- „Wo eine Operation **nichts** zu melden hat, lautet die Nutzlast `void`: **`Ergebnis<void>`** –
  das gelungene `ok` **ist** die Information." (TK 9.1.1)
- Niemals `throw`: Der Aufrufer ist der Export-Handler eines Auftrags; eine Ausnahme ließe den
  Auftrag auf `laeuft` stehen und brächte die streng serielle Warteschlange für den Rest der
  Sitzung zum Stillstand (TK 9.3.5).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `quellPfad`/`partPfad` leer oder kein String; `quellGroesse` negativ, `NaN`, `Infinity` oder keine Zahl | `ungueltige_eingabe` | **kein** Dateisystemzugriff, keine Wirkung |
| alter `.part`-Rest lässt sich nicht entfernen (nicht `ENOENT`) | `schreib_fehler` | **kein** Kopieren; Meldung nennt Zielordner und Dateinamen |
| `copyFile` scheitert mit `ENOSPC` (Medium voll) | `kein_platz` | `.part` best-effort entfernen; Meldung nennt die benötigte Größe |
| `copyFile` scheitert mit `ENOENT`/`ENODEV`/`ENXIO` **auf den Zielpfad** (Stick während des Kopierens gezogen) | `ziel_nicht_verfügbar` | `.part`-Entfernung wird versucht, scheitert erwartungsgemäß und wird verschluckt |
| `copyFile` scheitert mit `ENOENT` **auf den Quellpfad** (Datei wurde zwischenzeitlich gelöscht) | `schreib_fehler` | `.part` best-effort entfernen; die Meldung nennt ausdrücklich, dass die **Quelldatei** verschwunden ist. **Nicht** `keine_ausgabe`: Dieser Code gehört laut TK 9.6.4 zur **Vorab**-Prüfung (M6-30); hier ist der Vorgang bereits gestartet |
| `copyFile` scheitert mit `EACCES`/`EROFS`/`EIO` oder einem anderen Code | `schreib_fehler` | `.part` best-effort entfernen; Betriebssystem-Code steht in der `meldung`, **nie** im `code` |
| `stat(partPfad)` nach dem Kopieren scheitert | `schreib_fehler` | `.part` best-effort entfernen |
| `stat.size !== quellGroesse` | `schreib_fehler` | `.part` **entfernen** (best-effort); Meldung nennt Soll- und Ist-Größe. **Niemals** Erfolg melden |
| `open`/`sync`/`close` für den `fsync` scheitert | `schreib_fehler` | Handle im `finally` schließen, `.part` best-effort entfernen. **Ein nicht gesynctes `.part` gilt nie als Erfolg** |
| unerwartete Ausnahme | `unbekannter_fehler` | fangen und in das Ergebnis wandeln; **kein** `throw`, **kein** Stacktrace in der Meldung |
| Aufräumen der `.part` scheitert | – (**kein** Fehler) | wird verschluckt; das ursprüngliche Ergebnis bleibt unverändert |

Es wird **kein** Fehlercode erfunden: „**3. Fehlercodes sind ein geschlossener, typisierter Satz:**
die fachlichen je Operation (9.4.9, 9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`,
`nicht_gefunden`, `unbekannter_fehler`. **Eine rohe Exception-Meldung wird nie zum Code.**"
(TK 9.1.1)

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – niemals ohne `fsync` Erfolg melden, auch nicht „weil es sonst schneller ist".** Das ist
  die eine Zusage, für die es diese Funktion gibt. Kein „`fsync` nur bei großen Dateien", kein
  „`fsync` überspringen, wenn das Ziel kein Wechselmedium ist", kein Auslagern in einen
  Hintergrund-Task, dessen Ende niemand abwartet. Ohne diese Zusage ist die App genau so
  vertrauenswürdig wie „Datei kopieren im Explorer" – und die Folge ist eine halbe MP4 auf dem
  Stick, die im Studio zu einem eingefrorenen 85-Zoll-Bildschirm führt.
- **Verbot – niemals direkt auf den Zielnamen schreiben.** Diese Funktion kennt den Zielnamen nicht
  einmal; sie bekommt nur `partPfad`. Kein `copyFile` auf den Zielnamen „zum Testen", kein
  vorheriges Löschen der vorhandenen Zieldatei, um Platz zu schaffen. Die vorhandene Datei ist bis
  zum Rename (M6-32) **unantastbar**.
- **Verbot – keine Toleranz beim Größenvergleich.** Kein `Math.abs(diff) < n`, keine Rundung auf
  Blockgrenzen, kein „mindestens 99 %". Der Vergleich ist `===`. Eine Toleranz ließe genau den
  abgeschnittenen Kopiervorgang durch, den die Verifikation erkennen soll.
- **Verbot – kein Fortschritts-Ereignis, kein `meldeFortschritt` aus dieser Datei.** Der Vertrag
  definiert einen Fortschrittskanal **nur für den Render** (TK 9.2.7, `render:fortschritt`). Für den
  Export gibt es keinen; einen zu erfinden hieße, entweder ein zweites Ereignis anzumelden oder
  `copyFile` durch ein selbstgebautes Stream-Kopieren zu ersetzen (langsamer, mehr Fehlerquellen).
  Beides ist eine Vertragsänderung – **melden**, nicht nebenbei einbauen.
- **Verbot – keine Wiederholung in dieser Datei.** Kein Retry beim Kopieren, kein Backoff, keine
  zweite Chance nach `ENOSPC`. Die Wiederholung eines gescheiterten Exports ist eine
  **Auftragsfunktion**: TK 9.6.5 sagt dazu, ein Fehlschlag „landet in **Q2** und ist per „erneut
  einreihen" wiederholbar, sobald der Nutzer das Ziel behoben hat – genau der Wiederhol-Fall aus
  FA-17". Ein Retry hier würde einen 2,5-GB-Kopiervorgang blind wiederholen, während die
  Warteschlange streng seriell steht (NFA-09), und die Ursache (voller Stick) bessert sich durch
  Warten nicht. Die einzige Retry-Schleife des Exports sitzt in M6-32 – beim Rename, wo Warten
  tatsächlich hilft.
- **Verbot – keine Prüfsumme, kein Vergleich der Dateiinhalte, kein zweites Lesen.** Begründung
  oben (ENTSCHIEDEN).
- **Verbot – kein `chmod`, kein Entfernen von Schreibschutzattributen, kein Anlegen des
  Zielordners.** Ist das Ziel nicht beschreibbar, ist das eine Nutzer-Information; die Prüfung
  darauf ist bereits in M6-29 gelaufen.

      für `quellGroesse` als `-1`, `NaN`, `Infinity` (Test mit Spy auf das `fs`-Modul)
