### Issue M6-28: [export-service] Exportziel über einen Ordner-Dialog wählen

## Ziel (in einem Satz)
Der Nutzer wählt über den nativen Ordner-Dialog das Ziel des Exports (USB-Stick oder Zielordner),
vorbelegt mit dem zuletzt verwendeten Ziel – und ein Abbruch ist dabei ein normales, erfolgreiches
Ergebnis, kein Fehler.

## Modul & Datei
- Modul: `export-service` (Main)
- Datei: `src/main/export-service/ziel-dialog.ts`
- Vertrag: Technisches Konzept **9.6.1** (Quelle der Wahrheit), ergänzend **9.6.5** (Verzahnung mit
  dem `config-store`), **9.1.1** (Ergebnis-Hülle, Instant vs. Auftrag), **9.3.2** (was **kein**
  Auftrag ist)
- Prozess/Speicher: P4 (Export-Teil). **Kein** Dateizugriff, **kein** Schreiben, **kein** Lock. Die
  Funktion liest lediglich D3 (`config.json`) über `leseKonfig` (#26) und liefert einen Pfad zurück.
- IPC-Kanal: `export:wähleExportZiel` – **angemeldet wird er in M6-36**, nicht hier
  (`kanaele.ts` wird in dieser Datei **nicht** angefasst).

## Warum das im Gesamtsystem wichtig ist
**Diese Funktion existiert heute in keinem einzigen Issue – und ohne sie steht der ganze Export
still.** Drei Dinge hängen unmittelbar daran:

1. **#134 (Render/Export aus dem `composer` auslösen) setzt sie voraus.** Der Renderer kennt
   **keine** absoluten Pfade (TK 9.5.7); er kann den USB-Pfad also weder tippen noch erraten. Ohne
   diese Operation gibt es keinen Weg, `ExportRequest.zielPfad` überhaupt zu füllen, und FA-09
   („Export auf USB") sowie **Akzeptanzkriterium 2** („Aus der Zusammenstellung **eine durchgehende**
   abspielbare MP4-Datei erzeugt und auf einen USB-Speicher exportiert wird (FA-08, FA-09).")
   sind unerfüllbar.
2. **`setzeExportZiel` (#28) hätte sonst keinen Aufrufer.** Die `config-store`-Operation, die das
   Ziel merkt, ist bereits gebaut; gemerkt wird das Ziel aber erst nach einem **erfolgreichen**
   Export (M6-33). Diese Funktion ist die Gegenstelle: Sie **liest** den gemerkten Wert und belegt
   den Dialog damit vor. TK 9.6.5 wörtlich: „Das gewählte Ziel merkt sich der `config-store`
   (`setzeExportZiel`, 9.5.6) und belegt den Dialog beim nächsten Mal vor."
3. **Der Praxisnutzen ist die Vorbelegung.** Bedient wird das Werkzeug von Studio-Personal ohne
   IT-Hintergrund (NFA-01). Muss dieser Nutzer bei jedem Export den Laufwerksbuchstaben des Sticks
   im Dateibaum suchen, ist das der wiederkehrende Stolperstein, den #28 gerade abschaffen soll.

Die teuerste lokale Fehlentscheidung ist hier die **Behandlung des Abbruchs**. Klickt der Nutzer
„Abbrechen", ist das der häufigste Ausgang überhaupt und **kein Fehler**. Wird er als Fehler
gemeldet, zeigt die Oberfläche bei jedem versehentlich geöffneten Dialog eine Fehlermeldung – und
schlimmer: Ein Aufrufer, der Fehler protokolliert oder einen Wiederholversuch anbietet, tut das
dann für einen Vorgang, den der Nutzer bewusst abgebrochen hat. Genauso hält es der Muster-Dialog
`öffneMedienDialog` (#81) bereits.

Die zweitteuerste ist ein **leerer String als „nichts gewählt"**: Ein `''` ist ein falsy Pfad, der
unbemerkt an `path.join` oder `setzeExportZiel` weitergereicht werden kann und dann auf das
Arbeitsverzeichnis des Prozesses zeigt – der Export landete irgendwo im Programmordner statt auf
dem Stick. Deshalb ist der Abbruch unten ausdrücklich `null`.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/export-service/ziel-dialog.ts
import { dialog } from 'electron'
import type { Ergebnis } from '../../shared/contracts/ergebnis'

export async function wähleExportZiel(): Promise<Ergebnis<{ pfad: string | null }>>
// - INSTANT-Operation, KEIN Auftrag: sie trägt die Ergebnis-Hülle und läuft NICHT über reiheEin
// - `pfad` = absoluter Pfad des GEWÄHLTEN ORDNERS (nicht der Zieldatei)
// - `pfad === null` bedeutet: der Nutzer hat den Dialog abgebrochen. Das ist ok:true, KEIN Fehler
// - Kein zweiter Fehlercode-Typparameter: diese Operation kann keinen FACHLICHEN Fehler erzeugen;
//   nur die generischen Codes aus Ergebnis<T> (Default-Typparameter) kommen infrage
```

**ENTSCHIEDEN – `pfad: string | null` statt `pfad: string`.** TK 9.6.1 notiert
`wähleExportZiel() → Ergebnis<{ pfad }>` und lässt die Form von `pfad` offen. Der Abbruch ist der
häufigste Ausgang und darf kein Fehler sein (s. o.); ein leerer String wäre gefährlich (s. o.).
`null` ist der einzige Wert, den ein Aufrufer nicht versehentlich als Pfad benutzt.

**ENTSCHIEDEN – der Funktionsname trägt den Umlaut: `wähleExportZiel`.** So heißt die Operation in
TK 9.6.1, und so wird sie in M6-36 als Kanal `export:wähleExportZiel` angemeldet. Umlaute in
Bezeichnern sind im Projekt etabliert (`löscheMedium` #87, `öffneMedienDialog` #81, `fügeElementHinzu`
#41). Eine „bereinigte" Schreibweise `waehleExportZiel` bräche die Zuordnung zwischen Kanalname,
Vertrag und Funktion.

**Fremde Funktionen und APIs, die du benutzt, vollständig ausgeschrieben** (der umsetzende Agent
sieht die anderen Issues nicht):

```ts
// #26 – src/main/config-store/lese-konfig.ts (DEFINIERENDE QUELLE)
export async function leseKonfig(): Promise<Ergebnis<AppKonfig>>
// AppKonfig: { aktivesProjektId: string | null, letztesExportZiel: string | null,
//              uiVoreinstellungen: Record<string, unknown>, marke: Marke }
// existiert config.json nicht (erster Start) → liefert Ergebnis<AppKonfig> mit sinnvollen
// Defaults (aktivesProjektId: null, ...), OHNE Fehler

// #12 + #22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }

// Electron (externe Bibliothek), die verwendete Überladung OHNE Elternfenster:
dialog.showOpenDialog(options: {
  title?: string
  defaultPath?: string
  buttonLabel?: string
  properties?: Array<'openDirectory' | 'createDirectory' | ...>
}): Promise<{ canceled: boolean; filePaths: string[] }>
```

Weicht eine dieser Signaturen von der tatsächlichen Fassung der definierenden Datei ab, ist das ein
**Vertragsfehler** – **melden, NICHT eigenmächtig anpassen.** Die definierende Datei gewinnt immer.

### Der Ablauf (verbindlich)
1. `leseKonfig()` (#26) aufrufen und `letztesExportZiel` entnehmen.
   - `ok: true` und `letztesExportZiel !== null` → dieser Wert wird `defaultPath`.
   - `ok: true` und `letztesExportZiel === null` (erster Export überhaupt) → **kein** `defaultPath`
     setzen; das Betriebssystem wählt dann seinen üblichen Startordner.
   - `ok: false` → **kein** `defaultPath` setzen und **trotzdem weitermachen**. Der Dialog öffnet
     ohne Vorbelegung. Begründung: Die Vorbelegung ist eine Bequemlichkeit; eine unlesbare
     `config.json` darf den Export nicht verhindern, sonst kostet ein kosmetisches Problem die
     Kernfunktion FA-09.
2. `dialog.showOpenDialog({ title, defaultPath?, properties: ['openDirectory', 'createDirectory'] })`
   **await**en.
   - `title`: `'Zielordner für den Export wählen'`.
   - `properties`: **genau** `['openDirectory', 'createDirectory']`. `openDirectory` ist Pflicht –
     gewählt wird ein **Ordner**, nicht eine Datei. `createDirectory` erlaubt auf macOS das Anlegen
     eines neuen Unterordners im Dialog; auf Windows ist die Angabe wirkungslos und schadet nicht.
     **Kein** `multiSelections` (es gibt genau ein Ziel), **kein** `openFile`, **kein**
     `promptToCreate`.
   - **Keine** `filters` – Filter gelten für Dateien, nicht für Ordner.
3. `canceled === true` **oder** `filePaths` leer → `{ ok: true, wert: { pfad: null } }`.
   Beides ist **Erfolg**.
4. Sonst → `{ ok: true, wert: { pfad: filePaths[0] } }`, **unverändert** durchgereicht: nicht
   normalisiert, nicht auf Existenz geprüft, nicht auf Schreibbarkeit geprüft, nicht auf das
   Dateisystem geprüft. Auch `filePaths[1..]` wird ignoriert (es kann bei `openDirectory` ohne
   `multiSelections` keinen zweiten Eintrag geben).
5. Wirft der Aufruf wider Erwarten (z. B. weil noch kein Fenster bereit ist), wird die Ausnahme
   **hier** gefangen und als `{ ok: false, fehler: { code: 'unbekannter_fehler', meldung } }`
   zurückgegeben. Die Meldung enthält **keinen** Stacktrace.

**ENTSCHIEDEN – der Dialog wird ohne Elternfenster geöffnet.** Die Signatur nimmt kein
`BrowserWindow` entgegen, und der `export-service` soll die Fensterverwaltung nicht kennen; ein
`BrowserWindow.getFocusedWindow()`-Griff aus diesem Modul heraus wäre eine zusätzliche, unnötige
Abhängigkeit vom Renderer-Lebenszyklus. Praktische Folge: Der Dialog ist nicht als Sheet am Fenster
angeheftet. Das ist ein bewusst in Kauf genommener kosmetischer Nachteil, kein Versehen – genau so
entschieden wie beim Muster-Dialog #81.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – (`wähleExportZiel` hat kein Argument) | die Vorbelegung wird **selbst** aus D3 geholt, nicht übergeben | Übergäbe der Renderer sie, kennte er einen absoluten Pfad – das verbietet TK 9.5.7 |

Ausgang bei Erfolg: `{ ok: true, wert: { pfad } }` mit `pfad` = absoluter Ordnerpfad **oder**
`null` (Abbruch).
Ausgang bei Fehler: `unbekannter_fehler` – der einzige mögliche Code. Diese Operation vergibt
**keinen** der sieben fachlichen Export-Codes aus TK 9.6.4 (M6-27); geprüft wird das Ziel erst in
M6-29, und zwar mit der tatsächlich zu kopierenden Dateigröße.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operation, wörtlich (TK 9.6.1):
  ```
  wähleExportZiel() → Ergebnis<{ pfad }>   // Instant; Ordner-/Laufwerks-Dialog, vorbelegt mit letztem Ziel (config-store)
  ```
- „Das gewählte Ziel merkt sich der `config-store` (`setzeExportZiel`, 9.5.6) und belegt den Dialog
  beim nächsten Mal vor." (TK 9.6.5) – **diese Datei liest die Vorbelegung; geschrieben wird sie
  nach erfolgreichem Export in M6-33.**
- „**Nur Instant-Aufrufe tragen die Hülle.** Auftragsartige Operationen (`import`, `loeschen`,
  `render`, `export`) werden **nicht** direkt aufgerufen; der Aufruf ist `reiheEin` →
  `Ergebnis<{ auftragId }>`, ihr Fach-Ergebnis reist über den **Auftrags-Zustand** (Punkt 1, 9.3)."
  (TK 9.1.1) – `wähleExportZiel` ist **Instant** und trägt die Hülle; der **Export selbst** ist ein
  Auftrag und wird hier **nicht** angestoßen.
- Die Ergebnis-Hülle (TK 9.1.1):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Sie wird **nie** durch eine Ausnahme ersetzt: „**Fehlerklasse und eigene Felder wie `code` sind
  verloren** – übrig ist Text." (TK 9.1.1)
- „**Nicht** über die Queue laufen **Instant-Operationen** (Millisekunden, reine
  D1-Schreibvorgänge): Aktion anlegen/bearbeiten, Liste umsortieren, Trim setzen, **Aktion**
  löschen, Datei-Dialog öffnen." (TK 9.3.2) – ein Datei-/Ordner-Dialog ist ausdrücklich **kein**
  Auftrag und erscheint **nicht** im `queue-panel`.
- „Der Renderer sieht **nur relative** Referenzen (`dateiname`), **nie** absolute Pfade."
  (TK 9.5.7) – Der zurückgegebene Zielordner ist die **einzige** Ausnahme im ganzen System: Er ist
  eine **Nutzereingabe außerhalb** des Projektdatenbestands (ein USB-Laufwerk) und muss zum
  Anzeigen und zum späteren `ExportRequest.zielPfad` in den Renderer. Er ist **kein** Projekt-,
  Medien- oder Ausgabepfad; die Pfad-Autorität des `project-store` (#49) ist davon **nicht**
  berührt und wird hier **nicht** benutzt.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| Nutzer bricht den Dialog ab (`canceled: true`) | – (**kein** Fehler) | `{ ok: true, wert: { pfad: null } }` |
| `filePaths` ist leer, obwohl `canceled: false` | – (**kein** Fehler) | wie Abbruch: `{ ok: true, wert: { pfad: null } }` |
| `leseKonfig` (#26) liefert `ok: false` | – (**kein** Fehler) | Dialog öffnet **ohne** Vorbelegung; das Ergebnis dieses Aufrufs ist davon unberührt |
| `dialog.showOpenDialog` wirft (kein Fenster bereit, Plattformfehler) | `unbekannter_fehler` | Ausnahme wird hier gefangen; Meldung ohne Stacktrace, kein `throw` über die IPC-Grenze |

Es wird **kein** Fehlercode erfunden: „**3. Fehlercodes sind ein geschlossener, typisierter Satz:**
die fachlichen je Operation (9.4.9, 9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`,
`nicht_gefunden`, `unbekannter_fehler`. **Eine rohe Exception-Meldung wird nie zum Code.**"
(TK 9.1.1)

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – hier wird das Ziel NICHT gemerkt.** Kein Aufruf von `setzeExportZiel` (#28) in dieser
  Datei. Gemerkt wird erst **nach einem erfolgreichen Export** (M6-33, TK 9.6.5). Wer es hier tut,
  merkt sich einen Ordner, auf den nie geschrieben wurde – nach einem abgebrochenen Versuch auf
  einem falschen Laufwerk wäre der Dialog beim nächsten Mal **falsch** vorbelegt, und zwei Stellen
  schrieben denselben Konfigurationswert.
- **Verbot – hier wird nichts geprüft.** Keine Existenzprüfung, keine Schreibrechteprüfung, keine
  Dateisystem-Erkennung, keine Platzprüfung, kein `fs.*`-Aufruf. Das gehört **vollständig** zu
  M6-29 und läuft dort **mit der tatsächlichen Dateigröße** unmittelbar vor dem Kopieren. Eine
  Prüfung hier wäre zum Zeitpunkt des Exports längst veraltet (der Stick kann dazwischen gezogen
  werden) und erzeugte eine zweite, abweichende Wahrheit über dasselbe Ziel.
- **Verbot – hier wird nichts exportiert und nichts eingereiht.** Kein `reiheEin('export', …)`,
  kein Aufruf des Export-Handlers. Diese Funktion liefert einen Pfad und sonst nichts; das
  Einreihen macht der `composer` (#134).
- **Verbot – kein Dateiname im Ergebnis.** Zurück kommt der **Ordner**. Welche Ausgabedatei
  exportiert wird, entscheidet der Nutzer über die Ausgabe-Liste aus `listeAusgaben` (#75) und
  steht in `ExportRequest.dateiname`. Hier keinen Dateinamen anhängen, keinen vorschlagen und
  keinen aus der Konfiguration holen.
- **Verbot – der Abbruch wird nicht zum Fehler gemacht.** Kein `nicht_gefunden`, kein
  `ungueltige_eingabe`, kein eigener Code `abgebrochen`, kein `throw`. Der Abbruch ist `ok: true`
  mit `pfad: null`.
- **Verbot – kein `defaultPath`-Ersatz erfinden.** Fehlt `letztesExportZiel`, wird **kein**
  Startordner geraten – kein „erstes Wechsellaufwerk", kein `os.homedir()`, keine Laufwerksliste.
  Ein geratenes Laufwerk ist die wahrscheinlichste Ursache dafür, dass jemand versehentlich auf die
  falsche Platte exportiert.
