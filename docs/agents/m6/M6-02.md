### Issue M6-02: [contracts] Typ RenderProgress in eine eigene Datei ziehen und schärfen

## Ziel (in einem Satz)
Die Nutzlast des Ereignisses `render:fortschritt` steht als eigener geteilter Typ `RenderProgress` an
**einer** Stelle – vollständig nach TK 9.2.7, ohne Endzustand, ohne Ergebnis-Hülle – und ist
importierbar, ohne den ganzen `RenderResult`-Vertrag mitzuziehen.

## Modul & Datei
- Modul: `contracts/types` (geteilt)
- Datei: `src/shared/contracts/render-progress.ts`
- Zweite erlaubte Datei: `src/shared/contracts/render-result.ts` (#19) – dort **genau zwei**
  Eingriffe: die lokale `RenderProgress`-Deklaration entfällt, stattdessen **eine** Re-Export-Zeile
  (s. „ENTSCHIEDEN – Umzug mit Re-Export" unten). Sonst **nichts** an dieser Datei; `RenderResult`
  bleibt unangetastet.
- Vertrag: Technisches Konzept **9.2.7** (Fortschritts- und Abbruch-Ereignisse), ergänzend **9.1.1**
  Punkte 4 und 5 (Kanalbenennung, Ereignisse) – Quelle der Wahrheit
- Prozess/Speicher: P4 → Renderer; **reine Laufzeitdaten (Kategorie D), keine Persistenz**

**Vermerk für den Auftraggeber (kein Arbeitsauftrag an den umsetzenden Agenten):** `RenderProgress`
ist bereits in #19 mitdefiniert – dort **innerhalb** von `src/shared/contracts/render-result.ts`, und
#68 importiert ihn wörtlich mit
`import type { RenderResult, RenderProgress } from '../../shared/contracts/render-result'`. Ohne den
unten festgelegten Re-Export gäbe es nach diesem Issue **zwei** Deklarationen desselben Typs, oder
#68 verlöre seinen Importpfad. Der Umzug ist deshalb so geschnitten, dass **kein** bestehendes Issue
bricht. Ob #19 zusätzlich auf GitHub um einen Hinweis ergänzt wird, ist eine Entscheidung des
Auftraggebers.

## Warum das im Gesamtsystem wichtig ist
Dieser Typ ist die **einzige** Nutzlast, die während eines laufenden Renders vom Main zum Renderer
fließt. Ein Render kann Minuten dauern; ohne ihn zeigt die Oberfläche einen Balken, der nicht sagt,
ob überhaupt etwas passiert.

Er ist gleichzeitig die Stelle, an der zwei Regeln des IPC-Vertrags typmäßig sichtbar werden: Er
trägt **keine** Ergebnis-Hülle (Ereignisse tragen sie nie) und **keinen** Endzustand. Bekäme er ein
Feld wie `fertig: boolean` oder `status`, gäbe es zwei Wege, das Ende eines Laufs zu melden – der
Renderer würde irgendwann den falschen prüfen, und ein fehlgeschlagener Render sähe wie ein
erfolgreicher aus.

Der Umzug in eine eigene Datei hat einen praktischen Grund: Der Sender (M6-23, `render-service`), das
`ipc-gateway` (M6-36) und der Abonnent im Renderer (#151) brauchen **nur** diesen Typ. Läge er
weiterhin in `render-result.ts`, zöge jeder von ihnen den vollständigen Ergebnis-Vertrag mit
Fehlercodes und Abbruch-Varianten mit hinein, obwohl keiner ihn benutzt.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/shared/contracts/render-progress.ts

/**
 * Nutzlast des Ereignisses `render:fortschritt` (Main → Renderer, TK 9.2.7).
 * Ereignisse tragen KEINE Ergebnis-Hülle und KEINEN Endzustand (TK 9.1.1 Punkt 5).
 * Reine Laufzeitdaten – nichts davon wird persistiert.
 */
export interface RenderProgress {
  /** Lauf, auf den sich das Ereignis bezieht. Vom Renderer vergeben (TK 9.2.1). */
  renderId: string
  /** Phase des Laufs. */
  phase: 'normalisieren' | 'verketten'
  /** k von n – gesetzt in Phase 'normalisieren'; in 'verketten' null (ein Gesamtschritt). */
  elementIndex: number | null
  /** n – gesetzt in Phase 'normalisieren'; in 'verketten' null. */
  elementAnzahl: number | null
  /** aktuelles RenderItem zur UI-Markierung; laut TK optional -> null, wenn nicht zuordenbar. */
  elementId: string | null
  /** grober Gesamtfortschritt 0-100. Schaetzung, darf springen, nie <0, nie >100. */
  prozent: number
}
```

Genau diese sechs Felder – **keins mehr**. Insbesondere **kein** `status`, **kein** `fertig`,
**keine** Restzeit, **kein** `fehler`, **kein** `ausgabePfad`.

**Wer den Typ konsumiert und welche Felder er tatsächlich benutzt** (der umsetzende Agent sieht die
anderen Issues nicht):

```ts
// #68 – src/main/auftrags-manager/render-verzahnung.ts, bereits angelegt.
export function registriereRenderHandler(
  renderReel: (
    request: RenderRequest,
    aufFortschritt: (fortschritt: RenderProgress) => void,
  ) => Promise<RenderResult>,
  cancelRender: (renderId: string) => void,
): void
```

Aus dem übergebenen `RenderProgress` übernimmt #68 **ausschliesslich `prozent`** (nach `Auftrag.
fortschritt`, auf 0–100 begrenzt); `phase`, `elementIndex`, `elementAnzahl` und `elementId` benutzt
es **nicht**. **Das ist kein Argument, den Typ zu verkleinern:** Die vier übrigen Felder gehen an den
*anderen* Empfänger, die Render-Ansicht im Renderer (Abonnent #151), die daraus „Element 3 von 12,
Phase Normalisieren" anzeigt. Zwei Empfänger mit verschiedenem Bedarf, **ein** Typ.

**Melde-Klausel:** Weicht eine der hier abgeschriebenen fremden Signaturen von der tatsächlichen ab,
ist das ein **Vertragsfehler – melden, NICHT eigenmächtig anpassen.** Die definierende Datei gewinnt
immer.

**ENTSCHIEDEN – Umzug mit Re-Export, damit kein bestehender Importpfad bricht.** `render-result.ts`
(#19) deklariert `RenderProgress` heute selbst, und #68 importiert ihn von dort. Der Typ darf nach
diesem Issue **nicht zweimal** existieren. Deshalb, und nur das:

1. In `src/shared/contracts/render-result.ts` entfällt der Block `export interface RenderProgress
   { … }` ersatzlos.
2. Dieselbe Datei bekommt stattdessen **eine** Zeile:

   ```ts
   export type { RenderProgress } from './render-progress'
   ```

`RenderResult` selbst wird **nicht** angefasst – kein Feld, kein Kommentar, keine Umsortierung. Nach
dem Umzug übersetzt der Import aus #68 unverändert weiter, und `render-progress.ts` ist die
**einzige** Deklaration. Findest du in `render-result.ts` etwas anderes vor als die erwartete
`RenderProgress`-Deklaration – etwa zusätzliche Felder oder eine abweichende Schreibweise –, dann
**melden statt handeln**.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – | reine Typdefinition, kein Laufzeit-Eingang | Die Wertgrenzen (`prozent` 0–100, Drosselung, kein Ereignis nach dem terminalen Ergebnis) setzt der **Sender** durch: M6-05 (Berechnung/Drosselung) und M6-23 (Versand). Diese Datei erzwingt sie nicht und darf es auch nicht – sie hat keine Laufzeit. |

Ausgang bei Erfolg: `RenderProgress` ist aus `src/shared/contracts/render-progress.ts` importierbar
**und** – für bestehende Aufrufer wie #68 – weiterhin aus `src/shared/contracts/render-result.ts`.
Ausgang bei Fehler: entfällt (Typdefinition, keine Laufzeit-Fehlerpfade).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
Die Feldtabelle aus TK 9.2.7, **wörtlich**:

```
| Feld | Inhalt |
|---|---|
| `renderId` | Lauf, auf den sich das Ereignis bezieht |
| `phase` | `normalisieren` \| `verketten` |
| `elementIndex` / `elementAnzahl` | *k* von *n* (in Phase `normalisieren`; in `verketten` ein Gesamtschritt) |
| `elementId` | aktuelles `RenderItem` zur UI-Markierung (optional) |
| `prozent` | grober Gesamtfortschritt 0–100 |
```
(TK 9.2.7, Tabelle „Fortschritts-Ereignis `RenderProgress` (Main → Renderer, Kanal
`render:fortschritt`)")

- „**Keine** Restzeit-Schätzung – bei `ffmpeg` unzuverlässig, sie würde nur falsche Erwartungen
  erzeugen. Reine Laufzeitdaten (Kategorie D), **keine** Persistenz." (TK 9.2.7) – deshalb **kein**
  Feld `verbleibendeSekunden`, `eta` oder Ähnliches, und dieser Typ taucht in **keiner** Datei auf
  der Platte auf.
- „**5. Ereignisse sind Einbahnstraßen und tragen keinen Endzustand** (für `RenderProgress` bereits
  festgelegt, 9.2.7). Terminale Zustände kommen ausschließlich über Aufruf-Ergebnis bzw.
  Auftrags-Zustand." (TK 9.1.1)
- „Der Fortschrittskanal trägt **keinen** Endzustand. Erfolg, Fehler und Abbruch kommen
  **ausschließlich** über das `RenderResult` (9.2.3)." (TK 9.2.7)
- „Nach dem terminalen `RenderResult` dürfen **keine** weiteren `RenderProgress`-Ereignisse dieser
  `renderId` mehr folgen. Verspätete Ereignisse eines bereits beendeten Laufs erkennt der Renderer an
  der nicht mehr aktuellen `renderId` und verwirft sie." (TK 9.2.7) – genau **dafür** ist das Feld
  `renderId` da; es darf niemals entfallen oder optional werden.
- „**Ereignisse** (Main → Renderer) tragen ebenfalls keine Hülle (Punkt 5)." (TK 9.1.1 Punkt 2) –
  in dieser Datei steht deshalb **kein** `Ergebnis<…>`.
- „**Der Kanal `render:fortschritt` wird gebaut, nicht nur erwähnt.** […] Der `render-service` meldet
  darauf, das `ipc-gateway` meldet ihn an, der Renderer abonniert ihn." (TK 9.2.7) – dieser Typ ist
  kein Platzhalter für später, sondern die Nutzlast eines Kanals der v1.
- „**Daneben behält die Warteschlange ihren groben Prozentwert:** `RenderProgress.prozent` speist
  `Auftrag.fortschritt` (9.3.6), der über `queue:geaendert` in die Warteschlangen-Leiste geht. Zwei
  Kanäle mit verschiedenem Zweck – der eine detailliert und flüchtig für die Render-Ansicht, der
  andere grob im Auftrags-Zustand." (TK 9.2.7) – deshalb bleibt der Typ vollständig, obwohl #68 nur
  `prozent` liest.

## Fehlerpfade (vollständig)
Entfällt (reine Typdefinition, keine Laufzeit). Die Begrenzung von `prozent` auf 0–100 und die
Drosselung sind **Verhalten des Senders** (M6-05, M6-23) und des Empfängers (#68 begrenzt zusätzlich
auf 0–100); ein Typ kann sie nicht erzwingen, und ein Versuch, es doch zu tun (Branded Types,
Laufzeit-Prüffunktionen), gehört nicht in diese Datei.

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – kein Endzustand, in keiner Form.** Kein `status`, kein `fertig`, kein `abgeschlossen`,
  kein `fehler`, kein `ergebnis`, auch nicht optional und auch nicht „nur für die Anzeige". TK 9.2.7
  ist hier eindeutig, und die Doppelung wäre genau die Fehlerklasse, die im Projekt schon das
  `position`-Feld und `historieEintrag` gekostet hat.
- **Verbot – keine Restzeit und keine abgeleiteten Anzeigewerte.** Kein `eta`, kein
  `verbleibendeSekunden`, kein vorformatierter Text („Element 3 von 12"). Formatieren ist Sache der
  Oberfläche.
- **Verbot – keine Ergebnis-Hülle und keine Validierungsfunktion.** Diese Datei enthält **nur** eine
  Typdeklaration; keine `istGueltig`-Funktion, keine Konstanten, kein Default-Objekt.
- **Verbot – `elementId` bleibt `string | null`, nicht `elementId?: string`.** TK 9.2.7 nennt das
  Feld „(optional)"; die im Projekt gewählte Schreibweise für „kann fehlen" in Ereignis- und
  Ergebnistypen ist der **explizite `null`-Zweig** (so steht es in #19). Ein weggelassenes Feld und
  ein `null`-Feld sind über IPC nicht dasselbe, sobald jemand `in`-Prüfungen benutzt.
- **Verbot – an `render-result.ts` genau die zwei genannten Eingriffe.** `RenderResult` wird **nicht**
  angefasst. Jede darüber hinausgehende Änderung kollidiert mit #19 und ist zu **melden**, nicht
  auszuführen.
