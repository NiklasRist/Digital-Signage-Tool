### Issue M6-18: [render-service] RenderRequest vollständig validieren, bevor irgendetwas geschieht

## Ziel (in einem Satz)
Ein Render-Auftrag wird vollständig auf Stimmigkeit geprüft, **bevor** ein Ordner angelegt, eine
Datei geschrieben oder `ffmpeg` gestartet wird – und eine unstimmige Anfrage hinterlässt keinerlei
Spur.

## Modul & Datei
- Modul: `render-service` [P4] (Main)
- Datei: `src/main/render-service/validierung.ts`
- Vertrag: Technisches Konzept **9.2.3** (welche Situation welchen Code bekommt), **9.2.6**
  (Ausgabename ist Nutzereingabe und wird validiert), **9.2.1/9.2.2** (`RenderRequest`,
  `RenderItem`), **9.1.1** Punkt 6 (der Main vertraut dem Renderer nicht) – Quelle der Wahrheit
- Prozess/Speicher: P4; **kein** Dateisystem, **kein** ffmpeg, **kein** Zustand – reine Prüfung

## Warum das im Gesamtsystem wichtig ist
Diese Datei ist die Grenzkontrolle des teuersten Vorgangs im Programm. Ein Render dauert Minuten,
belegt Gigabyte in T1 und überschreibt am Ende – das ist der **Regelfall**, weil der Zielname mit
dem zuletzt verwendeten vorbelegt ist – eine vorhandene, funktionierende Ausgabedatei. Jeder Mangel,
der hier durchrutscht, wird erst irgendwo mitten im Lauf sichtbar: nach fünf Minuten
Normalisierungsarbeit, mit einem halb gefüllten Arbeitsbereich und einer angefangenen `.part`-Datei.

Zwei Fehlgriffe sind besonders teuer:

1. **Zu spät prüfen.** Ein Segment ohne PNG-Puffer oder ein Band-PNG mit falscher Höhe fällt sonst
   erst dem `ffmpeg`-Aufruf auf – und der meldet einen technischen Fehler, aus dem niemand ableiten
   kann, **welches** Element gemeint ist. Der geführte Reparatur-Modus (FA-19) muss den Nutzer aber
   an eine konkrete Stelle führen können.
2. **Dem Renderer glauben.** Der `ausgabeName` ist **Nutzereingabe**. Ein Name wie `../../config`
   führt aus dem Projektordner heraus, und geschrieben wird mit den Rechten der App. Genauso ist
   `einblendung.höhe` eine Zahl, die aus dem Renderer kommt – eine Höhe von 1080 ergäbe eine
   Videofläche von null Pixeln.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/render-service/validierung.ts
import type { RenderRequest } from '../../shared/contracts/render-request'
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { RenderFehlercode } from './fehlercodes'

/** Maße eines PNG-Puffers, aus dem IHDR-Kopf gelesen – ohne Dekodieren. */
export interface PngMasse {
  breite: number
  höhe: number
}

/** Liest Breite und Höhe aus den ersten 24 Bytes eines PNG. Dekodiert das Bild NICHT. */
export function liesPngMasse(png: Uint8Array): Ergebnis<PngMasse, RenderFehlercode>

/**
 * Prüft die gesamte Anfrage. Wirkungsfrei: liest nichts, schreibt nichts, startet nichts.
 * Erfolg heisst „diese Anfrage darf ausgeführt werden", nicht „sie wird gelingen".
 */
export function pruefeRenderRequest(request: RenderRequest): Ergebnis<void, RenderFehlercode>
```

**Die Prüfreihenfolge ist verbindlich: erst die Anfrage, dann die Elemente.**

**Stufe 1 – die Anfrage** (Verstoß → `ungueltige_eingabe`, **ohne** `daten`):

| # | Prüfung |
|---|---|
| 1 | `request` ist ein Objekt |
| 2 | `projektId` ist eine nicht leere Zeichenkette |
| 3 | `renderId` ist eine nicht leere Zeichenkette |
| 4 | `elemente` ist ein Array mit **mindestens einem** Eintrag |
| 5 | jedes Element hat eine nicht leere Zeichenkette `id`, und alle `id` sind **untereinander verschieden** |
| 6 | jedes Element hat eine `art` aus `'video' \| 'bild' \| 'segment'` |
| 7 | `profil` stimmt **feldweise** mit `RENDER_PROFILE` (#18) überein |
| 8 | `loeseAusgabePfad(projektId, ausgabeName)` (#49) liefert `ok` |

**Stufe 2 – jedes Element einzeln** (Verstoß → `ungueltiges_element` **mit**
`daten: { elementId: element.id }`, Abbruch beim **ersten** unstimmigen Element):

| `art` | Prüfungen |
|---|---|
| alle | `frameDauer(element)` (M6-19) liefert `ok` – damit sind Trim bzw. `dauer` endlich, positiv und mindestens **ein** Frame lang |
| `video` | `medienRef` ist eine nicht leere Zeichenkette · `einblendung` ist `null` **oder** besteht die Einblendungs-Prüfung (s. u.) |
| `bild` | `medienRef` ist eine nicht leere Zeichenkette · `dauer` liegt **einschließlich** im `DAUER_BEREICH` (#21) |
| `segment` | `png` ist ein `Uint8Array` mit `byteLength > 0` · `liesPngMasse(png)` ergibt genau `RENDER_PROFILE.breite × RENDER_PROFILE.hoehe` · `dauer` liegt **einschließlich** im `DAUER_BEREICH` |

**Einblendungs-Prüfung** (nur bei `art: 'video'` mit `einblendung !== null`):

| # | Prüfung |
|---|---|
| 1 | `bestimmeBandgeometrie({ art, höhe })` (M6-21) liefert `ok` – damit sind `art` und `höhe` gesetzt und plausibel |
| 2 | `abschnitte` ist ein Array mit **mindestens einem** Eintrag |
| 3 | je Abschnitt: `png` ist ein `Uint8Array` mit `byteLength > 0` |
| 4 | je Abschnitt: `liesPngMasse(png)` ergibt genau `bandBreite × bandHoehe` aus der Geometrie |
| 5 | je Abschnitt: `dauer` ist endlich, `> 0` und ergibt über `zuFrames` (M6-19) **mindestens einen** Frame |

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `request` | der vollständige Render-Auftrag, so wie er beim Einreihen eingefroren wurde | wird **vollständig** misstraut – der Typ sagt nichts über die Laufzeitwerte (TK 9.1.1 Punkt 6) |
| `png` (`liesPngMasse`) | Binärpuffer eines PNG aus dem Auftrag | mindestens 24 Bytes, gültige PNG-Signatur, `IHDR` als erster Abschnitt |

Ausgang bei Erfolg: `{ ok: true, wert: undefined }` – die Anfrage darf ausgeführt werden.
Ausgang bei Fehler: `ungueltige_eingabe` (Stufe 1, ohne `daten`) oder `ungueltiges_element`
(Stufe 2, mit `daten: { elementId }`).

## ENTSCHIEDEN (lokale Festlegungen dieses Issues)

1. **Die Zeichenregeln für den `ausgabeName` werden hier NICHT nachgebaut.** Diese Datei ruft
   `loeseAusgabePfad(projektId, ausgabeName)` (#49) auf und wertet **nur** aus, ob das Ergebnis
   `ok` ist; den gelieferten Pfad **verwirft** sie. Begründung: #49 ist die Pfad-Autorität und
   führt die Prüfung aus TK 9.2.6 bereits vollständig durch (Pfadtrenner, `..`, unzulässige
   Zeichen, reservierte Windows-Namen sowie die Schranke, dass der aufgelöste Pfad innerhalb von
   `projects/<id>/output/` liegen muss). Eine zweite Umsetzung
   derselben Regeln wäre eine zweite Wahrheit – und die gefährliche Sorte davon: Sie könnte
   **milder** ausfallen als die echte, und dann liefe die Prüfung hier durch, während der Render
   später an anderer Stelle scheitert. Der Aufruf ist ohne Nebenwirkung („reine
   String-/Validierungs-Operation (kein `fs.*`-Aufruf, keine Existenzprüfung)", #49), verletzt die
   Wirkungsfreiheit dieser Datei also nicht.
2. **Der Auflösungsvorgang wird später wiederholt.** Wer die Datei tatsächlich schreibt, ruft
   `loeseAusgabePfad` erneut auf. Das ist gewollt: Ein hier durchgereichter Pfad wäre ein zweiter
   Weg zum selben Wert, und die Auflösung kostet nichts.
3. **`profil` wird feldweise gegen `RENDER_PROFILE` geprüft; jede Abweichung ist
   `ungueltige_eingabe`.** Verglichen werden **alle** Felder, auch die verschachtelten
   (`ratensteuerung`, `farbmetadaten`, `audio`) – ausgeschrieben, **kein** selbstgebauter
   Tiefenvergleich und **kein** `JSON.stringify`-Vergleich (dessen Ergebnis von der
   Schlüsselreihenfolge abhängt). Begründung: Heute gibt es genau **ein** Profil; ein davon
   abweichender Wert im Auftrag kann also nur aus einem Fehler oder einer Manipulation im Renderer
   stammen, und das Profil ist die TV-Kompatibilität selbst (TK 9.2.4: „Wird das Format der Quelle
   übernommen (4:2:2, 4:4:4 oder 10 Bit), **spielt der TV die Datei nicht ab**"). Lieber ein lauter
   Fehlschlag als eine Datei, die im Studio nicht startet.
   **Vermerk für den Auftraggeber:** Sollte das Projekt je ein zweites Ausgabe-Profil bekommen, ist
   diese Prüfung bewusst zu lockern. Sie ist genau deshalb an **einer** Stelle und ausgeschrieben.
4. **Eine fehlende oder doppelte Element-`id` ist `ungueltige_eingabe`, nicht
   `ungueltiges_element`.** Begründung: Ohne eindeutige `id` gibt es keinen Wert für
   `daten: { elementId }` – der Fehler könnte den Nutzer nirgendwohin führen, und der
   Reparatur-Modus (FA-19) stünde vor zwei Elementen mit derselben Kennung. Das ist ein Mangel der
   **Anfrage** als Ganzes, kein Mangel eines einzelnen Elements. TK 9.2.1 begründet die `id`
   ausdrücklich mit der „eindeutigen **Fehlerzuordnung**".
5. **Die Maße der PNGs werden aus dem IHDR-Kopf gelesen, nicht durch Dekodieren.** Ein PNG beginnt
   mit der 8-Byte-Signatur `89 50 4E 47 0D 0A 1A 0A`, danach folgt die Länge (4 Byte), die
   Abschnittskennung `IHDR` (4 Byte, Versatz 12) und dann Breite und Höhe als je 4 Byte
   **Big-Endian** an Versatz **16** und **20**. Mehr wird nicht gebraucht und nichts weiter
   geprüft: keine Prüfsumme, keine Farbtiefe, kein Bibliotheks-Aufruf, kein Bild im Speicher. Ein
   Puffer von 30 MB darf beim Validieren nicht dekodiert werden.
6. **Beim ersten unstimmigen Element wird abgebrochen.** Es werden **nicht** alle Fehler gesammelt.
   Begründung: `RenderResult` hat genau **ein** Feld `fehlerhaftesElementId` (#19), und der
   Reparatur-Modus führt den Nutzer laut TK 9.7.5 ohnehin „eins nach dem anderen".
7. **`medium_fehlt` wird hier NIE vergeben.** Ob die Datei zu `medienRef` existiert, verlangt einen
   Dateisystem-Zugriff; diese Datei hat keinen. TK 9.2.3 verlangt die Prüfung „**vor** dem ersten
   `ffmpeg`-Aufruf" – das ist erfüllt, wenn sie beim Auflösen des Pfades im
   Normalisierungs-Schritt (M6-22) geschieht, also ebenfalls vor dem ersten Encodieren. Hier wird
   `medienRef` **nur** als nicht leere Zeichenkette geprüft.
8. **Keine eigene Pfadprüfung an `medienRef`.** Kein `..`-Test, keine Normalisierung, keine Prüfung
   auf Verzeichnistrenner. Das tut `loeseAssetPfad` (#49) an der Stelle, an der die Datei
   tatsächlich geöffnet wird. Zweite Prüfung = zweite Wahrheit; dieselbe Regel wie in #86.
9. **Die 10–45-Sekunden-Grenze gilt für `bild` und `segment`, NICHT für Band-Abschnitte und NICHT
   für Videos.** Für Videos ergibt sich die Dauer aus dem Trim (TK 9.11.3: „die Dauer ergibt sich
   aus dem Trim"); für Band-Abschnitte nennt das TK keinen Bereich, und eine erfundene Grenze
   würde einen zulässigen Auftrag abweisen. Für Abschnitte gilt nur: endlich, `> 0`, mindestens ein
   Frame.
10. **Die Grenzen des `DAUER_BEREICH` sind einschließlich.** `10` und `45` sind zulässig, `9.9` und
    `45.1` nicht. TK 9.2.3 schreibt „`dauer` außerhalb 10–45 s"; „außerhalb" schließt die Grenzen
    selbst nicht ein.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Der Main validiert jede eingehende Nutzlast** – er vertraut dem Renderer **nicht**. Ungültige
  Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten. Ein Fehler im Renderer darf
  D1 niemals beschädigen." (TK 9.1.1, Punkt 6)
- „| `ungueltige_eingabe` | Die **Anfrage** verletzt den Vertrag, unabhängig von einzelnen
  Elementen: unzulässiger `ausgabeName` (9.2.6), leere Elementliste, unbekannte `art`, fehlende
  `projektId`. Generischer Code aus 9.1.1 Punkt 3 – **ohne jede Wirkung** auf Daten oder Dateien |"
  (TK 9.2.3)
- „| `ungueltiges_element` | Ein einzelnes `RenderItem` ist in sich unstimmig: Trim außerhalb der
  Quelldauer, `dauer` außerhalb 10–45 s, `"segment"` ohne PNG-Puffer, `einblendung` ohne
  Abschnitte oder mit `höhe` ≥ 1080, PNG-Maße ≠ der erwarteten Fläche (1920 × 1080 bzw.
  1920 × `höhe`) | Das benannte Element im `composer` korrigieren (Dauer/Trim/Band) und erneut
  rendern |" (TK 9.2.3) – **bis auf „Trim außerhalb der Quelldauer"**: Die Quelldauer kennt nur,
  wer die Datei liest (ENTSCHIEDEN 7). Alle übrigen fünf Fälle werden hier abgedeckt.
- „**Der Ausgabename ist Nutzereingabe und wird validiert (FA-22):** Erlaubt ist ein reiner
  Dateiname **ohne** Endung – **keine** Pfadtrenner (`/`, `\`), **kein** `..`, keine für
  Windows/macOS/FAT32 unzulässigen Zeichen (`< > : " | ? *`, Steuerzeichen), nicht leer, keine
  reservierten Windows-Namen (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`). Der
  aufgelöste Pfad muss **innerhalb** von `projects/<id>/output/` liegen. Verstoß →
  `ungueltige_eingabe`, **ohne** Wirkung. Andernfalls könnte ein Name wie `../../config` aus dem
  Projekt ausbrechen." (TK 9.2.6) – **durchgeführt wird diese Prüfung von `loeseAusgabePfad`
  (#49)**, nicht hier (ENTSCHIEDEN 1).
- „Der Ausgabe-**Pfad** ist **nicht** Teil der Anfrage – nur der **Name**: Der Main setzt ihn über
  die Pfad-Autorität (9.5.7) zu `projects/<projektId>/output/<ausgabeName>.mp4` zusammen. Der
  Renderer kennt **keine** absoluten Pfade. Der Name ist **Nutzereingabe** und daher zu validieren
  (9.2.6)." (TK 9.2.1)
- „Jedes `RenderItem` trägt eine `id` zur eindeutigen **Fehlerzuordnung**; die Reihenfolge ergibt
  sich aus der Listenposition, nicht aus einem separaten Feld." (TK 9.2.1)
- „**Die betroffene Element-ID erreicht die Oberfläche über die strukturierten Fehlerdaten.** […]
  Die Form von `daten` ist damit **je Fehlercode festgelegt**: `{ elementId: string }` bei
  `medium_fehlt` und `ungueltiges_element`, sonst nicht gesetzt." (TK 9.2.3)
- „**Alle Werte gelten identisch für jedes Segment** – sonst scheitert die
  Uniformitäts-Voraussetzung von `-c copy` (9.2.6). Das Profil ist eine Konstante, wird aber
  **explizit** im Vertrag geführt (spätere Profil-Änderung = ein Datenwert, kein
  Schnittstellenbruch)." (TK 9.2.4) – Grundlage von ENTSCHIEDEN 3.
- „Bei `"segment"` werden **keine** Aktions-/Vorlagendaten mitgeschickt – die Pixel sind bereits
  final; das ist der Kern von Variante A." (TK 9.2.2) – deshalb ist ein `segment` **ohne** PNG-Puffer
  kein Sonderfall, sondern ein leeres Element.
- „**Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code. Es gibt keine Operation,
  die „einfach nichts" zurückgibt und auf Gelingen hofft." (TK 9.1.1, Punkt 7)
- Niemals `throw` – diese Funktion wird aus einer IPC-bedienten Operation heraus benutzt
  (TK 9.1.1).

| PNG-Maße eines `segment` ≠ `RENDER_PROFILE.breite × RENDER_PROFILE.hoehe` | `ungueltiges_element` + `daten: { elementId }` | keine Wirkung; Meldung nennt Soll- und Ist-Maße |
| `bestimmeBandgeometrie` (M6-21) liefert nicht `ok` | Code und Meldung von M6-21, **ergänzt** um `daten: { elementId }` | keine Wirkung |
| `einblendung.abschnitte` kein Array oder leer | `ungueltiges_element` + `daten: { elementId }` | keine Wirkung; der in TK 9.2.3 genannte Fall „`einblendung` ohne Abschnitte" |
| ein Abschnitts-`png` fehlt, ist kein `Uint8Array` oder ist leer | `ungueltiges_element` + `daten: { elementId }` | keine Wirkung; die Meldung nennt den **Index** des Abschnitts |
| PNG-Maße eines Abschnitts ≠ `bandBreite × bandHoehe` | `ungueltiges_element` + `daten: { elementId }` | keine Wirkung; Meldung nennt Abschnittsindex, Soll- und Ist-Maße |
| Abschnitts-`dauer` nicht endlich, `<= 0` oder weniger als ein Frame | `ungueltiges_element` + `daten: { elementId }` | keine Wirkung |
| `png` kürzer als 24 Bytes, falsche Signatur oder kein `IHDR` (`liesPngMasse`) | `ungueltiges_element` | keine Wirkung; `liesPngMasse` selbst setzt **kein** `daten` – der Aufrufer in dieser Datei ergänzt es |
| Unerwartete Ausnahme | `unbekannter_fehler` | fangen und in das Ergebnis wandeln; **kein** `throw` |

Es wird **kein** neuer Fehlercode eingeführt. Beide benutzten Codes stammen aus TK 9.2.3;
`ungueltiges_element` ist in M6-16 deklariert, `ungueltige_eingabe` ist einer der drei generischen
Codes aus #12.
