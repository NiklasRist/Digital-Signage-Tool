### Issue M7-18: [queue-panel] Fehlercodes in Klartext übersetzen

## Ziel (in einem Satz)
Aus dem Fehlercode eines gescheiterten Auftrags wird **eine** Stelle im ganzen Renderer ein
verständlicher Satz mit einer auf die Ursache zugeschnittenen Handlungsempfehlung – samt der
Nutzdaten, die den Fehler erst bedienbar machen: betroffene Listenelemente, der exFAT-Hinweis und
die Element-Kennung als Sprungziel in den Reparatur-Modus.

## Modul & Datei
- Modul: `queue-panel` (Renderer)
- Datei: `src/renderer/queue-panel/fehlertexte.ts` – **die einzige** Datei dieses Issues
  (+ zugehörige Testdatei)
- Vertrag: Technisches Konzept **9.1.1** (Fehlercodes und strukturierte Fehlerdaten – Quelle der
  Wahrheit), **9.2.3** (Fehlercodes `render-service`), **9.4.9** (Fehlercodes `media-service`),
  **9.6.4** (Fehlercodes `export-service`), **9.3.1** (`Auftrag.fehler`), **9.7.5** (geführter
  Reparatur-Modus)
- Prozess/Speicher: P6 mittelbar; **rein**, kein Zustand, keine IPC-Aufrufe

## Warum das im Gesamtsystem wichtig ist
Der ganze Aufwand, den das Konzept mit typisierten Fehlercodes treibt, zahlt sich **hier** aus oder
gar nicht. Das TK begründet die Ergebnis-Hülle ausdrücklich damit, dass an den Codes „echtes
Verhalten" hängt – und nennt genau die drei Fälle, die diese Datei bedienen muss: die betroffenen
Listenelemente bei `asset_referenziert`, die exFAT-Erklärung bei `datei_zu_gross_fat32` und
verschiedene Hinweise für `kein_platz` und `ziel_gesperrt`. Ohne diese Übersetzung degradieren
Reparatur-Modus, Wiederholen und der FAT32-Hinweis zu einer einzigen nichtssagenden Meldung – der
volle Wortlaut steht unten in den Invarianten.

**Eine** Tabelle für alle vier Dienste ist Absicht, nicht Bequemlichkeit. Die Codes sind über die
Dienste hinweg bewusst **vereinheitlicht**: `speicher_fehler` heißt im `render-service`, im
`media-service` und im `export-service` dasselbe, und das TK begründet das ausführlich – „Alles
andere zwänge die Oberfläche, **zwei** Namen für **eine** Sache zu kennen (zwei Meldungstexte, zwei
Zweige im Reparatur-/Wiederhol-Pfad)". Drei Übersetzungstabellen in drei Dateien wären genau der
Zustand, den diese Vereinheitlichung verhindern sollte: Derselbe Code bekäme drei Formulierungen,
und welche der Nutzer sieht, hinge davon ab, welcher Auftrag gescheitert ist.

Der teuerste lokale Fehlgriff ist der **Textvergleich**. Wer `meldung.includes('nicht gefunden')`
schreibt, baut eine Zuordnung, die bei jeder Umformulierung im Main lautlos bricht – und niemand
merkt es, weil dann eben der allgemeine Text erscheint. Das TK nennt genau diesen Fehler als
Begründung für die ganze Hüllen-Konstruktion.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/queue-panel/fehlertexte.ts
import type { AuftragArt } from '../../shared/contracts/auftrag'

export interface Fehlertext {
  /** Kurze Ueberschrift, z. B. „Nicht genug Speicherplatz". Nie leer. */
  titel: string
  /** Was passiert ist, in einem Satz. Nie leer. */
  erklaerung: string
  /** Was der Nutzer JETZT tun kann – ursachenbezogen, nie ein leerer Platzhalter. */
  handlung: string
  /**
   * Listenelement-Kennungen aus `fehler.daten`, sofern der Code welche traegt.
   * Leeres Array, wenn der Code keine Nutzdaten hat oder sie unbrauchbar sind.
   */
  betroffeneElementIds: string[]
  /**
   * Die Element-Kennung, zu der ein Sprung in den gefuehrten Reparatur-Modus fuehren soll –
   * oder null. Gesetzt NUR bei `medium_fehlt` und `ungueltiges_element` (TK 9.2.3).
   * Diese Datei fuehrt den Sprung NICHT aus; sie benennt nur das Ziel (s. STOPP).
   */
  reparaturElementId: string | null
  /** true, wenn der Fehler durch erneutes Ausfuehren behebbar sein kann (FA-17). */
  wiederholenSinnvoll: boolean
}

/**
 * Die EINZIGE Uebersetzung von Fehlercode nach Klartext im Renderer.
 * `art` verfeinert nur die Handlungsempfehlung dort, wo derselbe Code je nach Dienst
 * einen anderen ORT meint (`kein_platz`); sie ist nie noetig, um den Code zu ERKENNEN.
 */
export function uebersetzeFehler(
  fehler: { code: string; meldung: string; daten?: unknown },
  art: AuftragArt | null,
): Fehlertext

/** Die Codes, die diese Tabelle kennt – fuer die Vollstaendigkeitspruefung im Test. */
export const BEKANNTE_FEHLERCODES: readonly string[]
```

allen Diensten dieselbe Bedeutung; `art` verfeinert nur den **Ort** bei `kein_platz`. Begründung
aus dem Vertrag: „**Dieselbe Ursache bekommt denselben Namen.**" (TK 9.6.4)

`erklaerung` und `handlung` in der Tabelle sind **verbindlich dem Sinn nach**; die genaue
Formulierung darf sprachlich geglättet werden, solange die Handlungsempfehlung erhalten bleibt.
Der `titel` ist **zeichengleich** zu übernehmen (er ist Anzeigetext an mehreren Stellen).

**ENTSCHIEDEN 3 – `fehler.meldung` wird NICHT verworfen, aber auch nicht ausgewertet.** Der Text
aus dem Main ist eine zusätzliche technische Auskunft; er wird von dieser Datei **nicht** gelesen,
**nicht** verglichen und **nicht** in `erklaerung` eingesetzt. Ob und wo die Oberfläche ihn
zusätzlich zeigt (z. B. ausklappbar als Detail), entscheidet der Aufrufer.

**ENTSCHIEDEN 4 – `daten` wird defensiv ausgelesen.** Der Typ ist `unknown`; es wird auf Objekt,
Feldvorhandensein und Typ geprüft, bevor gelesen wird. Ist `daten` unbrauchbar, bleibt
`betroffeneElementIds` leer und `reparaturElementId` `null` – der Text erscheint trotzdem, ohne
Ausnahme und ohne Platzhalter wie `undefined` im Satz. Die zwei bekannten Formen (TK 9.1.1 / 9.2.3
/ 9.4.9):

```ts
// bei asset_referenziert (TK 9.4.9)
{ referenzenIds: string[] }
// bei medium_fehlt und ungueltiges_element (TK 9.2.3)
{ elementId: string }
```

**ENTSCHIEDEN 5 – `vorlage_referenziert` steht NICHT in dieser Tabelle.** Vorlagen-Operationen sind
**keine** Aufträge (TK 9.3.2 führt die Instant-Operationen ausdrücklich außerhalb der Queue), und
`Vorlagennutzung` (TK 9.12.1) ist eine ganz andere Nutzdatenform – zwei Trefferlisten mit Projekt-
und Fundstellennamen, die eine eigene Darstellung brauchen. Sie hier mitzuschleppen brächte in eine
Datei des `queue-panel` einen Typ, den das `queue-panel` nie sieht. Siehe dazu die offene Frage im
STOPP-Block.

**Fremde Typen, die du benutzt** – vollständig ausgeschrieben, du siehst die anderen Issues nicht:

```ts
// #16 – src/shared/contracts/auftrag.ts (Ausschnitt)
export type AuftragArt = 'import' | 'loeschen' | 'render' | 'export'
// Auftrag.fehler hat die Form:
//   { code: string; meldung: string; daten?: unknown } | null
// `code` ist im GETEILTEN Vertrag bewusst `string`: der geteilte Vertrag darf die fachlichen
// Unionen der Main-Module nicht kennen. Die Enge sitzt dort, wo der Code ENTSTEHT.
// Genau deshalb ist diese Datei nach `string` geschluesselt und braucht einen Zweig fuer
// „jeder andere Code".

// #12 + #22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
```

**MELDE-KLAUSEL (bindend).** Weicht eine dieser Signaturen von der tatsächlichen Fassung der
definierenden Datei ab, ist das ein **Vertragsfehler** – **melden, NICHT eigenmächtig anpassen.**
Besonders zu prüfen: Trägt `Auftrag.fehler.code` wider Erwarten eine **enge** Union statt `string`,
ist der Zweig „jeder andere Code" überflüssig – trotzdem **melden**, nicht stillschweigend
umbauen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `fehler.code` | der Fehlercode aus dem Fachdienst | beliebige Zeichenkette; unbekannte Werte müssen einen gültigen `Fehlertext` ergeben |
| `fehler.meldung` | technischer Text aus dem Main | wird **nicht** ausgewertet (ENTSCHIEDEN 3) |
| `fehler.daten` | strukturierte Nutzdaten, `unknown` | defensiv auslesen (ENTSCHIEDEN 4); nie ungeprüft in einen Text einsetzen |
| `art` | Auftragsart, oder `null` | verfeinert **nur** `kein_platz`; für alle anderen Codes wirkungslos |

Ausgang: ein vollständig belegter `Fehlertext`. `titel`, `erklaerung` und `handlung` sind **nie**
leer; `betroffeneElementIds` ist nie `undefined` (leeres Array statt dessen).
Ausgang bei Fehler: **keiner**. Die Funktion ist rein, wirft nie und trägt keine `Ergebnis`-Hülle.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- (TK 9.1.1, wörtlich)

  > Bei uns hängt an den Codes **echtes Verhalten**: `asset_referenziert` zeigt die betroffenen
  > Listenelemente, `vorlage_referenziert` beide Trefferlisten (9.12.1), `datei_zu_gross_fat32`
  > erklärt exFAT, `kein_platz` und `ziel_gesperrt` brauchen verschiedene Hinweise. Geht der Code
  > verloren, degradieren Reparatur-Modus, Wiederholen und der FAT32-Hinweis alle zu „irgendwas ist
  > schiefgelaufen".
- „Der Aufrufer müsste dann Meldungstexte vergleichen (`e.message.includes(...)`), was bei jeder
  Umformulierung, Tippfehler-Korrektur oder Übersetzung bricht." (TK 9.1.1) – **das** Verbot dieser
  Datei.
- „**3. Fehlercodes sind ein geschlossener, typisierter Satz:** die fachlichen je Operation (9.4.9,
  9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`.
  **Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1)
- „Regeln: Das Feld ist **optional** – Codes ohne Zusatzdaten lassen es weg; seine Form ist **je
  Fehlercode festgelegt und typisiert** (dokumentiert dort, wo der Code vergeben wird: 9.4.9, 9.6.4,
  9.12.1); es ist **kein Freitext-Anhang** und **kein Ersatz für `meldung`**. Ein Aufrufer, der
  `daten` nicht kennt, funktioniert unverändert weiter." (TK 9.1.1)
- „Die Form von `daten` ist damit **je Fehlercode festgelegt**: `{ elementId: string }` bei
  `medium_fehlt` und `ungueltiges_element`, sonst nicht gesetzt." (TK 9.2.3)
- „| `asset_referenziert` | ein ListItem zeigt noch darauf; trägt `daten: { referenzenIds:
  string[] }` (strukturierte Fehlerdaten, 9.1.1) |" (TK 9.4.9)
- „| `datei_zu_gross_fat32` | Ziel ist FAT32 und die Datei überschreitet 4 GB → exFAT nötig |"
  (TK 9.6.4)
- „**Dieselbe Ursache bekommt denselben Namen.** Alles andere zwänge die Oberfläche, **zwei** Namen
  für **eine** Sache zu kennen (zwei Meldungstexte, zwei Zweige im Reparatur-/Wiederhol-Pfad) – und
  der Code steht **dauerhaft** im Protokoll Q3 (9.3)" (TK 9.6.4) – **die** Begründung für **eine**
  Tabelle.
- „**`abgebrochen` ist *kein* Fehlercode.** Ein vom Nutzer abgebrochener Lauf endet über
  `status: "abgebrochen"` (9.2.7) und trägt **kein** `fehler`-Objekt – sonst gäbe es zwei Wege,
  denselben Ausgang zu melden, und die Oberfläche zeigte einen Abbruch als Fehler an." (TK 9.2.3) –
  diese Datei wird für einen Abbruch **nie** aufgerufen und hat dafür **keinen** Eintrag.
- „**8. Unerwartete Ausnahmen fängt das Gateway** und übersetzt sie in `unbekannter_fehler` (intern
  protokolliert). Die App stürzt nicht ab, und **kein Stacktrace** gelangt in die Oberfläche."
  (TK 9.1.1) – deshalb erscheint `fehler.meldung` **nie** als alleiniger Text.
- „Zu jedem Zeitpunkt ist erkennbar, welcher Auftrag gerade läuft, welche anstehen und welche
  fehlgeschlagen sind (jeweils mit Klartext-Bezeichnung, bei Fehlern mit Fehlergrund)."
  (Anforderungsdokument 4.3, FA-16) – **Fehlergrund** heißt Klartext, nicht Code.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| bekannter Code | – | Eintrag aus der Tabelle |
| unbekannter Code | – | Zweig „jeder andere Code": gültiger `Fehlertext`, `titel` `Unerwarteter Fehler`; der Rohcode wird **nicht** in den Text geschrieben |
| leerer Code (`''`) | – | wie unbekannter Code; **kein** `throw` |
| `daten` fehlt, obwohl der Code Nutzdaten haben sollte | – | `betroffeneElementIds` leer, `reparaturElementId` `null`; Text erscheint trotzdem; **kein** `throw`, **kein** Platzhalter im Satz |
| `daten` ist kein Objekt (Zahl, String, `null`) | – | wie oben |
| `daten.referenzenIds` ist kein Array oder enthält Nicht-Strings | – | nur die brauchbaren Einträge übernehmen; der Rest wird **stillschweigend** ausgelassen (die Anzeige ist nicht der Ort, an dem ein Vertragsbruch des Senders auffällt) |
| `daten.elementId` ist kein String oder leer | – | `reparaturElementId` bleibt `null`; die Anzeige bietet dann **keinen** Sprung an, statt ins Leere zu springen |
| `art` ist `null` bei `kein_platz` | – | die allgemeinere Render-Formulierung verwenden |

Es gibt in diesem Issue **keinen** Fehlercode nach außen: Die Funktion ist rein.

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – NIE Meldungstexte vergleichen.** Kein `meldung.includes(...)`, kein
  `startsWith`, kein `match`, kein `toLowerCase()`-Vergleich auf `meldung`. Ausschließlich `code`
  entscheidet. (Grep-Probe ist Teil der Definition of Done.)
- **Verbot – kein Stacktrace, kein Rohtext als Hauptmeldung.** `titel`, `erklaerung` und `handlung`
  werden **immer** aus der Tabelle gebaut. `fehler.meldung` wird nicht eingesetzt (ENTSCHIEDEN 3).
- **Verbot – keine leere Handlungsempfehlung.** Es gibt **keinen** Zweig, in dem `handlung` leer ist
  oder „Bitte wenden Sie sich an den Support" lautet. Auch der unbekannte Code bekommt eine
  ausführbare Empfehlung.
- **Verbot – kein Sprung von hier aus.** Diese Datei wechselt **keinen** Reiter, startet **keinen**
  Reparatur-Modus und ruft **nichts** aus dem `composer` auf. Sie liefert `reparaturElementId` als
  **Datenwert**; die Führung ist M7-08 (Shell) bzw. #132/#133 (Reparatur-Führung und Fix-Optionen).
- **Verbot – keine zweite Tabelle.** Kein anderes M7-Issue baut eine eigene Code-nach-Text-Zuordnung.
  Wer in einem anderen Issue einen Fehlercode anzeigen muss, ruft **diese** Funktion.
- **Verbot – kein IPC.** Kein `rufeAuf`, kein `abonniere`, kein Kanalname, kein `window.api`.
- **Verbot – keine Codes erfinden.** Die Tabelle enthält **genau** die Codes aus TK 9.2.3, 9.4.9,
  9.6.4 und die drei generischen aus 9.1.1. Kein weiterer Code wird „vorsorglich" ergänzt; ein Code,
  der im Vertrag nicht steht, gehört in den Zweig „jeder andere Code".
- **Offene Frage (echte Entscheidung nötig): Wo werden die `betroffeneElementIds` ANGEZEIGT?** Der
  Vertrag verlangt, dass `asset_referenziert` „die **betroffenen Listenelemente** nennen" muss
  (TK 9.1.1) – Kennungen allein sind für den Nutzer aber wertlos, er braucht **Namen**. Der
  Auflösungsweg von einer Listenelement-Kennung zu einem lesbaren Namen liegt im `composer` und
  nicht im `queue-panel`. Ob die Warteschlangen-Leiste die Namen selbst zeigt (dann braucht sie
  Zugriff auf den Projektstand) oder nur zur betroffenen Stelle führt, ist **nicht** hier zu
  entscheiden. **Fragen.**
- **Offene Frage (echte Entscheidung nötig): Bekommt der `vorlagen-editor` eine eigene
  Übersetzungstabelle?** `vorlage_referenziert` mit `Vorlagennutzung` (TK 9.12.1) ist ein
  Fehlercode mit echtem Verhalten, erscheint aber **nie** im `queue-panel` (Vorlagen-Operationen
  sind keine Aufträge). Entweder bekommt er eine eigene Stelle im `vorlagen-editor` – dann gibt es
  zwei Tabellen und die Begründung „eine Tabelle" ist aufgeweicht – oder diese Datei wandert später
  in einen geteilten Renderer-Bereich. **Nicht selbst entscheiden und hier NICHT vorgreifen.**
- **Offene Frage (echte Entscheidung nötig): `datei_fehler` meldet einen Zustand, in dem der Nutzer
  nichts tun muss** („wird beim nächsten Öffnen des Projekts nachgeholt", TK 9.4.9 →
  `pendingDeletion`). Ob so etwas überhaupt als **Fehlschlag** in der Warteschlange erscheinen soll
  oder als Hinweis, ist eine Bedienfrage; die Tabelle oben behandelt ihn vorerst wie jeden anderen
  Fehler. **Nicht selbst zu einem Erfolg umdeuten.**

## Definition of Done
- [ ] `BEKANNTE_FEHLERCODES` enthält **genau** die Codes der Tabelle (ohne den Zweig „jeder
      andere"), und ein Test prüft, dass jeder davon einen `titel`, eine `erklaerung` und eine
      **nicht leere** `handlung` ergibt
- [ ] Vollständigkeitstest gegen den Vertrag: Die Liste enthält alle fünf Import-Codes (TK 9.4.9),
