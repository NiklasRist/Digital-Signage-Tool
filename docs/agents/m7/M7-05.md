### Issue M7-05: [app-shell] Leerzustände ohne offenes Projekt

## Ziel (in einem Satz)
Ohne offenes Projekt zeigen **genau zwei** Reiter – Zusammenstellen und Aktionen – einen ruhigen
Hinweis mit dem Weg zum Reiter Projekte, während Projekte **und Vorlagen** unverändert voll
benutzbar bleiben.

## Modul & Datei
- Modul: `app-shell` (Renderer)
- Dateien dieses Issues:
  - `src/renderer/app-shell/leerzustand-regel.ts` – die **reine** Regel (ohne JSX, vollständig ohne
    Browser prüfbar)
  - `src/renderer/app-shell/leerzustand.tsx` – die Anzeige
- **Nicht** erlaubt: `src/renderer/app-shell/rahmen.tsx` (M7-02), `reiter.ts` (M7-01),
  `sichten.ts` (M7-04), `src/renderer/composer/**`, `src/renderer/action-editor/**`,
  `src/renderer/vorlagen-editor/**`, `src/renderer/projekt-verwaltung/**`
- Vertrag: Technisches Konzept **9.14.2** (Quelle der Wahrheit), ergänzend **9.14.3** und
  **9.11.1.1** (Vorlagen sind app-weit)
- Prozess/Speicher: –

## Warum das im Gesamtsystem wichtig ist
Beim allerersten Start – und nach jedem Start, bei dem das zuletzt aktive Projekt nicht mehr da ist
– hat die Anwendung **kein** offenes Projekt. Der Nutzer landet dann im Reiter Projekte (M7-03).
Klickt er von dort aus auf Zusammenstellen oder Aktionen, hätte er ohne dieses Issue eine Oberfläche
vor sich, die auf ein `Project` zugreift, das `null` ist: leere Listen, eine Vorschau ohne Inhalt,
im ungünstigen Fall eine Ausnahme beim Rendern. Das TK schließt genau das aus – die beiden Reiter
sind **leer statt kaputt**.

Die zweite, unauffälligere Hälfte dieses Issues ist die **Ausnahme**: Projekte **und Vorlagen**
bekommen **keinen** Hinweis. Der Reiter Projekte ist die Einstiegsstelle – dort einen Hinweis
„öffne erst ein Projekt" zu zeigen, wäre eine Schleife. Und die Vorlagen-Bibliothek ist **app-weit**
und gehört keinem Projekt: Wer eine Vorlage bauen will, bevor er ein Projekt anlegt, darf das. Ein
Hinweis dort wäre eine Abhängigkeit, die es gar nicht gibt – und er würde einen Nutzer, der genau
das tun will, wieder in die Projektliste schicken, wo er nichts zu suchen hat.

Deshalb ist die Regel **eine reine Funktion in einer eigenen Datei**: Sie ist die Stelle, an der die
Ausnahme steht, sie ist ohne Browser prüfbar, und sie kann nicht versehentlich in einer
JSX-Bedingung „vereinfacht" werden.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/app-shell/leerzustand-regel.ts   (rein, kein JSX, kein React)
import type { ReiterId } from './reiter'

/**
 * Zeigt dieser Reiter ohne offenes Projekt einen Leerzustand-Hinweis?
 * true AUSSCHLIESSLICH für 'zusammenstellen' und 'aktionen', und nur wenn kein Projekt offen ist.
 * 'projekte' und 'vorlagen' liefern IMMER false – auch ohne Projekt (TK 9.14.2).
 */
export function zeigtLeerzustand(reiter: ReiterId, projektOffen: boolean): boolean

/** Die Reiter, die überhaupt je einen Leerzustand zeigen können. Genau zwei. */
export const REITER_MIT_LEERZUSTAND: readonly ReiterId[]
```

```tsx
// src/renderer/app-shell/leerzustand.tsx
import type { JSX } from 'react'
import type { ReiterId } from './reiter'

export interface LeerzustandEigenschaften {
  /** Für welchen Reiter der Hinweis gezeigt wird. Bestimmt nur den Text. */
  reiter: 'zusammenstellen' | 'aktionen'
  /** Der Weg zum Reiter Projekte. Wird vom Aufrufer als wechsleReiter('projekte') gebildet. */
  aufProjekteWechseln: () => void
}

export function Leerzustand(eigenschaften: LeerzustandEigenschaften): JSX.Element
```

**Kein `Ergebnis<T>`, kein `async`, kein IPC.** Diese Dateien rufen keine Store-Operation auf und
laden nichts. Der Hinweis ist eine Anzeige, keine Fachlogik.

## ENTSCHIEDEN (lokale Festlegungen dieses Issues)

1. **Der Typ von `LeerzustandEigenschaften.reiter` ist auf die beiden möglichen Werte verengt** –
   nicht `ReiterId`. *Begründung:* Ein `Leerzustand` für `'vorlagen'` ist per Vertrag ausgeschlossen;
   ihn typmäßig überhaupt darstellbar zu machen, lädt genau den Fehler ein, den TK 9.14.2 als
   „erfundene Abhängigkeit" bezeichnet. Was nicht existieren darf, soll nicht kompilieren.
2. **Der Hinweis führt zum Reiter, nicht zu einer Handlung.** Der Knopf wechselt in den Reiter
   Projekte – er legt **kein** Projekt an und öffnet **keinen** Dialog. *Begründung:* Anlegen,
   Öffnen, Duplizieren und Löschen sind Vorgänge der `projekt-verwaltung` (TK 9.14.3, M7-31); ein
   zweiter Anlege-Weg in der Shell wäre eine zweite Bedienstelle für dieselbe Sache, mit eigener
   Fehlerbehandlung. TK 9.14.2 sagt ausdrücklich „einen Hinweis mit dem Weg zum Reiter Projekte".
3. **Der Hinweis nennt keine Fehlermeldung und keinen Code.** Warum kein Projekt offen ist – nie
   eines gehabt, extern gelöscht, `project.json` defekt –, gehört in die Projektliste (M7-29/M7-30),
   nicht in einen leeren Reiter. *Begründung:* TK 9.14.2 nennt es ausdrücklich „keine
   Fehlermeldung". Ein Fehlertext an dieser Stelle träfe auch den ganz normalen Erststart, bei dem
   nichts schiefgegangen ist.
4. **`zeigtLeerzustand` kennt keinen dritten Zustand.** Kein „lädt gerade", kein „unbekannt". Der
   Ladevorgang beim Start ist Sache von M7-03; solange er läuft, ist einfach noch kein Projekt
   offen. Ein Zwischenzustand hier wäre ein zweites Modell desselben Ablaufs.
5. **Die Anzeige ist ein einzelner, ruhiger Block** – Überschrift, ein Satz, ein Knopf. Kein
   Warnsymbol, keine rote Farbe, kein Rahmen mit Ausrufezeichen. *Begründung:* Es ist kein Fehler,
   sondern ein normaler Anfangszustand. Eine Warnoptik hier gewöhnt den Nutzer daran, Warnungen zu
   übersehen – und dieselbe Optik wird später für echte Speicherfehler gebraucht (M7-07).
6. **Der Text steht als deutsche Zeichenkette direkt in der `.tsx`.** Es gibt in v1 keine
   Übersetzungsschicht; eine hier eingeführte wäre eine Infrastruktur für ein Problem, das das
   Projekt nicht hat. Die **Regel**-Datei bleibt davon unberührt: Sie enthält keinen Anzeigetext und
   ist damit sprachfrei.

## Fremde Signaturen, die du benutzt (abgeschrieben aus der definierenden Quelle)
Der umsetzende Agent sieht die anderen Issues nicht; hier steht alles vollständig.
**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.**

```ts
// M7-01 – src/renderer/app-shell/reiter.ts   (DEFINIERENDE QUELLE)
export type ReiterId = 'zusammenstellen' | 'aktionen' | 'vorlagen' | 'projekte'
export function wechsleReiter(ziel: ReiterId): void
// Von HIER wird wechsleReiter NICHT aufgerufen: Der Aufrufer bildet daraus die Eigenschaft
// `aufProjekteWechseln` und übergibt sie. So bleibt die Anzeige ohne Browser prüfbar.

// M7-04 – src/renderer/app-shell/sichten.ts   (nur zur Einordnung, hier NICHT importiert)
export interface ProjektZugang { hole: () => Projektsicht /* … */ }
// #121: Projektsicht = { projekt: Project | null; ladefehler: … }
// Ob ein Projekt offen ist, ist also `sichten.projekt.hole().projekt !== null`.
// Diese Auswertung macht der AUFRUFER und übergibt das Ergebnis als `projektOffen`.
```

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `reiter` (`zeigtLeerzustand`) | der zu prüfende Reiter | einer der vier `ReiterId`-Werte; keine Laufzeitprüfung nötig |
| `projektOffen` | ist ein Projekt geladen? | `boolean`; der Aufrufer bildet ihn aus der Projekt-Sicht. **Kein** `Project | null` als Parameter: die Anzeige braucht die Projektdaten nicht und soll sie nicht sehen |
| `reiter` (`Leerzustand`) | bestimmt den Text | nur `'zusammenstellen'` oder `'aktionen'` |
| `aufProjekteWechseln` | der Weg zum Reiter Projekte | wird bei Klick **einmal** gerufen; die Komponente wechselt selbst keinen Reiter |

Ausgang bei Erfolg: `zeigtLeerzustand` liefert `true` für die beiden Reiter ohne Projekt und sonst
`false`; `Leerzustand` zeigt Überschrift, Satz und Knopf.
Ausgang bei Fehler: **entfällt** – kein IPC, kein Fehlercode, kein Wurf.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Ohne offenes Projekt sind die Reiter Zusammenstellen/Aktionen leer statt kaputt.** Beim Start
  ohne wiederherstellbares Projekt (9.5.6) landet der Nutzer im Reiter **Projekte**;
  **Zusammenstellen** und **Aktionen** zeigen dort einen Hinweis mit dem Weg zum Reiter Projekte,
  keine Fehlermeldung. **Ausgenommen sind Projekte und Vorlagen:** Beide bleiben ohne offenes
  Projekt **voll benutzbar** – der Reiter Projekte ist die Einstiegsstelle, und die
  Vorlagen-Bibliothek ist **app-weit** (9.11.1.1), gehört also keinem Projekt. Wer eine Vorlage
  bauen will, bevor er ein Projekt anlegt, darf das; ein Hinweis dort wäre eine erfundene
  Abhängigkeit." (TK 9.14.2)
- „**Der Reiter Projekte bleibt ohne offenes Projekt voll benutzbar.** Er ist die Einstiegsstelle
  beim Start ohne wiederherstellbares Projekt (9.14.2, 9.5.6) – als einziger Reiter zeigt er dann
  keinen Hinweis, sondern Inhalt." (TK 9.14.3)
- „**Die Shell rendert selbst keine Inhalte** – sie ordnet an, wechselt und hält die
  Warteschlangen-Leiste." (TK 9.14.2) – der Leerzustand ist die **eine** ausdrücklich vorgesehene
  Ausnahme: Er ist kein fachlicher Inhalt, sondern die Abwesenheit von Inhalt, und TK 9.14.2 weist
  ihn der Shell zu. Er zeigt deshalb **keine** Projektdaten, keine Liste, keine Vorschau.
- „**Ein Reiterwechsel verwirft nie Arbeit.**" (TK 9.14.2) – der Leerzustand ersetzt den
  Reiterinhalt **nur** solange kein Projekt offen ist; sobald eines geladen ist, tritt der echte
  Inhalt an seine Stelle. Er baut nichts ab und räumt nichts auf.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `zeigtLeerzustand('vorlagen', false)` | – | `false` – **immer**, ohne Ausnahme und ohne Sonderfall |
| `zeigtLeerzustand('projekte', false)` | – | `false` – **immer** |
| `zeigtLeerzustand('zusammenstellen', true)` | – | `false` (es ist ein Projekt offen) |
| Der Aufrufer übergibt `aufProjekteWechseln` nicht | – | typmäßig unmöglich (Pflicht-Eigenschaft); es wird **kein** Laufzeit-Rückfall gebaut |
| Klick auf den Knopf, während bereits ein Projekt offen ist | – | kann nicht auftreten, weil die Komponente dann gar nicht angezeigt wird; sie prüft das **nicht** selbst nach (das wäre eine zweite Wahrheit neben `zeigtLeerzustand`) |

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – keinen dritten Reiter ergänzen.** Auch wenn es beim Bauen naheliegt, den Reiter
  Vorlagen „der Vollständigkeit halber" mitzunehmen: TK 9.14.2 nennt ihn ausdrücklich als
  **Ausnahme**, mit Begründung. Wer ihn ergänzt, macht die Vorlagen-Bibliothek von einem Projekt
  abhängig, das sie nicht braucht.
- **Verbot – kein Projekt anlegen, kein Dialog, kein Öffnen.** Der Knopf wechselt den Reiter, mehr
  nicht.
- **Verbot – dieses Issue liest die Projekt-Sicht nicht selbst.** `projektOffen` kommt als
  Parameter. Ein Direktimport von `#121` hier wäre der Bruch von Entscheidung E1 (M7-04) an der
  unauffälligsten Stelle.
- **Verbot – dieses Issue abonniert `queue:geaendert` NICHT.** Der einzige Auswerter terminaler
  Auftrags-Übergänge ist M7-06.
- **Offen: der genaue Wortlaut der beiden Hinweistexte.** Sie sollen den Zweck des Reiters nennen
  und den Weg zeigen; welcher Satz genau, ist eine Produktentscheidung. Schreib einen sachlichen
  Vorschlag und **melde ihn zur Abnahme**, statt ihn als endgültig zu behandeln. Erfinde
  insbesondere **keine** Aussagen darüber, warum kein Projekt offen ist.
