### Issue M7-03: [app-shell] Start-Ablauf: die Sitzung wiederherstellen

## Ziel (in einem Satz)
Beim Start liest die Anwendung die Konfiguration, öffnet das zuletzt aktive Projekt und landet im
richtigen Reiter – und wenn dieses Projekt fehlt oder beschädigt ist, fällt sie **sanft** auf den
Reiter Projekte zurück, mit einer benannten Ursache und ohne Absturz.

## Modul & Datei
- Modul: `app-shell` (Renderer)
- Datei: `src/renderer/app-shell/start.ts` – **die einzige** Datei dieses Issues
- **Nicht** erlaubt: `src/renderer/app-shell/reiter.ts` (M7-01), `rahmen.tsx` (M7-02),
  `sichten.ts` (M7-04), `src/renderer/App.tsx` (M7-02/M7-65), `src/main/**` (anderer Prozess),
  `src/renderer/projekt-verwaltung/**` (M7-29 bis M7-33)
- Vertrag: Technisches Konzept **9.5.6** (Sitzungswiederherstellung) und **9.14.2/9.14.3**
  (wo der Nutzer landet) – Quelle der Wahrheit
- Prozess/Speicher: liest D3 (`config-store`) und löst das Öffnen von D1 aus

## Warum das im Gesamtsystem wichtig ist
Das ist der erste Ablauf, den die Anwendung nach dem Laden des Fensters ausführt – und er ist die
Hälfte von **Akzeptanzkriterium 6**: „Änderungen gehen nicht verloren: die Anwendung speichert
fortlaufend automatisch und stellt beim Start das zuletzt aktive Projekt wieder her (FA-15,
NFA-02)." (Anforderungsdokument, Akzeptanzkriterien)

Er ist zugleich die Stelle mit dem höchsten Risiko für einen **Start, der nicht startet**. Die
Anwendung ist portabel; ihr Datenort kann auf einem USB-Datenträger liegen, der Projektordner kann
extern gelöscht, umbenannt oder halb kopiert worden sein, und `project.json` kann samt `.bak` defekt
sein. In all diesen Fällen liefert der Main einen **Fehler**, keinen Absturz – aber wenn dieser
Ablauf den Fehler nicht abfängt, steht der Nutzer vor einem weißen Fenster und hat keinen Weg zu
seinen anderen, völlig heilen Projekten. Genau davor schützt der sanfte Rückfall.

Die zweite Fehlentscheidung, die hier teuer wäre: aus dem Fehlschlag **Aufräumarbeiten** abzuleiten
– das aktive Projekt in der Konfiguration löschen, den Ordner anfassen, ein Ersatzprojekt anlegen.
Ein einmalig nicht erreichbarer Datenträger würde damit dauerhaft zum Verlust der zuletzt
benutzten Sitzung.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/app-shell/start.ts
import type { Project } from '../../shared/contracts/project'
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import { KANAELE } from '../../shared/contracts/kanaele'
import { rufeAuf } from '../ipc-client/rufe-auf'
import {
  type ReiterId,
  istGueltigerReiter,
  wechsleReiter,
  aufReiterGeaendert,
  START_REITER_OHNE_PROJEKT,
  REITER_NACH_PROJEKT_OEFFNEN,
} from './reiter'

/** Der Schlüssel, unter dem der zuletzt aktive Reiter in AppKonfig.uiVoreinstellungen liegt. */
export const UI_SCHLUESSEL_REITER = 'app-shell.aktiverReiter'

/** Der Schlüssel, unter dem der Klappzustand der Warteschlangen-Leiste liegt. */
export const UI_SCHLUESSEL_QUEUE_AUFGEKLAPPT = 'queue-panel.aufgeklappt'

/** Warum kein Projekt wiederhergestellt wurde. Wird der Oberfläche gezeigt, nicht verschluckt. */
export type StartHinweis =
  | { art: 'kein_aktives_projekt' }                              // Erststart oder nie eines geöffnet
  | { art: 'konfig_unlesbar';  code: string; meldung: string }   // leseKonfig hat abgelehnt
  | { art: 'projekt_unlesbar'; projektId: string; code: string; meldung: string }

export type StartErgebnis =
  | { art: 'projekt-geladen'; projekt: Project; reiter: ReiterId }
  | { art: 'kein-projekt';    reiter: 'projekte'; hinweis: StartHinweis }

/**
 * Führt den Start-Ablauf EINMAL aus und setzt dabei den aktiven Reiter (über wechsleReiter).
 * Wirft NIE. Jeder Fehler wird zu `kein-projekt` mit benanntem Hinweis.
 */
export async function starteSitzung(): Promise<StartErgebnis>

/**
 * Merkt den aktiven Reiter über den Neustart hinweg: abonniert Reiterwechsel und schreibt den
 * neuen Wert als UI-Voreinstellung. Rückgabewert ist die Abmelde-Funktion.
 * DIESE Datei ist die EINZIGE Stelle der Shell, die eine UI-Voreinstellung schreibt.
 */
export function merkeAktivenReiter(): () => void

/**
 * Liest den gemerkten Klappzustand der Warteschlangen-Leiste. Wirft NIE.
 * Fehlt der Wert, ist er kein `boolean` oder scheitert das Lesen, lautet die Antwort `false`
 * (eingeklappt) – s. ENTSCHIEDEN 7.
 */
export async function leseQueueAufgeklappt(): Promise<boolean>

/**
 * Merkt den Klappzustand über den Neustart hinweg. Wirft NIE und liefert nichts zurück:
 * Ein gescheitertes Schreiben kostet eine Bequemlichkeit, keine Arbeit – das Ergebnis wird
 * trotzdem ausgewertet und intern vermerkt (kein unbehandeltes Promise).
 */
export function merkeQueueAufgeklappt(aufgeklappt: boolean): void
```

**Kein `throw` nach außen.** `starteSitzung` liefert immer ein `StartErgebnis`; sie trägt selbst
**keine** `Ergebnis<T>`-Hülle, weil „kein Projekt" hier **kein Fehler** ist, sondern ein normaler,
vorgesehener Ausgang (Erststart). Der Fehlergrund reist im `hinweis`.

## Der Ablauf (verbindlich – die Reihenfolge ist Vertrag, nicht Geschmack)

`starteSitzung` führt genau diese Schritte aus:

1. **`rufeAuf<AppKonfig>(KANAELE.config.leseKonfig)`** – ohne Nutzlast.
   - `ok: false` → `{ art: 'kein-projekt', reiter: 'projekte', hinweis: { art: 'konfig_unlesbar',
     code, meldung } }`, `wechsleReiter('projekte')`. **Ende.** Ohne Konfiguration gibt es keinen
     zu öffnenden Kandidaten; ein geratener wäre schlimmer als keiner.
2. **`konfig.aktivesProjektId === null`** → `{ art: 'kein-projekt', reiter: 'projekte',
   hinweis: { art: 'kein_aktives_projekt' } }`, `wechsleReiter('projekte')`. **Ende.** Das ist der
   Erststart und ausdrücklich **kein** Fehlerfall – der Hinweis trägt deshalb keinen Code.
3. **`rufeAuf<Project>(KANAELE.project.öffneProjekt, { id: konfig.aktivesProjektId })`.**
   Hinter diesem Kanal liegt der vollständige Öffnen-Ablauf aus #94 (Projekt laden →
   Wiederholungsspeicher laden → Aufräumen). Er wird **abgewartet**; erst danach darf die Oberfläche
   Medien zeigen.
   - `ok: false` → `{ art: 'kein-projekt', reiter: 'projekte', hinweis: { art: 'projekt_unlesbar',
     projektId, code, meldung } }`, `wechsleReiter('projekte')`. **Ende.** Der Code wird
     **unverändert** durchgereicht – nicht in einen eigenen umgeschrieben.
4. **Reiter bestimmen** (nur im Erfolgsfall):
   - `konfig.uiVoreinstellungen[UI_SCHLUESSEL_REITER]` durch `istGueltigerReiter` prüfen.
   - Ist er gültig **und nicht** `'projekte'` → dieser Reiter.
   - Sonst → `REITER_NACH_PROJEKT_OEFFNEN` (`'zusammenstellen'`).
   - `wechsleReiter(<Ergebnis>)`, dann `{ art: 'projekt-geladen', projekt, reiter }`.

**Warum ein gemerktes `'projekte'` übergangen wird:** Der Reiter Projekte ist die Einstiegsstelle,
wenn **kein** Projekt geladen ist. Wurde eines geladen, ist die Projektliste der falsche Ort – der
Nutzer soll dort weiterarbeiten, wo er aufgehört hat, und TK 9.14.3 sagt für den Öffnen-Weg
ausdrücklich `Zusammenstellen`. Ein gemerktes `'projekte'` entsteht ohnehin meist gerade **deshalb**,
weil beim letzten Start kein Projekt geladen war.

**Warum die Reihenfolge „Reiter erst nach dem Laden":** Würde der gemerkte Reiter **vor** Schritt 3
gesetzt, stünde der Nutzer im Reiter Zusammenstellen, während das Projekt noch lädt – und bei einem
Fehlschlag bliebe er dort, in einem Reiter, der ohne Projekt nur einen Hinweis zeigen kann.

`merkeAktivenReiter()` meldet sich über `aufReiterGeaendert` an und ruft bei jedem Wechsel
`rufeAuf<void>(KANAELE.config.setzeUIVoreinstellung, { schlüssel: UI_SCHLUESSEL_REITER, wert: aktiv })`.
Der Rückgabewert wird **nicht** dem Nutzer gezeigt: Scheitert das Schreiben, geht nur eine
Bequemlichkeit verloren, keine Arbeit. Das Ergebnis wird trotzdem **ausgewertet und intern
vermerkt** – ein `void`-Ausdruck ohne `catch` auf ein Promise ist verboten (dieselbe Regel wie in
#61 für das Journal).

`leseQueueAufgeklappt()` ruft `rufeAuf<AppKonfig>(KANAELE.config.leseKonfig)` und liest daraus
`konfig.uiVoreinstellungen[UI_SCHLUESSEL_QUEUE_AUFGEKLAPPT]`. Ist der Wert **nicht** genau `true`
oder `false` (fehlend, `undefined`, `'true'`, `1`, `null`), lautet die Antwort `false`. Bei
`ok: false` ebenfalls `false`, **ohne** Hinweis und **ohne** Wurf.

`merkeQueueAufgeklappt(aufgeklappt)` ruft
`rufeAuf<void>(KANAELE.config.setzeUIVoreinstellung, { schlüssel: UI_SCHLUESSEL_QUEUE_AUFGEKLAPPT, wert: aufgeklappt })`
– dieselbe Behandlung des Ergebnisses wie bei `merkeAktivenReiter`. `false` ist dabei ein
**gültiger** Wert und wird vom Gateway ausdrücklich nicht als „fehlt" behandelt (#77).

## ENTSCHIEDEN (lokale Festlegungen dieses Issues)

1. **Bei einem Fehlschlag wird die Konfiguration NICHT geändert.** Kein `setzeAktivesProjekt`, kein
   Zurücksetzen, kein Aufräumen. *Begründung:* Ein nicht erreichbarer Datenträger, ein noch nicht
   eingehängtes Netzlaufwerk oder eine gerade laufende Sicherung sind vorübergehende Zustände; wer
   die Kennung löscht, macht daraus einen dauerhaften Verlust. Hinzu kommt: `setzeAktivesProjekt`
   nimmt laut #27 einen `string` – es gibt gar keinen Weg, „kein Projekt" zu schreiben. Ein „Trick"
   mit leerer Zeichenkette wäre eine erfundene Vertragsergänzung.
2. **`starteSitzung` wird genau einmal je Fenster gerufen.** Diese Datei sorgt **nicht** selbst
   dafür (kein Modul-Merker, kein „schon gelaufen"-Flag) – sie ist eine gewöhnliche Funktion, und
   der Aufrufer ruft sie einmal beim Aufbau. *Begründung:* Ein eingebauter Einmal-Schutz wäre in
   Tests im Weg und würde eine Wiederholung nach einem behobenen Fehler verhindern. Ein zweiter
   Aufruf ist **unschädlich**: Er liest erneut und öffnet erneut.
3. **Es gibt keinen automatischen Wiederholversuch und keinen Timer.** Scheitert das Öffnen, endet
   der Ablauf. Der Nutzer landet im Reiter Projekte, sieht den Hinweis in der Meldungsfläche
   (ENTSCHIEDEN 4) und entscheidet selbst.
4. **Der Hinweis wird zurückgegeben, nicht angezeigt – und sein Anzeigeplatz ist entschieden.**
   Diese Datei enthält **kein JSX** und formuliert **keinen** Anzeigetext. Sie liefert `art`, `code`
   und die `meldung` des Main; damit ist sie sprachfrei und vollständig ohne Browser prüfbar.
   **Gezeigt wird der Hinweis in der anwendungsweiten `meldungsFlaeche` des Rahmens** (M7-02,
   unmittelbar unter der Reiterleiste), belegt von M7-65 aus dem `startHinweis` der `BootstrapLage`
   – **nicht** von der Projektverwaltung. *(Eine frühere Fassung wies die Anzeige M7-29/M7-30 zu;
   `ProjektVerwaltungWurzelProps` (M7-59) trägt dafür aber **kein** Feld, und M7-51 reicht keins
   durch. Der Auftraggeber hat die Naht entschieden: Der Hinweis ist reiterunabhängig – er entsteht,
   bevor überhaupt ein Reiter belegt ist – und gehört deshalb in den Rahmen.)* **Ergänze M7-59
   nicht** und formuliere hier weiterhin keinen Satz.
5. **Der Schlüssel der UI-Voreinstellung ist `'app-shell.aktiverReiter'`** und steht als exportierte
   Konstante genau hier. *Begründung:* `uiVoreinstellungen` ist ein `Record<string, unknown>` – ein
   frei gewählter Schlüssel an zwei Stellen wäre ein stiller Fehlschlag, denn ein Tippfehler liefert
   `undefined` und `istGueltigerReiter` macht daraus klaglos den Standardwert. Das Präfix `app-shell.`
   hält den gemeinsamen Namensraum sauber für die übrigen Module.
6. **Ein ungültiger gemerkter Wert wird stillschweigend verworfen, nicht gemeldet.** Er kann nur aus
   einer älteren Fassung oder einer von Hand bearbeiteten `config.json` stammen; ein Fehlerhinweis
   dafür hätte für den Nutzer keinen Handlungswert. Das gilt für **beide** Schlüssel dieses Issues
   und betrifft eine Bequemlichkeit, keine Daten.
7. **Der Klappzustand der Warteschlangen-Leiste wird HIER gemerkt, unter
   `'queue-panel.aufgeklappt'` – Vorbelegung `false`.** *Warum hier:* Diese Datei erklärt sich zur
   **einzigen** Stelle der Shell, die eine UI-Voreinstellung schreibt (s. Signaturblock). M7-13
   verlangt zugleich, dass die eingeklappte Zeile den Klappzustand **nicht** selbst hält, und
   begründet das damit, dass er sich über die Sitzung merkt. Ohne diesen zweiten Schlüssel hätte
   diese Zusage **keinen Besitzer**: M7-13 darf nicht schreiben, und jede andere Stelle, die es
   täte, bräche die Alleinstellung. `uiVoreinstellungen` ist ein `Record<string, unknown>` – ein an
   zwei Stellen frei getippter Schlüssel wäre ein stiller Fehlschlag, deshalb steht auch dieser als
   exportierte Konstante genau hier. Das Präfix `queue-panel.` benennt das besitzende **Modul**,
   nicht die schreibende Datei; so bleibt der gemeinsame Namensraum lesbar. *Warum die Vorbelegung
   `false` ist:* Die Grundstruktur in TK 9.14.1 führt die Zeile
   `queue-panel als schmale Leiste: „Render läuft · 3 von 7"  ▸ aufklappbar` – **schmal** ist der
   Ausgangszustand, das Aufklappen die Handlung. Eine beim ersten Start aufgeklappte Leiste nähme
   Fläche weg, die niemand angefordert hat.
8. **`leseQueueAufgeklappt` liest die Konfiguration ein ZWEITES Mal, statt den Wert an
   `StartErgebnis` anzuhängen.** *Begründung:* `StartErgebnis` wird von M7-04, M7-05 und M7-51
   **wörtlich** abgeschrieben; ein zusätzliches Feld dort wäre eine Vertragsänderung an vier
   Stellen für eine Bequemlichkeit. `config:leseKonfig` liest eine kleine JSON-Datei und läuft beim
   Start genau **einmal** zusätzlich. Die beiden Lesevorgänge können nicht auseinanderlaufen: Es
   wird zwischen ihnen nichts geschrieben, und ein abweichender Wert hätte ohnehin nur die Wirkung,
   dass die Leiste anders geklappt startet.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – (`starteSitzung` hat kein Argument) | die gesamte Eingabe kommt aus D3 | `aktivesProjektId` wird **nicht** vorgeprüft (kein Format-Test auf UUID): die Prüfung leistet der Main (TK 9.1.1 Punkt 6), eine zweite hier wäre eine zweite Wahrheit |
| `konfig.uiVoreinstellungen[UI_SCHLUESSEL_REITER]` | zuletzt aktiver Reiter | `unknown`; nur über `istGueltigerReiter` verwendbar; ungültig → Standardwert, ohne Meldung |

Ausgang bei Erfolg: `{ art: 'projekt-geladen', projekt, reiter }` – das vollständige, aufgeräumte
`Project` und der gesetzte Reiter.
Ausgang bei Fehler: `{ art: 'kein-projekt', reiter: 'projekte', hinweis }` – **immer** mit gesetztem
Reiter `'projekte'` und benanntem Grund. **Nie** ein Wurf, **nie** `null`.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Sitzungswiederherstellung (FA-15):** beim Start das zuletzt aktive Projekt laden; **fehlt** es
  (extern gelöscht) → sanfter Rückfall auf „kein aktives Projekt / Projektliste", **kein** Absturz."
  (TK 9.5.6)
- „**Ohne offenes Projekt sind die Reiter Zusammenstellen/Aktionen leer statt kaputt.** Beim Start
  ohne wiederherstellbares Projekt (9.5.6) landet der Nutzer im Reiter **Projekte**;
  **Zusammenstellen** und **Aktionen** zeigen dort einen Hinweis mit dem Weg zum Reiter Projekte,
  keine Fehlermeldung." (TK 9.14.2)
- „**Der Reiter Projekte bleibt ohne offenes Projekt voll benutzbar.** Er ist die Einstiegsstelle
  beim Start ohne wiederherstellbares Projekt (9.14.2, 9.5.6) – als einziger Reiter zeigt er dann
  keinen Hinweis, sondern Inhalt." (TK 9.14.3)
- „**Beim Öffnen eines Projekts wechselt die Shell in den Reiter Zusammenstellen** – der Nutzer
  landet dort, wo er weiterarbeitet, statt in der Liste stehen zu bleiben." (TK 9.14.3)
- „**7. Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code. Es gibt keine
  Operation, die „einfach nichts" zurückgibt und auf Gelingen hofft." (TK 9.1.1) – deshalb trägt
  **jeder** Rückfall einen benannten `hinweis`, nie ein blankes „ging nicht".
- „Beim Start öffnet die App automatisch das **zuletzt aktive Projekt** und stellt letztes
  Export-Ziel und UI-Voreinstellungen wieder her." (Anforderungsdokument, FA-15) – das Export-Ziel
  wird **nicht** hier wiederhergestellt (es liegt in `AppKonfig` und wird beim Export gelesen,
  #183); dieses Issue stellt die UI-Voreinstellung „aktiver Reiter" wieder her.
- „Änderungen gehen nicht verloren: die Anwendung speichert fortlaufend automatisch und stellt beim
  Start das zuletzt aktive Projekt wieder her (FA-15, NFA-02)." (Anforderungsdokument,
  Akzeptanzkriterium 6)
