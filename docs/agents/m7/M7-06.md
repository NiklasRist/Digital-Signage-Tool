### Issue M7-06: [app-shell] Der einzige Auswerter der Warteschlangen-Ereignisse

## Ziel (in einem Satz)
Genau **eine** Stelle im ganzen Renderer zieht aus einem beendeten Auftrag die fachlichen Folgen –
den importierten Asset in die Projekt-Sicht, den Motiv-Bestand leeren und neu bereitstellen, die
Undo-Historie leeren –, und alle anderen Stellen dürfen das ausdrücklich **nicht**.

## Modul & Datei
- Modul: `app-shell` (Renderer)
- Datei: `src/renderer/app-shell/auftrags-nachlauf.ts` – **die einzige** Datei dieses Issues
- **Nicht** erlaubt: `src/renderer/app-shell/sichten.ts` (M7-04), `rahmen.tsx` (M7-02),
  `src/renderer/queue-panel/**` (M7-12 bis M7-18 – die **Anzeige** der Warteschlange),
  `src/renderer/composer/**`, `src/main/**`
- Vertrag: Technisches Konzept **9.3.1/9.3.3** (Auftrags-Zustand und Übergänge), **9.3.4**
  (Ereignis `queue:geaendert`), **9.13.3** (Undo-Historie leeren), **9.1.1 Punkt 1 und 5**
  (Auftrags-Ergebnis reist über den Auftrags-Zustand) – Quelle der Wahrheit
- Prozess/Speicher: P6 (Auftragsverwaltung) → Renderer; wirkt auf die Projekt-Sicht und den
  Motiv-Bestand

## Warum das im Gesamtsystem wichtig ist
Auftragsartige Operationen – Import, Löschen, Render, Export – antworten sofort mit `{ auftragId }`
und sagen **nichts** über ihren Ausgang. Der Ausgang reist ausschließlich über den Auftrags-Zustand
und wird per `queue:geaendert` an das eine Fenster geschickt. Wer daraus keine Folgen zieht, hat
eine Anwendung, in der ein Import minutenlang läuft und danach **nichts** passiert: Der Asset ist in
D1, aber die Oberfläche kennt ihn nicht, bis der Nutzer das Projekt neu öffnet.

**Warum es genau EINEN Auswerter geben muss – ausgeschrieben.** Drei Wirkungen hängen an demselben
Ereignis: der neue Asset in die Sicht, der Motiv-Bestand leeren und neu bereitstellen, die
Undo-Historie leeren. Läge jede dieser Wirkungen in dem Issue, das sie braucht, gäbe es drei
Abonnenten auf demselben Kanal, und ihre Reihenfolge wäre nicht festgelegt:

- Leert Abonnent A den Motiv-Bestand, **bevor** Abonnent B den neuen Asset einträgt, ist alles gut.
  Läuft es umgekehrt, zeigt ein **unter gleichem Namen** neu importiertes Bild weiterhin das
  **alte** Motiv – der Bestand ist nach dem Schlüssel abgelegt, nicht nach dem Dateiinhalt. Der
  Nutzer sieht in Vorschau und Segment das falsche Bild und hat keinen Anhaltspunkt, warum.
- Leert **jeder** der drei Abonnenten die Undo-Historie, ist sie zwar leer – aber es wird
  unauffindbar, welcher der Auslöser war, sobald sie einmal zu früh leer ist.

Deshalb: **eine** Datei, **eine** feste Reihenfolge, und für alle anderen M7-Issues ein
ausdrückliches Verbot.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/app-shell/auftrags-nachlauf.ts
import type { Auftrag } from '../../shared/contracts/auftrag'
import type { Asset } from '../../shared/contracts/asset'
import type { Project } from '../../shared/contracts/project'
import type { Zeichenvoraussetzungen } from '../composer/zeichen-vorbereitung'
import type { Ergebnis } from '../../shared/contracts/ergebnis'

/** Alles, worauf der Nachlauf wirkt. Wird als Parameter übergeben (Entscheidung E1, M7-04) –
 *  diese Datei importiert KEINE Sicht und KEINEN Undo-Stapel direkt. */
export interface NachlaufWirkungen {
  /** Das aktuell geladene Projekt; null, wenn keins offen ist. Aus M7-04: projekt.hole().projekt */
  holeProjekt: () => Project | null
  /** Ersetzt das Projekt in der gemeinsamen Sicht (#121, über M7-04). */
  setzeProjekt: (projekt: Project) => void
  /** Verwirft den Motiv-Bestand und den gemerkten Stand (#154, über M7-04). */
  verwirfMotivBestand: () => void
  /** Stellt die Zeichenvoraussetzungen erneut her (#154, über M7-04). */
  bereiteZeichnenVor: (projekt: Project) => Promise<Ergebnis<Zeichenvoraussetzungen, string>>
  /** Leert die Undo-Historie der Projekt-Bearbeitung (TK 9.13.3). Kommt aus M7-41. */
  leereProjektHistorie: () => void
  /** Optional: die Ausgabe-Liste neu laden (M7-37). Fehlt sie, geschieht nichts. */
  aktualisiereAusgabenListe?: () => void
  /** Optional: meldet der Reparatur-Führung die Kennung eines ERFOLGREICH importierten Assets
   *  (M7-64 `schliesseMedienImportAb`, über M7-69). NUR bei art 'import' und status 'erfolg'.
   *  Fehlt sie, geschieht nichts. Diese Datei weiß NICHT, ob eine Reparatur läuft – das
   *  entscheidet der Empfänger (s. ENTSCHIEDEN 11). */
  meldeImportErgebnis?: (assetId: string) => void
  /** Meldeweg für Fehler, die beim Nachlauf selbst auftreten (z. B. Vorbereiten schlägt fehl).
   *  Diese Datei zeigt NICHTS selbst an. Wo die Meldung LANDET, ist entschieden: in der
   *  anwendungsweiten `meldungsFlaeche` des Rahmens (M7-02), gehalten von M7-69 (`App.tsx`). */
  meldeFehler: (code: string, meldung: string) => void
}

/**
 * Startet den Nachlauf: abonniert die Warteschlange und wertet TERMINALE Übergänge aus.
 * `abonniereQueue` bildet der Aufrufer aus `abonniere` (#151) – diese Datei kennt keinen
 * Kanalnamen und importiert die Kanal-Registry nicht.
 * Rückgabewert ist die Abmelde-Funktion; sie beendet das Abo und vergisst die gemerkten Kennungen.
 */
export function starteAuftragsNachlauf(
  abonniereQueue: (hoerer: (auftraege: Auftrag[]) => void) => () => void,
  wirkungen: NachlaufWirkungen,
): () => void

/** Die drei terminalen Zustände (TK 9.3.3). Exportiert, damit Tests sie nicht nachbauen müssen. */
export const TERMINALE_ZUSTAENDE: readonly ['erfolg', 'fehlgeschlagen', 'abgebrochen']

/** Die beiden Auftragsarten, die D1 verändern (TK 9.13.3). */
export const D1_AENDERNDE_ARTEN: readonly ['import', 'loeschen']
```

**Kein `Ergebnis<T>` als Rückgabe, kein `throw`.** Diese Datei ist ein Ereignis-Auswerter; sie hat
keinen Aufrufer, dem sie einen Fehlercode antworten könnte. Fehler, die **bei ihr** entstehen, gehen
über `meldeFehler`.

## Der Ablauf (verbindlich – die Reihenfolge ist Vertrag, nicht Geschmack)

Bei jeder eintreffenden Liste `Auftrag[]`:

1. **Neu terminal gewordene Aufträge bestimmen.** Ein Auftrag zählt, wenn sein `status` in
   `TERMINALE_ZUSTAENDE` liegt **und** seine `auftragId` noch nicht als terminal vermerkt ist. Die
   Kennung wird sofort vermerkt. Die Verarbeitung erfolgt in der Reihenfolge, in der die Aufträge
   in der eingetroffenen Liste stehen.
   *Warum das Vermerken zwingend ist:* `queue:geaendert` liefert jedes Mal den **vollständigen**
   Stand, und Fehlschläge liegen persistent in Q2 (TK 9.3.5) – ein und derselbe fehlgeschlagene
   Render vom Vortag steht also in **jedem** Ereignis erneut. Ohne Merkliste würde bei jedem
   beliebigen Warteschlangen-Ereignis die Undo-Historie geleert und der Motiv-Bestand verworfen.
2. **Je neu terminalem Auftrag, in dieser Reihenfolge:**
   1. **`art` ist `'import'` oder `'loeschen'` (gleich welcher terminale Zustand)** →
      `wirkungen.leereProjektHistorie()`.
   2. **`art === 'import'` und `status === 'erfolg'`** → `auftrag.ergebnis` ist der fertige `Asset`
      (TK 9.3.1). Das Projekt aus `holeProjekt()` holen; ist es `null`, geschieht nichts weiter
      (kein Projekt offen). Sonst ein **neues** `Project` bilden, in dem `assets` den Asset enthält:
      vorhandener Eintrag mit derselben `id` wird **ersetzt**, sonst **angehängt**. `setzeProjekt`
      damit rufen. Die übrigen Felder (`aktionen`, `liste`, `letzterAusgabeName`) bleiben
      **unverändert**.
   3. **`art === 'loeschen'` und `status === 'erfolg'`** → `auftrag.ergebnis` ist `{ assetId }`
      (TK 9.3.1). Das Asset mit dieser `id` aus `assets` **entfernen** und `setzeProjekt` rufen. Die
      Liste wird **nicht** angefasst – ein Medium blockiert, es kaskadiert nicht (TK 9.5.3); ein
      erfolgreiches Löschen bedeutet also, dass es keine Referenzen gab.
   4. **`art === 'import'` oder `'loeschen'`, `status === 'erfolg'`** → danach
      `wirkungen.verwirfMotivBestand()` und anschließend
      `await wirkungen.bereiteZeichnenVor(<das eben gesetzte Projekt>)`. Bei `ok: false` den Code
      über `meldeFehler` melden; **nicht** erneut versuchen, **keinen** Timer setzen.
   5. **`art === 'render'` oder `'export'`, `status === 'erfolg'`** →
      `wirkungen.aktualisiereAusgabenListe?.()`. Sonst nichts.
   6. **`art === 'import'` und `status === 'erfolg'`** → **zuletzt**, nach Schritt 2.4:
      `wirkungen.meldeImportErgebnis?.(<die `id` des Assets aus `ergebnis`>)`.
      *Warum ganz am Ende:* Der Empfänger setzt daraufhin einen Listenelement-Verweis auf **genau
      dieses** Asset um (M7-64). Wäre die Sicht dabei noch nicht geschrieben oder der Motiv-Bestand
      noch nicht neu bereitgestellt, zeigte das reparierte Element auf ein Asset, das die Oberfläche
      noch nicht kennt – die Stelle bliebe kaputt und die Reparatur endete mit einem neuen Fehler
      statt mit einem Erfolg.
      *Auch dann, wenn `bereiteZeichnenVor` fehlgeschlagen ist:* Der Asset ist in D1 **und** in der
      Sicht; ein fehlendes Motiv ist ein eigener, gemeldeter Zustand und kein Grund, die Reparatur
      hängen zu lassen.
      Ist `holeProjekt()` `null` (kein Projekt offen), unterbleibt die Meldung – dann gibt es auch
      kein Listenelement, das umgesetzt werden könnte.
3. **Fehlgeschlagene und abgebrochene Aufträge lösen ausschließlich Schritt 2.1 aus.** Sie ändern
   die Projekt-Sicht **nicht** und stellen die Zeichenvoraussetzungen **nicht** neu her. Die
   **Anzeige** des Fehlschlags ist Sache des `queue-panel` (M7-12 ff.), nicht dieser Datei.

## ENTSCHIEDEN (lokale Festlegungen dieses Issues)

1. **Die Undo-Historie wird bei JEDEM terminalen Zustand eines `import`/`loeschen`-Auftrags
   geleert – nicht nur bei Erfolg.** *Begründung:* Der Lösch-Ablauf ist ausdrücklich „D1 zuerst,
   Datei danach" (TK 9.4.6). Ein Löschauftrag, der **nach** dem D1-Schritt scheitert, hat den
   Datenbestand bereits verändert; ein danach gedrücktes Undo würde einen Schnappschuss von **vor**
   dieser Änderung zurückschreiben. TK 9.13.3 begründet die Regel genau damit, dass ein alter
   Schnappschuss eine Auftragswirkung rückgängig machen würde. Beim Erfolg zu leeren und beim
   Fehlschlag nicht, wäre die riskantere Hälfte offen gelassen – und das Leeren kostet nichts:
   „Da Aufträge seriell und vergleichsweise selten sind (9.3), ist das Leeren der Historie ein
   billiger Preis für Korrektheit." (TK 9.13.3)
2. **Der gelöschte Asset wird aus der Sicht entfernt, obwohl das Briefing nur den Import nennt.**
   *Begründung:* Es gibt genau **einen** Auswerter. Bliebe das Entfernen ungeregelt, müsste der
   Löschknopf (M7-36) selbst auf die Warteschlange hören – und damit gäbe es doch zwei Auswerter.
   Ohne die Entfernung zeigte die Medien-Bibliothek ein Medium, dessen Datei nicht mehr existiert;
   ein Zug daraus in die Liste erzeugte sofort eine kaputte Stelle.
3. **Nur `erfolg` verändert die Projekt-Sicht.** Ein Fehlschlag hat laut TK 9.4.5 nichts in D1
   hinterlassen (der Import ist atomar); ein Abbruch ebenso. Aus einem Nicht-Ereignis eine
   Sichtänderung abzuleiten, wäre die Umkehrung der Regel „nie eine Erfolgsmeldung aus dem
   Ausbleiben einer Fehlermeldung ableiten".
4. **Die Merkliste der terminalen Kennungen wächst unbegrenzt und wird nicht gekappt.**
   *Begründung:* Es sind Zeichenketten, ein Arbeitstag bringt Dutzende, nicht Millionen. Eine
   Kappung nach Anzahl oder Alter hätte genau eine Wirkung: Ein alter Fehlschlag aus Q2 fiele
   irgendwann aus der Liste und würde beim nächsten beliebigen Warteschlangen-Ereignis erneut als
   „neu terminal" gewertet – und leerte die Undo-Historie mitten in der Arbeit.
5. **Diese Datei kennt keinen Kanalnamen.** Das Abo kommt als Parameter. *Begründung:* Dieselbe
   Bauweise, die #126 für den Speicherstatus festlegt („Die Abo-Funktion wird ÜBERGEBEN – der
   Aufrufer bildet sie aus `abonniere` (#151); diese Datei kennt keinen Kanalnamen"). Sie macht die
   Datei ohne IPC-Doppel testbar.
6. **Es wird nichts nachgeladen.** Kein `project:öffneProjekt`, kein `listeProjekte`, kein
   `holeStand`. Der Nachlauf arbeitet ausschließlich mit dem, was im Ereignis steht, und mit den
   übergebenen Wirkungen. *Begründung:* Ein Nachladen wäre ein zweiter Weg an dieselben Daten und
   könnte einen **älteren** Stand über einen neueren schreiben – genau die Reihenfolge-Falle, die
   TK 9.1.1 Punkt 10 für „erst holen, dann abonnieren" beschreibt.
7. **`auftrag.ergebnis` wird eingegrenzt, nicht geglaubt.** Der Typ ist `unknown | null` (#16). Vor
   der Verwendung wird geprüft, dass es ein Objekt mit den erwarteten Feldern ist (`id`, `typ`,
   `dateiname` beim Import; `assetId` beim Löschen). Passt es nicht, wird der Auftrag übersprungen
   und über `meldeFehler` gemeldet – **nicht** stillschweigend ignoriert und **nicht** mit einem
   Ersatzwert gefüllt.
8. **Der Code für ein unbrauchbares `auftrag.ergebnis` ist `'unbekannter_fehler'` – es wird KEIN
   neuer Bezeichner erfunden.** Eine frühere Fassung dieses Issues nannte dafür
   `'auftragsergebnis_unbrauchbar'` und stellte zugleich die Frage, ob es diesen Code geben darf;
   beides zusammen ist unzulässig, und die Antwort lautet **nein**. *Begründung:* „**3. Fehlercodes
   sind ein geschlossener, typisierter Satz:** die fachlichen je Operation (9.4.9, 9.6.4, 9.12.1)
   plus die generischen `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`. **Eine rohe
   Exception-Meldung wird nie zum Code.**" (TK 9.1.1) Ein hier gebildeter Bezeichner stünde in
   keiner Vertragstabelle und wäre der Anfang eines zweiten, ungeführten Code-Satzes. Dass die Frage
   **hier** entschieden werden darf und nicht dem Auftraggeber vorgelegt werden muss, liegt an der
   Reichweite: `meldeFehler` ist ein Rückruf des Aufrufers **innerhalb** des Renderer-Prozesses –
   der Code überquert **keine** Prozessgrenze, wird in keiner Nutzlast gesendet, in kein Q3
   geschrieben und von keinem Main-Modul verglichen. Was dem Nutzer die Ursache nennt, ist die
   **Meldung**; sie trägt Auftragsart, `auftragId` und das fehlende Feld im Klartext.
9. **Gestartet und beendet wird der Nachlauf vom Renderer-Bootstrap M7-65** (`src/renderer/app-shell/bootstrap.ts`),
   **genau einmal** je Fenster, mit Aufruf der zurückgegebenen Abmelde-Funktion beim Abbau. Eine
   frühere Fassung dieses Issues ließ das offen und vermutete den Rahmen (M7-02); der Rahmen darf es
   **nicht**, weil seine Definition of Done ihm jeden IPC-Bezug verbietet, der Nachlauf aber ein Abo
   auf `queue:geaendert` braucht. M7-65 baut die Bausteine aus M7-04 (`holeProjekt`/`setzeProjekt`,
   `verwirfMotivBestand`, `bereiteZeichnenVor`) und M7-41 (`leereProjektHistorie`) zu
   `NachlaufWirkungen` zusammen und ruft `starteAuftragsNachlauf` an einer festgelegten Stelle
   seiner Reihenfolge. *Für diese Datei ändert sich dadurch nichts an der Signatur:* Abo und
   Wirkungen kommen weiterhin als **Parameter** herein (ENTSCHIEDEN 5).
10. **`meldeFehler` hat einen Anzeigeplatz – die anwendungsweite Meldungsfläche des Rahmens.**
    M7-02 führt dafür den Schlitz `meldungsFlaeche` (unmittelbar unter der Reiterleiste), M7-69 hält
    die Meldung in `App.tsx` und belegt den Schlitz. *Warum das hier vermerkt ist, obwohl es diese
    Datei nicht ändert:* Eine frühere Fassung ließ offen, wohin die Meldungen gehen – und ein
    Fehler, der niemandem angezeigt wird, ist schlimmer als keiner: Der Nutzer arbeitet weiter,
    während sein Import gescheitert ist. Dass die Fläche im **Rahmen** sitzt und nicht in einem
    Reiter, ist genau der Fall dieser Datei: Ein Auftrag läuft weiter, während der Nutzer den Reiter
    wechselt. *Für diese Datei ändert sich nichts:* Sie zeigt weiterhin **nichts** selbst an,
    formuliert **keinen** Text über `code` und `meldung` hinaus und kennt die Fläche nicht.
11. **Der fertige Import wird der Reparatur-Führung GEMELDET – aber diese Datei weiß nicht, ob eine
    läuft.** `meldeImportErgebnis` bekommt bei **jedem** erfolgreichen Import die Asset-Kennung;
    ob daraus ein Abschluss wird, entscheidet allein der Empfänger (M7-64
    `schliesseMedienImportAb`), indem er prüft, ob gerade eine Übergabe mit dem Ziel
    `'medien-import'` läuft. *Begründung – und warum die Prüfung NICHT hier steht:* Diese Datei
    kennt den Reparatur-Zustand nicht und darf ihn nicht kennen; sie hielte sonst eine zweite
    Wahrheit über „läuft gerade eine Reparatur?" neben dem Halter aus M7-64. Umgekehrt darf der
    Empfänger nicht selbst zuhören – der **einzige** Auswerter terminaler Auftrags-Übergänge bleibt
    diese Datei. Die Aufgabenteilung ist deshalb: **hier melden, dort entscheiden.**
    *Warum das Feld optional ist:* Genau wie `aktualisiereAusgabenListe`. Ein Aufrufer, der die
    Führung nicht verdrahtet hat (etwa ein Test), bekommt **kein** anderes Verhalten, und es wird
    **kein** Ersatz gebaut.
    *Warum die Kennung aus `ergebnis` kommt und nicht aus dem Projekt:* Sie steht dort bereits
    eingegrenzt (ENTSCHIEDEN 7). Sie aus `projekt.assets` zu erraten – „das zuletzt hinzugekommene" –
    wäre bei einer Mehrfachauswahl schlicht falsch.

## Fremde Signaturen, die du benutzt (abgeschrieben aus der definierenden Quelle)
Der umsetzende Agent sieht die anderen Issues nicht; hier steht alles vollständig.
**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.**

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `abonniereQueue` | bildet das Abo auf `queue:geaendert` | wird **genau einmal** je `starteAuftragsNachlauf` gerufen; die zurückgegebene Abmeldung wird gespeichert und beim Beenden ausgelöst |
| `auftraege` (Nutzlast) | der **vollständige** Stand der Warteschlange | wird **nicht** sortiert, **nicht** gefiltert und **nicht** verändert; die Reihenfolge kommt aus `holeStand`/Q1+Q2 |
| `auftrag.ergebnis` | fachliche Nutzdaten | `unknown`; vor der Verwendung auf die für die `art` dokumentierte Form eingegrenzt. Passt sie nicht → `meldeFehler`, Auftrag übersprungen |
| `wirkungen` | die Wirkstellen | Pflichtfelder; `aktualisiereAusgabenListe` und `meldeImportErgebnis` sind optional und werden mit `?.()` gerufen |

Ausgang bei Erfolg: die Abmelde-Funktion. Wirkung: die oben beschriebenen Folgen, jede genau einmal
je Auftrag.
Ausgang bei Fehler: **entfällt** als Rückgabewert; Fehler gehen über `wirkungen.meldeFehler`.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Ein Auftrag, der D1 verändert (Medien-Import oder -Löschen), leert die Undo-Historie der
  Projekt-Bearbeitung.**" (TK 9.13.3)
- „Da Aufträge seriell und vergleichsweise selten sind (9.3), ist das Leeren der Historie ein
  billiger Preis für Korrektheit." (TK 9.13.3)
- „**Aufträge sind daher grundsätzlich nicht undo-fähig**; ein gelöschtes Medium muss neu importiert
  werden." (TK 9.13.1)
- „**5. Ereignisse sind Einbahnstraßen und tragen keinen Endzustand** (für `RenderProgress` bereits
  festgelegt, 9.2.7). Terminale Zustände kommen ausschließlich über Aufruf-Ergebnis bzw.
  Auftrags-Zustand." (TK 9.1.1) – der terminale Zustand steht **im Auftrag** (`status`), nicht im
  Ereignis; das Ereignis transportiert nur die Liste.
- „**Ereignisse** (Main → Renderer) tragen ebenfalls keine Hülle (Punkt 5)." (TK 9.1.1 Punkt 2) –
  die Nutzlast ist ein **nacktes** `Auftrag[]`; es wird nichts ausgepackt.
- „**Ereignisse vor dem Aufbau des Fensters verfallen still – es wird NICHT gepuffert (bindend).**"
  (TK 9.1.1 Punkt 10) – deshalb ist es **richtig**, dass dieser Nachlauf einen Auftrag verpasst,
  der vor seinem Start terminal wurde. Er baut **keinen** Ausgleich und **holt keinen Stand nach**;
  das anfängliche Holen ist der Warteschlangen-Leiste zugewiesen (TK 9.14.2, M7-12).
- „Die umgekehrte Reihenfolge (erst abonnieren, dann holen) wäre **falsch** – die Antwort auf das
  Holen könnte einen **älteren** Stand tragen als ein zwischenzeitlich empfangenes Ereignis und es
  damit überschreiben." (TK 9.1.1 Punkt 10) – die Begründung dafür, dass hier **nichts** geholt wird.
- „**Randfall:** Wird ein Band durch das Entfernen leer (keine Abschnitte mehr), entfällt die
  **Einblendung ganz** (`einblendung = null`) – das **Videoelement bleibt**." (TK 9.5.3) – nur zur
  Abgrenzung: Diese Datei fasst **weder** Liste **noch** Einblendungen an. Sie ändert
  ausschließlich `assets`.

## Nicht selbst entscheiden – STOPP und fragen
**Das Verbot für alle anderen Issues – hier ausgeschrieben, damit es zitierbar ist:**

> **Kein anderes Issue des Meilensteins M7 leitet aus `queue:geaendert` eine fachliche Wirkung ab.**
> Verboten sind insbesondere: einen Asset in die Projekt-Sicht eintragen oder daraus entfernen, den
> Motiv-Bestand verwerfen, `bereiteZeichnenVor` erneut anstoßen, die Undo-Historie leeren, das
> Projekt neu laden. Diese Wirkungen gehören ausschließlich in `auftrags-nachlauf.ts` (M7-06).
> Ausgenommen ist allein die **Anzeige** der Warteschlange (`queue-panel`, M7-12 bis M7-18): Sie
> abonniert denselben Kanal, **zeigt** aber nur an und verändert weder Projekt noch Bestände.
> *Begründung:* Bei mehreren Auswertern ist die Reihenfolge nicht festgelegt. Leert einer den
> Motiv-Bestand, nachdem ein anderer den neuen Asset eingetragen hat, zeigt ein unter gleichem Namen
> importiertes Bild weiter das **alte** Motiv; leeren mehrere die Undo-Historie, wird unauffindbar,
> warum sie zu früh leer war.

Weiter gilt:
- **Verbot – hier wird nichts angezeigt.** Kein JSX, kein Text, kein Dialog. Fehler gehen über
  `meldeFehler`; angezeigt werden sie in der anwendungsweiten `meldungsFlaeche` des Rahmens
  (M7-02), belegt von M7-69 – **nicht** hier und **nicht** über einen zweiten Weg
  (kein `alert`, kein `console.error` als Ersatz).
- **Verbot – hier wird nichts nachgeladen und nichts eingereiht.** Kein `rufeAuf`, kein `reiheEin`,
  kein `holeStand`, kein Neuladen des Projekts.
- **Verbot – kein eigener Undo-Stapel.** `leereProjektHistorie` kommt aus M7-41
  (`src/renderer/app-shell/undo-historien.ts`, `export function leereProjektHistorie(): void`) und
  wird von M7-65 in die `NachlaufWirkungen` eingesetzt. Übergib **nicht** ersatzweise eine leere
  Funktion – dann sähe die Anwendung korrekt aus, während die Invariante aus TK 9.13.3 nicht gilt,
  und das fiele erst auf, wenn ein Undo ein importiertes Medium wieder verschwinden lässt.
- **Verbot – kein Selbststart.** `starteAuftragsNachlauf` wird von **M7-65** gerufen (s.
  ENTSCHIEDEN 9), **genau einmal** je Fenster. Diese Datei ruft sich **nicht** selbst auf – kein
  Aufruf beim Import der Datei, kein Modul-Merker „schon gestartet". Dann gäbe es keinen Ort, an
  dem sich das Abo wieder beenden ließe.
- **Offen: `Project.letzterAusgabeName` nach einem erfolgreichen Render.** Der Render setzt dieses
  Feld in D1; die Projekt-Sicht im Renderer erfährt davon **nichts**, weil das Auftrags-Ergebnis
  laut TK 9.3.1 nur Pfad, Dateigröße und Gesamtdauer trägt. Die Namensvorbelegung beim nächsten
  Render (FA-22) wäre damit veraltet. Möglich wären: das Feld hier aus dem Ergebnis-Pfad ableiten
  (rät), das Projekt neu laden (widerspricht ENTSCHIEDEN 6) oder den Vertrag ergänzen. **Nicht
  selbst wählen – melden.**
- **Verbot – hier wird NICHT geprüft, ob eine Reparatur läuft.** `meldeImportErgebnis` wird bei
  **jedem** erfolgreichen Import gerufen; kein Blick in einen Reparatur-Stand, keine `Uebergabe`,

- **Verbot – kein selbst erfundener Fehlercode.** Der Code für ein unbrauchbares `auftrag.ergebnis`

      einmal** mit einem `Project`, dessen `assets` den Asset aus `ergebnis` enthält, während
