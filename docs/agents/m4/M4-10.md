### Issue M4-10: [vorlagen-store] alsEigenstaendige – Arbeitskopie von ihrem Parent lösen

## Ziel (in einem Satz)
Eine Arbeitskopie wird unter einem neuen Namen zu einer eigenständigen, auswählbaren Vorlage, indem
**ihr** Feld `parent` auf `null` gesetzt wird – die Vorlage, von der sie abgeleitet wurde, bleibt
dabei unangetastet.

## Modul & Datei
- Modul: `vorlagen-store` (Main)
- Datei: `src/main/vorlagen-store/als-eigenstaendige.ts`
- Vertrag: Technisches Konzept **9.12.1** (Operationstabelle, „Zweck des `parent`-Feldes",
  Invarianten – Quelle der Wahrheit), ergänzend **9.11.1** (Datenmodell `Vorlage`), **9.11.1.1**,
  **9.1.1** (IPC-Konventionen, Ergebnis-Hülle)
- Prozess/Speicher: V1 (`vorlagen.json`, app-weit). **Kein** direkter Dateizugriff – gelesen und
  geschrieben wird ausschließlich über M4-04. **Kein** D1-Zugriff, **kein** D1-Lock.

## Warum das im Gesamtsystem wichtig ist
Dies ist der **einzige** Weg, auf dem eine eigene Vorlage aus einer eingebauten entsteht – und damit
der einzige Weg, auf dem FA-13 (eigene Vorlagen anlegen und bearbeiten) für die mitgelieferten
Layouts überhaupt funktioniert: Bei eingebauten Vorlagen „bleibt nur `alsEigenstaendige`"
(TK 9.12.1). Wer hier zusätzlich Sperren einbaut, die es im Vertrag nicht gibt (etwa „geht nicht,
weil der Parent eingebaut ist"), macht die eingebauten Vorlagen zu einer Sackgasse.

Die teure lokale Entscheidung steckt in der Frage, **welches** `parent`-Feld angefasst wird. Das
Konzept warnt ausdrücklich vor der Verwechslung: „wird **das Feld** auf `null` gesetzt (nicht der
Parent verändert!)". Wer stattdessen am Parent-Datensatz arbeitet – ihn löscht, umbenennt, seine
Zonen ersetzt oder ihn „aufräumt" –, verändert eine Vorlage, die in fremden Projekten in Benutzung
ist, obwohl der Nutzer gerade das Gegenteil gewählt hat.

Die zweite teure Stelle ist die **Identität** des Ergebnisses. Wird hier ein *zusätzlicher* Eintrag
mit neuer ID angelegt statt der vorhandenen Arbeitskopie ihr `parent` genommen, bleibt die
Arbeitskopie zurück: Sie taucht weiter unter „Bearbeitung fortsetzen" auf (`listeArbeitskopien`,
M4-05), hält weiter ihren Parent für ihr Ziel – und der Nutzer hat plötzlich zwei Datensätze, von
denen er nur einen wollte.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/vorlagen-store/als-eigenstaendige.ts

export async function alsEigenstaendige(
  arbeitsId: string,
  name: string,
): Promise<Ergebnis<Vorlage, VorlagenFehlercode>>
// - setzt am EINTRAG MIT id === arbeitsId: parent = null, name = <name>, eingebaut = false
// - behält dessen id, art, höhe und zonen unverändert
// - fasst den Parent-Datensatz NICHT an und liest ihn nicht einmal
// - legt KEINEN zusätzlichen Eintrag an und entfernt keinen
// - kein fs, kein Lock, kein IPC-Kanal (den meldet M4-15 an)
```

**Fremde Funktionen und Typen, die du benutzt** (der umsetzende Agent sieht die anderen Issues
nicht – deshalb hier vollständig ausgeschrieben):

```ts
// M4-01 – src/shared/contracts/vorlage.ts (geteilter Typ; hier NICHT neu deklarieren)
export interface Vorlage {
  id:        string                                        // UUID
  name:      string                                        // Anzeigename
  art:       VorlagenArt                                   // Fläche + Kompositionsart
  höhe:      number | null                                 // nur bei split/einblendung: Bandhöhe px
  parent:    string | null                                 // ≠ null → ARBEITSKOPIE; = null → nutzbar
  eingebaut: boolean                                       // true = mitgeliefert, eingefroren
  zonen:     Zone[]                                        // Zeichenreihenfolge = Array-Reihenfolge
}
// Der Aufbau von `Zone` ist für DIESE Funktion ohne Belang: Zonen werden unverändert übernommen.

// M4-03 – src/main/vorlagen-store/fehlercodes.ts (Fehlercode-Union des Moduls; hier NICHT neu anlegen)
export type VorlagenFehlercode = 'vorlage_referenziert' | 'parent_eingebaut' | 'speicher_fehler'
// Die drei generischen Codes (ungueltige_eingabe, nicht_gefunden, unbekannter_fehler) kommen über
// den zweiten Typparameter von Ergebnis automatisch dazu und stehen bewusst NICHT in dieser Union.
// DIESE Funktion vergibt weder vorlage_referenziert noch parent_eingebaut (s. Fehlerpfade).

// M4-04 – src/main/vorlagen-store/schreibe-vorlagen.ts (der EINZIGE Dateizugriff des Moduls)
export async function aendereBestand<T>(
  aenderung: (bestand: Vorlage[]) => Ergebnis<{ bestand: Vorlage[]; wert: T }, VorlagenFehlercode>,
  schreibart: 'sofort' | 'entprellt',
): Promise<Ergebnis<T, VorlagenFehlercode>>
// - `aenderung` ist SYNCHRON und darf NICHT `await`en; genau das macht Lesen-Ändern-Schreiben zu
//   einer ununterbrechbaren Einheit
// - `aenderung` bekommt eine TIEFE KOPIE des Bestands und darf sie verändern
// - liefert `aenderung` ok:false, wird NICHTS geschrieben, der Fehler wird unverändert durchgereicht
// - 'sofort' -> die Datei ist geschrieben, BEVOR das Promise erfüllt wird
// - Aufrufe laufen streng nacheinander (verkettete Promise), auch die aus anderen Operationen

// #12/#22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
// Diese Funktion setzt `daten` NIE.
```

**`aendereBestand` ist der einzige Weg, `vorlagen.json` zu ändern; die Quelle dieser Signatur ist
M4-04.** Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein
**Vertragsfehler**: **melden und NICHT eigenmächtig anpassen.** Baue **keine** eigene
Zwischenlösung.

**Wer ruft dich auf:** der `vorlagen-editor` (Renderer) über den IPC-Kanal
`vorlagen:alsEigenstaendige`, den **M4-15** anmeldet. Diese Datei kennt weder `ipcMain` noch den
Kanalnamen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `arbeitsId` | ID der Arbeitskopie, die eigenständig werden soll | nicht leerer String; muss im Bestand stehen **und** dort `parent ≠ null` haben, sonst s. Fehlerpfade |
| `name` | Anzeigename der neuen eigenständigen Vorlage | String; nach `trim()` nicht leer und höchstens 80 Zeichen lang – **dieselbe** Regel wie in M4-06 und M4-08. Gespeichert wird der **getrimmte** Name. Doppelte Namen sind erlaubt (s. u.) |

Ausgang bei Erfolg: `Ergebnis<Vorlage>` mit dem Eintrag in seinem neuen Zustand – **gleiche `id`**
wie die Arbeitskopie, `parent: null`, `eingebaut: false`, `name` = der getrimmte Name, `art`,
`höhe` und `zonen` unverändert. Der Bestand hat danach **genauso viele** Einträge wie vorher.
Ausgang bei Fehler: `ungueltige_eingabe`, `nicht_gefunden`, `speicher_fehler` (geschlossener Satz,
s. Fehlerpfade). `vorlage_referenziert` und `parent_eingebaut` entstehen hier **nie**.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operation, wörtlich (TK 9.12.1, Operationstabelle):
  ```
  | `alsEigenstaendige` | `arbeitsId`, `name` → `Ergebnis<Vorlage>` – setzt **`parent = null`**, Arbeitskopie wird eine echte Vorlage |
  ```
- **Die Begründung, warum das Feld genullt wird – wörtlich (TK 9.12.1):** „**Zweck des
  `parent`-Feldes (und warum es genullt wird):** Das Feld `parent` ist **die Merge-Beziehung** – es
  sagt „diese Vorlage stammt von X und kann in X zurückgeschrieben werden". Wählt der Nutzer „als
  eigenständige Vorlage", wird **das Feld** auf `null` gesetzt (nicht der Parent verändert!). Damit
  ist die Beziehung **bewusst durchtrennt** – genau das schließt spätere **Merge-Konflikte** aus:
  eine Vorlage ohne `parent` kann niemanden mehr überschreiben und von niemandem überschrieben
  werden."
  **Für dich heißt das zweierlei:** Das Nullen ist **kein** Informationsverlust, den du irgendwo
  „retten" sollst (kein zweites Feld `abgeleitetVon`, kein Vermerk im Namen) – die Beziehung soll
  weg sein. Und: Der Parent bleibt, wie er ist.
- Das Feld `parent`, wörtlich aus dem Datenmodell (TK 9.11.1):
  ```
  parent:    string | null // Herkunft: ID der Vorlage, von der diese abgeleitet wurde.
                           //   ≠ null → ARBEITSKOPIE (in Bearbeitung, nicht auswählbar)
                           //   = null → eigenständige, nutzbare Vorlage
  ```
- „**`uebernehmeInParent` ist gesperrt, wenn der Parent eingebaut ist.** Eingebaute Vorlagen bleiben
  unveränderlich (9.11.1.1); dort bleibt nur `alsEigenstaendige`. Der Editor macht das vorher
  sichtbar, statt beim Speichern zu scheitern." (TK 9.12.1) – **diese** Operation ist also für einen
  eingebauten Parent ausdrücklich der vorgesehene Weg und wird deswegen **niemals** gesperrt.
- „**Eingebaute Vorlagen** lassen sich nicht überarbeiten; bei ihnen steht nur „als neue
  eigenständige Vorlage" zur Verfügung (sie bleiben als verlässliche Ausgangsbasis erhalten)."
  (Anforderungsdokument 4.6)
- „**Arbeitskopien (`parent ≠ null`) sind nicht auswählbar.** `composer` und `action-editor`
  bekommen sie nicht angeboten – halbfertige Vorlagen können nicht in einen Render geraten."
  (TK 9.12.1) – der Sinn dieser Operation ist genau, diesen Zustand zu beenden: Nach dem Nullen ist
  der Eintrag auswählbar, und das ist beabsichtigt.
- „**Auto-Speichern trifft nur die Arbeitskopie.** Während des Bearbeitens wird entprellt gesichert
  (3–5 s, wie 9.5.4) – aber **ausschließlich** in die Arbeitskopie. Die genutzte Vorlage ändert sich
  **erst** beim expliziten `uebernehmeInParent` bzw. `alsEigenstaendige`." (TK 9.12.1)
- „**`art` ist nach dem Anlegen unveränderlich** – auch über die Arbeitskopie. Ein Wechsel würde alle
  Zonen-Rahmen ungültig machen (andere Fläche); stattdessen neu anlegen." (TK 9.12.1) – `art` und
  `höhe` bleiben deshalb hier unverändert; sie sind **kein** Parameter dieser Operation.
- „**Alle IDs sind UUIDs** – `Project`, `Asset`, `Aktion`, `Listenelement`, `Vorlage`, `Auftrag`.
  **Keine** fortlaufenden Zähler … **Keine** aus Namen abgeleiteten IDs: ein Umbenennen darf niemals
  Referenzen brechen." (TK 9.11.4) – daraus folgt: Der neue `name` hat **keinen** Einfluss auf die
  `id`.
- „**IDs werden nie wiederverwendet**, auch nicht nach dem Löschen." (TK 9.11.4)
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Kein `throw` – die Funktion wird aus einem IPC-bedienten Kanal heraus aufgerufen.
- „**Der Main validiert jede eingehende Nutzlast** – er vertraut dem Renderer **nicht**. Ungültige
  Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten." (TK 9.1.1, Punkt 6)
- „**Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code." (TK 9.1.1, Punkt 7)

**Ablauf (verbindlich), vollständig innerhalb EINER `aendereBestand(…, 'sofort')`-Einheit.**
1. `arbeitsId` und `name` formal prüfen – sonst `ungueltige_eingabe` **ohne** jeden Bestandszugriff,
   also **vor** dem Aufruf von `aendereBestand`.
2. `aendereBestand(aenderung, 'sofort')` aufrufen. Die Änderungsfunktion ist **synchron** und darf
   **nicht** `await`en (M4-04).
3. In der Änderungsfunktion: Eintrag mit `id === arbeitsId` suchen, Sperren prüfen (s. Fehlerpfade).
   Jeder Verstoß wird als `ok: false` **aus der Änderungsfunktion heraus** gemeldet – dann schreibt
   M4-04 **nichts**.
4. Sonst: an der **Position des Eintrags** steht danach
   `{ ...eintrag, parent: null, name: <getrimmt>, eingebaut: false }`; alle übrigen Einträge
   unverändert und in unveränderter Reihenfolge.
5. `{ ok: true, wert: { bestand: <neuer Bestand>, wert: <der neue Eintrag> } }` zurückgeben.
6. `aendereBestand` schreibt und erfüllt sein Promise erst danach (`'sofort'`); dessen Ergebnis ist
   der Rückgabewert dieser Funktion.

**ENTSCHIEDEN – `'sofort'`, nicht `'entprellt'`.** Hier entsteht eine **auswählbare** Vorlage; ab dem
gemeldeten Erfolg kann der Nutzer sie einer Aktion zuweisen. Wäre sie zu diesem Zeitpunkt nur im
Speicher, zeigte nach einem Absturz eine Aktion auf eine Vorlage, die in `vorlagen.json` nie
angekommen ist. `'entprellt'` ist ausschließlich für das Auto-Speichern der Arbeitskopie (M4-08).

**ENTSCHIEDEN – `eingebaut` wird ausdrücklich auf `false` gesetzt.** Eine Arbeitskopie trägt bereits
`eingebaut: false` (M4-07 legt sie so an; eine Kopie ist nie mitgeliefert), das Setzen ist im
Regelfall also folgenlos. Es steht trotzdem da, weil das **Ergebnis** dieser Operation per Definition
eine **eigene** Vorlage ist (FA-13) – und weil ein versehentlich mit `eingebaut: true` entstandener
Eintrag dauerhaft unreparierbar wäre: Er wäre „unlöschbar und eingefroren" (TK 9.11.1.1), ließe sich
also weder löschen noch überarbeiten. Eine Zeile hier verhindert einen Datensatz, den der Nutzer
nie wieder loswird.

**ENTSCHIEDEN – der Parent wird nicht einmal gelesen.** Diese Funktion sucht `eintrag.parent`
**nicht** im Bestand und prüft **nicht**, ob es ihn noch gibt. Begründung: Sie ändert am Parent
nichts, und ein fehlender Parent ist kein Grund zu scheitern – im Gegenteil, genau dieser Fall
(Parent gelöscht, Kopie verwaist) wird von M4-14 durch dasselbe Nullen behandelt. Eine
Existenzprüfung würde eine Operation blockieren, deren Ergebnis vom Parent unabhängig ist.

**ENTSCHIEDEN – doppelte Namen sind erlaubt (lokale Entscheidung).** Es wird **nicht** geprüft, ob
schon eine Vorlage so heißt, und **nicht** automatisch „(2)" angehängt. Begründung: Die Identität ist
die UUID (TK 9.11.4), nicht der Name; eine Namenssperre würde einen Nachfrage-Dialog erzwingen, den
der Vertrag nicht vorsieht, und ein automatischer Zusatz würde den vom Nutzer eingegebenen Namen
stillschweigend verändern.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `arbeitsId` ist kein String oder leer | `ungueltige_eingabe` | keine Wirkung; `aendereBestand` wird **gar nicht** aufgerufen |
| `name` ist kein String, nach `trim()` leer oder länger als 80 Zeichen | `ungueltige_eingabe` | keine Wirkung; **kein** Ersatzname, **kein** Kürzen, **kein** Übernehmen des alten Namens |
| `aendereBestand` kann den Bestand nicht laden | `speicher_fehler` | unverändert durchreichen; die Änderungsfunktion läuft gar nicht erst |
| keine Vorlage mit `id === arbeitsId` | `nicht_gefunden` | Abbruch aus der Änderungsfunktion heraus; es wird **nichts** geschrieben |
| Eintrag gefunden, aber `parent === null` (ist bereits eigenständig) | `ungueltige_eingabe` | keine Wirkung. **Kein** stiller Erfolg und **kein** heimliches Umbenennen: Sonst wäre diese Operation ein zweiter, ungeprüfter Weg, jede beliebige – auch eine eingebaute – Vorlage umzubenennen |
| das Schreiben in `aendereBestand` schlägt fehl | `speicher_fehler` | unverändert durchreichen; `vorlagen.json` ist entweder vollständig alt oder vollständig neu |

Fehlercodes werden **nicht erfunden**: „Fehlercodes sind ein geschlossener, typisierter Satz …
Eine rohe Exception-Meldung wird nie zum Code." (TK 9.1.1, Punkt 3)

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – den Parent nicht anfassen.** Kein Löschen, kein Umbenennen, kein Ändern seiner Zonen,
  kein Setzen irgendeines Feldes, kein „Aufräumen", weil er jetzt keine Kopie mehr hat. TK 9.12.1
  sagt es in Klammern: „(nicht der Parent verändert!)".
- **Verbot – keine neue ID, kein zusätzlicher Eintrag.** Der Bestand hat danach **genauso viele**
  Einträge wie vorher. Kein `erzeugeId()` (#20), kein Duplizieren, kein Zurücklassen der
  Arbeitskopie. Das Konzept sagt: „Arbeitskopie wird eine echte Vorlage" – derselbe Datensatz,
  nicht ein zweiter.
- **Verbot – keine Sperre wegen `eingebaut` des Parents.** Diese Operation ist der ausdrücklich
  vorgesehene Weg für eingebaute Vorlagen. Wer hier eine Prüfung „Parent ist eingebaut → abbrechen"
  einbaut, macht die mitgelieferten Layouts unbenutzbar für FA-13.
- **Verbot – die Zonen nicht anfassen.** Kein Sortieren, kein Zuschneiden, keine Prüfung fester
  Zonen, keine Umrechnung. Die Gültigkeit sichern der Editor (TK 9.12.2) und das Auto-Speichern
  (M4-08); zwei Prüfstellen laufen garantiert auseinander.
- **Verbot – den Namen nicht über das Trimmen hinaus reparieren.** Getrimmt wird, weil M4-06 und
  M4-08 dieselbe Regel anwenden und drei verschiedene Namensregeln in einem Modul niemand mehr
  durchschaut. Sonst gilt: kein Kürzen eines zu langen Namens, kein Ersetzen von Sonderzeichen, keine
  Vorbelegung bei leerem Namen, keine Eindeutigkeits-Nummerierung. Der Name ist ein Anzeigename und
  **kein** Dateiname – es entsteht durch ihn keine Datei und kein Pfad. Ungültig heißt abgelehnt,
  nicht zurechtgebogen.
- **Verbot – kein zweiter Schreibpfad, kein Dateisystem.** Kein `fs`, kein eigenes Temp/Rename, kein
  `.bak`. Ausschließlich `aendereBestand` (M4-04) – und **kein** `await` innerhalb der
  Änderungsfunktion. Kein `mitD1Lock` und **kein eigenes Lock** – die Serialisierung liegt bei
  M4-04. Auch **kein** `flushBestand()`: Das gehört laut M4-04 dem Beenden der App (#3).
- **Verbot – kein IPC, kein Ereignis.** Kein `ipcMain`, kein `BrowserWindow`, kein Eintrag in
  `kanaele.ts`, kein Kanalname als String. Der Kanal `vorlagen:alsEigenstaendige` gehört **M4-15**.
- **Verbot – keine Referenzprüfung, kein Merge.** Diese Funktion zählt keine Nutzungen und schreibt
  in keine andere Vorlage. Wer „zur Sicherheit" auch den Parent aktualisiert, hat aus zwei
  Nutzerentscheidungen eine gemacht.

## Definition of Done
- [ ] Erfolgsfall: Der Eintrag trägt danach `parent === null`, `eingebaut === false`, den
      übergebenen (getrimmten) `name`, **dieselbe** `id` wie vorher sowie unveränderte `art`, `höhe`
      und `zonen` (Deep-Vergleich der Zonen)
- [ ] Der Bestand hat danach **dieselbe Länge** wie vorher, und der Eintrag steht an **derselben
      Position** (Test vergleicht das ganze Array)
- [ ] Der Parent-Eintrag ist danach **byte-gleich** wie vorher (Deep-Vergleich) – insbesondere
      unverändert in `name`, `zonen`, `eingebaut` und `parent`
- [ ] Eine Arbeitskopie eines **eingebauten** Parents wird erfolgreich eigenständig (kein Fehler) –
      und der eingebaute Parent bleibt unverändert im Bestand
- [ ] `aendereBestand` wird **genau einmal** aufgerufen, mit `schreibart === 'sofort'` (Spy)
- [ ] Ein Name mit führenden und abschließenden Leerzeichen steht danach **getrimmt** im Eintrag
- [ ] `name = ''`, `name = '   '`, ein Name mit 81 Zeichen und ein Nicht-String liefern jeweils
      `ungueltige_eingabe`, und `aendereBestand` wurde nachweislich **nicht** aufgerufen (Spy: null
      Aufrufe)
- [ ] Eine `arbeitsId`, die auf einen Eintrag mit `parent === null` zeigt, liefert
      `ungueltige_eingabe` und benennt nichts um (Bestand unverändert)
- [ ] Eine unbekannte `arbeitsId` liefert `nicht_gefunden` ohne Schreibvorgang
- [ ] Eine Arbeitskopie, deren `parent` auf eine **nicht mehr vorhandene** ID zeigt, wird trotzdem
      erfolgreich eigenständig (Test) – der Parent wird nicht nachgeschlagen
- [ ] Liefert `aendereBestand` `{ ok: false, fehler: { code: 'speicher_fehler', … } }`, kommt genau
      dieser Code beim Aufrufer an
- [ ] Die Änderungsfunktion ist **synchron**: Ihr Rückgabewert ist kein `Promise`, und sie enthält
      kein `await` (Test + Grep-Probe)
- [ ] Die Datei enthält kein `fs`, kein `ipcMain`, kein `BrowserWindow`, kein `erzeugeId`, kein
      `mitD1Lock` und kein String-Literal `'vorlagen:'` (Grep-Probe)
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze)
- [ ] Keine Datei außerhalb von `src/main/vorlagen-store/als-eigenstaendige.ts` **(+ zugehörige
      Testdatei)** geändert
