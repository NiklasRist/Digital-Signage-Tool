### Issue M4-04: [vorlagen-store] vorlagen.json atomar und serialisiert lesen und schreiben

## Ziel (in einem Satz)
Die app-weite Vorlagen-Bibliothek wird über **eine** gemeinsame Stelle geladen und geschrieben –
absturzsicher (Backup + Temp + Rename), streng nacheinander und mit einem Anfangsbestand beim ersten
Start –, sodass zwei gleichzeitige Änderungen sich niemals verschränken und niemals eine bestehende
Vorlage überschrieben wird.

## Modul & Datei
- Modul: `vorlagen-store` (Main)
- Datei: `src/main/vorlagen-store/schreibe-vorlagen.ts`
- Vertrag: Technisches Konzept **9.12.1** (eigene Schreib-Serialisierung), **9.5.4** (die
  Schreib-Invarianten, auf die 9.12.1 verweist), **9.11.1.1** (eingebaute sind eingefroren),
  **9.5.5** (`schemaVersion`) – Quelle der Wahrheit
- Prozess/Speicher: V1 (`<Datenort>/vorlagen.json`, `<Datenort>/vorlagen.json.bak`)

## Warum das im Gesamtsystem wichtig ist
Dies ist die **einzige** Stelle im ganzen Modul, die `fs` anfasst. M4-05 bis M4-14 rufen
ausschliesslich hier auf. Drei Fehlerklassen entstehen, wenn diese Datei nachlässig gebaut wird, und
alle drei sind stiller Verlust:

**Erstens die Verschränkung.** Alle Operationen des Moduls sind Lesen-Ändern-Schreiben-Zyklen auf
**derselben** Datei: Der Editor speichert entprellt eine Arbeitskopie, während der Nutzer im
Vorlagen-Verwalter eine andere Vorlage löscht. Lesen beide den Bestand und schreiben ihn zurück,
überschreibt der zweite die Änderung des ersten (Lost Update). Anders als bei `project.json` gibt es
hier **kein** Lock, das das verhindern könnte – das D1-Lock schützt ausdrücklich nur `project.json`.
Deshalb bekommt der `vorlagen-store` eine **eigene** Serialisierung, und deshalb ist der
Änderungs-Baustein dieser Datei so geschnitten, dass Lesen, Ändern und Schreiben **eine
ununterbrechbare Einheit** sind.

**Zweitens der stille Fallback.** Wer eine defekte `vorlagen.json` mit
`try { … } catch { return eingebauteVorlagen() }` behandelt, verwandelt eine beschädigte Bibliothek in
eine frische – **alle** eigenen Vorlagen des Nutzers sind damit weg, und die App startet fröhlich
weiter. Schlimmer: Beim nächsten Schreiben wird der Verlust festgeschrieben. Deshalb muss diese Datei
zwischen „Datei existiert noch nicht" (normal, Erstbenutzung) und „Datei ist unlesbar" (Fehler,
meldepflichtig) hart unterscheiden.

**Drittens das Überschreiben beim Start.** Wer beim Start die drei eingebauten Vorlagen einfach in den
Bestand schreibt, macht aus einem App-Update eine Layout-Änderung an bestehenden Projekten – genau
das, was TK 9.11.1.1 verbietet. Ergänzt wird deshalb nur, was **fehlt**.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/vorlagen-store/schreibe-vorlagen.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { Vorlage } from '../../shared/contracts/vorlage'
import type { VorlagenFehlercode } from './fehlercodes'
import { eingebauteVorlagen, EINGEBAUTE_VORLAGEN_IDS } from './eingebaute-vorlagen'
import { ermittleDatenOrt } from '../datenort'

// Fremde Aufrufe – vollstaendige Signaturen, damit hier nichts geraten wird:
//   #5:     ermittleDatenOrt(): string
//           // absoluter Pfad zum Ordner, der projects/, config.json, vorlagen.json,
//           // protokoll.json, warteschlangen-journal.json enthaelt bzw. enthalten wird
//   M4-02:  eingebauteVorlagen(): Vorlage[]      // frische TIEFE Kopie der drei Mitgelieferten
//   M4-02:  const EINGEBAUTE_VORLAGEN_IDS = ['vollbild', 'split', 'band-standard'] as const
//   M4-03:  type VorlagenFehlercode = 'vorlage_referenziert' | 'parent_eingebaut' | 'speicher_fehler'
//   #12/#22: type Ergebnis<T, F extends string = GenerischerFehlercode> =
//              | { ok: true; wert: T }
//              | { ok: false; fehler: { code: F | GenerischerFehlercode
//                                       meldung: string; daten?: unknown } }

/**
 * Schema-Version von vorlagen.json. Modul-lokal und hier deklariert.
 * NICHT die AKTUELLE_SCHEMA_VERSION aus #21 verwenden – die gehoert zu project.json/config.json;
 * eine Kopplung an D1-Migrationen ist unerwuenscht. Auch NICHT die QUEUE_SCHEMA_VERSION aus #69.
 */
export const VORLAGEN_SCHEMA_VERSION = 1

/** Dateiform von vorlagen.json. `vorlagen` enthaelt nutzbare Vorlagen UND Arbeitskopien. */
export interface VorlagenDatei {
  schemaVersion: number
  vorlagen: Vorlage[]
}

/**
 * Liefert den vollstaendigen Bestand (nutzbare Vorlagen UND Arbeitskopien) als TIEFE Kopie.
 * Beim ersten Aufruf wird die Datei geladen bzw. angelegt; danach kommt der Bestand aus dem
 * Speicher. Reine Leser (M4-05, M4-13) benutzen diese Funktion.
 *
 * Laeuft auf DERSELBEN Serialisierungskette wie `aendereBestand` und niemals daran vorbei.
 */
export async function ladeBestand(): Promise<Ergebnis<Vorlage[], VorlagenFehlercode>>

/**
 * Die EINZIGE Art, den Bestand zu aendern. Laedt (falls noetig), ruft `aenderung` mit einer tiefen
 * Kopie des Bestands auf, uebernimmt das Ergebnis in den Speicher und schreibt.
 *
 * `aenderung` ist SYNCHRON – sie darf nicht `await`en. Genau das macht Lesen-Aendern-Schreiben zu
 * einer ununterbrechbaren Einheit: Ohne `await` kann zwischen Lesen und Schreiben kein zweiter
 * Aufruf dazwischenkommen. Eine asynchrone Aenderungsfunktion wuerde diese Zusage aufheben.
 *
 * Liefert `aenderung` ein `ok: false`, wird NICHTS geschrieben und der Fehler unveraendert
 * durchgereicht.
 *
 * Aufrufe laufen streng nacheinander (verkettete Promise), auch die aus verschiedenen Operationen.
 */
export async function aendereBestand<T>(
  aenderung: (bestand: Vorlage[]) => Ergebnis<{ bestand: Vorlage[]; wert: T }, VorlagenFehlercode>,
  schreibart: 'sofort' | 'entprellt',
): Promise<Ergebnis<T, VorlagenFehlercode>>
// 'sofort'    -> die Datei ist geschrieben, BEVOR das Promise erfuellt wird
// 'entprellt' -> der Bestand ist im Speicher uebernommen und das Promise wird erfuellt; die Datei
//                wird 4000 ms nach der LETZTEN entprellten Aenderung geschrieben

/**
 * Schreibt einen noch ausstehenden entprellten Stand sofort und bricht den Timer ab.
 * Steht nichts aus, ist das ein erfolgreicher Leerlauf ({ ok: true }), kein Fehler.
 * Aufrufer: das Beenden der App (#3) – „Beim Beenden blockiert die App, bis der Schreibvorgang
 * abgeschlossen ist" (TK 9.5.4).
 */
export async function flushBestand(): Promise<Ergebnis<void, VorlagenFehlercode>>
```

**Die oben ausgeschriebenen fremden Signaturen (#5, M4-02, M4-03, #12/#22) sind fremder Vertrag.**
Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein **Vertragsfehler**:
**melden und NICHT eigenmächtig anpassen.**

**`ladeBestand` läuft auf derselben Serialisierungskette wie `aendereBestand` (verbindlich).** Beide
hängen sich an **dieselbe** verkettete Promise; ein Laden kann sich also nie zwischen das Lesen und
das Schreiben einer laufenden Änderung schieben. Zusätzlich findet der **Erstladevorgang höchstens
einmal** statt: Das Promise des laufenden Ladens wird gemerkt und an alle weiteren Aufrufer
ausgegeben (geteiltes in-flight-Promise), statt ein zweites Laden zu starten. Ohne das legen zwei
gleichzeitige Leser beim allerersten Start **zweimal** den Anfangsbestand an und schreiben ihn
zweimal – im günstigen Fall doppelte Arbeit, im ungünstigen zwei sich überholende Schreibvorgänge auf
derselben Datei.

**Ablauf von `ladeBestand`, wenn der Bestand noch nicht im Speicher ist (verbindlich):**

1. `<Datenort>/vorlagen.json` lesen. Der Datenort kommt aus `ermittleDatenOrt()` (#5); der Dateiname
   `vorlagen.json` steht in TK 6.
2. **Datei fehlt** → Anfangsbestand `eingebauteVorlagen()` (M4-02), Datei anlegen (Schritt 6),
   fertig.
3. **Datei nicht parsebar** → `<Datenort>/vorlagen.json.bak` versuchen. Ist die parsebar, wird deren
   Inhalt verwendet; die defekte `vorlagen.json` bleibt dabei **unverändert liegen** und wird erst
   beim nächsten regulären Schreiben ersetzt. Dass aus dem `.bak` wiederhergestellt wurde, wird
   **gemerkt** – der nächste Schreibvorgang überspringt deshalb das Kopieren nach `.bak` (s. u.).
4. **Beide nicht parsebar oder nicht lesbar** → `speicher_fehler`. **Kein** Rückfall auf den
   Anfangsbestand.
5. **`schemaVersion` ungleich `VORLAGEN_SCHEMA_VERSION`** → `speicher_fehler`, Meldung nennt die
   gelesene und die erwartete Version. Es gibt aktuell nur die Version 1 und deshalb **keine**
   Migration; eine unbekannte Version wird **nicht** geraten.
6. **Fehlende eingebaute Vorlagen ergänzen:** Für jede ID aus `EINGEBAUTE_VORLAGEN_IDS`, die im
   gelesenen Bestand **nicht** vorkommt, wird die entsprechende Vorlage aus `eingebauteVorlagen()`
   **hinten angehängt**. Ein vorhandener Eintrag mit dieser ID wird **nie** ersetzt, ergänzt oder
   verglichen. Wurde etwas ergänzt (oder wurde die Datei neu angelegt), wird der Bestand geschrieben.
7. Der Bestand wird im Speicher gehalten. Schlägt das Schreiben in Schritt 6 fehl, wird
   `speicher_fehler` gemeldet und der Bestand **nicht** zwischengespeichert – der nächste Aufruf
   versucht es erneut.

**Ablauf jedes Schreibvorgangs (verbindlich):**

1. Bestehende `vorlagen.json` (falls vorhanden) nach `vorlagen.json.bak` kopieren (`fs.copyFile`,
   kein Verschieben). **Ausnahme:** Wurde der Bestand in Schritt 3 des Ladens aus dem `.bak`
   wiederhergestellt, wird dieser Kopierschritt **beim ersten Schreibvorgang danach übersprungen**.
2. `{ schemaVersion: VORLAGEN_SCHEMA_VERSION, vorlagen: <Bestand> }` als JSON nach
   `vorlagen.json.tmp` schreiben.
3. `vorlagen.json.tmp` durch Rename-mit-Ersetzen auf `vorlagen.json` bringen (gleiche Partition).
   Danach gilt die Datei wieder als heil: Der gemerkte Wiederherstellungs-Zustand wird gelöscht, und
   alle weiteren Schreibvorgänge kopieren wieder ganz normal nach `.bak`.

**Warum diese Ausnahme unverzichtbar ist:** Nach einer Wiederherstellung liegt die **defekte** Datei
noch auf der Platte, während das `.bak` die **einzige heile** Fassung ist. Ein blindes Kopieren
`vorlagen.json → vorlagen.json.bak` würde also die letzte heile Version mit dem Schrott überschreiben
– und scheitert danach das Schreiben der neuen Fassung (Platte voll, Rechte, Absturz), ist die
gesamte Vorlagen-Bibliothek des Nutzers weg. Genau davor soll das Backup schützen.

Geschrieben wird **immer die ganze Datei**, nie ein Teil. Daraus folgt eine Eigenschaft, auf die sich
die Aufrufer verlassen dürfen: Ein `'sofort'`-Schreibvorgang persistiert auch alles, was eine noch
ausstehende entprellte Änderung geschrieben hätte. Der ausstehende Timer wird dabei abgebrochen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `aenderung` (`aendereBestand`) | synchrone Funktion, die aus dem alten Bestand den neuen und den Rückgabewert `T` bildet | muss synchron sein (kein `Promise`); darf den übergebenen Bestand verändern, weil er bereits eine tiefe Kopie ist; wirft sie doch eine Ausnahme, wird sie gefangen und als `unbekannter_fehler` gemeldet, **ohne** zu schreiben |
| `schreibart` (`aendereBestand`) | `'sofort'` für strukturelle Änderungen (anlegen, öffnen, übernehmen, verwerfen, löschen), `'entprellt'` nur für das Auto-Speichern der Arbeitskopie (M4-08) | genau diese zwei Werte |

Ausgang bei Erfolg: `Ergebnis<Vorlage[], VorlagenFehlercode>` mit einer tiefen Kopie des Bestands
(`ladeBestand`); `Ergebnis<T, VorlagenFehlercode>` mit dem von `aenderung` gelieferten Wert
(`aendereBestand`); `Ergebnis<void, VorlagenFehlercode>` (`flushBestand`).
Ausgang bei Fehler: `fehler.code` ist `speicher_fehler` (die modul-eigene Union
`VorlagenFehlercode` aus M4-03) oder einer der generischen Codes `ungueltige_eingabe`,
`nicht_gefunden`, `unbekannter_fehler` aus #12, die `Ergebnis` immer zulässt – bzw. der Code, den
`aenderung` selbst geliefert hat und der hier unverändert durchgereicht wird.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Besitzt** `vorlagen.json` (app-weite Vorlagen-Bibliothek) samt **eigener**
  Schreib-Serialisierung. Die Schreib-Invarianten sind **dieselben** wie in 9.5.4: **atomar** (Temp +
  Rename), **`vorlagen.json.bak`** als letzte heile Version, **`schemaVersion`**, und Speicherfehler
  werden **sichtbar** gemacht statt still verschluckt." (TK 9.12.1) – **diese** Datei *ist* die eigene
  Schreib-Serialisierung.
- „**Lock-Grenze:** Das D1-Lock schützt **nur** `project.json`. Die Auftragsverwaltungs-Speicher
  Q2/Q3 (eigene Dateien, 9.3) haben ihre **eigene** Serialisierung – der `auftrags-manager` hängt
  **nicht** am `project-store`-Lock." (TK 9.5.4) – dasselbe gilt für den `vorlagen-store`: Er ruft
  **kein** `mitD1Lock` (#32) auf und führt **kein** zweites Lock ein. Die Verkettung hier ist eine
  Reihenfolge-Garantie **innerhalb dieser Datei**, keine systemweite Sperre, keine OS-Dateisperre und
  kein Mutex-Objekt, das andere Module benutzen könnten.
- „**Seriell:** höchstens **ein** Auftrag in `laeuft`. Das ist der einzige Sperr-Mechanismus des
  Systems; ein zweites Lock ist nicht nötig und darf nicht eingeführt werden." (TK 9.3.5) –
  Vorlagen-Operationen sind **keine** Aufträge und laufen an der Warteschlange vorbei; die Verkettung
  hier ist deshalb kein Widerspruch, aber auch kein Ersatz für die serielle Auftragsordnung.
- „**Atomar:** Schreiben nach Temp-Datei + Rename (gleiche Partition). `project.json` ist **nie**
  halb geschrieben." (TK 9.5.4) – wörtlich über `project.json` gesagt; TK 9.12.1 erklärt genau diese
  Invarianten für `vorlagen.json` ausdrücklich für gültig.
- „**Ein Backup:** `project.json.bak` = letzte heile Version. Ist `project.json` beim Laden defekt →
  aus `.bak` wiederherstellen; ist auch das defekt → **Fehler melden**, **nicht**
  leer/verlustbehaftet weiterstarten." (TK 9.5.4) – analog entsteht genau **eine** Datei
  `vorlagen.json.bak`. Keine Generationen, keine Zeitstempel im Backup-Namen. Und analog wird aus ihr
  auch **gelesen**: Ein Backup, aus dem nie wiederhergestellt wird, wäre reine Schreiblast.
- „**Speicherfehler sind sichtbar (NFA-02):** Scheitert eine Auto-Speicherung (Platte voll, Rechte),
  wird das **nicht still verschluckt** – die UI zeigt dauerhaft „nicht gespeichert" + automatischer
  Wiederholversuch; die Änderungen **bleiben im Speicher** (kein Rollback, kein Arbeitsverlust). Erst
  nach erfolgreichem Schreiben verschwindet der Hinweis." (TK 9.5.4) – **Folge hier:** Scheitert ein
  entprellter Schreibvorgang, bleibt der Bestand im Speicher gültig; es gibt **kein** Rollback auf
  den Dateistand. Ein verschluckter Fehler (leeres `catch`, `ok: true` trotz Fehlschlag) ist der
  schwerste denkbare Verstoss in dieser Datei. **Wie** der Nutzer davon erfährt, ist offen – s.
  „Nicht selbst entscheiden".
- „**Instant-Op vs. Speichern getrennt:** Eine Instant-Operation (9.5.2) validiert und wendet **im
  Speicher** an, *bevor* sie „ok" meldet – ihr Erfolg bedeutet „gültig übernommen", **nicht** „schon
  auf Platte". Die Platten-Schreibung ist die entprellte Auto-Speicherung." (TK 9.5.4) – das ist
  genau die Bedeutung von `schreibart: 'entprellt'`.
- „**Entprellt 3–5 s** nach der letzten Änderung (kein Platten-Hämmern beim Slider-Ziehen)."
  (TK 9.5.4) und „**Auto-Speichern trifft nur die Arbeitskopie.** Während des Bearbeitens wird
  entprellt gesichert (3–5 s, wie 9.5.4)" (TK 9.12.1). **ENTSCHIEDEN: 4000 ms** – die Mitte des
  vorgegebenen Bereichs. Der genaue Wert innerhalb von 3–5 s ist fachlich gleichgültig; wichtig ist
  allein, dass es **eine** Zahl an **einer** Stelle ist. Sie steht als benannte Konstante in dieser
  Datei und wird **nicht** aus dem `project-store` (#47) importiert: Die beiden Entprellungen
  bewachen verschiedene Dateien und dürfen unabhängig voneinander geändert werden.
- „Jede `project.json` und `config.json` trägt eine `schemaVersion`. Beim Laden: **höhere**
  (unbekannte) Version → Fehler (nicht raten); **ältere** Version → definierte Migration auf die
  aktuelle. So bleiben ältere Projekte nach App-Updates lesbar." (TK 9.5.5) – für `vorlagen.json`
  gilt dieselbe Regel; da es bisher nur die Version 1 gibt, existiert **keine** Migration, und jede
  abweichende Version ergibt `speicher_fehler`.
- „**Eingebaute Vorlagen sind unlöschbar und eingefroren:** Layout-Änderungen an einer eingebauten
  Vorlage werden **nicht in-place** vorgenommen, sondern als **neue Vorlagen-ID** ausgeliefert. Sonst
  sähen Aktionen in bestehenden Projekten nach einem App-Update plötzlich anders aus."
  (TK 9.11.1.1) – **Folge für das Ergänzen in Schritt 6:** Nur **fehlende** IDs werden angehängt. Ein
  vorhandener Eintrag mit der ID `vollbild` wird **nicht** mit der aktuellen Fassung aus M4-02
  überschrieben, auch wenn er davon abweicht. Ein „Reparieren beim Start" wäre exakt die verbotene
  In-place-Änderung.
- „**Vorlagen sind app-weit** – **eine** Bibliothek für **alle** Projekte (`vorlagen.json`, Abschnitt
  6). Das unterscheidet sie bewusst von **Medien** (pro Projekt, D2) und **Aktionen** (Bibliothek pro
  Projekt)." (TK 9.11.1.1) – diese Datei kennt **keine** `projektId` und **keinen** `projects/`-Pfad.
- Die Ergebnis-Hülle lautet wörtlich (TK 9.1.1):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
  Diese Funktionen werfen **nie**; jeder Ausgang ist eine Hülle. Der Grund steht im Vertrag: Renderer
  und Main sind getrennte Prozesse, ein `throw` verliert Fehlerklasse und `code`, übrig bleibt Text.
- **Fehlende Datei ist kein Fehler.** Beim allerersten Start existiert `vorlagen.json` nicht; die
  Erstbenutzung darf nicht als Defekt erscheinen. Sie wird mit dem Anfangsbestand angelegt.
- **Defekte Datei: erst `.bak`, dann Fehler – nie der Anfangsbestand.** Ein `JSON.parse`-Fehler, ein
  abgeschnittener Inhalt oder eine unlesbare Datei führt zuerst zu einem Leseversuch auf
  `vorlagen.json.bak`. Fehlt der oder ist er ebenfalls defekt, ergibt das `speicher_fehler`. Ein
  stiller Rückfall auf `eingebauteVorlagen()` würde **alle eigenen Vorlagen des Nutzers vernichten** –
  der Anfangsbestand gilt **ausschliesslich** für die fehlende Datei.
- **Die Wiederherstellung aus `.bak` repariert nichts von selbst.** Der Inhalt wird gelesen und
  verwendet; die defekte `vorlagen.json` wird dabei **nicht** gelöscht und **nicht** durch das Backup
  ersetzt. Das Zurückschreiben geschieht erst beim nächsten regulären Schreibvorgang.
- **Nach einer Wiederherstellung darf das heile `.bak` nicht überschrieben werden.** Der erste
  Schreibvorgang nach einer `.bak`-Wiederherstellung überspringt den Kopierschritt; erst wenn wieder
  eine heile `vorlagen.json` auf der Platte liegt, wird erneut nach `.bak` kopiert. Andernfalls
  vernichtet ausgerechnet die Rettung die einzige heile Fassung – und zwar bevor die neue Fassung
  überhaupt geschrieben ist.
- **`ladeBestand` und `aendereBestand` teilen sich eine Kette, und der Erstladevorgang findet
  höchstens einmal statt.** Ein Laden ausserhalb der Kette könnte einen Bestand liefern, den eine
  gleichzeitig laufende Änderung gerade überholt; zwei parallele Erstladevorgänge legen den
  Anfangsbestand doppelt an und schreiben ihn doppelt. Deshalb wird das Promise eines laufenden
  Ladens geteilt statt ein zweites zu starten.
- **Der Bestand verlässt diese Datei nur als tiefe Kopie**, und `aenderung` bekommt ebenfalls eine
  tiefe Kopie. Andernfalls könnte ein Aufrufer den zwischengespeicherten Bestand hinter dem Rücken
  dieser Datei verändern – die Änderung wäre wirksam, ohne je geschrieben zu werden, und ein späterer
  Absturz liesse sie verschwinden.
- **Keine Kenntnis über den Inhalt aufbauen.** Diese Datei prüft **nicht**, ob eine Vorlage gültig
  ist, ob Zonen innerhalb der Fläche liegen, ob `höhe` zur `art` passt oder ob feste Zonen verändert
  wurden. Sie kennt `parent` und `eingebaut` nur insoweit, als sie fehlende eingebaute IDs ergänzt.
  Alle fachlichen Regeln gehören den Operationen (M4-05 bis M4-14).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `ladeBestand`: `vorlagen.json` fehlt | – | **kein Fehler**: Anfangsbestand aus `eingebauteVorlagen()`, Datei wird angelegt |
| `ladeBestand`: Inhalt kein gültiges JSON, `.bak` ist gültiges JSON | – | **kein Fehler**: Inhalt des `.bak` wird Bestand; die defekte Datei bleibt unverändert liegen |
| `ladeBestand`: Inhalt kein gültiges JSON, `.bak` fehlt oder ist ebenfalls defekt | `speicher_fehler` | kein Rückfall auf den Anfangsbestand; Meldung nennt den Pfad, keine Exception-Rohmeldung als Code |

| `ladeBestand`: `vorlagen` fehlt oder ist kein Array | `speicher_fehler` | wie „nicht parsebar" behandelt (erst `.bak`, dann Fehler) |

| `ladeBestand`: Anlegen bzw. Ergänzen schlägt beim Schreiben fehl | `speicher_fehler` | Bestand wird **nicht** zwischengespeichert; der nächste Aufruf versucht es erneut |
| `aendereBestand`: `aenderung` liefert `ok: false` | der Code aus `aenderung` | **nichts** wird geschrieben, der Bestand im Speicher bleibt unverändert; der Code wird unverändert durchgereicht |
| `aendereBestand`: `aenderung` wirft eine Ausnahme | `unbekannter_fehler` | wie oben: nichts geschrieben, Bestand unverändert; kein Stacktrace nach aussen |
| `aendereBestand`/`flushBestand`: I/O-Fehler beim Kopieren nach `.bak` | `speicher_fehler` | ob der Vorgang abbricht oder trotzdem geschrieben wird, ist offen – s. „Nicht selbst entscheiden" |
| `aendereBestand`/`flushBestand`: I/O-Fehler beim Schreiben von `.tmp` (Platte voll, Rechte) | `speicher_fehler` | Zieldatei bleibt unverändert (das Rename fand nie statt); `.tmp`-Rest wird aufgeräumt; der Bestand **bleibt im Speicher** (kein Rollback, TK 9.5.4) |
| `aendereBestand`/`flushBestand`: Rename schlägt fehl (`EBUSY`/`EPERM` unter Windows) | `speicher_fehler` | Zieldatei bleibt unverändert; ob vorher ein Retry+Backoff läuft, s. „Nicht selbst entscheiden" |
| `flushBestand`: es steht nichts aus | – | **kein Fehler**: `{ ok: true, wert: undefined }`, keine Datei wird angefasst |
| unerwartete Ausnahme irgendwo im Ablauf | `unbekannter_fehler` | wird gefangen und als Hülle gemeldet, **kein** Stacktrace nach aussen, kein `throw` |

## Nicht selbst entscheiden – STOPP und fragen
- **Rename-mit-Ersetzen ist plattformabhängig.** Der Vertrag stellt das ausdrücklich fest:
  „**Rename-mit-Ersetzen plattformsicher:** Das atomare Ersetzen verhält sich auf Windows anders als
  auf POSIX; die Umsetzung muss ein **Ersetzen** garantieren, ohne die alte Datei vor Fertigstellung
  der neuen zu entfernen." (TK 9.6.3) Für den USB-Export ist die Antwort vorgezeichnet – „**Atomar
  ersetzen:** `.part` → `<dateiname>` per Rename-mit-Ersetzen. Auf Windows bei `EBUSY`/`EPERM`
  **Retry+Backoff**." (TK 9.6.2) –, für `vorlagen.json` nicht. **Dies ist dieselbe offene Frage wie
  bei #31 (`config.json` atomar schreiben), #46 (`project.json` atomar schreiben) und #69 (die
  Queue-Dateien).** Falls dort bereits eine Lösung feststeht: **exakt dieselbe verwenden.** Sonst
  gemeinsam klären – vier unterschiedliche Workarounds für dasselbe Problem sind das schlechteste
  aller Ergebnisse. **Nicht selbst erfinden.**
- **Ist ein `fsync` vor der Erfolgsmeldung nötig?** Für den Export ist es entschieden: „**`fsync` vor
  Erfolg:** Erst wenn die Bytes physisch auf dem Stick sind, gilt der Export als fertig – ein sofort
  abgezogener Stick verliert so keine gepufferten Daten." (TK 9.6.3) Für `project.json` (TK 9.5.4)
  und für `vorlagen.json` (TK 9.12.1) nennt der Vertrag es **nicht**. Zu klären ist, ob die
  `.tmp`-Datei vor dem Rename ge-`fsync`t wird und ob zusätzlich der Verzeichnis-Eintrag ge-`fsync`t
  werden muss. **Nicht stillschweigend weglassen** – der Datenort kann bei der portablen Auslieferung
  auf einem USB-Stick liegen, und dort ist genau dieser Fall real. **Gleiche Antwort wie #31, #46,
  #69 verwenden.**
- **Verhalten, wenn das `.bak`-Kopieren fehlschlägt.** Bricht der ganze Schreibvorgang ab (keine neue
  Fassung ohne frisches Backup) oder wird trotzdem geschrieben (die neuen Daten haben Vorrang, `.bak`
  bleibt veraltet)? Der Vertrag entscheidet das weder in TK 9.5.4 noch in TK 9.12.1, und beide
  Varianten haben eine echte Konsequenz. **Dieselbe Frage stellt sich in #31, #46 und #69** –
  dieselbe Antwort verwenden.
- **Wie erfährt die Oberfläche von einem gescheiterten ENTPRELLTEN Schreibvorgang?** Das ist eine
  echte Lücke im Vertrag. Beim `project-store` ist der Weg gebaut: #47 sendet ein Ereignis
  (`project:autoSpeichernStatus`, `{ typ: 'gespeichert' } | { typ: 'fehler'; code }`), aus dem die
  `app-shell` den dauerhaften „nicht gespeichert"-Hinweis baut. Für den `vorlagen-store` nennt
  TK 9.12.1 **kein** Ereignis und **keinen** Kanal – der Aufrufer von `aendereBestand(…,
  'entprellt')` hat sein `ok` längst bekommen, wenn der Schreibvorgang scheitert, und niemand erfährt
  davon. Das verletzt NFA-02 („Speicherfehler sind sichtbar"). Zu klären: ein eigenes Ereignis
  `vorlagen:autoSpeichernStatus` analog zu #47 (dann gehört es in die Kanal-Registry #25 und in die
  IPC-Verdrahtung M4-15), oder eine Mitbenutzung des bestehenden Kanals, oder ein automatischer
  Wiederholversuch ohne Anzeige. **Nicht selbst erfinden** – die Antwort legt einen IPC-Kanal fest
  und betrifft M4-15 und die `app-shell` (M7).
- **Verbot – kein zweites Lock.** Kein `mitD1Lock` (#32), keine OS-Dateisperre, kein exportierter
  Mutex. Die Verkettung bleibt privat in dieser Datei.
- **Verbot – kein Aufräumen erfinden.** Kein Löschen alter `.bak`-Dateien, keine Rotation, keine
  Kompaktierung, kein „verwaiste Arbeitskopien beim Laden entfernen" (das ist M4-14 und passiert
  nicht beim Laden).
- **Verbot – keine fachliche Prüfung.** Diese Datei validiert **keine** Vorlage: nicht die `höhe`,
  nicht die Zonen-Rahmen, nicht `art`, nicht die festen Zonen, nicht `parent`. Auch nicht „nur schnell,
  damit nichts Kaputtes in die Datei kommt" – die Prüfungen sitzen in M4-06 bis M4-14, und eine
  zweite, abweichende Prüfung hier wäre eine zweite Quelle der Wahrheit.

## Definition of Done
- [ ] `ladeBestand` legt bei fehlender `vorlagen.json` eine Datei mit genau den drei eingebauten
      Vorlagen an und liefert sie zurück
- [ ] `ladeBestand` ergänzt in einer vorhandenen Datei, in der `band-standard` fehlt, genau diese
      eine Vorlage – **hinten angehängt** – und lässt einen bereits vorhandenen, absichtlich
      abgeänderten Eintrag `vollbild` **byte-identisch** stehen (eigener Test)
- [ ] `ladeBestand` liefert bei ungültigem JSON **ohne** brauchbares `.bak` `speicher_fehler` – und
      **nicht** den Anfangsbestand (eigener Test mit absichtlich abgeschnittenem Inhalt)
- [ ] `ladeBestand` liefert bei ungültigem JSON **mit** gültigem `.bak` dessen Inhalt; die defekte
      `vorlagen.json` ist danach byte-identisch zu vorher (Test vergleicht den Inhalt)
- [ ] `ladeBestand` liefert bei `schemaVersion: 2` `speicher_fehler` und lädt nichts
- [ ] `VORLAGEN_SCHEMA_VERSION` ist als `1` exportiert; die Datei importiert weder
      `AKTUELLE_SCHEMA_VERSION` (#21) noch `QUEUE_SCHEMA_VERSION` (#69) – Grep-Probe
- [ ] Nach einem erfolgreichen Schreibvorgang enthält `vorlagen.json.bak` genau den vorherigen
      Dateiinhalt und `vorlagen.json` den neuen
- [ ] Nach einer `.bak`-Wiederherstellung (defekte `vorlagen.json`, gültiges `.bak`) ist das `.bak`
      beim nächsten Schreibvorgang **unverändert** – der defekte Inhalt landet nie darin (eigener
      Test); erst der übernächste Schreibvorgang legt wieder ein frisches `.bak` an
- [ ] Zwei gleichzeitig gestartete `ladeBestand`-Aufrufe auf einem leeren Datenort legen die Datei
      **einmal** an: Der Schreib-Zähler steht danach auf 1 und beide Aufrufer bekommen denselben
      Bestand (Test ohne dazwischenliegendes `await`)
- [ ] Ein simulierter Abbruch während des `.tmp`-Schreibens hinterlässt `vorlagen.json` unverändert
- [ ] Zwei ohne dazwischenliegendes `await` gestartete `aendereBestand`-Aufrufe, die beide je eine
      Vorlage anhängen, ergeben am Ende **beide** Vorlagen im Bestand – nie nur eine (Test; das ist
      der Lost-Update-Nachweis)
- [ ] Eine `aenderung`, die `ok: false` liefert, hinterlässt die Datei unverändert und der Bestand im
      Speicher ist unverändert (Test lädt danach erneut)
- [ ] Eine `aenderung`, die wirft, ergibt `unbekannter_fehler`, ändert nichts und wirft nicht nach
      aussen
- [ ] Nach `aendereBestand(…, 'entprellt')` ist die Datei unmittelbar danach noch **nicht** geändert;
      nach `flushBestand()` ist sie es (Test ohne Warten auf den Timer)
- [ ] Ein `aendereBestand(…, 'sofort')` nach einer noch ausstehenden entprellten Änderung schreibt
      **beide** Änderungen und lässt danach keinen Timer laufen (Test)
- [ ] Der von `ladeBestand` gelieferte Bestand ist eine tiefe Kopie: Eine Änderung an
      `bestand[0].zonen[0].rahmen.x` ist beim nächsten `ladeBestand` nicht sichtbar
- [ ] Die Datei enthält keine fachliche Prüfung und keinen Aufruf eines D1-Locks – Grep-Probe auf
      `mitD1Lock`
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze)
- [ ] Keine Datei außerhalb von `src/main/vorlagen-store/schreibe-vorlagen.ts` (+ zugehörige
      Testdatei) geändert
