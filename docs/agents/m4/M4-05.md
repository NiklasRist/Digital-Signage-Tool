### Issue M4-05: [vorlagen-store] listeVorlagen und listeArbeitskopien implementieren

## Ziel (in einem Satz)
Die Oberfläche bekommt zwei klar getrennte Listen: die **nutzbaren** Vorlagen, aus denen `composer`
und `action-editor` auswählen dürfen, und die **Arbeitskopien**, mit denen der Vorlagen-Editor eine
unterbrochene Bearbeitung fortsetzt.

## Modul & Datei
- Modul: `vorlagen-store` (Main)
- Datei: `src/main/vorlagen-store/liste.ts`
- Vertrag: Technisches Konzept **9.12.1** (Operations-Tabelle und Invarianten) – Quelle der Wahrheit
- Prozess/Speicher: V1 (`vorlagen.json`), nur lesend

## Warum das im Gesamtsystem wichtig ist
Diese Trennung ist eine **Sicherheitsschranke**, keine Bequemlichkeit. `listeVorlagen` ist die Liste,
aus der eine Aktion ihre `vorlagenId` und ein Listenelement seine `einblendung.bandVorlageId`
bekommt. Rutscht dort eine Arbeitskopie hinein, kann ein halbfertiges Layout – eine Zone, die der
Nutzer gerade zur Hälfte verschoben hat – in einen Render geraten und auf dem Fernseher im Studio
landen. Und weil eine Arbeitskopie später verworfen werden kann, hätte das Projekt danach eine
**verwaiste Referenz**: Der nächste Render bricht ab, und niemand versteht, warum eine Vorlage
verschwunden ist, die es sichtbar gab.

Umgekehrt ist `listeArbeitskopien` der einzige Weg, eine unterbrochene Bearbeitung wiederzufinden.
Fehlt sie oder liefert sie das Falsche, bleiben Arbeitskopien für immer in `vorlagen.json` liegen,
ohne dass der Nutzer je an sie herankommt.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/vorlagen-store/liste.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { Vorlage } from '../../shared/contracts/vorlage'
import type { VorlagenFehlercode } from './fehlercodes'
import { ladeBestand } from './schreibe-vorlagen'

// Fremde Aufrufe – vollstaendige Signaturen, damit hier nichts geraten wird:
//   M4-04: ladeBestand(): Promise<Ergebnis<Vorlage[], VorlagenFehlercode>>
//          // vollstaendiger Bestand als TIEFE Kopie: nutzbare Vorlagen UND Arbeitskopien
//   M4-03: type VorlagenFehlercode = 'vorlage_referenziert' | 'parent_eingebaut' | 'speicher_fehler'
//   M4-01: interface Vorlage { id: string; name: string; art: VorlagenArt; höhe: number | null
//                              parent: string | null; eingebaut: boolean; zonen: Zone[] }

/** Nur NUTZBARE Vorlagen: parent === null. Arbeitskopien erscheinen hier nicht. */
export async function listeVorlagen(): Promise<Ergebnis<Vorlage[], VorlagenFehlercode>>

/** Nur ARBEITSKOPIEN: parent !== null. Fuer „Bearbeitung fortsetzen". */
export async function listeArbeitskopien(): Promise<Ergebnis<Vorlage[], VorlagenFehlercode>>
```

Beide Funktionen sind **reine Filter** über `ladeBestand()`. Sie schreiben nichts, legen nichts an
und ändern nichts. Zusammen decken sie den Bestand **lückenlos und überschneidungsfrei** ab: Jede
Vorlage hat entweder `parent === null` oder `parent !== null`, und keine erscheint in beiden Listen.

**Die Reihenfolge ist die Reihenfolge im Bestand.** Es wird **nicht** sortiert – weder alphabetisch
noch nach `eingebaut` noch nach `art`. Begründung: Dieselbe Regel gilt bereits für die Zonen einer
Vorlage („**Kein** implizites Sortieren", TK 9.11.1 Punkt 2) und für `Project.liste` (TK 9.11.3).
Eine Sortierung hier wäre eine zweite, unsichtbare Ordnung neben der gespeicherten; will die
Oberfläche alphabetisch anzeigen, sortiert sie selbst. Weil M4-04 die drei eingebauten Vorlagen als
Anfangsbestand anlegt und fehlende **hinten** anhängt, stehen sie ohne weiteres Zutun am Anfang.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – | beide Funktionen nehmen keine Parameter | – |

Ausgang bei Erfolg: `Ergebnis<Vorlage[], VorlagenFehlercode>`. `listeVorlagen` liefert alle Einträge
mit `parent === null` (mindestens die drei eingebauten), `listeArbeitskopien` alle mit
`parent !== null` (oft eine leere Liste – das ist der Normalfall und **kein** Fehler).
Ausgang bei Fehler: `fehler.code` ist `speicher_fehler` (aus M4-03, durchgereicht von `ladeBestand`)
oder einer der generischen Codes `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler` aus
#12, die `Ergebnis` immer zulässt.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operations-Tabelle, wörtlich (TK 9.12.1):
  - „`listeVorlagen` | – → `Ergebnis<Vorlage[]>` – **nur nutzbare** (`parent = null`); Arbeitskopien
    erscheinen hier **nicht**"
  - „`listeArbeitskopien` | – → `Ergebnis<Vorlage[]>` (`parent ≠ null`) – für „Bearbeitung
    fortsetzen""
- „**Arbeitskopien (`parent ≠ null`) sind nicht auswählbar.** `composer` und `action-editor` bekommen
  sie nicht angeboten – halbfertige Vorlagen können nicht in einen Render geraten." (TK 9.12.1) –
  **das ist der Zweck von `listeVorlagen`.** Ein Filter, der „nur Arbeitskopien mit vollständigen
  Zonen" oder „auch Arbeitskopien, die der Nutzer angepinnt hat" durchlässt, hebt die Zusage auf.
- „**Zweck des `parent`-Feldes (und warum es genullt wird):** Das Feld `parent` ist **die
  Merge-Beziehung** – es sagt „diese Vorlage stammt von X und kann in X zurückgeschrieben werden"."
  (TK 9.12.1) – `parent` ist damit **das** Unterscheidungsmerkmal. **Nicht** `eingebaut`, **nicht**
  der Name, **nicht** ein zusätzliches Kennzeichen.
- „**Vorlagen sind app-weit** – **eine** Bibliothek für **alle** Projekte (`vorlagen.json`, Abschnitt
  6)." (TK 9.11.1.1) – beide Funktionen nehmen deshalb **keine** `projektId` und filtern **nicht**
  nach Projekt.
- „**Ausschreiben statt andeuten.** In **allen** Operations-Signaturen von Abschnitt 9 steht die
  Hülle **explizit** (`→ Ergebnis<Asset>`), nicht nur die Nutzlast." (TK 9.1.1) – deshalb
  `Promise<Ergebnis<Vorlage[], VorlagenFehlercode>>` und **nicht** `Promise<Vorlage[]>`.
- „**Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code." (TK 9.1.1, Punkt 7) – ein
  Lesefehler aus `ladeBestand` wird **durchgereicht**, nicht in eine leere Liste verwandelt. Eine
  leere Vorlagen-Liste sähe für den Nutzer aus wie „es gibt keine Vorlagen" und würde ihn dazu
  bringen, neue anzulegen, während die alten unversehrt auf der Platte liegen.
- **Kein Zugriff auf `fs`.** Der Dateizugriff läuft ausschliesslich über `ladeBestand` (M4-04). Ein
  `fs.readFile` in dieser Datei ist verboten.
- **Keine Zwischenspeicherung in dieser Datei.** Der Bestand wird bereits in M4-04 im Speicher
  gehalten; ein zweiter Zwischenspeicher hier würde nach einer Änderung veraltete Listen liefern.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `ladeBestand` meldet `speicher_fehler` (defekte Datei ohne brauchbares `.bak`, I/O-Fehler, falsche `schemaVersion`) | `speicher_fehler` | unverändert durchgereicht; **keine** leere Liste als Ersatz |
| Bestand enthält keine Vorlage mit `parent !== null` | – | **kein Fehler**: `{ ok: true, wert: [] }` – der Normalfall, wenn gerade nichts bearbeitet wird |
| Bestand enthält keine Vorlage mit `parent === null` | – | **kein Fehler**: leere Liste. Praktisch unmöglich, weil M4-04 die drei eingebauten Vorlagen ergänzt; hier wird trotzdem **nichts** repariert und **nichts** nachgelegt |
| unerwartete Ausnahme | `unbekannter_fehler` | wird gefangen und als Hülle gemeldet, kein `throw` |

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – keine Sortierung, keine Gruppierung, keine Anzeige-Aufbereitung.** Kein `sort` nach
  Name, `art` oder `eingebaut`, keine „eingebaute zuerst"-Umordnung, kein Anhängen eines
  Anzeige-Namens wie „Arbeitskopie von X". Die Oberfläche gestaltet; dieses Modul liefert Daten in
  Bestandsreihenfolge.
- **Verbot – nicht nach `art` filtern.** Dass `composer` und `action-editor` „jeweils nur die passende
  Art" anbieten (TK 9.11.1, Punkt 0), erledigt die **Oberfläche**. Eine Filterung hier bräuchte einen
  Parameter, den die Vertragstabelle nicht kennt, und es gäbe zwei Stellen mit derselben Regel.
- **Verbot – nichts reparieren.** Findet sich eine Arbeitskopie, deren `parent` auf eine nicht mehr
  existierende Vorlage zeigt, wird sie hier **weder** korrigiert **noch** ausgeblendet. Das Nullen
  verwaister `parent`-Verweise ist ausschliesslich M4-14. Eine zweite Stelle, die dasselbe „nebenbei"
  tut, macht die Ursache eines Fehlers unauffindbar.
- **Verbot – keine dritte Listenfunktion erfinden.** Kein `listeAlle`, kein `findeVorlage(id)`, kein
  `existiertVorlage`. Wer eine einzelne Vorlage braucht, lädt den Bestand über M4-04 – so bleibt
  sichtbar, wer den Bestand anfasst.
