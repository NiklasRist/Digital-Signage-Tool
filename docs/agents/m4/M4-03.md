### Issue M4-03: [vorlagen-store] Fehlercode-Union des Moduls definieren

## Ziel (in einem Satz)
Der `vorlagen-store` besitzt eine eigene, geschlossene Fehlercode-Union, sodass jede seiner
Operationen einen typisierten Code liefert statt einer Textmeldung – und die Oberfläche eine
blockierte Löschung von einem Schreibfehler unterscheiden kann.

## Modul & Datei
- Modul: `vorlagen-store` (Main)
- Datei: `src/main/vorlagen-store/fehlercodes.ts`
- Vertrag: Technisches Konzept **9.12.1** (die Operationen und ihr Fehlerverhalten), **9.1.1**
  Punkt 3 (geschlossener Satz) – Quelle der Wahrheit
- Prozess/Speicher: V1; kein Speicherzugriff (reine Typdatei)

## Warum das im Gesamtsystem wichtig ist
An diesen Codes hängt **echtes Verhalten**, nicht nur eine Meldung. `vorlage_referenziert` führt in
der Oberfläche zur Anzeige beider Trefferlisten („wird von 7 Aktionen in 2 Projekten verwendet",
TK 9.12.2) – der Nutzer sieht, **was** er zuerst aufräumen muss. `parent_eingebaut` führt zu der
Erklärung, dass eingebaute Vorlagen eingefroren sind und nur „als neue eigenständige Vorlage"
gespeichert werden können. `speicher_fehler` führt zum dauerhaften „nicht gespeichert"-Hinweis und
zum automatischen Wiederholversuch (NFA-02). Degradieren diese drei zu einem gemeinsamen „irgendwas
ist schiefgelaufen", steht der Nutzer vor einer Vorlage, die sich nicht löschen lässt, und erfährt
nicht, warum.

Zweitens ist diese Datei der Ort, der verhindert, dass jedes M4-Issue seine eigenen Codes erfindet.
Neun spätere Operationen des Moduls liefern Fehler; schreiben sie ihre Codes je selbst als
String-Literal hin, weicht früher oder später eine Schreibweise ab (`vorlageReferenziert` in
camelCase, `vorlage_referenzieren` als Tippfehler), und der Aufrufer, der auf den Code prüft, trifft
ihn nicht mehr. Der Fehler ist dabei **nicht sichtbar**: Der Ablauf läuft, nur der Sonderfall greift
nicht mehr – die Vorlage wird korrekt blockiert, aber die Oberfläche zeigt keine Trefferliste an.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/vorlagen-store/fehlercodes.ts

/**
 * Fachliche Fehlercodes des vorlagen-store (TK 9.12.1).
 *
 * Die drei generischen Codes (ungueltige_eingabe, nicht_gefunden, unbekannter_fehler) stehen hier
 * BEWUSST NICHT – sie kommen ueber den zweiten Typparameter von Ergebnis (#22) automatisch dazu.
 * Eine Wiederholung erzeugte zwei Quellen fuer denselben Wert.
 */
export type VorlagenFehlercode =
  | 'vorlage_referenziert'
  | 'parent_eingebaut'
  | 'speicher_fehler'
```

Genau diese drei Werte. **Keine** zweite Union, **kein** Alias, **kein** `const`-Array „zum Prüfen".

**Fremde Typen, die du benutzt** (der umsetzende Agent sieht die anderen Issues nicht):

```ts
// #12 + #22 – src/shared/contracts/ergebnis.ts, bereits angelegt:
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'

export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }

// Der zweite Typparameter ist der Einhaengepunkt fuer DIESE Datei. Eine Operation schreibt danach
// z. B.:  Promise<Ergebnis<Vorlage, VorlagenFehlercode>>
// Die drei generischen Codes sind darin automatisch enthalten und werden hier NICHT wiederholt.
// `daten` ist das optionale Feld fuer strukturierte Fehlerdaten (TK 9.1.1); seine Form ist JE
// FEHLERCODE festgelegt und wird NICHT hier deklariert – s. Invariante zu vorlage_referenziert.
// Schreibweise beachten: Das TK nennt den Platzhalter `Fehlerdaten`; in `ergebnis.ts` steht
// `unknown` (#12) – die Form wird dort zugesichert, wo der Code vergeben wird.
```

**Wo jeder Code vergeben wird und was er bedeutet** (gehört als Kommentar bzw. Doku in die Datei):

| Code | Vergeben von | Ursache |
|---|---|---|
| `vorlage_referenziert` | `löscheVorlage` (M4-13) | Mindestens eine Aktion (`aktion.vorlagenId`) oder mindestens ein Listenelement (`listenelement.einblendung.bandVorlageId`) in **irgendeinem** Projekt zeigt noch auf die Vorlage. Trägt **beide** Trefferlisten in `daten` (TK 9.12.1). Blockierend, **nicht** kaskadierend. |
| `parent_eingebaut` | `uebernehmeInParent` (M4-09) | Der `parent` der Arbeitskopie ist eine eingebaute Vorlage; die ist eingefroren (TK 9.11.1.1). Der Nutzer muss stattdessen „als neue eigenständige Vorlage" wählen. |
| `speicher_fehler` | jede schreibende Operation, über M4-04 | `vorlagen.json` liess sich nicht lesen oder nicht schreiben (Platte voll, Rechte, defekte Datei ohne brauchbares `.bak`). |

**Warum die generischen Codes die restlichen Fälle abdecken** (damit niemand einen vierten Wert
erfindet): Eine unbekannte `id` oder `arbeitsId` ist `nicht_gefunden`. Eine ungültige Nutzlast –
`höhe` ausserhalb `> 0` und `< 1080`, eine Zone ausserhalb der Fläche, eine Textzone ohne
Text-Parameter, ein Versuch, `art` oder eine feste Zone zu ändern, ein leerer `name` – ist
`ungueltige_eingabe`; TK 9.1.1 Punkt 6 sagt dazu: „Der Main validiert jede eingehende Nutzlast – er
vertraut dem Renderer **nicht**. Ungültige Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf
die Daten." Alles Unerwartete ist `unbekannter_fehler`.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| – | reine Typdefinition, kein Laufzeit-Eingang | – |

Ausgang bei Erfolg: Jede Operation des `vorlagen-store` kann
`Ergebnis<T, VorlagenFehlercode>` schreiben und bekommt beim Typecheck exakt die Vereinigung aus den
drei fachlichen Codes und den drei generischen – nicht mehr, nicht weniger.
Ausgang bei Fehler: entfällt (Typdefinition, keine Laufzeit-Fehlerpfade).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Fehlercodes sind ein geschlossener, typisierter Satz:** die fachlichen je Operation (9.4.9,
  9.6.4, 9.12.1) plus die generischen `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler`.
  **Eine rohe Exception-Meldung wird nie zum Code.**" (TK 9.1.1, Punkt 3)
- „Bei uns hängt an den Codes **echtes Verhalten**: `asset_referenziert` zeigt die betroffenen
  Listenelemente, `vorlage_referenziert` beide Trefferlisten (9.12.1), `datei_zu_gross_fat32` erklärt
  exFAT, `kein_platz` und `ziel_gesperrt` brauchen verschiedene Hinweise. Geht der Code verloren,
  degradieren Reparatur-Modus, Wiederholen und der FAT32-Hinweis alle zu „irgendwas ist
  schiefgelaufen"." (TK 9.1.1) – deshalb ist der Code eine typisierte Konstante, nie ein freier
  String.
- Der Name `vorlage_referenziert` steht wörtlich im Vertrag: „`löscheVorlage` | `id` →
  `Ergebnis<void>`; im Fehlerfall Code `vorlage_referenziert` mit **beiden** Trefferlisten:
  betroffene **Aktionen** und betroffene **Listenelemente**, je mit Projekt" (TK 9.12.1). Er wird
  **exakt so** geschrieben – nicht `vorlage_in_benutzung`, nicht `vorlage_referenziert_von_aktion`.
- **ENTSCHIEDEN – `vorlage_referenziert` transportiert seine Nutzdaten im Feld `daten` der
  Ergebnis-Hülle.** Die Hülle führt dieses Feld ausdrücklich: „**Strukturierte Fehlerdaten (`daten`,
  optional).** Manche Fehler sind erst mit ihren Nutzdaten bedienbar: `asset_referenziert` muss die
  **betroffenen Listenelemente** nennen (`{ referenzenIds: string[] }`, 9.4.9),
  `vorlage_referenziert` beide Trefferlisten (9.12.1)." (TK 9.1.1) Es gibt dafür **keinen** Sondertyp
  und **keinen** Sonderkanal.
  **Folge für DIESE Datei:** Sie deklariert weiterhin **nur den Code**. Die Form von `daten` ist „je
  Fehlercode festgelegt und typisiert (dokumentiert dort, wo der Code vergeben wird: 9.4.9, 9.6.4,
  9.12.1)" (TK 9.1.1) – vergeben wird `vorlage_referenziert` in M4-13, dort wird das Objekt gefüllt.
  Hier entsteht **kein** Typ `VorlagenReferenzFehler`, **kein** `Fehlerdaten`-Alias und **keine**
  Zuordnungstabelle Code → Datenform.
- **Muster aus #22 (verbindlich):** Fachliche Module deklarieren ihre eigene Union in ihrer eigenen
  Datei; `src/shared/contracts/ergebnis.ts` wird dafür **nicht** angefasst. Wörtlich aus #22:
  „Fachliche Module deklarieren ihre eigene Union in ihrer eigenen Datei" und „und re-exportieren sie
  hier NICHT automatisch – der Aufrufer einer bestimmten Operation importiert die konkrete
  Fehlercode-Union der jeweiligen Operation direkt".
- **Die generischen Codes werden hier NICHT wiederholt.** Weder `ungueltige_eingabe` noch
  `nicht_gefunden` noch `unbekannter_fehler` taucht in der Union auf – sie kommen über den
  `Ergebnis`-Typ automatisch dazu. Eine Wiederholung erzeugt zwei Quellen für denselben Wert.
  Insbesondere gilt: **`nicht_gefunden` ist ein generischer Code und gehört nicht in diese Union**,
  obwohl das Modul ihn häufig vergibt (unbekannte `id`, unbekannte `arbeitsId`).
- **Die Codes erreichen die Auftragsverwaltung, ohne durch `Fehlercode` (#12) zu müssen.**
  `HandlerErgebnis` ist seit #60 über seinen Fehlercode generisch: `HandlerErgebnis<F>` typisiert
  `fehler.code` als `F | GenerischerFehlercode`. Ein Vorlagen-Handler gibt seinen fachlichen Code
  also **unverengt** heraus. Es gibt hier nichts zu umgehen – **kein** `as Fehlercode`-Cast, **keine**
  Erweiterung von `ergebnis.ts`, **kein** Abbilden auf `unbekannter_fehler`. Der geschlossene Satz aus
  TK 9.1.1 Punkt 3 bleibt gewahrt: Er ist **je Operation** geschlossen und typisiert, nämlich dort,
  wo der Code **entsteht**.
- Diese Datei enthält **ausschliesslich Typen** – keine Laufzeit-Werte, keine Meldungstexte, keine
  Übersetzungstabelle Code → Klartext. Der Klartext für die Oberfläche entsteht später und woanders.

**ENTSCHIEDEN – warum `parent_eingebaut` dazugehört, obwohl TK 9.12.1 nur `vorlage_referenziert`
namentlich nennt.** Der Vertrag verlangt das Verhalten ausdrücklich: „**`uebernehmeInParent` ist
gesperrt, wenn der Parent eingebaut ist.** Eingebaute Vorlagen bleiben unveränderlich (9.11.1.1);
dort bleibt nur `alsEigenstaendige`. Der Editor macht das vorher sichtbar, statt beim Speichern zu
scheitern." (TK 9.12.1) Die Sperre muss im Store trotzdem greifen (TK 9.1.1 Punkt 6: der Main
vertraut dem Renderer nicht), und sie braucht einen unterscheidbaren Code: `ungueltige_eingabe` würde
dem Nutzer suggerieren, er habe etwas falsch eingegeben, obwohl seine Eingabe völlig korrekt ist –
nur der gewählte Weg ist für diese Vorlage nicht vorgesehen. Genau das ist der Unterschied, den
TK 9.1.1 mit „an den Codes hängt echtes Verhalten" meint.

**ENTSCHIEDEN – `speicher_fehler` ist kein neuer Code**, sondern derselbe, den TK 9.4.9 für den
`media-service` und TK 9.5.4 für den `project-store` bereits führt. Er steht hier, weil jede
Fehlercode-Union modul-lokal ist (Muster #22) – nicht, weil ein zweiter Fehlerbegriff entstünde.
