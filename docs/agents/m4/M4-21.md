### Issue M4-21: [template-canvas] Eine Bildzone zeichnen

## Ziel (in einem Satz)
Ein bereits dekodiertes Motiv steht danach in seiner Zone – bei `contain` vollständig sichtbar und
zentriert, bei `cover` flächenfüllend und mittig beschnitten – und ein fehlendes Motiv hinterlässt
keine leere Fläche, sondern einen unübersehbaren Platzhalter.

## Modul & Datei
- Modul: `template-canvas` (Renderer, geteilt)
- Datei: `src/renderer/template-canvas/zone-bild.ts`
- Vertrag: Technisches Konzept **9.10.7** (fehlendes Motiv), **9.11.1** (Zonen-Modell,
  `bild.einpassung`, die eingebauten Vorlagen) – Quelle der Wahrheit
- Prozess/Speicher: Renderer, reine Zeichenfunktion; **kein** IPC, **kein** Dateizugriff

## Warum das im Gesamtsystem wichtig ist
Das Motiv ist die Fläche, die auf dem 85-Zoll-Bildschirm am stärksten wirkt – und die einzige Zone,
in der eine falsche lokale Rechnung sofort **Inhalt vernichtet**: `cover` schneidet zu. Wird die
Einpassung verwechselt, verschwindet in der eingebauten Vorlage „Split" der Rand des Produkts, das
beworben werden soll; das Konzept schreibt dort ausdrücklich `contain` vor, „das ganze Produkt bleibt
sichtbar, kein Beschnitt" (TK 9.11.1). Wird das Seitenverhältnis nicht erhalten (etwa durch ein
`drawImage`, das das Bild einfach auf den Rahmen streckt), wirken Menschen auf Fotos breiter oder
schmaler – ein Fehler, den niemand als „Rechenfehler" erkennt, sondern als schlechtes Video.

Der zweite Grund ist die Diagnose: Ein Motiv kann **fehlen**, weil die Datei außerhalb der App
gelöscht wurde (`fehlt`-Asset, TK 9.4.7). Zeichnete diese Funktion dann einfach nichts, sähe die
Bildzone genauso aus wie ein bewusst leer gelassener Bereich – der `action-editor` könnte den Defekt
nicht zeigen (TK 9.8.5) und der geführte Reparatur-Modus (FA-19) hätte nichts, worauf er zeigen
kann. Deshalb ist der Platzhalter Pflicht.

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.** Genau die gegenteilige Regel („dann passt du den Aufruf
eben an") hat in der ersten Fassung dieses Meilensteins fünf Funktionen in je zwei Fassungen
gebracht, ohne dass es irgendwo aufgefallen wäre.

```ts
// M4-01 – src/shared/contracts/vorlage.ts (Ausschnitt)
export interface Zone {
  id: string
  rolle: 'fest' | 'frei'
  bindung: Bindung | null
  rahmen: { x: number; y: number; breite: number; höhe: number }   // ABSOLUTE Pixel
  ausrichtung: { horizontal: 'links' | 'mitte' | 'rechts'; vertikal: 'oben' | 'mitte' | 'unten' }
  wennLeer: 'leer' | 'ausblenden'
  bild?: { einpassung: 'contain' | 'cover' }
  // text?, deko? s. M4-20 / M4-22
}
```

**Der Ablauf-Rahmen, verbindlich – er gilt für beide Zweige (Motiv und Platzhalter):**

1. **Abbruchbedingungen zuerst.** Ist `zone.rahmen.breite` oder `.höhe` ≤ 0 oder nicht endlich, kehrt
   die Funktion **sofort** zurück – **ohne** `ctx.save()`, ohne Zeichenaufruf, ohne Platzhalter.
2. `ctx.save()` als **erste** Anweisung nach den Abbruchbedingungen.
3. Zeichnen: entweder das Motiv (Rechnungen unten) oder der Platzhalter.
4. `ctx.restore()` als **letzte** Anweisung – auf **jedem** Pfad, der nach Schritt 2 endet, auch bei
   einem gefangenen `drawImage`-Fehler und auch dann, wenn ein Teilschritt übersprungen wurde.

Es gibt damit **genau ein** `save()` und **genau ein** `restore()` je Aufruf. Grund: Diese Funktion
setzt `fillStyle`, `strokeStyle`, `lineWidth`, `font`, `textAlign`, `textBaseline` und die
Interpolationseinstellungen. Bleibt auch nur einer dieser Werte stehen, sieht die **nächste** Zone
anders aus – ein Fehler, der dort auftritt, wo er nicht verursacht wurde.

**Die beiden Rechnungen, verbindlich ausgeschrieben.** `iw`/`ih` sind `motiv.breite` und
`motiv.höhe`, `bild` ist `motiv.bild`; `x`, `y`, `rb`, `rh` sind `zone.rahmen.x/y/breite/höhe`.

**`contain` – ganzes Motiv sichtbar, kein Beschnitt** (Ziel-Rechteck wird kleiner als der Rahmen
oder gleich groß; das Motiv wird im Rahmen zentriert):

```
skalierung = Math.min(rb / iw, rh / ih)
zielBreite = iw * skalierung
zielHöhe   = ih * skalierung
zielX      = x + (rb - zielBreite) / 2
zielY      = y + (rh - zielHöhe)  / 2
ctx.drawImage(bild, zielX, zielY, zielBreite, zielHöhe)      // 5 Argumente
```

**`cover` – Fläche gefüllt, Beschnitt erlaubt** (der Rahmen wird vollständig bedeckt; überzähliger
Bildinhalt wird **mittig** weggeschnitten, indem ein Quell-Rechteck gewählt wird):

```
skalierung  = Math.max(rb / iw, rh / ih)
quellBreite = rb / skalierung        // sichtbarer Ausschnitt, in QUELLpixeln
quellHöhe   = rh / skalierung
quellX      = (iw - quellBreite) / 2
quellY      = (ih - quellHöhe)   / 2
ctx.drawImage(bild, quellX, quellY, quellBreite, quellHöhe, x, y, rb, rh)   // 9 Argumente
```

`cover` wird **über das Quell-Rechteck** gelöst, nicht über einen Beschnittbereich (`clip`) mit einem
übergroßen Ziel-Rechteck. Begründung (entschieden): Die 9-Argument-Form ist reine Arithmetik – sie
lässt sich mit einem Aufzeichnungs-Doppel Zahl für Zahl prüfen, hinterlässt keinen Kontext-Zustand
und kann nicht vergessen werden. Ein `clip` müsste zusätzlich gesichert und zurückgenommen werden;
wird das vergessen, bluten alle **folgenden** Zonen in dieses Rechteck.

**Nicht runden.** Weder `skalierung` noch die Ziel- und Quellwerte werden auf ganze Pixel gerundet.
Runden würde das Seitenverhältnis um bis zu einem Pixel verziehen, ohne irgendetwas zu gewinnen: Die
Werte gehen in **einen** Zeichenaufruf, dessen Ergebnis für Vorschau und Render dasselbe ist.

**Interpolation explizit setzen:** `ctx.imageSmoothingEnabled = true` und
`ctx.imageSmoothingQuality = 'high'`. Begründung (entschieden): Importierte Fotos sind regelmäßig
mehrere tausend Pixel breit und werden hier auf 960–1920 px herunterskaliert. Mit der
Voreinstellung (`'low'`) entsteht dabei sichtbares Aliasing an Kanten und Text im Foto – auf einem
85-Zoll-Gerät deutlich zu sehen. Der Wert wird **explizit** gesetzt und nicht der Voreinstellung
überlassen, damit eine künftige Chromium-Fassung das Ergebnis nicht stillschweigend verändert.

**Der Platzhalter** (`motiv.zustand === 'fehlt'`), verbindlich und bewusst nicht markenschön – er
ist eine **Defektanzeige**, kein Gestaltungselement:

1. Rahmenfläche vollständig füllen mit `loeseFarbe(marke, 'flaecheDunkel')`.
2. Umlaufender Strich, 4 px, `loeseFarbe(marke, 'akzent')`, um 2 px nach innen versetzt, damit er
   vollständig innerhalb der Zone liegt.
3. Zwei Diagonalen von Ecke zu Ecke, 4 px, `loeseFarbe(marke, 'akzent')`.
4. Beschriftung **„Bild fehlt"**, Farbe `loeseFarbe(marke, 'textAufDunkel')`,
   Schrift `schriftKurzform(loeseSchrift(marke, 'fliesstext'), größe)` mit
   `größe = Math.min(48, Math.max(16, Math.round(zone.rahmen.höhe / 8)))`.
   Gesetzt wird sie **exakt so**: `ctx.textAlign = 'center'`, `ctx.textBaseline = 'middle'`, und
   `ctx.fillText('Bild fehlt', zone.rahmen.x + zone.rahmen.breite / 2,
   zone.rahmen.y + zone.rahmen.höhe / 2)` – ohne `maxWidth`. Damit sitzt sie im geometrischen
   Mittelpunkt der Zone, unabhängig von der Schrift-Metrik; „mittig" ist damit eine nachrechenbare
   Zahl und keine Auslegungsfrage.

**Jeder dieser vier Schritte steht in einem eigenen `try`/`catch`.** `loeseFarbe` und `loeseSchrift`
**werfen** bei unbekannter Rolle – so ist es dort festgelegt, und Vorlagen und Marke kommen zur
Laufzeit aus Daten, die TypeScript nicht prüft. Diese Funktion darf aber **niemals** werfen. Im
`catch` wird deshalb **genau der betroffene Teilschritt übersprungen** (keine Ersatzfarbe, keine
Ersatzschrift, keine Systemschrift), die übrigen drei Schritte werden normal gezeichnet, und
`ctx.restore()` läuft trotzdem. Ein Platzhalter ohne Beschriftung ist immer noch eine sichtbare
Defektanzeige; ein geratenes Schwarz wäre dagegen von einer gestalteten Fläche nicht zu
unterscheiden.

Die Beschriftung folgt **nicht** den Textparametern der Zone (eine Bildzone hat keine) und geht
deshalb ausnahmsweise nicht durch `zeichneTextZone`. Das ist kein zweiter Zeichenpfad im Sinne von
TK 9.10.1: Es wird kein Inhalt der Aktion gezeichnet, sondern eine Fehlermeldung, und sie erscheint
nie im fertigen Video (s. u.).

**Ein Segment mit Platzhalter darf nie in den finalen Render – die Sperre sitzt aber nicht hier.**
Diese Funktion zeichnet den Platzhalter **immer**, wenn das Motiv fehlt, ohne Ausnahme und ohne
Schalter. Wer versucht, den Platzhalter „für den Render" zu unterdrücken, hebt genau die Sichtbarkeit
auf, wegen der es ihn gibt. Die Sperre gehört in den `composer` (Reparatur-Modus, M5).

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `ctx` | der 2D-Kontext des Segment-Canvas (M4-23) | wird nicht hier erzeugt; jede Zustandsänderung mit `save`/`restore` einklammern |
| `zone` | die zu zeichnende Bildzone | `zone.bild` **kann** fehlen (s. Fehlerpfade); `rahmen` wird unverändert verwendet |
| `motiv` | Ergebnis des Ladens aus M4-17 | `zustand: 'geladen'` → zeichnen, `zustand: 'fehlt'` → Platzhalter; ein dritter Zustand existiert nicht. Maße **nur** aus `motiv.breite`/`motiv.höhe` |
| `marke` | die gebündelte, read-only Marke (#52) | liefert die Platzhalter-Farben und -Schrift, ausschließlich über Rollen |

Ausgang bei Erfolg: Das Motiv bzw. der Platzhalter steht im Zonenrahmen; der Kontext ist in exakt
dem Zustand, in dem er hereinkam.
Ausgang bei Fehler: entfällt – diese Funktion kennt keine Fehlercodes (s. u.).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „Ist `aktion.bildRef` ein `fehlt`-Asset (9.4.7), zeichnet `template-canvas` einen **Platzhalter**
  an der Bildzone, damit der `action-editor` den Defekt zeigen kann (9.8.5). **Ein Segment mit
  Platzhalter darf nie in den finalen Render gelangen** – diese Sperre sitzt im `composer`
  (Reparatur-Modus 9.7.5), nicht hier." (TK 9.10.7)
- „**Bilder sind vor dem Zeichnen dekodiert.** Der Aufruf wartet auf das Motiv (geladen über
  `media://`, 9.5.7) – sonst entsteht ein Segment ohne Bild." (TK 9.10.3, Punkt 4) – das **Warten**
  erledigt M4-17 **vor** diesem Aufruf.
- „Kennt **keine** Dateisystem-Pfade – Motive kommen ausschließlich über `media://` (9.5.7)."
  (TK 9.10.8)
- Die Einpassung der eingebauten Vorlagen, wörtlich aus den Zonen-Tabellen (TK 9.11.1):
  - „Vollbild" / `motiv`: „`cover`; darf über die Inhaltsbox bluten"
  - „Split" / `motiv`: „**`contain`** – das ganze Produkt bleibt sichtbar, kein Beschnitt"
- „**Absolute Pixel** im Raster der Vorlagenart – keine Prozentwerte." (TK 9.11.1, Punkt 1) –
  `zone.rahmen` wird unverändert verwendet.
- „**Gleiche Eingabe → gleiches Bild.** Keine Zeit-, Zufalls- oder Zustandsabhängigkeit (keine
  Animation, kein Datum, kein `Math.random`)." (TK 9.10.3, Punkt 5)
- „**`devicePixelRatio` wird ignoriert** – feste Canvas-Backing-Größe entsprechend der Vorlagenart."
  (TK 9.10.3, Punkt 2) – in dieser Datei kommt `devicePixelRatio` nicht vor.
- **Das Seitenverhältnis des Motivs bleibt in beiden Einpassungen erhalten.** Es gibt keine
  Einpassungsart, die verzerrt; `drawImage(bild, x, y, rb, rh)` mit den Rahmenmaßen als Zielgröße
  ist deshalb **verboten**.
- **Der Kontext wird lückenlos wiederhergestellt** – zu jedem `ctx.save()` genau ein
  `ctx.restore()`, auch bei vorzeitigem Ende.
- **Niemals `throw`.** Diese Funktion läuft in einer Schleife über alle Zonen; eine Ausnahme würde
  das ganze Segment leer lassen – in der Vorschau und im Render.

## Fehlerpfade (vollständig)
Keine Fehlercodes (kein Rückgabewert, keine IPC-Grenze). Jede Ausnahmesituation endet in einem
definierten Zeichenergebnis:

| Situation | Verhalten |
|---|---|
| `motiv.zustand === 'fehlt'` | Platzhalter zeichnen (**kein** Fehler – der Normalfall dieses Zweigs) |
| `motiv.zustand === 'geladen'`, aber `motiv.breite` oder `motiv.höhe` ist 0, nicht endlich oder negativ | **Platzhalter** zeichnen – ein Bildobjekt ohne Maße ist nicht zeichenbar, und eine leere Fläche wäre wieder der unsichtbare Defekt |
| `loeseFarbe` oder `loeseSchrift` **wirft** (unbekannte Rolle) | Ausnahme fangen, **nur** den betroffenen Teilschritt überspringen (Fläche, Strich, Diagonalen oder Beschriftung), die übrigen normal zeichnen, `restore()` ausführen – **keine** Ersatzfarbe, **keine** Ersatzschrift |
| `zone.bild` fehlt (Vorlage bindet ein Bild, nennt aber keine Einpassung) | wie `einpassung: 'contain'` behandeln; **kein** Fehler, kein Platzhalter. Begründung: `contain` kann nie Inhalt abschneiden – der schadensärmere der beiden Werte |
| `zone.bild.einpassung` enthält einen unbekannten Wert | ebenfalls wie `'contain'` behandeln |
| `zone.rahmen.breite` oder `.höhe` ist ≤ 0 oder nicht endlich | nichts zeichnen (auch keinen Platzhalter – eine Zone ohne Fläche kann nichts anzeigen), **kein** `save`/`restore`, keine Ausnahme |
| `drawImage` wirft (verwaistes Bildobjekt) | die Ausnahme fangen und den Platzhalter zeichnen; die Ausnahme **nicht** weiterreichen; `restore()` läuft trotzdem |

- **Offen: Was gilt, wenn ein Motiv kleiner ist als seine Zone.** Bei `cover` wird ein 400×300-Foto

## Definition of Done

**Ohne Browser prüfbar** (Vitest, `ctx` als Aufzeichnungs-Doppel; `motiv` als von Hand gebautes
Objekt – `bild` darf ein beliebiger Platzhalterwert sein, weil die Maße aus `motiv.breite`/
`motiv.höhe` kommen):

- [ ] `contain`, Rahmen `0, 0, 960, 1080` (Zone `motiv` der eingebauten Vorlage „Split"),
      `motiv.breite = 1600`, `motiv.höhe = 1200` → `drawImage` mit **5** Argumenten und den Werten
      `(bild, 0, 180, 960, 720)`
- [ ] `cover`, Rahmen `0, 0, 1920, 1080` (Zone `motiv` der eingebauten Vorlage „Vollbild"),
      `motiv.breite = 1600`, `motiv.höhe = 1200` → `drawImage` mit **9** Argumenten und den Werten
      `(bild, 0, 150, 1600, 900, 0, 0, 1920, 1080)`
- [ ] `cover`, Rahmen `0, 0, 960, 1080`, Motiv 1920×1080 → `(bild, 480, 0, 960, 1080, 0, 0, 960, 1080)`
      – der Beschnitt liegt **mittig**, nicht am linken Rand
- [ ] Motiv und Rahmen mit gleichem Seitenverhältnis → `contain` und `cover` liefern dasselbe
      Ziel-Rechteck (kein Beschnitt, kein Rand)
- [ ] In beiden Einpassungen bleibt das Seitenverhältnis erhalten. Verglichen wird mit einer
      **Toleranz**, nicht auf Gleichheit: `Math.abs(zielBreite / zielHöhe - iw / ih) < 1e-9` bzw.

- [ ] `motiv = { zustand: 'fehlt' }` → kein `drawImage`, aber `fillRect` über den ganzen Rahmen,

- [ ] Wirft ein `loeseFarbe`-Doppel für **eine** der drei Rollen bzw. das `loeseSchrift`-Doppel, so

- [ ] `loeseFarbe` wird mit `marke` als **erstem** und der Rolle als **zweitem** Argument aufgerufen

### Was hier NICHT abgenommen wird (nur am Bild prüfbar)

Diese Punkte brauchen ein laufendes Fenster mit echten Fotos und einer echten Vorlage – also Dinge,
die dieses Issue nicht besitzt. Sie sind **keine** Abnahmekriterien hier, sondern gehören in die
Integrationsprüfung (M5). Sie stehen hier, damit sie nicht verlorengehen:

- Ein Hochkant-Foto in der Vorlage „Split" bleibt vollständig sichtbar (kein abgeschnittener Kopf),
  ein Querformat-Foto in der Vorlage „Vollbild" füllt die Fläche randlos.
- Der Platzhalter ist auf einen Blick als Defekt erkennbar und nicht mit einer gestalteten dunklen
  Fläche zu verwechseln.
- Ein 4000 px breites Foto wirkt in der Zone nicht verrauscht oder aliasing-behaftet (Wirkung der
  Interpolationseinstellung – nur am Bild beurteilbar).
