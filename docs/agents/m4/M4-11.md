### Issue M4-11: [vorlagen-store] verwerfeArbeitskopie – Bearbeitungsstand fallenlassen

## Ziel (in einem Satz)
Der Bearbeitungsstand einer Vorlage wird verworfen, indem **genau die Arbeitskopie** aus
`vorlagen.json` entfernt wird – die Vorlage, von der sie abgeleitet wurde, bleibt dabei
nachweislich unverändert.

## Modul & Datei
- Modul: `vorlagen-store` (Main)
- Datei: `src/main/vorlagen-store/verwerfe-arbeitskopie.ts`
- Vertrag: Technisches Konzept **9.12.1** (Operationstabelle, Arbeitskopie-Fluss, Invarianten –
  Quelle der Wahrheit), ergänzend **9.11.1** (Datenmodell `Vorlage`), **9.1.1** (IPC-Konventionen,
  Ergebnis-Hülle)
- Prozess/Speicher: V1 (`vorlagen.json`, app-weit). **Kein** direkter Dateizugriff – gelesen und
  geschrieben wird ausschließlich über M4-04. **Kein** D1-Zugriff, **kein** D1-Lock.

## Warum das im Gesamtsystem wichtig ist
Diese Funktion ist die kleinste des Moduls und zugleich die einzige, die **löscht, ohne vorher
irgendetwas zu prüfen** – und genau darin liegt ihre Gefahr. `löscheVorlage` (M4-13) darf einen
Eintrag erst entfernen, nachdem die Referenzprüfung über **alle** Projekte gelaufen ist; diese
Funktion entfernt sofort. Beides ist richtig, solange die Trennung hält: Eine Arbeitskopie ist „nicht
auswählbar" (TK 9.12.1) und kann deshalb von keiner Aktion und keinem Listenelement referenziert
werden – bei ihr ist Löschen ohne Prüfung gefahrlos.

Fällt die Trennung weg, ist der Schaden groß: Wird hier ein Eintrag mit `parent === null` akzeptiert
– etwa weil die Oberfläche eine falsche ID schickt oder weil jemand den Prüfschritt „spart" –, dann
verschwindet eine **genutzte** Vorlage an der Referenzprüfung vorbei. Die Aktionen, die auf sie
zeigen, behalten ihre `vorlagenId`, finden aber keine Vorlage mehr: Der `action-editor` kann sie
nicht mehr zeichnen, und der nächste Render bricht mit einer verwaisten Referenz ab – dem Fehlerbild,
das TK 9.12.1 ausdrücklich verhindern will. Die eine Zeile „nur wenn `parent ≠ null`" ist damit die
gesamte Sicherung dieser Datei.

Die zweite Stelle ist der Parent. „Verwerfen" heißt laut Konzept „alles zurück, X unverändert" –
wer beim Verwerfen am Parent noch etwas zurücksetzt, „aufräumt" oder ihn gar mitlöscht, zerstört
genau die Vorlage, die der Nutzer behalten wollte.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/vorlagen-store/verwerfe-arbeitskopie.ts

export async function verwerfeArbeitskopie(
  arbeitsId: string,
): Promise<Ergebnis<void, VorlagenFehlercode>>
// - entfernt GENAU den einen Eintrag mit id === arbeitsId, und nur wenn dessen parent ≠ null ist
// - fasst den Parent NICHT an und liest ihn nicht einmal
// - liefert bei Erfolg Ergebnis<void> – das gelungene `ok` IST die Information
// - laeuft vollstaendig in EINER aendereBestand(…, 'sofort')-Einheit (M4-04)
// - kein fs, kein Lock, kein IPC-Kanal (den meldet M4-15 an)
```

**Fremde Funktionen und Typen, die du benutzt** (der umsetzende Agent sieht die anderen Issues
nicht – deshalb hier vollständig ausgeschrieben):

```ts
// M4-01 – src/shared/contracts/vorlage.ts (geteilter Typ; hier NICHT neu deklarieren)
export interface Vorlage {
  id:        string                                        // UUID
  name:      string                                        // Anzeigename

  eingebaut: boolean                                       // true = mitgeliefert, eingefroren
  zonen:     Zone[]                                        // Zeichenreihenfolge = Array-Reihenfolge
}
// Der Aufbau von `Zone` ist für DIESE Funktion ohne Belang – gelesen wird nur `id` und `parent`.

export type VorlagenFehlercode = 'vorlage_referenziert' | 'parent_eingebaut' | 'speicher_fehler'

// den zweiten Typparameter von Ergebnis automatisch dazu und stehen bewusst NICHT in dieser Union.
// DIESE Funktion vergibt weder vorlage_referenziert noch parent_eingebaut (s. Fehlerpfade).

// M4-04 – src/main/vorlagen-store/schreibe-vorlagen.ts (der EINZIGE Dateizugriff des Moduls)
export async function aendereBestand<T>(
  aenderung: (bestand: Vorlage[]) => Ergebnis<{ bestand: Vorlage[]; wert: T }, VorlagenFehlercode>,
  schreibart: 'sofort' | 'entprellt',
): Promise<Ergebnis<T, VorlagenFehlercode>>
// - `aenderung` ist SYNCHRON und darf NICHT `await`en; genau das macht Lesen-Ändern-Schreiben zu
//   einer ununterbrechbaren Einheit
// - `aenderung` bekommt eine TIEFE KOPIE des Bestands und darf sie verändern
// - liefert `aenderung` ok:false, wird NICHTS geschrieben, der Fehler wird unverändert durchgereicht
// - 'sofort' -> die Datei ist geschrieben, BEVOR das Promise erfüllt wird
// - Aufrufe laufen streng nacheinander (verkettete Promise), auch die aus anderen Operationen

// #12/#22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
// Diese Funktion setzt `daten` NIE. Bei Erfolg lautet die Antwort { ok: true, wert: undefined }.
```

**`aendereBestand` ist der einzige Weg, `vorlagen.json` zu ändern; die Quelle dieser Signatur ist
M4-04.** Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein
**Vertragsfehler**: **melden und NICHT eigenmächtig anpassen.** Baue **keine** eigene
Zwischenlösung.

**Wer ruft dich auf:** der `vorlagen-editor` (Renderer) über den IPC-Kanal
`vorlagen:verwerfeArbeitskopie`, den **M4-15** anmeldet. Diese Datei kennt weder `ipcMain` noch den
Kanalnamen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `arbeitsId` | ID der Arbeitskopie, deren Stand fallengelassen wird | nicht leerer String; muss im Bestand stehen **und** dort `parent ≠ null` haben, sonst s. Fehlerpfade |

Ausgang bei Erfolg: `Ergebnis<void>` – der Bestand hat danach **einen** Eintrag weniger; alle
übrigen Einträge stehen unverändert und in unveränderter Reihenfolge.
Ausgang bei Fehler: `ungueltige_eingabe`, `nicht_gefunden`, `speicher_fehler` (geschlossener Satz,
s. Fehlerpfade). `vorlage_referenziert` entsteht hier **nie** – eine Arbeitskopie kann nicht
referenziert sein –, `parent_eingebaut` ebenso wenig (das ist der Code von M4-09).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operation, wörtlich (TK 9.12.1, Operationstabelle):
  ```
  | `verwerfeArbeitskopie` | `arbeitsId` → `Ergebnis<void>` |
  ```
- Der Arbeitskopie-Fluss, wörtlich (TK 9.12.1) – die letzte Zeile ist diese Funktion:
  ```
  Vorlage X bearbeiten
    └─ oeffneZurBearbeitung(X)  →  Arbeitskopie  (parent = X)
          └─ Bearbeiten  →  speichereArbeitskopie (AUTO, entprellt)   ← X bleibt unberührt
                ├─ uebernehmeInParent   →  Änderungen wandern in X, Arbeitskopie weg
                ├─ alsEigenstaendige    →  parent = null, neue eigene Vorlage entsteht
                └─ verwerfeArbeitskopie →  alles zurück, X unverändert
  ```
  „alles zurück, X unverändert" ist wörtlich zu nehmen: Am Parent wird **nichts** getan – auch
  nichts „Zurücksetzendes".
- „**Auto-Speichern trifft nur die Arbeitskopie.** Während des Bearbeitens wird entprellt gesichert
  (3–5 s, wie 9.5.4) – aber **ausschließlich** in die Arbeitskopie. Die genutzte Vorlage ändert sich
  **erst** beim expliziten `uebernehmeInParent` bzw. `alsEigenstaendige`. So kann Experimentieren
  **nie** laufende Werbung in anderen Projekten verändern." (TK 9.12.1) – deshalb gibt es beim
  Verwerfen am Parent nichts rückgängig zu machen: Er wurde nie verändert.
- „**Arbeitskopien (`parent ≠ null`) sind nicht auswählbar.** `composer` und `action-editor`
  bekommen sie nicht angeboten – halbfertige Vorlagen können nicht in einen Render geraten."
  (TK 9.12.1) – **das** ist der Grund, warum diese Funktion ohne Referenzprüfung löschen darf.
- „**Arbeitskopien blockieren das Löschen nicht** – sie sind kein „Benutzen". Wird der Parent
  gelöscht, wird deren `parent` genullt (s. u.)." (TK 9.12.1)
- „**Löschen erst, wenn keine Aktion in *keinem* Projekt die Vorlage mehr verwendet.** Blockiert wie
  beim Medium-Löschen (9.4.6), **nicht** kaskadierend – ein Layout-Verlust würde alle betroffenen
  Aktionen zerstören." (TK 9.11.1.1) – das gilt für **nutzbare** Vorlagen und ist der Grund, warum
  ein Eintrag mit `parent === null` hier **nicht** entfernt werden darf. Diese Funktion ist **kein**
  Nebeneingang zu M4-13.
- „**Besitzt** `vorlagen.json` (app-weite Vorlagen-Bibliothek) samt **eigener**
  Schreib-Serialisierung. Die Schreib-Invarianten sind **dieselben** wie in 9.5.4: **atomar**
  (Temp + Rename), **`vorlagen.json.bak`** als letzte heile Version, **`schemaVersion`**, und
  Speicherfehler werden **sichtbar** gemacht statt still verschluckt." (TK 9.12.1) – all das leistet
  **M4-04**.
- Die Ergebnis-Hülle (TK 9.1.1, Punkt 2):
  ```
  Ergebnis<T> =
    | { ok: true,  wert: T }
    | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
  ```
- „Wo eine Operation **nichts** zu melden hat, lautet die Nutzlast `void`: **`Ergebnis<void>`** – das
  gelungene `ok` **ist** die Information. **Verboten** sind Ersatzformen wie `Ergebnis<boolean>`,
  `Ergebnis<null>` oder ein blankes `true`." (TK 9.1.1, Punkt 2)
- „**Kein stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code. Es gibt keine Operation,
  die „einfach nichts" zurückgibt und auf Gelingen hofft." (TK 9.1.1, Punkt 7)
- „**Der Main validiert jede eingehende Nutzlast** – er vertraut dem Renderer **nicht**. Ungültige
  Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten." (TK 9.1.1, Punkt 6)

**Ablauf (verbindlich), vollständig innerhalb EINER `aendereBestand(…, 'sofort')`-Einheit.**
1. `arbeitsId` formal prüfen – sonst `ungueltige_eingabe` **ohne** jeden Bestandszugriff, also
   **vor** dem Aufruf von `aendereBestand`.
2. `aendereBestand(aenderung, 'sofort')` aufrufen. Die Änderungsfunktion ist **synchron** und darf
   **nicht** `await`en (M4-04).
3. In der Änderungsfunktion: Eintrag mit `id === arbeitsId` suchen; fehlt er → `nicht_gefunden`; hat
   er `parent === null` → `ungueltige_eingabe`. Beides wird als `ok: false` **aus der
   Änderungsfunktion heraus** gemeldet – dann schreibt M4-04 **nichts**.
4. Sonst: den Bestand ohne diesen einen Eintrag bilden (gefiltert nach `id !== arbeitsId`).
5. `{ ok: true, wert: { bestand: <neuer Bestand>, wert: undefined } }` zurückgeben.
6. `aendereBestand` schreibt und erfüllt sein Promise erst danach (`'sofort'`); dessen Ergebnis ist
   der Rückgabewert dieser Funktion.

**ENTSCHIEDEN – `'sofort'`, nicht `'entprellt'`.** Das Verwerfen ist eine bewusste, unumkehrbare
Nutzerhandlung; der Editor schließt danach die Bearbeitung. Wäre der Stand nur im Speicher, käme die
verworfene Arbeitskopie nach einem Absturz zurück und stünde wieder unter „Bearbeitung fortsetzen".
`'entprellt'` ist ausschließlich für das Auto-Speichern der Arbeitskopie (M4-08).

**ENTSCHIEDEN – eine unbekannte `arbeitsId` meldet `nicht_gefunden`, nicht stillen Erfolg (lokale
Entscheidung).** Es wäre vertretbar, das Verwerfen idempotent zu machen („war schon weg, also ok") –
so ist es beim Streichen eines Q2-Eintrags in der Auftragsverwaltung. Dort ist der Regelfall aber
das **routinemäßige** Aufräumen nach jedem erfolgreichen Auftrag; hier ist der Regelfall eine
**bewusste Nutzerhandlung** auf einem Eintrag, den der Editor gerade anzeigt. Kommt eine unbekannte
ID an, ist entweder die Liste des Editors veraltet oder die ID falsch – beides soll sichtbar werden,
statt als Erfolg zu erscheinen. Zusätzlich hält es die drei Arbeitskopie-Operationen (M4-09, M4-10,
dieses Issue) auf **einer** Regel: unbekannte ID → `nicht_gefunden`, existiert-aber-keine-Kopie →
`ungueltige_eingabe`. Zwei Nachschlage-Regeln in einem Modul wären eine Falle für jeden, der den
Renderer-Aufruf schreibt.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `arbeitsId` ist kein String oder leer | `ungueltige_eingabe` | keine Wirkung; `aendereBestand` wird **gar nicht** aufgerufen |
| `aendereBestand` kann den Bestand nicht laden | `speicher_fehler` | unverändert durchreichen; die Änderungsfunktion läuft gar nicht erst |
| keine Vorlage mit `id === arbeitsId` | `nicht_gefunden` | Abbruch aus der Änderungsfunktion heraus; es wird **nichts** geschrieben |
| Eintrag gefunden, aber `parent === null` (nutzbare Vorlage, keine Arbeitskopie) | `ungueltige_eingabe` | **keine Wirkung** – der Eintrag bleibt stehen. Das ist die zentrale Sicherung dieser Datei: Löschen einer nutzbaren Vorlage geht ausschließlich über M4-13 mit Referenzprüfung |
| das Schreiben in `aendereBestand` schlägt fehl | `speicher_fehler` | unverändert durchreichen; die Datei ist entweder vollständig alt oder vollständig neu (das sichert M4-04 zu) |

Fehlercodes werden **nicht erfunden**: „Fehlercodes sind ein geschlossener, typisierter Satz …
Eine rohe Exception-Meldung wird nie zum Code." (TK 9.1.1, Punkt 3)

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – niemals einen Eintrag mit `parent === null` entfernen.** Auch nicht „weil die ID ja
  stimmt", auch nicht mit Zusatzprüfung, auch nicht für Tests. Nutzbare Vorlagen löscht
  **ausschließlich** M4-13, und zwar erst nach der Referenzprüfung über alle Projekte. Eine zweite
  Löschtür ohne Prüfung wäre der direkte Weg zu verwaisten `vorlagenId`-Referenzen.
- **Verbot – den Parent nicht anfassen.** Kein Löschen, kein Zurücksetzen, kein Umbenennen, kein
  Setzen irgendeines Feldes, kein Vermerk „hatte mal eine Kopie". „alles zurück, X unverändert"
  (TK 9.12.1).
- **Verbot – nur dieser eine Eintrag.** Kein Entfernen weiterer Arbeitskopien desselben Parents,
  kein „Aufräumen" verwaister Kopien (das ist M4-14 und läuft ausschließlich im Zuge von M4-13),
  keine Altersprüfung, kein Aufräumen nach Datum. Gefiltert wird nach `id !== arbeitsId`.
- **Verbot – kein zweiter Schreibpfad, kein Dateisystem.** Kein `fs`, kein eigenes Temp/Rename,
  kein `.bak`, kein Verschieben in einen „Papierkorb". Ausschließlich `aendereBestand` (M4-04) – und
  **kein** `await` innerhalb der Änderungsfunktion. Kein `mitD1Lock` und **kein eigenes Lock**; auch
  **kein** `flushBestand()` (das gehört laut M4-04 dem Beenden der App, #3).
- **Verbot – keine Ersatzform für `void`.** Kein `Ergebnis<boolean>`, kein `Ergebnis<Vorlage>` mit
  dem gelöschten Eintrag, kein `wert: true`. TK 9.1.1 Punkt 2 verbietet das ausdrücklich, weil es
  sonst zwei Wege gäbe, „hat funktioniert" zu sagen.
- **Verbot – kein IPC, kein Ereignis.** Kein `ipcMain`, kein `BrowserWindow`, kein Eintrag in
  `kanaele.ts`, kein Kanalname als String. Der Kanal `vorlagen:verwerfeArbeitskopie` gehört
  **M4-15**.

## Definition of Done
- [ ] Erfolgsfall: Der Eintrag mit `id === arbeitsId` ist im geschriebenen Bestand nicht mehr
      enthalten; alle übrigen Einträge sind unverändert und stehen in unveränderter Reihenfolge
      (Deep-Vergleich des ganzen Arrays)
- [ ] Der Erfolgsfall liefert `{ ok: true, wert: undefined }` – kein `true`, kein `null`, kein
      gelöschter Datensatz als `wert`
- [ ] Der Parent-Eintrag ist danach **byte-gleich** wie vorher (Deep-Vergleich)
- [ ] Eine zweite Arbeitskopie **desselben** Parents bleibt im Bestand stehen (Test)
- [ ] Ein Eintrag mit `parent === null` liefert `ungueltige_eingabe` und steht danach **noch im
      Bestand**; die Änderungsfunktion liefert dabei `ok: false`, es wird nachweislich **nichts**
      geschrieben – auch dann nicht, wenn er `eingebaut: false` trägt
- [ ] Eine unbekannte `arbeitsId` liefert `nicht_gefunden` ohne Schreibvorgang
- [ ] `arbeitsId = ''` und ein Nicht-String liefern `ungueltige_eingabe`, und `aendereBestand` wurde
      nachweislich **nicht** aufgerufen (Spy: null Aufrufe)
- [ ] `aendereBestand` wird im Erfolgsfall **genau einmal** aufgerufen, mit
      `schreibart === 'sofort'` (Spy)
- [ ] Liefert `aendereBestand` `{ ok: false, fehler: { code: 'speicher_fehler', … } }`, kommt genau
      dieser Code beim Aufrufer an
- [ ] Die Änderungsfunktion ist **synchron**: Ihr Rückgabewert ist kein `Promise`, und sie enthält
      kein `await` (Test + Grep-Probe)
- [ ] Die Datei enthält kein `fs`, kein `ipcMain`, kein `BrowserWindow`, kein `mitD1Lock` und kein
      String-Literal `'vorlagen:'` (Grep-Probe)
- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze)
- [ ] Keine Datei außerhalb von `src/main/vorlagen-store/verwerfe-arbeitskopie.ts` **(+ zugehörige
