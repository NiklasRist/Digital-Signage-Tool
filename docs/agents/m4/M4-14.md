### Issue M4-14: [vorlagen-store] Verwaiste Arbeitskopien vom gelöschten Parent lösen

## Ziel (in einem Satz)
Wird eine Vorlage gelöscht, verlieren ihre Arbeitskopien im selben Zug ihr Feld `parent` (es wird
`null`) und werden damit zu eigenständigen Vorlagen – es bleibt **keine** Referenz auf einen
Datensatz zurück, den es nicht mehr gibt.

## Modul & Datei
- Modul: `vorlagen-store` (Main)
- Datei: `src/main/vorlagen-store/verwaiste-arbeitskopien.ts`
- Vertrag: Technisches Konzept **9.12.1** (Invariante „Eine Arbeitskopie hält den Parent nicht am
  Leben" – Quelle der Wahrheit), ergänzend **9.11.1** (Datenmodell `Vorlage`)
- Prozess/Speicher: V1 mittelbar. Diese Datei **hat keinen** Speicherzugriff: kein Dateisystem,
  keine Lese-, keine Schreibfunktion. Sie formt ein Array um, mehr nicht.

## Warum das im Gesamtsystem wichtig ist
Diese Funktion ist der Aufräumschritt, ohne den das Löschen einer Vorlage einen kaputten Datensatz
hinterlässt. Eine Arbeitskopie zeigt über `parent` auf die Vorlage, aus der sie entstanden ist. Wird
diese gelöscht und das Feld nicht genullt, entsteht eine Kopie, die auf nichts zeigt – mit drei
Folgen: „Vorlage überarbeiten" (M4-09) scheitert bei ihr dauerhaft mit `nicht_gefunden`, der Editor
zeigt einen Parent an, den es nicht gibt, und `listeVorlagen` (M4-05) blendet sie aus (sie hat ja
`parent ≠ null`), während `listeArbeitskopien` sie ewig unter „Bearbeitung fortsetzen" führt. Der
Nutzer hat dann Arbeit, an die er nicht mehr herankommt – und keinen Hinweis, warum.

Die entscheidende lokale Eigenschaft ist deshalb, **wann** und **wie** diese Umformung läuft: Sie
gehört in **denselben** Schreibvorgang wie das Löschen (M4-13). Wäre sie ein eigener Schreibvorgang,
gäbe es ein Zeitfenster, in dem die Vorlage schon weg und die Kopie noch angebunden ist – und wenn
der zweite Schreibvorgang scheitert oder die App dazwischen abstürzt, bleibt genau der verwaiste
Zustand dauerhaft stehen. Deshalb ist diese Funktion **synchron** und **ohne I/O**: Sie kann gar
nicht in Versuchung geraten, selbst zu speichern.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/vorlagen-store/verwaiste-arbeitskopien.ts

export function löseArbeitskopienVomParent(
  bestand: Vorlage[],
  parentId: string,
): Vorlage[]
// - SYNCHRON, rein: kein await, kein fs, kein Lesen, kein Schreiben, kein Ergebnis<T>
// - liefert ein NEUES Array gleicher Länge und gleicher Reihenfolge
// - jeder Eintrag mit parent === parentId wird durch ein NEUES Objekt mit parent: null ersetzt
// - jeder andere Eintrag wird UNVERÄNDERT durchgereicht (dieselbe Objekt-Referenz)
// - der Eintrag mit id === parentId bleibt unangetastet; ENTFERNT wird er von M4-13
// - mutiert weder das übergebene Array noch die darin enthaltenen Objekte
```

**Warum ohne Ergebnis-Hülle:** Die Hülle trägt Fehler über die IPC-Grenze („niemals Exceptions über
die Grenze", TK 9.1.1, Punkt 2). Diese Funktion ist main-intern, hat keinen Kanal, berührt kein
Dateisystem und **kann nicht fehlschlagen**; eine Hülle würde einen Fehlerzweig erzwingen, den
niemand jemals betritt – und der Aufrufer müsste ihn behandeln, als könnte etwas schiefgehen.

**Fremde Typen, die du benutzt** (der umsetzende Agent sieht die anderen Issues nicht – deshalb hier
vollständig ausgeschrieben):

```ts
// M4-01 – src/shared/contracts/vorlage.ts (geteilter Typ; hier NICHT neu deklarieren)
export interface Vorlage {
  id:        string                                        // UUID oder "vollbild"/"split"/"band-standard"
  name:      string                                        // Anzeigename
  art:       VorlagenArt                                   // Fläche + Kompositionsart
  höhe:      number | null
  parent:    string | null                                 // ≠ null → ARBEITSKOPIE; = null → nutzbar
  eingebaut: boolean
  zonen:     Zone[]                                        // Zeichenreihenfolge = Array-Reihenfolge
}
// Der Aufbau von `Zone` ist hier ohne Belang: Zonen werden nie gelesen und nie verändert.
```

**Wer ruft dich auf:** ausschließlich **M4-13** (`löscheVorlage`), main-intern, **zwischen** dem
Lesen des Bestands und dem einen Schreibvorgang – und erst, nachdem die Referenzprüfung (M4-12) das
Löschen freigegeben hat. Das Ergebnis dieser Funktion ist das Array, aus dem M4-13 anschließend den
gelöschten Eintrag herausfiltert und das es dann **einmal** schreibt. Diese Datei bekommt **keinen**
IPC-Kanal.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `bestand` | der vollständige, gerade gelesene Inhalt von `vorlagen.json` (nutzbare Vorlagen **und** Arbeitskopien) | wird **nicht** verändert; ist er leer, ist das Ergebnis ein leeres Array |
| `parentId` | ID der Vorlage, die gerade gelöscht wird | ist er kein nicht leerer String, wird der Bestand unverändert (als neues Array) zurückgegeben – die Eingabeprüfung macht M4-13, s. u. |

Ausgang: ein **neues** Array `Vorlage[]` – gleiche Länge, gleiche Reihenfolge, mit genullten
`parent`-Feldern bei allen Arbeitskopien des genannten Parents.
Ausgang bei Fehler: **keiner** – die Funktion kann nicht fehlschlagen und wirft nie.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- **Die Vorschrift, wörtlich (TK 9.12.1):** „**Eine Arbeitskopie hält den Parent nicht am Leben:**
  Wird der Parent gelöscht, während eine Arbeitskopie existiert, wird deren `parent` auf `null`
  gesetzt (sie wird zur eigenständigen Vorlage) – **keine** verwaiste Referenz."
- „**Arbeitskopien blockieren das Löschen nicht** – sie sind kein „Benutzen". Wird der Parent
  gelöscht, wird deren `parent` genullt (s. u.)." (TK 9.12.1) – daraus folgt beides: Sie halten das
  Löschen nicht auf, **und** sie werden dabei nicht mitgelöscht.
- Das Feld `parent`, wörtlich aus dem Datenmodell (TK 9.11.1):
  ```
  parent:    string | null // Herkunft: ID der Vorlage, von der diese abgeleitet wurde.
                           //   ≠ null → ARBEITSKOPIE (in Bearbeitung, nicht auswählbar)
                           //   = null → eigenständige, nutzbare Vorlage
  ```
  Nach dieser Umformung ist die Kopie also **auswählbar** – das ist beabsichtigt und wörtlich so
  vorgeschrieben („sie wird zur eigenständigen Vorlage").
- „**Zweck des `parent`-Feldes (und warum es genullt wird):** Das Feld `parent` ist **die
  Merge-Beziehung** … Damit ist die Beziehung **bewusst durchtrennt** – genau das schließt spätere
  **Merge-Konflikte** aus: eine Vorlage ohne `parent` kann niemanden mehr überschreiben und von
  niemandem überschrieben werden." (TK 9.12.1) – dieselbe Umformung wie in `alsEigenstaendige`
  (M4-10), nur ausgelöst durch das Löschen statt durch den Nutzer.
- „**Höchstens eine Arbeitskopie pro Parent.** Wird eine Vorlage geöffnet, für die bereits eine
  Arbeitskopie existiert, wird **diese fortgesetzt** statt eine zweite anzulegen." (TK 9.12.1) – im
  Regelfall trifft die Umformung also genau **einen** Eintrag. Sie ist trotzdem für **alle**
  Treffer geschrieben: Ein zurückgebliebener zweiter Eintrag darf nicht verwaist stehen bleiben,
  und eine Schleife kostet nichts.
- „**Zeichenreihenfolge = Array-Reihenfolge** (später gezeichnete Zone liegt oben). **Kein**
  implizites Sortieren – sonst ist die Überlagerung nicht reproduzierbar." (TK 9.11.1, Punkt 2) –
  das gilt für Zonen; sie werden hier **nicht** angefasst. Aus demselben Grund wird auch die
  Reihenfolge der **Vorlagen** nicht verändert.

**ENTSCHIEDEN – wie kopiert wird (lokale Entscheidung, mit Begründung).** Ein Treffer wird als
flache Kopie mit ausgetauschtem Feld erzeugt: `{ ...vorlage, parent: null }`. `zonen` bleibt
dabei **dieselbe** Array-Referenz. Das ist gewollt: Zonen werden nirgends an Ort und Stelle
verändert (jede Operation dieses Moduls baut neue Objekte), eine tiefe Kopie wäre reine Arbeit ohne
Gewinn – und sie würde bei großen Vorlagen bei jedem Löschvorgang den ganzen Zonenbaum duplizieren.
Nicht-Treffer werden **überhaupt nicht** kopiert, sondern als dieselbe Objekt-Referenz
weitergereicht; so lässt sich im Test mit `toBe` beweisen, dass sie unangetastet blieben.

**ENTSCHIEDEN – keine Eingabeprüfung mit Fehlermeldung.** Ist `parentId` leer oder kein String,
trifft die Bedingung `eintrag.parent === parentId` schlicht auf nichts zu; zurück kommt eine Kopie
des Bestands. Begründung: Diese Funktion hat keine Hülle, in der ein Fehler Platz hätte, und die
Prüfung der Eingabe ist bei ihrem einzigen Aufrufer (M4-13) bereits erledigt. Eine geworfene
Exception hier wäre schlimmer als nutzlos: Sie käme mitten im Löschvorgang, zwischen Lesen und
Schreiben.

**ENTSCHIEDEN – keine Rekursion, keine transitive Kette.** Es wird **nur** die eine Ebene
`parent === parentId` behandelt. Eine Arbeitskopie einer Arbeitskopie kann nicht entstehen:
`oeffneZurBearbeitung` (M4-07) öffnet ausschließlich nutzbare Vorlagen, und die haben `parent = null`
(„**Arbeitskopien (`parent ≠ null`) sind nicht auswählbar.**", TK 9.12.1). Wer trotzdem der Kette
folgt, nullt bei einem beschädigten Bestand fremde Arbeitskopien mit – ein Datenverlust als
Nebenwirkung eines Aufräumschritts.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| kein Eintrag hat `parent === parentId` | – (kein Fehler) | ein neues Array mit denselben Einträgen (gleiche Referenzen), gleiche Reihenfolge |
| `bestand` ist leer | – (kein Fehler) | leeres neues Array |
| `parentId` ist leer oder kein String | – (kein Fehler) | kein Treffer, s. o.; **keine** Exception |
| ein Eintrag hat `parent === null` | – (kein Fehler) | unverändert durchgereicht |
| ein Eintrag ist die zu löschende Vorlage selbst (`id === parentId`) | – (kein Fehler) | **unverändert** durchgereicht – das Entfernen macht M4-13 |
| mehrere Einträge zeigen auf denselben Parent | – (kein Fehler) | **alle** werden gelöst |

Diese Funktion vergibt **keine** Fehlercodes und wirft nicht: Sie hat keine Fehlerquelle. „**Kein
stiller Fehlschlag:** Jede Operation antwortet – `ok` oder Code." (TK 9.1.1, Punkt 7) gilt für die
IPC-bedienten Operationen; hier antwortet die Funktion mit ihrem Rückgabewert.

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – nicht selbst speichern.** Kein `aendereBestand`, kein `ladeBestand` (M4-04), kein
  `fs`, kein `await`, kein `async`. Diese Funktion **gibt zurück**; geschrieben wird genau
  einmal, von M4-13, zusammen mit dem Entfernen der Vorlage. Ein eigener Schreibvorgang hier wäre
  ein zweiter Schreibvorgang – und damit das Zeitfenster, in dem die Vorlage weg und die Kopie noch
  angebunden ist.
- **Verbot – keine Arbeitskopie löschen.** Getroffene Einträge werden **gelöst**, nicht entfernt:
  Sie enthalten Nutzerarbeit („**Auto-Speichern trifft nur die Arbeitskopie.**", TK 9.12.1), und das
  Konzept sagt ausdrücklich „sie wird zur eigenständigen Vorlage". Das Array behält seine Länge.
- **Verbot – die zu löschende Vorlage nicht selbst entfernen.** Auch nicht „gleich mit". Das
  Entfernen und der eine Schreibvorgang gehören M4-13; wer hier filtert, macht die Aufgabenteilung
  unklar und erzeugt bei doppelter Anwendung Überraschungen.
- **Verbot – nichts umbenennen und nichts markieren.** Kein Zusatz „(verwaist)" im Namen, kein
  neues Feld `warParent`, kein Zeitstempel, kein Setzen von `eingebaut`. Die Vorlage soll danach
  aussehen wie jede andere eigenständige Vorlage; das Konzept sieht kein Merkmal für „ehemals
  abgeleitet" vor – im Gegenteil, die Merge-Beziehung soll ja gerade durchtrennt sein (s. Invarianten).
- **Verbot – keine Eingabe an Ort und Stelle verändern.** Kein `bestand[i].parent = null`, kein
  `splice`, kein `sort`, kein `reverse`. Der Aufrufer hält denselben Bestand noch in der Hand und
  darf ihn unverändert vorfinden, falls der Schreibvorgang scheitert.
- **Verbot – keine Sortierung, keine Deduplizierung, kein Filtern.** Länge und Reihenfolge sind nach
  dem Aufruf identisch.
- **Verbot – kein IPC.** Kein `ipcMain`, kein Eintrag in `kanaele.ts`. Diese Funktion ist
  main-intern und wird ausschließlich von M4-13 aufgerufen.
