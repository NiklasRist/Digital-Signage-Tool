### Issue M4-08: [vorlagen-store] speichereArbeitskopie implementieren

## Ziel (in einem Satz)
Während des Bearbeitens wird der Stand der Arbeitskopie fortlaufend und entprellt gesichert – geprüft,
im Speicher sofort gültig, auf der Platte einige Sekunden später – und **ausschliesslich** in die
Arbeitskopie, nie in die genutzte Vorlage.

## Modul & Datei
- Modul: `vorlagen-store` (Main)
- Datei: `src/main/vorlagen-store/speichere-arbeitskopie.ts`
- Vertrag: Technisches Konzept **9.12.1** (Operations-Tabelle und Invarianten), **9.12.2** (welche
  Prüfungen harte Sperren sind), **9.5.4** (Entprellung, Instant-Op vs. Speichern) – Quelle der
  Wahrheit
- Prozess/Speicher: V1 (`vorlagen.json`)

## Warum das im Gesamtsystem wichtig ist
Diese Funktion ist die einzige Stelle, an der ein bearbeitetes Layout überhaupt haltbar wird – und
zugleich die Stelle, an der die Trennung zwischen Experiment und laufender Werbung steht oder fällt.
Schreibt sie versehentlich in den Parent statt in die Arbeitskopie, verändert jeder Mausschubser im
Editor sofort das Aussehen aller Aktionen in **allen** Projekten, die diese Vorlage benutzen. Der
Nutzer würde es nicht einmal merken: Der Editor zeigt ja die Arbeitskopie, und dass die Vorlage
darunter mitwandert, sieht man erst im nächsten Render eines anderen Projekts.

Die zweite Verantwortung ist die **Validierung**. Der Main „vertraut dem Renderer nicht" (TK 9.1.1
Punkt 6). Eine Zone, die halb aus der Fläche ragt, eine Textzone ohne Grössenbereich, eine
verschobene feste Zone – all das käme sonst ungeprüft in `vorlagen.json` und würde beim Zeichnen zu
einem stillen Fehler: Der Text wird abgeschnitten, das Logo steht falsch, und die Ursache liegt
Wochen zurück in einer JSON-Datei.

Die dritte ist die **Entprellung**. Der Editor bewegt Zonen per Ziehen und per Zahlenfeld; ohne
Entprellung schreibt jede Mausbewegung die komplette Bibliothek auf die Platte.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/main/vorlagen-store/speichere-arbeitskopie.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { Vorlage, Zone } from '../../shared/contracts/vorlage'
import type { VorlagenFehlercode } from './fehlercodes'
import { aendereBestand } from './schreibe-vorlagen'

// Fremde Aufrufe – vollstaendige Signaturen, damit hier nichts geraten wird:
//   M4-04: aendereBestand<T>(
//            aenderung: (bestand: Vorlage[]) =>
//              Ergebnis<{ bestand: Vorlage[]; wert: T }, VorlagenFehlercode>,
//            schreibart: 'sofort' | 'entprellt',
//          ): Promise<Ergebnis<T, VorlagenFehlercode>>
//          // 'entprellt': der Bestand ist im Speicher uebernommen und das Promise wird erfuellt;
//          //             die Datei wird 4000 ms nach der LETZTEN entprellten Aenderung geschrieben.
//          //             Ein Fehler der SYNCHRONEN `aenderung` kommt sofort im Ergebnis zurueck.
//   M4-03: type VorlagenFehlercode = 'vorlage_referenziert' | 'parent_eingebaut' | 'speicher_fehler'
//   M4-01: interface Vorlage { id: string; name: string; art: VorlagenArt; höhe: number | null
//                              parent: string | null; eingebaut: boolean; zonen: Zone[] }
//          interface Zone { id: string; rolle: 'fest'|'frei'; bindung: Bindung | null
//                           rahmen: { x: number; y: number; breite: number; höhe: number }
//                           ausrichtung: { horizontal: 'links'|'mitte'|'rechts'
//                                          vertikal: 'oben'|'mitte'|'unten' }
//                           wennLeer: 'leer'|'ausblenden'
//                           text?: { schriftRolle: SchriftRolle; farbRolle: FarbRolle
//                                    größeMax: number; größeMin: number; maxZeilen: number }
//                           bild?: { einpassung: 'contain'|'cover' }
//                           deko?: { füllungFarbRolle?: FarbRolle; radius?: number
//                                    statischerText?: string; verlauf?: { … } } }

/** Auto-Speichern waehrend des Bearbeitens. Trifft NUR die Arbeitskopie mit dieser arbeitsId. */
export async function speichereArbeitskopie(
  arbeitsId: string,
  vorlage: Vorlage,
): Promise<Ergebnis<Vorlage, VorlagenFehlercode>>
```

**Die oben ausgeschriebenen fremden Signaturen (M4-04, M4-03, M4-01) sind fremder Vertrag.** Weicht
die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein **Vertragsfehler**: **melden
und NICHT eigenmächtig anpassen.**

**Ablauf (verbindlich), vollständig innerhalb **einer** `aendereBestand(…, 'entprellt')`-Einheit:**

1. `arbeitsId` prüfen: nicht-leerer String; `vorlage` prüfen: ein Objekt. Sonst
   `ungueltige_eingabe`, **ohne** Bestandszugriff.
2. Eintrag mit `id === arbeitsId` suchen. Nicht vorhanden → `nicht_gefunden`.
3. Der gefundene Eintrag muss `parent !== null` haben. Sonst → `ungueltige_eingabe` (das wäre ein
   Schreibversuch auf eine **genutzte** Vorlage – genau das, was der Arbeitskopie-Fluss ausschliesst).
4. **Unveränderliche Felder abgleichen.** `vorlage.id`, `vorlage.art`, `vorlage.parent` und
   `vorlage.eingebaut` müssen mit dem gespeicherten Eintrag übereinstimmen (`vorlage.id` also mit
   `arbeitsId`). Weicht eines ab → `ungueltige_eingabe`. **Nicht** stillschweigend korrigieren: Eine
   Abweichung ist ein Fehler im Aufrufer, und ein stilles Zurechtbiegen liesse Editor und Store
   dauerhaft verschiedene Stände zeigen.
5. **Veränderliche Felder prüfen und übernehmen:** `name`, `höhe`, `zonen`.
   - `name`: String, nach `trim()` nicht leer, höchstens 80 Zeichen (gleiche Regel wie M4-06);
     gespeichert wird der getrimmte Name.
   - `höhe`: bei `art === 'vollflaeche'` **muss** `null` sein; sonst ganze Zahl `> 0` und `< 1080`.
   - `zonen`: s. Prüfungen unten.
6. Den Eintrag **an seinem bisherigen Platz** im Bestands-Array ersetzen (kein Entfernen und
   Anhängen – das würde die Reihenfolge der Bibliothek bei jedem Auto-Speichern umwerfen).
7. Den gespeicherten – also den getrimmten und geprüften – Stand zurückgeben.

**Zonen-Prüfungen (alle Verstösse → `ungueltige_eingabe`, nichts wird übernommen):**

| Prüfung | Regel |
|---|---|
| Fläche | Jede Zone liegt **vollständig** in `1920 × (höhe ?? 1080)`: `x ≥ 0`, `y ≥ 0`, `breite > 0`, `höhe > 0`, `x + breite ≤ 1920`, `y + höhe ≤ Flächenhöhe`. Alle vier Rahmenwerte sind endliche Zahlen. |
| Feste Zonen | Die Zonen mit `rolle: 'fest'` sind gegenüber dem gespeicherten Stand **unverändert**: gleiche Anzahl, gleiche `id`s, jede tief-gleich zum gespeicherten Gegenstück, und ihre **relative Reihenfolge** untereinander unverändert. Freie Zonen dürfen dazwischen eingefügt, entfernt und umsortiert werden. |
| Text-Parameter | Jede Zone, deren `bindung` einer von `titel`, `beschreibung`, `preis`, `cta`, `slogan` ist, **und** jede Zone mit `deko.statischerText`, **muss** `text` haben, mit `0 < größeMin ≤ größeMax` und ganzzahligem `maxZeilen ≥ 1`. |
| Bild-Parameter | Jede Zone, deren `bindung` `bild` oder `logo` ist, **muss** `bild` haben, und `bild.einpassung` **muss** `'contain'` oder `'cover'` sein. Ohne diesen Wert müsste der Zeichner beim Einpassen raten – und wählte er `cover`, würde ein Produktfoto oder das Logo beschnitten, wo `contain` gemeint war. Das ist dieselbe Lückenklasse wie die fehlenden Text-Parameter, für die TK 9.12.2 eine **Sperre** vorsieht. |
| Eindeutigkeit | Die `id`s aller Zonen einer Vorlage sind paarweise verschieden. |
| Überlappung | **Erlaubt** und ausdrücklich **kein** Fehler. |
| Sicherheitsabstand | Eine Zone **darf** ihn überschreiten – das ist laut Vertrag eine **Warnung** der Oberfläche, keine Sperre. Diese Funktion weist deswegen **nichts** zurück und erzeugt **keine** Warnung. |

**Die relative Reihenfolge der festen Zonen, nicht ihr Index.** Ein Vergleich der absoluten Indizes
wäre falsch: In der eingebauten Vorlage „Vollbild" stehen die festen Zonen an den Positionen 0, 2 und
3; fügt der Nutzer eine freie Zone hinzu, verschieben sich die Indizes zwangsläufig. Geprüft wird
deshalb nur, dass `hintergrund` weiterhin vor `scrim` und `scrim` vor `logo` liegt. Warum überhaupt:
Die Zeichenreihenfolge **ist** die Überlagerung (TK 9.11.1, Punkt 2); dürfte der `hintergrund` ans
Ende wandern, deckte er alles zu, und der Markenrahmen wäre praktisch abgeschaltet – obwohl FA-11 ihn
für „nicht abschaltbar" erklärt.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `arbeitsId` | ID der Arbeitskopie, die gespeichert wird | nicht-leerer String; muss im Bestand existieren und `parent !== null` haben |
| `vorlage` | der vollständige neue Stand der Arbeitskopie | `id`, `art`, `parent`, `eingebaut` müssen zum gespeicherten Eintrag passen; `name`, `höhe` und `zonen` werden übernommen, nachdem sie die Prüfungen oben bestanden haben |

Ausgang bei Erfolg: `Ergebnis<Vorlage, VorlagenFehlercode>` mit dem Stand, der im Bestand liegt
(getrimmter Name, geprüfte Zonen). **Erfolg bedeutet „gültig übernommen", nicht „auf der Platte"** –
die Platten-Schreibung folgt entprellt.
Ausgang bei Fehler: `nicht_gefunden` (unbekannte `arbeitsId`), `ungueltige_eingabe` (jede
fehlgeschlagene Prüfung, auch der Versuch, eine genutzte Vorlage zu speichern), `speicher_fehler`
(nur, wenn schon das Laden des Bestands scheitert), sowie `unbekannter_fehler` aus dem generischen
Satz (#12).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Operations-Zeile, wörtlich (TK 9.12.1): „`speichereArbeitskopie` | `arbeitsId`, `vorlage` →
  `Ergebnis<Vorlage>` – **Auto-Speichern** während des Bearbeitens"
- „**Auto-Speichern trifft nur die Arbeitskopie.** Während des Bearbeitens wird entprellt gesichert
  (3–5 s, wie 9.5.4) – aber **ausschließlich** in die Arbeitskopie. Die genutzte Vorlage ändert sich
  **erst** beim expliziten `uebernehmeInParent` bzw. `alsEigenstaendige`. So kann Experimentieren
  **nie** laufende Werbung in anderen Projekten verändern." (TK 9.12.1) – **das ist die Kernzusage
  dieses Issues.** Der Parent wird hier **nie** angefasst, auch nicht teilweise, auch nicht „nur der
  Name".
- „**Instant-Op vs. Speichern getrennt:** Eine Instant-Operation (9.5.2) validiert und wendet **im
  Speicher** an, *bevor* sie „ok" meldet – ihr Erfolg bedeutet „gültig übernommen", **nicht** „schon
  auf Platte". Die Platten-Schreibung ist die entprellte Auto-Speicherung." (TK 9.5.4) – deshalb
  `schreibart: 'entprellt'` und deshalb bedeutet das zurückgegebene `ok` **nicht**, dass
  `vorlagen.json` bereits geschrieben ist.
- „**Entprellt 3–5 s** nach der letzten Änderung (kein Platten-Hämmern beim Slider-Ziehen)."
  (TK 9.5.4) – die Zahl liegt in M4-04 (4000 ms); diese Datei enthält **keinen** eigenen Timer und
  **keine** eigene Zeitkonstante.
- „**Speicherfehler sind sichtbar (NFA-02):** Scheitert eine Auto-Speicherung (Platte voll, Rechte),
  wird das **nicht still verschluckt** – die UI zeigt dauerhaft „nicht gespeichert" + automatischer
  Wiederholversuch; die Änderungen **bleiben im Speicher** (kein Rollback, kein Arbeitsverlust). Erst
  nach erfolgreichem Schreiben verschwindet der Hinweis." (TK 9.5.4) – der Schreibfehler entsteht
  **nach** der Rückgabe dieser Funktion und wird deshalb **nicht** hier gemeldet; wie er sichtbar
  wird, ist eine offene Frage von M4-04 und **nicht** in dieser Datei zu lösen. **Verboten** ist
  jedoch jeder Rollback: Scheitert später das Schreiben, bleibt der hier übernommene Stand gültig.
- „**Feste Zonen (`rolle: "fest"`) dürfen nie entfernt oder verschoben werden** – auch nicht in
  eigenen Vorlagen (Markenrahmen erzwungen, FA-11)." (TK 9.12.1)
- „**Feste Zonen sind Teil der Vorlage**, nicht hartkodiert […] Der Editor darf Zonen mit
  `rolle: "fest"` **nicht** ändern, verschieben oder entfernen (Markenrahmen erzwungen, FA-11)."
  (TK 9.11.1, Punkt 4) – der Editor *darf* es nicht, und diese Funktion *lässt* es nicht zu; der Main
  vertraut dem Renderer nicht.
- „**`art` ist nach dem Anlegen unveränderlich** – auch über die Arbeitskopie. Ein Wechsel würde alle
  Zonen-Rahmen ungültig machen (andere Fläche); stattdessen neu anlegen." (TK 9.12.1) – deshalb wird
  `vorlage.art` abgeglichen und nie übernommen.
- „**`höhe` nur bei `split`/`einblendung`**, Wertebereich > 0 und < 1080. Bei `vollflaeche` immer
  `null`." (TK 9.12.1) – dieser Wertebereich wird hier durchgesetzt, mit denselben Grenzen wie beim
  Anlegen (M4-06). Ob eine **geänderte** Höhe darüber hinaus durchgeht, hängt an ihrem Zusammenspiel
  mit der festen Zone `hintergrund`, und das ist **offen** – s. „Nicht selbst entscheiden".
- Die harten Sperren, wörtlich aus der Tabelle „Prüfungen – harte Sperre vs. Warnung" (TK 9.12.2):
  „Zone ganz oder teilweise **außerhalb der Fläche** | **Sperre** – nicht speicherbar";
  „`höhe` ≤ 0 oder ≥ 1080 (bei `split`/`einblendung`) | **Sperre**";
  „Textzone ohne Text-Parameter (Größenbereich, Max-Zeilen) | **Sperre**";
  „Zone überschreitet den **Sicherheitsabstand** (5 %, 9.10.5) | **Warnung** – am TV evtl.
  abgeschnitten"; „Zonen **überlappen** | **erlaubt** – wird für Hintergrund und Scrim gebraucht";
  „Feste Zone verschieben oder löschen | **gesperrt**, nur sichtbar".
  **Folge:** Die drei Sperren werden hier durchgesetzt; die **Warnung** wird hier **nicht** erzeugt
  und führt zu **keiner** Ablehnung – sie ist Sache der Oberfläche.
- „**Zonen-Rahmen in absoluten Pixeln** der jeweiligen Vorlagen-Fläche (9.11.1); Eingaben werden auf
  die Fläche **begrenzt**." (TK 9.12.2) – der Editor begrenzt bereits; diese Funktion begrenzt
  **nicht** nach, sondern **lehnt ab**. Ein stilles Zurechtschieben würde dem Nutzer eine andere
  Zone zurückgeben, als er gesetzt hat.
- „**Zeichenreihenfolge = Array-Reihenfolge** (später gezeichnete Zone liegt oben). **Kein**
  implizites Sortieren – sonst ist die Überlagerung nicht reproduzierbar." (TK 9.11.1, Punkt 2) – die
  übergebene Zonen-Reihenfolge wird **unverändert** übernommen (bis auf die Prüfung der relativen
  Reihenfolge der festen Zonen). Kein Sortieren, kein Nach-hinten-Schieben von Dekorationen.
- „Der Main validiert jede eingehende Nutzlast – er vertraut dem Renderer **nicht**. Ungültige
  Eingabe → `ungueltige_eingabe`, **ohne** jede Wirkung auf die Daten." (TK 9.1.1, Punkt 6) – die
  Prüfung läuft **vollständig**, bevor der Eintrag ersetzt wird; ein teilweise übernommener Stand
  darf nie entstehen.
- **Der Bestand wird an genau einer Stelle verändert.** Nur der Eintrag mit `id === arbeitsId` wird
  ersetzt; Länge und Reihenfolge des Bestands bleiben gleich.

## Nicht selbst entscheiden – STOPP und fragen
- **ECHTE OFFENE FRAGE: Was geschieht mit der festen Zone `hintergrund`, wenn der Nutzer die
  Bandhöhe ändert?** Beide Regeln stehen fest und widersprechen sich in genau diesem Fall:
  Der Editor darf „Bandhöhe setzen" (TK 9.12.2), und der Merge übernimmt die Höhe ausdrücklich mit
  („Zonen, Parameter, Höhe", TK 9.12.1) – zugleich gilt „**Feste Zonen (`rolle: "fest"`) dürfen nie
  entfernt oder verschoben werden** – auch nicht in eigenen Vorlagen (Markenrahmen erzwungen,
  FA-11)." (TK 9.12.1). Der `hintergrund` eines Bandes ist aber eine **feste** Zone, die die
  Bandfläche **exakt ausfüllt** (bei `band-standard`: 0, 0, 1920, 162). Daraus folgt:
  1. **Verkleinern ist unmöglich.** Bei `höhe = 120` liegt der 162 px hohe `hintergrund` teilweise
     ausserhalb der Fläche → Flächen-Sperre. Ihn anzupassen ist ebenfalls gesperrt. Der Nutzer kommt
     aus dieser Sackgasse nicht heraus und bekommt nur ein `ungueltige_eingabe`, dessen Ursache er
     nicht erkennen kann.
  2. **Vergrössern hinterlässt eine Lücke.** Bei `höhe = 200` deckt der `hintergrund` nur die oberen
     162 px ab; die unteren 38 px des Bandes bleiben ungefüllt – bei `art: 'split'` schwarz, bei
     `art: 'einblendung'` durchsichtig. Genau der lautlose Fehler, gegen den die Zone überhaupt
     eingeführt wurde (TK 9.11.1: ohne sie würde eine Aktion ohne Motiv „**schwarz** rendern statt
     markenkonform").

  Drei Wege sind denkbar, und die Wahl legt **Verhalten und Schnittstelle** fest:
  **(a)** Die `höhe` wird nur bei `erstelleVorlage` (M4-06) festgelegt und ist über die Arbeitskopie
  **nicht** änderbar – diese Funktion lehnt dann jede abweichende `höhe` ab.
  **(b)** Feste Zonen, die die volle Fläche abdecken, werden bei einer Höhenänderung **mitgeführt** –
  dann muss ausgeschrieben werden, welche Zonen das betrifft und nach welcher Regel, denn eine
  erfundene Regel wäre genau das verbotene „automatisches Umlayouten" (TK 9.11.1, Punkt 3).
  **(c)** Nur **Vergrössern** ist erlaubt – dann muss festgelegt werden, wer die zusätzliche Fläche
  füllt.
  **Betrifft ausserdem M4-06** (dort entstehen die festen Zonen) **und M4-09** (der Merge trägt die
  Höhe in die genutzte Vorlage). **Nicht raten, nicht vorsorglich einbauen.** Verbindlich bis zur
  Klärung: Es wird **keine** Sonderbehandlung gebaut – die Flächenprüfung gegen
  `1920 × (höhe ?? 1080)` und die Unveränderlichkeit der festen Zonen gelten beide unverändert und
  ohne Ausnahme; kein Mitskalieren, kein automatisches Nachziehen des `hintergrund`, kein Clamping.
- **Verbot – den Parent nicht anfassen.** Diese Funktion schreibt **nur** in den Eintrag mit
  `id === arbeitsId`. Kein Durchreichen an den Parent, kein „Name gleich mitziehen", kein
  Zeitstempel am Parent. Das ist die wichtigste Zusage des ganzen Arbeitskopie-Flusses.
- **Verbot – keinen eigenen Timer bauen.** Die Entprellung liegt vollständig in M4-04
  (`schreibart: 'entprellt'`). Kein `setTimeout` in dieser Datei, keine zweite Zeitkonstante, kein
  „nur alle 10 Änderungen schreiben".
- **Verbot – kein `schreibart: 'sofort'`.** Auch nicht „bei grösseren Änderungen" oder „beim ersten
  Aufruf". Der Vertrag kennt für das Auto-Speichern genau eine Betriebsart.
- **Verbot – nichts stillschweigend korrigieren.** Kein Clamping von Rahmenwerten auf die Fläche,
  kein Auffüllen fehlender `text`-Parameter mit Vorgabewerten, kein Wiederherstellen veränderter
  fester Zonen, kein Umsortieren. Abgelehnt wird abgelehnt – sonst zeigt der Editor etwas anderes an,
  als gespeichert ist, und die Vorschau weicht vom Endvideo ab, ohne dass es jemandem auffällt.
- **Verbot – keine Warnung erzeugen.** Der Sicherheitsabstand ist laut TK 9.12.2 eine Warnung der
  Oberfläche. Diese Funktion gibt **keine** Warnliste zurück und schreibt **kein** Warnfeld in die
  Vorlage; die Signatur liefert `Ergebnis<Vorlage>` und sonst nichts.
- **Verbot – keine Referenzprüfung.** Ob die Vorlage irgendwo benutzt wird, spielt beim Speichern
  einer Arbeitskopie keine Rolle (eine Arbeitskopie ist nicht auswählbar). Die Prüfung über alle
  Projekte gehört M4-12/M4-13.
- **Verbot – kein direkter Dateizugriff.** Kein `fs`, kein `ermittleDatenOrt()`.

## Definition of Done
- [ ] Ein gültiger Aufruf ändert nur den Eintrag mit `id === arbeitsId`; alle übrigen Einträge – vor
      allem der Parent – sind danach byte-identisch (eigener Test, der den Parent vergleicht)
- [ ] Länge und Reihenfolge des Bestands sind nach dem Speichern unverändert
- [ ] Der Rückgabewert enthält den getrimmten `name` und exakt die übergebene Zonen-Reihenfolge
- [ ] Unmittelbar nach dem Aufruf ist `vorlagen.json` **noch nicht** geändert; nach `flushBestand()`
      (M4-04) ist sie es (Test ohne Warten auf den Timer)
- [ ] Ein Aufruf mit `parent === null` im gespeicherten Eintrag ergibt `ungueltige_eingabe` und
