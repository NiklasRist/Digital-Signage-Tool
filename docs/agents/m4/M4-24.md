### Issue M4-24: [template-canvas] Ein SegmentBild als PNG-Binärpuffer ausgeben

## Ziel (in einem Satz)
Aus dem bereits gezeichneten `SegmentBild` entstehen die PNG-Bytes, die als `Uint8Array` in den
`RenderRequest` wandern – verlustfrei, ohne Base64, und **ohne** dass dabei noch einmal gezeichnet
wird.

## Modul & Datei
- Modul: `template-canvas` (Renderer, geteilt)
- Datei: `src/renderer/template-canvas/als-png.ts`
- Vertrag: Technisches Konzept **9.10.1** (die zweite der beiden Verwendungen), **9.1** Punkte 2
  und 3 (PNG, Binärpuffer), **9.2.2** (`RenderItem` der Art `segment`) – Quelle der Wahrheit
- Prozess/Speicher: Renderer; Zulieferung für P4 (finaler Render). **Kein** Dateizugriff – der
  Renderer schreibt nichts auf die Platte.

## Warum das im Gesamtsystem wichtig ist
Das hier ist der **einzige** Weg, auf dem Pixel aus dem Renderer in das fertige Video gelangen
(TK 9.2.2: Segment-PNGs sind der „einziger Pixel-Transport"). Alles, was in dieser Funktion vom
gezeichneten Canvas abweicht, ist ein Unterschied zwischen dem, was der Nutzer auf dem Bildschirm
geprüft hat, und dem, was auf dem Fernseher läuft – und er wird nirgends gemeldet.

Zwei Abkürzungen zerstören genau das:

- **Neu zeichnen.** Wer hier `zeichneSegment` noch einmal aufruft oder ein eigenes Canvas aufbaut
  („ich brauche ja nur die Pixel"), hat einen **zweiten Zeichenpfad** geschaffen. Solange beide
  Pfade zufällig gleich sind, fällt nichts auf; sobald einer von beiden angepasst wird, driften
  Vorschau und Endvideo auseinander.
- **Base64.** `toDataURL()` ist verlockend, weil es synchron ist. Es liefert aber eine Zeichenkette
  statt Bytes: rund ein Drittel mehr Daten durch die IPC-Grenze, plus Kodieren und Dekodieren, und
  es widerspricht dem Vertrag ausdrücklich.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/template-canvas/als-png.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { SegmentBild } from './zeichne-segment'

export type PngFehlercode = 'png_export_fehler'

export async function alsPng(bild: SegmentBild): Promise<Ergebnis<Uint8Array, PngFehlercode>>
```

**Diese eine Funktion ist asynchron – und das steht nicht im Widerspruch zur synchronen
Zeichenroutine.** Gezeichnet wird synchron (M4-23); hier wird nichts mehr gezeichnet, sondern ein
**fertiges** Canvas serialisiert. Die einzigen Wege, aus einem Canvas echte Bytes statt Base64 zu
bekommen (`toBlob` und `convertToBlob`), sind beide asynchron. Das `await` liegt damit **hinter**
dem Determinismus, nicht in ihm: Die Pixel stehen bereits fest, wenn diese Funktion beginnt.

**Warum ausgerechnet diese Funktion eine `Ergebnis<T>`-Hülle trägt und keine andere im Modul:** Sie
ist die **einzige fehlbare Operation des Moduls**. Alle übrigen Funktionen von `template-canvas`
sind reine Zeichenaufrufe ohne Rückgabewert (M4-20/21/22), reine Rechnungen (M4-18/19) oder liefern
einen definierten Zustand (M4-17); scheitern kann von ihnen keine auf eine Weise, die ein Aufrufer
behandeln müsste. Hier dagegen kann der PNG-Kodierer wirklich versagen – und das Ergebnis reist
anschließend in einem `RenderRequest` über die Renderer↔Main-Grenze, wo laut TK 9.1.1 Punkt 2
niemals Exceptions, sondern nur die Hülle zulässig sind. Aus demselben Grund steht auch die
Fehlercode-Union in dieser Datei: Ein eigenes Fehlercode-Modul für einen einzigen Code wäre eine
Datei ohne Inhalt.

`Uint8Array`, nicht `ArrayBuffer` und nicht `Buffer`: `Buffer` gibt es im abgeschotteten Renderer
nicht, und die Zielfelder sind bereits als `Uint8Array` festgeschrieben (#17):

```ts
// #17 – src/shared/contracts/render-request.ts (Ausschnitt)
export interface RenderItemSegment {
  id: string
  art: 'segment'
  png: Uint8Array                  // Binärpuffer, vom Renderer via template-canvas gerendert
  dauer: number
}
// und für die parallele Einblendung (TK 9.2.8):
//   abschnitte: Array<{ png: Uint8Array; dauer: number }>

// M4-23 – src/renderer/template-canvas/zeichne-segment.ts
export interface SegmentBild {
  canvas: HTMLCanvasElement
  breite: number
  höhe: number
}

// #22 – src/shared/contracts/ergebnis.ts
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
```

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.** Wer den Aufruf still an eine abweichende Signatur
anpasst, macht aus einem Vertragsfehler einen unsichtbaren – und dieselbe Funktion bzw. derselbe Typ
existiert dann in zwei Fassungen im Projekt.

**Der Ablauf, verbindlich:**

1. **Maßprüfung vor allem anderen:** Stimmen `bild.canvas.width`/`.height` nicht mit
   `bild.breite`/`bild.höhe` überein, wird abgebrochen mit `png_export_fehler`. Das ist kein
   Formalismus: Das Setzen von `canvas.width` oder `canvas.height` **leert** ein Canvas
   vollständig. Weichen die Werte ab, hat jemand nach dem Zeichnen an der Größe gedreht, und das
   PNG wäre eine leere Fläche – im Video ein schwarzes bzw. durchsichtiges Segment, ohne jede
   Fehlermeldung.
2. `bild.canvas.toBlob(callback, 'image/png')`, in ein Promise gehüllt. Der MIME-Typ wird
   **ausdrücklich** angegeben; ohne ihn gilt zwar ohnehin PNG, aber die Absicht soll im Code stehen.
   Ein Qualitätsargument wird **nicht** übergeben – PNG ist verlustfrei, der Parameter ist dort
   wirkungslos und würde nur suggerieren, es gäbe eine Stellschraube.
3. Ist der Blob `null`, endet der Aufruf mit `png_export_fehler`.
4. `const puffer = new Uint8Array(await blob.arrayBuffer())`.
5. Ist `puffer.byteLength === 0`, endet der Aufruf mit `png_export_fehler` – ein leerer Puffer wäre
   im Main erst beim ffmpeg-Lauf aufgefallen.
6. Sonst `{ ok: true, wert: puffer }`.
7. Der **gesamte** Ablauf liegt in einem `try`/`catch`. Jede Ausnahme (insbesondere der
   `SecurityError` eines „verunreinigten" Canvas, s. STOPP-Block) wird in `png_export_fehler`
   übersetzt, mit der ursprünglichen Meldung im Feld `meldung`. Es verlässt **keine** Ausnahme diese
   Funktion: Ihr Ergebnis wandert in einen `RenderRequest`, also über die IPC-Grenze.

**Farbraum: sRGB, und zwar unangetastet.** TK 9.10.2 legt für die Ausgabe „Farbraum | sRGB" fest.
Ein Canvas-2D-Kontext arbeitet in Chromium ohne weiteres Zutun in sRGB, und `toBlob` schreibt genau
diese Werte. Daraus folgt für diese Datei genau zweierlei, beides verbindlich: Es wird **kein
abweichendes Farbprofil eingebettet** (kein Display-P3, kein Rec.2020, kein `colorSpace`-Argument
an `getContext`, keine ICC-Nachbehandlung), und ein vom Kodierer erzeugtes Profil wird **nicht
entfernt**, um Bytes zu sparen. Begründung: Die PNGs gehen unverändert in den ffmpeg-Lauf, dessen
Profil BT.709 ist (TK 9.2.4). Ein abweichendes Profil verschöbe alle Farben – das Markenrot sähe auf
dem Fernseher anders aus als in der Vorschau, ohne dass irgendwo ein Fehler erschiene.

**Anzeige und Export stammen aus demselben Aufruf von `zeichneSegment`.** Diese Funktion bekommt das
Ergebnis dieses Aufrufs übergeben und exportiert **es**. Sie ruft `zeichneSegment` nicht auf, erzeugt
kein Canvas, holt keinen 2D-Kontext, liest keine Vorlage, keine Aktion und keine Marke – sie sieht
diese Typen nicht einmal.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `bild` | das Ergebnis **eines** Aufrufs von `zeichneSegment` (M4-23) | `canvas.width`/`.height` müssen zu `breite`/`höhe` passen; sonst `png_export_fehler` |

Ausgang bei Erfolg: `{ ok: true, wert: Uint8Array }` – die vollständigen PNG-Bytes, bei
`art: 'einblendung'` **einschließlich Alphakanal**.
Ausgang bei Fehler: Code `png_export_fehler` (der einzige fachliche Code dieser Funktion) bzw. die
generischen Codes aus `Ergebnis<T, F>`.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- Die Schnittstelle des Moduls, wörtlich (TK 9.10.1):

  ```
  zeichneSegment(aktion, vorlage, marke) → SegmentBild        // Canvas 1920×1080
     ├─ Anzeige : Canvas wird nur per CSS herunterskaliert (Vorschau, Thumbnail)
     └─ Export  : alsPng(SegmentBild) → PNG-Bytes (Binärpuffer für den RenderRequest, 9.2.2)
  ```

  „**Invariante:** Es gibt **keinen zweiten Zeichenpfad.** Anzeige und Export stammen immer aus
  **demselben** Aufruf – sonst driften Vorschau und Endvideo auseinander." (TK 9.10.1)
- „**PNG-Übergabe als Binärpuffer** (kein Base64 im Nachrichtenkörper). Der **Renderer schreibt
  nichts auf die Platte**; er liefert die Bytes, der **Main** persistiert sie in den flüchtigen
  Arbeitsbereich (T1). Die Regel „nur der Main berührt das Dateisystem" bleibt unangetastet."
  (TK 9.1, Punkt 3)
- „**Segment-Format = PNG** (verlustfrei, text- und kantensicher für flächiges Corporate-Design; von
  `ffmpeg` nativ lesbar). Kein JPEG (DCT-Artefakte an Textkanten), keine verlustbehaftete
  Umkodierung." (TK 9.1, Punkt 2)
- „**Binärdaten** (Segment- und Band-PNGs) reisen als **Binärpuffer**, nicht als Base64 (9.1,
  Punkt 3) – die Hülle ändert daran nichts." (TK 9.1.1, Punkt 9)
- „Export-Format | **PNG** (verlustfrei; Begründung 9.1, Punkt 2)" und „Deckkraft | **folgt der
  Vorlagenart:** `vollflaeche` und `split` → **deckend**; `einblendung` → **mit Alpha** (das Band
  überlagert das Video, 9.2.8). PNG trägt den Alphakanal verlustfrei." (TK 9.10.2) – der Alphakanal
  darf beim Export **nicht** wegoptimiert oder auf Schwarz gerechnet werden.
- „Farbraum | sRGB" (TK 9.10.2) – kein abweichendes Farbprofil einbetten und keines entfernen.
- „**Kein persistenter Cache**" (TK 9.10.3, Punkt 6) – diese Funktion legt keine erzeugten Puffer ab
  und gibt bei erneutem Aufruf keinen gespeicherten Puffer zurück.
- **Niemals `throw`.** Das Ergebnis geht in einen `RenderRequest` und damit über die
  Renderer↔Main-Grenze; dort gilt die Ergebnis-Hülle (TK 9.1.1, Punkt 2).

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `bild.canvas.width !== bild.breite` oder `.height !== bild.höhe` | `png_export_fehler` | kein `toBlob`-Aufruf; Meldung nennt erwartete und tatsächliche Maße |
| `toBlob` ruft mit `null` zurück (Kodierung gescheitert, Speichermangel) | `png_export_fehler` | keine Wirkung, kein Puffer |
| `toBlob` oder `blob.arrayBuffer()` wirft (u. a. `SecurityError` bei verunreinigtem Canvas) | `png_export_fehler` | Ausnahme gefangen, Originalmeldung in `meldung` |
| Der erzeugte Puffer hat die Länge 0 | `png_export_fehler` | leerer Puffer wird **nicht** weitergereicht |
| `bild.canvas` fehlt oder ist kein Canvas (`toBlob` ist keine Funktion) | `png_export_fehler` | keine Ausnahme nach außen |

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – nicht neu zeichnen.** Kein Aufruf von `zeichneSegment`, kein
  `document.createElement('canvas')`, kein `getContext`, kein `drawImage`. Auch nicht „nur um das
  Canvas zu kopieren".
- **Verbot – kein Base64.** Kein `toDataURL`, kein `btoa`, kein `FileReader.readAsDataURL`, keine
  Zeichenketten-Zwischenstufe. Auch nicht als Rückfallebene.
- **Verbot – kein anderes Format.** Kein JPEG, kein WebP – auch nicht „nur für die Vorschau" oder
  „weil es kleiner ist". WebP-lossless ist im Konzept ausdrücklich als **spätere** Optimierung nach
  einer Messung vorgemerkt, nicht als Wahlmöglichkeit hier.
- **Verbot – nichts auf die Platte schreiben.** Kein `showSaveFilePicker`, kein Download-Link, kein
  `IndexedDB`. Der Renderer liefert Bytes, der Main persistiert sie.
- **Verbot – nicht zwischenspeichern.** Zwei Aufrufe mit demselben Bild erzeugen den Puffer zweimal.
- **Offen und empirisch zu prüfen: Verunreinigt das `media://`-Protokoll das Canvas?** Ein Canvas,
  in das ein Bild aus einer anderen Herkunft gezeichnet wurde, gilt als „tainted"; `toBlob` wirft
  dann einen `SecurityError`, und **jeder** Export scheitert – nicht nur bei einem Motiv, sondern
  bei jedem Segment mit Bild. Ob das für `media://` (#50) zutrifft, hängt davon ab, mit welchen
  Rechten das Schema registriert wurde (`registerSchemesAsPrivileged`, u. a. `standard`, `secure`,
  `supportFetchAPI`, `corsEnabled`) und ob das Bildobjekt beim Laden ein `crossOrigin`-Attribut
  bekommt – beides gehört zu #9/#50 bzw. M4-17, **nicht** hierher. Das ist eine **empirische** Frage
  (einmal ausprobieren, nicht ableiten). Tritt der Fehler auf: **melden**, nicht umgehen. Der
  naheliegende Ausweg – das Motiv erst in einen Data-URI verwandeln und dann zeichnen – ist genau
  die Base64-Krücke, die dieser Vertrag verbietet, und würde zusätzlich den Speicherbedarf jedes
  Imports verdoppeln.
- **Offen: Ob die PNG-Bytes bei gleichen Pixeln byteweise identisch sind.** Der Vertrag verlangt
  „gleiche Eingabe → gleiches Bild" (TK 9.10.3, Punkt 5) – das ist eine Aussage über **Pixel**. Ob
  der PNG-Kodierer von Chromium darüber hinaus Byte für Byte reproduzierbar arbeitet, ist nirgends
  zugesagt. **Keine** eigene Nachbehandlung erfinden (kein Neu-Kodieren, kein Entfernen von Chunks),
  um Byte-Gleichheit zu erzwingen; falls sie irgendwo gebraucht wird, ist das eine Frage an den
  Vertrag.

## Definition of Done

**Ohne Browser prüfbar** (Vitest; `bild` ist ein von Hand gebautes Objekt mit einem
`canvas`-Doppel, das `width`, `height` und eine steuerbare `toBlob`-Methode besitzt, sowie einem
Blob-Doppel mit `arrayBuffer()` – die Funktion nimmt das `SegmentBild` als Parameter, genau dafür):

- [ ] Erfolgsfall: Rückgabe ist `{ ok: true, wert }` und `wert` ist eine **`Uint8Array`**
      (`instanceof`-Prüfung), nicht `ArrayBuffer`, nicht `Blob`, nicht `string`
- [ ] `toBlob` wird mit dem MIME-Typ `'image/png'` und **ohne** drittes Argument aufgerufen
- [ ] `canvas.width = 1920`, `bild.breite = 1080` (vertauschte Maße) → `png_export_fehler`, und
      `toBlob` wurde **nicht** aufgerufen
- [ ] `toBlob` liefert `null` → `png_export_fehler`
- [ ] `toBlob` wirft → `png_export_fehler`, die Meldung enthält den Text der Ausnahme, und es
      verlässt **keine** Ausnahme die Funktion
- [ ] `arrayBuffer()` liefert 0 Bytes → `png_export_fehler`
- [ ] `bild.canvas` ist `null` bzw. hat kein `toBlob` → `png_export_fehler`, keine Ausnahme
- [ ] Zwei Aufrufe mit demselben `bild` rufen `toBlob` **zweimal** auf (kein Zwischenspeicher)
- [ ] Die Datei enthält kein `toDataURL`, kein `btoa`, kein `createElement`, kein `getContext`,
      kein `drawImage`, kein `jpeg`/`webp`, kein `zeichneSegment`
- [ ] Die Datei enthält keinen Farbraum- oder Profil-Eingriff: kein `colorSpace`, kein `icc`, kein
      `display-p3`, kein Umschreiben oder Entfernen von PNG-Chunks
- [ ] Der `Ergebnis`-Typ wird mit dem zweiten Typparameter verwendet
      (`Ergebnis<Uint8Array, PngFehlercode>`), nicht als blankes `Ergebnis<Uint8Array>`

- [ ] Alle Fehlerpfade oben liefern den genannten Code (kein `throw` über die IPC-Grenze)
- [ ] Keine Datei außerhalb von `src/renderer/template-canvas/als-png.ts` (+ zugehörige Testdatei)
      geändert

### Was hier NICHT abgenommen wird (nur im laufenden Programm prüfbar)

`toBlob` existiert in jsdom nicht, und ein echtes `SegmentBild` entsteht erst mit Vorlagen, Marke
und geladenen Medien. Diese Punkte sind **keine** Abnahmekriterien hier, sondern gehören in die
Integrationsprüfung (M5/M6). Sie stehen hier, damit sie nicht verlorengehen:

- Ein echtes `SegmentBild` einer `vollflaeche`-Vorlage ergibt einen Puffer, dessen erste acht Bytes
  die PNG-Signatur sind (`89 50 4E 47 0D 0A 1A 0A`) und dessen IHDR-Maße 1920 × 1080 lauten.
- Ein `SegmentBild` einer `einblendung`-Vorlage ergibt ein PNG **mit** Alphakanal, und die
  durchsichtigen Bereiche sind im Ergebnis durchsichtig, nicht schwarz.
- Ein Segment mit Motiv (also mit einem über `media://` geladenen Bild) lässt sich exportieren, ohne
  dass ein `SecurityError` auftritt – das ist der Nachweis für den STOPP-Punkt oben.
