### Issue M4-25: [template-canvas] Das gebündelte Marken-Logo laden und bereitstellen

## Ziel (in einem Satz)
Das Marken-Logo wird einmal je Sitzung aus dem **Bundle** des Renderers geladen und **fertig
dekodiert** in einem Bestand abgelegt, aus dem die synchrone Zeichenroutine es ohne Warten holen
kann – damit die feste Logo-Zone jeder Vorlage wirklich ein Bild bekommt.

## Modul & Datei
- Modul: `template-canvas` (Renderer)
- Datei: `src/renderer/template-canvas/logo-laden.ts`
- Vertrag: Technisches Konzept **9.10.5** (fester Markenrahmen), **9.10.3** Punkt 4 (dekodiert vor
  dem Zeichnen), **9.11.2** (`Marke.logo`), **9.11.1** (die Logo-Zonen der eingebauten Vorlagen) –
  Quelle der Wahrheit
- Prozess/Speicher: P2, P3, P4, P5 (jeder Zeichenaufruf des Systems); kein Speicher im Sinne von
  D1/D2/D3 – das Logo ist Teil des App-Bundles

## Warum das im Gesamtsystem wichtig ist
**Ohne diese Datei bleibt das Logo in jedem einzigen Segment leer.** Die Bindung `logo` ist eine
**Bild**bindung: `zeichneSegment` (M4-23) reicht ein `Motiv` an die Bildzone (M4-21), und die
zeichnet bei `{ zustand: 'fehlt' }` den Platzhalter „Bild fehlt". Der einzige andere Bildlader des
Moduls (M4-17) holt Motive über `media://`, und dieses Protokoll löst **ausschließlich** innerhalb
des Medienordners eines Projekts auf und lehnt alles andere ab (#50). `marke.logo.datei` ist aber
kein Projektmedium, sondern ein **gebündeltes** Asset – über `media://` ist es unerreichbar. Ohne
eigenen Ladeweg trüge also **jedes** Segment und **jedes** Band an der Stelle des Logos eine rote
Defektanzeige, und FA-11 („fester Markenrahmen, nicht abschaltbar") wäre schlicht **unerfüllbar**.

Das ist kein Randfall: Alle drei eingebauten Vorlagen haben eine feste Logo-Zone („Vollbild"
96, 54, 420, 120 · „Split" 1056, 54, 420, 120 · „Band-Standard" 96, 20, 240, 69). Das Logo ist damit
das einzige Bild, das in **jeder** Ausgabe des Systems vorkommt – auch in Aktionen ganz ohne Motiv.

Die zweite Falle ist der **Zeitpunkt**. `zeichneSegment` ist synchron und darf nicht `await`en
(sonst ist „gleiche Eingabe → gleiches Bild" nicht mehr prüfbar und die Vorschau flackert). Deshalb
wird hier – genau wie beim Motiv-Bestand aus M4-17 – **vorher** geladen und beim Zeichnen nur noch
**nachgeschlagen**. Wer stattdessen im Zeichenpfad lädt, macht die Kernzusage des Moduls kaputt.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/template-canvas/logo-laden.ts
import type { Marke } from '../../shared/contracts/marke'
import type { Motiv } from './bild-laden'

export async function bereiteLogoVor(marke: Marke): Promise<void>
// Lädt marke.logo.datei aus dem Bundle des Renderers, dekodiert es mit await img.decode() und legt
// das Ergebnis im Modul-Bestand ab. Idempotent: merkt sich das EINE Promise und gibt es bei jedem
// weiteren Aufruf unverändert zurück; ein abgelehntes Promise wird NICHT gemerkt.
// Wirft NIE wegen eines Ladefehlers – ein nicht ladbares Logo landet als { zustand: 'fehlt' } im
// Bestand. Geworfen wird nur bei einem leeren marke.logo.datei (Programmierfehler).

export function holeLogo(): Motiv
// SYNCHRON, ohne Parameter. Liest ausschließlich den Bestand – lädt nichts, wartet auf nichts,
// erzeugt kein Image. Vor der ersten erfolgreichen Vorbereitung: { zustand: 'fehlt' }.
```

**Kein `leereLogoBestand()`.** Das Gegenstück zu `leereMotivBestand()` (M4-17) gibt es hier
absichtlich **nicht**: Die `Marke` ist „in v1 gebündelt und read-only" (TK 9.11.2), sie kann sich
zur Laufzeit nicht ändern, und das Logo gehört keinem Projekt. Ein Leeren hätte keinen Auslöser und
wäre nur eine weitere Stelle, an der das Logo verschwinden kann.

## Fremde Funktionen und Typen, die du benutzt
```ts
// M4-17 – src/renderer/template-canvas/bild-laden.ts (DEFINIERT den Typ, du importierst ihn nur)
export type Motiv =
  | { zustand: 'geladen'; bild: ImageBitmap | HTMLImageElement; breite: number; höhe: number }
  | { zustand: 'fehlt' }

// Mal in dieser Datei: M4-21 nimmt genau diesen einen Typ entgegen, gleichgültig ob das Motiv aus
// einem Projekt oder aus dem Bundle stammt.

// #52 – src/shared/contracts/marke.ts (Ausschnitt)
export interface Marke {
  logo: { datei: string; seitenverhaeltnis: number }   // Balken ist im Asset enthalten
  // …

```
```ts
// M4-23 – src/renderer/template-canvas/zeichne-segment.ts – DEIN AUFRUFER beim Zeichnen:
//   bindung === 'logo'  →  zeichneBildZone(ctx, zone, holeLogo(), marke)
// M4-21 – src/renderer/template-canvas/zone-bild.ts – zeichnet das Ergebnis:
```

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.** Wer den Aufruf still an eine abweichende Signatur
anpasst, macht aus einem Vertragsfehler einen unsichtbaren – und derselbe Typ existiert dann in
zwei Fassungen im Projekt.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `marke` (`bereiteLogoVor`) | die gebündelte, read-only Marke (#52, aus `config-store.leseMarke`) | wird nicht verändert und nicht zwischengespeichert; `marke.logo.datei` nicht leer und nicht nur Leerraum, sonst wirft die Funktion |
| – (`holeLogo`) | kein fachlicher Eingang | – |

Ausgang bei Erfolg: `bereiteLogoVor` löst mit `void` auf, sobald das Logo dekodiert im Bestand
liegt; `holeLogo()` liefert danach `{ zustand: 'geladen', bild, breite, höhe }` – `bild` ist
**fertig dekodiert**, nicht nur geladen.
Ausgang bei Fehler: `{ zustand: 'fehlt' }` aus `holeLogo()`. **Keine** `Ergebnis<T>`-Hülle und
**kein** `throw` bei Ladefehlern (Begründung s. Festlegung 4).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „Der **feste Markenrahmen** wird **immer** gezeichnet (Logo, Grundgestaltung) und ist **nicht
  abschaltbar** (FA-11); gestalterischer Spielraum besteht ausschließlich in den **freien Zonen**
  (FA-12)." (TK 9.10.5)
- „**Bilder sind vor dem Zeichnen dekodiert.** Der Aufruf wartet auf das Motiv (geladen über
  `media://`, 9.5.7) – sonst entsteht ein Segment ohne Bild." (TK 9.10.3, Punkt 4)
  **Zur Einordnung (keine Abweichung):** Der Klammerzusatz `media://` beschreibt die
  **Projektmedien** (M4-17). Für das gebündelte Logo gilt derselbe Satz ohne den Klammerzusatz: Es
  ist dekodiert, bevor gezeichnet wird. Ein anderer Ladeweg wäre für ein Bundle-Asset gar nicht
  möglich – s. „Nicht selbst entscheiden".
- „Kennt **keine** Dateisystem-Pfade – Motive kommen ausschließlich über `media://` (9.5.7)."
  (TK 9.10.8) – auch hier entsteht **kein** Dateisystem-Pfad: kein `fs`, kein `path`, kein
  `file://`, kein absoluter Pfad. Geladen wird über eine vom Bundler erzeugte URL.
- „**Playfair Display ist auf Windows/macOS nicht vorinstalliert.** Die Marken-Schriften werden daher
  als **Dateien mit der App gebündelt** und explizit registriert/geladen (`FontFace`), bevor
  gezeichnet wird." (TK 9.10.4) – dasselbe Muster gilt für das Logo: **gebündelt** und **vor** dem
  Zeichnen geladen.
- „**Logo 420×120**, **oben links** (Seitenverhältnis des Assets ≈ 3,5 : 1; der dunkle Balken ist im
  Logo-Asset **enthalten** – es braucht keine eigene Hintergrundzone)." (TK 9.11.1)
- **ZURÜCKGENOMMEN – nicht mehr als Vorgabe lesen.** Bis TK v3.3 stand in 9.11.2 „Marke ist in
  v1 gebündelt und read-only (`config-store.leseMarke`, 9.5.6); ein Marken-Editor ist kein MVP."
  Heute gilt: „**Marken sind ein app-weiter Bestand und bearbeitbar** (`marken-store`, 9.15.1;
  FA-23/FA-24)" (TK 9.11.2). `leseMarke` liegt im `marken-store` und trägt eine `markeId`
  (TK 9.15.1).
- „**Gleiche Eingabe → gleiches Bild.** Keine Zeit-, Zufalls- oder Zustandsabhängigkeit (keine
  Animation, kein Datum, kein `Math.random`)." (TK 9.10.3, Punkt 5)
- „Es gibt **keinen zweiten Zeichenpfad.** Anzeige und Export stammen immer aus **demselben** Aufruf
  – sonst driften Vorschau und Endvideo auseinander." (TK 9.10.1) – diese Datei zeichnet **nichts**.

**Festlegungen dieses Issues (verbindlich, keine Zitate):**
1. **`new Image()` + `await img.decode()`, niemals `onload`.** Reihenfolge: Element erzeugen, `src`
   setzen, dann `decode()` awaiten (`decode()` auf einem Bild ohne `src` lehnt ab). `onload`,
   `addEventListener('load', …)` und `img.complete` kommen in dieser Datei nicht vor. Begründung:
   `onload` bedeutet „die Bytes sind da", **nicht** „das Bild ist dekodiert" – ein zu früh
   gezeichnetes Segment trüge dauerhaft ein halbes oder gar kein Logo.
2. **`breite`/`höhe` sind `naturalWidth`/`naturalHeight` des dekodierten Bildes** – dieselbe Regel
   wie in M4-17, damit M4-21 für **beide** Bildquellen mit denselben zwei Feldern rechnet und
   `contain`/`cover` nicht je Quelle anders ausfällt.
3. **`marke.logo.seitenverhaeltnis` wird hier NICHT gelesen** und **nicht** gegen die echten
   Bildmaße geprüft. Die Geometrie bestimmt allein der Zonenrahmen der Vorlage plus
   `bild.einpassung` (M4-21); der Wert im Datenmodell ist eine Angabe für den, der Vorlagen
   entwirft. Eine Korrektur „weil das Verhältnis nicht passt" wäre ein zweiter, unsichtbarer
   Layout-Pfad.
4. **Keine `Ergebnis<T>`-Hülle, kein `throw` bei Ladefehlern.** TK 9.1.1 gilt laut eigenem Wortlaut
   für „**jede** Operation über die Renderer↔Main-Grenze"; diese Datei bleibt vollständig im
   Renderer. Ein fehlendes Logo ist außerdem ein **vorgesehener Zustand mit definiertem Bild**: der
   Platzhalter aus M4-21. Genau so wird der Ausfall sichtbar, statt lautlos zu verschwinden.
5. **Ein abgelehnter Ladeversuch wird nicht gemerkt.** Sonst wäre nach einem einzigen (womöglich
   vorübergehenden) Fehlschlag die **ganze Sitzung** ohne Logo, ohne Wiederholungsmöglichkeit – und
   jedes Segment trüge die Defektanzeige.
6. **Ein einziger Bestand, kein weiterer Cache.** Eine modul-globale Variable für das gemerkte
   Promise und das Ergebnis; **kein** `localStorage`/`sessionStorage`/`IndexedDB`, keine `Map` nach
   Dateinamen, kein zweites Logo. Es gibt genau **eine** Marke und genau **ein** Logo.
7. **Kein eigener Timeout.** Das Logo liegt im Bundle, also lokal. Ein künstlicher Abbruch nach n
   Millisekunden machte das Ergebnis zeitabhängig und verletzte „Gleiche Eingabe → gleiches Bild":
   derselbe Aufruf lieferte auf einem langsamen Rechner `fehlt`, auf einem schnellen das Logo.
8. **Das Bild wird nicht in den DOM gehängt**, bekommt kein `crossOrigin`, kein `loading`-Attribut
   und keine Größenattribute. Es dient allein als Quelle für `ctx.drawImage`.
9. **Diese Datei zeichnet nicht und kennt keinen Canvas.** Kein `ctx`, kein `drawImage`, kein
   `createElement('canvas')`. Sie beschafft nur ein `Motiv`.

| Situation | Code | Verhalten |
|---|---|---|
| Die Logo-Datei fehlt im Bundle oder die URL liefert nichts | – (kein IPC-Fehlercode; die Funktion überschreitet keine IPC-Grenze) | `{ zustand: 'fehlt' }` im Bestand, **kein** `throw`; `bereiteLogoVor` löst normal auf |
| Bytes kommen an, sind aber kein dekodierbares Bild (beschädigt, unbekanntes Format) | – | `decode()` lehnt ab → `{ zustand: 'fehlt' }` |

| `marke` ist `null`/`undefined` oder `marke.logo.datei` ist leer bzw. nur Leerraum | – | wirft (Programmierfehler: die Marke ist gebündelt und read-only, TK 9.11.2) |

## Nicht selbst entscheiden – STOPP und fragen
- **Wie aus `marke.logo.datei` eine ladbare URL wird – das ist offen und darf nicht geraten
  werden.** Zwei Dinge fehlen: (a) **wo** die Logo-Datei physisch liegt – #52 nennt nur das Feld,
  und #29 (`config-store.leseMarke`) führt ausdrücklich als offen, „woher die gebündelte
  Markendatei physisch stammt"; (b) **wie** der Renderer-Bundler einen zur **Laufzeit** gelesenen
  Dateinamen in eine URL übersetzt – ein Bundler löst normalerweise nur **statisch** bekannte
  Importe auf. Das ist eine **empirische Frage am laufenden Grundgerüst** (einmal ausprobieren,
  nicht ableiten) und zugleich eine Vertragsfrage an #8/#29. Baue insbesondere **nicht** auf
  Verdacht: keinen erratenen Pfad, kein `fetch` auf `/assets/...`, kein `require`, kein
  `import()` mit zusammengesetztem Pfad, kein Einbetten der Datei als Data-URI in den Quelltext,
  und **auf keinen Fall** einen zweiten Ladeweg als Rückfallebene. Vorlegen.
- **Verbot – kein `media://`.** Dieses Protokoll (#50) löst ausschließlich innerhalb des
  Medienordners eines Projekts auf und lehnt alles andere ab; eine `media://`-URL mit
  `marke.logo.datei` liefert also **immer** `fehlt`. Sie wäre außerdem eine zweite Auffassung davon,
  was ein Projektmedium ist.
- **Verbot – das Logo nicht in ein Projekt kopieren**, weder beim Anlegen noch beim Import. Es
  gehört keinem Projekt; eine Kopie je Projekt wäre eine zweite Wahrheit über das Markenlogo, die
  nach einem App-Update veraltet.
- **Verbot – keinen dritten Motiv-Zustand erfinden** („lädt noch", „unbekannt") und den Typ `Motiv`
  nicht hier neu definieren. Er gehört M4-17.
- **Offen (empirisch, gemeinsam mit M4-24): Verunreinigt das geladene Logo das Canvas?** Ein Canvas,
  in das ein Bild fremder Herkunft gezeichnet wurde, gilt als „tainted"; `toBlob` wirft dann einen
  `SecurityError`, und **jeder** PNG-Export scheitert – bei einem Logo in jeder Vorlage also bei
  **jedem** Segment. Ob das für den Bundle-Ladeweg zutrifft, hängt davon ab, unter welcher Herkunft
  der Renderer die Seite lädt. Tritt der Fehler auf: **melden**, nicht umgehen. Der naheliegende
  Ausweg – das Logo erst in einen Data-URI verwandeln – ist genau die Base64-Krücke, die der
  IPC-Vertrag verbietet (TK 9.1, Punkt 3).
- **Offen: Wer `bereiteLogoVor` wann aufruft.** Naheliegend ist der App-Start, sobald die Marke
  gelesen ist – aber der Aufrufer ist ein Renderer-Bildschirm aus M5, und dort ist die
  Start-Reihenfolge noch nicht festgelegt. Ruf dich **nicht** selbst auf (kein Aufruf beim
  Modul-Import, kein „lazy" Nachladen aus `holeLogo` heraus): Ein Ladevorgang, den niemand angestoßen
  hat, läuft irgendwann – und „irgendwann" ist genau die Zeitabhängigkeit, die TK 9.10.3 Punkt 5
  ausschließt.
