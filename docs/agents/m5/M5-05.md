### Issue M5-05: [composer] Ein Element aus der Wiedergabeliste entfernen

## Ziel (in einem Satz)
Ein Listenelement verschwindet aus der Wiedergabeliste – und **nur** von dort: Das referenzierte
Medium und die referenzierte Aktion bleiben in ihren Bibliotheken erhalten.

## Modul & Datei
- Modul: `composer` [P3] (Renderer)
- Datei: `src/renderer/composer/element-entfernen.ts`
- Vertrag: Technisches Konzept **9.7.2** (Instant-Mutationen), **9.5.2** (`entferneElement`),
  **9.7.5** (Fix-Option im Reparatur-Modus), **9.5.3** (Löschsemantik) – Quelle der Wahrheit
- Prozess/Speicher: P3

## Warum das im Gesamtsystem wichtig ist
Diese Datei sieht harmlos aus und sitzt an einer heiklen Stelle: Der geführte Reparatur-Modus
(TK 9.7.5, FA-19) benutzt genau diesen Weg als eine seiner drei Fix-Optionen. Sie muss deshalb auch
auf einem **kaputten** Element funktionieren – auf einem, dessen Referenz auf ein Asset mit
`zustand: 'fehlt'` zeigt. Wer hier eine „Sicherheitsprüfung" einbaut („Element ist kaputt, erst
reparieren"), verriegelt die Reparatur gegen sich selbst: Der Nutzer soll das Element ja gerade
loswerden dürfen.

Der zweite Punkt ist die Löschgrenze. „Entfernen" heißt hier **nur** den Listeneintrag streichen.
Ein Medium zu löschen ist ein **Auftrag** des `media-service` (blockiert sogar bei Referenz), eine
Aktion zu löschen eine eigene Operation mit chirurgischer Kaskade (#40). Wer diese Wege hier
zusammenfasst („Element weg, dann brauchen wir die Datei ja nicht mehr"), löscht dem Nutzer Material,
das an anderer Stelle noch verwendet wird – Aktionen sind ausdrücklich mehrfach referenzierbar, und
ein Asset kann in mehreren Listenelementen **und** in Aktionen stecken.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/composer/element-entfernen.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'

/** Entfernt genau ein Listenelement aus der Wiedergabeliste. */
export async function entferneElementAusListe(elementId: string): Promise<Ergebnis<void>>
```

**Der Name ist bewusst NICHT `entferneElement`.** So heisst die Main-Operation (#42,
`src/main/project-store/entferne-element.ts`); zwei gleichnamige Exporte auf beiden Seiten der
Prozessgrenze laden dazu ein, in einer Importzeile die falsche zu erwischen – und der Fehler fiele
erst zur Laufzeit auf, weil beide dieselbe Signatur haben. Die Nachbardatei M5-04 ist durch den
Umlaut unterschieden (`fuegeElementHinzu` gegen `fügeElementHinzu`); hier fehlte die Trennung, also
trägt der Renderer-Export den Zusatz `AusListe` – er sagt zugleich, was die Datei tut und was sie
ausdrücklich **nicht** tut (Medium oder Aktion löschen).

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `elementId` | ID des zu entfernenden Listenelements | nicht leerer String; die Existenzprüfung macht #42 (`nicht_gefunden`) |

Ausgang bei Erfolg: `Ergebnis<void>` mit `ok: true`; das Element ist aus der Sicht entfernt, die
übrigen behalten ihre relative Reihenfolge.
Ausgang bei Fehler: das **unveränderte** `Ergebnis` des Main – bei unbekannter `elementId`
`nicht_gefunden` (#42); die Sicht bleibt dann unverändert.

## ENTSCHIEDEN (lokale Festlegungen dieses Issues)
1. **Entfernen läuft NICHT optimistisch.** TK 9.7.3 nennt als optimistisch bediente Vorgänge
   ausdrücklich „Reorder/Trim/Dauer" – Entfernen steht dort nicht. Das Element verschwindet erst
   nach `ok: true` aus der Sicht. Begründung: Die Instant-Operation arbeitet im Arbeitsspeicher
   (TK 9.5.4, „Instant-Op vs. Speichern getrennt") und antwortet praktisch sofort; ein optimistisch
   verschwundenes und nach einer Ablehnung wieder auftauchendes Element ist für den Nutzer
   verwirrender als die minimale Verzögerung – und es gäbe eine zweite Rollback-Stelle neben M5-07.
2. **Die Sicht wird über die vollständige neue Liste aktualisiert** (`setzeListe` mit der um das
   Element verkürzten Liste), nicht durch ein Herausschneiden im vorhandenen Array. Begründung:
   die Unveränderlichkeits-Invariante aus M5-02 – ein zuvor genommener Stand darf sich nicht
   nachträglich verändern.
3. **Keine Rückfrage, keine Bestätigung, kein Papierkorb in dieser Datei.** Ob die Oberfläche vorher
   fragt, entscheidet die Oberfläche. Ein Rückgängig-Weg ist **Undo/Redo** und gehört zu FA-21 /
   TK 9.13 – ausdrücklich **nicht** M5. Baue hier **keinen** Undo-Stapel und **kein**
   „zuletzt entfernt"-Gedächtnis.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „`entferneElement` | `elementId` → `Ergebnis<void>`" (TK 9.5.2)
- „**Fix-Optionen je Element:** Medium **neu verknüpfen/importieren** (media-service), durch ein
  **anderes ersetzen** (Referenz umsetzen), oder das **Element entfernen** (`entferneElement`,
  project-store). Es werden ausschließlich bestehende Operationen genutzt." (TK 9.7.5) – daraus
  folgt: Diese Datei ist auch der Weg des Reparatur-Modus und darf ein kaputtes Element **nicht**
  ablehnen.
- „Die von der Aktion **verwendeten Medien-Assets bleiben unangetastet** und projektweit verfügbar –
  eine Aktion *referenziert* ein Asset nur, sie besitzt es nicht." (TK 9.5.3) – sinngemäß hier: Das
  Entfernen eines Listeneintrags fasst weder `Project.assets` noch `Project.aktionen` an.
- „**Medium löschen** (`media-service` 9.4.6): **blockiert** bei Referenz (`asset_referenziert`). Die
  Datei ist die schwere, geteilte Ressource; versehentlicher Verlust wäre teuer." (TK 9.5.3) – der
  Löschweg für Medien ist ein **anderer** und läuft als Auftrag; er wird hier nicht angestoßen.
- „**Die Reihenfolge ist die Array-Reihenfolge von `liste`** – es gibt **kein** separates
  `position`-Feld." (TK 9.11.3) – nach dem Entfernen rückt alles auf; es bleibt kein Platzhalter,
  keine Lücke, kein `undefined` im Array.
- „**`project-store` ist die Wahrheit:** die Liste im composer ist nur eine Sicht; nach jeder
  Mutation mit dem Rückgabestand abgleichen." (TK 9.7.4)

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `elementId` ist leer oder kein String | `ungueltige_eingabe` | **kein** IPC-Aufruf, Sicht unverändert |
| kein Projekt geladen (`holeSicht().projekt === null`) | `ungueltige_eingabe` | **kein** IPC-Aufruf |
| Main antwortet `nicht_gefunden` | Code **unverändert** vom Main | Sicht unverändert – insbesondere wird das Element **nicht** „vorsichtshalber" auch lokal entfernt |
| Main antwortet mit einem anderen `ok: false` | Code **unverändert** | Sicht unverändert |
| Auto-Speichern schlägt später fehl | – | **kein** Rollback, **keine** Zuständigkeit dieser Datei – das behandelt M5-07 (Klasse 2) |

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – kein Löschen von Medien oder Aktionen.** Diese Datei ruft **ausschließlich**
  `project:entferneElement`. Kein `media:`-Kanal, kein `project:löscheAktion`, keine „Aufräumen"-
  Logik („das Asset wird jetzt nirgends mehr benutzt"). Verwaiste Medien behandelt der Reconcile des
  `media-service` (TK 9.4.7), nicht der `composer`.
- **Verbot – keine Zusatzprüfung auf kaputte Elemente.** Ein Element, dessen Referenz auf ein
  `fehlt`-Asset zeigt, wird **genauso** entfernt wie ein heiles. Es ist ausdrücklich einer der drei
  Reparatur-Wege (TK 9.7.5).
- **Verbot – kein Undo.** FA-21 / TK 9.13 ist M7. Kein Stapel, kein „rückgängig"-Puffer, kein
  Zwischenspeichern des entfernten Elements „für später".
- **Offen: Entfernen mehrerer Elemente auf einmal.** Weder AD noch TK 9.7 sehen eine
  Mehrfachauswahl vor, und `entferneElement` (#42) nimmt genau eine ID. Umgesetzt wird das Entfernen
  **eines** Elements; eine Stapelvariante **nicht** eigenmächtig ergänzen – sie müsste festlegen, was
  bei einem Fehlschlag mitten in der Reihe geschieht.
- **Offen: was passiert, wenn das letzte Element entfernt wird.** Ob eine leere Liste zulässig ist,
  führt #42 ausdrücklich als offenen Punkt (der Main entscheidet es). Diese Datei prüft es
  **nicht** vorab und reicht die Antwort des Main durch.
