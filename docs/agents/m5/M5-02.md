### Issue M5-02: [composer] Projektzustand laden und als Sicht halten

## Ziel (in einem Satz)
Der `composer` hält den Projektzustand als **Sicht** auf den `project-store` – geladen über den
IPC-Vertrag, nach jeder Mutation mit dem Rückgabestand abgeglichen, nie als zweite Wahrheit.

## Modul & Datei
- Modul: `composer` [P3] (Renderer)
- Datei: `src/renderer/composer/projektzustand.ts`
- Vertrag: Technisches Konzept **9.7.4** (Invariante „`project-store` ist die Wahrheit"), **9.7.1**
  (Grenze), **9.5.4** (Instant-Op vs. Speichern), **9.1.1** (IPC-Konventionen) – Quelle der Wahrheit
- Prozess/Speicher: P3; **kein** eigener Speicher – reiner Laufzeitzustand im Renderer

## Warum das im Gesamtsystem wichtig ist
Diese Datei ist der **einzige** Ort, an dem der `composer` weiß, wie die Wiedergabeliste gerade
aussieht. Alle anderen composer-Issues (Reorder, Hinzufügen, Entfernen, Dauer/Trim, Gesamtlänge,
Thumbnails, Reparatur-Modus) lesen von hier. Entsteht daneben eine zweite Zustandsquelle – eine
lokale Kopie der Liste in einer Komponente, ein zweiter Store, ein „schneller" Zwischenspeicher –,
laufen beide auseinander: Der Nutzer sieht dann eine Reihenfolge, die es in `project.json` nicht
gibt, und **erst die gerenderte Ausgabedatei** deckt den Unterschied auf. Genau deshalb formuliert
TK 9.7.4 die Invariante so scharf.

Der zweite teure Fehler wäre, den Zustand **in place** zu ändern (das Element im Array direkt
umschreiben). Dann gibt es keinen „letzten bestätigten Stand" mehr, auf den ein Rollback (TK 9.7.3,
Fehlerklasse 1) zurückkehren könnte – der optimistische Schritt hätte die alte Wahrheit bereits
überschrieben, und ein abgelehnter Aufruf ließe die Oberfläche in einem Zustand zurück, den weder
Nutzer noch Store kennen.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/composer/projektzustand.ts
import type { Project, Listenelement } from '../../shared/contracts/project'
import type { Ergebnis } from '../../shared/contracts/ergebnis'

export interface Projektsicht {
  projekt: Project | null          // null = noch kein Projekt geladen
  ladefehler: { code: string; meldung: string } | null
}

/** Lädt ein Projekt über den IPC-Vertrag und macht es zur aktuellen Sicht. */
export async function ladeProjekt(projektId: string): Promise<Ergebnis<Project>>

/** Momentaufnahme der Sicht. Der zurückgegebene Wert wird NIE verändert (s. Invarianten). */
export function holeSicht(): Projektsicht

/** Ersetzt die Liste der Sicht vollständig – benutzt für den optimistischen Schritt UND für den
 *  Rollback auf einen zuvor mit holeSicht() genommenen Stand. */
export function setzeListe(liste: Listenelement[]): void

/** Ersetzt genau ein Listenelement anhand seiner id durch den vom Store zurückgegebenen Stand. */
export function gleicheElementAb(element: Listenelement): void

/** Ersetzt das gesamte Projekt (nach dem Laden und nach Operationen, die ein Projekt liefern). */
export function setzeProjekt(projekt: Project): void

/** Abonnement für Sicht-Änderungen; Rückgabewert ist die Abmelde-Funktion. */
export function aufSichtGeaendert(hoerer: (sicht: Projektsicht) => void): () => void
```

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projektId` | Projekt, das geladen werden soll | nicht leerer String; **keine** fachliche Prüfung hier – der Main validiert (TK 9.1.1, Punkt 6) |
| `liste` (`setzeListe`) | vollständige neue Liste der Sicht | ersetzt die vorhandene komplett; kein Mischen, kein Anhängen |
| `element` (`gleicheElementAb`) | vom Store zurückgegebenes `Listenelement` | wird anhand `element.id` ersetzt; unbekannte `id` → s. Fehlerpfade |

Ausgang bei Erfolg (`ladeProjekt`): `Ergebnis<Project>` mit dem geladenen Projekt; die Sicht trägt
danach dieses Projekt, `ladefehler` ist `null`, und alle Hörer wurden **einmal** benachrichtigt.
Ausgang bei Fehler (`ladeProjekt`): das **unveränderte** `Ergebnis` des Main (Codes u. a.
`nicht_gefunden`, `speicher_fehler`, `ungueltige_eingabe`); die Sicht behält `projekt: null` bzw. das
**bisher** geladene Projekt und trägt den Fehler in `ladefehler`.
Die übrigen Funktionen liefern `void` und können nicht fehlschlagen (reine Zustandsführung).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**`project-store` ist die Wahrheit:** die Liste im composer ist nur eine Sicht; nach jeder
  Mutation mit dem Rückgabestand abgleichen." (TK 9.7.4)
- „**Angezeigte Reihenfolge = gerenderte Reihenfolge** – keine versteckte Sortierung." (TK 9.7.4) –
  diese Datei sortiert **nichts**; sie übernimmt die Array-Reihenfolge, wie sie kommt.
- „**Die Reihenfolge ist die Array-Reihenfolge von `liste`** – es gibt **kein** separates
  `position`-Feld." (TK 9.11.3)
- „**Instant-Op vs. Speichern getrennt:** Eine Instant-Operation (9.5.2) validiert und wendet **im
  Speicher** an, *bevor* sie „ok" meldet – ihr Erfolg bedeutet „gültig übernommen", **nicht** „schon
  auf Platte"." (TK 9.5.4) – ein `ok: true` ist für diese Sicht die Bestätigung; **auf keinen Fall**
  wartet sie zusätzlich auf ein Speicher-Signal, sonst hinge die Oberfläche 3–5 s hinterher.
- „**Ist NICHT:** rendert **keine** Pixel …; bearbeitet **keine** Aktions-Inhalte (`action-editor`
  [P2]) – er *platziert* Aktionen nur; berührt **kein** Dateisystem/ffmpeg (alles über `ipc-client`
  an den Main)." (TK 9.7.1)
- **Unveränderlichkeit (Entscheidung dieses Issues, kein TK-Zitat):** Weder die Sicht noch ein
  einzelnes `Listenelement` wird jemals **an Ort und Stelle** verändert. Jede Änderung erzeugt ein
  **neues** Array bzw. ein neues Elementobjekt. Begründung: Der Rollback aus TK 9.7.3 („letzter
  bestätigter Stand") ist nur möglich, wenn ein zuvor mit `holeSicht()` genommener Stand von einer
  späteren Änderung **nicht** mitverändert wird. Genau diese Verwechslung – lebende Einträge statt
  Kopien – hat im Prüflauf von M2 eine Garantie lautlos gebrochen.

## Fremde Funktionen, die du aufrufst (abgeschrieben aus der definierenden Quelle)
Der umsetzende Agent sieht die anderen Issues nicht; hier stehen die Signaturen vollständig.
**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.**

```ts
// #24 – src/renderer/ipc-client/rufe-auf.ts   (der EINZIGE Weg des Renderers zum Main)
export async function rufeAuf<T, F extends string = GenerischerFehlercode>(
  kanal: string,
  nutzlast?: unknown,
): Promise<Ergebnis<T, F>>
// reicht die Antwort des Main UNVERÄNDERT durch, castet nur den Typ

// #25/#76 – src/shared/contracts/kanaele.ts (Kanalnamen kommen NUR von hier, nie als Literal)
KANAELE.project.öffneProjekt   // === 'project:öffneProjekt'
// Nutzlast-Form laut #76 (verbindlich):  { id }   →  Main ruft oeffneProjektAblauf(nutzlast.id)
// Rückgabe: Ergebnis<Project>

// #15 – src/shared/contracts/project.ts
export interface Project {
  id: string; name: string; erstelltAm: string; geaendertAm: string; schemaVersion: number
  assets: Asset[]; aktionen: Aktion[]; liste: Listenelement[]
  letzterAusgabeName: string | null
}
```

**Wichtig zu `project:öffneProjekt`:** Dieser Kanal ruft im Main **nicht** nur `öffneProjekt` (#34),
sondern den Ablauf `oeffneProjektAblauf` (#94) – Projekt laden, Q2 wiederherstellen, **Reconcile**
(fehlende Medien werden auf `zustand: 'fehlt'` gesetzt, verwaiste Dateien entfernt). Er ist damit
**kein** billiger Lesezugriff und hat **Nebenwirkungen**. Siehe STOPP.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `ladeProjekt` bekommt vom Main `ok: false` | Code **unverändert** vom Main | Sicht bleibt auf dem bisherigen Stand; `ladefehler` wird gesetzt; Hörer werden benachrichtigt |
| `projektId` ist leer oder kein String | `ungueltige_eingabe` | **kein** IPC-Aufruf; Sicht unverändert (diese eine Prüfung passiert lokal, damit ein offensichtlicher UI-Bug nicht als Main-Fehler erscheint) |
| `gleicheElementAb` bekommt ein Element, dessen `id` nicht in der Sicht vorkommt | – (kein Fehler nach außen) | Sicht bleibt unverändert; der Vorgang wird über `console.warn` sichtbar gemacht – ein stiller Einbau eines unbekannten Elements ist verboten, weil er eine zweite Wahrheit erzeugen würde |
| `setzeListe`/`gleicheElementAb`/`setzeProjekt` ohne geladenes Projekt (`projekt === null`) | – (kein Fehler nach außen) | Aufruf wird ignoriert, Sicht bleibt `null`; ebenfalls über `console.warn` sichtbar |

## Nicht selbst entscheiden – STOPP und fragen
- **Es gibt keinen Lese-Kanal für den aktuellen Projektstand – und das ist eine Vertragslücke.**
  Die einzige Möglichkeit, ein `Project` aus dem Main zu bekommen, ist `project:öffneProjekt`, und
  der löst laut #76/#94 den kompletten Öffnen-Ablauf samt **Reconcile** aus. Ein „Auffrischen" der
  Sicht darüber wäre also ein Nebenwirkungs-Aufruf. Verschärfend: `ordneNeu` (#43) und
  `entferneElement` (#42) liefern `Ergebnis<void>` – bei ihnen gibt es **gar keinen Rückgabestand**,
  mit dem TK 9.7.4 verlangt abzugleichen. **Bis zur Klärung gilt:** Nach einem `ok: true` einer
  void-Operation übernimmt die Sicht den optimistisch bereits angezeigten Stand als bestätigt
  (der Main hat ihn ja gerade validiert), und `project:öffneProjekt` wird **niemals** als
  Auffrisch-Aufruf benutzt. Ob ein zusätzlicher, nebenwirkungsfreier Kanal (etwa
  `project:leseProjekt`) in den Vertrag gehört, ist eine Vertragsentscheidung – **melden, nicht
  selbst einführen**.
- **Wer `ladeProjekt` aufruft und woher die `projektId` kommt, ist NICHT Sache dieser Datei.** Die
  Projektverwaltung (FA-10) und die Sitzungswiederherstellung (FA-15, zuletzt aktives Projekt aus
  dem `config-store`) gehören zur `app-shell` (M7, TK 9.14). Baue hier **keinen** Autostart, **kein**
  Lesen des `config-store` und **keine** Projektauswahl ein – sonst gibt es zwei Stellen, die
  entscheiden, welches Projekt geladen ist.
- **Verbot – kein Zustand außerhalb dieser Datei.** Keine Kopie der Liste in einer React-Komponente,
  kein zweiter Store, kein Zwischenspeicher „für die Performance". Andere composer-Dateien lesen
  ausschließlich über `holeSicht()`/`aufSichtGeaendert`.
- **Verbot – kein `window.api`, kein `ipcRenderer`, kein `fs`.** Jeder Aufruf geht über `rufeAuf`
  (#24); Kanalnamen kommen aus `KANAELE` (#25), niemals als String-Literal.
- **Offen: ob diese Datei die React-Anbindung (Hook/Context) gleich mitbringt.** Der Dateiname ist
  `projektzustand.ts` (kein `.tsx`), und die Bindung an React-Komponenten ist Sache der
  Oberflächen-Issues. Umgesetzt wird deshalb ein **framework-freier** Zustandsbehälter mit
  Abonnement; ob zusätzlich ein `useProjektsicht`-Hook gewünscht ist und wo der liegen soll,
  **nicht selbst entscheiden**.
