### Issue M5-27: [vorlagen-editor] Die Zonen-Liste als Zeichenreihenfolge führen

## Ziel (in einem Satz)
Der Editor zeigt die Zonen in genau der Reihenfolge, in der sie gezeichnet werden, und ein Ziehen in
dieser Liste ändert die Überlagerung – ohne `z-index`, ohne jede Sortierung, und ohne dass feste
Zonen ihren Platz verlassen.

## Modul & Datei
- Modul: `vorlagen-editor` (Renderer)
- Datei: `src/renderer/vorlagen-editor/zonen-liste.ts`
- Vertrag: Technisches Konzept **9.12.2** (Quelle der Wahrheit), ergänzend **9.11.1** (Punkt 2:
  Zeichenreihenfolge; Punkt 4: feste Zonen)
- Prozess/Speicher: P7; kein Speicher – reine Umordnung im Arbeitsspeicher

## Warum das im Gesamtsystem wichtig ist
Die Überlagerung der Zonen ist im ganzen System **ausschließlich** über die Array-Reihenfolge
ausgedrückt – es gibt kein `z-index`-Feld und keine Ebenen-Nummer im Datenmodell. Der Zeichner
(#117) durchläuft `vorlage.zonen` von vorne nach hinten; was später kommt, liegt oben. Diese Liste
ist damit **die einzige Bedienoberfläche für die Überlagerung**, und drei Fehlgriffe sind hier
besonders teuer, weil sie sich erst im fertigen MP4 zeigen:

1. **Anzeigen in einer anderen Reihenfolge, als gezeichnet wird.** Sortiert die Liste alphabetisch,
   nach Position oder „Freie zuerst", denkt der Nutzer in einer Ordnung, die es im Datensatz nicht
   gibt. Ein Ziehen muss dann zurückgerechnet werden – und ein Off-by-one dabei vertauscht lautlos
   Scrim und Text.
2. **Ein eigenes Ebenen-Feld erfinden.** Damit gäbe es zwei Quellen für dieselbe Information; die
   Vorlage würde in `vorlagen.json` mit einem Feld landen, das der Typ `Zone` (#95) gar nicht
   kennt, oder – schlimmer – die Reihenfolge im Array bliebe die alte, während die Anzeige die neue
   zeigt.
3. **Eine feste Zone verschieben.** Der `hintergrund` wird bewusst **zuerst** gezeichnet, „das Bild
   einer Aktion ist **optional** (FA-02) – ohne diese Zone würde eine Aktion ohne Motiv **schwarz**
   rendern statt markenkonform" (TK 9.11.1). Rutscht er nach oben, verdeckt eine deckende Fläche das
   ganze Segment: ein einfarbiges Bild im Endvideo, ohne jede Fehlermeldung. Der Store lehnt so eine
   Vorlage beim Speichern zwar ab (#102 prüft die relative Reihenfolge der festen Zonen), aber erst
   dann – die Arbeit ist bis dahin gemacht.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/vorlagen-editor/zonen-liste.ts
import type { Ergebnis } from '../../shared/contracts/ergebnis'
import type { Vorlage, Zone } from '../../shared/contracts/vorlage'

/** Eine Zeile der Zonen-Liste. Die Reihenfolge der Zeilen IST die Zeichenreihenfolge. */
export interface ZonenListenEintrag {
  zone: Zone
  index: number       // Position in vorlage.zonen – identisch mit der Position in dieser Liste
  ebene: number       // index + 1; 1 = zuunterst, die höchste Zahl = zuoberst. NUR Anzeigetext.
  beweglich: boolean  // zone.rolle === 'frei' – nur diese Zeilen sind ziehbar
}

/** Baut die Liste. Reine Abbildung 1:1 auf vorlage.zonen – ohne jede Sortierung. */
export function baueZonenListe(vorlage: Vorlage): ZonenListenEintrag[]

/**
 * Verschiebt den Eintrag von `vonIndex` an die Position `nachIndex`.
 * Liefert ein NEUES Array; das übergebene bleibt unverändert.
 */
export function ordneZonenNeu(
  zonen: readonly Zone[],
  vonIndex: number,
  nachIndex: number,
): Ergebnis<Zone[]>
```

**`ebene` ist ausschließlich ein Anzeigewert und wird nirgends gespeichert.** Er wird bei jedem
`baueZonenListe` neu aus `index` berechnet und existiert im Typ `Zone` (#95) nicht. Er steht hier,
damit die Oberfläche „Ebene 3 von 7" schreiben kann, ohne selbst zu rechnen – nicht, um eine zweite
Ordnung einzuführen.

**Fremde Typen, die du benutzt** (der umsetzende Agent sieht die anderen Issues nicht – deshalb hier
vollständig ausgeschrieben):

```ts
// #95 – src/shared/contracts/vorlage.ts (geteilte Typen; hier NICHT neu deklarieren)
export type ZonenRolle = 'fest' | 'frei'
export interface Zone {
  id: string                      // "ueberschrift" | "motiv" | "preis" | "logo" …
  rolle: ZonenRolle               // fest = Markenrahmen (FA-11), im Editor unveränderlich
  bindung: Bindung | null
  rahmen: { x: number; y: number; breite: number; höhe: number }
  ausrichtung: { horizontal: 'links'|'mitte'|'rechts'; vertikal: 'oben'|'mitte'|'unten' }
  wennLeer: 'leer' | 'ausblenden'
  text?: ZonenText; bild?: ZonenBild; deko?: ZonenDeko
}
export interface Vorlage {
  id: string; name: string
  art: 'vollflaeche' | 'split' | 'einblendung'
  höhe: number | null
  parent: string | null
  eingebaut: boolean
  zonen: Zone[]                   // Zeichenreihenfolge = Array-Reihenfolge (später = darüber)
}

// #12/#22 – src/shared/contracts/ergebnis.ts
export type GenerischerFehlercode = 'ungueltige_eingabe' | 'nicht_gefunden' | 'unbekannter_fehler'
export type Ergebnis<T, F extends string = GenerischerFehlercode> =
  | { ok: true; wert: T }
  | { ok: false; fehler: { code: F | GenerischerFehlercode; meldung: string; daten?: unknown } }
// Diese Datei setzt `daten` NIE.
```

**Die Regel, die #102 beim Speichern erzwingt** (fremder Vertrag – wörtlich aus dem Issue des
`vorlagen-store`, damit hier nichts geraten wird):

> „Die Zonen mit `rolle: 'fest'` sind gegenüber dem gespeicherten Stand **unverändert**: gleiche
> Anzahl, gleiche `id`s, jede tief-gleich zum gespeicherten Gegenstück, und ihre **relative
> Reihenfolge** untereinander unverändert. Freie Zonen dürfen dazwischen eingefügt, entfernt und
> umsortiert werden."

**Weicht die tatsächliche Prüfung von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.** Diese Datei muss dieselbe Grenze **vorher** ziehen, damit
der Nutzer nicht erst beim Speichern erfährt, dass sein Umsortieren ungültig war.

**Ablauf von `baueZonenListe` (verbindlich):**

1. `vorlage.zonen` **in genau dieser Reihenfolge** durchlaufen und je einen Eintrag bilden:
   `{ zone, index, ebene: index + 1, beweglich: zone.rolle === 'frei' }`.
2. **Nichts sortieren, nichts umdrehen, nichts gruppieren.** Kein `sort`, kein `reverse`, kein
   „feste Zonen ans Ende". Die Liste wird in der Oberfläche **von oben nach unten** in derselben
   Reihenfolge dargestellt, in der sie hier steht: **erste Zeile = zuerst gezeichnet = unterste
   Ebene.**
   *Warum nicht umgedreht („oberste Ebene zuerst", wie in Grafikprogrammen üblich):* Jede
   Darstellungs-Umkehr ist eine zweite Ordnung, in der der Nutzer denkt und in die ein
   Drag-and-Drop-Index zurückgerechnet werden muss. Der Vertrag sagt „Zonen-Liste =
   Zeichenreihenfolge"; eine 1:1-Abbildung braucht keine Rückrechnung und kann deshalb auch keine
   verkehren. Die Spalte `ebene` macht die Bedeutung im Text sichtbar.
3. `zone` wird **als Referenz** übernommen, nicht kopiert. Diese Datei verändert keine Zone.

**Ablauf von `ordneZonenNeu` (verbindlich):**

1. `vonIndex` und `nachIndex` prüfen: ganze Zahlen im Bereich `0 … zonen.length − 1`. Sonst
   `ungueltige_eingabe`, **ohne** Wirkung.
2. `vonIndex === nachIndex` → `ok: true` mit einer **flachen Kopie** des Arrays. Kein Fehler: Ein
   Ziehen, das dort endet, wo es begann, ist eine gültige Handlung ohne Ergebnis.
3. `zonen[vonIndex].rolle === 'fest'` → `ungueltige_eingabe`, Meldung:
   `'Feste Zonen gehören zum Markenrahmen und behalten ihren Platz in der Zeichenreihenfolge.'`
4. Umordnen: das Element an `vonIndex` entfernen und an `nachIndex` **wieder einfügen** (Splice-
   Semantik – die Zielposition bezieht sich auf das Array **nach** dem Entfernen, so wie dnd-kit die
   Indizes meldet). Alle anderen Elemente behalten ihre relative Reihenfolge.
5. **Nachprüfen:** Die Folge der `id`s aller Zonen mit `rolle: 'fest'` muss im Ergebnis **identisch**
   zu der im Eingangsarray sein. Ist sie es nicht → `ungueltige_eingabe`, **das Ergebnis wird
   verworfen**.
   *Warum diese Prüfung, obwohl Schritt 3 sie schon garantiert:* Sie ist die wörtliche Umsetzung der
   Regel, die #102 beim Speichern anwendet. Steht sie hier, kann eine spätere Erweiterung (etwa
   Mehrfachauswahl oder Umordnen per Tastatur) die Regel nicht versehentlich unterlaufen – der Fehler
   fiele sonst erst im Store auf, nach dem Verlust des Zwischenstandes.
6. Das neue Array zurückgeben. Das übergebene bleibt unverändert (`readonly` im Typ, und es wird
   auch tatsächlich nicht verändert).

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `vorlage` | die bearbeitete Arbeitskopie | nur `zonen` wird gelesen |
| `zonen` | die aktuelle Zonenfolge | wird nicht verändert |
| `vonIndex` | Position des gezogenen Eintrags | ganze Zahl in `0 … length−1`; muss auf eine **freie** Zone zeigen |
| `nachIndex` | Zielposition **nach** dem Entfernen | ganze Zahl in `0 … length−1` |

Ausgang bei Erfolg: `ZonenListenEintrag[]` in Array-Reihenfolge bzw. `{ ok: true, wert: Zone[] }`
mit unveränderter relativer Reihenfolge aller festen Zonen.
Ausgang bei Fehler: `ungueltige_eingabe`. **Keine** weiteren Codes.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Zonen-Liste = Zeichenreihenfolge:** per Drag sortierbar; sie **bestimmt die Überlagerung**
  (9.11.1, Punkt 2). **Kein** `z-index`, **keine** Sortierung nach Position – sonst ist die
  Überlagerung nicht reproduzierbar." (TK 9.12.2)
- „**Zeichenreihenfolge = Array-Reihenfolge** (später gezeichnete Zone liegt oben). **Kein**
  implizites Sortieren – sonst ist die Überlagerung nicht reproduzierbar." (TK 9.11.1, Punkt 2)
- „Der Editor darf Zonen mit `rolle: "fest"` **nicht** ändern, verschieben oder entfernen
  (Markenrahmen erzwungen, FA-11)." (TK 9.11.1, Punkt 4)
- „**Feste Zonen sind sichtbar, aber gesperrt** – der Nutzer sieht den Markenrahmen, kann ihn aber
  nicht verändern." (TK 9.12.2)
- „Die Zone **`hintergrund`** (fest, dekorativ, Markenfarbe) wird **als erstes** gezeichnet. Grund:
  das Bild einer Aktion ist **optional** (FA-02) – ohne diese Zone würde eine Aktion ohne Motiv
  **schwarz** rendern statt markenkonform." (TK 9.11.1) – deshalb ist die Position der festen Zonen
  keine Geschmacksfrage.
- „es gibt **kein** separates `position`-Feld. Zwei Quellen für dieselbe Information würden
  unweigerlich auseinanderlaufen. (Gleiche Regel wie bei den Zonen einer Vorlage und beim
  `RenderRequest`, 9.2.1.)" (TK 9.11.3)

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `vonIndex` oder `nachIndex` keine ganze Zahl oder außerhalb `0 … length−1` | `ungueltige_eingabe` | keine Wirkung, kein neues Array |
| `zonen[vonIndex].rolle === 'fest'` | `ungueltige_eingabe` | keine Wirkung; Meldung nennt den Markenrahmen |
| Ergebnis änderte die relative Reihenfolge der festen Zonen | `ungueltige_eingabe` | Ergebnis verworfen; Eingangsarray unverändert |
| `vonIndex === nachIndex` | – (`ok: true`) | flache Kopie, sonst nichts |
| `zonen` ist leer | `ungueltige_eingabe` | jeder Index liegt außerhalb; keine Wirkung |

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – kein `sort`, kein `reverse`, keine Gruppierung.** Weder in `baueZonenListe` noch in der
  Ansicht, die sie darstellt. Auch nicht „nur für die Anzeige".
- **Verbot – kein `z-index` und kein Ebenen-Feld im Datensatz.** `Zone` (#95) hat kein solches Feld
  und bekommt hier keines. Weder als zusätzliche Eigenschaft noch als CSS-Wert, der die Überlagerung
  auf dem Canvas anders darstellt, als der Zeichner sie später malt.
- **Verbot – kein „nach vorne/nach hinten"-Sonderweg für feste Zonen.** Auch nicht mit Rückfrage,
  auch nicht in eigenen Vorlagen. FA-11 gilt dort genauso.
- **Verbot – Zonen werden hier nicht verändert, nicht hinzugefügt und nicht entfernt.** Diese Datei
  ordnet ausschließlich um. Das Hinzufügen gehört zu M5-28.
- **Verbot – kein Undo-Stapel.** Kein Merken der vorherigen Reihenfolge. Undo/Redo ist TK 9.13 und
  gehört nach M7.
- **Verbot – keine Bibliotheks-Annahme im Rechenteil.** dnd-kit liefert die Indizes; diese Funktion
  nimmt zwei Zahlen entgegen und kennt keine Drag-Bibliothek. Kein Import aus dnd-kit in dieser Datei.
