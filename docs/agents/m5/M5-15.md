### Issue M5-15: [composer] Render und Export auslösen

## Ziel (in einem Satz)
Der `composer` baut aus der Wiedergabeliste einen vollständigen `RenderRequest` samt fertiger
Segment- und Band-PNGs und **reiht ihn ein** – gesperrt, solange kaputte Stellen existieren –, und
reiht ebenso einen Export einer bereits gerenderten Ausgabedatei ein.

## Modul & Datei
- Modul: `composer` (Renderer)
- Datei: `src/renderer/composer/render-ausloesen.ts` – **die einzige** Datei dieses Issues
- Vertrag: Technisches Konzept **9.7.4** (Render-Sperre, Snapshot), **9.3.4** (`reiheEin`),
  **9.2.1/9.2.2** (`RenderRequest`/`RenderItem`), **9.2.6** (Ausgabename), **9.2.8** (Bandspur),
  **9.6.1** (`ExportRequest`), **9.1.1** (IPC-Konventionen) – Quelle der Wahrheit
- Prozess/Speicher: P3 → P6 (Warteschlange Q1); **kein** Dateisystem, **kein** ffmpeg

## Warum das im Gesamtsystem wichtig ist
Das ist die Stelle, an der Wochen an Arbeit in eine Datei münden, die auf dem Fernseher im
Fitnessstudio läuft. Drei lokale Fehlgriffe sind teuer und still: (1) Wer den Render **direkt**
statt über `reiheEin` startet, umgeht den seriellen Torwächter – dann kann ein Medien-Löschauftrag
mitten in einen laufenden Render fahren (auf Windows `EBUSY` auf einer offenen Datei). (2) Wer die
Render-Sperre bei kaputten Stellen weglässt, produziert entweder einen Abbruch nach Minuten oder
eine fertige MP4 mit einem **Platzhalter-Bild** darin. (3) Wer den Ausgabenamen nicht als
Nutzereingabe behandelt, lässt einen Namen wie `../../config` aus dem Projektordner ausbrechen.

**Die Ergebnis-Hülle, wörtlich aus TK 9.1.1:**

> ```
> Ergebnis<T> =
>   | { ok: true,  wert: T }
>   | { ok: false, fehler: { code: Fehlercode, meldung: string, daten?: Fehlerdaten } }
> ```
> (TK 9.1.1)

Im tatsächlichen Typ (`src/shared/contracts/ergebnis.ts`, #12/#22) heißt das Feld `daten?: unknown`.

**Aufruf-Ergebnis, nicht Auftrags-Ergebnis** – die wichtigste Unterscheidung dieser Datei
(TK 9.1.1 Punkt 1, wörtlich):

> „**Aufruf-Ergebnis:** Hat der *Aufruf* funktioniert (z. B. „Auftrag eingereiht", „Trim gesetzt")?
> **Auftrags-Ergebnis:** Wie ging der *Vorgang* aus (`RenderResult`, Export-Ergebnis …)? Das reist
> **nicht** als Aufruf-Antwort, sondern über den **Auftrags-Zustand** (9.3)." (TK 9.1.1)

`{ ok: true, wert: { auftragId } }` heißt also **„eingereiht"**, nicht **„gerendert"**. Diese Datei
wartet auf **nichts**, zeigt **keinen** Fortschritt und meldet **keinen** Erfolg des Renders – das
tut das `queue-panel` über `queue:geaendert` (#65).

**`daten` bei `kaputte_elemente`:** Der Fehler trägt
`daten: { stellen: KaputteStelle[] }`. Ohne diese Nutzdaten könnte die Oberfläche den Nutzer
nirgendwohin führen – genau der Grund, aus dem TK 9.1.1 das Feld überhaupt eingeführt hat: „Ohne
dieses Feld bliebe von der Zusage „der Code trägt echtes Verhalten" nur der Code selbst übrig, und
der geführte Reparatur-Modus (FA-19) könnte den Nutzer nirgendwohin führen." (TK 9.1.1)

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.**

**Der Ablauf von `loeseRenderAus`, verbindlich:**

**1. Zuerst die Sperre – vor allem anderen.**
```
const stellen = findeKaputteStellen(projekt)
if (stellen.length > 0) → { ok: false, fehler: { code: 'kaputte_elemente',
      meldung: …, daten: { stellen } } }
```
Es wird **kein** PNG gezeichnet und **nichts** eingereiht. Der Vertrag im Wortlaut:

> „**Kaputte Stellen blockieren den Render und starten die geführte Reparatur (9.7.5):** zeigt ein
> Listenelement **oder ein Band-Abschnitt** auf ein `fehlt`-Asset (media-service 9.4.7), wird die
> Stelle **rot markiert**; ein Render wird nicht gestartet (er würde mit `medium_fehlt` scheitern
> bzw. einen Platzhalter einbetten), sondern der Nutzer in den Reparatur-Modus geführt." (TK 9.7.4)

**2. Den Ausgabenamen vorprüfen.** Er ist **Nutzereingabe**; die Regel steht wörtlich in TK 9.2.6:

> „**Der Ausgabename ist Nutzereingabe und wird validiert (FA-22):** Erlaubt ist ein reiner
> Dateiname **ohne** Endung – **keine** Pfadtrenner (`/`, `\`), **kein** `..`, keine für
> Windows/macOS/FAT32 unzulässigen Zeichen (`< > : " | ? *`, Steuerzeichen), nicht leer, keine
> reservierten Windows-Namen (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`). Der
> aufgelöste Pfad muss **innerhalb** von `projects/<id>/output/` liegen. Verstoß →
> `ungueltige_eingabe`, **ohne** Wirkung. Andernfalls könnte ein Name wie `../../config` aus dem
> Projekt ausbrechen." (TK 9.2.6)

Diese Prüfung hier ist **frühe Rückmeldung, kein Ersatz**: Die maßgebliche Validierung macht der
Main (TK 9.1.1 Punkt 6). Die Prüfung „innerhalb von `projects/<id>/output/`" kann der Renderer
**nicht** leisten – er kennt keine absoluten Pfade (TK 9.5.7); sie bleibt allein beim Main.

**3. Vorbelegung des Namens.** Der Aufrufer belegt das Eingabefeld mit
`projekt.letzterAusgabeName` vor; ist es `null`, gibt es keine Vorbelegung. Diese Datei nimmt den
Namen **wie übergeben** entgegen und setzt **keinen** Standard ein – ein hier eingesetzter Ersatzname
würde still eine andere Datei überschreiben, als der Nutzer im Feld gesehen hat. Fachlich (FA-22):
„vorbelegt ist der **zuletzt verwendete** Name, sodass wiederholtes Rendern die vorige Fassung
standardmäßig **ersetzt** und der Ordner nicht zuläuft."

**4. Über `projekt.liste` in Array-Reihenfolge die `RenderItem`s bauen.** `RenderItem.id` ist die
`Listenelement.id` – so lässt sich ein Fehler des Renders (`fehlerhaftesElementId`, TK 9.2.3) einer
Zeile zuordnen.

| `element.art` | `RenderItem` |
|---|---|
| `'video'` | `{ id, art: 'video', medienRef: asset.dateiname, trimStart: element.trimStart ?? 0, trimEnde: element.trimEnde ?? asset.dauer, einblendung }` |
| `'bild'` | `{ id, art: 'bild', medienRef: asset.dateiname, dauer: element.dauer }` |
| `'segment'` | `{ id, art: 'segment', png, dauer: element.dauer }` |

- `medienRef` ist der **relative** `Asset.dateiname` – nie ein absoluter Pfad, nie der
  `originalname` (TK 9.4.8 Punkt 1, TK 9.5.7).
- **Die Dauern sind im Vertrag optional, im `RenderItem` aber nicht.** `Listenelement.dauer`,
  `trimStart` und `trimEnde` sind `number | null` (#15), `Asset.dauer` ebenfalls (#13) – während
  `RenderItemBild.dauer`, `RenderItemSegment.dauer` sowie `RenderItemVideo.trimStart` **und**
  `RenderItemVideo.trimEnde` ein `number` verlangen (#17). Bleibt nach dem Ausweichwert (`?? 0` bzw.
  `?? asset.dauer`) ein `null` übrig, ist das Element unbrauchbar → `ungueltige_eingabe`, **nicht
  einreihen** (s. Fehlerpfade). Es wird **nichts** ersetzt, geraten oder auf einen Standardwert
  gesetzt: Ein hier erfundener Wert liefe durch den ganzen Render und käme als falsch lange
  Ausgabedatei heraus. Diese eine Prüfung ist die Ausnahme zu „Keine Vorprüfung von Dauern" unten –
  sie prüft keine **Fachregel** (Bereich, Trim), sondern nur, dass der geforderte Typ überhaupt
  erfüllbar ist. Ohne sie fiele der Fall erst im `render-service` (M6) auf, nach dem Einreihen und
  ohne Bezug zur Zeile in der Liste.
- **ENTSCHIEDEN – ein fehlender Trim ist KEIN Fehler, sondern heißt „ganzes Video".** `trimStart:
  null` wird zu `0`, `trimEnde: null` zu `asset.dauer`; erst wenn `trimEnde` **und** `asset.dauer`
  `null` sind, greift `ungueltige_eingabe`. Genau das leisten die beiden Ausweichwerte in der
  Tabelle oben – sie sind **nicht** kosmetisch, sondern die getroffene Entscheidung.
  **Warum dieser Zustand real vorkommt:** `setzeElementReferenz` (**M5-33**) setzt beim Umhängen
  eines Video-Elements `trimStart` und `trimEnde` **bewusst** auf `null` zurück, weil die alten
  Werte auf der Zeitachse der **alten** Quelldatei lagen. Unmittelbar nach einer Reparatur über die
  Fix-Option „durch ein anderes ersetzen" (FA-19) steht also ein Video-Element ohne Trim in der
  Liste. Ohne diese Festlegung entstünde eine der beiden schlechten Varianten: entweder ginge ein
  Video **ohne** Trim in den `RenderRequest` (der Typ verlangt `number` – es entstünde ein
  `undefined`/`NaN` im Auftrag, und der `render-service` schnitte an einer unbestimmten Stelle),
  oder ein frisch repariertes Element würde als Fehler abgewiesen, obwohl der Nutzer gerade eben
  genau das getan hat, was der Reparatur-Modus von ihm verlangt hat.
  **Warum „ganzes Video" der richtige Ersatzwert ist und kein geratener:** Er ist kein neuer Wert,
  sondern derselbe, den `fügeElementHinzu` (#41) beim Anlegen eines Video-Elements einsetzt – die
  volle Länge der Quelle. „Kein Schnitt" ist die einzige Auslegung von „kein Trim", die keine
  Information erfindet; jede andere (Standarddauer, halbe Länge, Anfang plus 10 s) wäre eine
  Annahme über ein Video, das niemand geprüft hat. **Kein Nachrechnen, kein Kappen:** Ist
  `trimStart` gesetzt und `trimEnde` `null`, wird `trimEnde = asset.dauer` gesetzt und **nicht**
  geprüft, ob `trimStart < trimEnde` gilt – diese Fachregel prüft der `render-service`
  (TK 9.2.3, `ungueltiges_element`), und eine zweite Prüfung hier wäre eine zweite Wahrheit.
- `png` bei `'segment'`: `alsPng(zeichneSegment(aktion, vorlage, marke))`. `vorlage` ist die mit
  `id === aktion.vorlagenId` aus `vorlagen`.
- `einblendung` bei `'video'`: ist `element.einblendung === null`, dann `null`. Sonst
  `{ art: bandVorlage.art, höhe: bandVorlage.höhe, bandVorlageId: element.einblendung.bandVorlageId,
  abschnitte }`, wobei je Abschnitt `png = alsPng(zeichneSegment(aktion, bandVorlage, marke))` mit
  **derselben** `bandVorlage` für alle Abschnitte (TK 9.2.8) und `dauer` unverändert übernommen wird.
  `bandVorlage` ist die Vorlage mit `id === element.einblendung.bandVorlageId` aus `vorlagen`.
- **`art` und `höhe` werden HIER, beim Einreihen, aus der Band-Vorlage abgeleitet – das ist der
  Kern der Änderung, nicht Beiwerk.** Wörtlich: „Die Art wird **beim Einreihen** des Render-Auftrags
  aus der Band-Vorlage abgeleitet und zusammen mit der Bandhöhe `H` als `einblendung.art` /
  `einblendung.höhe` im `RenderRequest` **mitgeführt** (9.2.2). Der `render-service` schlägt die
  Vorlage **nicht** zur Laufzeit nach – sein Eingang ist beim Einreihen eingefroren (9.3.5), und die
  Band-PNGs sind bereits in `1920 × H` gezeichnet." (TK 9.2.8) **Es sind exakt dieselben Werte, mit
  denen `zeichneSegment` das Band gezeichnet hat** – dieselbe `bandVorlage`, im selben Durchlauf.
  Wer sie stattdessen aus einer zweiten Quelle holt (neu geladene Vorlagenliste, Standardwert,
  eigene Konstante), erzeugt genau den Schaden, den die Änderung verhindern soll: PNGs in
  `1920 × H_alt` und ein Auftrag mit `H_neu` – ein verzerrtes oder falsch platziertes Band im
  fertigen Video, das erst am Fernseher auffällt.
- **`bandVorlage.höhe` ist `number | null` (#95), `einblendung.höhe` verlangt `number` (#17).** Ist
  `höhe` `null` – was bei `art: 'vollflaeche'` immer und bei einer defekten Vorlage sonst der Fall
  ist –, ist das Element **nicht baubar**: `ungueltige_eingabe`, **nicht einreihen**, Meldung nennt
  die `id` des Elements. Es wird **kein** Ersatzwert gesetzt (kein `0`, kein `162`, keine
  Vorlagenhöhe eines anderen Bandes). Dieselbe Regel gilt, wenn `bandVorlage.art === 'vollflaeche'`
  ist: Eine Vollflächen-Vorlage ist keine Band-Vorlage, `einblendung.art` kennt den Wert nicht (#17),
  und ein Band daraus zu bauen wäre geraten.
- Liefert ein `alsPng` `{ ok: false }`, bricht der ganze Aufbau ab und die Funktion antwortet mit
  `png_export_fehler` – **ohne** einzureihen. Ein halb bestücktes `elemente`-Array darf nie in die
  Warteschlange.

**5. `RenderRequest` zusammensetzen und einreihen.**
```
const request: RenderRequest = {
  renderId: erzeugeId(), projektId: projekt.id, elemente, profil: RENDER_PROFILE, ausgabeName,
}
return rufeAuf<{ auftragId: string }>(KANAELE.queue.reiheEin, { art: 'render', payload: request })
```
- Die `renderId` wird **hier** vergeben. Grund wörtlich: „Die `renderId` wird **vom Renderer
  vergeben**, sodass er verspätete Ereignisse eines alten Laufs sicher erkennen kann (9.2.7)."
  (TK 9.2.1)
- `profil` ist die Konstante `RENDER_PROFILE` (#18), unverändert. Es wird **nichts** daran
  angepasst – kein Bitratenwechsel, keine Auflösung, kein `dateiname`-Feld (das gibt es dort
  bewusst nicht).
- Der **Ausgabepfad** ist **nicht** Teil der Anfrage: „Der Ausgabe-**Pfad** ist **nicht** Teil der
  Anfrage – nur der **Name**" (TK 9.2.1). Diese Datei baut **keinen** Pfad.

**6. Nach dem Einreihen ist die Liste wieder frei.** Wörtlich:

> „**Render friert die Liste beim Einreihen ein (9.3.5):** die Liste bleibt danach editierbar, aber
> der bereits eingereihte Render nutzt den Snapshot – der composer stellt das nicht in Frage."
> (TK 9.7.4)

Diese Datei sperrt die Oberfläche also **nicht**, zeigt **keine** Warnung bei späteren Änderungen
und versucht **nicht**, einen laufenden Render nachzuführen. Den Snapshot nimmt der
`auftrags-manager` beim Einreihen.

**Der Ablauf von `loeseExportAus`, verbindlich:**

Nutzlast ist der `ExportRequest` aus TK 9.6.1: `{ projektId, dateiname, zielPfad }`.
```
return rufeAuf<{ auftragId: string }>(KANAELE.queue.reiheEin,
  { art: 'export', payload: { projektId, dateiname, zielPfad } })
```
- `dateiname` ist die Ausgabedatei **mit** Endung, wie sie `listeAusgaben` (TK 9.5.2) liefert. Diese
  Datei **listet den Ordner nicht selbst**: „Die Auswahl speist sich aus `listeAusgaben` (9.5.2);
  der Renderer liest den Ausgabeordner **nie** selbst und kennt **keine** absoluten Pfade."
  (TK 9.6.1)
- `zielPfad` kommt aus `wähleExportZiel()` (TK 9.6.1) – ein Instant-Aufruf, den die Oberfläche
  vorher macht. Diese Datei öffnet **keinen** Dialog.
- Der Export ist **kein** Sonderfall des Renders: eigener Auftrag, eigene Fehlercodes (TK 9.6.4),
  läuft seriell nach dem Render.
- **Kein Zwang auf einen bestimmten Zielnamen.** Auf dem Stick behält die Datei **ihren** Namen
  (FA-22); der frühere Zwang auf `loop.mp4` ist entfallen.

**7. Entscheidungen, die bereits getroffen sind (nicht erneut abwägen):**
- **Der Wurf von `zeichneSegment` wird NICHT gefangen** (#117 wirft bei nicht bereiten Schriften
  oder defekter Vorlage). Ein mit Systemschrift gemaltes Segment sieht gültig aus, misst aber andere
  Textbreiten – ein hier geglätteter Wurf brächte genau diesen Drift in die fertige Datei.
- **Die Zeichenvoraussetzungen stellt M5-35 her, nicht diese Datei und nicht M5-02.** `M5-35`
  (`src/renderer/composer/zeichen-vorbereitung.ts`) ruft in dieser Reihenfolge
  `stelleSchriftenBereit()` (#110) → `bereiteLogoVor(marke)` (#119) →
  `bereiteMotiveVor(projektId, eintraege)` (#111) und lädt `listeVorlagen()` (#99) und
  `leseMarke()` (#29). **Erst danach** darf gerendert werden: Ohne diesen Lauf liefert `holeMotiv`
  (#111) für jedes Bild `{ zustand: 'fehlt' }`, `zeichneSegment` malt einen **Platzhalter**, und
  diese Datei backte ihn in den `RenderRequest`. TK 9.10.7 verbietet das ausdrücklich: „**Ein
  Segment mit Platzhalter darf nie in den finalen Render gelangen** – diese Sperre sitzt im
  `composer` (Reparatur-Modus 9.7.5), nicht hier." Diese Datei ruft `bereiteMotiveVor`,
  `bereiteLogoVor` und `stelleSchriftenBereit` **nicht** selbst auf; sie prüft nur (s. DoD und
  Fehlerpfade), dass die Schriften bereit sind, und **verweigert** sonst.
- **Die PNGs werden bei jedem Auslösen neu gezeichnet.** Segment-PNGs sind flüchtig (CLAUDE.md,
  Datenmodell-Entscheidung 4); ein Zwischenspeicher hätte keine Ungültigkeitsregel und schickte
  veraltete Pixel in den Render.
- **Keine fachliche Vorprüfung von Dauern, Trim-Werten oder Vollständigkeit** außer den kaputten
  Stellen. Ob eine Dauer im Bereich liegt, ob `trimStart < trimEnde` gilt, ob das Video lang genug
  ist – das prüft der `render-service` (TK 9.2.3, `ungueltiges_element`); eine zweite Prüfung hier
  wäre eine zweite Wahrheit, die bei der nächsten Regeländerung auseinanderläuft. **Ausgenommen ist
  allein das `null`**: Ein `null`, für das der `RenderItem`-Typ ein `number` verlangt, ist keine
  Fachregel, sondern ein nicht baubarer Datensatz (s. Punkt 4 und Fehlerpfade).
- **Kein Abbruch, kein Fortschritt, kein Wiederholen in dieser Datei.** `entferne`, `wiederhole`
  und `holeStand` (TK 9.3.4) gehören zum `queue-panel` (M7).
- **ENTSCHIEDEN (TK v2.8) – der Sofort-Flush des Auto-Speicherns wird hier NICHT ausgelöst.** Den
  Flush erzwingt der **Main**, und zwar unmittelbar bevor der Auftrag **startet**, nicht beim
  Einreihen. Wörtlich: „**`anstehend` → `laeuft`:** […] Bei `render` und `export` erzwingt der Main
  **unmittelbar vor** diesem Übergang den **Sofort-Flush** von D1 (9.5.4) – nicht beim Einreihen."
  (TK 9.3.3) *Begründung (TK 9.5.4):* „Die Warteschlange ist streng seriell; zwischen Einreihen und
  Start können **Minuten** liegen, und der Nutzer darf in dieser Zeit weiterarbeiten. Ein Flush beim
  Einreihen schriebe einen Stand fest, der beim Start längst überholt ist, und verlöre bei einem
  Absturz genau die Arbeit dazwischen. Dass der **Main** auslöst und nicht der Renderer, spart zudem
  einen IPC-Kanal: Der Renderer müsste sonst vor jedem `reiheEin` erst „jetzt speichern" rufen und
  auf die Antwort warten." Diese Datei ruft also **kein** „jetzt speichern", wartet auf **keine**
  Speicherbestätigung und baut **keinen** solchen Kanal. (Der eingereihte Render arbeitet ohnehin auf
  seinem **eingefrorenen** Snapshot, TK 9.3.5 – der Flush sichert die *Projektdaten*, nicht den
  Auftrags-Eingang.)

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projekt` | der aktuelle Projektstand | nur gelesen; liefert `id`, `liste`, `assets`, `aktionen` |
| `ausgabeName` | Dateiname **ohne** Endung, Nutzereingabe | nicht leer, keine Pfadtrenner, kein `..`, keine `< > : " \| ? *`/Steuerzeichen, kein reservierter Windows-Name |
| `marke` | Farb-/Schrift-Rollen für `zeichneSegment` | unverändert durchgereicht |
| `vorlagen` | nutzbare Vorlagen (`parent === null`) | `readonly`; löst `aktion.vorlagenId` und `einblendung.bandVorlageId` auf |
| `projektId`, `dateiname`, `zielPfad` | `ExportRequest` (TK 9.6.1) | `dateiname` **mit** Endung, aus `listeAusgaben` |

Ausgang bei Erfolg: `{ ok: true, wert: { auftragId } }` – **eingereiht**, nicht fertig.
Ausgang bei Fehler: `kaputte_elemente` (mit `daten.stellen`), `png_export_fehler`,
`ungueltige_eingabe`, `nicht_gefunden` sowie unverändert jeder Code, den `reiheEin` liefert.

- „**Render friert die Liste beim Einreihen ein (9.3.5):** die Liste bleibt danach editierbar, aber

  Request/Response-Operationen aufgerufen, sondern über `reiheEin` eingereiht; ihr Fach-Ergebnis

  Ausgang" (TK 9.3.4)

  `ungueltige_eingabe`, **ohne** Wirkung. Andernfalls könnte ein Name wie `../../config` aus dem
  Projekt ausbrechen." (TK 9.2.6)

  baut **keinen** Pfad und kennt **keine** absoluten Pfade.

  sicher erkennen kann (9.2.7)." (TK 9.2.1)
- „**Alle Abschnitte eines Elements nutzen dieselbe Band-Vorlage** (eine `bandVorlageId` pro
  Einblendung) – damit `H` und die Kompositionsart während eines Videos nicht wechseln." (TK 9.2.8)
- „**Die `einblendung` eines `"video"`-Items trägt die Geometrie mit:** `art` | `"split"` \|
  `"einblendung"` – Kompositionsart (Band **unter** bzw. **über** dem Video, 9.2.8) · `höhe` |
  Bandhöhe `H` in Pixeln (ganzzahlig und **gerade**, 9.2.8) · `abschnitte` | geordnete Folge `{ png (Binärpuffer,
  1920 × H), dauer }`" (TK 9.2.2)
- „Der Render **friert seinen Eingang beim Einreihen ein** (9.3.5). Beide Werte stammen aus der
  Band-Vorlage und werden **beim Einreihen** aus ihr abgeleitet. […] Ändert jemand die Bandhöhe,
  während der Auftrag in der Warteschlange wartet, passten die bereits gezeichneten Band-PNGs
  (1920 × H **zum Einreih-Zeitpunkt**) nicht mehr zur nachgeschlagenen Höhe – das Band im fertigen
  Video wäre verzerrt oder falsch platziert." (TK 9.2.2) – deshalb liefert **diese** Datei die
  beiden Werte mit; der `render-service` schlägt nichts nach.
- „**Die Bandhöhe `H` stammt ausschließlich aus der Vorlage** – sie ist **kein** Wert am
  Listenelement und **nicht** pro Element überschreibbar." (TK 9.2.8) – die Werte kommen also aus
  `bandVorlage`, **nie** aus `element.einblendung` und **nie** aus einer Eingabe des Nutzers.
- „Bei `"segment"` werden **keine** Aktions-/Vorlagendaten mitgeschickt – die Pixel sind bereits
  final; das ist der Kern von Variante A." (TK 9.2.2)
- „Die Auswahl speist sich aus `listeAusgaben` (9.5.2); der Renderer liest den Ausgabeordner **nie**
  selbst und kennt **keine** absoluten Pfade." (TK 9.6.1)
- „**Nur der Main schreibt/liest das Dateisystem;** der Renderer liefert ausschließlich Bytes über
  IPC." (TK 9.2.6)
- Binärdaten reisen als **Uint8Array**, nicht als Base64 (TK 9.1.1 Punkt 9, #17).

## Nicht selbst entscheiden – STOPP und fragen
- **Niemals `render` oder `export` direkt aufrufen.** Der einzige Weg ist `reiheEin` über
  `queue:reiheEin`. Ein Direktaufruf umgeht den einzigen Sperr-Mechanismus des Systems (TK 9.3.5)
  und lässt ein Löschen in einen laufenden Render fahren.
- **Die Render-Sperre nicht aufweichen** – kein „trotzdem rendern", kein Schalter, kein Überspringen
  einzelner kaputter Stellen. „Erst wenn **kein** kaputtes Element mehr existiert, ist der Render
  wieder frei." (TK 9.7.5)
- **Das `RenderProfile` nicht verändern** – keine andere Auflösung, keine andere Bitrate, kein
  `dateiname`-Feld. Das Profil ist am Fernseher verifizierte Ausgabe (TV-kritisch); jede Abweichung
  fällt erst am Gerät auf.
- **Keinen Pfad bauen.** Weder Ausgabepfad noch Medienpfad. Der Renderer kennt nur relative
  Dateinamen; die Pfad-Autorität ist der `project-store` (TK 9.5.7).
- **Den Wurf von `zeichneSegment` nicht fangen** (Begründung oben unter „Entscheidungen").
- **Keine eigene Warnung bei Listenänderungen nach dem Einreihen** – der Snapshot ist gewollt.
- **Kein Eintrag in `src/shared/contracts/kanaele.ts`** – den Kanal `queue:reiheEin` trägt #71 ein.
- **Offene Frage an den Auftraggeber:** Soll ein Render, dessen `ausgabeName` einer **bereits
  vorhandenen** Ausgabedatei entspricht, eine Rückfrage auslösen? FA-22 sagt, gleicher Name
  **ersetzt** die vorige Fassung – und der Standardwert ist genau der zuletzt verwendete Name, das
  Ersetzen also der Regelfall. Ob der Nutzer dabei trotzdem einmal bestätigen soll, legt der Vertrag
  nicht fest; die Antwort bestimmt, ob diese Funktion `listeAusgaben` überhaupt braucht. Nicht raten.
- **Verbot – keinen Sofort-Flush auslösen.** (Die frühere offene Frage ist mit TK v2.8 **beantwortet**
  und steht jetzt unter „Entscheidungen", Punkt 7.)
