### Issue M5-25: [vorlagen-editor] Zonen auf dem Canvas ziehen, bemaßen und einrasten

## Ziel (in einem Satz)
Eine Zone lässt sich auf der Vorlagenfläche mit der Maus verschieben und an ihren Griffen bemaßen,
rastet dabei an den Sicherheitsabstand-Linien, an den Kanten der anderen Zonen und an einem
8-px-Raster ein, bleibt immer vollständig innerhalb der Fläche – und feste Zonen bewegen sich nicht.

## Modul & Datei
- Modul: `vorlagen-editor` (Renderer)
- Datei: `src/renderer/vorlagen-editor/zonen-canvas.ts`
- Vertrag: Technisches Konzept **9.12.2** (Quelle der Wahrheit), ergänzend **9.11.1** (Punkt 1:
  absolute Pixel; Punkt 4: feste Zonen), **9.10.5** und **9.11.2** (Sicherheitsabstand)
- Prozess/Speicher: P7; kein Speicher – reine Geometrie im Arbeitsspeicher

## Warum das im Gesamtsystem wichtig ist
Diese Datei ist die **Geometrie-Grundlage des ganzen Moduls**: Der Zahlen-Inspektor (M5-26), das
Hinzufügen einer Zone (M5-28) und die Prüfungen (M5-29) rechnen mit den hier definierten Flächen-
und Sicherheitsboxen. Läuft die Rechnung hier auseinander, weichen Canvas-Anzeige, eingetippte Zahl
und Speicher-Prüfung voneinander ab – der Nutzer schiebt eine Zone sichtbar an den Rand, und der
Store lehnt sie beim Speichern trotzdem ab.

Drei lokale Entscheidungen sind hier teuer:

1. **Gerundet wird auf ganze Pixel.** `Zone.rahmen` ist absolut in Pixeln der Vorlagenfläche. Ein
   Bruchteil-Pixel aus einer Maus-Bewegung landet sonst in `vorlagen.json`, und der Zeichner (#117)
   entscheidet beim Zeichnen selbst, wie er rundet – zwei Zonen, die bündig aussehen, stehen im
   Endvideo 1 px auseinander.
2. **Die Bandfläche ist nicht die Bildfläche.** Bei `split`/`einblendung` ist die Fläche
   1920 × `höhe`, nicht 1920 × 1080. Wer hier 1080 annimmt, erlaubt Zonen weit unterhalb des Bandes
   – sie werden nie gezeichnet, und der Nutzer sucht den Fehler im Layout.
3. **Der Sicherheitsabstand ist eine Eigenschaft des Bildrahmens, nicht der Vorlagenfläche.** Beim
   Band liegt der untere Rand des Rahmens **innerhalb** des Bandes. Wer den 54-px-Rand einfach auf
   die Bandfläche anwendet, zieht die Linie an der falschen Stelle – und der Editor warnt vor der
   falschen Zone.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/vorlagen-editor/zonen-canvas.ts
import type { Rahmen, Vorlage, Zone } from '../../shared/contracts/vorlage'
import { SICHERHEITSABSTAND_PX } from '../../shared/contracts/konstanten'
import { RENDER_PROFILE } from '../../shared/contracts/render-profile'

/** Die native Zeichenfläche einer Vorlage (TK 9.10.2). */
export interface Flaeche {
  breite: number
  höhe: number
}

/** Kandidatenlinien zum Einrasten, getrennt nach Achse. Aufsteigend sortiert, ohne Dubletten. */
export interface Einrastlinien {
  x: number[]
  y: number[]
}

/** Anfasser einer Zone. Himmelsrichtungen; `n` = obere Kante, `se` = untere rechte Ecke. */
export type Griff = 'nw' | 'n' | 'ne' | 'e' | 'se' | 's' | 'sw' | 'w'

export const EINRAST_RASTER_PX = 8
export const EINRAST_TOLERANZ_PX = 6
export const MINDEST_ZONEN_KANTE_PX = 8

/** 1920 × 1080 bei `vollflaeche`, sonst 1920 × vorlage.höhe. */
export function flaecheDerVorlage(vorlage: Vorlage): Flaeche

/**
 * Der sichere Bereich IN KOORDINATEN DER VORLAGENFLÄCHE (nicht des Bildrahmens).
 * Kann bei sehr niedrigen Bändern die Breite/Höhe 0 haben – dann ist nichts sicher nutzbar.
 */
export function sicherheitsBox(vorlage: Vorlage): Rahmen

/** Begrenzt einen Rahmen auf die Fläche, OHNE ihn zu verkleinern (verschiebt ihn hinein). */
export function begrenzeAufFlaeche(rahmen: Rahmen, flaeche: Flaeche): Rahmen

/** Alle Kandidatenlinien: Flächenkanten, Sicherheitsbox, Kanten ALLER anderen Zonen. */
export function sammleEinrastlinien(vorlage: Vorlage, ausserZonenId: string): Einrastlinien

/** Verschiebt die Zone um (dx, dy) in FLÄCHENPIXELN. Feste Zonen bleiben unverändert. */
export function verschiebeZone(
  zone: Zone,
  dx: number,
  dy: number,
  flaeche: Flaeche,
  linien: Einrastlinien,
): Zone

/** Bemaßt die Zone an einem Griff um (dx, dy). Feste Zonen bleiben unverändert. */
export function bemasseZone(
  zone: Zone,
  griff: Griff,
  dx: number,
  dy: number,
  flaeche: Flaeche,
  linien: Einrastlinien,
): Zone
```

**Alle sechs Funktionen sind rein und synchron:** gleiche Eingabe → gleiches Ergebnis, kein
DOM-Zugriff, kein Ereignis, kein Zustand, kein `Ergebnis<T>`. Sie überqueren **keine** IPC-Grenze –
dieselbe Begründung wie bei `zeichneSegment`: „Ist **kein** Auftrag der Queue – eine reine, synchron
aufrufbare Renderer-Funktion." (TK 9.10.8). Sie verändern die übergebene `Zone` **nie**, sondern
geben eine neue mit neuem `rahmen` zurück (die übrigen Felder werden unverändert übernommen).

**Fremde Typen und Konstanten, die du benutzt** (der umsetzende Agent sieht die anderen Issues
nicht – deshalb hier vollständig ausgeschrieben):

```ts

export interface Vorlage {

// #21 – src/shared/contracts/konstanten.ts

// #18 – src/shared/contracts/render-profile.ts
export const RENDER_PROFILE: RenderProfile   // u. a. breite: 1920, hoehe: 1080
// ACHTUNG: das Feld heisst dort `hoehe` OHNE Umlaut, in `Rahmen`/`Flaeche` dagegen `höhe` MIT
// Umlaut. Nicht angleichen – beide Namen sind anderswo festgeschrieben.
```

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.**

**Die Zahlen 1920, 1080, 96 und 54 werden NICHT als Literale hingeschrieben**, sondern aus
`RENDER_PROFILE.breite`, `RENDER_PROFILE.hoehe` und `SICHERHEITSABSTAND_PX` gelesen. Sie stehen
bereits an je einer Stelle; eine zweite Niederschrift läuft beim ersten Nachjustieren auseinander.

**`flaecheDerVorlage` (verbindlich):**

| `vorlage.art` | Fläche |
|---|---|
| `vollflaeche` | `{ breite: RENDER_PROFILE.breite, höhe: RENDER_PROFILE.hoehe }` |
| `split` | `{ breite: RENDER_PROFILE.breite, höhe: vorlage.höhe }` |
| `einblendung` | `{ breite: RENDER_PROFILE.breite, höhe: vorlage.höhe }` |

Ist `vorlage.art` `split` oder `einblendung` und `vorlage.höhe` **keine** endliche Zahl `> 0`, wird
`{ breite: RENDER_PROFILE.breite, höhe: 0 }` geliefert. **Keine** geratene Ersatzhöhe: Eine Fläche
der Höhe 0 lässt danach jede Prüfung (M5-29) zuschlagen, eine geratene Höhe würde ein Layout
erlauben, das nie zu seiner echten Fläche passt. Der Fall kann nur aus einem kaputten Datenbestand
kommen – die Höhe wird beim Anlegen (#100) und beim Speichern (#102) geprüft.

**`sicherheitsBox` (verbindlich) – und warum sie beim Band anders gerechnet wird:**

Der Sicherheitsabstand gilt **absolut im 1920×1080-Rahmen**. Bei `vollflaeche` ist die
Vorlagenfläche derselbe Rahmen:

```
vollflaeche:  x = 96
              y = 54
              breite = 1920 − 2·96 = 1728
              höhe   = 1080 − 2·54 =  972
```

Bei `split`/`einblendung` mit Bandhöhe `H` sitzt das Band am **unteren** Rahmenrand, belegt also die
Rahmenzeilen `1080 − H` bis `1080`. Umgerechnet in Bandkoordinaten:

```
obenUnsicher = max(0, 54 − (1080 − H))     // nur relevant, wenn H > 1026
untenSicherBis = H − 54                    // die unteren 54 px des Rahmens liegen IM Band

split/einblendung:  x = 96
                    y = obenUnsicher
                    breite = 1728
                    höhe   = max(0, untenSicherBis − obenUnsicher)
```

Bei `H = 162` ergibt das `y = 0`, `höhe = 108` – also genau die „oberen **108 px**", die der Vertrag
nennt. Bei `H ≤ 54` ergibt sich `höhe = 0`: im Band ist **nichts** sicher.

**`begrenzeAufFlaeche` (verbindlich):** `breite` und `höhe` bleiben unverändert; `x` wird auf
`[0, max(0, flaeche.breite − breite)]` und `y` auf `[0, max(0, flaeche.höhe − höhe)]` begrenzt. Ist
die Zone größer als die Fläche, landet sie bei 0 und ragt hinaus – das ist dann ein Fall für die
**Sperre** in M5-29, nicht für ein stilles Verkleinern. Eine Zone, die unter der Hand kleiner wird,
ist für den Nutzer nicht nachvollziehbar.

**`sammleEinrastlinien` (verbindlich).** Gesammelt wird, jeweils für die passende Achse:

| Quelle | x-Linien | y-Linien |
|---|---|---|
| Flächenkanten | `0`, `flaeche.breite` | `0`, `flaeche.höhe` |
| Sicherheitsbox | `box.x`, `box.x + box.breite` | `box.y`, `box.y + box.höhe` |
| **Jede** Zone mit `id !== ausserZonenId` | `rahmen.x`, `rahmen.x + rahmen.breite` | `rahmen.y`, `rahmen.y + rahmen.höhe` |

Auch **feste** Zonen liefern Linien: Der Nutzer soll an Logo und Hintergrund ausrichten können,
obwohl er sie nicht bewegen darf. Die Linien werden auf ganze Zahlen gerundet, entdoppelt und
**aufsteigend sortiert** – die Sortierung macht das Ergebnis bei Gleichstand eindeutig.

**Die Einrast-Regel (verbindlich, an genau einer Stelle im Code):**

```
raste(wert, linien):
  1. wert auf eine ganze Zahl runden (Math.round)
  2. unter den Linien die mit dem kleinsten |wert − linie| suchen;
     bei Gleichstand die KLEINERE Linie (die Liste ist sortiert -> die erste)
  3. ist dieser Abstand <= EINRAST_TOLERANZ_PX -> diese Linie zurückgeben
  4. sonst: Math.round(wert / EINRAST_RASTER_PX) * EINRAST_RASTER_PX
```

**Warum die Linien Vorrang vor dem Raster haben:** Sicherheitslinien und fremde Zonenkanten liegen
in den eingebauten Vorlagen auf 96, 54, 1824, 1026, 1056 – Werte, die **nicht** alle auf dem
8-px-Raster liegen (54 und 1026 nicht). Rastete zuerst das Raster, käme die Zone nie exakt auf der
Sicherheitslinie zu liegen, und der Editor warnte hartnäckig vor einer Zone, die der Nutzer sichtbar
angelegt hat. Die Toleranz ist mit 6 px kleiner als eine Rasterweite, damit nie unklar ist, welche
der beiden Regeln greift.

**`verschiebeZone` (verbindlich):**

1. `zone.rolle === 'fest'` → die **unveränderte** `zone` zurückgeben. Kein Rechnen, kein neues
   Objekt, kein Einrasten. Das ist die strukturelle Umsetzung der Sperre.
   Ebenso: Ist `dx` **oder** `dy` keine endliche Zahl, die **unveränderte** `zone` zurückgeben –
   **vor** Schritt 2, also ohne Einrasten und ohne Begrenzen.
2. Rohziel: `xRoh = rahmen.x + dx`, `yRoh = rahmen.y + dy`.
3. Je Achse **zwei** Kandidaten bilden und den mit dem kleineren Abstand zum Rohziel nehmen
   (bei Gleichstand den ersten):
   - führende Kante: `raste(xRoh, linien.x)`
   - nachlaufende Kante: `raste(xRoh + breite, linien.x) − breite`
   Ohne den zweiten Kandidaten könnte man Zonen nie an ihrer **rechten** oder **unteren** Kante
   ausrichten – und genau das braucht man, um an der Inhaltsbox (rechts 1824, unten 1026) bündig
   abzuschließen.
4. `begrenzeAufFlaeche` anwenden. Größe bleibt unverändert.

**`bemasseZone` (verbindlich):**

1. `zone.rolle === 'fest'` → die **unveränderte** `zone` zurückgeben. Dasselbe, wenn `dx` oder `dy`
   keine endliche Zahl ist – **vor** jeder weiteren Rechnung.
2. Aus dem Rahmen die vier Kanten bilden: `links = x`, `oben = y`, `rechts = x + breite`,
   `unten = y + höhe`.
3. Nur die vom Griff betroffenen Kanten bewegen; die gegenüberliegenden bleiben **fest**:
   | Griff | bewegt |
   |---|---|
   | `nw` | `links` um `dx`, `oben` um `dy` |
   | `n` | `oben` um `dy` |
   | `ne` | `rechts` um `dx`, `oben` um `dy` |
   | `e` | `rechts` um `dx` |
   | `se` | `rechts` um `dx`, `unten` um `dy` |
   | `s` | `unten` um `dy` |
   | `sw` | `links` um `dx`, `unten` um `dy` |
   | `w` | `links` um `dx` |
4. Jede **bewegte** Kante durch `raste(…)` schicken (x-Kanten gegen `linien.x`, y-Kanten gegen
   `linien.y`).
5. Jede bewegte Kante auf die Fläche begrenzen: x-Kanten auf `[0, flaeche.breite]`, y-Kanten auf
   `[0, flaeche.höhe]`.
6. Mindestgröße erzwingen: Ist `rechts − links < MINDEST_ZONEN_KANTE_PX`, wird die **bewegte** Kante
   so korrigiert, dass der Abstand genau `MINDEST_ZONEN_KANTE_PX` beträgt (die feste Kante bleibt).
   Analog für `unten − oben`. Eine Zone mit `breite` oder `höhe` von 0 wäre nach #102 nicht
   speicherbar (`breite > 0`, `höhe > 0`) – sie darf hier gar nicht erst entstehen.
7. Ergebnis: `{ x: links, y: oben, breite: rechts − links, höhe: unten − oben }`, alle Werte
   ganzzahlig.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `vorlage` | die bearbeitete Arbeitskopie | `art` bestimmt die Fläche; `höhe` nur bei `split`/`einblendung` gültig |
| `zone` | die angefasste Zone | `rolle: 'fest'` → unverändert zurück |
| `dx`, `dy` | Verschiebung in **Flächenpixeln**, nicht in Bildschirmpixeln | endliche Zahlen; die Umrechnung von der CSS-Anzeigegröße macht der Aufrufer |
| `griff` | angefasster Anfasser | einer der acht Werte |
| `flaeche` | Zielfläche | aus `flaecheDerVorlage` |
| `linien` | Einrast-Kandidaten | aus `sammleEinrastlinien`, ohne die eigene Zone |
| `ausserZonenId` | Zone, deren eigene Kanten **nicht** als Linie zählen | sonst rastet die Zone an sich selbst ein und lässt sich nicht bewegen |

Ausgang bei Erfolg: eine **neue** `Zone` mit ganzzahligem, flächenkonformem `rahmen`; alle anderen
Felder unverändert übernommen. Bzw. `Flaeche` / `Rahmen` / `Einrastlinien` bei den Hilfsfunktionen.
Ausgang bei Fehler: entfällt – diese Funktionen liefern **keine** Fehler und werfen nie. Ungültige
Geometrie wird von M5-29 als Sperre gemeldet, nicht hier.

  (TK 9.12.2)

- „**Zonen-Rahmen in absoluten Pixeln** der jeweiligen Vorlagen-Fläche (9.11.1); Eingaben werden auf
  die Fläche **begrenzt**." (TK 9.12.2)
- „**Feste Zonen sind sichtbar, aber gesperrt** – der Nutzer sieht den Markenrahmen, kann ihn aber
  nicht verändern." (TK 9.12.2)
- „Der Editor darf Zonen mit `rolle: "fest"` **nicht** ändern, verschieben oder entfernen
  (Markenrahmen erzwungen, FA-11)." (TK 9.11.1, Punkt 4)
- „**Absolute Pixel** im Raster der Vorlagenart – keine Prozentwerte. Eindeutig, keine
  Rundungsdrift, deckungsgleich mit der Canvas-Auflösung (9.10.2)." (TK 9.11.1, Punkt 1)
- „**Sicherheitsabstand ist eine Eigenschaft des Bildrahmens, nicht der Vorlagenfläche.** Er gilt
  absolut im 1920×1080-Rahmen (96 px horizontal, 54 px vertikal, 9.10.5).
  **Der Wert gehört der MARKE, nicht der Konstanten (v3.6, entschieden).** `Marke.sicherheit`
  ist seit v3.4 **bearbeitbar** – FA-24 nennt „Sicherheitsabstände" ausdrücklich. Die 96/54 px in
  9.11.4 sind damit nur noch die **Vorbelegung der eingebauten Marke**; wer zeichnet oder prüft,
  liest den Wert aus der **jeweils zuständigen Marke** (9.15.4). **Folge, die beim Bauen zählt:**
  Vorlagen sind **app-weit** und kennen die Marke nicht, mit der sie später gezeichnet werden –
  eine für 54 px gebaute Vorlage ist bei einer Marke mit größerem Abstand **nicht mehr sicher**.
  Der `vorlagen-editor` zeichnet seine Sicherheitslinie deshalb gegen eine **benannte** Marke (die
  Projekt-Standardmarke bzw. die eingebaute, wenn kein Projekt offen ist) und **sagt dazu, gegen
  welche** – eine Linie ohne diese Angabe wäre eine Zusage, die die Vorlage nicht halten kann.
  **Wichtige Folge für Bänder:** Ein Band sitzt am unteren Rahmenrand – die unteren **54 px des
  Rahmens liegen damit *innerhalb* des Bandes**. Bei einem 162 px hohen Band sind also nur die
  oberen **108 px** sicher nutzbar; Inhalt darunter kann am TV abgeschnitten werden." (TK 9.11.2)
- „Zonen **überlappen** | **erlaubt** – wird für Hintergrund und Scrim gebraucht" (TK 9.12.2). Diese
  Datei verhindert Überlappungen **nicht** und weicht ihnen **nicht** aus; fremde Kanten sind
  ausschließlich Einrast-Kandidaten, keine Hindernisse.
- „**Ist NICHT:** … rendert **keine** Pixel selbst, **kein** Dateisystem/ffmpeg." (TK 9.12.2)

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `zone.rolle === 'fest'` | – | die unveränderte `zone` wird zurückgegeben; kein Fehler, keine Meldung – die Sperre ist stumm und strukturell |
| `dx`/`dy` nicht endlich (`NaN`, `Infinity`) | – | die **unveränderte** Zone zurückgeben – **ohne** Einrasten und **ohne** Begrenzen (also **nicht** wie `dx = 0` behandeln, bei dem beides läuft und den Rahmen verschieben kann). Ein `NaN` im Rahmen würde nach `vorlagen.json` wandern und dort jede spätere Prüfung unterlaufen; ein stillschweigendes Einrasten auf eine fremde Linie wäre für den Nutzer eine Bewegung, die er nie ausgelöst hat |
| `vorlage.höhe` bei `split`/`einblendung` ungültig | – | `flaecheDerVorlage` liefert Höhe `0`; jede Zone gilt danach als außerhalb und wird von M5-29 gesperrt |
| Zone größer als die Fläche | – | `begrenzeAufFlaeche` setzt sie auf `0` und verkleinert **nicht**; die Sperre meldet M5-29 |
| Bemaßung unter die Mindestkante | – | auf `MINDEST_ZONEN_KANTE_PX` begrenzt, nie `0` oder negativ |

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – keine Prozentwerte, keine relativen Einheiten.** `rahmen` ist absolut in Flächenpixeln.
  Rechne **nicht** in Bildschirm- oder CSS-Pixeln und speichere **nichts** als Anteil. Die
  Umrechnung von der (per CSS skalierten) Anzeige in Flächenpixel macht der Aufrufer, bevor er `dx`
  und `dy` übergibt.
- **Verbot – `devicePixelRatio` wird nirgends gelesen.** Weder für die Fläche noch für die Toleranz
  noch für das Raster. Das Ergebnis darf nicht vom Gerät abhängen.
- **Verbot – feste Zonen nicht „nur ein bisschen" bewegen.** Kein Sonderfall „mit gedrückter
  Umschalttaste doch", kein Entsperren im Entwicklermodus. Die Sperre ist FA-11 und gilt auch in
  eigenen Vorlagen.
- **Verbot – kein Umlayouten der anderen Zonen.** Wird eine Zone verschoben, bewegt sich **keine**
  andere mit, weicht keine aus und schrumpft keine. „Es gibt **kein** automatisches Umlayouten"
  (TK 9.11.1, Punkt 3).
- **Verbot – kein Undo-Stapel.** Diese Datei merkt sich **keinen** vorherigen Rahmen. Undo/Redo im
  Vorlagen-Editor ist TK 9.13 und gehört nach M7.
- **Verbot – keine Ereignisbehandlung in dieser Datei.** Kein `addEventListener`, kein
  `pointerdown`, kein React-Hook. Hier stehen nur die reinen Rechenschritte; die Maus-Behandlung
  gehört in die Ansicht, die diese Funktionen aufruft.
