### Issue M5-21: [action-editor] Live-Vorschau der Aktion über die einzige Pixelquelle

## Ziel (in einem Satz)
Der Editor zeigt die gerade bearbeitete Aktion als Bild – erzeugt durch **denselben** Aufruf von
`zeichneSegment`, dessen Pixel später als Segment-PNG in den finalen Render gehen, nur per CSS
verkleinert dargestellt.

## Modul & Datei
- Modul: `action-editor` (Renderer)
- Datei: `src/renderer/action-editor/live-vorschau.ts`
- Vertrag: Technisches Konzept **9.8.3** (Live-Vorschau), **9.8.4** (einzige Pixelquelle),
  **9.10.1** (eine Zeichenroutine, zwei Verwendungen), **9.10.2/9.10.3** (Ausgabe-Festlegungen und
  Determinismus) – Quelle der Wahrheit
- Prozess/Speicher: P2; nutzt `template-canvas`; **kein** IPC, **kein** Dateisystem, **kein**
  ffmpeg, **kein** Auftrag der Warteschlange

## Warum das im Gesamtsystem wichtig ist
Die Live-Vorschau ist das einzige Bild, das der Nutzer beim Gestalten sieht – und sie ist zugleich
das Versprechen, dass genau das später auf dem Fernseher läuft. „**`template-canvas` ist die einzige
Pixelquelle:** die Live-Vorschau ist **pixelgleich** zur Vorschau (P5) und zum finalen Segment-PNG
(Variante A). Es gibt **keinen** zweiten Gestaltungs-/Renderpfad." (TK 9.8.4)

Alle Fehler, die hier möglich sind, sind **lautlos**. Wer für die Vorschau „schnell" ein kleineres
Canvas zeichnet, weil die Anzeigefläche ohnehin nur 640 px breit ist, bekommt ein hübsches
Vorschaubild und ein unscharfes Endvideo. Wer `canvas.width` setzt, um die Darstellung anzupassen,
**leert damit das Canvas vollständig** – im Video ein schwarzes Segment ohne jede Fehlermeldung
(#118 bricht genau deshalb bei abweichenden Maßen ab). Und wer zeichnet, bevor Schriften, Motive und
Logo bereitstehen, bekommt Fallback-Schriften und leere Bildflächen: „Zeichnen mit Fallback-Schrift
ist ein **Vertragsbruch** (lautloser Drift zwischen Vorschau und Endvideo)." (TK 9.10.3, Punkt 3)

Keiner dieser Fehler erzeugt eine Meldung. Alle fallen erst auf dem 85-Zoll-Gerät im Studio auf.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/action-editor/live-vorschau.ts
import type { Aktion } from '../../shared/contracts/aktion'
import type { Asset } from '../../shared/contracts/asset'
import type { Marke } from '../../shared/contracts/marke'
import type { Vorlage } from '../../shared/contracts/vorlage'
import type { SegmentBild } from '../template-canvas/zeichne-segment'

/** Einmalige Vorbereitung, BEVOR gezeichnet wird: Schriften, Logo und alle Motive der
 *  Aktions-Bibliothek. Danach ist zeichneVorschau synchron aufrufbar.
 *  Wirkungsgleich bei Mehrfachaufruf: ein zweiter Aufruf mit denselben Eingaben führt zum
 *  gleichen Bestand (#111 überschreibt vorhandene Schlüssel und lädt neu – NICHT idempotent im
 *  Sinne von „tut beim zweiten Mal nichts"). Nach einem Projektwechsel oder einem abgeschlossenen
 *  Import erneut aufrufen. */
export async function bereiteVorschauVor(
  projektId: string,
  aktionen: Aktion[],
  assets: Asset[],
  marke: Marke,
): Promise<void>

/** Die Vorschau: EIN Aufruf von zeichneSegment, sonst nichts. Synchron. */
export function zeichneVorschau(aktion: Aktion, vorlage: Vorlage, marke: Marke): SegmentBild

/** Hängt das Canvas in ein Anzeigeelement und skaliert es AUSSCHLIESSLICH per CSS.
 *  Verändert canvas.width/canvas.height NIEMALS. */
export function haengeVorschauEin(ziel: HTMLElement, bild: SegmentBild): void
```

**`zeichneVorschau` ist ein Weiterreichen, keine zweite Zeichenroutine.** Sie ruft
`zeichneSegment(aktion, vorlage, marke)` und gibt dessen Ergebnis zurück – **kein** eigener
`ctx`-Aufruf, **kein** nachträgliches Übermalen, **kein** Zuschneiden, **kein** Wasserzeichen, kein
„nur für die Vorschau"-Zusatz. Sie existiert überhaupt nur, damit der Editor eine benannte Stelle
hat, an der die Vorbereitungspflicht (`bereiteVorschauVor`) mit dem Zeichnen zusammenhängt.

**Deshalb prüft die Definition of Done die Identität, nicht den Determinismus.** „**Gleiche Eingabe
→ gleiches Bild.**" (TK 9.10.3, Punkt 5) gilt selbstverständlich auch hier – aber hergestellt wird
es in `zeichneSegment` (#117), und dort wird es auch geprüft. Ein Pixelvergleich in **dieser**
Testdatei prüfte fremden Code: Er schlüge fehl, wenn #117 kaputt ist, und bliebe grün, wenn diese
Datei heimlich ein zweites Canvas dazwischenschöbe – also genau falsch herum. Nachweisbar ist hier
nur, dass **kein zweiter Zeichenpfad** entsteht, und das zeigt die Identität des zurückgegebenen
Objekts.

**Warum `bereiteVorschauVor` alle Motive der Bibliothek lädt, nicht nur das der offenen Aktion.**
`holeMotiv` (#111) ist ein **synchroner** Nachschlag in einem vorbereiteten Bestand; ein nicht
vorbereitetes Motiv liefert `{ zustand: 'fehlt' }` und wird als Platzhalter gezeichnet. Würde je
Aktion einzeln vorbereitet, zeigte jeder Wechsel in der Bibliothek für einen Moment einen
Platzhalter – ununterscheidbar von einem echten Defekt, den die Oberfläche gerade melden soll
(TK 9.8.5). Die Bibliothek eines Projekts ist klein genug, dass das Vorbereiten einmalig geschehen
kann.

**`haengeVorschauEin` ist der einzige Ort, an dem die Anzeigegröße bestimmt wird.** Sie setzt
`style.width`, `style.maxWidth` und `style.aspectRatio` und überlässt die Skalierung dem Browser.
„Skalierung geschieht **nur** zur Darstellung (CSS)." (TK 9.10.3, Punkt 1)

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.** Wer den Aufruf still an eine abweichende Signatur anpasst,
macht aus einem Vertragsfehler einen unsichtbaren – und dieselbe Funktion existiert dann in zwei
Fassungen im Projekt.

**Der Ablauf von `bereiteVorschauVor`, verbindlich – die Reihenfolge ist Teil der Vorgabe:**

1. `await stelleSchriftenBereit()` (#110). Ohne Schriften wirft `zeichneSegment` sofort.
2. `await bereiteLogoVor(marke)` (#119). Ohne das Logo trägt **jedes** Segment an der festen
   Logo-Zone einen Platzhalter, und FA-11 wäre unerfüllbar.
3. Die Motiv-Einträge bilden: für **jede** Aktion mit `bildRef !== null`, deren
   `findeBildAsset(bildRef, assets)` ein Asset liefert, ein Eintrag
   `{ schluessel: aktion.bildRef, dateiname: asset.dateiname }`. Aktionen ohne Bild und Aktionen mit
   kaputtem Bild erzeugen **keinen** Eintrag – ihr Motiv ist ohnehin `{ zustand: 'fehlt' }`, und ein
   Ladeversuch auf eine nicht vorhandene Datei wäre eine `media://`-Anfrage ins Leere.
   **Doppelte Schlüssel werden vorher entfernt:** Mehrere Aktionen dürfen dasselbe Bild
   referenzieren, und ein zweites Laden derselben Datei ist reine Arbeit ohne Wirkung.
4. `await bereiteMotiveVor(projektId, eintraege)` (#111).

Die drei `await` liegen **vor** dem Zeichnen, nicht darin. Genau deshalb bleibt `zeichneVorschau`
synchron, und „**Gleiche Eingabe → gleiches Bild.**" (TK 9.10.3, Punkt 5) bleibt prüfbar.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projektId` | Projekt, aus dessen Medienordner die Motive kommen | nicht leer; wird unverändert an `bereiteMotiveVor` gereicht |
| `aktionen` | `Project.aktionen` – **alle** Aktionen, nicht nur die offene | leeres Array ist gültig: dann werden nur Schriften und Logo vorbereitet |
| `assets` | `Project.assets` zum Auflösen von `bildRef` → `dateiname` | leeres Array ist gültig; dann entstehen keine Motiv-Einträge |
| `marke` | die gebündelte, read-only `Marke` | Pflicht; Herkunft `leseMarke` (#29), durchgereicht vom Bildschirm |
| `aktion`, `vorlage` | Eingang des Zeichnens | werden **unverändert** an `zeichneSegment` gereicht |
| `ziel` | das Anzeigeelement | vorhandener Inhalt wird ersetzt, nicht ergänzt |

Ausgang bei Erfolg: `bereiteVorschauVor` löst auf, sobald alles bereitsteht; `zeichneVorschau`
liefert das `SegmentBild` von `zeichneSegment`; `haengeVorschauEin` gibt nichts zurück.
Ausgang bei Fehler: **keine** `Ergebnis<T>`-Hülle – diese Datei überquert keine IPC-Grenze.
`zeichneSegment` wirft, wenn die Schriften fehlen; dieser `Error` wird **nicht** gefangen und
**nicht** in einen Ersatz umgewandelt (s. Fehlerpfade).

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**`template-canvas` ist die einzige Pixelquelle:** die Live-Vorschau ist **pixelgleich** zur
  Vorschau (P5) und zum finalen Segment-PNG (Variante A). Es gibt **keinen** zweiten
  Gestaltungs-/Renderpfad." (TK 9.8.4)
- „**Invariante:** Es gibt **keinen zweiten Zeichenpfad.** Anzeige und Export stammen immer aus
  **demselben** Aufruf – sonst driften Vorschau und Endvideo auseinander." (TK 9.10.1)
- „**Live-Vorschau:** `template-canvas` rendert (Aktion + Vorlage + Marke) → dieselben Pixel, die
  später als Segment-PNG in den finalen Render gehen." (TK 9.8.3)
- „**Immer bei der nativen Fläche der Vorlagenart zeichnen** (1920×1080 bzw. 1920×162, s. 9.10.2);
  Skalierung geschieht **nur** zur Darstellung (CSS). **Nie** kleiner rendern und hochskalieren –
  das erzeugt ein unscharfes Segment bzw. Band im Endvideo." (TK 9.10.3, Punkt 1)
- „**`devicePixelRatio` wird ignoriert** – feste Canvas-Backing-Größe entsprechend der Vorlagenart.
  Das Ergebnis darf **nicht** vom Gerät abhängen (HiDPI-Laptop = gleiches Bild)." (TK 9.10.3,
  Punkt 2)
- „**Schriften sind vor dem Zeichnen geladen.** Der Aufruf wartet, bis alle benötigten Fonts
  einsatzbereit sind. Zeichnen mit Fallback-Schrift ist ein **Vertragsbruch** (lautloser Drift
  zwischen Vorschau und Endvideo)." (TK 9.10.3, Punkt 3)
- „**Bilder sind vor dem Zeichnen dekodiert.** Der Aufruf wartet auf das Motiv (geladen über
  `media://`, 9.5.7) – sonst entsteht ein Segment ohne Bild." (TK 9.10.3, Punkt 4)
- „**Gleiche Eingabe → gleiches Bild.** Keine Zeit-, Zufalls- oder Zustandsabhängigkeit (keine
  Animation, kein Datum, kein `Math.random`)." (TK 9.10.3, Punkt 5)
- „**Kein persistenter Cache** (Modellierungs-Entscheidung 4); innerhalb einer Sitzung darf ein
  bereits gezeichnetes Canvas zur *Anzeige* weiterverwendet werden." (TK 9.10.3, Punkt 6)
- „Ist `aktion.bildRef` ein `fehlt`-Asset (9.4.7), zeichnet `template-canvas` einen **Platzhalter**
  an der Bildzone, damit der `action-editor` den Defekt zeigen kann (9.8.5). **Ein Segment mit
  Platzhalter darf nie in den finalen Render gelangen** – diese Sperre sitzt im `composer`
  (Reparatur-Modus 9.7.5), nicht hier." (TK 9.10.7) – auch **nicht** hier.
- „Kennt **keine** Dateisystem-Pfade – Motive kommen ausschließlich über `media://` (9.5.7)."
  (TK 9.10.8)

## Fehlerpfade (vollständig)
| Situation | Verhalten |
|---|---|
| `stelleSchriftenBereit` lehnt ab (Font-Datei fehlt im Bundle) | Die Ablehnung wird **weitergereicht**; `bereiteVorschauVor` lehnt ab. **Kein** Zeichnen mit Fallback-Schrift, **kein** stilles Weitermachen. Der Bildschirm zeigt statt der Vorschau eine Meldung |
| `zeichneVorschau` wird gerufen, ohne dass vorbereitet wurde | `zeichneSegment` wirft; der `Error` wird **nicht** gefangen. Ein Ersatzbild wäre ein zweiter Zeichenpfad |
| `bereiteLogoVor` findet die Logodatei nicht | Kein Fehler (#119 wirft dabei nie); jedes Segment zeigt an der Logo-Zone den Platzhalter. Der Defekt ist damit **sichtbar** und nicht verschleiert |
| `aktion.bildRef` zeigt auf ein `fehlt`-Asset oder eine unbekannte ID | Kein Fehler: kein Motiv-Eintrag, `holeMotiv` liefert `{ zustand: 'fehlt' }`, die Bildzone zeichnet den Platzhalter (TK 9.10.7). Die Kennzeichnung als „kaputt" macht M5-16/M5-22, **nicht** diese Datei |
| `aktionen` ist leer | Kein Fehler; Schriften und Logo werden trotzdem vorbereitet |

Es gibt in dieser Datei **keine** IPC-Fehlercodes, weil sie keine IPC-Grenze überquert
(TK 9.10.8: „Ist **kein** Auftrag der Queue – eine reine, synchron aufrufbare Renderer-Funktion.").

## Nicht selbst entscheiden – STOPP und fragen
- **Verbot – kein zweiter Zeichenpfad, in keiner Form.** Kein eigenes `getContext('2d')`, kein
  `drawImage` außerhalb von `template-canvas`, kein Übermalen des zurückgegebenen Canvas, kein
  Zuschneiden, keine Vorschau-Markierung, kein Raster darüber. Was der Nutzer sieht, muss das sein,
  was gerendert wird.
- **Verbot – die Canvas-Maße nicht anfassen.** `canvas.width` und `canvas.height` werden **nie**
  gesetzt. Das Setzen leert ein Canvas vollständig (#118 prüft genau darauf); ein danach als PNG
  exportiertes Bild wäre eine leere Fläche.
- **Verbot – `devicePixelRatio` nicht lesen.** Weder für die Backing-Größe noch für die Anzeige.
- **Verbot – kein `alsPng`.** Der PNG-Export (#118) gehört zum Render-Weg, nicht zur Vorschau. Diese
  Datei erzeugt **keine** Bytes.
- **Verbot – keine Animation, kein Datum, kein Zufall.** Kein Blinken, kein „aktualisiert um …",
  keine zufällige Beispielfarbe.
- **Verbot – keinen eigenen Motiv-Bestand.** Der Bestand liegt in #111; ein zweiter hier würde nach
  einem Import veraltete Bilder zeigen.
- **Verbot – weder Projektwechsel noch Importabschluss behandeln.** `leereMotivBestand()` wird laut
  #111 „bei jedem **Projektwechsel** und nach **jedem Import**" gerufen – **beides** gehört
  nicht hierher, sondern zu der Stelle, die den Wechsel bzw. den Auftragsabschluss überhaupt
  bemerkt: **M5-35** hält die Zeichenvoraussetzungen des Fensters vor (dort steht dieser Aufruf
  ausgeschrieben), und wer den Abschluss eines Imports meldet, ist die `app-shell` (M7). Der Bestand
  in #111 ist **modulglobal** – einmal geleert genügt für alle Zeichner. Der zweite Fall ist der leicht
  übersehene: Nach einem Import unter gleichem Dateinamen lieferte ein stehengebliebener Bestand
  weiter das **alte** Bild. Zwei Stellen, die den Bestand leeren, machen unauffindbar, warum ein
  Bild verschwunden ist – und eine, die es nie tut, zeigt lautlos veraltete Motive.
- **Verbot – die Vorlage nicht ersetzen.** Ist `aktion.vorlagenId` unbekannt, wird **nicht** auf
  eine eingebaute Vorlage zurückgefallen; die Auswahl regelt M5-18. Diese Datei bekommt die Vorlage
  als Parameter und verwendet genau sie.
