### Issue M5-19: [action-editor] Bild zuweisen – aus der Bibliothek wählen oder neu importieren

## Ziel (in einem Satz)
Der Nutzer weist einer Aktion ein Motiv zu, indem er ein vorhandenes Bild-Asset des Projekts wählt
oder neue Dateien importiert – in beiden Fällen hält die Aktion am Ende nur eine **Asset-ID**, nie
eine Kopie des Bildes.

## Modul & Datei
- Modul: `action-editor` (Renderer)
- Datei: `src/renderer/action-editor/bild-zuweisen.ts`
- Vertrag: Technisches Konzept **9.8.3** (Bildzuweisung), **9.8.4** (Bild = Referenz),
  **9.4.3** (`öffneMedienDialog`, `ImportRequest`), **9.3.4** (die Warteschlange ist die einzige
  Tür), **9.1.1** (IPC-Konventionen) – Quelle der Wahrheit
- Prozess/Speicher: P2; stößt P1 (Import) über die Warteschlange P6 an; **kein** Dateisystem,
  **kein** direkter Aufruf von `importMedium`

## Warum das im Gesamtsystem wichtig ist
Hier treffen zwei Wege auf **ein** Ergebnis: Ob das Bild schon im Projekt lag oder eben erst
importiert wurde – am Ende steht in `Aktion.bildRef` eine Asset-ID, sonst nichts. „Das Bild ist stets
eine **Referenz**." (TK 9.8.3). Würde stattdessen ein Pfad, ein Dateiname oder gar der Bildinhalt in
der Aktion landen, bräche die Löschsemantik: Das Asset „bleibt projektweit und wird beim Löschen der
Aktion **nicht** angetastet" (TK 9.8.4) – das setzt voraus, dass Aktion und Asset zwei getrennte
Datensätze sind, die nur über eine ID verbunden sind.

Zwei weitere lokale Fehlentscheidungen wären teuer. **Der Import darf nicht direkt aufgerufen
werden.** `importMedium` ist ein Auftrag; der einzige Weg dorthin ist `reiheEin` (TK 9.3.4). Wer die
Datei „schnell selbst" kopiert oder am Torwächter vorbei importiert, hebelt die serielle Freigabe
aus (NFA-09) – auf Windows endet das im günstigen Fall in einem `EBUSY`, im ungünstigen in einer
halb geschriebenen Mediendatei mitten in einem laufenden Render. **Und die Mehrfachauswahl gehört
aufgefächert:** Ein Sammel-Auftrag über fünf Dateien wäre unteilbar – schlägt die dritte fehl, ist
nicht wiederholbar, was schon geklappt hat (FA-17).

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/action-editor/bild-zuweisen.ts
import type { Aktion } from '../../shared/contracts/aktion'
import type { Asset } from '../../shared/contracts/asset'
import type { Ergebnis } from '../../shared/contracts/ergebnis'

/** Die Bilder des Projekts, die als Motiv taugen: typ === 'bild' UND zustand === 'ok'.
 *  Reihenfolge = Reihenfolge in Project.assets, ohne Sortierung. */
export function waehlbareBilder(assets: Asset[]): Asset[]

/** Setzt bildRef auf eine bereits vorhandene Asset-ID. Schreibt über M5-17.
 *  `assets` ist Project.assets – ohne den Bestand kann diese Funktion die Zuweisung nicht prüfen. */
export async function weiseBildZu(
  aktionId: string,
  assetId: string,
  assets: readonly Asset[],
): Promise<Ergebnis<Aktion>>

/** Entfernt das Bild: bildRef = null. Die Aktion bleibt gültig (Bild optional, Titel Pflicht). */
export async function entferneBild(aktionId: string): Promise<Ergebnis<Aktion>>

/** Öffnet den Medien-Dialog und reiht für JEDEN gewählten Pfad einen EIGENEN Import-Auftrag ein.
 *  Setzt bildRef NICHT – die neue Asset-ID entsteht erst, wenn der Auftrag durchgelaufen ist.
 *  `abbruchGrund` ist der Fehlercode des Aufrufs, an dem die Schleife stehengeblieben ist, sonst
 *  null. Ein Teilerfolg ist ein ERFOLG mit Teilmenge, kein Fehler. */
export async function starteBildImport(
  projektId: string,
): Promise<Ergebnis<{ auftragIds: string[]; abbruchGrund: string | null }>>
```

**`starteBildImport` weist kein Bild zu – und das ist kein Versehen.** Der Import ist ein
**Auftrag**: Der Aufruf antwortet sofort mit der `auftragId`, das fachliche Ergebnis (der fertige
`Asset`) reist über den Auftrags-Zustand (TK 9.1.1, Punkt 1; TK 9.4.3). Eine Funktion, die „importiert
und danach zuweist", müsste auf den Auftrag warten – und würde damit die Oberfläche für die Dauer des
Imports blockieren, also genau das, wofür die Warteschlange gebaut wurde. Der Ablauf ist deshalb
zweistufig: erst `starteBildImport`, später – wenn das neue Asset in `Project.assets` auftaucht –
`weiseBildZu(aktionId, neueAssetId, assets)`. **Wodurch der Editor davon erfährt, ist entschieden;
es liegt nur nicht in dieser Datei – s. den ersten Punkt im STOPP-Block.**

**ENTSCHIEDEN – `weiseBildZu` bekommt den Asset-Bestand als dritten Parameter.** Diese Funktion muss
prüfen, dass `assetId` zu einem Bild-Asset mit `zustand: 'ok'` gehört (s. Fehlerpfade) – ohne
`Project.assets` **kann** sie das nicht. Ein modul-eigener Zwischenspeicher schiede aus (zweite
Wahrheit über den Projektzustand), und den Bestand über IPC nachzuholen wäre ein zweiter Leseweg
neben dem gehaltenen Projektzustand. Der Bestand kommt deshalb als Parameter herein – genau wie bei
`waehlbareBilder(assets)` in derselben Datei und bei `betroffeneStellen(aktionId, liste)` in M5-22.
`readonly`, weil diese Datei den Bestand **nur liest**.

**Abbruch im Dialog ist Erfolg mit leerer Liste.** „| Nutzer bricht ab | `ok: true` mit
`pfade = []` – Abbruch ist **kein** Fehler |" (TK 9.4.3). `starteBildImport` gibt dann
`{ ok: true, wert: { auftragIds: [], abbruchGrund: null } }` zurück und reiht **nichts** ein.

**ENTSCHIEDEN – ein Teilerfolg reist NICHT durch `fehler.daten`.** Bricht die Einreih-Schleife nach
dem ersten erfolgreichen Auftrag ab, ist das Ergebnis `ok: true` mit der bis dahin vergebenen
Teilmenge und dem gesetzten `abbruchGrund`. Der naheliegende Gegenentwurf – `ok: false` und die
schon vergebenen IDs in `fehler.daten` – verstößt gegen TK 9.1.1: Die Form von `daten` ist „**je
Fehlercode festgelegt und typisiert** (dokumentiert dort, wo der Code vergeben wird: 9.4.9, 9.6.4,
9.12.1); es ist **kein Freitext-Anhang**". Für einen **generischen** Code gibt es keine solche
Festlegung, und diese Datei dürfte sie auch gar nicht treffen – sie vergibt den Code nicht, sie
reicht ihn durch. Sachlich ist der Fall ohnehin kein Fehler: Die eingereihten Aufträge **laufen**,
sie sind in der Warteschlangen-Leiste sichtbar, und zurückgerollt wird nichts („Aufträge sind daher
grundsätzlich nicht undo-fähig", TK 9.13.1). Die Oberfläche zeigt beides: die Zahl der gestarteten
Importe **und** den Abbruchgrund.

**Warum `entferneBild` eine eigene Funktion ist und nicht `weiseBildZu(aktionId, '')`.** Ein leerer
String wäre eine zweite Schreibweise für „kein Bild" neben `null`, und irgendein Aufrufer prüft
später die falsche. `bildRef` ist `string | null` (#14) – es gibt genau **einen** Wert für „kein
Bild".

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.** Wer den Aufruf still an eine abweichende Signatur anpasst,
macht aus einem Vertragsfehler einen unsichtbaren – und dieselbe Funktion existiert dann in zwei
Fassungen im Projekt.

**Der Ablauf von `starteBildImport`, verbindlich:**

1. `rufeAuf<{ pfade: string[] }>(KANAELE.media.oeffneMedienDialog)` aufrufen – **ohne** Nutzlast.
2. Antwortet der Dialog mit `ok: false`, wird die Antwort **unverändert** zurückgegeben; es wird
   **nichts** eingereiht.
3. Ist `pfade` leer (Abbruch), wird `{ ok: true, wert: { auftragIds: [], abbruchGrund: null } }`
   zurückgegeben; es wird **nichts** eingereiht.
4. Sonst **je Pfad ein eigener Auftrag**, in der Reihenfolge der Pfade:
   `rufeAuf<{ auftragId: string }>(KANAELE.queue.reiheEin, { art: 'import', payload: { projektId, quellPfad } })`.
   Das entspricht der Festlegung aus #81: „Sie reiht für **jeden** zurückgegebenen Pfad einen
   eigenen Auftrag ein (`reiheEin('import', …)` je Pfad), weil die Warteschlange sie dann einzeln und
   sichtbar abarbeitet und jeder Fehlschlag einzeln wiederholbar ist (FA-17); ein Sammel-Auftrag wäre
   unteilbar."
5. **Ein Fehlschlag beim Einreihen bricht die Schleife ab.** Weitere Pfade werden **nicht** mehr
   versucht. Was dann zurückkommt, hängt daran, ob schon etwas läuft:
   - **Noch kein Auftrag vergeben** (der **erste** Pfad scheitert): Die Antwort des
     fehlgeschlagenen `rufeAuf` wird **unverändert** zurückgegeben – `ok: false`, mit dem Code, den
     der Aufruf geliefert hat. Es ist nichts geschehen, was zu berichten wäre.
   - **Mindestens ein Auftrag vergeben:** `{ ok: true, wert: { auftragIds, abbruchGrund } }`, wobei
     `auftragIds` die bis dahin vergebenen IDs in Pfadreihenfolge enthält und `abbruchGrund` der
     Fehlercode des gescheiterten Aufrufs ist. Diese Aufträge **laufen bereits** – sie zu
     verschweigen hieße dem Nutzer eine Wirkung zu verheimlichen, die er im Warteschlangen-Panel
     ohnehin sieht. Ein Zurückrollen ist ausgeschlossen: „Aufträge sind daher grundsätzlich nicht
     undo-fähig" (TK 9.13.1).
6. Sonst `{ ok: true, wert: { auftragIds, abbruchGrund: null } }` – die IDs in derselben Reihenfolge
   wie die Pfade.

**Der Dialog ist eine Bequemlichkeit, keine Garantie.** Sein Formatfilter kann umgangen werden
(#81); ob eine gewählte Datei überhaupt ein unterstütztes Bild ist, entscheidet die
Format-Prüfung beim Import (#80). Diese Datei prüft die Pfade **nicht** und filtert sie **nicht** –
sie reicht durch. Insbesondere wird **nicht** anhand der Dateiendung vorsortiert: Das wäre eine
zweite, schwächere Fassung der `FORMAT_WHITELIST`.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `assets` | `Project.assets` des geladenen Projekts – für `waehlbareBilder` **und** für die Prüfung in `weiseBildZu` | leeres Array ist gültig; ergibt eine leere Auswahl, und **jede** Zuweisung wird abgelehnt |
| `aktionId` | ID der zu ändernden Aktion | nicht leer; die Existenzprüfung macht der Main (`nicht_gefunden`) |
| `assetId` | ID des zuzuweisenden Bild-Assets | nicht leer; muss in `waehlbareBilder(assets)` vorkommen (s. Fehlerpfade) |
| `projektId` | Ziel-Projekt des Imports | nicht leer; wird **unverändert** in `ImportRequest.projektId` gesetzt |

Ausgang bei Erfolg: `weiseBildZu`/`entferneBild` liefern die vom Main zurückgegebene, aktualisierte
`Aktion`; `starteBildImport` liefert die eingereihten `auftragIds` (leer bei Abbruch) und
`abbruchGrund` (`null`, wenn alle Pfade eingereiht wurden).
Ausgang bei Fehler: `ungueltige_eingabe`, `nicht_gefunden`, `unbekannter_fehler` (generisch,
TK 9.1.1 Punkt 3). Diese Datei erzeugt **keinen** eigenen Fehlercode; alle Codes kommen vom Main
bzw. von M5-17.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „**Bildzuweisung:** aus der Medien-Bibliothek **wählen** (Asset-ID) **oder** neu **importieren**
  (media-service → dann Asset-ID). Das Bild ist stets eine **Referenz**." (TK 9.8.3)
- „**Bild = Referenz, nie Kopie:** die Aktion hält nur eine Asset-ID; das Asset bleibt projektweit
  und wird beim Löschen der Aktion **nicht** angetastet (9.5.3)." (TK 9.8.4)
- „**Fix-Optionen:** Bild **neu verknüpfen/importieren** (media-service), durch ein **anderes
  ersetzen**, oder **entfernen** (eine Aktion ohne Bild ist gültig – Bild ist optional, Titel
  Pflicht)." (TK 9.8.5) – deshalb ist `entferneBild` eine reguläre Bedienhandlung und kein Notfall.
- „| Nutzer wählt Dateien | `pfade` = Array absoluter Quellpfade |" und „| Nutzer bricht ab |
  `ok: true` mit `pfade = []` – Abbruch ist **kein** Fehler |" (TK 9.4.3)
- „`reiheEin` antwortet also sofort mit `{ ok, auftragId }`; ob der Render gelang, kommt später über
  die Queue." (TK 9.1.1, Punkt 1) – dasselbe gilt für den Import: Der Rückgabewert sagt **nichts**
  über den Ausgang.
- „**Nur Instant-Aufrufe tragen die Hülle.** Auftragsartige Operationen (`import`, `loeschen`,
  `render`, `export`) werden **nicht** direkt aufgerufen; der Aufruf ist `reiheEin` →
  `Ergebnis<{ auftragId }>`, ihr Fach-Ergebnis reist über den **Auftrags-Zustand** (Punkt 1, 9.3)."
  (TK 9.1.1)
- „**Ist NICHT:** platziert Aktionen **nicht** in die Liste (`composer` [P3]); macht **keinen**
  finalen Render; **kein** Dateisystem/ffmpeg (alles über `ipc-client` an den Main)." (TK 9.8.1)
- „**Aufträge sind daher grundsätzlich nicht undo-fähig**; ein gelöschtes Medium muss neu importiert
  werden." (TK 9.13.1) – deshalb wird ein teilweise gelungenes Einreihen **nicht** zurückgenommen.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `assetId` ist leer | `ungueltige_eingabe` | **kein** IPC-Aufruf; Meldung nennt das Feld |
| `assetId` kommt in `assets` gar nicht vor | `ungueltige_eingabe` | **kein** IPC-Aufruf; Meldung nennt die unbekannte ID |
| `assetId` gehört zu einem Asset mit `zustand: 'fehlt'` | `ungueltige_eingabe` | **kein** IPC-Aufruf – ein bewusst zugewiesenes kaputtes Bild wäre ein Defekt auf Bestellung; Reparatur läuft über M5-22 |
| `assetId` gehört zu einem Asset mit `typ: 'video'` | `ungueltige_eingabe` | **kein** IPC-Aufruf; es steht nicht in `waehlbareBilder` (s. STOPP – die Einstufung **bestehender** Aktionen ist davon unberührt) |
| `aktionId` existiert im Projekt nicht | `nicht_gefunden` | Antwort von M5-17 unverändert durchgereicht |
| Dialog meldet `unbekannter_fehler` | `unbekannter_fehler` | unverändert durchgereicht; **nichts** eingereicht |
| Nutzer bricht den Dialog ab / wählt nichts | – | **kein Fehler**: `{ ok: true, wert: { auftragIds: [], abbruchGrund: null } }` |
| `reiheEin` lehnt den **ersten** Pfad ab | Code des Aufrufs | Antwort unverändert durchgereicht; es läuft nichts, es gibt nichts zu melden |
| `reiheEin` lehnt einen **späteren** Pfad ab | – | **kein Fehler**: `{ ok: true, wert: { auftragIds: <bis dahin>, abbruchGrund: <Code des Aufrufs> } }`; Schleife bricht ab; **kein** Zurückrollen |
| unerwartete Ausnahme | `unbekannter_fehler` | wird gefangen und als Hülle gemeldet, **kein** `throw` |

`assetId` gegen `waehlbareBilder(assets)` zu prüfen ist eine **Renderer**-Prüfung und damit eine
Bequemlichkeit; die verbindliche Prüfung bleibt eigentlich beim Main. Der Main lehnt eine unbekannte
Asset-ID allerdings **nicht** ab – `bearbeiteAktion` (#39) prüft `bildRef` nicht auf Existenz. Genau
deshalb steht der Bestand als dritter Parameter in der Signatur: Ohne diese Prüfung gäbe es
**nirgends** eine. Das ist bewusst so festgehalten und Teil des STOPP-Blocks unten.

## Nicht selbst entscheiden – STOPP und fragen
- **ENTSCHIEDEN – wie der Renderer erfährt, dass ein Import fertig ist (und warum trotzdem NICHT in
  dieser Datei).** Das fertige Asset steht in `Auftrag.ergebnis` und erreicht den Renderer über
  `queue:geaendert` bzw. `queue:holeStand` (TK 9.4.3, TK 9.1.1 Punkt 1). Der typisierte Empfangsweg
  dafür **existiert**: `abonniere<T>(kanal, hoerer): () => void` in **M5-32**
  (`src/renderer/ipc-client/ereignisse.ts`), das Gegenstück zu `rufeAuf` – der Kanal
  `queue:geaendert` ist von #71 angemeldet. Ein `window.api.on(…)` in dieser Datei bleibt damit
  verboten, aber nicht mangels Alternative, sondern weil es die Alternative gibt.
  **Wer abonniert, ist entschieden und ist nicht M5:** Der Hörer speist das fertige Asset in die
  gemeinsame Projekt-Sicht des Fensters (M5-02) ein; wer ihn beim Aufbau der Oberfläche registriert
  und die Abmeldung verwaltet, ist Sache der `app-shell` (M7). Diese Datei ruft **kein**
  `abonniere`, **kein** `holeStand` und endet bei den `auftragIds` – genau wie bisher, nur ist das
  jetzt eine Festlegung und keine Lücke.
- **Prüft irgendwer im MAIN, dass `bildRef` auf ein existierendes Asset zeigt?** `bearbeiteAktion`
  (#39) prüft nur `titel`; eine unbekannte oder fremde Asset-ID würde also unbeanstandet in D1
  landen und erst beim Zeichnen als Platzhalter auffallen. Ob die Prüfung (a) zusätzlich in den Main
  gehört, (b) die Renderer-Prüfung dieser Datei genügt, oder (c) sie bewusst entfällt, weil die
  Kaputt-Erkennung (M5-16/M5-22) den Fall ohnehin fängt, ist eine Vertragsentscheidung über zwei
  Prozesse hinweg. **Nicht raten** – melden.
  **Die Signatur oben ist davon nicht betroffen:** Diese Datei prüft gegen `waehlbareBilder(assets)`,
  und zwar in **jeder** Variante. Fällt die Entscheidung auf (a), kommt die Main-Prüfung **dazu**;
  sie ersetzt die hiesige nicht (eine Prüfung im Renderer erspart dem Nutzer den Umweg über einen
  IPC-Fehler). Baue die Main-Prüfung **nicht** selbst ein – #39 liegt außerhalb deines
  Dateibereichs.
- **Hier entschieden, dort offen: Videos als Aktions-Bild.** `waehlbareBilder` filtert Assets mit
  `typ: 'video'` heraus – das ist die konservative Wahl und in der Signatur festgeschrieben, weil
  `template-canvas` eine MP4-Datei nicht in eine Bildzone laden kann. Das TK schließt den Fall
  allerdings nirgends ausdrücklich aus (`bildRef` ist schlicht „Referenz auf eine Asset-ID",
  TK 9.8.2). Offen ist deshalb, wie eine **bereits bestehende** Aktion mit einem Video in `bildRef`
  einzustufen ist (kaputt oder heil) – diese Frage steht in M5-16 und **muss gemeinsam beantwortet
  werden**, sonst filtert die eine Datei, was die andere für heil hält. **Nicht einseitig
  entscheiden**, und die Filterregel hier auch nicht „passend" lockern.
- **Verbot – kein direkter Import.** `importMedium` wird **nicht** aufgerufen, keine Datei kopiert,
  kein `fs`, kein Pfad zusammengesetzt. Der einzige Weg ist `reiheEin` über `queue:reiheEin`.
- **Verbot – kein Warten auf den Auftrag.** Weder `await` auf einen Auftrags-Abschluss noch eine
  Abfrage-Schleife (`holeStand` in einer Schleife). Beides blockiert die Oberfläche für die Dauer
  des Imports und macht die Warteschlange sinnlos.
- **Verbot – die Pfade nicht anfassen.** Nicht sortieren, nicht deduplizieren, nicht normalisieren,
  nicht nach Endung filtern und **nicht** kürzen. Sie gehen unverändert in je einen `ImportRequest`.
- **Verbot – kein Kanal-Literal, kein `window.api`.** Die Kanalnamen stammen aus `KANAELE` (#25),
  der Aufruf aus `rufeAuf` (#24).
- **Verbot – kein zweiter Schreibweg.** `bildRef` wird ausschließlich über `speichereAktion`
  (M5-17) gesetzt; `project:bearbeiteAktion` wird in dieser Datei **nicht** direkt gerufen.
