### Issue M5-13: [composer] Durch die Reparatur führen

## Ziel (in einem Satz)
Statt eines stillen Abbruchs führt der `composer` den Nutzer **eins nach dem anderen** durch die
kaputten Stellen – erste Stelle hervorgehoben, „X von N behoben", nach jedem Fix automatisch zur
nächsten – und gibt den Render erst frei, wenn keine mehr übrig ist.

## Modul & Datei
- Modul: `composer` (Renderer)
- Datei: `src/renderer/composer/reparatur-fuehrung.ts` – **die einzige** Datei dieses Issues
- Vertrag: Technisches Konzept **9.7.5** (Reparatur-Modus), **9.7.4** (Render-Sperre),
  **9.14.2** (Fortschritt über den Reiterwechsel hinweg) – Quelle der Wahrheit
- Prozess/Speicher: P3; **kein** Speicherzugriff, **kein** IPC – reine Zustandsführung

## Warum das im Gesamtsystem wichtig ist
FA-19 ist ein **Soll**-Kriterium mit einem eigenen Akzeptanzkriterium (Nr. 7), und es geht nicht um
Bequemlichkeit: Der Nutzer ist Berufspraktikant, das Gerät hängt im Studio, und der einzige Weg zu
neuen Inhalten führt über einen Render, der Minuten dauert. Bricht er wortlos ab, weil irgendwo in
einer Liste von dreißig Elementen ein Medium fehlt, sucht der Nutzer von Hand. Führt die Anwendung
dagegen falsch – etwa mit einem Zähler, der zurückspringt, oder einer Freigabe, die zu früh kommt –,
ist das schlimmer als gar keine Führung: Er hält das Projekt für repariert und startet einen Render,
der wieder scheitert oder einen Platzhalter einbettet.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/composer/reparatur-fuehrung.ts
import type { Project } from '../../shared/contracts/project'
import type { KaputteStelle } from './kaputt-erkennung'

export interface ReparaturStand {
  aktiv: boolean
  offen: KaputteStelle[]      // in der Reihenfolge aus findeKaputteStellen
  gesamt: number              // N – wächst nie zurück, s. Ablauf 3
  behoben: number             // X = gesamt - offen.length
  zeigerIndex: number         // Position in `offen`, auf die die UI zeigt
  aktuelle: KaputteStelle | null   // offen[zeigerIndex] bzw. null, wenn nichts offen ist
}

/** Startet den geführten Modus für den aktuellen Projektstand. */
export function starteReparatur(projekt: Project): ReparaturStand

/** Rechnet nach jeder Änderung neu – aus DEM Projektstand, nicht aus vermuteten Wirkungen. */
export function aktualisiereReparatur(stand: ReparaturStand, projekt: Project): ReparaturStand

/** Manuelles Überspringen/Zurückgehen; klemmt auf den gültigen Bereich. */
export function springeZu(stand: ReparaturStand, index: number): ReparaturStand

/** Verlässt den geführten Modus, ohne etwas zu reparieren. Die Render-Sperre bleibt bestehen. */
export function beendeReparatur(stand: ReparaturStand): ReparaturStand

/** Die einzige Freigabe-Auskunft des composer. */
export function istRenderFreigegeben(projekt: Project): boolean
```

**Keine `Ergebnis<T>`-Hülle, kein `async`.** Diese Datei überquert keine IPC-Grenze und ruft keine
Store-Operation auf. Sie **führt** nur; die Reparaturen selbst führt M5-14 aus.

**Der Stand ist ein Wert, keine Klasse und kein Modul-Zustand.** Jede Funktion liefert einen
**neuen** `ReparaturStand`; keine mutiert die Eingabe. Grund: Der Stand muss **über einen
Reiterwechsel hinweg** überleben (TK 9.14.2) – er wird deshalb von der `app-shell` gehalten und
weitergereicht. Läge er als Modulvariable in dieser Datei, wäre er an die Lebensdauer des
Renderer-Moduls gebunden und die Zusage nicht mehr prüfbar.

**Fremde Funktionen und Typen, die du benutzt** – vollständig ausgeschrieben, du siehst die anderen
Issues nicht:

## Was der Vertrag verlangt – wörtlich

> - **Zurückleiten:** Beim Render-Versuch mit kaputten Elementen (oder auf Hinweis direkt nach dem
>   Öffnen) wird der Nutzer in den **Bearbeitungsmodus** zurückgeleitet – kein stiller Abbruch.
> - **Eins nach dem anderen:** Das erste kaputte Element wird hervorgehoben; ein Fortschritt zeigt
>   „**X von N behoben**". Ist es behoben, springt die UI **automatisch zum nächsten** kaputten
>   Element – bis keins mehr übrig ist.
> - **Freigabe:** Erst wenn **kein** kaputtes Element mehr existiert, ist der Render wieder frei. So
>   kann ein Lauf nicht an einem übersehenen kaputten Element scheitern.
>
> (TK 9.7.5)

> „Da Aktionen **referenzierbar** sind, behebt **ein** Fix an der Aktion **alle** Stellen, die sie
> verwenden – Listenelemente **und Band-Abschnitte**. Der Fortschritt „X von N" kann dadurch um mehr
> als eins sinken." (TK 9.7.5)

> „**Der geführte Reparatur-Modus wechselt den Reiter.** Führt die Reparatur eines Aktions-Bildes in
> den `action-editor` (9.7.5, 9.8.5), wechselt die Shell in den Reiter **Aktionen**, hebt die
> betroffene Aktion hervor und **kehrt danach zum Reiter Zusammenstellen zurück**, zur nächsten
> kaputten Stelle. Der Fortschritt „X von N behoben" bleibt dabei **über den Reiterwechsel hinweg**
> sichtbar – sonst verliert der Nutzer den Faden." (TK 9.14.2)

**Zur letzten Zusage die Abgrenzung, die du einhalten musst:** Der *Reiterwechsel* selbst gehört zur
`app-shell` (TK 9.14, Meilenstein **M7**), nicht in diese Datei. Diese Datei stellt nur sicher, dass
der Stand ein **weiterreichbarer Wert** ist, den die Shell über den Wechsel hinwegtragen kann – sie
wechselt keinen Reiter, sie kennt keine Reiter, und sie legt den Stand in keiner Modulvariablen ab.

**Der Ablauf, verbindlich:**

**1. `starteReparatur(projekt)`**
```
offen  = findeKaputteStellen(projekt)
gesamt = offen.length
→ { aktiv: offen.length > 0, offen, gesamt, behoben: 0, zeigerIndex: 0,
    aktuelle: offen[0] ?? null }
```
Ist die Liste leer, ist `aktiv: false` – es gibt nichts zu führen.

**2. `aktualisiereReparatur(stand, projekt)` rechnet aus dem Projekt neu, nie aus einer Vermutung.**
Es wird **nicht** versucht, die Wirkung eines Fixes vorherzusagen und eine Stelle „abzuhaken". Nur
so kann der Fortschritt um **mehr als eins** sinken, wenn ein Fix an einer Aktion drei Verwendungen
auf einmal behebt – und nur so verschwindet eine Stelle wieder, wenn der Nutzer die Datei
zurückkopiert hat (TK 9.4.7 setzt `zustand` dann auf `'ok'`).

**3. `gesamt` wächst, schrumpft aber nie.**
```
neuOffen = findeKaputteStellen(projekt)
gesamt   = Math.max(stand.gesamt, neuOffen.length + (stand.gesamt - stand.offen.length))
behoben  = gesamt - neuOffen.length
```
Begründung: Entfernt der Nutzer während der Reparatur ein Element und fügt ein anderes, ebenfalls
kaputtes hinzu, darf „X von N" **nicht rückwärts** laufen – ein Fortschrittsbalken, der springt,
zerstört das Vertrauen in die Zusage „erst wenn alles behoben ist". `N` steigt dann eben auf die
neue Gesamtzahl. `behoben` ist immer `≥ 0`, weil `gesamt ≥ neuOffen.length` gilt.

**4. Der Zeiger bleibt stehen – dadurch springt die UI automatisch weiter.**
`zeigerIndex` wird **nicht** zurückgesetzt und **nicht** hochgezählt: Wird die Stelle an Position
`i` behoben, rutscht die nächste offene Stelle genau auf Position `i` nach. Anschließend wird der
Zeiger auf `[0, neuOffen.length - 1]` geklemmt; ist `neuOffen` leer, gilt `zeigerIndex: 0` und
`aktuelle: null`. Das ist die einfachste Umsetzung von „springt die UI **automatisch zum nächsten**
kaputten Element" und braucht keinen Sonderfall dafür, dass ein Fix mehrere Stellen auf einmal
entfernt.

**5. `aktualisiereReparatur` schaltet `aktiv` NIE ein – nur aus.**
```
aktiv = stand.aktiv && neuOffen.length > 0
```
`aktiv` bleibt also `true`, solange etwas offen ist **und** der Modus schon lief, und wird `false`,
sobald `neuOffen` leer ist – das ist der Moment der Freigabe. Der Übergang `false → true` ist
**allein** `starteReparatur` vorbehalten. Begründung: Nach `beendeReparatur` steht der Stand auf
`aktiv: false`, während `offen` weiter gefüllt ist; würde `aktualisiereReparatur` aus
`neuOffen.length > 0` erneut `true` ableiten, risse die nächste beliebige Mutation den Nutzer in
den Modus zurück, den er gerade verlassen hat – bei jeder Änderung aufs Neue, bis alles repariert
ist. Der Verzicht kostet nichts: Wer den Modus wieder betreten will, ruft `starteReparatur`, und
die Render-Sperre hängt ohnehin **nicht** an `aktiv`, sondern an `istRenderFreigegeben` (Punkt 6).

`beendeReparatur` setzt `aktiv: false`, **ohne** an `gesamt`, `behoben` oder `offen` zu rühren: Der
Nutzer darf den geführten Modus verlassen, aber die Render-Sperre bleibt.

**6. `istRenderFreigegeben(projekt)` nimmt das Projekt, nicht den Stand.**
```
return findeKaputteStellen(projekt).length === 0
```
Das ist bewusst so: Eine Freigabe, die aus dem `ReparaturStand` abgeleitet wäre, ließe sich durch
`beendeReparatur` oder einen veralteten Stand aushebeln. Die Sperre muss aus **derselben Quelle**
kommen wie die Erkennung, sonst gibt es zwei Wahrheiten über „ist das Projekt renderbar" – und der
Vertrag verlangt: „Erst wenn **kein** kaputtes Element mehr existiert, ist der Render wieder frei."

**7. Entscheidungen, die bereits getroffen sind (nicht erneut abwägen):**
- **Überspringen ist erlaubt, Freigeben nicht.** `springeZu` lässt den Nutzer eine Stelle
  zurückstellen, an der er gerade nicht weiterkommt (etwa weil die Datei auf einem anderen Rechner
  liegt). Das ändert an der Sperre **nichts** – „eins nach dem anderen" ist eine Führung, kein
  Zwangsablauf.
- **Der Stand enthält keine Projektdaten.** Nur IDs und Indizes aus `KaputteStelle`. Eine Kopie von
  Elementen oder Aktionen im Stand wäre eine zweite Wahrheit neben dem `project-store`
  (TK 9.7.4: „`project-store` ist die Wahrheit").
- **Kein Timer, kein automatischer Neulauf.** `aktualisiereReparatur` wird vom Aufrufer nach jeder
  bestätigten Mutation gerufen – demselben Zeitpunkt, an dem die Ansicht ohnehin abgeglichen wird.
  Ein eigener Intervall-Lauf wäre ein zweiter, unsichtbarer Auslöser.
- **Keine Meldungstexte.** Diese Datei formuliert „X von N behoben" **nicht**; sie liefert die
  Zahlen `behoben` und `gesamt`. Text und Hervorhebung macht die Ansicht. Damit ist die Datei
  sprachfrei und vollständig ohne Browser prüfbar.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `projekt` | der **aktuelle**, bestätigte Projektstand | nur gelesen; nie verändert; muss der Stand nach der letzten Mutation sein |
| `stand` | der bisherige Führungsstand | nie mutiert; jede Funktion liefert eine neue Instanz |
| `index` | Zielposition für `springeZu` | geklemmt auf `[0, offen.length - 1]`; bei leerer Liste `0` |

Ausgang bei Erfolg: ein neuer `ReparaturStand` bzw. `boolean` bei `istRenderFreigegeben`.
Ausgang bei Fehler: **keiner**. Diese Funktionen werfen nie und liefern keine Fehlercodes.

## Nicht selbst entscheiden – STOPP und fragen
- **Die Freigabe niemals aus dem `ReparaturStand` ableiten.** `istRenderFreigegeben` fragt das
  Projekt. Ein `stand.offen.length === 0` aus einem veralteten oder beendeten Stand wäre eine
  zweite Wahrheit – und die eine, die den Render fälschlich freigibt.
- **`gesamt` darf nicht schrumpfen** und **`behoben` nicht sinken**. Ein rückwärts laufender
  Fortschritt sieht wie ein Fehler der Anwendung aus, auch wenn er rechnerisch stimmt.
- **Kein Reiterwechsel, keine Navigation, kein React-Zustand in dieser Datei.** Die `app-shell`
  (TK 9.14, M7) wechselt den Reiter; hier entsteht nur der Wert, den sie mitnimmt.
- **Kein Auto-Fix.** Diese Datei repariert nichts – auch nicht „das Offensichtliche" (etwa ein
  Element mit unbekannter Referenz stillschweigend entfernen). Die Optionen liegen bei M5-14, die
  Entscheidung beim Nutzer.
- **Kein Undo-Stapel** (TK 9.13 gehört nach M7).
- **Diese Datei entscheidet nicht, WANN der Modus startet.** TK 9.7.5 nennt zwei Auslöser („Beim
  Render-Versuch mit kaputten Elementen (oder auf Hinweis direkt nach dem Öffnen)"); beide rufen
  dieselbe Funktion `starteReparatur`. **Entschieden:** Die Datei ist auslöser-neutral – sie enthält
  **keine** Prüfung auf „gerade geöffnet", **keinen** Selbststart und **keinen** Timer. Wer den Modus
  wann anstößt, legen M5-02 (Projektzustand) und die `app-shell` (M7) fest.
