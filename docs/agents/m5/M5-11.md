### Issue M5-11: [composer] Wirkung der Abschnittsfolge anzeigen

## Ziel (in einem Satz)
Der Nutzer sieht **vor** dem Rendern, was sein Werbeband während des Videos tut: wie oft die
Abschnittsfolge durchläuft, ob sie sich wiederholt oder am Videoende abgeschnitten wird – berechnet
in derselben Frame-Rundung wie der Render.

## Modul & Datei
- Modul: `composer` (Renderer)
- Datei: `src/renderer/composer/einblendung-vorschau.ts` – **die einzige** Datei dieses Issues
- Vertrag: Technisches Konzept **9.2.8** (Zeitverhalten), **9.2.6** (Frame-Genauigkeit),
  **9.7.2** (Anzeige der Wirkung) – Quelle der Wahrheit
- Prozess/Speicher: P3; **kein** Speicherzugriff, **kein** IPC – reine Rechnung

## Warum das im Gesamtsystem wichtig ist
Ein Render kann bei einem langen Video **Minuten** dauern; danach zu entdecken, dass die letzte
Aktion des Bandes nie zu sehen war, kostet den Nutzer genau diese Minuten – und zwar jedes Mal aufs
Neue, weil er ohne Anzeige nicht weiß, welche Änderung hilft. TK 9.7.2 verlangt deshalb
ausdrücklich, dass der `composer` das **anzeigt**, „damit der Nutzer die Wirkung versteht, ohne
rendern zu müssen". Rechnete diese Datei in **rohen Sekunden** statt in Frames, wäre die Anzeige
knapp daneben: Bei einer Folge, die fast genau ins Video passt, entschiede ein einziger Frame
darüber, ob ein weiterer Durchlauf beginnt – die Anzeige sagte „passt genau", die Ausgabedatei
zeigte einen angeschnittenen Abschnitt.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/composer/einblendung-vorschau.ts

export type BandVerhalten = 'leer' | 'exakt' | 'wiederholt' | 'abgeschnitten'

export interface BandAblaufplan {
  verhalten: BandVerhalten
  videoFrames: number            // frame-gerundete Länge des GETRIMMTEN Videos
  folgeFrames: number            // frame-gerundete Summe aller Abschnitts-Dauern (ein Durchlauf)
  volleDurchlaeufe: number       // vollständig gezeigte Durchläufe der Folge
  restFrames: number             // Frames des angebrochenen letzten Durchlaufs (0 = keiner)
  angeschnittenerIndex: number | null   // Index des Abschnitts, der am Videoende abbricht
  abschnittsFrames: number[]     // frame-gerundete Dauer je Abschnitt, gleiche Reihenfolge
  nullFrameIndizes: number[]     // Indizes der Abschnitte mit abschnittsFrames[i] === 0
}

export function planeBandAblauf(
  trimStartSek: number,
  trimEndeSek: number,
  abschnitte: ReadonlyArray<{ aktionRef: string; dauer: number }>,
): BandAblaufplan
```

**Keine `Ergebnis<T>`-Hülle, kein `async`.** Diese Funktion überquert keine IPC-Grenze und ruft
nichts auf, was scheitern könnte. Sie ist eine reine Rechnung: gleiche Eingabe → gleiches Ergebnis.

**Frames sind die Wahrheit, Sekunden sind Anzeige.** Der Plan trägt bewusst **Frame-Zahlen** und
keine Sekunden: Sekunden entstehen erst in der Oberfläche durch `frames / RENDER_PROFILE.fps`. Zwei
Rundungsschritte hintereinander (erst auf Sekunden, dann auf Frames) ergeben ein anderes Ergebnis
als einer – und der Render rundet genau **einmal**.

**Fremde Werte, die du benutzt** – vollständig ausgeschrieben, du siehst die anderen Issues nicht:

```ts
// #18 – src/shared/contracts/render-profile.ts (Ausschnitt)
export const RENDER_PROFILE: RenderProfile
// u. a.: breite: 1920, hoehe: 1080, fps: 30
// ACHTUNG: das Feld heißt `hoehe` OHNE Umlaut. Gebraucht wird hier ausschließlich `fps`.

// #15 – src/shared/contracts/project.ts (Ausschnitt)
export interface Einblendung {
  bandVorlageId: string
  abschnitte: Array<{ aktionRef: string; dauer: number }>
}
export interface Listenelement {
  id: string; art: 'video' | 'bild' | 'segment'; ref: string
  dauer: number | null; trimStart: number | null; trimEnde: number | null
  einblendung: Einblendung | null
}
// Diese Datei nimmt trimStart/trimEnde und abschnitte als ZAHLEN entgegen, nicht das Element:
// so ist sie auch für einen unbestätigten Entwurf aus M5-10 nutzbar, der noch nicht im Projekt steht.
```

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.**

**Der Ablauf, verbindlich:**

**1. Die Frame-Rundung ist die des Renders – Zeichen für Zeichen dieselbe Regel** (TK 9.2.6,
wörtlich):

> „Beide Grenzen werden auf **dasselbe** 30-fps-Raster gerundet: `startFrame = round(trimStart × 30)`,
> `endFrame = round(trimEnde × 30)`; behalten werden die Frames `[startFrame, endFrame)`. Die
> effektive Elementdauer ist damit `(endFrame − startFrame) / 30` – **nicht** die rohe
> Sekundendifferenz. […] Dieselbe Rundungsregel gilt ausnahmslos (kein `floor` an einer, `round` an
> anderer Stelle) – sonst weicht die Dauer um einen Frame ab." (TK 9.2.6)

Also:
```
const fps = RENDER_PROFILE.fps
videoFrames = Math.round(trimEndeSek * fps) - Math.round(trimStartSek * fps)
abschnittsFrames[i] = Math.round(abschnitte[i].dauer * fps)
folgeFrames = Summe der abschnittsFrames
```
Die Zahl `30` wird **nicht** als Literal geschrieben – sie gehört dem Ausgabe-Profil und steht
bereits an genau einer Stelle (#18). Und es wird **nur einmal** gerundet: Es gibt keinen
Zwischenschritt in Sekunden.

Für die Abschnitts-Dauern gilt dieselbe Regel ausdrücklich (TK 9.2.8, wörtlich):

> „Abschnitts-Dauern unterliegen **derselben Frame-Rundung** wie alles andere (30 fps, 9.2.6) –
> sonst driftet das Band gegen das Video." (TK 9.2.8)

**2. Das Zeitverhalten** – die drei Fälle stehen wörtlich im Vertrag (TK 9.2.8):

> „Ist die Abschnitts-Folge **kürzer** als das (getrimmte) Video, **wiederholt** sie sich bis zum
> Videoende."
> „Ist sie **länger**, wird am Videoende **abgeschnitten**."
> „Die Elementdauer bestimmt **allein das Video** (Trim). Das Band verlängert oder verkürzt sie
> **nie**." (TK 9.2.8)

Daraus die Berechnung:
```
volleDurchlaeufe = Math.floor(videoFrames / folgeFrames)
restFrames       = videoFrames - volleDurchlaeufe * folgeFrames
```
und die Einstufung:

| Bedingung | `verhalten` | `angeschnittenerIndex` |
|---|---|---|
| `folgeFrames === 0` (keine Abschnitte oder alle auf 0 gerundet) | `'leer'` | `null` |
| `restFrames === 0` und `volleDurchlaeufe ≥ 1` | `'exakt'` | `null` |
| `volleDurchlaeufe ≥ 1` und `restFrames > 0` | `'wiederholt'` | Index des Abschnitts, in dem der Rest endet |
| `volleDurchlaeufe === 0` | `'abgeschnitten'` | Index des Abschnitts, in dem `videoFrames` endet |

`angeschnittenerIndex` ist der kleinste `i`, für den die kumulierte Summe
`abschnittsFrames[0..i]` **größer** als `restFrames` ist (bzw. größer als `videoFrames`, wenn
`volleDurchlaeufe === 0`). Genau dieser Abschnitt wird in der fertigen Datei **nicht** zu Ende
gezeigt – ihn zu benennen ist der eigentliche Zweck der Anzeige.

**2b. `nullFrameIndizes` benennt die Abschnitte, die im Render gar nicht erscheinen.**
```
nullFrameIndizes = alle i mit abschnittsFrames[i] === 0
```
Ein Abschnitt, dessen Dauer unter einem halben Frame liegt (< 1/60 s bei 30 fps) oder der als
`NaN`/unendlich/negativ als 0 Frames zählt (s. Punkt 4), rundet auf **0** Frames und ist in der
fertigen Datei **nicht vorhanden** – er verschwindet lautlos. Ohne dieses Feld hätte die Oberfläche
keine Möglichkeit, darauf hinzuweisen: `folgeFrames` und `volleDurchlaeufe` sähen völlig plausibel
aus, und der Nutzer entdeckte die fehlende Werbeaktion erst in der Ausgabedatei. Genau das ist der
Zweck dieser Anzeige („damit der Nutzer die Wirkung versteht, ohne rendern zu müssen", TK 9.7.2).
Das Feld ist **immer** vorhanden – ein leeres Array, wenn kein Abschnitt betroffen ist. Bei
`verhalten: 'leer'` sind das zwei verschiedene Lagen: Ist `abschnitte` leer, ist auch
`nullFrameIndizes` leer (es gibt keine Indizes); runden dagegen **alle** Abschnitte auf 0, stehen
**alle** Indizes darin. Diese Datei **wertet** das nur aus; sie ändert nichts, schlägt nichts vor
und stuft es nicht als Fehler ein (s. Punkt 4: Anzeige, keine Prüfstelle).

**3. Der Fall `folgeFrames === 0` ist ein eigener Zweig, keine Division.** Ohne ihn ergäbe
`videoFrames / 0` `Infinity`, `Math.floor(Infinity)` bliebe `Infinity`, und die Anzeige zeigte
„unendlich viele Durchläufe". Bei `'leer'` gilt: `volleDurchlaeufe = 0`, `restFrames = 0`,
`angeschnittenerIndex = null`. Dieser Fall tritt real auf – ein Entwurf aus M5-10, in dem noch kein
Abschnitt steht, und ein Abschnitt mit einer Dauer unter einem halben Frame (< 1/60 s), der auf 0
gerundet wird.

**4. Entscheidungen, die bereits getroffen sind (nicht erneut abwägen):**
- **`volleDurchlaeufe` zählt nur *vollständige* Durchläufe.** Ein angebrochener zählt nicht mit; er
  steckt in `restFrames`. So kann die Oberfläche „3× vollständig, danach abgeschnitten bei Aktion 2"
  formulieren, ohne selbst zu rechnen.
- **`'exakt'` verlangt mindestens einen vollen Durchlauf.** Ein Video von 0 Frames Länge mit einer
  nicht leeren Folge ergibt `volleDurchlaeufe = 0` und `restFrames = 0` → `'abgeschnitten'` mit
  `angeschnittenerIndex = 0`. Das ist die ehrliche Aussage: Zu sehen ist nichts.
- **Negative oder nicht endliche Eingaben werden geklemmt, nicht geworfen.** `videoFrames` wird auf
  `≥ 0` geklemmt; ein `abschnitte[i].dauer`, das `NaN` oder unendlich ist, zählt als **0 Frames**.
  Begründung: Diese Funktion ist eine **Anzeige**; sie darf die Listendarstellung nicht abstürzen
  lassen. Die Gültigkeitsprüfung der Werte sitzt in M5-10 und im Main (TK 9.1.1 Punkt 6).
- **Diese Datei zeigt nichts an und rendert nichts.** Sie liefert Zahlen; die Formulierung des
  Satzes und die Balkendarstellung macht die Ansicht. Damit ist sie vollständig und ohne Browser
  prüfbar.
- **Die Frame-Formel ist dieselbe wie in `gesamtlaenge.ts` (M5-08) – bewusst zweimal, nicht
  versehentlich.** M5-08 rechnet mit `frameDauer(element: Listenelement): Ergebnis<number>` über
  **bestätigte** Listenelemente; diese Datei bekommt `trimStartSek`/`trimEndeSek` als **Zahlen**,
  damit sie auch einen noch nicht übernommenen Entwurf aus M5-10 bewerten kann. Beide müssen
  `Math.round(sekunden × RENDER_PROFILE.fps)` benutzen. **Weicht M5-08 davon ab, ist das ein
  Vertragsfehler: melden, nicht eigenmächtig angleichen** – zwei verschiedene Rundungen wären genau
  der Drift, den TK 9.2.6 ausschließt.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `trimStartSek` | Trim-Anfang des Videos in Sekunden | nicht endlich → als 0 behandelt |
| `trimEndeSek` | Trim-Ende des Videos in Sekunden | nicht endlich → als 0 behandelt; `videoFrames` wird auf `≥ 0` geklemmt |
| `abschnitte` | die Abschnittsfolge (bestätigt oder Entwurf) | `readonly`; leeres Array zulässig → `'leer'` |

Ausgang bei Erfolg: `BandAblaufplan` – immer, für jede Eingabe.
Ausgang bei Fehler: **keiner**. Diese Funktion wirft nie und liefert keine Fehlercodes.

## Nicht selbst entscheiden – STOPP und fragen
- **Nicht in Sekunden rechnen.** Kein Zwischenergebnis in Sekunden, keine Sekunden-Division, kein
  `toFixed`. Die einzige Rundung ist `Math.round(sekunden * RENDER_PROFILE.fps)` – genau einmal je
  Wert.
- **Die Rundungsrichtung nicht ändern.** `Math.round` steht wörtlich im Vertrag; `floor` oder `ceil`
  an irgendeiner Stelle bricht die Zusicherung, dass Anzeige und Ausgabedatei übereinstimmen.
- **Das Band verlängert die Elementdauer nicht.** Auch nicht „damit der letzte Abschnitt noch ganz
  zu sehen ist". Wer meint, ein Aufrunden auf ein Vielfaches der Folgenlänge sei freundlicher:
  **fragen** – es widerspricht TK 9.2.8 unmittelbar.
- **Keine Empfehlung, kein Autokorrektur-Vorschlag.** Diese Datei schlägt keine anderen Dauern vor
  und ändert nichts. Sie beschreibt nur, was passieren wird.
- **Keine zweite Kaputt-Erkennung.** Ob ein Abschnitt auf eine Aktion mit fehlendem Bild zeigt,
  entscheidet ausschließlich `kaputt-erkennung.ts` (M5-12). Diese Datei kennt `aktionRef` nur als
  undurchsichtige Zeichenkette.
