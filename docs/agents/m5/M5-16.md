### Issue M5-16: [action-editor] Aktions-Bibliothek des Projekts anzeigen und kaputte Aktionen kennzeichnen

## Ziel (in einem Satz)
Aus dem geladenen Projekt entsteht die anzeigbare Aktions-Bibliothek: alle Aktionen in
Bestandsreihenfolge, jede mit dem Kennzeichen, ob ihr Bild fehlt – damit der Nutzer einen Defekt
sieht, **bevor** er die Aktion in die Wiedergabeliste stellt.

## Modul & Datei
- Modul: `action-editor` (Renderer)
- Datei: `src/renderer/action-editor/bibliothek.ts`
- Vertrag: Technisches Konzept **9.8.1** (Rolle & Grenze), **9.8.5** (Kaputt-Handling),
  **9.4.4** (`Asset.zustand`), **9.11.3** (`Project`) – Quelle der Wahrheit
- Prozess/Speicher: P2; **kein** IPC, **kein** Dateisystem – reine Ableitung aus dem übergebenen
  Projektzustand

## Warum das im Gesamtsystem wichtig ist
Die Aktions-Bibliothek ist die Liste, aus der der `composer` seine Aktions-Segmente und seine
Band-Abschnitte zieht. Sie ist damit die **erste** Stelle, an der ein fehlendes Bild sichtbar werden
kann – und die billigste: Wird ein Defekt hier nicht gezeigt, merkt der Nutzer ihn erst beim
Render-Versuch, dann aber gleich an mehreren Listenelementen gleichzeitig (Aktionen sind
referenzierbar), und der geführte Reparatur-Modus (FA-19) muss ihn aus der Wiedergabeliste heraus
zurück in den `action-editor` schicken.

Zwei lokale Fehlentscheidungen sind teuer. **Erstens die Definition von „kaputt".** Wer nur auf
`zustand === 'fehlt'` prüft und den Fall „`bildRef` zeigt auf eine Asset-ID, die es im Projekt gar
nicht mehr gibt" übersieht, hält eine defekte Aktion für heil. `template-canvas` zeichnet in beiden
Fällen denselben Platzhalter (`holeMotiv` antwortet bei unbekanntem Schlüssel mit
`{ zustand: 'fehlt' }`, #111), und ein Segment mit Platzhalter darf nie in den finalen Render
(TK 9.10.7). **Zweitens die Reihenfolge:** Sortiert diese Datei die Bibliothek um, sieht der Nutzer
eine andere Ordnung als die gespeicherte, und jede spätere Anzeige, die sich auf einen Index stützt,
zeigt auf die falsche Aktion.

## Signatur (verbindlich – NICHT ändern)
```ts
// src/renderer/action-editor/bibliothek.ts
import type { Aktion } from '../../shared/contracts/aktion'
import type { Asset } from '../../shared/contracts/asset'

export interface BibliothekEintrag {
  aktion: Aktion
  kaputt: boolean            // true = bildRef gesetzt, aber kein nutzbares Asset dahinter
  bildAsset: Asset | null    // das aufgelöste Bild-Asset; null bei bildRef === null ODER bei kaputt
}

/** Löst `bildRef` gegen die Medien-Bibliothek des Projekts auf.
 *  null bei `bildRef === null`, bei unbekannter ID und bei `zustand === 'fehlt'`. */
export function findeBildAsset(bildRef: string | null, assets: Asset[]): Asset | null

/** true, wenn `bildRef` gesetzt ist, aber `findeBildAsset` nichts Nutzbares liefert. */
export function istAktionKaputt(aktion: Aktion, assets: Asset[]): boolean

/** Die anzeigbare Bibliothek – in der Reihenfolge von `Project.aktionen`, ohne Sortierung. */
export function baueBibliothek(aktionen: Aktion[], assets: Asset[]): BibliothekEintrag[]

/** Anzahl der Einträge mit `kaputt === true` – für den Zähler in der Oberfläche. */
export function zaehleKaputte(eintraege: BibliothekEintrag[]): number
```

**Alle vier Funktionen sind rein und synchron.** Kein `async`, kein IPC, kein `Ergebnis<T>`: Diese
Datei überquert keine Prozessgrenze und kann nicht scheitern – sie leitet nur aus zwei Arrays ein
drittes ab. Eine Hülle hier wäre eine Fehlerbehandlung ohne Fehler.

**`bildAsset` ist bei `kaputt === true` bewusst `null`.** Wer ein `fehlt`-Asset trotzdem durchreicht,
lädt jeden Aufrufer dazu ein, dessen `dateiname` doch noch zu benutzen – und genau das erzeugt eine
`media://`-Anfrage auf eine Datei, die es nicht gibt. Die Anzeige braucht vom kaputten Fall nur die
Tatsache, nicht den Dateinamen.

### Fremde Typen, die du benutzt
Der umsetzende Agent sieht die anderen Issues **nicht**; deshalb hier vollständig ausgeschrieben:

```ts
// #14 – src/shared/contracts/aktion.ts
export interface Aktion {
  id: string
  titel: string                    // Pflicht
  beschreibung: string | null
  preis: string | null
  bildRef: string | null           // Referenz auf eine Asset-ID (NICHT eingebettet)
  cta: string | null
  standardDauer: number | null     // nur Vorgabe, s. TK 9.8.4
  vorlagenId: string
  akzentfarbe: string              // Rollen-Verweis in die Markenpalette, kein Hex
}

// #13 – src/shared/contracts/asset.ts
export interface Asset {
  id: string                                   // UUID
  typ: 'video' | 'bild'
  dateiname: string                             // "<uuid>.<ext_kleingeschrieben>", OHNE Verzeichnisanteil
  originalname: string                          // nur für UI-Anzeige
  maße: { breite: number; höhe: number }        // Display-Maße, Pixel, ganzzahlig
  dauer: number | null                          // Sekunden, 3 Nachkommastellen (Video); null (Bild)
  importdatum: string                           // ISO-8601 UTC
  zustand: 'ok' | 'fehlt'
}

// #15 – src/shared/contracts/project.ts (Ausschnitt – WOHER die beiden Arrays stammen)
export interface Project {
  assets: Asset[]                 // Medien-Bibliothek des Projekts
  aktionen: Aktion[]              // Aktions-Bibliothek des Projekts
  // …
}
```

**Weicht die tatsächliche Signatur von der hier ausgeschriebenen ab, ist das ein Vertragsfehler:
melden und NICHT eigenmächtig anpassen.** Wer den Zugriff still an eine abweichende Fassung anpasst,
macht aus einem Vertragsfehler einen unsichtbaren.

**Woher `aktionen` und `assets` kommen:** aus dem gehaltenen Projektzustand des Renderers (M5-02).
Diese Datei **holt** ihn nicht selbst und hält **keine** eigene Kopie – sonst gäbe es eine zweite
Wahrheit über den Projektzustand neben dem `project-store`, und die beiden liefen nach der ersten
Mutation auseinander. Sie bekommt die Arrays als Parameter und wird nach jeder Änderung **neu**
aufgerufen.

## Eingang → Ausgang
| Eingang | Bedeutung | Grenzen/Validierung |
|---|---|---|
| `aktionen` | `Project.aktionen`, die Aktions-Bibliothek des Projekts | leeres Array ist gültig (neues Projekt) und ergibt eine leere Bibliothek |
| `assets` | `Project.assets`, die Medien-Bibliothek des Projekts | leeres Array ist gültig; dann ist **jede** Aktion mit gesetztem `bildRef` kaputt |
| `bildRef` | `Aktion.bildRef` | `null` erlaubt und ausdrücklich **kein** Defekt – „eine Aktion ohne Bild ist gültig" (TK 9.8.5) |

Ausgang bei Erfolg: `BibliothekEintrag[]` mit **genau so vielen** Einträgen wie `aktionen`, in
**derselben** Reihenfolge; `zaehleKaputte` liefert eine Zahl zwischen 0 und der Länge.
Ausgang bei Fehler: entfällt – die Funktionen können nicht scheitern und werfen nie.

## Verbindliche Invarianten (wörtlich – Verletzung = Issue nicht erfüllt)
- „Zeigt `bildRef` auf ein `fehlt`-Asset (media-service 9.4.7), wird die **Aktion** als kaputt
  markiert; die Live-Vorschau zeigt einen **Platzhalter** statt des Bildes." (TK 9.8.5)
- „**Fix-Optionen:** Bild **neu verknüpfen/importieren** (media-service), durch ein **anderes
  ersetzen**, oder **entfernen** (eine Aktion ohne Bild ist gültig – Bild ist optional, Titel
  Pflicht)." (TK 9.8.5) – daraus folgt für diese Datei: `bildRef === null` ist **niemals** `kaputt`.
- „**Bild = Referenz, nie Kopie:** die Aktion hält nur eine Asset-ID; das Asset bleibt projektweit
  und wird beim Löschen der Aktion **nicht** angetastet (9.5.3)." (TK 9.8.4)
- „**Assets und Aktionen sind projekt-eigen** (Modellierungs-Entscheidungen 2 + 3); ihre IDs sind
  nur **innerhalb** des Projekts eindeutig." (TK 9.11.3) – deshalb wird `bildRef` ausschließlich
  gegen die **übergebene** Asset-Liste aufgelöst, nie gegen einen globalen Bestand.
- „**Die Reihenfolge ist die Array-Reihenfolge von `liste`** – es gibt **kein** separates
  `position`-Feld. Zwei Quellen für dieselbe Information würden unweigerlich auseinanderlaufen."
  (TK 9.11.3) – dieselbe Regel gilt hier für `Project.aktionen`: **keine** Sortierung, **keine**
  Gruppierung.
- „**Ein Segment mit Platzhalter darf nie in den finalen Render gelangen**" (TK 9.10.7) – deshalb
  muss `kaputt` **jeden** Fall erfassen, in dem `template-canvas` einen Platzhalter zeichnen würde,
  nicht nur den Fall `zustand === 'fehlt'`.

**Entscheidung dieses Issues (kein TK-Zitat, aber verbindlich für die Umsetzung).** Das TK nennt in
9.8.5 nur den Fall „`bildRef` zeigt auf ein `fehlt`-Asset". Der Fall „`bildRef` zeigt auf eine
Asset-ID, die in `Project.assets` **gar nicht** vorkommt" wird hier **gleich** behandelt und zählt
ebenfalls als kaputt. Begründung: `template-canvas` unterscheidet die beiden Fälle nicht –
`holeMotiv(schluessel)` liefert bei unbekanntem Schlüssel `{ zustand: 'fehlt' }` (#111) – und beide
enden im Platzhalter. Würde nur der erste Fall gezählt, gäbe es eine Klasse von Aktionen, die als
heil gilt und trotzdem einen Platzhalter rendert; genau das soll der Reparatur-Modus ausschließen.

## Fehlerpfade (vollständig)
| Situation | Code | Verhalten |
|---|---|---|
| `bildRef === null` | – | `kaputt: false`, `bildAsset: null`. Kein Defekt, kein Hinweis in der Oberfläche |
| `bildRef` gesetzt, ID in `assets` nicht gefunden | – | `kaputt: true`, `bildAsset: null` |
| `bildRef` gesetzt, Asset gefunden, `zustand === 'fehlt'` | – | `kaputt: true`, `bildAsset: null` |
| `bildRef` gesetzt, Asset gefunden, `zustand === 'ok'`, aber `typ === 'video'` | – | s. „Nicht selbst entscheiden" – **nicht** eigenmächtig als kaputt oder als heil einstufen |
| `aktionen` oder `assets` leer | – | leeres bzw. vollständig kaputtes Ergebnis; **kein** Fehler, **kein** `throw` |

Es gibt in dieser Datei **keine** IPC-Fehlercodes, weil sie keine IPC-Grenze überquert.

## Nicht selbst entscheiden – STOPP und fragen
- **Zeigt `bildRef` auf ein Asset mit `typ: 'video'` – ist das kaputt?** Das TK verlangt für die
  Bindung `bild` ein Motiv (9.11.1), sagt aber nirgends, ob ein Video als Aktions-Bild ausgeschlossen
  ist; `Aktion.bildRef` ist schlicht „Referenz auf eine Asset-ID" (TK 9.8.2). Praktisch würde
  `template-canvas` eine MP4-Datei über `media://` in ein `<img>` laden und **scheitern** – der
  Nutzer sähe einen Platzhalter ohne erklärbaren Grund. Ob dieser Fall (a) hier als `kaputt` gilt,
  (b) bereits bei der Bildzuweisung (M5-19) unmöglich gemacht wird, oder (c) beides, ist eine
  Vertragsfrage über zwei Dateien hinweg. **Nicht raten** – bis zur Klärung diesen Fall wie
  `zustand === 'ok'` behandeln und melden.
- **Verbot – keine Sortierung, keine Gruppierung, keine Filterung.** Kein `sort` nach Titel, kein
  „kaputte zuerst", kein Ausblenden kaputter Aktionen. Die Oberfläche gestaltet die Darstellung;
  diese Datei liefert die Bestandsreihenfolge. Eine hier eingebaute Ordnung wäre eine zweite,
  unsichtbare Ordnung neben der gespeicherten.
- **Verbot – nichts reparieren.** Findet sich eine Aktion mit verwaistem `bildRef`, wird sie hier
  **weder** korrigiert **noch** ausgeblendet und `bildRef` **nicht** auf `null` gesetzt. Reparieren
  ist ausschließlich M5-22. Eine zweite Stelle, die dasselbe „nebenbei" tut, macht die Ursache eines
  Defekts unauffindbar – und würde eine Änderung an D1 ohne Auftrag des Nutzers vornehmen.
- **Verbot – kein eigener Projektzustand.** Kein Modul-Zustand, kein Zwischenspeicher, kein
  `rufeAuf`. Die Arrays kommen als Parameter; „**`project-store` ist die Wahrheit:** die Liste im
  composer ist nur eine Sicht" (TK 9.7.4).
- **Verbot – keine Pixel.** Diese Datei erzeugt **kein** Vorschaubild und ruft `zeichneSegment`
  (#117) **nicht** auf. Jede Pixeldarstellung einer Aktion kommt aus M5-21.
